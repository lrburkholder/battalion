# ADR-0002 — Enforce Write Scope Through Tool Binding

## Status

Accepted

## Date

2026-08-01

## Implementation status

Implemented in v1.
BTN-166 adds project containment checks at configuration, binding, and use time.

## Context

Battalion roles have different write authority. A central runtime guard is easy
to bypass accidentally if a new write path forgets to call it.

## Decision

Construct each node's write tools before role execution using only that node's
declared paths. A node is never given a tool capable of writing outside its
scope.

### BTN-166 containment amendment

Scope entries declare authority relative to the admitted project, never an
arbitrary filesystem location. The scope layer owns one reusable normalization
rule for directory and single-file declarations: interpret both separator
styles, reject anchored paths and parent traversal, resolve the project and
entry with native filesystem semantics, and require strict containment.
Windows drive-relative, alternate-drive, UNC/device, reserved-name, and path
alias forms are rejected on all hosts so portable configurations cannot acquire
different authority. No current role contract allows the project root itself.

Validate the full declaration before returning any tools, including inactive
phase entries. Application start/resume and worker launch also validate before
mutation; the graph validates before execution capture or model calls. Preserve
the original declarations through configuration and state serialization and
validate the saved Run authority again on resume. Invalid configuration raises
`WriteScopeMisconfigured` (translated to application `InvalidWriteScope`), with
no fallback, model correction, or new interrupt semantics.

Tools pin the validated canonical root and recheck it on use. A changed bound
directory, file, or ancestor that redirects authority is blocked through the
existing scope-violation audit path. Contained links are supported without
granting their original alias permission to redirect future writes. These path
checks do not provide an OS sandbox against a hostile process racing path
resolution and file opening, or against hard-link aliases. Future BTN-123
workspace isolation must reuse this containment invariant for its workspace
base; an isolated workspace must not broaden role authority.

## Rationale

Authority is structural when tools are bound. A missing capability is a stronger
boundary than a policy check that every caller must remember to perform.

## Consequences

- Out-of-scope write detection remains a defense-in-depth interrupt and audit
  signal.
- Tool construction is a security boundary and requires exact-scope tests.
- New write mechanisms must go through the same scoped binding path.
