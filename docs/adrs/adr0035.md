# ADR-0035 — Correct Pre-write Role-contract Violations In-run

## Status

Accepted

## Date

2026-08-29

## Implementation status

In progress by BTN-154.

## Context

RED and GREEN prompts state different artifact contracts, but a model can
return an otherwise parseable candidate that violates one of them.  The Driver
already detects this before calling its scoped write tools.  Treating that
safe, observable error as a generic infrastructure failure makes a simple
recoverable mistake terminal for the Run.

## Decision

A recoverable role-contract violation is a typed, pre-write invalid candidate,
separate from a write-scope or capability violation.  The shared execution
scaffold records the rejected candidate attempt, supplies deterministic
Battalion-authored correction context to the same role and phase, and performs
at most one automatic retry.  Every attempted role call consumes the normal
Run budget.

The rejected execution evidence records a reason code, bounded offending
paths, correction attempt number, no-mutation confirmation, and whether the
result was retried or escalated.  A successful corrected attempt remains a
successful Run attempt; it does not erase the prior evidence.

After the one retry is consumed, the existing human-interrupt route handles
the violation.  Actual scoped-write and other authority violations bypass this
mechanism and retain their stronger interrupt policy.

## Consequences

- The graph gains no semantic role or GREEN-specific loop.
- Execution evidence version `1.4` adds optional attempt disposition and
  role-contract evidence; earlier records remain readable.
- CLI and desktop presentation must show correction evidence as a visible
  nonblocking event rather than a successful first attempt.
