# ADR-0040 — Keep history search and analytics as rebuildable local projections

**Status:** Accepted  
**Date:** 2026-09-05  
**Implements:** BTN-44  
**Related:** RFC-0004, ADR-0014, ADR-0017, ADR-0018, ADR-0020, ADR-0024, BTN-24, BTN-32, BTN-33, BTN-35, BTN-42, BTN-54

## Context

RFC-0004 defines History and Analytics as operator-facing views over durable
Battalion evidence. BTN-44 requires cross-run search and descriptive
model-by-role analytics while preserving explicit unknown/incomparable evidence
and avoiding a hidden model score, automatic model router, or replacement
source of truth.

The canonical evidence already lives in Battalion-owned records such as
RunState, node executions, human actions, artifacts, verification evidence,
usage observations, and Intel repositories. Searching all of those stores on
every query would couple presentation behavior to persistence layout and become
increasingly expensive as project history grows. Persisting query-optimized
copies as if they were authoritative would create a second source of truth.

Projection schema evolution also raises a different problem from canonical
record migration. Because a projection can be reconstructed, retaining a chain
of migrations for derived data adds long-term complexity without preserving new
evidence. However, a human or external tool may deliberately modify a local
projection. Battalion must not silently destroy such changes even though those
changes do not become canonical evidence.

BTN-54 now provides the inference-identity evidence BTN-44 was waiting for.
Execution-record schema 1.8 keeps the compatibility/display `model` field while
adding independently typed `requested_model`, `response_model`, configured
`backend`, `endpoint_url`, `inference_location`, explicitly reported
`routed_provider`, `routed_model`, and `identity_contradiction`. Missing response
or router metadata remains absent rather than being inferred from aliases or
display strings.

That evidence is intentionally multi-dimensional. A requested model, a response
model, and a router-reported model answer different questions and must not be
collapsed into one synthetic "effective model" identity merely for easier
analytics.

## Decision

Battalion will treat history search and analytics storage as a **derived,
rebuildable, project-local projection** over canonical persisted evidence.
Projection contents never outrank or replace their source records.

### Projection boundary

A projection record retains stable references back to the canonical evidence
from which it was derived. Search results and analytics observations are
presentation/query products, not new execution facts. Deleting a projection
must not lose canonical Battalion evidence.

All projection construction and query behavior belongs behind the shared
application boundary. CLI, desktop, and future clients do not read or mutate
the projection store directly.

### Initial storage

The initial implementation should use one embedded SQLite database owned by
Battalion. Structured columns and ordinary SQLite indexes support exact filters
and aggregations. SQLite FTS5 may be used for bounded free-text fields such as
ticket text and operator summaries when available in Battalion's supported
Python builds. Semantic/vector retrieval is out of scope for BTN-44.

The storage technology is an implementation detail of the projection boundary,
not a new persistence authority. A future implementation may replace it if the
same rebuildability, application-boundary, and evidence-linkage contracts are
preserved.

### Versioning and rebuild

Each projection format carries an explicit projection schema version and enough
Battalion-owned metadata to determine whether the store still matches the last
state Battalion produced.

Projection schema changes use **rebuild, not derived-data migration**:

- a missing projection is built from canonical evidence;
- an obsolete projection that Battalion can establish has not been externally
  modified may be replaced automatically;
- an obsolete projection that appears to have been modified outside Battalion
  requires explicit operator confirmation before destructive replacement; and
- a corrupt or unreadable projection is reported explicitly and may be rebuilt
  only through the same safe replacement path.

External edits receive protection from accidental destruction but do not become
canonical Battalion evidence. Battalion does not provide a generic path for
promoting arbitrary projection edits back into source records; durable facts
must enter through the authority boundary that owns that kind of evidence.

### Search semantics

The first projection supports exact/structured filtering and bounded free-text
search over the evidence BTN-44 names: tickets, operator summaries, roles,
inference identity, phases, outcomes, interrupts, verification, artifacts, and
Intel references.

Search results identify their originating Run/evidence and never claim fields
that were unavailable in the source record. Historical compatibility projects
what a record actually contains rather than fabricating newer evidence.

Inference-identity search is field-aware. A query may filter or inspect the
requested model, reported response model, configured backend, endpoint,
inference location, routed provider, routed model, or contradiction evidence
independently. The legacy `model` field may remain available for historical
records and display compatibility but is not interpreted as equivalent to all
new identity dimensions.

### Analytics semantics

Analytics are descriptive observations, not effectiveness judgments. Initial
measures may include attempts, outcomes, review results, token counts, sourced
monetary cost, and duration when those facts are available and comparable.

Unknown values stay unknown. Incomparable currencies or evidence classes are
not silently combined. Sample counts are always available alongside aggregates
where meaningful, and the product does not convert correlation into a hidden
quality score or automatic model-selection rule.

Ticket characteristics may be exposed only when they are backed by typed,
inspectable evidence. BTN-44 does not invent a difficulty score or semantic
classification to normalize model performance.

### Inference-identity analytics

BTN-44 consumes BTN-54's typed fields directly. It does **not** derive provider,
backend, endpoint, response identity, or routed identity by parsing model names,
aliases, endpoint strings, or other display text.

The initial projection exposes the following inference dimensions separately:

- **requested model** — the concrete model Battalion configured/requested;
- **response model** — the model identity explicitly reported by the inference
  response when available;
- **routed model** — the model identity explicitly reported by a router when
  available;
- **routed provider** — the provider explicitly reported by a router when
  available;
- **backend** — Battalion's configured backend classification;
- **endpoint** — the configured endpoint evidence retained by BTN-54;
- **inference location** — Battalion's typed `local`, `remote`, or `unknown`
  classification; and
- **identity contradiction** — durable evidence that runtime identity disproved
  an admitted Driver/Reviewer distinction.

Analytics callers choose the dimension they are comparing. Battalion does not
manufacture one precedence rule such as "routed model else response model else
requested model" and label the result as an authoritative effective model.
Such a field would hide whether an observation was requested configuration,
provider response evidence, or router evidence.

For presentation convenience Battalion may derive an **identity evidence
status** from field presence, for example `requested-only`, `response-reported`,
`route-reported`, or `contradicted`. This status describes completeness or
quality of the available identity evidence; it does not infer a missing model or
provider identity and is not an effectiveness score.

Historical records that predate BTN-54 remain comparable only on dimensions
they actually contain. A legacy `model` value may be displayed and searched as
legacy evidence, but it must not be silently copied into `requested_model`,
`response_model`, `routed_model`, backend, provider, endpoint, or location
fields during projection rebuild.

Later evidence contracts such as terminal-Run follow-up history, audit
projections, resource accounting, or context manifests may add new projection
fields without becoming prerequisites for BTN-44's initial projection contract.

## Consequences

History and analytics remain disposable accelerators over durable evidence, so
projection corruption or schema evolution cannot destroy execution history.
Rebuilds are simpler than maintaining migrations for data that can be derived
again, while explicit external-modification detection protects deliberate human
experimentation from silent deletion.

SQLite adds a local derived artifact but no service dependency and no new
source of truth. The application layer owns both projection maintenance and
queries, preserving the presentation boundary established by RFC-0004.

BTN-54 removes BTN-44's final external dependency. Model-role analytics can now
compare the requested, response-reported, routed, backend, endpoint, and
location dimensions without guessing what any display string means. This makes
identity uncertainty visible rather than compressing it into a misleading
single model label.
