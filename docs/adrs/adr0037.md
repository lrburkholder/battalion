# ADR-0037 — Require semantic-review and human-acceptance evidence for compact completion

**Status:** Accepted  
**Date:** 2026-08-29  
**Implements:** BTN-142  
**Related:** RFC-0012, RFC-0013, RFC-0014, ADR-0032, ADR-0033, ADR-0034, ADR-0036

## Context

RFC-0012 permits proportionate compact Implementation Runs only when they retain behavioral verification, deterministic gates, independent review, and human acceptance. RFC-0014 clarifies that the existing checkpoint reviewer is a RejectionAnalyzer, not independent semantic review. Treating its GREEN checkpoint as semantic review would silently weaken the compact assurance contract.

Compact execution must also ratchet upward when authoritative evidence exposes ambiguity, an architecture decision, material scope expansion, a security concern, untrustworthy verification, gate failure, a material review concern, write-scope exceedance, or a configured full-only condition. That ratchet must retain prior compact evidence and must never restore compact assurance automatically.

## Decision

The initial compact `WorkflowRecipe` retains Driver RED/GREEN behavioral evidence and configured deterministic gates, but completion additionally requires, in order:

1. Evidence from the independently initiated semantic Review Run policy.
2. An authorized human acceptance record.

These are typed recipe completion requirements with exact policy references. They are not embedded graph nodes, and the legacy checkpoint reviewer does not fulfil the semantic-review requirement. The Review Run implementation is a separate follow-up under RFC-0014.

BTN-142 owns an application-bound `WorkflowExecutionState` policy contract. It records completed stage evidence, ordered completion evidence, and the first upgrade event. A full upgrade records the exact full Implementation Run continuation recipe; a clarification upgrade records no execution continuation. Once upgraded, compact stages and compact completion cannot continue. Completed pre-upgrade evidence remains immutable in the execution record.

BTN-143 owns durable Run linkage, save/load migration, and resume behavior. It must persist these exact policy records rather than re-admit work or infer a lower-assurance recipe after restart.

## Consequences

Compact policy does not weaken write scope, authorization, side-effect, provenance, cost, interrupt, deterministic verification, or human authority requirements. It avoids falsely calling checkpoint failure normalization an independent review.

An Implementation Run cannot become terminal merely because its compact Driver stages passed: it remains incomplete until the referenced semantic-review and human-acceptance evidence exist. The policy remains executable only through the shared application and recipe boundary; no CLI-specific compact path is added.

The compact policy contract is not yet durable `RunState` state and does not alter the shipped v1 graph. BTN-143 and the Review Run follow-up consume it to provide persistence/resume and actual independent-review execution.
