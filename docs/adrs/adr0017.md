# ADR-0017 — Attribute LLM Costs to Durable Node Executions

## Status

Accepted

## Date

2026-08-13

## Implementation status

Implemented by BTN-16 and revised by BTN-35.

## Context

Battalion's interrupt budget is a run-level turn counter. It can pause runaway
execution, but it cannot explain which model or phase consumed tokens and
dollars. BTN-19 already established the durable node execution as the source
of execution evidence, so a separate cost log would split provenance and
resumption across competing records.

## Decision

Record each successful LiteLLM completion as a bounded usage observation on the
active `NodeExecution`. An observation identifies the provider-reported model
and input and output token counts. Monetary evidence is a nullable decimal
amount with a separately validated ISO 4217 currency and an explicit source:
`provider-reported`, `estimated`, or `unknown`. A known zero has a currency and
known source. An unavailable amount has no currency and uses `unknown`; it is
never represented as zero.

The execution record contract advances to version `1.2`. Versions `1.0` and
`1.1` remain readable. Legacy `cost_usd` observations are interpreted as USD
provider-reported evidence, matching the `1.1` contract, without rewriting the
persisted record. Records with no monetary observation retain their token usage
and acquire no invented cost.

Expose cost reporting as a deterministic projection of the persisted execution
record, grouped by concrete graph phase and role. The CLI queries that projection
with `battalion status RUN_ID --costs`.

The integer `RunState.budget` remains the sole input to interrupt trigger #3.
Dollar costs are observability evidence and do not change its threshold,
increment, pause, or resume behavior.

## Consequences

- Every reported amount and its provenance remain attributable to a run and
  node execution.
- Save, load, pause, and resume use the existing state path.
- Older execution records remain valid; legacy USD observations preserve their
  meaning and absent observations remain explicitly unknown.
- Failed provider attempts without a completion response have no usage record;
  retry counts remain represented by the existing infrastructure-failure path.
- Future pricing or cost-limit policy would require a separate decision rather
  than silently changing trigger #3.
