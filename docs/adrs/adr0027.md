# ADR-0027: Generate status documentation from the canonical backlog

Date: 2026-08-23
Status: Accepted

## Context

Ticket status was hand-maintained in four places at once: the README Status
section (narrative, per-ticket checklist, component-readiness table) and its
separate Roadmap section, the `plan.md` status narrative, the ADR index
implementation column, and `backlog.json` itself. Every status change
required reconciling all of them by hand, and the copies had already drifted
(the ADR index showed "BTN-43 in progress" after BTN-43 shipped). The
repository's own working agreements require documentation to be reconciled as
part of each ticket, which this duplication made expensive and unreliable.

GitHub-flavored Markdown has no include or transclusion mechanism, so a
single-source document cannot be composed at render time.

## Decision

- `backlog.json` remains the sole machine-readable source of truth for
  ticket identity and status.
- `docs/status.md` becomes the single human-readable status document. It
  contains authored narrative (current milestone, roadmap themes) plus a
  mechanically generated "Delivered work" region.
- `scripts/sync_status.py` regenerates that region directly from
  `backlog.json`, then splices the whole document into `README.md` between
  HTML comment markers. `--check` fails on drift without writing, so tests
  and CI enforce currency instead of trusting hand edits.
- The component-readiness table and roadmap live only in `docs/status.md`;
  the README embeds them rather than keeping its own copy. Authored ticket
  citations in that document are validated against `backlog.json`
  (`tests/test_docs_status.py`), so "Complete" claims must cite done
  tickets.
- Publication stays explicit: `docs/status.md` and `backlog.json` join the
  `PUBLISHED_DOCUMENTS` set in `scripts/build_pages.py`; nothing is public
  merely because it exists in the repository.

The first reconciliation pass under this decision corrected the stale
ADR-0023 index entry and replaced README's hand-written checklist with the
generated projection.

## Consequences

- A ticket status change touches one generated region plus, where needed,
  the authored narrative — not four documents. Drift fails tests instead of
  surviving review.
- The README remains GitHub-native: markers are invisible HTML comments and
  the embedded content renders as ordinary Markdown on GitHub, in `git
  diff`, and on Pages.
- Bulk backlog changes produce bounded, mechanical README diffs inside the
  marker block; reviewers can ignore regenerated churn safely.
- Contributors must run `python scripts/sync_status.py` after backlog
  edits; forgetting fails `tests/test_docs_status.py` rather than shipping
  staleness.

## Future

When the ticket source moves from `backlog.json` to GitHub Issues, it moves
through the already-accepted WorkSource capability boundary (BTN-71 local
backlog provider, BTN-72 GitHub Issues adapter; RFC-0006 / ADR-0025). At
that point only `load_tickets()` in `scripts/sync_status.py` changes its
input; the generation, embedding, validation, and publication contract is
unaffected. No speculative provider abstraction is introduced before then;
the standard library JSON reader is the correct amount of machinery today.
