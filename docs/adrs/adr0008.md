# ADR-0008 — Give Refactorer Driver's Implementation Scope

## Status

Accepted

## Date

2026-08-01

## Implementation status

Implemented in v1 by BTN-13.

## Context

Refactorer and Driver both modify implementation files. Separate declarations
of the same path set could drift while granting no useful distinction in
authority.

## Decision

Give Refactorer the same declared implementation scope as Driver and keep one
scope declaration as the source of truth.

## Rationale

The roles differ in purpose, not in which implementation paths they may edit.
Sharing the declaration avoids duplicated authority configuration.

## Consequences

- Refactorer reuses Driver's scope entry when write tools are built.
- Refactorer still has distinct role behavior and must preserve passing tests.
- Sharing scope does not grant either role architectural authority.
- BTN-129 clarifies that shared scope is a filesystem ceiling, not permission to
  expand the task. When the current run has GREEN artifact provenance,
  Refactorer may write only the latest successful GREEN Driver's production
  artifacts. It cannot create or modify tests, documentation, configuration,
  or examples; attempted non-artifact output becomes a typed, recoverable role
  contract failure.

ADR-0013 extends this decision for project-layout-aware runs. The shared
`driver` entry remains the backward-compatible default; an explicit
`refactorer` entry may now narrow or separate Refactorer's implementation roots.
