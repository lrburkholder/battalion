# ADR-0022 — Use PySide6 for Desktop Presentation

## Status

Accepted

## Date

2026-08-18

## Implementation status

Selected by BTN-41 and implemented by BTN-42 as the production read-only
operator console. The disposable benchmark remains separate from production UI
code.

## Context

RFC-0004 requires a standalone desktop operator interface that remains a
disposable presentation client over `battalion.application`. BTN-37 defined one
provider-free fixture, scenario, validator, and nine-category measurement
procedure. BTN-38, BTN-39, and BTN-40 implemented that control case in Tauri,
PySide6, and Electron respectively.

The human operator selected PySide6 after reviewing the benchmark evidence and
the architectural tradeoffs. Familiarity was considered but was not sufficient
on its own: the decision must account for resource cost, packaging, process and
authority boundaries, maintainability, accessibility, recovery, testing,
platform support, and the learning value of each stack.

All measurements were made on Windows. None of the spikes establishes
production confidence for macOS or Linux. Clean-machine launch was unavailable,
and no candidate exercised a real Battalion worker crash. PySide6 and Electron
also lack separately retained active-memory and native accessibility samples.
The selection accepts those limitations because the available evidence is
sufficient to distinguish the candidates; it does not convert them into passes.

## Decision

Use PySide6 with Qt Widgets for Battalion's production desktop presentation.
The UI remains a presentation adapter over `battalion.application`; choosing a
Python toolkit does not collapse the application, worker, persistence, or graph
boundaries.

Production work must follow these guardrails:

- Widgets and presentation controllers may call only transport-neutral
  application commands and queries. They must not invoke LangGraph, mutate
  persisted `RunState`, or create a second persistence path.
- Long-running application calls and observation consumption execute outside
  Qt's UI thread. Only presentation updates return to the UI thread.
- The desktop process receives no provider credentials or broad authority merely
  because Python permits it. Effective operations remain explicit, narrow, and
  testable through the application boundary.
- ADR-0019 remains authoritative for detached one-worker-per-run supervision.
  A future native component may be introduced behind a bounded interface only
  when measured need justifies it.
- BTN-42 must independently validate keyboard operation, Windows UI Automation
  and screen-reader semantics, client restart and durable reconnect, malformed
  data, real-worker failure, clean-machine packaging, and resource use. Its
  acceptance cannot rely on the disposable spike's unverified areas.
- Benchmark code stays under `benchmarks/desktop/`. Production code must be
  reconciled with repository naming, dependency, testing, documentation, and
  application-boundary standards instead of being copied wholesale.

## Consequences

- Battalion keeps product policy and desktop presentation in the same primary
  language while Qt supplies its mature C++ UI implementation.
- The measured desktop baseline uses substantially less idle memory and fewer
  processes than either webview candidate on the benchmark workstation.
- Packaging is larger and less turnkey than Tauri's system-WebView-based
  artifact. Python, PySide6, Qt plugins, and the chosen freezer become release
  engineering responsibilities.
- PySide6 provides no renderer capability sandbox. Architectural dependency
  direction and tests are mandatory safeguards, and process isolation remains
  at the worker boundary.
- Tauri's stronger accessibility and permission evidence remains useful as the
  standard PySide6 production work must meet, even though Tauri is not selected.
- This decision does not select a web UI, QML, Rust-native UI toolkit, or a
  general plugin model. Any later change requires new evidence and an ADR.

## Alternatives rejected

### Tauri

Tauri produced the smallest package and strongest renderer permission and
accessibility evidence. It was not selected because its WebView2 process tree
used the most idle memory in this benchmark, its completed scenario was slower
than PySide6's, and it adds a Rust/webview/Python boundary without a demonstrated
benefit for Battalion's operator workload. Learning Rust remains valuable but
is not, by itself, a product architecture requirement.

### Electron

Electron offers a mature web ecosystem and a mechanically sandboxed renderer.
It was not selected because it had the slowest scenario, the largest package,
high idle resource use, and the broadest presentation toolchain and privileged
main-process surface.

### More framework spikes

A Rust-native toolkit or .NET desktop framework could answer different
questions, but the three controlled spikes supplied enough evidence for the
current decision. Additional framework search would delay the read-only
vertical slice without resolving the known PySide6 production obligations.
