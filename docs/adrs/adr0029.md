# ADR-0029: Persist side-effect evidence in RunState with replay-safe logical operation identity

Date: 2026-08-26

Status: Accepted

Implementation status: Accepted and implemented for the substrate (BTN-70):
state contract, coordinator semantics, and deterministic coverage. Individual
capability operations that consume this substrate arrive with BTN-71 onward.

## Context

Battalion Runs are durable and resumable, so any externally visible effect —
a Slack-like message, email, webhook, GitHub comment, or equivalent — will
eventually be retried, resumed after a crash, reprocessed from a duplicate
event, or replayed after reconnect. RFC-0006 (accepted with ADR-0025)
requires that every side-effecting operation carry a stable logical identity,
typed ambiguous-outcome behavior, and durable evidence, while a timeout after
submission must be treated as ambiguous rather than failed. BTN-67 shipped
the structural adapter/transport binding but deliberately recorded no
evidence; nothing in the runtime today prevents one logical notification
from being delivered twice across resume.

Existing durable identity primitives are `run_id`, `NodeExecution`
execution IDs, `integration_id`, and `actor_id` (ADR-0014, ADR-0019,
ADR-0021, ADR-0026). Observation events (BTN-36) already define duplicate
delivery semantics — identical redelivery is ignored, conflicting content is
rejected — but their streams are per-invocation and not a side-effect
ledger. ADR-0014, ADR-0021, and ADR-0023 all reject parallel event stores.

## Decision

1. **One ledger inside the single state contract.** `RunState` gains a
   separately versioned `SideEffectLedger` (schema 1.0) containing
   `SideEffectOperation` records with ordered `SideEffectAttempt` evidence.
   Evidence lives beside execution history and human-action audit records;
   Battalion does not introduce a second persistence authority or competing
   event model.

2. **Battalion mints the stable logical identity before first delivery.**
   Each externally visible attempted side effect receives an immutable
   `operation_id` (`op-{uuid4}`) persisted as write-ahead intent *before*
   any send. A caller-supplied stable logical-operation or event key makes
   opening idempotent so duplicate event processing, retry, and resume
   converge on one operation.

3. **Attempts record typed outcomes; ambiguity is explicit.** An attempt is
   `succeeded`, `failed` (confirmed no external effect), or `ambiguous`.
   Timeouts, cancellations, transport failures, and malformed responses
   after submission are ambiguous per RFC-0006. Adapter-typed confirmed
   rejections are failed and remain distinguishable from workflow failure:
   they never fail the graph by themselves.

4. **Unresolved operations refuse automatic redelivery.** Pending intents
   inherited from another process (crash-before-response candidates) and
   ambiguous attempts raise a typed reconciliation requirement.
   Reconciliation resolves them against provider idempotency or status
   evidence, recording who decided, when, on what basis, and any provider
   reference. Confirmed failures may retry under the same `operation_id`;
   succeeded operations replay-skip without sending.

5. **Provider idempotency mechanisms are engaged, never trusted alone.** The
   delivery callback receives Battalion's stable operation ID for use as a
   provider idempotency key where supported; adapters report whether the
   mechanism was used plus any provider reference as attempt evidence.

6. **Evidence excludes secrets and payload contents.** Records retain Run
   and Actor identity where applicable, capability, integration references,
   operation name, timestamps, bounded detail text, optional SHA-256 request
   digests, and provider references — never credentials, raw requests, or
   response bodies.

7. **The application boundary owns coordination.** A transport-neutral
   `SideEffectCoordinator` (in `battalion/integrations/effects.py`) performs
   no IO itself: callers inject persistence callbacks so write-ahead ordering
   is mechanical. Capability ports resolve before intent is recorded, so
   configuration and policy denials cannot leave spurious evidence.

## Consequences

- Retry, resume, crash-recovery, and duplicate-processing behavior for every
  future integration operation is defined once and tested once (BTN-72
  through BTN-80 consume this substrate instead of redefining it).
- Unresolved operations surface as inspectable ledger state, so operators
  can see exactly which external effects are unproven after a crash.
- Delivery requires two durable saves per successful operation (intent,
  outcome); acceptable at Battalion's local-write scale.
- Adapters must classify their failures using the shared integration error
  vocabulary for correct ambiguous/failed classification.
- The ledger grows with external activity; bounded at 500 operations and
  100 attempts each, matching existing RunState list bounds.

## Alternatives rejected

- **A separate side-effect store or event log.** Violates the single-state
  authority established by ADR-0014/0021/0023 and creates a second source of
  truth that resume logic would have to reconcile.
- **Trusting provider idempotency keys alone.** Providers differ in support
  and window; Battalion retains its own identity so safety never depends on
  provider behavior it cannot verify.
- **Recording evidence only after responses.** Loses the write-ahead marker
  that makes crash-before-response detectable instead of silent.
- **Automatic retry of ambiguous outcomes.** RFC-0006 forbids treating
  timeout-after-submission as failed; blind retry risks duplicate external
  effects.
