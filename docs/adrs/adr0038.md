# ADR-0038 — Gate Driver on a revision-pinned artifact-target contract

**Status:** Proposed  
**Date:** 2026-09-01  
**Implements:** BTN-193 architecture; runtime delivery deferred  
**Related:** RFC-0012, ADR-0013, ADR-0014, ADR-0020, ADR-0023, ADR-0032, ADR-0033, ADR-0034, ADR-0036, ADR-0037, BTN-129, BTN-139–144

## Context

CLI UAT produced an Architect plan that identified `src/test_greeting.py` as
the test artifact in one section and `test_greeting.py` in its implementation
sequence. A manual checkpoint stopped Driver, but the only handoff was prose.
The human therefore had to infer which path was intended, and an automated
resume could have treated a generic checkpoint resolution as permission to
continue despite the contradiction.

`plan.md` must remain useful explanatory material, but model prose is not an
executable file contract. Parsing path-like strings out of Markdown would be
format-dependent, would turn narrative into hidden authority, and would still
leave presentation clients or Driver to resolve ambiguity differently.

RFC-0012 already separates deterministic evidence, optional Tactician advice,
human workflow choice, and execution. BTN-193 must preserve those separations,
the existing six-interrupt taxonomy, and mechanically enforced write scopes.

## Decision

Battalion will require one current, validated `ArtifactTargetContract` before
starting a Driver attempt. The contract is an application-owned evidence
record, not a project capability, write-scope declaration, prompt, or graph
definition.

### Contract and identity

The version 1 contract contains:

```text
ArtifactTargetContract
  contract_version: "1.0"
  contract_id: sha256 of canonical contract content
  project_id
  work_item_revision
  specification_revision
  project_source_revision
  workflow_admission_decision_id
  architect_execution_id | null
  plan_artifact_digest | null
  supersedes_contract_id | null
  evidence_references[]
  targets[]

ArtifactTarget
  target_id
  project_relative_path
  assignments[]
  evidence_references[]

ArtifactTargetAssignment
  owner_role
  workflow_phase
  intended_operation: create | modify | delete
```

`contract_id` is computed from canonical JSON containing every field above
except the ID itself. Object keys are sorted and array ordering is defined by
the schema. Changing a target, revision, provenance reference, assignment, or
supersession link produces a different identity. Human approval is a separate
immutable record referencing that identity; it is not included in the hash.

Paths use `/` separators and identify exact files relative to the project
root. Absolute, drive-qualified, UNC, empty, dot-segment, parent-traversing,
glob, NUL-containing, Battalion-state, VCS-metadata, or project-escaping
symlink paths are unsafe and invalid. Normalization happens before identity
calculation. Duplicate normalized paths, duplicate target IDs, duplicate
assignments, or one target ID mapped to different paths are invalid. Project
case-sensitivity policy determines whether case-only collisions are duplicates.

`project_source_revision` identifies the repository/workspace evidence against
which the paths were assessed; it is not inferred from the current directory
at display time. The work-item and specification revisions use the same
revision-pinned meanings as workflow admission. Missing revision evidence is a
contract failure, not an empty or "latest" value.

### Architect output and plan narrative

Architect will return a typed `ArchitectHandoffCandidate` containing bounded
plan Markdown, target definitions, and implementation steps that reference
`target_id` values. Steps cannot restate or override a target path. The role
runner validates and canonicalizes the candidate before its existing scoped
write of `plan.md`; the rendered plan includes a generated target table. An
invalid candidate follows the existing pre-write role-contract correction and
escalation policy and cannot advance to Driver.

The candidate remains model-produced evidence. Application policy binds its
source revisions and execution/plan provenance, reconciles it with other
evidence, and seals the contract. Raw reasoning, free-form path mentions, and
the rendered Markdown never become the authoritative target list.

Compact recipes that omit Architect use exact targets from authoritative,
revision-pinned work-item/specification evidence. Bounded-scope admission
evidence alone does not invent paths. If exact targets are absent, compact
execution requires clarification or upgrade rather than a Tactician-generated
manifest.

### Deterministic reconciliation and human authority

Application policy evaluates the candidate against:

- current work-item, specification, project-source, and workflow-admission
  identities;
- the selected recipe and phase vocabulary;
- existing role write scopes and project path policy; and
- exact target evidence plus any contradiction or staleness evidence.

The result is either `ready` or `clarification-required`, with stable reason
codes and evidence references. Missing, ambiguous, duplicate, unsafe, stale,
or internally contradictory targets are never `ready`. A target contract must
be a subset of the role's already authorized structural write scope. Neither
Architect output, human approval, admission, nor Tactician can widen that
scope.

Workflow admission contributes its revision/policy/decision identity and
bounded-scope evidence. Tactician may contribute referenced ambiguity or risk
evidence when deterministic admission was uncertain, but remains advisory: it
cannot create, edit, approve, or dispatch a target contract.

A configured manual `driver` checkpoint displays and resolves against the
exact current `contract_id`; generic resolution prose is insufficient if the
identity changed. A valid, consistent contract does not add a mandatory model
call or human pause to every full Run. When reconciliation requires
clarification, however, Driver is fail-closed until an active human Actor uses
a transport-neutral application operation to:

1. approve an exact corrected contract (creating a new identity and preserving
   the superseded record),
2. return to Architect/clarification for a new candidate, or
3. cancel execution.

This is an application admission gate, not a seventh v1 interrupt. The graph
cannot dispatch Driver without current gate evidence, and presentation clients
cannot manufacture that evidence.

### Persistence, inspection, and resume

BTN-143's durable admission work must retain target contracts, reconciliation
results, approvals/corrections, supersession links, and the active contract
reference without combining them with deterministic or Tactician assessments.
Each Driver attempt records the contract ID under which it began. Later target
changes append evidence and apply only to later attempts; they do not rewrite
historical execution records.

Resume revalidates the active contract against persisted revisions, selected
recipe, write scope, and project path policy. Changed source/spec/admission
identity or an unresolved correction returns to the pre-Driver gate. Resume
does not infer approval from a prior generic interrupt resolution and does not
silently substitute a newer contract.

BTN-144 presentation work must expose, through shared application queries, the
active/superseded contract identities, canonical target table, assignments,
source revisions, evidence, reconciliation state/reasons, and approving Actor
where applicable. JSON output exposes the typed records; human CLI/desktop
views must not require log or `plan.md` parsing.

### Credential-free acceptance scenario

A deterministic fixture will supply the historical greeting shape without an
LLM or credentials:

1. Pin a disposable project, work-item, and specification revision.
2. Supply an Architect candidate whose logical `greeting-test` target is
   `src/test_greeting.py` while an implementation-step target definition tries
   to map that same target ID to `test_greeting.py`.
3. Verify validation writes no `plan.md`, creates no Driver attempt, and
   reports `clarification-required` with both conflicting paths and source
   evidence.
4. Submit a human-Actor correction selecting `src/test_greeting.py`; verify a
   new contract supersedes the rejected candidate and resume binds the next
   Driver attempt to the corrected ID.
5. Inspect JSON and human views, save/load/resume, and execution history; both
   identities and the reason for correction remain visible.

Intended UAT evidence is the credential-free fixture transcript, persisted
records before and after correction, absence of Driver/tool activity before
approval, the generated canonical target table after correction, and the
Driver execution reference to the corrected contract. BTN-129 retains the
original live CLI finding and remains responsible for release-gate CLI UAT;
this scenario does not rewrite or convert that historical Run into a pass.

## Consequences

- Driver receives exact, inspectable target evidence while `plan.md` remains
  explanatory rather than executable authority.
- A target contract narrows expectations but does not replace structural write
  scope, role policy, or observed-write enforcement.
- Consistent Runs do not pay a mandatory Tactician or human-checkpoint toll;
  contradictory Runs fail closed before Driver.
- Architect's final-output contract and pre-Driver graph/application boundary
  are architectural changes. Runtime work requires a separately scoped
  implementation ticket with state migration, application, graph, prompt,
  CLI/desktop, and end-to-end tests.
- BTN-139 through BTN-142 are complete prerequisites. BTN-143, BTN-144, and
  BTN-129 remain open dependencies, so BTN-193 cannot claim completed runtime
  delivery or UAT acceptance.

## Alternatives considered

### Parse paths from `plan.md` — rejected

This makes formatting and model prose authoritative, cannot reliably
distinguish examples from instructions, and encourages each client to resolve
conflicts differently.

### Derive write scope directly from Architect output — rejected

That would let a model grant its successor new authority. Target contracts may
only narrow an independently authorized scope.

### Require Tactician or a human approval for every contract — rejected

RFC-0012 keeps Tactician optional and uses deterministic evidence first.
Consistent exact evidence should not add fixed probabilistic or human ceremony;
human authority is mandatory when correction or configured checkpoint policy
requires it.

### Treat a generic manual-checkpoint resolution as approval — rejected

Free-form prose does not identify the target set or revisions being approved
and can be replayed against changed evidence.
