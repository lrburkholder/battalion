# ADR-0038 — Gate Driver on a revision-pinned artifact-target contract

**Status:** Accepted  
**Date:** 2026-09-02  
**Implements:** BTN-193 architecture; runtime delivery BTN-194–197  
**Related:** RFC-0012, ADR-0013, ADR-0014, ADR-0020, ADR-0023, ADR-0032, ADR-0033, ADR-0034, ADR-0036, ADR-0037, ADR-0039, BTN-129, BTN-139–144, BTN-194–197

## Context

CLI UAT produced an Architect plan that identified `src/test_greeting.py` as
the test artifact in one section and `test_greeting.py` in its implementation
sequence. A manual checkpoint stopped Driver, but the only handoff was prose.
The human therefore had to infer which path was intended, and an automated
resume could have treated a generic checkpoint resolution as permission to
continue despite the contradiction.

`plan.md` must remain useful explanatory material, but model prose is not an
executable file contract. Parsing path-like strings out of Markdown would be
format-dependent, would turn narrative into hidden authority, and would still
leave presentation clients or Driver to resolve ambiguity differently.

RFC-0012 already separates deterministic evidence, optional Tactician advice,
human workflow choice, and execution. BTN-193 must preserve those separations,
the existing six-interrupt taxonomy, and mechanically enforced write scopes.

## Decision

Battalion will require one current, validated `ArtifactTargetContract` before
starting a Driver attempt. The contract is an application-owned evidence
record, not a project capability, write-scope declaration, prompt, or graph
definition.

### Contract and identity

The version 1 contract contains:

```text
ArtifactTargetContract
  contract_version: "1.0"
  contract_id: sha256 of canonical contract content
  project_id
  work_item_revision
  specification_revision
  project_source_revision
  workflow_admission_decision_id
  architect_execution_id | null
  plan_artifact_digest | null
  supersedes_contract_id | null
  evidence_references[]
  targets[]

ArtifactTarget
  target_id
  project_relative_path
  assignments[]
  evidence_references[]

ArtifactTargetAssignment
  owner_role
  workflow_phase
  intended_operation: create | modify | delete
```

`contract_id` is computed from canonical JSON containing every field above
except the ID itself. Object keys are sorted and array ordering is defined by
the schema. Changing a target, revision, provenance reference, assignment, or
supersession link produces a different identity. Human approval is a separate
immutable record referencing that identity; it is not included in the hash.

Paths use `/` separators and identify exact files relative to the project
root. Absolute, drive-qualified, UNC, empty, dot-segment, parent-traversing,
glob, NUL-containing, Battalion-state, VCS-metadata, or project-escaping
symlink paths are unsafe and invalid. Normalization happens before identity
calculation. Duplicate normalized paths, duplicate target IDs, duplicate
assignments, or one target ID mapped to different paths are invalid. Project
case-sensitivity policy determines whether case-only collisions are duplicates.

`project_source_revision` identifies the repository/workspace evidence against
which the paths were assessed; it is not inferred from the current directory
at display time. The work-item and specification revisions use the same
revision-pinned meanings as workflow admission. Missing revision evidence is a
contract failure, not an empty or "latest" value.

### Architect output and plan narrative

Architect will return a typed `ArchitectHandoffCandidate` containing bounded
plan Markdown, target definitions, and implementation steps that reference
`target_id` values. Steps cannot restate or override a target path. The role
runner validates and canonicalizes the candidate before its existing scoped
write of `plan.md`; the rendered plan includes a generated target table. An
invalid candidate follows the existing pre-write role-contract correction and
escalation policy and cannot advance to Driver.

The candidate remains model-produced evidence. Application policy binds its
source revisions and execution/plan provenance, reconciles it with other
evidence, and seals the contract. Raw reasoning, free-form path mentions, and
the rendered Markdown never become the authoritative target list.

Compact recipes that omit Architect use exact targets from authoritative,
revision-pinned work-item/specification evidence. Bounded-scope admission
evidence alone does not invent paths. If exact targets are absent, compact
execution requires clarification or upgrade rather than a Tactician-generated
manifest.

### Deterministic reconciliation and human authority

Application policy evaluates the candidate against:

- current work-item, specification, project-source, and workflow-admission
  identities;
- the selected recipe and phase vocabulary;
- existing role write scopes and project path policy; and
- exact target evidence plus any contradiction or staleness evidence.

The result is either `ready` or `clarification-required`, with stable reason
codes and evidence references. Missing, ambiguous, duplicate, unsafe, stale,
or internally contradictory targets are never `ready`. A target contract must
be a subset of the role's already authorized structural write scope. Neither
Architect output, human approval, admission, nor Tactician can widen that
scope.

Workflow admission contributes its revision/policy/decision identity and
bounded-scope evidence. Tactician may contribute referenced ambiguity or risk
evidence when deterministic admission was uncertain, but remains advisory: it
cannot create, edit, approve, or dispatch a target contract.

A configured manual `driver` checkpoint displays and resolves against the
exact current `contract_id`; generic resolution prose is insufficient if the
identity changed. A valid, consistent contract does not add a mandatory model
call or human pause to every full Run. When reconciliation requires
clarification, however, Driver is fail-closed until an active human Actor uses
a transport-neutral application operation to:

1. approve an exact corrected contract (creating a new identity and preserving
   the superseded record),
2. return to Architect/clarification for a new candidate, or
3. cancel execution.

This is an application admission gate, not a seventh v1 interrupt. The graph
cannot dispatch Driver without current gate evidence, and presentation clients
cannot manufacture that evidence.

### Persistence, inspection, and resume

BTN-143 now persists the exact pre-execution assessment, optional Tactician
assessment, human decision, and execution state in an immutable
`WorkflowAdmissionRunRecord` on `RunState` schema `1.1`. Artifact targets are
produced after that record admits a full Run and Architect executes, so they
must not be inserted retroactively into its original admission decision.

Runtime delivery will add a separately versioned sibling
`ArtifactTargetHandoffRecord` to a later `RunState` schema. It retains target
contracts, reconciliation results, approvals/corrections, supersession links,
and the active contract reference while cross-validating the persisted
workflow-admission decision ID. Each Driver attempt records the contract ID
under which it began. Later target changes append evidence and apply only to
later attempts; they do not rewrite the admission record or historical
execution records. Schema `1.1` Runs remain readable as explicit pre-target-
contract history and cannot claim evidence they never recorded.

Resume revalidates the active contract against persisted revisions, selected
recipe, write scope, and project path policy. Changed source/spec/admission
identity or an unresolved correction returns to the pre-Driver gate. Resume
does not infer approval from a prior generic interrupt resolution and does not
silently substitute a newer contract.

### BTN-195 persistence foundation (branch work)

The first BTN-195 slice introduces optional `artifact_target_handoff` storage
on `RunState` schema `1.2`, with independently versioned handoff schema `1.0`.
Frozen nested models and tuple histories retain contracts, reconciliation
snapshots, and Actor-attributed correction actions. Contracts form an ordered
supersession chain; the active ID must explicitly reference its unsuperseded
tip or remain absent. Loading never selects a contract implicitly.

Reconciliation records retain the exact recipe, source revision, write-scope
digest, and path-policy digest for later application revalidation. A `ready`
record requires a known contract, matching source revision, and no failure
reasons. Clarification requires typed reasons. State validation checks project,
admission decision/revisions, admitted recipe references, and any supplied
Architect execution plus `plan.md` provenance. Correction records retain stable
action IDs and Actor UUIDs; deserialization does not reauthorize historical
Actors or perform action replay.

Schema `1.0`/`1.1` remains explicit legacy history and cannot store the new
handoff record. Real save/load and corruption tests cover the migration boundary.
Subsequent branch slices add initial sealing, source collection, mandatory
Driver entry checks, attempt linkage, and human actions as described below.
Compact initial construction is described below; integration review and acceptance
evidence remain before complete Driver-gate acceptance.

### BTN-195 deterministic reconciliation (branch work)

`artifact_target_reconciliation` is an IO-free policy boundary. Its inputs are
explicit current project/work/spec/source/admission identities, exact recipe
identity, current reference conditions and authority, optional exact target
evidence, and a fresh path inspection. It never infers a source revision from
the current directory. Missing source evidence remains absent in clarification
records rather than receiving a fabricated revision. The application must
collect and verify these inputs before production use.

Ready results require exact matching revisions/references, coverage of every
selected Driver phase, and assignments within the registered recipe vocabulary.
Full recipes require matching Architect execution and plan digest evidence.
Compact targets must match current authoritative work-item/specification target
definitions; bounded-scope admission facts and repository/model hints cannot
invent paths. Conflicting definitions, duplicate targets, missing evidence,
and explicitly unresolved ambiguity fail closed with stable reason codes.

The read-only `scope.artifact_target_paths` adapter reuses bound-tool resolution
without performing writes. Exact project-relative targets never use the legacy
root-relative output fallback. Explicit empty phase scopes remain authoritative.
Resolved target paths must remain inside the project, outside protected metadata,
and identify files with directory parents. Case-policy and resolved-path collisions
fail closed, including aliases through symlinks or Windows junctions.

Snapshot digests use canonical JSON and SHA-256. Scope digest version `1.0` sorts
and deduplicates declarations while retaining spelling, trailing slashes, role
keys, and explicit empty phases. Path digest version `1.0` records the case and
containment policy plus project-relative target and scope-root resolutions. It
does not hash file contents or existence, so intended file creation does not
invalidate path evidence; retargeted aliases do. Supplying a prior reconciliation
requires the same contract, recipe, source revision, scope, and path-policy
digests. Neither a scope expansion nor a superseding contract is silently accepted
as resume. Project-source revision collection separately distinguishes expected
run changes from unrelated edits as described below.

### BTN-195 captured candidate and initial sealing (branch work)

Architect records its validated candidate through the existing execution capture
only after its scoped plan write. Execution-record schema `1.9` retains it across
checkpoint/save/load. Initial sealing reads these typed targets, never Markdown
path mentions. Successful attempts are eligible; an interrupted attempt is also
eligible only when it retained a candidate and its linked interrupts are post-write
manual/budget pauses. Their outcome and unresolved interrupt records stay unchanged.
Failure, rejection, unfinished execution, and older prose-only history do not
provide a sealable candidate.

`seal_architect_target_handoff` is a transport-neutral initial-sealing operation
protected by the existing inactive-worker/action guard. It requires the latest
Architect execution explicitly, an admitted project with pinned specification
and source revisions, and current evidence from application intake. It verifies
the project marker and hashes the actual contained `plan.md`, then uses persisted
structural scopes for reconciliation. The command accepts no replacement candidate.
The immutable admission record and all existing execution/interrupt evidence are
preserved; only the new sibling handoff and RunState version are persisted.

Identical replay leaves the state file untouched. Initial sealing cannot authorize
earlier Driver attempts, supersede/reactivate a contract, alter terminal history,
or clear a recorded clarification without the future human-correction operation.
Changed observations may invalidate a previously ready record. The operation does
not resolve manual checkpoints or dispatch Driver. The graph now uses the shared
observation policy at its mandatory pre-Driver gate, described below.

### BTN-195 source collection (branch work)

New admitted Git Runs capture a pre-execution `ProjectSourceSnapshot` in RunState
`1.2`. Policy `git-visible-source-v1` hashes HEAD and tracked/nonignored untracked
regular files, including resolved project-relative paths, link status, and the
filesystem executable bit. Ignored untracked files and root `.battalion` metadata
are excluded. Digests contain no file contents or absolute workspace location.
Collection requires a Git worktree root, allows unborn HEAD, and fails closed for
escaping/dangling links, non-file entries such as submodules, observed concurrent
changes, and limits above 10,000 files, 32 MiB per file, or 512 MiB total. This is
bounded workspace evidence, not a reconstructable Git commit or atomic filesystem
snapshot.

Initial sealing recollects source, including baseline paths and verified output
paths even when ignore rules now hide them. The baseline identity remains current
only when every changed file has matching scoped-write evidence from a completed
attempt and every such output still exists with its recorded bytes. Scope
declarations and general artifact snapshots cannot excuse changes. HEAD changes,
deletions, link/executable metadata changes, and unrelated edits require
clarification. Execution capture records each tool write's digest and verifies it
again at completion; failed/rejected/unfinished attempts cannot authorize changes.
Post-write manual/budget pauses preserve receipts without resolving interrupts.

The sealing caller may omit source revision or echo the pinned baseline; it cannot
substitute a new identity. Non-Git and legacy Runs without a pre-execution snapshot
remain readable but cannot seal by inventing a baseline after role execution.

### BTN-195 Driver gate and attempt linkage (branch work)

Both Driver phases run application-owned admission policy inside their graph
scaffolding, before execution capture, budget consumption, input assembly, or tool
setup. Every entry, automatic retry, and resume must supply current target
evidence. The runtime verifies the project marker, recollects source/path evidence,
and seals an initial full contract or revalidates the exact active identity.
Runtime path policy uses conservative case-insensitive collision checks on every
platform. Clients cannot submit a ready boolean or skip the graph gate.

The graph checkpoints new reconciliation evidence before creating an attempt or
raising `ArtifactTargetGateRejected`. Shared start/resume translate that failure
into `ArtifactTargetHandoffRejected` with its stable reason code. It is an
application admission failure, not a new interrupt or model/provider failure.
The same source-observation policy serves inactive-worker initial sealing and
live graph admission; neither clears a previous clarification automatically.

Execution-record `1.9` retains the active `artifact_target_contract_id` on Driver
attempt creation and completion. RunState checks historical contract existence,
phase assignment, and ready evidence predating the attempt. Unstarted-attempt
recovery revalidates files and preserves both attempt and contract identities;
started attempts without outcomes keep the existing unsafe-recovery behavior.

This slice accepts current evidence through shared `StartRun`/`ResumeRun` commands.
Presentation intake and compact recipe dispatch remain outside this gate's
implementation. Those paths remain fail-closed. Exact checkpoint authorization is
described below; generic prose cannot supply it. Existing
role/routing regression modules explicitly isolate the new policy seam; separate
real-gate scenarios cover scoped output, persistence, restart, and failed admission.

### BTN-195 exact checkpoint authorization (branch work)

Shared `ResumeRun` now accepts an explicit `artifact_target_contract_id`. A manual
Driver checkpoint with a retained handoff requires this to match the active ready
contract. The existing active-human Actor boundary records the ID on the applied
`HumanActionRecord`, together with its exact interrupt target and resolution.
Fresh source/path reconciliation occurs before saving the resolution and resume
intent atomically. Failure leaves both the interrupt and action ID unconsumed.

Replay retains the original Actor, resolution text, and contract identity. A
completed replay returns without rewriting state or dispatching another attempt;
an authorization saved before a crash can resume without a duplicate action.
Every later Driver entry checks the latest Driver checkpoint's applied action
against the active contract. Superseding contracts do not inherit prior approval.
RunState validates the historical contract reference, resolved checkpoint, and
preceding ready evidence. Older unbound actions remain readable but cannot supply
target authority. This changes neither the interrupt taxonomy nor structural scope.

### BTN-195 human handoff changes (branch work)

`ChangeArtifactTargetHandoff` names the expected history tip, stable action ID,
reason, and one action: approve an exact correction, return to Architect, or cancel.
The shared application verifies the project marker and active human Actor under
the existing inactive-worker/action guard. It checks both human-action journals
for ID conflicts. Identical replay performs no write or dispatch; a changed
Actor, action, reason, predecessor, or replacement identity is a conflict.

Correction approval requires an exact superseding contract and fresh current
evidence. It reconciles the replacement afresh against persisted structural scope
and the original source baseline; it cannot automatically rebase changed source,
specification, or admission identities. Failed validation saves no partial action.
Successful approval appends contract, reconciliation, and Actor attribution in one
state save. Historical admission, attempts, and prior checkpoint resolutions are
preserved. At a Driver boundary, a previously resolved manual checkpoint is renewed
for the replacement contract and requires its own exact authorization.

Returning to Architect clears active target authority and prepares the Architect
entry point without executing it or resolving prior interrupts. The selected
recipe must already admit Architecture; compact policy must explicitly upgrade
first. Subsequent correction approval requires a newly completed Architect
candidate. Cancellation clears active authority, records blocked status, and
prevents role execution and resume. Terminal/cancelled histories reject new
actions, and any unfinished attempt prevents handoff changes. Source rebasing and
client presentation remain outside this operation's authority.

### BTN-195 compact contract construction (branch work)

`construct_compact_target_contract` accepts exact targets only from current,
authoritative work-item/specification references pinned to the admitted revisions.
Bounded-scope admission facts and advisory/repository evidence cannot invent paths.
The contract retains work-item and specification provenance as well as each exact
target source; it contains no fabricated Architect execution or plan digest.
Conflicting descriptions remain available to deterministic reconciliation rather
than being silently merged into approval. Duplicate paths and exceeded bounds
produce typed rejection. Missing targets require clarification or explicit upgrade.

`seal_compact_target_handoff` provides inactive-worker application persistence,
and Driver-entry policy can construct the same contract before its first attempt.
Both routes use the existing source baseline, conservative path policy, structural
scopes, and immutable handoff history. Replay never substitutes newly supplied
targets into an existing contract or replaces human correction history.

Target readiness is independent of recipe execution. The existing resume adapter
already rejected compact/upgrade execution through the full graph; start now applies
the same check before saving or dispatch. This prevents a compact Run from being
silently routed into Architect or the full topology. A compact executor must still
honor its exact stages and semantic-review/human-acceptance completion requirements.

BTN-144 now exposes admission decisions and history through shared application
read models plus transport-neutral human/JSON projections. Artifact-target
inspection will extend that same boundary with a distinct
`ArtifactTargetHandoffInspection`: active/superseded contract identities,
canonical target table, assignments, source revisions, evidence,
reconciliation state/reasons, and approving Actor where applicable. CLI and
desktop consume the shared projection and application commands; neither client
parses logs or `plan.md`, revalidates policy, or mutates `RunState` directly.

### Credential-free acceptance scenario

A deterministic fixture will supply the historical greeting shape without an
LLM or credentials:

1. Pin a disposable project, work-item, and specification revision.
2. Supply an Architect candidate whose logical `greeting-test` target is
   `src/test_greeting.py` while an implementation-step target definition tries
   to map that same target ID to `test_greeting.py`.
3. Verify validation writes no `plan.md`, creates no Driver attempt, and
   reports `clarification-required` with both conflicting paths and source
   evidence.
4. Submit a human-Actor correction selecting `src/test_greeting.py`; verify a
   new contract supersedes the rejected candidate and resume binds the next
   Driver attempt to the corrected ID.
5. Inspect JSON and human views, save/load/resume, and execution history; both
   identities and the reason for correction remain visible.

Intended UAT evidence is the credential-free fixture transcript, persisted
records before and after correction, absence of Driver/tool activity before
approval, the generated canonical target table after correction, and the
Driver execution reference to the corrected contract. BTN-129 retains the
original live CLI finding and remains responsible for release-gate CLI UAT;
this scenario does not rewrite or convert that historical Run into a pass.

## Consequences

- Driver receives exact, inspectable target evidence while `plan.md` remains
  explanatory rather than executable authority.
- A target contract narrows expectations but does not replace structural write
  scope, role policy, or observed-write enforcement.
- Consistent Runs do not pay a mandatory Tactician or human-checkpoint toll;
  contradictory Runs fail closed before Driver.
- Architect's final-output contract and pre-Driver graph/application boundary
  are architectural changes. Runtime work requires a separately scoped
  implementation ticket with state migration, application, graph, prompt,
  CLI/desktop, and end-to-end tests.
- BTN-139 through BTN-144 are complete prerequisites and supply the admitted
  Run, persistence, resume, and presentation seams consumed here. BTN-129
  remains an open dependency, so BTN-193 cannot claim completed runtime
  delivery or UAT acceptance.

## Implementation decomposition

1. **BTN-194** implements the provider-neutral target contracts, deterministic
   identity/path validation, and typed Architect handoff before `plan.md` is
   written.
2. **BTN-195** persists the sibling handoff record and enforces deterministic
   reconciliation, human correction, graph admission, attempt linkage, and
   resume behavior before Driver.
3. **BTN-196** exposes the shared application inspection/correction boundary in
   CLI and desktop without moving policy into either client.
4. **BTN-197** independently exercises the production enforcement path and the
   greeting contradiction through credential-free end-to-end tests and UAT
   evidence.

The order is strict: BTN-194 → BTN-195 → BTN-196 → BTN-197. BTN-197 also
reconciles its results with BTN-129's preserved live CLI evidence.

### BTN-194 domain construction details (branch work)

The first implementation slice supplies frozen, extra-field-forbidding domain
models under aggregate version `1.0`; it does not yet change Architect output,
persist a handoff, or activate a Driver gate. The domain layer reuses
`WorkflowStage` and admission's evidence-source vocabulary. Assignments name
writing roles only (Architect, Driver, Refactorer), use a phase belonging to
that role, and cannot declare competing operations for the same target/phase.
Reviewer remains read-only.

Targets sort by target ID, assignments by role/phase/operation, and evidence
references by evidence ID before hashing canonical JSON (sorted object keys,
compact separators, UTF-8 without ASCII escaping). Implementation-step order
is retained; each step contains narrative plus a sorted set of referenced
target IDs, with no path-definition or authority fields. Free-form narrative
is not parsed into target evidence.

Lexical normalization converts backslashes and collapses repeated internal
separators while rejecting dot components, protected state/VCS components,
and Windows aliases/devices on every host. Case-sensitive construction is
deterministic by default; callers supply `case_sensitive_paths=False` in
Pydantic validation context for case-insensitive projects. Case policy is a
validation input, not model-authored authority or ambient host inference.
Filesystem/symlink containment, evidence reconciliation, and scope admission
remain separate application-boundary obligations for BTN-195.

The BTN-194 node slice accepts only an unfenced JSON candidate, rejects
ambiguous duplicate JSON fields, and completes all schema validation before
calling the existing `plan.md` scoped tool. The human projection retains the
candidate Markdown and appends a Battalion-marked canonical target table plus
target-referenced steps. Reserved generated markers are invalid in model prose,
so the provider cannot impersonate that projection. Malformed or invalid
candidates raise bounded `RoleContractViolation` evidence; Architect's one
automatic retry receives that correction ahead of potentially long
specification context. This changes neither the six-interrupt taxonomy nor the
role's sole `plan.md` write tool.

## Alternatives considered

### Parse paths from `plan.md` — rejected

This makes formatting and model prose authoritative, cannot reliably
distinguish examples from instructions, and encourages each client to resolve
conflicts differently.

### Derive write scope directly from Architect output — rejected

That would let a model grant its successor new authority. Target contracts may
only narrow an independently authorized scope.

### Require Tactician or a human approval for every contract — rejected

RFC-0012 keeps Tactician optional and uses deterministic evidence first.
Consistent exact evidence should not add fixed probabilistic or human ceremony;
human authority is mandatory when correction or configured checkpoint policy
requires it.

### Treat a generic manual-checkpoint resolution as approval — rejected

Free-form prose does not identify the target set or revisions being approved
and can be replayed against changed evidence.
