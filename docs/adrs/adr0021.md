# ADR-0021 — Recover Live Observation from Durable State

## Status

Accepted

## Date

2026-08-17

## Implementation status

Implemented by BTN-36.

## Context

RFC-0004 requires active runs to be watchable by disposable presentation
clients without making a callback stream, desktop process, or future framework
adapter authoritative. Existing graph callbacks expose node lifecycle and token
activity, but their dictionaries do not identify the run or node attempt, have
no ordering or timestamp contract, and cannot support safe reconnect behavior.

Persisting every token or progress notification would turn incidental UI data
into an unbounded second execution record. Treating delivery as reliable would
instead make a client unable to recover after disconnect. Concurrent per-run
workers also make one global event sequence artificial and operationally
expensive.

## Decision

Expose immutable, versioned `ObservationEvent` values through the shared
application boundary. Every event identifies its canonical run, one operation
stream, a monotonically increasing sequence in that stream, a timezone-aware
occurrence time, a deterministic event identifier, and—where applicable—the
node and generated attempt identifier. Ordering is defined by
`(run_id, stream_id, sequence)`; timestamps are evidence and are not a global
ordering mechanism across worker processes.

Classify observations as:

- `durable`: a notification that authoritative evidence was already saved,
  such as a state checkpoint;
- `transient`: node lifecycle, token, and reasoning progress that may be
  dropped; or
- `action-required`: an interrupt notification backed by canonical interrupt
  state and requiring the existing human-authorized application operation.

Durable observation payloads contain bounded state identity and status, not a
second serialized `RunState`. Transports may keep a bounded buffer and may
evict transient events. Duplicate event delivery is idempotent; conflicting or
malformed values fail validation.

Reconnect captures the current live-stream cursor first, reloads authoritative
state through `inspect_run`, and returns both as a snapshot. A client renders
that durable snapshot before asking its transport for events after the cursor.
Events produced during the reload are therefore newer than the barrier, while
older or missed transient events are unnecessary for reconstruction.

Observation remains a one-way projection. It provides no graph, persistence,
interrupt-resolution, or resume capability. Clients must use the canonical
application commands for every mutation and human action. The bounded in-memory
buffer is a reference transport, not a required desktop framework or IPC
choice.

## Consequences

- Several active runs can be merged deterministically without clock-based
  global ordering or shared sequence allocation.
- A dropped token or node-progress message can reduce animation fidelity but
  cannot change or obscure authoritative run state after reload.
- Framework spikes can choose IPC and buffering appropriate to their process
  model while sharing event validation, cursor, and recovery semantics.
- Node attempts created only for live progress do not replace durable
  `NodeExecution` identities; durable execution evidence remains canonical.
- A live interrupt notification never grants authority to resolve, override,
  or resume it.
