# ADR-0026 — Separate Actor Identity, Authority, and Responsibility

## Status

Accepted

## Date

2026-08-21

## Implementation status

Accepted with RFC-0007 by the human operator through BTN-58 on 2026-08-21.
BTN-59 implements durable Actor identity, offline FTUE bootstrap evidence,
local selection, shared application queries, and compatible action provenance.
Authorization, assignment, ownership, authentication, and collaboration
behavior remains deferred to BTN-60 through BTN-62 and later work.

## Context

BTN-43 persists human action provenance as bounded actor strings. Future local
and remote clients, assignment, external identity links, and collaboration
evidence need a stable subject without turning display names, provider logins,
credentials, assignment, or observed expertise into authority.

Battalion already requires presentation clients to use the shared application
boundary. Extending human collaboration without an explicit identity and
authorization model would let each client or persistence record invent its own
meaning for operator, owner, assignee, reviewer, and Actor.

## Decision

Use a Battalion-owned, opaque `actor_id` as the stable identity for human and
system Actors. Display names, operating-system usernames, email addresses,
provider logins, authentication subjects, and credentials are mutable
attributes or external bindings, not Actor identity.

Keep identity, authentication, authorization, project membership,
responsibility, and collaboration evidence separate:

- authentication proves control of a configured identity binding or trusted
  local session but grants no project authority;
- project membership grants explicit capabilities: `inspect`, `operate`,
  `resolve-interrupt`, `approve`, `assign`, and `administer`;
- interrupt resolution uses `resolve-interrupt`, separate from other governed
  decisions under `approve`;
- Architect, Driver, Reviewer, Refactorer, and Recon remain AI execution roles,
  not human capability roles;
- assignment records current responsibility and Ticket ownership records
  current accountability; neither grants capabilities;
- assignment, handoff, and ownership changes retain append-only history and do
  not rewrite prior provenance; and
- inferred expertise or social evidence may support recommendations but can
  never authenticate, authorize, assign, or approve.

Project first-time use is a one-time local trust-root ceremony. It creates or
selects the first human Actor, then credits an atomic bootstrap membership and
administration event to that Actor. The exceptional grant is valid only while
the project has no existing Actor or membership authority and cannot be
replayed. Local unauthenticated read-only inspection uses an explicit
inspect-only system Actor rather than anonymous or falsely human attribution.

Historical BTN-43 string actors remain literal legacy attribution. Migration
does not infer Actor identity from matching display names, logins, email, or
operating-system usernames. New commands carry durable Actor identity and the
shared application boundary performs authorization before mutation. CLI,
desktop, web, and mobile presentations receive no direct persistence or graph
authority.

RFC-0007 defines the detailed Actor contract, responsibility vocabulary,
authorization matrix, migration rules, and follow-up delivery.

## Consequences

- Local-first operation remains possible without OAuth or a hosted identity
  service, but its trust-root and system activity are explicit.
- Existing state and Intel evidence need a compatibility representation before
  durable Actor references can become required.
- A caller may need multiple capabilities for one compound operation, such as
  both `operate` and `resolve-interrupt` for resume-with-resolution.
- Ticket ownership and Ticket or Run assignment require separate projections
  and immutable histories.
- Presentation clients must render typed authorization failures and cannot
  derive authority from UI visibility, authentication, or assignment.
- Provider choice, remote sessions, organization administration, and account
  lifecycle remain deferred rather than embedded in the Actor contract.

## Alternatives rejected

Using display names or provider subjects as Actor IDs makes mutable,
provider-scoped values the author of durable evidence. Treating authentication,
assignment, ownership, or collaboration evidence as authority permits unrelated
facts to manufacture permissions. Giving each client its own authorization or
persistence path breaks the shared application boundary. Anonymous local
inspection loses attribution when an explicit least-authority system Actor can
represent it instead.
