# ADR-0007 — Review Against an Expected Outcome

## Status

Accepted

## Date

2026-08-01

## Implementation status

Implemented in v1 by BTN-12.
The BTN-164 amendment is in progress on its feature branch.

## Context

Reviewer originally treated a passing test command as success at every
checkpoint. At the RED checkpoint, however, a correctly written test is
expected to fail.

## Decision

Give Reviewer an `expect_pass` input. Acceptance means the observed result
matches the checkpoint's expected outcome: failure for RED, success for GREEN
and REFACTOR.

BTN-164 tightens what constitutes an observed result. Pytest exits 0 and 1
must agree with bounded, well-formed JUnit counts: a pass has collected tests
and no failures/errors; a RED-eligible failure has collected tests and actual
failures, with no harness errors. Exit 5, collection/usage/internal errors,
setup/teardown errors, unsupported exits, malformed output, launch failure,
timeout, and cancellation are not polarity values. They raise a typed execution
failure and use existing infrastructure interrupt #5, without a rejection-cause
LLM call or a same-cause rejection entry. Human-authorized resume reruns the
exact Reviewer checkpoint.

Project configuration supplies `reviewer_test_timeout_seconds` (default 300,
greater than zero, maximum 3600). The pytest subprocess owns a process group;
timeout/cancellation terminate the tree on Windows and the group on POSIX,
including forced cleanup of descendants. This adds no interrupt category and
does not change graph order or Reviewer write authority. Actual process evidence
is retained under ADR-0014 rather than inferred from the next graph phase.

## Rationale

Review must evaluate the purpose of a checkpoint rather than apply one global
definition of test success.

## Consequences

- A passing RED test is rejected.
- A failing GREEN or REFACTOR test is rejected.
- Graph wiring must supply the expected outcome for every review transition.
