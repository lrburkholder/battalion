# ADR-0031 — Separate canonical status validation from public status rendering

## Status

Accepted

## Date

2026-08-27

## Context

GitHub Issues and Milestones are the canonical source for work status. The
former status check compared that mutable remote state to generated Markdown
committed on every branch. A legitimate lifecycle transition after branch
creation could therefore fail unrelated CI. The same payload was also stored
in both `docs/status.md` and `README.md`, allowing the two presentation copies
to disagree.

## Decision

- A dedicated status-governance workflow validates the complete GitHub Issue
  corpus for Issue Schema v1 and lifecycle invariants when Issue lifecycle
  data changes. Ordinary test CI remains hermetic and does not compare or
  retrieve live GitHub state.
- Deterministic normalization and rendering remain independently unit-tested
  with injected fixtures.
- GitHub Pages renders the single public status document from the live Issue
  corpus during its build. The checked-in document is a build template, not a
  synchronized status authority.
- The public projection summarizes work by canonical milestone, with active
  Issues as links for drill-down. `README.md` links to that projection rather
  than embedding a second mutable status payload.
- Post-merge lifecycle automation changes only the linked Issue lifecycle.
  It does not commit rendered documentation.

## Consequences

Canonical data failures and rendering/publication failures have separate
commands and workflow steps. A stale branch document cannot invalidate ordinary
test CI, while a Pages failure remains visible in the publication workflow.
The GitHub CLI reader stays isolated behind normalization so the planned
WorkSource/GitHub adapter can replace it without altering rendering policy.
