# ADR-0019 — Supervise Active Runs with Detached Per-Run Workers

## Status

Accepted

## Date

2026-08-14

## Implementation status

Implemented by BTN-31.

## Context

RFC-0004 selects one supervised Python process per active run and requires a
desktop client to recover by reloading durable state after disconnect. BTN-31
must make that direction concrete without turning a desktop process, callback
stream, or monolithic daemon into a second state authority. Cancellation and
abnormal termination must also leave an inspectable outcome without risking an
unrelated run.

## Decision

Launch each active start or resume operation in one detached Python subprocess.
The worker receives its request once over standard input, closes that transport,
and owns exactly one canonical `run_id` for its lifetime. Closing or crashing a
presentation client therefore does not close a worker-owned request pipe or
terminate other active runs.

Persist a small project-local worker record under `.battalion/workers`. The
record contains a generated worker identity, canonical run association,
operation, process identifier, timestamps, lifecycle status, state path,
cancellation intent, and any terminal error. It is supervision evidence, not a
replacement for `RunState`. The application boundary owns start, observe,
cancel, and reconnect commands; clients do not retain authoritative process
handles or invoke worker internals.

Starting a new run writes an `in-progress` baseline `RunState` before provider
work begins. Both state and worker-record writes use same-directory temporary
files followed by atomic replacement. On reconnect, an active record whose
process no longer exists becomes `crashed`; it is explicitly recoverable when
canonical state still exists. A process that disappears after recorded
cancellation intent becomes `cancelled`. Normal completion and caught failures
are recorded by the worker itself.

Only one active worker record may be associated with a run at a time. A cancel
request targets only the process identifier in that run's current durable
record. Terminal records may be replaced by a later authorized resume attempt;
the canonical execution record remains in `RunState`.

## Consequences

- Concurrent runs do not share a process, callback channel, or failure domain.
- A newly started client can inspect and reconcile a worker using durable files
  without reconstructing the original `Popen` handle.
- Transient token and node event streaming remains a separate live-observation
  contract; missed transient messages are not required for recovery.
- A crash during one node preserves the last atomically committed state, not
  arbitrary in-memory graph progress. Recovery continues through the existing
  human-authorized application operations.
- Worker records are project-local operational metadata and must never contain
  provider credentials. Configuration travels over the one-shot stdin channel.
