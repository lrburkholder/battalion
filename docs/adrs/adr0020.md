# ADR-0020 — Separate Canonical Run and Project Identity from Display Names

## Status

Accepted

## Date

2026-08-16

## Implementation status

Implemented by BTN-32.

## Context

Battalion historically derived `run_id` as `run-{ticket_id}` and used it as a
state filename. A second run for the same ticket therefore collided with the
first, and a human-readable label became both presentation text and a durable
foreign key. RFC-0004 requires collision-resistant run identity, meaningful
operator labels, a project-wide run catalog, compatibility with existing state,
and project identity that survives a repository move.

Filesystem paths cannot be stable project identifiers. Deriving identity from
Git metadata would also merge distinct working projects that share history and
would fail for non-Git projects. Rewriting legacy run identifiers would alter
execution and artifact provenance without evidence that every reference had
been migrated safely.

## Decision

Generate a UUIDv4 for every new run through the transport-neutral application
boundary. Store its ticket-derived short label separately as `run_alias`. State
filenames, worker associations, execution provenance, and run-catalog entries
use the UUID `run_id`; aliases are display-only and need not be unique. Graph
execution may not change a run's canonical identity.

Persist a generated UUID project marker at `.battalion/project.json`. The
marker contains no absolute repository path, so moving the repository together
with its Battalion data preserves project identity. Persist the rebuildable,
project-local run catalog at `.battalion/runs.json`; every catalog carries the
project UUID and rejects state from another project.

When an operator opens several project roots together, two live roots claiming
the same project UUID are reported as a duplicate-copy conflict requiring
explicit reconciliation. Distinct project UUIDs and their local catalogs are
never merged merely because paths or Git history resemble one another.

Pre-BTN-32 state remains valid without `project_id` or `run_alias`. Catalog
discovery projects those files as `legacy_id: true`, retains their original
human-readable `run_id`, and does not rewrite state or provenance. Resume and
inspection continue to accept those original IDs. Newly cataloged runs must use
UUID identifiers.

## Consequences

- Re-running one ticket creates a distinct durable run without overwrite.
- Operators retain meaningful labels while persisted references remain stable.
- Moving a repository does not change its project or run identities.
- Copying a project preserves identity intentionally, but opening both copies
  together requires the human to decide whether one should be re-keyed.
- Legacy runs remain accessible, but their non-UUID identity is clearly marked
  and is not presented as a migrated canonical UUID.
- The catalog is a derived navigation aid, not a replacement state authority;
  canonical graph state remains in each `RunState` file.
