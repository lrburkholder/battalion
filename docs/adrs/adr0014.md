# ADR-0014 — Persist a Bounded Execution Record in RunState

## Status

Accepted

## Date

2026-08-13

## Implementation status

Implemented by BTN-19, extended with execution-record `1.2` evidence by
BTN-33, and extended on the active BTN-129 branch with `1.3` streamed-text
counts.
BTN-164 is extending the same record to `1.6` on its feature branch.
BTN-165 extends it to `1.7` on its feature branch with durable unfinished
attempt identity and crash recovery ordering.

## Context

The v1 state records current graph control data, rejection history, and
interrupts, but not which node produced an artifact or verdict. Logs and
conversation are transient and cannot support later human inspection or Recon.
Copying prompts, responses, test output, or artifact contents into `RunState`
would make the durable state grow without a meaningful bound.

## Decision

Add a separately versioned `execution_record` to `RunState`. Every Architect,
Driver, Reviewer, and Refactorer attempt appends a `NodeExecution` with its
role, concrete graph phase, configured model identity, bounded input
references, output reference or verdict, timestamps, and outcome.

Review decisions and clean-tree test outcomes are nested in the
execution that produced them. Tool activity and artifact provenance are also
nested. New interrupt log entries explicitly carry the node execution ID, and
the execution points back to their indexes in the run's interrupt log.

Artifact provenance contains only a project-relative path, SHA-256 digest,
originating run ID, and originating node execution ID. Node inputs are named
references to persisted state or workspace snapshots. Neither mechanism embeds
unbounded contents. The execution record uses the existing `RunState` JSON
persistence and graph resume path.

BTN-33 extends this same record rather than adding an event store. Each new
node execution carries a bounded operator handoff, prompt identity and explicit
human-readable contract version, SHA-256 prompt-template and model-configuration
identities, the Battalion revision, Git base/branch/dirty-state evidence, and
bounded context-reference hashes with inclusion and truncation metadata.
Prompt templates, rendered prompts, source contents, configuration values, and
dirty-worktree patches are not retained. When either workspace endpoint is
dirty, the record explicitly says exact reconstruction is unavailable because
no patch was retained. Records written with schema versions `1.0` and `1.1`
remain valid and expose the new optional evidence as unavailable.

BTN-129 adds bounded per-node counts for streamed reasoning and ordinary
content text. The record retains only character totals, never the raw stream;
the latter remains an explicit local CLI export. This makes a configured model
and concrete node comparable during UAT without turning presentation events
into durable source or prompt evidence. Persisted `1.0` through `1.2` records
read with zero counts.

BTN-164 adds optional, bounded `test_execution` evidence rather than deriving
process success from graph routing. It records the exact command, temporary
working-directory identity, classification, exit code, collected-test counts,
duration, configured timeout, timeout/cancellation disposition, and process-tree
cleanup result. At most 64 KiB of each stdout/stderr stream is retained, with
observed-byte and truncation metadata. The JUnit report is disposable and its
parser input is limited to 8 MiB. Invalid harness results have an `unavailable`
review verdict; no rejection-cause judgment is fabricated. The same evidence
survives pause/save/load/resume. Legacy `1.0` through `1.5` records remain readable
with process evidence unavailable; their historical inferred outcomes are not
rewritten.

Retaining bounded diagnostic output is an intentional exception to the earlier
no-test-output policy. It makes timeout, launch, and harness failures inspectable
without retaining an unbounded transcript. Output is local project-generated
text and may contain sensitive diagnostics; it is not automatically published.

## BTN-165 amendment — unfinished attempts and durable progression

Execution-record `1.7` permits an `in-progress` attempt without an end timestamp.
Register it atomically with intervention delivery, before context assembly or
generation. Completion replaces this entry under its existing execution ID.
Legacy `1.0` through `1.6` completed records remain readable and unchanged.

A separately versioned `graph_progress` cursor in `RunState` records the exact
next node and whether an attempt is created, started, completed, or its outcome
checkpointed. It also retains bounded automatic-correction context and retry
allowance. Resume authorization before any attempt is explicit through a
`resume_intent` tied to the immutable human action (ADR-0023). There is no
prose-based recovery inference for these new states.

An outcome checkpoint includes the completed execution evidence and exact
successor before completion observations are emitted. Recursion-limit handling
uses the latest checkpoint; application failures reload it without overwriting
it. Unknown started-attempt outcomes are retained for human inspection and
cannot be automatically replayed. A crash between external effects and outcome
persistence therefore has an honest terminal recovery result, not fabricated
success or an exactly-once guarantee.

## Rationale

Keeping evidence in the versioned state contract gives completion, pause, and
resume identical semantics and avoids a parallel event store before one is
needed. Separate record versioning permits the evidence contract to evolve
without falsely changing the meaning of the enclosing v1 run schema.

## Consequences

- Completed and paused runs contain inspectable, attributable evidence.
- Recon can consume references and verdicts without conversation history.
- Artifact content remains in its normal repository location and can be
  checked against its recorded digest.
- A future external event store may index this contract, but must not become a
  second source of graph control state.
- Human-readable prompt contract versions distinguish intentional interface
  changes; the exact template hash distinguishes every content revision.
- A configuration digest can establish identity without persisting provider
  settings that may contain credentials.
