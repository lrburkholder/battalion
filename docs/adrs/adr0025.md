# ADR-0025 — Put Provider Adapters and Transports Beneath Battalion Capabilities

## Status

Accepted

## Date

2026-08-21

## Implementation status

Accepted with RFC-0006 by the human operator through BTN-65 on 2026-08-21. No
runtime or provider behavior changes until follow-up tickets implement the
decision.

## Context

Battalion needs external work intake, knowledge retrieval, repository-service
operations, human notifications, machine events, and remote human interaction.
Those behaviors may be implemented by local code, HTTP APIs, webhooks, MCP,
SMTP, SDKs, or later protocols. If graph nodes consume provider clients or raw
MCP tools, transport vocabulary and ambient credentials become part of graph
authority. If every integration requires a plugin, an unaccepted lifecycle
architecture becomes privileged over deterministic built-in adapters.

BTN-30 already makes `battalion.application` the transport-neutral policy
boundary for presentation clients. ADR-0002 establishes structural binding as
the model for least authority. External integrations need the same dependency
direction without confusing remote provider permissions with Battalion
authorization.

## Decision

Define six initial Battalion capability contracts: `WorkSource`,
`KnowledgeSource`, `RepositoryService`, `Notification`, `OutboundEventSink`, and
`HumanInteraction`.

`RepositoryService` covers shared or remote repository-host operations. It does
not make Git, or any other local source-control engine, part of this capability
contract. Battalion's current Git-dependent local revision and provenance
behavior remains unchanged. A future `VersionControl` contract may abstract
local engine mechanics only after a separate architecture decision reconciles
working-copy writes, scope enforcement, provenance, diff semantics, and quality
gates.

Keep four distinct layers below application policy:

1. a Battalion capability names normalized operations and their caller, data,
   side-effect, failure, and authority semantics
2. a provider adapter maps only those operations to one external provider
3. a least-authority transport supplies bounded mechanics such as local/native,
   HTTP/REST, webhook, MCP, or SMTP
4. the external system owns only its external state

The application boundary admits operations and retains Actor authorization,
operation policy, durable identity, evidence, and idempotency. Provider
adapters and transports cannot broaden an admitted operation. Graph nodes may
receive only capability-specific normalized ports; they never receive raw SDK
clients, authenticated HTTP sessions, credential resolvers, MCP connections,
or arbitrary tool collections.

Separate reads from mutations and externally visible side effects. Every
side-effecting operation has a stable logical identity, typed ambiguous-outcome
behavior, and follow-up BTN-70 evidence/idempotency semantics. Identity
resolution, credential possession, provider permission, discovery, and
delivery do not constitute Battalion authorization.

MCP is an optional transport. Its discovered tools are validation evidence and
must be explicitly bound through a provider adapter; discovery never expands
node authority. Native/local, REST, webhook, and protocol-specific transports
remain first-class.

Future plugins may implement the same adapters or transports, but built-in
implementations do not require plugins and plugins receive no privileged path.
BTN-46 remains responsible for plugin provenance, lifecycle, isolation,
packaging, and permission decisions.

RFC-0006 defines the operation-level contracts, data boundaries, transport
taxonomy, failure semantics, and delivery sequence governed by this decision.

## Consequences

- Provider and transport changes do not redefine graph or application
  semantics.
- The integration runtime needs explicit adapter and transport bindings rather
  than a generic client registry.
- Some provider conveniences remain unavailable until represented as a bounded
  Battalion operation.
- Side effects require more durable evidence than simple request/response
  wrappers.
- KnowledgeSource and RepositoryService can remain unimplemented without allowing
  WorkSource, Intel, or scoped filesystem tools to absorb them.
- MCP and plugins remain optional, replaceable implementation mechanisms.

## Alternatives rejected

Making MCP the integration model leaks transport tool names and discovery into
authority. Giving nodes raw provider clients creates ambient permissions.
Requiring plugins for every integration privileges an unimplemented lifecycle.
A generic external-tool capability is too broad to express least-authority,
side-effect, and failure semantics.
