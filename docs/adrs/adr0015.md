# ADR-0015 — Keep Recon Outside the Completed Execution Graph

## Status

Accepted

## Date

2026-08-13

## Implementation status

Implemented by BTN-22.

## Context

Recon needs the durable BTN-19 execution record to propose BTN-20 candidate
Instincts after a run completes. Adding Recon before the graph's terminal
boundary would let an incomplete run generate knowledge. Adding its output to
`RunState` would mutate the completed execution and mix untrusted candidate
material with graph-control state. Giving Recon repository write tools would
also weaken the human promotion boundary assigned to BTN-23.

The older Recon draft listed conversation history as an input. That conflicts
with BTN-22's accepted contract and with the durable record's purpose.

## Decision

Implement Recon as a post-completion role invoked with a validated `RunState`
and zero or more accepted Instincts for duplicate comparison. Recon rejects a
state unless it is terminal and contains a durable execution record. Its model
context contains that record and the supplied accepted Instincts, never
conversation history.

Recon returns zero or more separately validated `CandidateInstinct` values. A
candidate's run, node execution identifiers, and canonical record references
must resolve to the supplied record. Normalized recommendation duplicates and
identifier collisions with supplied accepted Instincts are discarded.

Recon has no write tools, Intel repository dependency, or graph edge. Its
result is not written into `RunState`. Publishing, editing, acceptance, and
rejection remain the responsibility of the human workflow in BTN-23.

## Consequences

- Recon cannot affect execution status, artifacts, standards, or architecture.
- Candidate output can be independently reviewed without acquiring knowledge
  authority.
- Callers explicitly decide when to invoke Recon after graph completion.
- Candidate persistence and operator decisions are deferred to BTN-23.
