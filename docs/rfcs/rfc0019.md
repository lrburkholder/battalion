# RFC-0019 — Repository-Grounded Architect Plan Contract

**Status:** Draft  
**Date:** 2026-09-03  
**Ticket:** BTN-135  
**Author:** Architecture  
**Related:** `philosophy.md`, `battalion/prompts/architect.md`, RFC-0012, RFC-0013, ADR-0004

---

## Summary

Battalion should strengthen the Architect boundary so an approved Architect plan is a durable, repository-grounded statement of **architectural intent**, not merely a decomposition of the specification and not a remote-control implementation script.

The Architect receives an already admitted, bounded evidence package containing the approved specification plus applicable architectural and repository evidence. It must use those inputs to produce a plan that leaves the Driver free to determine local implementation mechanics while leaving the Driver **no unresolved architectural choice**.

The governing distinction is:

```text
approved spec says what must be true
accepted architectural decisions constrain how the system may be shaped
repository evidence says what structure and conventions already exist
Architect resolves the architectural implications
Driver resolves local implementation mechanics inside that architecture
```

When the supplied authorities conflict or are insufficient to resolve a material architectural choice, Architect does not invent intent. It identifies the unresolved decision and routes it for human resolution through Battalion's accepted decision mechanism.

This RFC does not change workflow admission, Cartography/Recon, Tactician, or repository-context assembly. Those mechanisms determine whether Architect runs and what bounded evidence it receives. This RFC defines what Architect may conclude from that evidence and what its output must guarantee to Driver.

---

## Problem

The current Architect prompt already aims at the right middle ground: it asks for the smallest executable plan a Driver can follow without inventing architecture, tells Architect to prefer existing project structure, and requires assumptions and unresolved decisions to be explicit.

That contract is still underspecified in four important ways.

### 1. The specification is treated as the dominant planning input

A specification describes desired behavior, but it does not by itself describe the architecture that already exists. An Architect planning from the specification in isolation can unnecessarily introduce a new abstraction, dependency, persistence model, ownership boundary, or integration shape even when the repository already has an accepted way to carry the requirement.

Battalion should instead make applicable ADRs and authoritative repository evidence explicit governing inputs.

### 2. Existing architecture is a constraint, not merely a preference

"Prefer existing project structure" is too weak. Where an existing boundary, convention, or abstraction cleanly satisfies the approved requirement, Architect should extend it rather than inventing a parallel one. A new architectural boundary requires evidence that the existing architecture cannot carry the requirement cleanly.

### 3. The Architect/Driver line is not mechanically testable today

A plan can fail in opposite directions:

- **under-specified architecture:** Driver must choose ownership, dependency direction, persistence semantics, public contract shape, integration boundary, or another material design decision;
- **over-specified mechanics:** Architect dictates file edits, function bodies, syntax, local sequencing, or other details the Driver can infer safely from repository evidence.

Both are contract failures.

### 4. Architectural decisions need durable routing

If planning reveals a new long-lived boundary or contract, hiding the decision inside `plan.md` makes architectural memory weaker. Material architecture should be identified as an ADR candidate or routed through the repository's accepted architectural-decision mechanism before Driver is expected to implement it.

---

## Goals

- make approved specification, applicable ADRs, and authoritative repository evidence explicit governing Architect inputs;
- define precedence and conflict behavior among those inputs;
- prefer extension of established repository architecture over unsupported new abstractions;
- ensure an approved plan contains every material architectural decision Driver needs;
- preserve Driver freedom over local implementation mechanics where architecture is already determined;
- distinguish confirmed architecture, proposals requiring human approval, assumptions/evidence gaps, and deferred work;
- identify material new architectural decisions for ADR routing;
- keep deterministic context, scope, schema, and capability enforcement outside prompt prose where possible;
- provide credential-free evals for both under-specification and over-specification failures;
- keep Architect non-mutating with respect to production and test source.

## Non-goals

- selecting whether a ticket needs Architect;
- expanding Architect into Tactician or workflow admission;
- defining Cartography/Recon discovery policy;
- requiring Architect to inspect the entire repository;
- deterministic impact analysis across every repository artifact;
- prescribing Driver's file-by-file implementation;
- turning every implementation choice into an ADR;
- replacing human architectural authority.

---

## Governing input model

Architect consumes an **admitted evidence package** assembled upstream. Conceptually:

```text
ArchitectContext
  approved_specification
  applicable_architectural_decisions[]
  authoritative_repository_evidence[]
  accepted_human_decisions[]?
  explicit_constraints[]?
  evidence_gaps[]?
```

This is a conceptual contract, not a requirement that BTN-135 introduce this exact runtime type.

### Authority order

For architectural planning, the sources have different jobs rather than being interchangeable evidence:

1. **Approved specification** governs required product behavior and acceptance criteria.
2. **Accepted ADRs / accepted human architectural decisions** govern architectural intent and constraints.
3. **Authoritative repository evidence** establishes the current implementation shape, existing boundaries, conventions, dependencies, and reusable abstractions.
4. **Architect inference** may connect those authorities but cannot override them.

Repository evidence cannot silently negate an approved requirement or accepted ADR merely because the code currently differs. Conversely, a specification does not authorize Architect to ignore an accepted architecture because a greenfield design would appear cleaner.

If the sources materially conflict, Architect must surface the conflict as an unresolved decision rather than choosing whichever source is convenient.

### Evidence is admitted, not self-expanded

BTN-135 does not authorize Architect to broaden its own context arbitrarily. Cartography/Recon and context-assembly policy remain responsible for supplying bounded repository evidence. Architect may identify a missing evidence requirement, but missing context is an escalation/input problem, not permission to roam the repository.

## Reuse-before-new-boundary rule

For each material requirement, Architect should ask in order:

1. Does the repository already contain a boundary, abstraction, service, persistence mechanism, dependency direction, or integration pattern that owns this behavior?
2. Is that existing architecture compatible with the approved specification and accepted ADRs?
3. Can the requirement be satisfied by extending that architecture without creating incoherent ownership or coupling?
4. Only if not, what new architectural decision is actually required?

A new abstraction or boundary therefore needs a short architectural justification tied to governing evidence. "Cleaner", "more scalable", or generic best practice is not enough when the admitted repository evidence already provides an adequate solution.

This is not a blanket ban on new architecture. It is a burden-of-proof rule: novelty is justified by the requirement and existing constraints, not by model preference.

## What counts as an architectural decision

Architect owns decisions that materially affect long-lived system shape, including when relevant:

- ownership and module/service boundaries;
- public or cross-module contracts;
- dependency direction;
- persistence semantics and authoritative state ownership;
- external integration shape;
- concurrency/execution ownership where it changes system boundaries;
- capability/security boundaries;
- lifecycle semantics that multiple components must honor;
- durable compatibility/versioning obligations;
- introduction of a new architectural abstraction or dependency with system-wide consequences.

Driver normally owns local implementation mechanics inside those decisions, including:

- exact helper/function names where no public contract is affected;
- local code organization within an already selected boundary;
- syntax and language idioms;
- straightforward reuse of existing utilities;
- test fixture mechanics;
- local error-handling details already determined by established contracts;
- exact file edits where repository structure makes them unambiguous.

The test is authority, not granularity. A small one-line change can be architectural if it changes a public contract; a multi-file refactor can be mechanical if it simply implements an already approved boundary.

## Plan contract

An approved Architect plan should answer all of the following without forcing Driver to invent design intent:

### Goal and governing constraints

- the required behavior/acceptance criteria being implemented;
- the accepted architectural constraints that materially shape the work;
- the repository structures or conventions the plan intends to extend.

### Assumptions, gaps, and unresolved decisions

- material assumptions supported by the admitted evidence;
- missing evidence that prevents a safe architectural conclusion;
- conflicts among governing inputs;
- decisions requiring human authority before implementation may proceed.

### Architecture and boundaries

For each materially affected boundary:

- existing owner/boundary being extended, or justified new boundary;
- responsibility and externally meaningful behavior;
- dependency/ownership direction;
- material failure/lifecycle semantics where relevant.

### Decisions and ADR candidates

Each material decision is classified as one of:

```text
CONFIRMED_EXISTING
CONFIRMED_FOR_THIS_PLAN
PROPOSED_REQUIRES_APPROVAL
ADR_CANDIDATE
UNRESOLVED
DEFERRED
```

The exact machine representation, if any, is an implementation concern. The semantic distinction is required.

### Implementation sequence

The sequence describes **obligations**, dependencies, and verification order, not a script of local edits.

Each step should connect to one or more acceptance criteria and identify any architectural dependency that must already be resolved. Architect may name a file, API, type, or function when that artifact is itself architecturally material or when repository evidence makes it the authoritative boundary. It should not enumerate local edits merely to make the plan look precise.

### Risks and deferred work

Only material risks/deferred items are included. Deferred work must not be required to satisfy the current approved acceptance criteria.

## ADR routing

A plan should identify an ADR candidate when implementing it would establish or materially change a long-lived architectural decision such as:

- a new ownership boundary;
- a new durable cross-module/public contract;
- a new dependency direction;
- a new authoritative persistence model;
- a new external integration pattern;
- a material lifecycle or compatibility rule;
- a replacement of an accepted architectural pattern.

An ADR candidate is not automatically an accepted ADR. Architect proposes the decision; the human-owned architectural decision mechanism accepts, rejects, or revises it.

Routine implementation choices, local helper structure, and direct applications of an already accepted ADR do not need new ADRs.

If an ADR candidate is required to remove architectural ambiguity for Driver, implementation cannot treat the proposal as silently accepted. The plan remains blocked on the accepted decision.

## Architect-to-Driver boundary

The handoff invariant is:

> Given the approved plan and admitted bounded repository context, Driver must not need to make a new architectural decision to satisfy the ticket.

The converse invariant is equally important:

> If architecture is already determined by the approved plan and repository evidence, Driver may infer ordinary local implementation mechanics without returning to Architect for permission.

Examples:

### Correct Architect specificity

```text
Extend the existing Run application service as the owner of terminal-state
validation; persistence adapters continue to store state but do not decide
whether the transition is legal.
```

This fixes ownership and dependency direction while leaving local code shape to Driver.

### Under-specified

```text
Add terminal-state validation somewhere appropriate before persistence.
```

Driver must choose the architectural owner.

### Over-specified

```text
Edit battalion/application/run_service.py, add `_validate_terminal_state()`
above `save_run()`, call it on line X, then add three pytest parametrizations in
specific test files.
```

Unless those exact artifacts are architectural contracts, this is Driver-level mechanics.

## Prompt and controller responsibilities

The Architect prompt should remain concise and role-specific. It should express semantic obligations that require model judgment:

- ground planning in admitted specification, ADR, and repository evidence;
- reuse existing architecture where adequate;
- distinguish architecture from mechanics;
- surface unsupported decisions and evidence gaps;
- identify ADR candidates;
- produce a Driver-complete architectural plan.

Battalion/controller code should continue to own deterministic constraints where enforceable:

- what context is admitted;
- role capability/write scope;
- output/schema validation;
- source mutation restrictions;
- workflow transitions;
- acceptance/interrupt state;
- evidence identity/provenance where supported by the surrounding context system.

BTN-135 should not duplicate these controls as long prompt prohibitions merely because they are important.

## Evaluation strategy

Credential-free tests/evals should exercise the semantic contract using small deterministic fixtures.

At minimum:

### 1. Repository-grounded extension

Fixture contains an existing suitable application boundary. The spec requires adjacent behavior. Passing plan extends that boundary; failing plan invents a parallel service/abstraction without evidence.

### 2. ADR-candidate detection

Fixture requires a new durable ownership or public-contract decision not covered by existing ADRs. Passing plan marks it for decision/ADR routing rather than treating it as an implementation detail.

### 3. Explicit unresolved decision

Fixture contains insufficient or conflicting governing evidence. Passing plan surfaces the unresolved decision and does not manufacture generic architecture.

### 4. Under-specified architecture rejection

Fixture plan leaves Driver to choose ownership, dependency direction, persistence authority, or another material design decision. Evaluator rejects it.

### 5. Over-specified mechanics rejection

Fixture architecture is already settled, but candidate plan dictates local files/functions/syntax unnecessarily. Evaluator rejects it.

### 6. Legitimate local Driver inference

Fixture verifies that a plan does not need to decide trivial mechanics where existing repository conventions make them unambiguous.

Evaluator claims must remain bounded: these tests can demonstrate conformance on fixture classes, not prove that every real-world architectural distinction is objectively classifiable.

## Documentation impact

User/developer documentation describing the workflow should make the boundaries explicit:

```text
Tactician / workflow admission
  decides whether Architect is needed and what workflow is admitted

Cartography / Recon / context assembly
  supplies bounded structural repository evidence

Architect
  resolves architectural intent from approved authorities and produces the plan

Driver
  implements that approved architecture and chooses local mechanics
```

This prevents BTN-135 from accidentally absorbing responsibilities already assigned elsewhere.

## Alternatives considered

### A. Only expand `architect.md`

Rejected as the sole solution. Prompt wording is necessary for semantic behavior, but without a documented contract and eval surface the role boundary remains difficult to preserve as other workflow/context work evolves.

### B. Require detailed file-by-file plans

Rejected. This makes plans appear deterministic but moves implementation mechanics into Architect, increases staleness as code changes, and weakens Driver's ability to use authoritative repository evidence.

### C. Let Driver make small architectural decisions when convenient

Rejected. "Small" is not a stable authority boundary. If a choice changes ownership, contracts, dependency direction, persistence semantics, integration shape, or another material architectural property, it belongs in the architectural decision path regardless of how little code it requires.

### D. Treat repository state as higher authority than ADR/specification

Rejected. Existing code is evidence of current shape, including possible drift or incomplete implementation. It cannot silently override approved product or architectural intent.

### E. Make every material plan decision an ADR

Rejected. The plan may apply already accepted architecture or make ticket-local decisions that do not deserve repository-wide architectural records. ADR routing is reserved for durable architectural consequences.

## Open questions

1. **How explicit should evidence references be in `plan.md`?**  
   Should each material architectural decision cite its governing ADR/repository artifact directly, or is a compact governing-evidence section sufficient unless a decision is disputed?

2. **Should ADR-candidate classification be a structured plan field now, or remain a Markdown semantic contract until a later plan schema exists?**  
   The RFC requires the distinction, but BTN-135 does not necessarily need to create a new typed plan format.

3. **What should happen when repository evidence conflicts with an accepted ADR but the specification can still be implemented either way?**  
   The default proposed here is to surface drift/conflict and preserve the accepted ADR as architectural authority rather than silently ratifying the current code. We should confirm whether that is always the desired Battalion policy.

4. **How much exact artifact naming is useful before it becomes over-specification?**  
   Proposed rule: name artifacts that are architectural boundaries or authoritative existing integration points; avoid naming local edit targets solely as implementation instructions.
