# RFC-0019 — Repository-Grounded Architect Plan Contract

**Status:** Accepted  
**Date:** 2026-09-03  
**Accepted:** 2026-09-04  
**Ticket:** BTN-135  
**Author:** Architecture  
**Related:** `philosophy.md`, `battalion/prompts/architect.md`, RFC-0008, RFC-0012, RFC-0013, RFC-0015, ADR-0004, BTN-98, BTN-110, BTN-117, BTN-157, BTN-158, BTN-208, BTN-223, BTN-224

---

## Summary

Battalion should strengthen the Architect boundary so an approved Architect plan is a durable, repository-grounded statement of **architectural intent**, not merely a decomposition of the specification and not a remote-control implementation script.

The Architect receives an already admitted, bounded evidence package containing the approved specification plus applicable architectural and repository evidence. It must use those inputs to produce a plan that leaves the Driver free to determine local implementation mechanics while leaving the Driver **no unresolved architectural choice**.

The governing distinction is:

```text
approved spec says what must be true
accepted architectural decisions record intended architectural constraints
repository evidence says what structure and conventions actually exist
Cartography indexes architectural significance and structural relationships
Architect reconciles those authorities, including possible documentation drift
Driver resolves local implementation mechanics inside the approved architecture
```

When the supplied authorities conflict or are insufficient to resolve a material architectural choice, Architect does not invent intent. It identifies the unresolved decision and routes it for human resolution through Battalion's accepted decision mechanism.

This RFC does not change workflow admission, Cartography/Recon, Tactician, or repository-context assembly. Those mechanisms determine whether Architect runs and what bounded evidence it receives. This RFC defines what Architect may conclude from that evidence and what its output must guarantee to Driver.

---

## Problem

The current Architect prompt already aims at the right middle ground: it asks for the smallest executable plan a Driver can follow without inventing architecture, tells Architect to prefer existing project structure, and requires assumptions and unresolved decisions to be explicit.

That contract is still underspecified in four important ways.

### 1. The specification is treated as the dominant planning input

A specification describes desired behavior, but it does not by itself describe the architecture that already exists. An Architect planning from the specification in isolation can unnecessarily introduce a new abstraction, dependency, persistence model, ownership boundary, or integration shape even when the repository already has an accepted way to carry the requirement.

Battalion should instead make applicable ADRs and authoritative repository evidence explicit governing inputs.

### 2. Existing architecture is a constraint, not merely a preference

"Prefer existing project structure" is too weak. Where an existing boundary, convention, or abstraction cleanly satisfies the approved requirement, Architect should extend it rather than inventing a parallel one. A new architectural boundary requires evidence that the existing architecture cannot carry the requirement cleanly.

At the same time, existing code and accepted architecture records can diverge. That divergence is itself important evidence: the implementation may have drifted away from an accepted decision, or the ADR may simply be stale because reality forced a later design that humans did not document. Architect must surface that disagreement rather than automatically treating either artifact as current truth.

### 3. The Architect/Driver line is not mechanically testable in full

A plan can fail in opposite directions:

- **under-specified architecture:** Driver must choose ownership, dependency direction, persistence semantics, public contract shape, integration boundary, or another material design decision;
- **over-specified mechanics:** Architect dictates file edits, function bodies, syntax, local sequencing, or other details the Driver can infer safely from repository evidence.

Both are contract failures. Battalion can mechanically validate evidence identity, admitted scope, typed relationships, and Cartography linkage, but architectural materiality remains partly semantic and therefore requires bounded behavioral evaluation rather than a fictional deterministic proof.

### 4. Architectural decisions need durable routing and evidence

If planning reveals a new long-lived boundary or contract, hiding the decision inside `plan.md` makes architectural memory weaker. Material architecture should be identified as an ADR candidate or routed through the repository's accepted architectural-decision mechanism before Driver is expected to implement it.

The same applies when an existing ADR no longer matches the repository. The durable outcome may be to restore the implementation to the accepted decision, amend/supersede the ADR to ratify the implementation reality, or record a different human decision. Leaving the conflict unexplained perpetuates documentation drift.

A bare reference such as `ADR-0038` is also insufficient grounding. The plan needs to identify the particular claim/section it relies on and why that evidence supports, governs, or conflicts with the architectural decision.

## Goals

- make approved specification, applicable ADRs, and authoritative repository evidence explicit governing Architect inputs;
- define precedence and conflict behavior among those inputs;
- detect and surface possible ADR/documentation drift rather than silently preferring documentation or code;
- use Cartography as a primary machine-usable signal of architectural significance while preserving its derived/fallible status;
- prefer extension of established repository architecture over unsupported new abstractions;
- ensure an approved plan contains every material architectural decision Driver needs;
- preserve Driver freedom over local implementation mechanics where architecture is already determined;
- distinguish confirmed architecture, proposals requiring human approval, assumptions/evidence gaps, ADR candidates, drift candidates, and deferred work;
- ground material decisions in section/claim-level evidence relationships with immutable Battalion-owned provenance;
- keep deterministic context, scope, schema, capability, artifact identity, and provenance enforcement outside prompt prose where possible;
- provide credential-free evals for both under-specification and over-specification failures;
- keep Architect non-mutating with respect to production and test source.

## Non-goals

- selecting whether a ticket needs Architect;
- expanding Architect into Tactician or workflow admission;
- defining Cartography/Recon discovery policy;
- requiring Architect to inspect the entire repository;
- deterministic impact analysis across every repository artifact;
- prescribing Driver's file-by-file implementation;
- turning every implementation choice into an ADR;
- automatically declaring either documentation or implementation authoritative when they conflict;
- making Cartography architectural authority;
- proving architectural materiality with a simplistic deterministic rule;
- creating an Architect-only provenance system;
- replacing human architectural authority.

## Governing input model

Architect consumes an **admitted evidence package** assembled upstream. Conceptually:

```text
ArchitectContext
  approved_specification
  applicable_architectural_decisions[]
  authoritative_repository_evidence[]
  cartography_evidence[]?
  accepted_human_decisions[]?
  explicit_constraints[]?
  evidence_gaps[]?
```

This is a conceptual contract, not a requirement that BTN-135 introduce this exact runtime type.

### Authority and reconciliation

For architectural planning, the sources have different jobs rather than being interchangeable evidence:

1. **Approved specification** governs required product behavior and acceptance criteria.
2. **Accepted ADRs / accepted human architectural decisions** record the architecture humans previously approved and therefore establish strong architectural intent.
3. **Authoritative repository evidence** establishes the architecture the system actually implements now: current boundaries, conventions, dependencies, integrations, and reusable abstractions.
4. **Cartography evidence** provides a machine-usable index of mapped architectural entities, boundaries, ownership, relationships, constraints, significance, provenance, and freshness, but remains derived/fallible evidence rather than governing authority.
5. **Architect inference** may connect and compare those authorities but cannot silently choose which one should become canonical when they disagree.

An accepted ADR is therefore not merely optional documentation, but neither is it infallible current truth. Humans frequently update code as a design meets operational reality without making the corresponding documentation change. Conversely, code may have accidentally drifted away from an architecture that is still intended.

When ADR/human-decision evidence and repository evidence disagree materially, Architect should classify the condition as **possible architectural drift** and surface enough evidence for a human to determine which of these broad cases applies:

```text
IMPLEMENTATION_DRIFT
  repository no longer conforms to architecture that is still intended

DOCUMENTATION_DRIFT
  repository reflects an intentional/evolved architecture that the ADR failed to capture

UNRESOLVED_DRIFT
  admitted evidence is insufficient to determine which is stale
```

Repository evidence cannot silently negate an approved requirement merely because the code currently differs. An ADR cannot silently force restoration of older architecture merely because it was once accepted. The conflict itself becomes an architectural decision point: the human may restore the implementation, ratify reality by amending/superseding the ADR, or choose another explicit resolution.

Cartography can strengthen the evidence available for that judgment. For example, an ADR that disagrees with both fresh Cartography structural evidence and current code is stronger evidence of possible documentation drift than an ADR/code disagreement alone. It still does not authorize the model to adjudicate the conflict.

Until resolved, Architect may plan unaffected work but must not make Driver implicitly choose which authority wins.

### Evidence is admitted, not self-expanded

BTN-135 does not authorize Architect to broaden its own context arbitrarily. Cartography/Recon and context-assembly policy remain responsible for supplying bounded repository evidence. Architect may identify a missing evidence requirement, but missing context is an escalation/input problem, not permission to roam the repository.

## Reuse-before-new-boundary rule

For each material requirement, Architect should ask in order:

1. Does admitted repository/Cartography evidence identify an existing boundary, abstraction, service, persistence mechanism, dependency direction, or integration pattern that owns this behavior?
2. Is that existing architecture compatible with the approved specification and recorded architectural decisions, or does it expose possible ADR/documentation drift that must be resolved first?
3. Can the requirement be satisfied by extending that architecture without creating incoherent ownership or coupling?
4. Only if not, what new architectural decision is actually required?

A new abstraction or boundary therefore needs a short architectural justification tied to governing evidence. "Cleaner", "more scalable", or generic best practice is not enough when the admitted repository evidence already provides an adequate solution.

This is not a blanket ban on new architecture. It is a burden-of-proof rule: novelty is justified by the requirement and existing constraints, not by model preference.

---

## What counts as an architectural decision

Architect owns decisions that materially affect long-lived system shape, including when relevant:

- ownership and module/service boundaries;
- public or cross-module contracts;
- dependency direction;
- persistence semantics and authoritative state ownership;
- external integration shape;
- concurrency/execution ownership where it changes system boundaries;
- capability/security boundaries;
- lifecycle semantics that multiple components must honor;
- durable compatibility/versioning obligations;
- introduction of a new architectural abstraction or dependency with system-wide consequences;
- resolution of material drift between recorded architectural intent and implemented reality.

Driver normally owns local implementation mechanics inside those decisions, including:

- exact helper/function names where no public contract is affected;
- local code organization within an already selected boundary;
- syntax and language idioms;
- straightforward reuse of existing utilities;
- test fixture mechanics;
- local error-handling details already determined by established contracts;
- exact file edits where repository structure makes them unambiguous.

The test is authority, not granularity. A small one-line change can be architectural if it changes a public contract; a multi-file refactor can be mechanical if it simply implements an already approved boundary.

## Architectural significance and exact artifact naming

Exact artifact naming is useful when the artifact itself carries architectural meaning. It becomes over-specification when it merely predicts which local files/functions Driver will edit.

Cartography is the primary machine-usable signal for this distinction. An exact artifact reference is presumptively architecturally meaningful when it can be traced to a relevant admitted Cartography entity/boundary, accepted ADR or governing contract, or an explicit proposed architectural boundary.

Conceptually:

```text
exact artifact named by Architect
        |
        +-- mapped to relevant Cartography architectural entity
        +-- itself an accepted governing/public contract
        +-- necessary to describe a proposed architectural boundary
        |
        v
architectural naming is justified
```

An exact source artifact that cannot be connected to one of those architectural signals is presumptively Driver-level mechanics. This is a heuristic, not an absolute prohibition: Architect may still identify a semantic reason the artifact is architecturally material.

Battalion should not replace this rule with simplistic limits such as "no filenames" or "at most N files." Such gates are easy to game and would suppress legitimate references to real contracts.

Cartography freshness materially affects the strength of this signal. BTN-223 owns the separate mechanical freshness backstop inspired by Regiment's pre-commit charter enforcement. RFC-0019 consumes freshness evidence but does not implement the hook itself.

## Decision-evidence relationships

A material Architect decision must identify **what evidence it relies on and what proposition that evidence supports**, not merely list document identifiers.

The semantic model is a typed relationship between an Architect decision and an exact evidence/artifact target. Initial relationship semantics should include at least:

```text
GOVERNED_BY
SUPPORTED_BY
CONFLICTS_WITH
ADR_CANDIDATE_FOR
ADR_DRIFT_CANDIDATE_FOR
```

A relationship carries the human/model-readable semantics:

```text
ArchitectDecisionRelationship
  decision
  relation
  target artifact/evidence
  section/anchor/claim where available
  semantic claim explaining why the target matters
```

Battalion's general artifact/provenance machinery carries the machine identity:

```text
stable artifact identity
exact revision/digest/content identity
repository/run/context provenance
resolution/freshness evidence
```

The **Architect chooses the semantic relationship and claim. Battalion records the evidence identity.** A model must not manufacture Git hashes, digests, revision IDs, or other immutable provenance fields.

Repository-relative Markdown links remain useful human projections, but they are live pointers. Historical plan grounding therefore relies on the exact persisted artifact revision/content identity, so a later ADR amendment does not make an older plan appear falsely unsupported.

This relationship mechanism also carries ADR candidate and ADR drift status. Battalion should not add a separate `adr_candidate: true` boolean that loses which decision needs an ADR, why, and what evidence caused that classification.

BTN-224 owns this implementation and should reuse RFC-0015 artifact/provenance primitives rather than inventing Architect-specific provenance storage.

## Plan contract

An approved Architect plan should answer all of the following without forcing Driver to invent design intent:

### Goal and governing constraints

- the required behavior/acceptance criteria being implemented;
- the accepted architectural constraints that materially shape the work;
- the repository/Cartography structures or conventions the plan intends to extend;
- any material disagreement between those recorded constraints and current repository reality.

### Assumptions, gaps, and unresolved decisions

- material assumptions supported by the admitted evidence;
- missing evidence that prevents a safe architectural conclusion;
- conflicts among governing inputs, including possible ADR/documentation drift;
- decisions requiring human authority before implementation may proceed.

### Architecture and boundaries

For each materially affected boundary:

- existing owner/boundary being extended, or justified new boundary;
- responsibility and externally meaningful behavior;
- dependency/ownership direction;
- material failure/lifecycle semantics where relevant.

### Material decisions and evidence

Each material decision is semantically classified as one of:

```text
CONFIRMED_EXISTING
CONFIRMED_FOR_THIS_PLAN
PROPOSED_REQUIRES_APPROVAL
UNRESOLVED
DEFERRED
```

ADR candidate/drift semantics are represented through the typed evidence relationships described above rather than a separate plan-only status field.

For each material decision, `plan.md` renders concise, human-readable evidence references at section/claim granularity where available. Example:

```markdown
**Decision:** Run transition legality is owned by the application layer.

**Evidence**
- [ADR-0038 § Decision] — governs ownership of transition validation.
- `RunApplicationService` (Cartography: Run lifecycle boundary) — current
  repository evidence confirms the corresponding ownership boundary.
```

The underlying durable relationship retains exact revision/provenance identity without cluttering `plan.md` with hashes.

### Implementation sequence

The sequence describes **obligations**, dependencies, and verification order, not a script of local edits.

Each step should connect to one or more acceptance criteria and identify any architectural dependency that must already be resolved. Architect may name a file, API, type, function, Cartography entity, or schema when that artifact is itself architecturally material. It should not enumerate local edits merely to make the plan look precise.

### Risks and deferred work

Only material risks/deferred items are included. Deferred work must not be required to satisfy the current approved acceptance criteria.

## ADR routing

A plan should identify an ADR candidate when implementing it would establish or materially change a long-lived architectural decision such as:

- a new ownership boundary;
- a new durable cross-module/public contract;
- a new dependency direction;
- a new authoritative persistence model;
- a new external integration pattern;
- a material lifecycle or compatibility rule;
- a replacement of an accepted architectural pattern.

A plan should identify an ADR drift candidate when admitted repository evidence materially conflicts with an accepted architectural record, even if no new architecture is required for the current ticket. Drift is important institutional information and should not disappear merely because the current code works.

The candidate/drift classification is recorded as a typed relationship attached to the material decision and evidence. It is not automatically an accepted decision. Architect identifies the issue; the human-owned architectural decision mechanism accepts, rejects, revises, supersedes, or restores the relevant architecture.

Routine implementation choices, local helper structure, and direct applications of an already accepted ADR do not need new ADRs.

If an ADR candidate is required to remove architectural ambiguity for Driver, implementation cannot treat the proposal as silently accepted. Likewise, if an ADR drift candidate affects architecture needed by the ticket, Driver cannot be left to choose between code and documentation. The plan remains blocked on the accepted human resolution.

## Architect-to-Driver boundary

The handoff invariant is:

> Given the approved plan and admitted bounded repository context, Driver must not need to make a new architectural decision to satisfy the ticket.

The converse invariant is equally important:

> If architecture is already determined by the approved plan and repository evidence, Driver may infer ordinary local implementation mechanics without returning to Architect for permission.

Examples:

### Correct Architect specificity

```text
Extend the existing Run application service as the owner of terminal-state
validation; persistence adapters continue to store state but do not decide
whether the transition is legal.
```

This fixes ownership and dependency direction while leaving local code shape to Driver.

### Under-specified

```text
Add terminal-state validation somewhere appropriate before persistence.
```

Driver must choose the architectural owner.

### Over-specified

```text
Edit battalion/application/run_service.py, add `_validate_terminal_state()`
above `save_run()`, call it on line X, then add three pytest parametrizations in
specific test files.
```

Unless those exact artifacts are architectural contracts or mapped relevant Cartography entities, this is Driver-level mechanics.

### ADR/repository drift

```text
ADR-00XX records persistence adapters as the owner of transition validation,
but fresh admitted Cartography/repository evidence places transition authority
in the Run application service. Record a CONFLICTS_WITH / ADR_DRIFT_CANDIDATE_FOR
relationship and route the conflict for human reconciliation.
```

This preserves both architectural memory and implemented evidence without asking Driver to guess which one is stale.

## Prompt and controller responsibilities

The Architect prompt should remain concise and role-specific. It should express semantic obligations that require model judgment:

- ground planning in admitted specification, ADR, Cartography, and repository evidence;
- identify the particular claim/section supporting each material decision rather than merely naming documents;
- reuse existing architecture where adequate;
- detect material disagreement between accepted architecture records and implemented reality;
- distinguish architecture from mechanics;
- use Cartography/contract significance to justify exact artifact naming;
- surface unsupported decisions and evidence gaps;
- identify ADR candidates and ADR drift candidates semantically;
- produce a Driver-complete architectural plan.

Battalion/controller code should continue to own deterministic constraints where enforceable:

- what context is admitted;
- role capability/write scope;
- output/schema validation;
- source mutation restrictions;
- workflow transitions;
- acceptance/interrupt state;
- artifact resolution and exact revision/content identity;
- evidence provenance/freshness;
- Cartography linkage/freshness evidence where available.

BTN-135 should not duplicate these controls as long prompt prohibitions merely because they are important.

## Evaluation strategy

Credential-free tests/evals should exercise the semantic contract using small deterministic fixtures.

At minimum:

### 1. Repository-grounded extension

Fixture contains an existing suitable application boundary. The spec requires adjacent behavior. Passing plan extends that boundary; failing plan invents a parallel service/abstraction without evidence.

### 2. ADR-candidate detection

Fixture requires a new durable ownership or public-contract decision not covered by existing ADRs. Passing plan marks the material decision with ADR-candidate semantics rather than treating it as an implementation detail.

### 3. ADR/documentation drift detection

Fixture contains an accepted ADR that conflicts with the current implementation, with insufficient evidence to establish whether code or documentation is stale. Passing plan identifies the conflict and requires human reconciliation; failing plans silently enforce the ADR or silently ratify the code.

### 4. Section/claim-level evidence grounding

Fixture contains a relevant ADR whose unrelated sections could superficially support several conclusions. Passing plan identifies the actual governing section/claim and explains the semantic relationship; document-name-only references are insufficient.

### 5. Exact historical evidence identity

A fixture mutates an ADR after the candidate plan was produced. Battalion must retain evidence that the plan was grounded in the exact earlier revision rather than resolving historical provenance to current mutable content.

### 6. Explicit unresolved decision

Fixture contains insufficient or conflicting governing evidence. Passing plan surfaces the unresolved decision and does not manufacture generic architecture.

### 7. Under-specified architecture rejection

Fixture plan leaves Driver to choose ownership, dependency direction, persistence authority, or another material design decision. Evaluator rejects it.

### 8. Over-specified mechanics rejection

Fixture architecture is already settled, but candidate plan dictates local files/functions/syntax unnecessarily. Evaluator rejects it.

### 9. Cartography-significance artifact naming

Fixture includes both a mapped architectural entity/public contract and unrelated local implementation files. Exact naming of the mapped architectural boundary is acceptable; unnecessary local edit instructions are rejected. Missing/stale Cartography evidence reduces the deterministic significance signal rather than fabricating certainty.

### 10. Legitimate local Driver inference

Fixture verifies that a plan does not need to decide trivial mechanics where existing repository conventions make them unambiguous.

Evaluator claims must remain bounded: these tests can demonstrate conformance on fixture classes, not prove that every real-world architectural distinction is objectively classifiable.

## Documentation impact

User/developer documentation describing the workflow should make the boundaries explicit:

```text
Tactician / workflow admission
  decides whether Architect is needed and what workflow is admitted

Cartography / Recon / context assembly
  supplies bounded structural repository evidence and architectural-significance signals

Architect
  resolves architectural intent from approved authorities, records material
  decision/evidence relationships, detects documentation/implementation drift,
  and produces the human-readable plan

Battalion artifact/provenance machinery
  binds semantic references to exact immutable evidence identity

Driver
  implements that approved architecture and chooses local mechanics
```

This prevents BTN-135 from accidentally absorbing responsibilities already assigned elsewhere.

## Alternatives considered

### A. Only expand `architect.md`

Rejected as the sole solution. Prompt wording is necessary for semantic behavior, but without a documented contract and eval surface the role boundary remains difficult to preserve as other workflow/context work evolves.

### B. Require detailed file-by-file plans

Rejected. This makes plans appear deterministic but moves implementation mechanics into Architect, increases staleness as code changes, and weakens Driver's ability to use authoritative repository evidence.

### C. Let Driver make small architectural decisions when convenient

Rejected. "Small" is not a stable authority boundary. If a choice changes ownership, contracts, dependency direction, persistence semantics, integration shape, or another material architectural property, it belongs in the architectural decision path regardless of how little code it requires.

### D. Treat either repository state or ADRs as automatically authoritative in a conflict

Rejected. Existing code is evidence of current reality, including possible accidental drift. ADRs are evidence of accepted intent, including possible stale documentation. Automatically preferring either would erase useful information. A material conflict is itself an architectural signal that requires reconciliation.

### E. Make every material plan decision an ADR

Rejected. The plan may apply already accepted architecture or make ticket-local decisions that do not deserve repository-wide architectural records. ADR routing is reserved for durable architectural consequences and material drift in those records.

### F. Store evidence references only as Markdown links

Rejected. Mutable links are useful navigation but do not preserve what exact evidence the Architect saw when the decision was made.

### G. Add a bespoke typed `plan.md` schema containing all provenance

Rejected. Battalion already has/generalizes artifact and provenance machinery through RFC-0015 and related work. Architect should supply semantic decision/evidence relationships while Battalion supplies immutable identity. `plan.md` is a human-readable projection, not a second provenance database.

### H. Define architectural significance solely by Cartography

Rejected. Cartography is a strong machine-usable signal, especially when freshness is mechanically backstopped, but it remains derived/fallible and cannot represent newly proposed architecture before that architecture exists. Governing contracts and explicit architectural proposals remain valid significance sources.

## Resolved questions

### 1. How explicit should evidence references be in `plan.md`?

**Decision:** Material Architect decisions identify the relevant governing/supporting/conflicting artifact at section/anchor/claim granularity where available and state the semantic proposition being relied upon. A bare document ID such as `ADR-0038` is insufficient grounding.

Human-readable links remain in `plan.md`; immutable revision/content identity is persisted by Battalion's general artifact/provenance machinery.

### 2. Should ADR-candidate classification be a structured plan field now?

**Decision:** Do not create a plan-specific boolean or second provenance schema. ADR candidate and ADR drift candidate semantics are typed decision-evidence relationships implemented through the same general artifact/provenance structure used for governing/supporting/conflicting evidence. `plan.md` renders those relationships for humans.

### 3. How should ADR/documentation drift be resolved?

**Decision:** Neither ADR nor repository automatically wins. Architect surfaces material disagreement as possible implementation drift, documentation drift, or unresolved drift. A human decides whether to restore the implementation, amend/supersede the ADR to reflect reality, or choose another resolution.

### 4. How much exact artifact naming is useful before it becomes over-specification?

**Decision:** Name exact artifacts when they are themselves architectural authorities/contracts, map to relevant admitted Cartography architectural entities/boundaries, or are necessary to describe proposed architecture. Otherwise exact source-edit naming is presumptively Driver-level mechanics unless Architect can explain its architectural significance.

This boundary is only partly deterministic. Battalion can validate mapping, provenance, freshness, and evidence relationships mechanically; representative adversarial evals test the remaining semantic judgment. No simplistic filename-count/no-filename gate is introduced.

Cartography freshness is separately mechanically backstopped by BTN-223, following the Regiment pre-commit-hook principle without making RFC-0019 own Cartography enforcement.

---

## Decision

**Accepted.**

Battalion's Architect plan contract is repository-grounded and evidence-linked. Architect resolves architectural intent from admitted specification, accepted architectural decisions, Cartography, repository evidence, and human decisions; prefers existing architecture where adequate; records material decision/evidence relationships; surfaces drift and unsupported choices; and leaves Driver no architectural decisions while avoiding unnecessary local implementation mechanics.

Follow-up implementation is decomposed rather than folded into this RFC. BTN-223 owns Cartography freshness enforcement. BTN-224 owns typed Architect decision-evidence relationships and human-readable plan projection. Additional follow-ups own prompt/controller integration and the credential-free Architect-plan evaluation suite.
