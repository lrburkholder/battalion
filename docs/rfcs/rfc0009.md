# RFC-0009 — Plugin Architecture and Integration Lifecycle

**Status:** Accepted
**Decision Date:** 2026-08-24
**Ticket:** BTN-46
**Author:** Architecture
**Target:** Post-v2
**Related:** `philosophy.md`, RFC-0006, RFC-0022, ADR-0002, ADR-0025, BTN-28, BTN-30, BTN-31, BTN-58, BTN-105

---

## Summary

Battalion will support third-party plugins as separately packaged implementations of Battalion-owned integration contracts. Plugins extend provider-adapter and transport layers beneath the application and capability boundaries; they do not create peer policy, graph, state, interrupt, scope, or human-decision authority.

The initial third-party execution model is an isolated plugin process communicating with Battalion through a typed, versioned plugin protocol. Built-in implementations may remain ordinary Battalion code, but built-in and third-party implementations expose the same Battalion capability semantics to callers.

Plugin admission is organization-governed. A Battalion Actor with plugin-administration authority approves plugin packages, versions, publisher/provenance evidence, requested capabilities, and permission changes. **Quartermaster** is the administrative surface for this governance. Quartermaster is not an SDLC model role and does not itself own authorization; it presents and invokes typed Battalion application operations on behalf of authorized Actors.

RFC-0006 and ADR-0025 remain authoritative for external integration semantics. The initial capability set at the time this RFC was accepted was `WorkSource`, `KnowledgeSource`, `RepositoryService`, `Notification`, `OutboundEventSink`, and `HumanInteraction`. RFC-0022 subsequently adds `SignalSource` as an additional Battalion-owned capability under the same closed extension and least-authority rules. MCP remains an optional transport beneath provider adapters and has no privileged relationship to the plugin system.

This RFC defines the plugin boundary, lifecycle, permissions, trust model, failure behavior, administrative ownership, and follow-up delivery plan. It does not implement a loader, SDK, registry, marketplace, provider integration, or runtime.

---

## Context

Battalion needs integrations with systems such as GitHub, GitLab, Jira, Slack, Teams, Confluence, telemetry systems, CI systems, and organization-specific services without embedding every provider in core or allowing arbitrary external tools to become graph authority.

RFC-0006 already separates Battalion application policy from capability contracts, provider adapters, transports, and external systems. ADR-0025 further establishes that graph nodes never receive raw SDK clients, authenticated sessions, MCP connections, or arbitrary tool collections.

BTN-46 therefore does not need to invent a second integration abstraction. Its question is narrower:

> How can independently packaged code participate as implementations of already-approved Battalion extension contracts without acquiring authority beyond those contracts?

Battalion's philosophy requires human ownership of architecture and consequential decisions, transparency over hidden automation, and durable repository artifacts as institutional memory. A plugin system must preserve those properties even when executable code originates outside Battalion core.

---

## Goals

- permit third parties and organizations to implement Battalion provider adapters and transports without modifying Battalion core
- keep the extension topology deliberately small and Battalion-owned
- make plugin identity, provenance, compatibility, configuration, permissions, lifecycle, and effective authority inspectable
- keep installation, approval, configuration, authorization, and enablement distinct
- enforce organization-level approval through an authorized Battalion Actor
- isolate third-party failures and authority from Battalion core
- preserve secret boundaries and exclude credentials from manifests, repository configuration, logs, durable execution evidence, fixtures, and model context by default
- preserve RFC-0006 side-effect, idempotency, ambiguity, and evidence semantics
- allow configuration to be portable without making secrets portable
- support deterministic offline Battalion operation when optional plugins are absent or unavailable
- leave room for future public or private registries without making a marketplace part of the initial runtime

## Non-goals

- allowing plugins to add or replace LangGraph nodes or graph edges
- allowing plugins to mutate `RunState` directly
- allowing plugins to redefine interrupt semantics, Reviewer authority, human-decision meanings, or node write scopes
- exposing generic external-tool authority to role prompts
- making MCP the plugin or integration model
- implementing complete Actor/RBAC architecture inside BTN-46
- implementing a marketplace, billing system, hosted plugin service, or commercial control plane
- making a hosted ticket, repository, telemetry, or alerting service silently replace an existing Battalion source of truth
- allowing plugin installation or provider credentials to imply Battalion authorization
- allowing runtime plugin-to-plugin authority composition outside Battalion capability contracts

## Architectural decision

### 1. Closed extension topology

The initial plugin architecture is closed to implementations beneath Battalion-owned contracts:

```text
presentation / graph orchestration
             |
   battalion.application
             |
 authorization + operation policy + evidence
             |
 Battalion capability contract
             |
 provider adapter implementation   <-- plugin extension point
             |
 bounded transport implementation  <-- plugin extension point
             |
 external system
```

A plugin may implement one or more compatible provider-adapter or transport contracts. It may not register arbitrary graph-facing tools or invent a new capability merely by declaring it in a manifest.

Adding a new Battalion capability is an architecture change to core and requires its own accepted decision. Plugin discovery cannot expand the capability set. RFC-0022 is such an accepted core architecture decision for `SignalSource`; its acceptance does not weaken this rule.

### 2. Provider and transport extensions are distinct

Provider adapters own provider semantics. Transports own bounded communication mechanics.

For example:

```text
WorkSource
    |
GitHub Issues provider adapter
    |
HTTP transport
    |
GitHub API
```

or, where a compatible provider implementation is intentionally built on MCP:

```text
WorkSource
    |
GitHub Issues provider adapter
    |
MCP transport
    |
GitHub-capable MCP server
```

A `SignalSource` provider follows the same shape. For example:

```text
SignalSource
    |
CI provider adapter
    |
Webhook or HTTP transport
    |
CI system
```

Changing transport must not change the capability semantics visible to Battalion. MCP tool discovery or webhook delivery is validation/input to binding, never authority expansion.

### 3. Built-in and third-party implementations share semantics

Built-in implementations do not require plugin lifecycle machinery. A built-in local `WorkSource` and a third-party GitHub Issues `WorkSource` nevertheless implement the same Battalion capability contract. The same rule applies to built-in and third-party `SignalSource` implementations.

Being built in, bundled, installed, or third-party does not alter capability meaning, Actor authorization, operation policy, durable identity, or side-effect semantics.

### 4. Third-party plugins execute behind an isolation boundary

The reference and required initial third-party execution model is a separate process communicating through a typed, versioned protocol.

The host owns process creation, lifecycle supervision, timeout, cancellation, health state, and termination. A plugin crash or hang must not crash Battalion core. The host may restart a plugin process according to explicit policy, but retries of externally side-effecting operations remain governed by RFC-0006 idempotency and ambiguous-outcome rules. Observational SignalSource retries and webhook redelivery additionally preserve stable observation identity so transport replay does not manufacture duplicate Signals.

The architecture may later permit an explicitly trusted in-process tier for built-in or first-party code, but in-process execution is not the default third-party model and may not pretend manifest permissions are mechanically enforced if the process has ambient host authority.

Process separation is not, by itself, a complete OS sandbox. Supported implementations must state which resource restrictions are actually enforced on each platform and which remain policy/inspection controls.

### 5. The graph cannot discover plugins

Plugin discovery and selection occur below `battalion.application` and capability contracts. LangGraph nodes cannot enumerate installed plugins, load plugin packages, receive plugin clients, or dynamically invoke plugin-defined operations.

Nodes consume normalized, admitted capability data or ports supplied through existing orchestration/application boundaries. Plugin failure is surfaced as a typed integration/application failure, not as a new graph transition invented by the plugin.

## Identity model

Battalion distinguishes at least three identities:

1. **Plugin package identity** — stable plugin ID, publisher/source identity, exact version, package/content digest, compatible protocol/capability versions.
2. **Integration identity** — Battalion-owned `integration_id` for one configured use of a plugin, independent of provider account name or URL.
3. **External identity** — provider tenant, account, repository, project, workspace, endpoint, or equivalent external reference.

One package may back multiple integrations with different endpoints, credentials, operation grants, projects, or Actors.

A plugin update changes package identity even when the stable plugin ID remains the same. Approval is version-aware.

Signal and `OperationalFinding` identities are Battalion domain/evidence identities defined by RFC-0022, not replacements for plugin package, integration, or external identity.

---

## Manifest contract

A plugin package exposes a machine-readable manifest before execution. The exact serialization belongs to implementation work, but the manifest must include enough information to evaluate compatibility and requested authority without importing or running plugin code.

Minimum manifest concepts:

- stable plugin ID
- human-readable name and description
- publisher/source identity and provenance information
- exact plugin version
- package/content digest or reproducibly derivable digest
- plugin protocol compatibility range
- implemented Battalion capability and/or transport contract versions
- runtime/entrypoint metadata
- package dependencies required for execution
- requested resource categories and operation classes
- configuration schema excluding secret values
- migration/retained-data declarations where applicable

A plugin may declare implementation of an accepted `SignalSource` contract/version exactly as it may declare another accepted Battalion capability. The manifest does not define Signal semantics, add SignalSource operations, or grant permission to create canonical work.

Manifests declare requirements; they do not grant authority.

## Authority and permission model

Effective authority is the intersection of independent constraints:

```text
effective authority =
    plugin-declared support
  ∩ organization/admin approval
  ∩ integration configuration
  ∩ Actor authorization
  ∩ Battalion application/operation policy
```

No layer may widen authority granted by another.

### Plugin-declared support

A plugin states which Battalion contract versions and operations it knows how to implement and which resource classes it requires.

For `SignalSource`, declaring `signal.get`, `signal.list`, or `signal.refresh` support permits only those admitted evidence operations. It does not imply `WorkSource` mutation, Issue creation, Run creation, or repository authority.

### Organization approval

A plugin-administration Actor approves the package/version and the maximum capabilities/resource classes the organization is willing to expose to it.

### Integration configuration

A particular `integration_id` selects only the subset needed for that integration. Read and mutation operations remain separately grantable. For example, allowing `work.get` and `work.list` does not imply `work.comment`, assignment, label mutation, or state transition. Similarly, a SignalSource integration grant remains bounded to operational-evidence receipt/retrieval and does not become a WorkSource grant.

### Actor authorization

The Actor architecture decides who may request particular application operations. Possession of a configured integration or provider credential is not authorization.

BTN-46 does not mandate that `Admin` remain one hard-coded global role. Plugin administration may be represented by a role, a permission such as `plugins.approve`, or a scoped role/permission combination as decided by the Actor/RBAC architecture.

### Application policy

`battalion.application` remains the final Battalion admission boundary and preserves operation, state, idempotency, evidence, and stale-state rules.

Provider-side authorization is necessary only for the external action; it is never sufficient for Battalion authorization.

For SignalSource-derived work, application policy may correlate/classify evidence and prepare an exact Issue candidate, but RFC-0022 requires explicit human confirmation before canonical WorkSource-backed ticket creation.

## Battalion Admin and Quartermaster

Plugin governance requires a Battalion Actor with plugin-administration authority for the relevant organization or Battalion instance.

Administrative decisions include:

- approving or blocking a plugin package
- approving a publisher/source according to organization policy
- approving exact versions or accepted version ranges
- approving requested capability/resource classes
- reviewing permission expansion on update
- pinning or rolling back versions
- disabling or revoking a plugin organization-wide
- controlling which approved plugins are available for project/integration configuration

**Quartermaster** is the administrative product surface for these actions. It is analogous to an organization-curated extension manager/catalog, not an autonomous agent and not an authority source. Quartermaster calls typed application operations and displays their durable results.

A future public registry may supply discovery metadata. An organization may also use a private registry/catalog. In either case:

> discovery != approval != installation != enablement.

Ordinary project users may configure and use only packages and permissions made available by their organization policy unless they separately possess plugin-administration authority.

## Lifecycle

Package lifecycle and integration lifecycle are separate.

### Package lifecycle

```text
DISCOVERED
    |
ACQUIRED
    |
ADMIN_REVIEW
    |----> BLOCKED
    v
APPROVED
    |
INSTALLED
    |
AVAILABLE
```

Additional conditions include `INCOMPATIBLE`, `DISABLED`, `UNHEALTHY`, `REVOKED`, and `REMOVED` where appropriate.

Installation must never imply approval. Approval must never imply that an integration is configured or enabled.

### Integration lifecycle

```text
CONFIGURED
    |
AUTHORIZED
    |
ENABLED
    |----> DISABLED
```

Configuration validation checks compatibility, required grants, referenced credentials, provider/transport binding, and required endpoint/target information without performing unauthorized side effects.

### Updates

An update requires revalidation. An update that changes any of the following requires explicit new administrative approval before activation:

- requested capabilities or operations
- resource/permission classes
- plugin protocol compatibility
- implemented capability contract versions in a breaking way
- publisher/provenance identity
- dependency or isolation requirements that materially change trust

Organizations may pin a known-good version. Rollback must be supported when retained data/configuration remain compatible; otherwise the incompatibility must be explicit before upgrade.

### Removal and retained data

Removing executable plugin code must not delete Battalion-owned audit evidence, Run evidence, Signal/OperationalFinding evidence retained under policy, human decisions, or canonical state. Plugin-owned caches or provider-specific retained data follow explicit retention declarations and operator choice. Unknown retained data is not silently deleted.

---

## Configuration and secrets

Portable configuration identifies plugins, integration IDs, capability bindings, non-secret endpoint/provider settings, operation grants, and symbolic credential references.

Secrets are Battalion-owned values accessed through an approved secret boundary. Manifests and project configuration contain references such as `CredentialRef`, never bearer tokens, passwords, private keys, cookies, or raw authenticated sessions.

Plugin code does not receive general credential-store authority. An admitted operation supplies only the credential/material or scoped authenticated transport required for that integration and operation according to the implementation chosen in follow-up work.

Secrets are excluded from:

- plugin manifests
- repository configuration
- fixtures and tests
- plugin stdout/stderr retained as normal logs
- durable operation evidence
- Signal or OperationalFinding evidence
- model context
- error messages and UI surfaces by default

Redaction is defense in depth, not permission to persist raw secrets first and redact later.

Portable configuration must remain useful when copied between environments without carrying secrets. Missing credential references produce an explicit not-ready state rather than fallback to ambient credentials.

Operational evidence references whose URL or query material itself carries bearer authority must be converted to a safe opaque reference, redacted, or rejected according to the SignalSource adapter contract rather than persisted as ordinary evidence.

---

## Resource grants

The permission model must represent at least these classes where a plugin actually needs them:

- filesystem
- process/subprocess
- network destinations
- credential references
- model/inference access
- Battalion capability operations, including read versus mutation distinctions
- application commands exposed to external human-interaction adapters

The isolated runtime must enforce meaningful constraints where the host/platform can do so. Where a requested constraint cannot be mechanically enforced on a supported platform, Quartermaster must not present it as a guaranteed sandbox property.

Generic `execute`, `call_tool`, `mutate_ticket`, `create_work_from_signal`, or equivalent wildcard authority is rejected in the initial plugin API.

---

## Plugin-to-plugin composition

Plugins may use ordinary package/library dependencies inside their isolated implementation, subject to provenance and packaging rules.

They may not obtain runtime authority by discovering and invoking arbitrary operations exported by another Battalion plugin.

Cross-integration composition is coordinated by Battalion through capability contracts and application policy. For example, a SignalSource plugin cannot directly invoke a WorkSource plugin to turn an observation into an Issue; Battalion owns the OperationalFinding, human-confirmation, and ticket-creation path. This prevents a hidden ambient extension bus beneath the authority model.

---

## Provenance and trust

Before a plugin can be approved, Battalion must be able to identify what executable package is under review.

Minimum durable provenance for package approval includes:

- stable plugin ID
- exact version
- publisher/source identity as available
- acquisition source
- package/content digest
- approval Actor and time
- approved capability/resource ceiling
- compatibility result

A future registry may add signatures, publisher verification, reputation, vulnerability metadata, or certification. Those are additional trust evidence, not substitutes for organization approval.

Unsigned/local development plugins may be supported under explicit development policy, but must be visibly distinguished from organization-approved production plugins.

---

## Audit evidence

Plugin-originated externally visible operations are auditable through Battalion's existing application/capability evidence model.

At minimum, durable evidence associates:

- integration ID
- plugin ID and exact version/digest
- requesting Actor where applicable
- Battalion operation name and schema version
- logical operation/correlation identity
- admission/authorization outcome
- completion, typed failure, or ambiguous outcome
- bounded provider evidence required by the capability contract

For SignalSource operations, durable evidence additionally preserves the stable observation/provenance identity required to recognize replay/redelivery without indiscriminately retaining the raw telemetry payload.

Audit evidence does not require retaining arbitrary raw provider requests, responses, plugin logs, telemetry payloads, or secrets.

Administrative actions such as approve, block, install, update, pin, rollback, disable, revoke, and remove are also durable human actions.

---

## Failure, cancellation, and recovery

Third-party plugin failures are contained beneath the application boundary.

Required behavior:

- startup failure marks the plugin/integration unavailable with a typed reason
- protocol or compatibility mismatch prevents activation
- crashes do not crash Battalion core
- hangs are bounded by host timeout/cancellation policy
- cancellation propagates to the plugin process where possible
- process restart does not itself replay externally side-effecting operations
- ambiguous remote outcomes remain ambiguous until capability-specific reconciliation resolves them
- observational replay/redelivery preserves Signal identity rather than manufacturing duplicate observations
- unavailable optional integrations degrade explicitly; required integrations block only the admitted operation that depends on them
- offline Battalion functions that do not require the plugin remain available

Plugin stdout/stderr may be bounded diagnostic evidence but is untrusted input and must pass secret-handling/redaction policy before persistence or display.

---

## Source-of-truth conflicts

Plugins do not change Battalion source-of-truth ownership merely by connecting to a remote system.

`WorkSource`, `KnowledgeSource`, `RepositoryService`, `Notification`, `OutboundEventSink`, `HumanInteraction`, and the later-added `SignalSource` retain their RFC-0006/RFC-0022 authority semantics. Importing GitHub Issues work does not by itself authorize the requested code changes, a Slack response does not itself resolve a Battalion Human Interrupt, and a telemetry/CI observation does not itself become canonical work.

SignalSource providers are authoritative only for the bounded external evidence they report according to the configured adapter contract. Battalion owns normalization, OperationalFinding correlation/classification, human confirmation of the exact proposed Issue candidate, and the subsequent WorkSource-backed ticket creation path. Provider severity does not silently become backlog priority.

Where a provider and Battalion disagree, the capability contract returns typed revision/conflict evidence. Resolution occurs through Battalion application/human policy rather than adapter guesswork.

Duplicate remote mutation is controlled through stable logical operation identity and the idempotency/ambiguous-outcome requirements already established by RFC-0006 and its follow-up work. SignalSource replay/redelivery uses stable observation identity for the analogous non-mutating duplicate-evidence case.

GitHub Issues becoming Battalion's own practical WorkSource does not make GitHub authoritative for `RunState`, graph transitions, human decisions, accepted Intel, or scoped working-tree writes. Likewise, GitHub Actions, Sentry, Application Insights, or another SignalSource provider does not become authoritative for the existence, priority, or acceptance of canonical work.

---

## Compatibility model

The plugin system requires explicit versioning at two layers:

- the **plugin protocol**, governing host/plugin lifecycle, handshake, configuration, health, invocation, cancellation, and diagnostics
- the **Battalion capability/transport contracts**, governing semantic operations

A plugin advertises compatible ranges in its manifest. Battalion validates compatibility before starting the plugin and again before enabling an integration after upgrade.

A Battalion core upgrade must not silently start an incompatible plugin. Existing configuration remains inspectable even when its plugin is unavailable or incompatible.

A SignalSource plugin that supports an older contract version cannot gain newly added Signal fields/operations or authority by discovery. Compatibility is explicit and validated like every other Battalion-owned contract.

## Disposable proving scenario: GitHub Issues `WorkSource`

The first end-to-end disposable scenario will be a GitHub Issues `WorkSource` plugin.

GitHub Issues is deliberately selected rather than Jira because Battalion is moving toward using GitHub Issues as its own WorkSource. This makes the scenario a dogfooding target while still exercising the important architecture boundaries: remote reads, optional mutations, credentials, repository-scoped external identity, revision/conflict evidence, rate limiting, retries, cancellation, and idempotency.

The scenario must demonstrate:

1. discovery and manifest inspection without executing plugin code
2. Admin review through canonical application/Quartermaster behavior
3. exact-version approval with a bounded organization permission ceiling
4. out-of-process startup and typed protocol handshake
5. normalized `work.get` and `work.list` reads
6. separately authorized `work.comment` mutation with stable logical operation identity
7. denial of an unapproved mutation, such as label/assignment/state change, before provider invocation even when the provider credential itself could perform it
8. portable configuration with a Battalion-owned `integration_id` and symbolic credential reference
9. provider revision/conflict handling and rate-limit classification
10. timeout, cancellation, plugin crash containment, and process restart
11. an ambiguous mutation outcome that is not automatically replayed unsafely
12. an updated plugin version requesting more authority returning to administrative review
13. disable/remove preserving Battalion-owned evidence while leaving offline core behavior usable

The scenario must be deterministic and credential-independent. It should use a mocked or disposable local GitHub-compatible boundary and must not require a live repository token, hosted service, or paid infrastructure.

Disposable scenario code is evidence, not production plugin code. A production GitHub Issues `WorkSource` plugin is a separate follow-up ticket.

RFC-0022 does not replace this initial proving scenario with a SignalSource provider. A representative SignalSource plugin/provider scenario may be added by its own implementation work after the base plugin protocol and grants are exercised.

## Threat model

The implementation tickets derived from this RFC must cover at least:

### Malicious or compromised plugin

A plugin attempts to invoke undeclared operations, access unrelated credentials, widen network/filesystem/process authority, bypass application policy, forge evidence, or crash/hang the host.

**Boundary:** admission happens before invocation; third-party code runs behind the isolated protocol; core authority is never delegated to the plugin.

For SignalSource, forged or malformed evidence is still untrusted provider input; it cannot directly create a Run or canonical Issue and remains subject to normalization, correlation, policy, and human confirmation.

### Over-privileged provider credential

A GitHub token or equivalent credential can perform more operations than Battalion has approved.

**Boundary:** provider permission is not Battalion permission. Denied operations do not reach the plugin/provider.

A telemetry credential with mutation/admin rights similarly grants only the SignalSource operations admitted by Battalion, not those ambient provider capabilities.

### Stale or incompatible plugin

A plugin no longer supports the host protocol or capability version after a Battalion upgrade.

**Boundary:** compatibility validation prevents activation; configuration/evidence remain inspectable.

### Permission-expanding update

A newer version requests additional capabilities, destinations, credentials, subprocess access, model access, or mutations.

**Boundary:** the previous approval ceiling is not inherited; administrative review is required.

### Dependency/provenance change

A package changes publisher/source identity, digest, dependencies, or isolation assumptions.

**Boundary:** trust-relevant drift is visible and revalidated rather than silently accepted.

### Confused deputy

A plugin or external provider possesses authority that the requesting Actor does not.

**Boundary:** Actor/application authorization is evaluated before plugin invocation.

### Secret leakage

A plugin emits credentials in logs/errors or attempts to include them in model context/evidence.

**Boundary:** least credential exposure, no ambient secret-store access, bounded diagnostics, redaction, and secret-exclusion tests. SignalSource additionally uses reference-first/minimize-by-default operational evidence; raw telemetry and credential-bearing references are not ordinary durable results.

### Duplicate remote mutation

A process crash or timeout occurs after an external system may have accepted a mutation.

**Boundary:** stable logical operation identity and explicit ambiguous-outcome handling; restart alone never causes replay.

### Duplicate operational observation

A webhook or polling result is delivered more than once.

**Boundary:** SignalSource adapters preserve stable observation identity across transport retries/redelivery. Deduplication of identical delivery is separate from OperationalFinding correlation across distinct observations.

### Source-of-truth conflict

GitHub Issues or another WorkSource disagrees with local/repository state or a stale imported snapshot.

**Boundary:** typed conflict/revision evidence is returned for human/application policy; provider adapter does not silently choose authority.

A SignalSource provider may also disagree with Battalion's current OperationalFinding classification or Issue state. Provider evidence may update the evidence set, but provider grouping/status does not overwrite Battalion interpretation or canonical work state.

### Plugin-to-plugin escalation

One plugin attempts to discover and invoke another plugin to obtain authority it lacks.

**Boundary:** no ambient plugin bus; composition occurs only through Battalion-owned capability/application coordination. A SignalSource plugin therefore cannot silently route itself into WorkSource mutation.

## Alternatives rejected

### Raw MCP/tool plugins

Allowing plugins to expose arbitrary tools directly to graph nodes would make transport/tool discovery an authority model and undermine RFC-0006. Rejected.

### In-process third-party Python plugins by default

An in-process extension has ambient access that manifest permissions cannot reliably constrain. It may remain a future trusted tier but is rejected as the initial general model.

### Plugin-specific graph nodes

Allowing extensions to contribute graph topology, checkpoints, Reviewer behavior, or interrupt semantics would make the plugin system a second architecture authority. Rejected.

### Marketplace-first design

A public marketplace, billing model, hosted registry, reputation system, or commercial control plane is not required to validate the core lifecycle and would prematurely couple the architecture to distribution. Deferred.

### Provider-owned policy

Letting GitHub, Jira, Slack, telemetry systems, MCP servers, or another provider define Battalion authorization because the remote credential can perform an action creates a confused-deputy boundary. Rejected.

### Plugin-defined Signal semantics

Allowing a plugin manifest or provider adapter to invent its own SignalSource operation names, convert signals directly into work, or make provider grouping authoritative would reopen the extension topology above Battalion-owned contracts. RFC-0022 defines SignalSource in core; plugins only implement that accepted contract. Rejected.

---

## Consequences

### Positive

- external integrations can evolve independently of Battalion core
- third parties can build extensions against stable Battalion semantics
- an organization can heavily curate its available plugin set
- plugin updates cannot silently expand effective authority
- process failures remain contained below core orchestration
- GitHub Issues can become Battalion's own WorkSource through the same public extension model used by third parties
- operational/telemetry providers can implement SignalSource without becoming WorkSources or work-authority providers
- a future plugin ecosystem or enterprise distribution model can be layered on without redefining core authorization

### Costs

- a separate protocol/runtime adds implementation and packaging complexity
- cross-process serialization requires explicit contract/version design
- permission and lifecycle UX is more work than loading Python entrypoints directly
- platform-level sandbox guarantees will vary and must be represented truthfully
- provider adapters may need more normalization work than direct SDK/tool use
- SignalSource plugins additionally need stable observation identity and bounded evidence normalization rather than passing raw telemetry through

These costs are accepted because Battalion's architecture prioritizes structural authority boundaries, transparency, and human control over convenience.

## Follow-up delivery plan

BTN-46 itself remains architecture-only. Accepted work is split into separate tickets:

- **BTN-87 — Plugin manifest, protocol, and compatibility contract**
- **BTN-88 — Isolated plugin host and supervised runtime**
- **BTN-89 — Plugin permission grants and secret/resource brokerage**
- **BTN-90 — Plugin package provenance and lifecycle management**
- **BTN-91 — Quartermaster plugin administration and organization policy**
- **BTN-92 — Portable plugin integration configuration and credential references**
- **BTN-93 — Plugin audit, health, failure, and recovery evidence**
- **BTN-94 — Disposable GitHub Issues `WorkSource` plugin scenario**
- **BTN-95 — Plugin SDK, authoring, and packaging tooling**
- **BTN-96 — Production GitHub Issues `WorkSource` plugin**

BTN-89 and BTN-91 consume the accepted Actor/authorization architecture rather than inventing a second identity/RBAC model.

BTN-94 intentionally precedes BTN-95. The SDK should codify an exercised protocol rather than freeze an API that has only existed on paper.

BTN-96 is production implementation and must not silently promote disposable BTN-94 code.

RFC-0022 adds SignalSource to the capability surface future plugin implementation tickets may target. It does not retroactively add a SignalSource provider implementation to BTN-46's original delivery plan; such providers remain separate follow-up work.

A public/private marketplace or registry, commercial plugin catalog, certification program, or organization-wide hosted control plane may be proposed later from evidence gathered by these tickets. None is required by RFC-0009.

---

## Decision summary

Battalion plugins are comparable to an extension ecosystem such as VS Code in that third parties may build independently packaged functionality against host-owned contracts. Battalion deliberately applies a stricter authority model: third-party plugins operate behind an isolation boundary, implement a closed set of Battalion-owned provider/transport contracts, and are admitted per organization by an authorized Admin through Quartermaster.

The plugin author defines how an external provider implements an approved Battalion contract. The organization Admin decides which package/version and maximum permissions are acceptable. The integration configuration chooses the subset needed for one configured provider instance. The requesting Actor and `battalion.application` decide whether a concrete operation is authorized. No one layer can silently enlarge another.

GitHub Issues is the initial reference `WorkSource` plugin and dogfooding target; it is not granted special core authority by that choice.

RFC-0022 subsequently adds `SignalSource` to the Battalion-owned capability set. A plugin may implement that accepted evidence contract under the same approval, isolation, compatibility, and effective-authority model, but SignalSource support never grants WorkSource mutation, Run creation, repository/graph authority, or permission to bypass the explicit human confirmation required before signal-derived work becomes canonical.
