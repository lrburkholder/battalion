# RFC-0011 — Actor Authorization and External-Action Authority

**Status:** Proposed  
**Ticket:** BTN-64  
**Author:** Architecture  
**Target:** External-integration foundation  
**Related:** BTN-30, BTN-43, BTN-58, BTN-60, BTN-61, BTN-62, BTN-63, BTN-65, BTN-68, ADR-0026

---

## Summary

Battalion must treat identity resolution and operation authorization as separate
steps. Resolving a local or external identity to a durable `Actor` answers only
**who is acting**. It does not answer **what that Actor may do**.

This RFC defines a transport-neutral authorization boundary at
`battalion.application`. Every human-controlled Battalion operation is
identified by a stable Battalion operation name and evaluated against durable
Battalion policy before the operation can mutate Run, worker, assignment,
ownership, Intel, integration, or administrative state.

The decision deliberately does not authorize providers, transports, desktop
widgets, REST routes, MCP tools, notifications, or AI roles directly. Those
surfaces may authenticate or resolve an Actor and may request an operation, but
only Battalion's application policy decides whether the resolved Actor may
perform it.

The authorization result is an explicit value: allow or deny, with the Actor,
operation, target, policy basis, and bounded reason available for inspection and
audit. A denied command must not partially mutate the protected resource.

## Why BTN-64 exists separately from BTN-58 and BTN-60

RFC-0007 established the durable Actor model and the initial project capability
vocabulary: `inspect`, `operate`, `resolve-interrupt`, `approve`, `assign`, and
`administer`. BTN-60 owns project membership persistence and baseline capability
checks.

BTN-64 defines the more general authority contract needed before external
systems become bidirectional:

- identity resolution never implies authority;
- application operations, not provider actions, are the policy vocabulary;
- authorization semantics are identical across local and remote transports;
- contextual policy may consider project, Run, assignment, ownership, or
  bounded human-role facts without importing provider concepts;
- denials are explicit outcomes with no protected-state mutation; and
- authority-changing decisions cannot originate solely from an AI model or an
  external identity mapping.

BTN-60 can therefore implement project capabilities as one policy input while
BTN-68 and later integration work reuse the same operation-level decision
boundary.

## Goals

- preserve the separation of authentication, identity, and authorization;
- define stable Battalion operation identifiers for authorization;
- centralize enforcement at the shared application boundary;
- permit target-aware policy without coupling policy to presentation clients or
  providers;
- define deterministic policy precedence for future organization policy;
- make denied actions explicit and inspectable;
- prevent an external provider's permissions from becoming Battalion authority;
- prevent AI output from granting or widening human authority; and
- give BTN-60, BTN-61, BTN-63, BTN-65, and BTN-68 one common contract to build
  against.

## Non-goals

- selecting an authentication provider or remote session mechanism;
- implementing organization administration;
- defining plugin permission brokerage, which belongs to BTN-89;
- making assignment or ownership grant authority by itself;
- defining provider-specific scopes, OAuth claims, Discord roles, GitHub teams,
  or MCP tool names as Battalion permissions;
- replacing graph write-scope enforcement or other application invariants; or
- implementing every future operation named in this RFC.

## Core invariant

Authorization is evaluated in this order:

```text
credential / local session
        |
        v
external or local identity resolution
        |
        v
Battalion Actor
        |
        v
Battalion operation request + target context
        |
        v
Battalion authorization policy
        |
   allow | deny
        |
        v
canonical application operation (allow only)
```

Each arrow is a boundary, not an implication.

A valid credential may fail to resolve to an Actor. A resolved Actor may lack
project membership. A project member may lack the required capability. An Actor
with the baseline capability may still fail a target-specific policy. A
provider credential may permit an external side effect that Battalion policy
forbids; Battalion must deny the operation before invoking that side effect.

## Operation vocabulary

Policy operates on Battalion-owned operation identifiers. Operation identifiers
are semantic application actions and are independent of presentation route,
transport, or provider API.

The initial human-controlled vocabulary is:

| Battalion operation | RFC-0007 baseline capability | Notes |
| --- | --- | --- |
| `project.inspect` | `inspect` | Project projection only |
| `run.inspect` | `inspect` | Run projection; sensitive-field filtering may further constrain output |
| `run.start` | `operate` | Existing creation/overwrite rules remain authoritative |
| `run.resume` | `operate` | Does not by itself authorize interrupt resolution |
| `interrupt.resolve` | `resolve-interrupt` | May be combined atomically with `run.resume` |
| `intervention.correction.queue` | `operate` | Existing bounded target and inactive-worker rules remain |
| `intervention.design-decision.queue` | `approve` | Existing Architect-target restriction remains |
| `recon.accept` | `approve` | Includes accept and edit-and-accept under the immutable candidate rules |
| `recon.reject` | `approve` | Existing append-only decision rules remain |
| `run.cancel` | `operate` | Worker lifecycle rules still apply after authorization |
| `run.assign` | `assign` | Implemented with BTN-61 target/member rules |
| `ticket.assign` | `assign` | Implemented with BTN-61 target/member rules |
| `ticket.owner.transfer` | `assign` | Ownership remains separate from assignment and authority |
| `membership.grant` | `administer` | Cannot widen authority beyond delegable policy |
| `membership.revoke` | `administer` | Security-sensitive authority change |

Future capabilities may introduce additional operations, but adapters must not
invent aliases with different authorization semantics. A REST `POST`, desktop
button, CLI subcommand, MCP tool, notification action, or provider webhook maps
to one of these application operations before authorization is evaluated.

## Authorization request

The application layer should evaluate a typed request equivalent to:

```text
AuthorizationRequest
  actor_id
  operation
  project_id
  target_type: project | run | ticket | candidate | membership | ...
  target_id: optional stable target identifier
  context:
    assignment facts (optional)
    ownership facts (optional)
    run facts required by policy (optional)
    requested authority delta (optional)
```

The request contains only Battalion-domain facts needed to evaluate policy. It
must not contain provider-specific authority such as GitHub repository
permission names, Discord guild roles, OAuth scopes, MCP server names, or UI
control identifiers.

Provider facts may participate before this boundary as authentication or
identity-resolution evidence, or below it as provider capability constraints.
They do not become positive Battalion authorization evidence unless explicitly
translated into a durable Battalion policy fact by an authorized administrative
operation.

## Authorization decision

Evaluation returns a typed decision equivalent to:

```text
AuthorizationDecision
  decision_id
  actor_id
  operation
  project_id
  target_type
  target_id
  allowed: bool
  required_capabilities
  satisfied_policy_layers
  denied_by: optional policy layer
  reason_code
  reason: bounded presentation text
  evaluated_at
```

`reason_code` is stable enough for CLI, desktop, REST, and integrations to
render or map consistently. Initial denial reasons should distinguish at least:

- unknown or unavailable Actor;
- no project membership;
- missing capability;
- target policy denial;
- assignment or ownership constraint failure when such policy exists;
- stale authority or target context;
- non-delegable authority change; and
- higher-scope policy denial.

Presentation code may translate or summarize the reason. It must not re-run or
reinterpret the policy to decide whether the operation is actually allowed.

## Enforcement boundary

`battalion.application` remains the canonical enforcement boundary established
by BTN-30 and RFC-0007.

An application command that can change protected Battalion state must:

1. resolve or receive the requesting `actor_id` through the trusted caller
   context;
2. construct the canonical Battalion operation and target context;
3. obtain an authorization decision;
4. stop before protected-state mutation if denied;
5. run existing domain/lifecycle invariants if allowed; and
6. retain sufficient decision/action evidence for later inspection.

Authorization is necessary but not sufficient. An allowed operation can still
fail because the Run is in the wrong state, the worker is active, an optimistic
version is stale, a candidate was already decided, a write scope forbids an
operation, or another application invariant fails.

Conversely, satisfying an application invariant does not bypass authorization.
For example, an awaiting-human Run with an unresolved interrupt is not enough to
permit a caller to resolve it.

## Atomicity and denial behavior

A denied operation must not mutate the protected resource it was attempting to
change. In particular, denial must not partially update:

- `RunState`;
- interrupt resolution;
- worker lifecycle metadata;
- Intel candidate decisions;
- assignment or ownership state;
- project membership or grants; or
- external provider state.

Authorization evidence itself may be persisted outside the protected target as
a bounded security/audit event. That evidence is not considered partial success
of the denied operation.

The authorization check should occur as late as necessary to have trustworthy
target context and as early as possible before side effects. If authoritative
state must be read to evaluate policy, the read is permitted as an internal
policy prerequisite; it does not imply that the requesting Actor is entitled to
receive that state as an inspection response.

## Compound operations

Some user intents correspond to more than one authority requirement. The
existing `ResumeRun` path can resolve an interrupt and then resume the Run. That
combined action requires both:

- `interrupt.resolve` / `resolve-interrupt`; and
- `run.resume` / `operate`.

The compound command must not perform the first protected mutation when the
second authorization requirement is denied. The application layer should
therefore evaluate all required operation permissions before applying the
compound transition, or expose a single policy plan whose decision contains all
required capabilities.

The same rule applies to future operations that both change authority and
perform an action under the new authority: an Actor may not grant itself a
capability and consume it in one unchecked transaction.

## Contextual authorization

Project capability is the baseline, not necessarily the complete policy.
Future policy may consider Battalion-owned contextual facts including:

- project membership;
- Run or Ticket assignment;
- Ticket ownership;
- an explicit human responsibility/approval role if one is later introduced;
- target lifecycle state;
- requested authority delta; and
- policy constraints associated with the project or organization.

These facts constrain a baseline grant; they do not implicitly create one.
Assignment and ownership remain responsibility signals and grant no capability
by themselves.

Example: a future project may require an `approve` capability **and** current
Ticket ownership for a particular governed approval. An owner without
`approve` is denied; an approver who is not the owner is also denied under that
policy. The policy is expressed in Battalion terms, not GitHub CODEOWNERS,
provider teams, or chat roles.

## Policy precedence

BTN-64 does not implement organization configuration, but the precedence model
must be fixed before organization policy arrives.

Authorization uses an intersection model: a lower scope may narrow authority
but may not widen a denial or ceiling established at a higher scope.

For future deployments the effective decision is constrained in this order:

```text
non-overridable Battalion safety/application invariants
        INTERSECT
organization policy ceiling (when implemented)
        INTERSECT
project policy and project membership grants
        INTERSECT
Actor-specific grants/restrictions
        INTERSECT
target-specific contextual policy
```

A deny or ceiling at a higher layer cannot be converted to allow by a lower
layer. Absence of a future organization layer does not mean implicit denial in
today's local project model; until organization policy exists, evaluation begins
with Battalion invariants and project policy.

Provider-side permission is intentionally outside this positive authorization
intersection. It is an execution prerequisite after Battalion allows an
external action. A provider may still reject an operation Battalion allowed,
but a permissive provider cannot turn a Battalion denial into success.

## External identity and bidirectional integrations

BTN-63 may resolve an external `(integration_id, external_subject)` to an
`actor_id`. That resolution contributes identity only.

A webhook, Discord interaction, email action, GitHub callback, REST request, or
future MCP-mediated external command must follow the same sequence:

1. authenticate the external caller or message as required by its transport;
2. resolve the external identity to a durable Battalion Actor;
3. map the requested intent to one Battalion application operation;
4. evaluate Battalion authorization for that Actor, operation, and target;
5. execute through the canonical application operation only if allowed.

An external provider role, repository permission, verified email address, OAuth
scope, signed webhook, or successfully resolved identity never skips step 4.

Outbound notifications do not carry authority merely because they were sent to
an Actor. If a notification later contains an actionable control, activating it
creates a new authenticated application request and is authorized at execution
time against current policy.

## Security-sensitive authority changes

`membership.grant`, equivalent future organization grants, plugin
administration authority, credential delegation, and other operations that can
widen authority are security-sensitive.

They require a human Actor with the applicable administrative authority and any
higher-scope delegation constraint. The following are never sufficient by
themselves:

- an AI model recommendation or tool call;
- an AI execution role such as Architect, Driver, or Reviewer;
- a resolved external identity;
- provider administrator status;
- assignment or Ticket ownership; or
- possession of a broad provider credential.

AI may propose an authority change and explain why. It may not be the sole
approver of that change. If future policy allows system Actors to perform
bounded administrative maintenance, that authority must be explicitly granted
by a prior human-controlled policy decision and constrained so it cannot widen
its own grant.

## Relationship to current code

BTN-59 has already introduced durable `Actor` identity and the one-time project
bootstrap event. The bootstrap event records initial capabilities, but current
application operations primarily call `_resolve_human_actor`, which validates
identity, kind, and active status rather than evaluating the requested operation.

That behavior is acceptable as transitional identity plumbing but is not the
BTN-64 authorization boundary. Implementation work should move from
"is this an active human?" to "is this Actor authorized for this exact
operation and target?" without deleting the identity checks.

BTN-60 remains the natural implementation ticket for project membership and
capability persistence. BTN-64 supplies the operation/policy contract that
BTN-60 and external-action work should enforce.

## Recommended implementation shape

The architecture does not require these exact Python names, but the boundary
should resemble:

```text
AuthorizationPolicy.authorize(request) -> AuthorizationDecision

require_authorized(
    actor,
    operation,
    project,
    target,
    context,
) -> AuthorizationDecision
```

Application command handlers call this boundary before mutation. CLI, desktop,
REST, and integration adapters call application commands rather than the policy
engine directly for mutation.

The policy implementation should be deterministic and side-effect-free with
respect to the protected operation. Loading durable policy/context is allowed;
mutating the target during evaluation is not.

## Tests required by implementations consuming this RFC

At minimum, tests should demonstrate:

- an external identity can resolve successfully while authorization is denied;
- the same Actor/operation/target yields the same authorization semantics from
  CLI, desktop, REST, and integration adapters;
- a missing baseline capability denies before protected mutation;
- target-specific policy can narrow but not widen project authority;
- assignment and ownership do not grant authority in the absence of capability;
- a denied compound interrupt-resolution/resume mutates neither step;
- a denied cancellation does not change worker state;
- a denied Recon decision does not create a decision or promote Intel;
- a denied reassignment does not change assignment history or current assignee;
- a broad provider permission cannot bypass Battalion denial;
- an AI/system recommendation cannot directly widen human authority; and
- historical action evidence remains attached to the authority that existed at
  action time rather than being reinterpreted after later grant changes.

## Alternatives rejected

### Treat successful identity resolution as authorization

Rejected. This would make account linking, provider compromise, or identity
mapping equivalent to project authority and collapse the explicit separation
accepted in RFC-0007.

### Authorize provider operations directly

Rejected. Policies such as `github.issue.comment`, `discord.message.send`, or
MCP tool names would couple core authority to transports and create different
security semantics for the same Battalion action.

### Put authorization in each presentation client

Rejected. Desktop, CLI, REST, mobile, and integrations would drift, and any
client with direct persistence access could bypass the UI rule. The application
boundary is already Battalion's authority boundary.

### Let assignment or ownership imply permission

Rejected. Responsibility and authority are separate. Conflating them makes
handoff an implicit privilege-escalation mechanism.

### Use fixed named RBAC roles as the core model

Rejected for now. RFC-0007 deliberately chose explicit capabilities. Named
human roles may later bundle capabilities for administration or presentation,
but operation policy must remain evaluable from durable grants and context.

### Allow AI roles to approve authority changes

Rejected. Battalion exists to preserve human judgment at meaningful authority
boundaries. AI may propose, analyze, and execute approved changes; it is not the
root of human authorization.

## Open review questions

1. Should authorization denials be persisted immediately as a dedicated
   project security log, or should BTN-65's broader external-operation audit
   contract own durable denial evidence while BTN-60 initially returns typed
   decisions?
2. Should `recon.accept` and `recon.reject` remain separate operation IDs or be
   represented as one `recon.decide` operation with a bounded action field?
3. When BTN-61 lands, which operations, if any, should add assignment/ownership
   constraints by default versus allowing projects to opt into those narrower
   policies?
4. Should capability administration distinguish `membership.grant` and
   `membership.revoke` from a broader `membership.manage`, given that grant is
   the privilege-escalating half of the pair?

These questions affect implementation detail but not the core boundary:
identity resolution is not authorization, application operations are the policy
vocabulary, and denial occurs before protected side effects.
