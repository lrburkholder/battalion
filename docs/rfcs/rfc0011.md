# RFC-0011 — Actor Authorization and External-Action Authority

**Status:** Proposed  
**Ticket:** BTN-64  
**Author:** Architecture  
**Target:** External-integration foundation  
**Related:** BTN-30, BTN-43, BTN-58, BTN-60, BTN-61, BTN-62, BTN-63, BTN-65, BTN-68, BTN-70, ADR-0026, ADR-0028

---

## Summary

Battalion must treat identity resolution and operation authorization as separate
steps. Resolving a local or external identity to a durable `Actor` answers only
**who is acting**. It does not answer **what that Actor may do**.

Authorization is evaluated at `battalion.application` against stable
Battalion-owned operation identifiers and Battalion-owned target context before
a protected operation can mutate Run, worker, assignment, ownership, Intel,
membership, integration, or external-provider state.

Desktop, CLI, REST, notifications, MCP-backed integrations, provider adapters,
and future bidirectional integrations do not own authorization semantics. They
resolve identity and request Battalion operations. Battalion decides whether the
resolved Actor may perform them.

## Relationship to RFC-0007 and BTN-60

RFC-0007 established durable Actor identity and the initial project capability
vocabulary:

- `inspect`
- `operate`
- `resolve-interrupt`
- `approve`
- `assign`
- `administer`

BTN-60 owns project membership persistence and baseline capability checks.
BTN-64 defines the reusable operation-level policy boundary around those grants
so the same authorization semantics apply to local and external callers.

Identity resolution, authentication, project membership, assignment, ownership,
provider permission, and authorization remain separate concepts.

## Core invariant

```text
credential / local session
        |
        v
external or local identity resolution
        |
        v
Battalion Actor
        |
        v
Battalion operation + target context
        |
        v
Battalion authorization policy
        |
   allow | deny
        |
        v
canonical application operation (allow only)
```

Each arrow is a boundary, not an implication.

A valid credential may fail to resolve to an Actor. A resolved Actor may lack
project membership. A project member may lack the required capability. An Actor
with a baseline capability may still fail target policy. A provider credential
may permit an external side effect that Battalion policy forbids.

## Operation vocabulary

Policy operates on Battalion-owned operations, not provider API methods,
transport verbs, UI controls, MCP tools, or OAuth scopes.

| Battalion operation | Baseline capability | Notes |
| --- | --- | --- |
| `project.inspect` | `inspect` | Project projection only |
| `run.inspect` | `inspect` | Sensitive-field policy may further constrain output |
| `run.start` | `operate` | Existing overwrite/configuration policy still applies |
| `run.resume` | `operate` | Does not by itself authorize interrupt resolution |
| `interrupt.resolve` | `resolve-interrupt` | May be combined atomically with `run.resume` |
| `intervention.correction.queue` | `operate` | Existing target/inactive-worker constraints remain |
| `intervention.design-decision.queue` | `approve` | Existing Architect-target constraint remains |
| `recon.accept` | `approve` | Includes accept and edit-and-accept |
| `recon.reject` | `approve` | Separate operation from accept |
| `run.cancel` | `operate` | Worker lifecycle rules remain authoritative |
| `run.assign` | `assign` | BTN-61 target/member rules apply |
| `ticket.assign` | `assign` | Default target-context constraints apply |
| `ticket.owner.transfer` | `assign` | Default ownership/target-context constraints apply |
| `membership.grant` | `administer` | Default delegable-authority constraints apply |
| `membership.revoke` | `administer` | Separate operation from grant |

`recon.accept` and `recon.reject` are deliberately separate operation IDs. Their
side effects and audit meaning differ enough that collapsing them into a generic
`recon.decide` operation would make policy and evidence less explicit.

Likewise, capability administration distinguishes `membership.grant` and
`membership.revoke`. Grant is privilege-widening and may require stricter policy
than revocation; a generic `membership.manage` operation would erase that
security distinction.

## Authorization request

The policy boundary should evaluate a typed request equivalent to:

```text
AuthorizationRequest
  actor_id
  operation
  project_id
  target_type
  target_id
  context:
    assignment facts (optional)
    ownership facts (optional)
    run lifecycle facts (optional)
    requested authority delta (optional)
```

The request contains Battalion-domain facts only. Provider-specific roles,
scopes, repository permissions, Discord roles, MCP server/tool names, or UI
identifiers do not become core authorization inputs.

## Authorization decision

Evaluation returns an explicit decision equivalent to:

```text
AuthorizationDecision
  decision_id
  actor_id
  operation
  project_id
  target_type
  target_id
  allowed
  required_capabilities
  satisfied_policy_layers
  denied_by
  reason_code
  reason
  evaluated_at
```

Initial denial reasons should distinguish at least:

- unknown or unavailable Actor;
- no project membership;
- missing capability;
- target policy denial;
- assignment/ownership constraint failure;
- stale authority or target context;
- non-delegable authority change; and
- higher-scope policy denial.

Presentation clients may render these decisions but must not reinterpret policy.

## Enforcement boundary

`battalion.application` remains the canonical enforcement point.

A protected command must:

1. resolve or receive the requesting Actor;
2. map the request to one or more Battalion operations;
3. load only the target context needed for policy;
4. obtain all required authorization decisions;
5. stop before protected mutation if any required decision denies;
6. run existing lifecycle, write-scope, stale-write, and other invariants if
   authorized; and
7. retain the required action/evidence records.

Authorization is necessary but not sufficient. Existing graph, persistence,
worker, lifecycle, immutable-evidence, and write-scope rules remain independently
authoritative after an allow.

## Atomicity and compound operations

A denied command must not partially mutate:

- `RunState`;
- interrupt resolution;
- worker state;
- Intel candidate decisions;
- assignment or ownership state;
- membership or capability grants; or
- external-provider state.

Compound actions must satisfy every authorization requirement before the first
protected mutation. For example, resolving an interrupt and resuming its Run
requires both:

- `interrupt.resolve` / `resolve-interrupt`; and
- `run.resume` / `operate`.

The system must not persist the resolution and then discover that resume is
unauthorized.

The same rule prevents an Actor from granting itself authority and consuming the
new grant in one unchecked transaction.

## Contextual authorization defaults

Baseline capability remains necessary. Assignment, ownership, and role-like
context can narrow authority but never create it.

The initial operations with default target/context constraints are:

### `ticket.assign`

The caller requires `assign`. The target assignee must satisfy the target
project's membership/eligibility rules. Assignment does not grant any capability.

### `ticket.owner.transfer`

The caller requires `assign`. The new owner must satisfy the target project's
ownership/membership eligibility rules. Ownership does not imply assignment or
grant capabilities.

### `membership.grant`

The caller requires `administer`. The requested grant must remain within the
caller's delegable authority and every higher-scope policy ceiling. Possessing
`administer` is not permission to mint arbitrary authority.

Other operations may gain contextual constraints later through explicit policy,
but Battalion does not infer assignment/ownership restrictions merely because
those facts exist.

## Policy precedence

Authorization uses an intersection model. Lower scopes may narrow authority but
cannot widen a higher-scope denial or ceiling.

```text
non-overridable Battalion safety/application invariants
        INTERSECT
organization policy ceiling (when implemented)
        INTERSECT
project policy and membership grants
        INTERSECT
Actor-specific grants/restrictions
        INTERSECT
target-specific contextual policy
```

Organization policy is not implemented by BTN-64. Its future place in the
precedence model is fixed here so later organization administration does not
redefine project semantics.

Provider permission is not a positive Battalion policy layer. It is an execution
prerequisite after Battalion authorizes an external operation. An over-privileged
provider credential cannot turn a Battalion denial into success.

## External identities and bidirectional integrations

External identity mappings establish who is acting, never what they may do.

A webhook, REST request, Discord interaction, GitHub callback, email action, or
future MCP-mediated command follows the same sequence:

1. authenticate the external caller/message as required by the transport;
2. resolve the external identity to a Battalion Actor;
3. map the intent to a Battalion operation;
4. authorize the Actor/operation/target through `battalion.application`;
5. execute only if allowed.

Provider administrator status, OAuth scope, repository permission, verified
email, signed webhook, or successful external identity resolution never skips
step 4.

Outbound notifications carry no authority merely because Battalion sent them to
an Actor. An actionable notification creates a new request evaluated against
current policy when the action is invoked.

## Denial evidence and BTN-65 / BTN-70 ownership

BTN-64 does **not** introduce a second dedicated authorization-security log.

The accepted BTN-65 architecture (RFC-0006 / ADR-0025) already requires each
external capability operation to define the minimum durable evidence it needs,
and keeps operation admission, Actor association, policy, evidence, and
idempotency above provider adapters and transports.

BTN-70 owns the runtime persistence model for externally visible side-effect
attempts: stable logical operation/event identity, Actor/Run/capability/
integration/operation provenance, attempts, outcomes, and replay-safe delivery.
External-action policy denials therefore participate in that evidence model when
an external operation is being admitted or rejected.

BTN-60 may initially return typed authorization decisions for local/internal
operations. BTN-64 does not require every denied local inspection or Run command
to create a new durable security-log record. If Battalion later needs a general
security-event journal covering internal authorization denials as well as
external operations, that should be introduced as one deliberate cross-cutting
audit contract rather than smuggled into Actor authorization or duplicating
BTN-70.

This preserves the ownership split:

- **BTN-65:** architecture and minimum evidence semantics for integration
  capability operations;
- **BTN-70:** durable external side-effect attempt/outcome and idempotency
  implementation;
- **BTN-60:** typed local project membership/capability authorization decisions;
- **BTN-64:** operation-level authorization semantics and denial-before-mutation
  invariants.

## Security-sensitive authority changes

Authority-widening operations, especially `membership.grant`, require an
appropriately authorized human Actor plus all applicable delegation ceilings.

The following are never sufficient by themselves:

- AI/model recommendation or tool invocation;
- Architect, Driver, Reviewer, or other AI execution role;
- external identity mapping;
- provider administrator status;
- assignment or ownership; or
- possession of a broad provider credential.

AI may propose and explain an authority change. It may not be its sole approver.
A system Actor may receive bounded administrative authority only through prior
human-controlled policy and may not widen its own grant.

## Relationship to current code

BTN-59 has introduced durable Actor identity and bootstrap evidence. Current
application paths still primarily resolve an Actor and verify that the Actor is
an active human. That establishes identity suitability, not operation authority.

Implementation should move from:

> is this an active human?

to:

> is this Actor authorized for this exact Battalion operation and target?

without removing the existing Actor validity checks.

BTN-60 remains the natural implementation ticket for project membership and
capability persistence. BTN-61 consumes the contextual rules for assignment and
ownership. BTN-63 supplies external identity mappings. BTN-68 applies the same
operation policy to integration capabilities.

## Recommended implementation shape

The architecture does not require exact Python names, but should resemble:

```text
AuthorizationPolicy.authorize(request) -> AuthorizationDecision

require_authorized(
    actor,
    operation,
    project,
    target,
    context,
) -> AuthorizationDecision
```

Application handlers call this boundary before mutation. CLI, desktop, REST,
and integration adapters call application commands rather than mutating state or
using the policy engine as an alternate execution path.

## Required tests for consuming implementations

At minimum:

- an external identity can resolve successfully while authorization is denied;
- the same Actor/operation/target has identical semantics across clients;
- missing baseline capability denies before protected mutation;
- contextual policy can narrow but not widen project authority;
- assignment and ownership do not grant capability;
- `ticket.assign` enforces target assignee eligibility;
- `ticket.owner.transfer` enforces ownership/member eligibility;
- `membership.grant` cannot exceed delegable authority;
- a denied interrupt-resolution/resume mutates neither step;
- denied cancellation leaves worker state unchanged;
- denied Recon accept/reject creates no candidate decision;
- denied reassignment changes neither current assignment nor history;
- provider permission cannot bypass Battalion denial;
- AI/system recommendation cannot directly widen authority; and
- later grant changes do not reinterpret historical action authority.

## Alternatives rejected

### Identity resolution implies authority

Rejected because account linking or identity mapping would become implicit
privilege grant.

### Provider permissions are Battalion permissions

Rejected because a permissive provider credential must not bypass Battalion
policy.

### Client-specific authorization

Rejected because desktop, CLI, REST, mobile, and integrations would drift and a
new adapter could bypass policy.

### Assignment or ownership implies permission

Rejected because responsibility transfer must not become privilege escalation.

### Generic `recon.decide`

Rejected. Accept and reject remain distinct application operations.

### Generic `membership.manage`

Rejected. Grant and revoke remain distinct because grant is authority-widening
and may require stricter policy.

### AI roles approve authority changes

Rejected. Authority-changing decisions remain a human governance boundary.
