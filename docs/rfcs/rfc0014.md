# RFC-0014 — First-Class Run Types, Semantic Review, and Architecture Workflows

**Status:** Proposed  
**Decision Date:** —  
**Ticket:** BTN-134  
**Author:** Architecture  
**Target:** Post-v2 workflow orchestration  
**Related:** `philosophy.md`, BTN-108, BTN-109, BTN-112, BTN-113, BTN-120, BTN-122, BTN-131, BTN-133, BTN-138, BTN-139, BTN-140, BTN-143, RFC-0012, RFC-0013, ADR-0014, ADR-0017, ADR-0020, ADR-0023, ADR-0024, ADR-0026, ADR-0028, ADR-0032, ADR-0033, ADR-0034, ADR-0035

---

## Summary

Battalion should distinguish a **first-class Run** from a **stage/node/subgraph** by lifecycle and authority semantics, not by how many model calls or graph nodes an activity contains.

The proposed architecture is:

1. A first-class Run has its own durable identity, governing inputs, lifecycle, resumability, audit/history value, terminal outcome, and human/authority boundary.
2. A reusable subgraph is implementation structure inside one or more Run types. It may be shared without owning an independent persistence identity.
3. A stage or node is a bounded step whose meaning is subordinate to its containing Run.
4. **Semantic code review should become a first-class Review Run.**
5. The semantic review mechanics should be implemented as a reusable review workflow/subgraph so other Run types may invoke equivalent review behavior without duplicating policy.
6. The current `prompts/reviewer.md` behavior is not semantic code review. It is checkpoint failure normalization and should remain inside Implementation Run under a distinct capability name such as **RejectionAnalyzer**.
7. A prospective **Architecture Run** also satisfies the first-class-Run criteria. Battalion should design Review Run so Architecture, Specification, Research, and future Run types can reuse the same registered, versioned Run/recipe lifecycle rather than each becoming a bespoke graph.
8. Architecture authority remains human. An Architecture Run may assemble evidence, propose, critique, compare, revise, and decompose work, but only an authorized human decision plus a durable accepted RFC/ADR establishes governing architecture.

This RFC therefore extends Battalion's existing **`WorkflowKind` / `WorkflowRecipe` family** rather than introducing a Reviewer-specific exception or a parallel Run-type abstraction.

---

## Problem

Battalion currently overloads the word `Reviewer`.

Inside Implementation Run, Reviewer is used after deterministic RED/GREEN/REFACTOR checks to classify an unexpected result into a stable rejection cause. That behavior is useful because retry policy and same-cause detection need a bounded semantic normalization step.

It is not the broader Reviewer role described by Battalion philosophy: independent assessment of specification compliance, correctness, maintainability, architectural consistency, and risk.

Expanding the existing checkpoint Reviewer node until it also performs semantic review would create three problems:

- semantic review would inherit Implementation Run's lifecycle even when reviewing human-authored or externally authored work;
- Driver-produced summaries and transient implementation state would be too easy to treat as authoritative review context;
- future workflows such as Architecture Run would likely reinvent independent lifecycle, persistence, iteration, human-decision, and audit semantics.

BTN-131 already establishes registered, versioned `WorkflowRecipe`s and proportionate workflow admission. BTN-134 should extend that model rather than create a second orchestration vocabulary.

---

## Goals

- define a general test for first-class Run types;
- preserve checkpoint failure normalization without conflating it with semantic review;
- make semantic review independently initiable and auditable;
- permit review of Battalion-produced and externally produced changes;
- preserve independent evidence custody from BTN-120;
- reuse BTN-133's accepted distinction between role-attempt results and aggregate Run lifecycle rather than creating another incompatible outcome taxonomy;
- separate severity from confidence;
- distinguish failed requirements from requirements that could not be verified;
- keep Reviewer non-mutating;
- keep human disposition separate from original review evidence;
- make review depth policy-selectable rather than mandatory at one fixed strength;
- test the Run-type criteria against Architecture Run;
- define a reusable Run/recipe family that can support Implementation, Review, Architecture, Specification, Research, and future workflows.

## Non-goals

- implementing Review Run in BTN-134;
- implementing Architecture Run in BTN-134;
- making every implementation use the same semantic review depth;
- allowing Reviewer to repair its own findings;
- allowing Architect models to approve architecture;
- persisting raw model chain-of-thought;
- replacing deterministic tests, linting, security tooling, or checkpoint evaluation with model judgment;
- turning every reusable subgraph into a top-level Run.

## First-class Run criterion

An activity deserves first-class Run identity when the **combination** of the following properties makes independent lifecycle semantics valuable.

| Criterion | First-class Run signal | Stage/subgraph signal |
| --- | --- | --- |
| Independent initiation | useful to start directly from admitted work/evidence | meaningful only after a parent stage |
| Governing inputs | has a distinct authoritative input contract | mainly consumes parent transient state |
| Authority boundary | has distinct human/policy decision points | authority is inherited from parent |
| Durable output | produces an artifact/evidence record valuable on its own | output exists mainly to steer parent |
| Persistence identity | should be addressable, resumed, inspected, cancelled independently | parent identity is sufficient |
| Reuse | useful outside one parent workflow | meaningful only in one workflow |
| Audit/history value | history should appear independently to operators | parent execution history is enough |
| Lifecycle semantics | materially different start/blocked/revision/terminal states | shares parent lifecycle |
| Cost/provenance boundary | independent cost/model evidence is useful | parent attribution is sufficient |
| Termination | can reach a meaningful terminal outcome without parent completion | termination only means “continue parent” |

No single criterion is sufficient. In particular, “uses a model” and “has multiple nodes” are not Run criteria.

A reusable subgraph can satisfy **reuse** without satisfying independent initiation, identity, authority, or terminal-outcome semantics. Reuse therefore does not force first-class Run status.

## WorkflowKind versus WorkflowRecipe

RFC-0012 and ADR-0032 already define the vocabulary BTN-134 should extend. `develop` now contains a finite `WorkflowKind` enum and registered, versioned `WorkflowRecipe` policy artifacts. BTN-134 therefore does **not** introduce a separate `RunType` abstraction.

A **`WorkflowKind`** identifies a first-class Battalion workflow/Run lifecycle. A **`WorkflowRecipe`** selects one exact registered execution strategy for that kind.

Conceptually:

```text
WorkflowKind
  IMPLEMENTATION_RUN
  REVIEW_RUN
  ARCHITECTURE_RUN
  ...

WorkflowRecipe
  recipe_id
  recipe_version
  workflow_kind
  stages[]
  capabilities[]
  mandatory_verification[]
  review/completion requirements
  human_interrupt_policy refs
  failure/escalation policy refs
  termination/upgrade policy refs
```

This keeps `review:standard`, `review:deep-security`, or future compact review variants from becoming separate workflow kinds merely because their internal graphs differ.

ADR-0032 currently registers only `IMPLEMENTATION_RUN`. Review and Architecture should extend that enum and registry when their contracts are implemented.

The application layer owns admission, Run identity, persistence, authorization, exact recipe selection, resume/cancel, human actions, related-Run linkage, and durable outputs. Graphs execute admitted recipes; they do not redefine Run authority.

### Generic Run envelope and kind-specific state

Current `RunState` remains strongly Implementation-shaped: it contains `ticket_id`, `spec`, `write_scope`, `reviewer_rejection_history`, and implementation retry state, while it does not yet persist `workflow_kind` or the selected recipe identity. That is consistent with ADR-0032, which explicitly defers recipe persistence and dispatch to later workflow-admission work such as BTN-143, but it means first-class Review and Architecture Runs should not be added by continually widening one monolithic state model.

The target shape should separate a common durable Run envelope from workflow-kind-specific state/contracts:

```text
Run
  run_id
  project_id
  workflow_kind
  recipe_id + recipe_version
  status / lifecycle metadata
  budget / cost evidence
  execution record / provenance
  human actions / interrupts
  related Run/artifact references
  kind-specific state
      ImplementationState
      ReviewState
      ArchitectureState
      ...
```

The exact Python representation belongs to BTN-108 and consuming implementation tickets. The invariant is architectural: common lifecycle evidence is reusable, while Implementation-only fields must not become nullable baggage on every future Run kind.

## Evaluation: Review Run

Review strongly satisfies the first-class criteria.

### Independent initiation

A Review Run can target:

- a completed or in-progress Battalion Implementation Run change set;
- a human-authored branch or PR;
- an external-agent branch or PR;
- a historical commit/range;
- a supplied patch or diff where repository evidence is available.

Review is therefore not semantically subordinate to Implementation Run.

### Distinct governing inputs

Review requires authoritative context assembled by Battalion:

- approved ticket/specification and revision;
- applicable accepted ADRs/architecture/policies;
- exact target change identity: repository/ref/commit range/diff/patch;
- RED/GREEN/refactor execution evidence when available;
- deterministic tests, quality gates, and tool evidence when available;
- relevant repository context assembled through bounded evidence selection;
- prior durable review evidence when policy says it is relevant.

Driver-authored summaries are supplemental only. They are not authoritative descriptions of requested behavior, changed artifacts, or verification.

### Distinct authority

Reviewer creates evidence. It does not:

- accept the change;
- dismiss its own findings;
- approve architecture;
- mutate reviewed artifacts;
- remediate defects.

Human/Architect/Driver/Refactorer/Guardian or another admitted actor/process owns disposition and remediation.

### Durable output

Review produces a versioned `ReviewResult` valuable independently of any Implementation Run.

### Independent identity/history

Operators should be able to inspect, compare, resume, cancel, and audit a review separately from the implementation that produced the change.

### Distinct lifecycle

A Review Run may terminate with:

- review completed with zero findings;
- review completed with findings;
- blocked/incomplete evidence;
- requirements requiring human verification;
- cancelled;
- failed infrastructure.

These are not equivalent to Implementation Run completion semantics.

**Conclusion:** semantic review should be a first-class Run.

## Alternatives for semantic review

### A. First-class Review Run — proposed

```text
admitted review target
      ↓
authoritative context assembly
      ↓
review recipe
      ↓
durable ReviewResult
      ↓
separate human/remediation disposition
```

**Advantages**

- independently initiable;
- works for non-Battalion changes;
- clean evidence-custody boundary;
- distinct history, cost, retry, and lifecycle;
- compatible with proportionate review recipes;
- clean separation between findings and disposition.

**Costs**

- requires Run-type contracts and application/UI support;
- needs explicit linkage between parent/related Runs;
- requires migration away from overloaded Reviewer terminology.

### B. Expanded Reviewer node inside Implementation Run — rejected

This is simpler initially but fails independent initiation, external-change review, independent history, and lifecycle separation. It also increases the chance that implementation-authored state becomes implicit authority.

### C. Reusable review subgraph only — useful but insufficient

Battalion should have a reusable semantic-review subgraph/recipe component, but sharing graph structure does not supply independent Run identity, authority, audit, or lifecycle semantics.

The subgraph is therefore an implementation mechanism **inside** Review Run and may also be invoked by other admitted recipes where appropriate.

### D. Retain current architecture with no semantic Review Run — rejected

This preserves a useful failure-normalization step but leaves Battalion without the independent review trust boundary described by project philosophy and BTN-120.

## Rename checkpoint Reviewer

The current checkpoint capability should be renamed to avoid semantic overload.

Preferred conceptual name: **RejectionAnalyzer**.

Its contract remains narrow:

```text
expected checkpoint outcome
actual deterministic checkpoint evidence
prior same-checkpoint rejection evidence
        ↓
RejectionAnalyzer
        ↓
normalized accepted/rejected classification
stable cause when rejected
```

Alternative names such as `FailureClassifier` are acceptable, but “Reviewer” should be reserved for independent semantic review.

RejectionAnalyzer remains part of Implementation Run and does not gain independent Run identity.

---

## Review inputs

A proposed versioned input contract:

```text
ReviewInput v1
  review_target
    project_id
    repository identity
    target kind: branch | pull-request | commit-range | patch | implementation-run
    immutable revision/diff evidence where available
  governing_work
    WorkItem/spec identity + revision
  architecture_refs[]
  policy_refs[]
  execution_evidence_refs[]
  repository_context_refs[]
  prior_review_refs[]
  evidence_limitations[]
  requested_recipe_id / admitted review policy
```

Every retained input is a bounded reference/digest/provenance record consistent with Battalion's existing execution-evidence model. Raw provider clients, unrestricted repository access, and arbitrary external payloads do not become graph state.

For patches or changes without an authoritative repository revision, the Run records that limitation explicitly. Lack of reconstructable code provenance may block some findings or move requirements into human-verification status; it is not silently treated as success.

## SemanticReviewResult v1 and BTN-133 outcome layering

The existing `ReviewResult` in `battalion/state/models.py` represents checkpoint acceptance/rejection and should migrate with RejectionAnalyzer rather than constrain semantic review.

Accepted RFC-0013 (BTN-133) now fixes an important layering rule:

```text
RoleExecutionResult = what happened in one bounded role/node attempt
RunStatus           = aggregate workflow lifecycle state
domain artifact     = durable evidence produced by the workflow
```

BTN-134 should preserve that separation. `SemanticReviewResult` therefore does **not** carry its own `COMPLETED / BLOCKED / ESCALATED` lifecycle enum. Those meanings already belong to `RoleExecutionResult` and `RunStatus`.

Conceptually:

```text
SemanticReviewResult v1
  schema_version
  target_revision
  findings[]
  unverifiable_requirements[]
  evidence_limitations[]
  summary
  provenance refs
```

The Reviewer node attempt separately records a BTN-133 `RoleExecutionResult` such as `COMPLETED_WITH_CHANGE`, `BLOCKED`, or `ESCALATED`. The Review Run separately records its aggregate `RunStatus`.

A successfully completed semantic Review Run always produces durable review evidence, including the valid case where `findings = []`.

### Finding

```text
ReviewFinding
  finding_id
  category
  violated_requirement_or_invariant
  evidence_refs[]
  trigger
  impact
  severity
  confidence
  affected_artifacts[]
```

A finding is valid only when it identifies a concrete violated requirement/invariant or defect and supplies enough evidence to explain a realistic trigger and impact.

Unsupported speculation, stylistic preference, and “might be better” observations are not findings.

### Severity and confidence

Severity represents impact if the finding is real.

Confidence represents strength of evidence that the finding is real.

They are independent. A high-severity/low-confidence concern may require human verification or specialist review without being represented as a confirmed high-confidence defect.

### Unverifiable requirements

Requirements that cannot be verified from available evidence are recorded separately:

```text
UnverifiableRequirement
  requirement_ref
  reason
  missing_evidence[]
  human_verification_needed
```

“Could not verify” is neither approval nor failure.

## Reviewer role-result semantics

BTN-133 defines `COMPLETED_WITH_CHANGE` as successful production of the mutation **or artifact** required by a role contract. A read-only semantic Reviewer that completes successfully still produces a durable `SemanticReviewResult` artifact, even when it contains zero findings.

Therefore the initial semantic Reviewer policy should be:

```text
COMPLETED_WITH_CHANGE
  reviewer produced a valid SemanticReviewResult artifact
  findings may be empty or non-empty

BLOCKED
  required context/evidence or a mechanically satisfiable capability is unavailable

ESCALATED
  proceeding requires authority the Reviewer does not possess

COMPLETED_WITH_NO_CHANGE
  not admitted merely to mean "no findings"
```

This explicitly resolves RFC-0013's open question about whether Reviewer should use `COMPLETED_WITH_NO_CHANGE` for “no findings”: **no**. “No findings” still produces review evidence and therefore satisfies the artifact-producing success contract.

Examples:

```text
target diff unavailable or unreconstructable evidence required by policy
    -> BLOCKED

ticket requirement cannot be interpreted without a product/architecture decision
    -> ESCALATED

review completes and finds zero defects
    -> COMPLETED_WITH_CHANGE + SemanticReviewResult(findings=[])
```

A Reviewer role result never selects remediation or workflow routing itself; Battalion validates it and applies deterministic application/graph policy as required by RFC-0013.

---

## Findings and disposition are separate records

Consistent with BTN-120, a Review Run owns immutable review evidence. Later actions do not rewrite it.

A separate disposition record may say that a finding was:

- accepted;
- dismissed with rationale;
- deferred;
- remediated by a linked change/Run;
- superseded by new governing evidence;
- escalated for specialist or human verification.

Disposition records reference the original finding ID and Actor/human authority evidence.

Reviewer cannot create its own terminal disposition.

## Expected human gates versus escalation

Architecture and Review both contain human authority boundaries, but not every expected human decision should be represented as a BTN-133 `ESCALATED` role result.

`ESCALATED` means a role discovers that it cannot choose because authority outside its admitted contract is required. A **planned human gate** is instead part of the admitted workflow recipe.

For Architecture Run:

```text
Architect proposal
    -> planned human review/decision gate
    -> revise / accept / reject
```

is normal lifecycle behavior, not an error-like escalation.

By contrast:

```text
Architect discovers an unanticipated ownership/policy decision outside
the admitted architecture authority
    -> ESCALATED
```

The same distinction applies to Review: ordinary human disposition of findings is a planned downstream authority boundary, while an unexpected requirement that only a human/product/architecture authority can interpret may be an escalated Reviewer attempt.

This keeps BTN-133's role-result semantics meaningful rather than turning every human-in-the-loop step into “escalation.”

## Relationship to Implementation Run

Semantic review should be **policy-selected**, not universally fixed at one depth.

RFC-0012 already establishes deterministic-first workflow admission, Tactician escalation on uncertainty, registered recipes, and explicit human choice for reduced workflows.

`develop` sharpens an important terminology problem. The current `WorkflowRecipe` contract contains `independent_review_required: bool`, and compact admission requires `INDEPENDENT_REVIEW`; however, the concrete Implementation `Reviewer` still performs checkpoint verification and rejection-cause normalization, not semantic independent review. BTN-134 should prevent that overloaded phrase from becoming a permanent public contract.

Long-term recipe policy should distinguish deterministic/checkpoint verification from semantic Review Run requirements. Conceptually:

```text
Implementation recipe
  mandatory_verification:
    behavioral evidence
    deterministic gates
    checkpoint verification as required

  semantic_review_requirement:
    none | standard | deep/specialist | policy-selected
```

The exact enum/schema belongs to follow-up implementation. The important point is that `independent_review_required: bool` is transitional/underspecified for proportionate semantic review.

BTN-134 extends the workflow model as:

```text
Implementation Run
   ↓
change + deterministic execution evidence
   ↓
semantic review completion policy
   ├─ no Review Run required by admitted policy
   ├─ linked standard Review Run
   └─ linked deeper/specialist Review Run
```

Semantic review should **not** become another `WorkflowStage` such as `SEMANTIC_REVIEW` inside the Implementation graph. If an Implementation recipe requires semantic review before its admitted workflow is complete, it should require a **related first-class Review Run** satisfying the selected review policy while preserving a separate `run_id`, lifecycle, evidence record, and disposition boundary.

Tactician may recommend among **admissible** review recipes when deterministic admission is uncertain, subject to the human authority defined by RFC-0012. It does not invent review graphs, silently waive hard policy, or collapse the Review Run into Implementation state.

## Battalion-owned semantic review construction

RFC-0013 also establishes that models submit **semantic arguments** through Battalion-owned capabilities while Battalion validates and constructs canonical persisted results. Semantic Review should reuse that pattern.

The Reviewer should not be required to serialize the complete durable `SemanticReviewResult` envelope correctly in one model response.

Conceptually:

```text
Reviewer model
    |
    | Battalion-owned capability surface
    v
report_finding(...)
report_unverifiable_requirement(...)
submit_role_result(...)
    |
    v
Battalion validation
    - allowed role result kinds
    - finding schema
    - severity/confidence independence
    - requirement/evidence references
    - trigger/impact requirements
    - evidence custody
    |
    v
canonical SemanticReviewResult + RoleExecutionResult
```

A Battalion MCP server is the preferred general model-facing adapter under RFC-0013, while MCP remains transport rather than authority. Provider-native tool/function calls or direct application adapters may expose the same domain capabilities. All paths converge on Battalion-owned validation and canonical construction.

This is particularly important for semantic review because vague prose, unsupported speculation, malformed severity/confidence combinations, or unverifiable requirements must not become durable findings merely because a model emitted syntactically valid JSON.

## Model independence

Independent review is a trust boundary, not merely a role label.

At minimum:

- the semantic Reviewer execution must not share hidden mutable model-session state with the implementation author;
- its context is assembled independently from authoritative evidence;
- the reviewed change cannot redefine the governing review prompt/policy for its own Run;
- model/prompt/config identity and cost evidence are retained using existing Battalion provenance mechanisms.

A different provider/model from the Driver may be preferred by project policy for stronger independence, but this RFC does not make “different vendor” a universal requirement. Independence is primarily enforced by evidence custody, clean context construction, role authority, and durable provenance.

---

## Review Run persistence and linkage

Each Review Run has its own canonical `run_id`, status, state version, execution record, cost evidence, and history.

It may link to:

- originating Implementation Run;
- reviewed repository revision or PR;
- prior Review Runs;
- remediation Runs;
- human disposition records.

Links do not merge persistence ownership. The reviewed Implementation Run remains immutable evidence of what happened there; Review Run records what the independent review observed.

Retry/resume continues within the same Review Run when retrying infrastructure or bounded recipe steps. A materially changed target revision creates a new review target revision and, by default, a new Review Run or explicit review iteration according to future revision policy. Silent retargeting is forbidden.

---

## Application and CLI/UI presentation

Review should appear as a first-class Run kind in history rather than as a hidden Implementation node.

Minimum presentation:

- Run kind and recipe/version;
- reviewed target and immutable revision evidence;
- governing ticket/spec/ADR references;
- status and blocked reason;
- findings count by severity and confidence;
- unverifiable requirement count;
- linked originating/remediation Runs;
- model/provenance and token/cost evidence;
- human disposition status without mutating the original review result.

CLI and desktop use the same application contract; presentation clients do not own review semantics.

## Evaluation: prospective Architecture Run

Architecture also satisfies the first-class criteria.

### Independent initiation

An architecture ticket/design question may begin without an Implementation Run.

### Governing inputs

Architecture requires a distinct bounded context: approved problem/specification, existing ADRs, Cartography/repository evidence, relevant accepted Intel/research, project policy, constraints, and human-provided organizational context.

### Authority boundary

This boundary is stronger than semantic review:

```text
Architect proposes / critiques / compares
             ↓
human reviews, comments, decides, or requests revision
             ↓
Architect revises if requested
             ↓
authorized human accepts or rejects
             ↓
accepted RFC/ADR becomes governing repository artifact
```

Model agreement or model-to-model consensus never establishes architectural authority.

### Durable output

Meaningful terminal outputs include:

- accepted RFC/ADR;
- rejected/no-change decision with rationale;
- blocked for missing evidence/authority;
- cancelled;
- downstream implementation-ticket decomposition after acceptance.

### Persistence/lifecycle

Architecture is iterative and human-centered. It needs resume across evidence gathering, proposal, annotation/revision, and decision points. BTN-122's revision-aware annotations are therefore a reusable primitive, not merely UI polish.

**Conclusion:** Architecture should eventually be a first-class Run represented by `WorkflowKind.ARCHITECTURE_RUN` (name subject to implementation conventions) with registered `WorkflowRecipe`s beneath it.

## Minimum viable Architecture Run

The minimum path to execute today's `web-architect:candidate` work inside Battalion is:

```text
ArchitectureInput
  ↓
bounded authoritative evidence assembly
  ↓
Architect proposal with alternatives/tradeoffs
  ↓
HumanInterrupt: review / annotation / decision
  ├─ revise → Architect
  ├─ request evidence → bounded evidence assembly
  ├─ reject/no-change → terminal decision artifact
  └─ accept
       ↓
durable RFC/ADR
       ↓
implementation-ticket decomposition
       ↓
terminal ArchitectureResult
```

This is deliberately not an autonomous Architect↔Reviewer debate loop. Specialist critique or steelman stages may be registered recipe components, but they provide evidence to the human decision.

## Reusable primitives and ticket relationships

### BTN-108 — typed Run input/output contracts

Direct substrate. ReviewInput, SemanticReviewResult, ArchitectureInput, and ArchitectureResult should be specific contracts registered under the common Run-type boundary.

### BTN-109 — declarative failure and escalation policies

Direct substrate for blocked evidence, retry, escalation, and terminal behavior without hard-coding policy into each graph.

### BTN-113 — bounded iterative workflow edges

Direct substrate for Architecture revision loops and any review re-evaluation loop. Termination must remain deterministic and bounded.

### BTN-122 — anchored annotations and revision-aware human review

Direct substrate for human review of architecture proposals and likely useful for disposition/commentary on semantic findings.

### BTN-112 — architectural significance signals and steelman interrupts

Reusable Architecture recipe stage/policy input. It should not become architectural authority; significance and steelman outputs are evidence for the human/Architect workflow.

### BTN-120 — independent review evidence

Normative trust boundary for Review Run evidence custody and disposition separation.

### BTN-133 / RFC-0013 — typed role execution outcomes

Normative role-attempt result model. Reviewer and Architect attempts should reuse `RoleExecutionResult` and role-aware result policy. `SemanticReviewResult` and architecture artifacts should remain domain evidence rather than duplicating role/run lifecycle enums. Planned human gates are workflow semantics; `ESCALATED` is reserved for discovered authority boundaries.

### BTN-131 / RFC-0012 — workflow admission and registered recipes

Normative admission model. Review depth and future Architecture recipes are registered/versioned and selected through deterministic policy plus Tactician only where uncertainty remains.

### BTN-138 / ADR-0032 — finite WorkflowRecipe registry

Implemented substrate on `develop`. BTN-134 should extend its existing `WorkflowKind` and exact recipe-version semantics rather than adding a parallel Run-type registry.

### BTN-139 / ADR-0033 — deterministic workflow admission

Implemented substrate on `develop`. Its bounded evidence-first classification reinforces the distinction between pre-admission assessment and an actual Run.

### BTN-140 / ADR-0034 — advisory Tactician

Implemented substrate on `develop`. Tactician is explicitly pre-admission evidence rather than a Run or graph node, providing a useful precedent that a model-backed activity does not automatically deserve Run identity.

### BTN-143 — admitted recipe persistence/resume

Required substrate for durable `workflow_kind` and exact `recipe_id`/`recipe_version` interpretation across resume/history. BTN-134 should not imply this identity is already persisted in current `RunState`.

### ADR-0035 — in-Run role-contract correction

A useful negative test for the first-class Run criterion. The correction path may perform another model call, persist attempt evidence, retry, and escalate to a human, yet remains inside the parent Implementation Run because it has no independent initiation, governing purpose, authority boundary, or terminal artifact. Iteration, persistence, and model use therefore do not by themselves justify a new Run.

## Additional architecture work required

BTN-134 should decompose accepted architecture into follow-up tickets rather than implement it directly.

Expected follow-up areas:

1. **WorkflowKind/common Run lifecycle extension** — extend the existing `WorkflowKind` registry beyond Implementation and define common durable Run-envelope versus kind-specific state boundaries, coordinated with BTN-108 and BTN-143.
2. **Review contracts** — semantic `ReviewInput`, `SemanticReviewResult`, findings, unverifiable requirements, disposition linkage, and Reviewer-specific BTN-133 role-result policy.
3. **Reviewer/RejectionAnalyzer split** — rename/migrate checkpoint review semantics without changing retry behavior.
4. **Review Run graph/recipe** — independent context assembly, semantic review execution, Battalion-owned result construction, durable output, BTN-133 block/escalation paths, and planned human disposition boundaries.
5. **Review target adapters/application intake** — Battalion Run, branch, PR, commit range, patch/diff.
6. **Review application/UI/CLI surfaces** — start, inspect, resume, cancel, findings, evidence, cost, linkage, disposition.
7. **Review workflow admission** — standard/deep/optional policy integrated with RFC-0012 recipes.
8. **Architecture Run contracts** — versioned inputs/artifacts plus explicit separation among Architect RoleExecutionResult, RunStatus, planned human decisions, and accepted/no-change architecture decisions.
9. **Architecture Run MVP graph** — evidence → proposal → human revision/decision → durable artifact → ticket decomposition.
10. **Artifact annotation integration** — BTN-122-backed revision comments for RFC/ADR review.
11. **Human acceptance and repository promotion** — authorized acceptance creates/promotes durable governing RFC/ADR without allowing model self-approval.
12. **Architecture ticket decomposition integration** — accepted architecture emits proposed implementation tickets through the canonical ticket authority path.

These may reuse or be sequenced after BTN-108/109/112/113/122 rather than duplicating those primitives.

## Consequences

### Positive

- “Run” gains a principled meaning instead of becoming a synonym for “graph.”
- Semantic review becomes independently reusable and auditable.
- Human/external work can receive the same Review Run as Battalion-produced work.
- checkpoint retry semantics stay small and deterministic in purpose.
- Architecture can move into Battalion later without inventing incompatible lifecycle semantics.
- the current external web-architect loop becomes a replaceable executor/presentation choice rather than permanent architecture infrastructure.
- model cost and identity are attributable at the workflow humans actually perceive.

### Costs

- first-class Run linkage is more complex than embedding every stage in one graph;
- current code assumes a narrow role vocabulary and checkpoint-oriented `ReviewResult`, while BTN-133's accepted role-result contract must now be consumed rather than duplicated;
- UI/history must handle related Runs rather than one monolithic Run;
- architecture acceptance requires careful Actor authorization and repository-artifact promotion semantics;
- recipe/run contract versioning becomes an explicit compatibility responsibility;
- current Implementation-oriented `RunState` requires a deliberate common-envelope/kind-specific-state evolution rather than unbounded field growth;
- current `independent_review_required` terminology must migrate without confusing historical checkpoint assurance with semantic Review Run policy.

---

## Alternatives rejected

### Treat every role as a Run

Role isolation does not imply Run identity. RejectionAnalyzer, Refactorer stages, deterministic verification, and many future specialist checks remain nodes/subgraphs unless they independently satisfy lifecycle criteria.

### Treat every reusable graph as a Run

Reuse alone is insufficient. A reusable review subgraph can serve several recipes while only the admitted Review workflow owns independent identity.

### One universal SDLC Run

A single giant Run makes independent review, architecture, research, or specification history subordinate to one parent lifecycle and prevents clean initiation on externally produced work.

### Bespoke graph per workflow

This would recreate Run lifecycle, persistence, failure, human action, and audit semantics repeatedly. Existing `WorkflowKind` + registered `WorkflowRecipe` semantics should carry the common policy/lifecycle vocabulary while allowing different graphs.

### Make every iterative or model-backed activity a Run

ADR-0035 demonstrates why this is wrong. A role-contract correction can add model attempts, persisted evidence, bounded retry, and human escalation while remaining meaningful only as part of its parent Implementation Run. First-class Run identity follows independent lifecycle and authority semantics, not implementation complexity.

---

## Open decision questions

The proposal is directionally complete, but these details should be resolved before acceptance:

1. Does a changed target revision always create a new Review Run, or may one Run contain explicit immutable review iterations?
2. What minimum independent-model policy should be configurable for Review Run: clean session only, different model configuration, different provider, or project-selectable tiers?
3. Should human disposition be a generic cross-Run evidence contract or initially Review-specific and later generalized?
4. What exact recipe contract should replace the transitional `independent_review_required: bool` without overfitting to today's Review variants?
5. Which follow-up ticket should own RFC/ADR promotion after Architecture Run human acceptance versus ticket decomposition?

---

## Proposed decision

Adopt the first-class Run criterion and extend the existing `WorkflowKind` / `WorkflowRecipe` distinction defined by RFC-0012 and ADR-0032, while consuming RFC-0013's accepted `RoleExecutionResult` semantics for individual role attempts.

Approve semantic Review as a first-class Run whose internal semantic-review logic is reusable as a registered subgraph/recipe component. A completed Reviewer attempt produces a durable `SemanticReviewResult` artifact and therefore uses BTN-133 `COMPLETED_WITH_CHANGE` even when the findings list is empty; `COMPLETED_WITH_NO_CHANGE` is not used as a synonym for “no findings.”

Rename the current checkpoint Reviewer capability to RejectionAnalyzer (final implementation name may vary) and keep it inside Implementation Run.

Treat Architecture as a prospective first-class Run using the same lifecycle, persistence, provenance, recipe, and human-action primitives. Preserve architecture authority exclusively at the authorized human + durable repository-artifact boundary.

Do not implement Review Run or Architecture Run in BTN-134. After human acceptance of this RFC, record the corresponding ADR and create implementation/architecture tickets for the decomposed work above.
