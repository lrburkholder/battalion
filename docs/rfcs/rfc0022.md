# RFC-0022 — SignalSource Operational Evidence Capability

**Status:** Accepted  
**Decision Date:** 2026-09-05  
**Ticket:** BTN-105  
**Author:** Architecture  
**Target:** BTN-M7 Integration Hardening & Channels  
**Related:** RFC-0006, RFC-0009, RFC-0014, ADR-0025, BTN-46, BTN-65

---

## Summary

Battalion should add an additional Battalion-owned integration capability,
`SignalSource`, for bounded operational evidence that may indicate work is
needed.

A `SignalSource` is deliberately not a `WorkSource`. It reports observations
from systems such as telemetry platforms, CI, dependency/security alerting, or
future diagnostic applications. Those observations are evidence. They do not
become Runs, tickets, workflow transitions, or repository authority merely by
arriving.

Battalion may correlate and classify Signals into Battalion-owned
`OperationalFinding` aggregates, or pass those findings to a separate
diagnostic/RCA capability, before proposing a canonical GitHub Issue. Every
proposed Issue requires explicit human confirmation. Once the human accepts the
exact Issue candidate and a GitHub Issue exists, the existing `WorkSource` and
Run machinery applies.

This RFC extends RFC-0006's transport-neutral capability model, RFC-0009's
plugin extension model, and RFC-0014's existing human-gated WorkSource-backed
ticket-creation boundary. It does not turn Battalion into an observability,
incident-management, support, or general diagnostic product.

## Motivation

Battalion currently has a strong boundary around canonical work: GitHub Issues
are units of work and `WorkSource` exposes them through normalized integration
contracts. Operational systems, however, often know about a possible defect
before a ticket exists:

- a Sentry error group begins recurring
- Application Insights reports a new failure pattern
- a CI workflow repeatedly fails
- a dependency or security scanner raises an alert
- a future Battalion-built diagnostic application finds evidence that deserves
  engineering attention

Treating each such system as a `WorkSource` would collapse evidence and work
into the same authority boundary. Treating each individual event as a ticket
would create noisy, duplicated work and allow external systems to bypass human
and workflow policy.

The missing abstraction is a bounded source of operational evidence.

## Goals

- define `SignalSource` separately from `WorkSource`
- preserve provider- and transport-neutral integration semantics
- normalize enough identity and provenance to correlate repeated observations
- permit bounded summaries and evidence references without persisting arbitrary
  telemetry payloads into Run state
- preserve a visible human boundary between evidence and canonical work
- permit built-in and plugin implementations under the same least-authority
  integration architecture
- support future diagnosis/RCA systems without assigning that responsibility to
  the capability itself
- reuse the existing WorkSource-backed, human-gated ticket-creation path rather
  than inventing a second backlog mutation mechanism

## Non-goals

- implementing Sentry, Application Insights, CI, security-scanner, or other
  concrete providers in this ticket
- making Battalion an observability dashboard, log store, incident manager, or
  support product
- creating a `Debugger` role as part of this capability
- defining a general diagnostic or RCA Run type
- copying raw logs, traces, dumps, exception payloads, or arbitrary external
  telemetry into GitHub Issues, model context, or durable Run state
- granting a provider authority to create Runs, modify repositories, accept
  work, or alter graph policy
- requiring one GitHub Issue per signal or telemetry event
- allowing organizational policy to bypass human confirmation for creating
  canonical work from operational evidence
- redefining RFC-0014's accepted backlog-creation authority boundary

## Semantic boundary

```text
operational system
      |
      v
  SignalSource
      |
      v
 immutable normalized Signals
      |
      v
 Battalion-owned OperationalFinding
 correlation / deduplication / classification
      |
      +--> optional diagnosis / RCA outside SignalSource
      |
      v
 proposed Issue candidate
      |
      v
 explicit human confirmation
      |
      v
 WorkSource-backed ticket creation
      |
      v
 canonical GitHub Issue
      |
      v
   WorkSource intake
      |
      v
 Battalion Run workflow
```

A **Signal** says: "something was observed that may deserve work."

An **OperationalFinding** says: "Battalion currently believes these
observations may represent one underlying operational problem worth
considering."

A **WorkItem** says: "this is a canonical unit of work Battalion may intake."

Receiving a Signal never implies that work has been accepted, prioritized,
assigned, or authorized.

`OperationalFinding` is intentionally named rather than the generic `Finding`.
RFC-0014 already uses `ReviewFinding` for semantic-review evidence. These are
different domain records and should not share an ambiguous type name.

## Capability contract

`SignalSource` is an observational capability beneath `battalion.application`,
with provider adapters and transports arranged exactly as in RFC-0006.

Candidate initial operations:

- `signal.get` — retrieve one observation by admitted stable identity/reference
- `signal.list` — retrieve bounded observations according to admitted query or
  cursor criteria
- `signal.refresh` — re-read admitted provider evidence associated with a known
  source reference and emit zero or more new normalized observations when new
  evidence exists

`signal.refresh` never mutates a previously emitted Signal. Mutable
provider-side grouping or status may influence new evidence or correlation
hints, but historical Signal records remain immutable.

Inbound webhook delivery is a transport mechanism, not a new semantic
capability. A verified webhook may supply evidence to a configured
`SignalSource` adapter, but receipt still produces only normalized Signal
evidence.

The initial contract intentionally has no `signal.create_work` operation.
Creating canonical work belongs above the capability boundary.

### RFC-0006 common-contract applicability

RFC-0006 currently says every capability operation declares required Actor,
Project, Run, WorkItem, and integration references. `SignalSource` exposes a
case that makes the intended interpretation explicit: operation contracts must
declare which Battalion references are required **when applicable**, rather
than every external operation requiring an artificial Run or WorkItem.

A Signal may exist before any WorkItem or Run exists. `SignalSource` therefore
requires stable integration/source identity and whatever Actor/Project scope is
needed for admission, but it must not manufacture `Run` or `WorkItem` identity
solely to satisfy a generic integration envelope.

RFC-0006 reconciliation should clarify this operation-specific applicability
for all capabilities rather than create a SignalSource-only exception.

## Normalized Signal record

A normalized Signal needs enough stable information for correlation,
provenance, inspection, and policy decisions without reproducing the provider's
telemetry model.

Required concepts:

- **signal identity** — stable Battalion-side identity for the normalized
  observation
- **integration identity** — the configured Battalion `integration_id`
- **source reference** — stable provider-side identity sufficient to retrieve or
  recognize the evidence again
- **observed time** — when the relevant condition/event was observed, preserving
  provider time where supplied
- **normalized summary** — bounded human-readable statement of what was
  observed
- **provenance** — provider/integration and retrieval or receipt evidence

Optional concepts:

- **provider severity / importance** — the source system's supplied value,
  retained as provenance rather than silently becoming Battalion priority
- **normalized operational severity** — a small Battalion-owned cross-provider
  vocabulary such as `info | warning | error | critical`, when enough evidence
  exists to derive it
- **affected component / scope** — repository, service, workflow, deployment,
  package, environment, or another bounded normalized scope where known
- **external evidence references** — durable URLs or opaque provider references
  to logs, traces, alert groups, workflow runs, dashboards, or records
- **occurrence evidence** — bounded count/window information useful for
  correlation without retaining every raw event
- **correlation hints** — bounded normalized attributes that can help determine
  whether observations represent the same underlying defect

Neither provider severity nor normalized operational severity maps
automatically to Battalion/GitHub backlog priority. Operational severity answers
how significant the observation appears to be; work priority remains a human
engineering decision made when reviewing a proposed Issue candidate.

The core contract must not require vendor-specific concepts such as Sentry
issue groups, Azure resource IDs, GitHub workflow-run objects, or a particular
trace/span schema. Provider adapters map those into the normalized contract.

## Signal identity and redelivery

A Signal is an immutable historical observation. Retried polling, webhook
redelivery, reconnect replay, or another transport retry must not create a new
Signal merely because delivery occurred twice.

Adapters therefore need a stable source/provenance identity sufficient for
Battalion to recognize the same external observation again. Where a provider
supplies an immutable event/record identity, that identity is preferred. Where
it does not, the adapter must derive a bounded stable observation identity from
provider evidence according to its versioned contract rather than using receipt
time as identity.

This identity rule is observational deduplication only. It does not claim that
two different external observations represent the same engineering defect;
that interpretation belongs to `OperationalFinding` correlation above the
capability boundary.

Provider-side changes such as a later successful workflow run, alert closure,
or changed grouping state become new Signal evidence; they do not rewrite a
historical observation into `resolved`.

## OperationalFindings, correlation, and deduplication

`SignalSource` must not assume one provider event equals one engineering defect.
Providers may emit retries, repeated occurrences, changing group identities, or
multiple observations for the same underlying problem.

Battalion therefore separates provider observations from its own interpretation:

1. **source identity** — which configured integration and external record/event
   supplied evidence;
2. **Signal identity** — a stable identity for one immutable normalized
   observation;
3. **OperationalFinding identity** — a Battalion-owned aggregate representing
   the current interpretation that one or more Signals may correspond to one
   underlying defect or operational concern.

An OperationalFinding, not a Signal, owns:

- correlation/grouping state
- deduplication decisions across distinct observations
- classification
- mutable lifecycle such as `open`, `resolved`, `recurring`, or `dismissed`
- Issue proposal history
- linkage to any canonical GitHub Issue created from it

Correlation may use provider grouping when available, but Battalion core must
not depend on provider-specific grouping semantics. A provider grouping key is
provenance evidence, not universal truth.

One OperationalFinding may collect many Signals, and Battalion is not required
to create one Issue per event. A later Signal may reopen or mark an
OperationalFinding as recurring without rewriting prior Signal history.

## Authority boundary: OperationalFinding to canonical work

A Signal provider has no authority to create a Run or canonical work merely by
emitting evidence. An OperationalFinding also remains candidate interpretation
rather than accepted work.

The transition to GitHub Issue is an explicit human decision. The states are:

1. immutable Signal evidence exists;
2. Battalion correlates that evidence into an OperationalFinding;
3. Battalion prepares an exact Issue candidate;
4. a human reviews the OperationalFinding evidence and the proposed Issue
   candidate;
5. the human accepts or rejects that candidate;
6. only an accepted candidate may be created as the canonical GitHub Issue.

There is no initial auto-create policy. Organizational configuration may govern
what evidence is collected, how OperationalFindings are classified, how
proposals are formatted, and what provenance is exposed externally, but it may
not bypass the human confirmation required to turn operational evidence into
canonical work.

Human approval binds to the exact proposed Issue candidate rather than granting
a generic permission to "make a ticket." A meaningful change to the proposed
title, description, scope, priority, affected project, or other work-defining
content invalidates the prior acceptance and requires the revised candidate to
be reviewed again.

This does not introduce a second ticket-creation authority. RFC-0014 already
establishes that Battalion may create proposed WorkItems only after an explicit
authorized human approval/edit gate, through a Battalion-owned ticket-creation
capability backed by `WorkSource`. Signal-derived work uses that same boundary.

`SignalSource` itself never gains WorkSource mutation authority, and possession
of a SignalSource provider credential or plugin grant cannot imply permission
to create a ticket.

## Issue provenance is organization-policy governed

Organizations have materially different disclosure, security, privacy, and
audit needs. An open-source project may reasonably include public workflow-run
links and a concise OperationalFinding reference in an Issue, while a
high-security or regulated organization may prohibit exposing operational
source details in the canonical work item at all.

Battalion therefore separates **internal durable provenance** from
**Issue-visible provenance**:

- Battalion must retain enough internal durable linkage to explain that an
  accepted Issue candidate came from a particular OperationalFinding and
  bounded Signal evidence.
- Organization policy decides what, if any, provenance is copied or rendered
  into the external GitHub Issue or equivalent WorkSource item.
- Policy may choose a public URL, an opaque OperationalFinding ID, a sanitized
  evidence summary, an internal-only reference, or no operational reference in
  the Issue body when disclosure is inappropriate.
- Policy cannot make sensitive data safe merely by declaring it acceptable;
  credential/secret minimization rules still apply.
- A lack of Issue-visible provenance must not erase Battalion's own audit trail
  of the human decision and originating OperationalFinding.

This keeps the capability useful across open-source, commercial, regulated, and
high-security environments without forcing one organization's disclosure policy
onto another.

## Evidence retention, privacy, and secrets

Operational evidence is especially likely to contain secrets, personal data,
customer content, stack traces, request payloads, or large-volume telemetry.
The default retention rule is reference-first and minimize-by-default.

Battalion may durably retain:

- normalized Signal identity and summary
- source/integration provenance
- timestamps and bounded correlation evidence
- OperationalFinding membership/linkage
- durable external references or opaque IDs
- the minimum evidence needed to explain a proposal or Issue-creation decision

Battalion should not indiscriminately retain:

- raw logs or traces
- memory/process dumps
- complete exception/request payloads
- arbitrary telemetry event bodies
- access tokens, signed URLs whose bearer value is itself authority, cookies,
  or other secrets
- provider SDK response objects

A provider may expose an evidence reference that requires authorization at read
time. Persisting the reference does not imply persisting the underlying payload.
References that themselves contain credentials or sensitive query material must
be redacted, transformed into opaque provider IDs, or rejected according to the
adapter contract.

## Diagnosis and RCA boundary

`SignalSource` reports evidence. It does not diagnose root cause.

Correlation, classification, and lightweight deterministic enrichment may occur
above the capability boundary in OperationalFinding construction. Rich
diagnosis/RCA should belong to a future Run type, role/workflow, or separate
Battalion-built application with its own permissions, context budget, and
evidence rules.

Such a diagnostic system may consume Signals/OperationalFindings and improve a
proposed Issue candidate, but its output still crosses the same human authority
boundary before becoming a GitHub Issue. This keeps the integration primitive
small and allows diagnostic products to evolve independently.

## Representative provider mapping: CI failures

A current Battalion example is the `Complete merged Battalion tickets` GitHub
Actions workflow. A run can have provider conclusion `failure` because the
post-merge lifecycle automation expected the linked Issue to have
`status:in-review` and found none. That is a real operational failure, but it
does not imply the defect is a P0/P1 engineering priority.

Example external evidence:

```text
workflow: Complete merged Battalion tickets
repository: lrburkholder/battalion
run: <workflow-run identity>
conclusion: failure
failed step: Validate and close declared tickets
reason: linked Issue must have exactly status:in-review; found []
observed: <provider timestamp>
url: <provider run reference>
```

Possible normalized Signal:

```text
signal_id: <Battalion stable identity>
integration_id: github-actions-battalion
source_ref: workflow-run/<id>
observed_at: <provider timestamp>
summary: post-merge ticket lifecycle automation failed because the linked Issue lacked status:in-review
provider_severity: failure
operational_severity: error
scope:
  repository: lrburkholder/battalion
external_refs:
  - kind: ci_run
    ref: workflow-run/<id>
correlation_hints:
  workflow: ticket-lifecycle
  failed_step: validate-and-close-declared-tickets
```

A later occurrence with the same failure may attach to the same
OperationalFinding. A later successful run is new evidence that may help
resolve the OperationalFinding. Neither provider `failure` nor normalized
`error` determines the engineering priority of an Issue proposal.

No GitHub Issue is created solely because the CI provider emitted the Signal.

## Transport and plugin compatibility

`SignalSource` follows RFC-0006's existing transport taxonomy. Implementations
may be native/local, HTTP/REST, inbound webhook, MCP-backed, protocol-specific,
or another approved bounded transport.

The transport does not change capability meaning. For example, a webhook may
push a Sentry observation and an HTTP adapter may poll the same source, but both
must normalize through the same `SignalSource` contract and neither receives
workflow authority.

RFC-0009's plugin rules apply unchanged in principle:

- a plugin may implement an accepted `SignalSource` provider adapter or bounded
  transport
- plugin manifests declare support; they do not create the capability or grant
  authority
- an authorized plugin-administration Actor approves the package/version and
  maximum capability/resource exposure
- integration configuration and Battalion application policy narrow that
  authority further
- the graph cannot discover arbitrary plugin operations
- plugin isolation, secret handling, failure, and durable evidence rules remain
  in force

Acceptance of this RFC therefore extends the Battalion-owned capability set
that future plugins may implement. It does not allow plugins to invent signal
semantics or silently convert signals into work.

## RFC-0006 reconciliation

If accepted, RFC-0006 should be amended in place without rewriting the
historical fact that its original accepted capability set contained six
contracts.

The current architecture should then state that `SignalSource` is an additional
Battalion-owned capability and should:

- add a `SignalSource` contract section defining observational semantics,
  normalized data boundary, immutable observation identity, failure categories,
  and authority boundary
- clarify the common-contract reference rule so Actor/Project/Run/WorkItem
  references are required according to each operation's semantics rather than
  forcing nonexistent WorkItem/Run identities onto pre-work evidence
- clarify that inbound webhook receipt may feed `SignalSource` evidence but
  does not imply command or WorkSource authority
- preserve the existing prohibition on graph nodes receiving raw clients or
  discovered tool collections
- preserve the distinction between provider evidence and Battalion authority

No existing capability should be widened to absorb SignalSource behavior.

## RFC-0009 reconciliation

RFC-0009 explicitly says adding a new Battalion capability is a core
architecture change requiring its own accepted decision. RFC-0022 is that
architecture decision; plugin discovery itself still cannot expand the
capability set.

If accepted, RFC-0009 should be amended to:

- distinguish its historically initial six-capability set from the current set,
  which also includes `SignalSource`
- include `SignalSource` wherever RFC-0009 enumerates Battalion-owned
  capability/source-of-truth semantics
- permit plugin manifests to declare compatible `SignalSource` implementations
  and contract versions under the existing capability-grant model
- preserve Admin/authorized-Actor approval, isolation, and effective-authority
  intersection rules
- state explicitly that plugin support for `SignalSource` grants evidence
  retrieval/receipt capability only; it does not grant WorkSource mutation,
  Run creation, or workflow-policy authority

No plugin manifest, transport discovery result, or provider feature may create
new SignalSource operations beyond the Battalion-owned contract.

## RFC-0014 reconciliation

RFC-0014 already establishes the relevant backlog-creation boundary:
Architecture Run may produce proposed WorkItems, but canonical backlog items
are created only after an explicit authorized human approval/edit gate through
a Battalion-owned ticket-creation capability backed by `WorkSource`.

RFC-0022 reuses that pattern for operational evidence:

```text
OperationalFinding
      |
      v
proposed Issue candidate
      |
      v
explicit authorized human approval/edit gate
      |
      v
WorkSource-backed ticket creation
```

The provenance and proposal source differ; the authority boundary does not.
RFC-0014 therefore needs no semantic weakening or parallel mechanism for
SignalSource.

## Failure semantics

SignalSource-specific normalized failures should include at least:

- source record not found or expired
- unsupported query, cursor, or provider grouping behavior
- malformed or incompatible signal evidence
- authentication or external permission denial
- Battalion authorization or operation-policy denial
- rate limit/provider overload
- timeout/cancellation
- transport failure
- partial result set or dropped/invalid observation indication where knowable
- stale external evidence reference

Because the initial capability is observational rather than externally
side-effecting, retry semantics are simpler than WorkSource mutations. However,
retries and webhook redelivery must preserve observation identity strongly
enough to avoid manufacturing duplicate Signals or OperationalFindings.

## Consequences

### Positive

- telemetry and alert providers gain a first-class integration boundary without
  becoming sources of canonical work
- correlation and deduplication can happen before backlog pollution
- immutable Signals preserve historical truth while OperationalFindings carry
  evolving interpretation and lifecycle
- provider and plugin integrations remain transport-neutral and least-authority
- future diagnostic applications can consume a stable evidence contract
- privacy and secret exposure are bounded before model or Run context assembly
- organization-specific disclosure policy can vary without changing
  SignalSource semantics
- every transition from operational evidence to canonical work remains visible
  to and understood by a human
- backlog creation reuses RFC-0014 rather than introducing another mutation path

### Costs

- Battalion needs durable identity/provenance semantics for Signals and a
  separate OperationalFinding aggregate above providers
- creating work from evidence becomes an explicit multi-step human-confirmed
  operation rather than a convenient provider callback
- candidate-bound approval requires re-review when proposed work changes
  meaningfully
- provider adapters must normalize grouping and evidence references rather than
  exposing raw vendor payloads
- organizations need an explicit policy for Issue-visible operational
  provenance
- RFC-0006's common reference wording must be clarified for evidence that
  legitimately predates WorkItem and Run identity

## Alternatives rejected

### Treat telemetry systems as WorkSources

A telemetry event is evidence, not accepted work. Reusing `WorkSource` would
allow external observation systems to blur canonical backlog authority and
would make provider grouping/status semantics look like Battalion work state.

### Create one Issue per event

Operational systems are noisy and repetitive. This would create duplicate work,
encourage alert fatigue, and make external event volume drive backlog shape.

### Permit policy-driven automatic Issue creation

Even deterministic auto-creation would turn an observation into canonical work
without the human understanding the concrete work item being added to the
codebase's backlog. Battalion may automate evidence collection, correlation,
classification, diagnosis, and proposal preparation, but the final transition
to canonical work remains explicitly human-confirmed.

### Put correlation lifecycle on Signal

That would make an observation mutable and conflate historical evidence with
Battalion's changing interpretation of what the evidence means.
OperationalFindings own that interpretation instead.

### Reuse the generic name `Finding`

RFC-0014 already defines `ReviewFinding` as semantic-review evidence. A generic
`Finding` type for operational correlation would invite accidental conflation
between review defects and telemetry-derived candidate problems.
`OperationalFinding` keeps the domains explicit.

### Put diagnosis inside SignalSource

Diagnosis requires richer context, tools, cost, policy, and potentially model
execution. Folding it into an integration contract would turn a narrow evidence
adapter into a workflow engine and observability product.

### Store raw telemetry in Battalion

Raw operational payloads are often large, sensitive, provider-specific, and
short-lived. Battalion needs durable references and bounded evidence, not a
second telemetry datastore.

### Require one universal Issue-provenance policy

Open-source, commercial, regulated, and high-security organizations have
materially different disclosure needs. Battalion requires internal durable
provenance but leaves Issue-visible provenance to organization policy.

### Make every integration operation require a WorkItem or Run reference

Signals often exist precisely because no work has been created yet. Inventing a
placeholder WorkItem/Run would invert the evidence-to-work boundary and pollute
canonical lifecycle semantics. RFC-0006 should instead require operation-
specific Battalion references.

## Resolved design decisions

1. **Correlation ownership:** correlation belongs to a separate Battalion-owned
   `OperationalFinding` aggregate above `SignalSource`; Signals remain
   individual evidence.
2. **Human authority:** every proposed Issue requires explicit human
   confirmation. Auto-creation from Signals/OperationalFindings is outside this
   design.
3. **Severity:** preserve provider-native severity/importance and optionally
   derive a small Battalion operational-severity vocabulary. Neither maps
   automatically to backlog priority.
4. **Lifecycle:** Signals are immutable observations. Mutable lifecycle belongs
   to OperationalFindings.
5. **Issue provenance:** Battalion always preserves internal durable linkage to
   the originating OperationalFinding/Signals, while organization policy
   determines what provenance is safe and appropriate to expose in the
   canonical Issue.
6. **Backlog creation:** Signal-derived Issue creation reuses RFC-0014's explicit
   authorized human approval/edit gate and WorkSource-backed ticket-creation
   capability.
7. **Reference applicability:** pre-work Signals do not require artificial
   WorkItem/Run identity; RFC-0006 common contract references are operation-
   specific.
8. **Domain naming:** operational correlation uses `OperationalFinding` so it
   cannot be confused with RFC-0014 `ReviewFinding` evidence.

## Proposed acceptance

Accept the following architecture:

1. `SignalSource` becomes an additional Battalion-owned integration capability
   distinct from `WorkSource`.
2. SignalSource emits bounded immutable operational evidence, never canonical
   work.
3. Signals carry stable source/provenance identity and bounded normalized
   evidence, with redelivery/replay preserving observation identity.
4. Battalion-owned OperationalFindings correlate, deduplicate, classify, and
   carry mutable lifecycle and Issue linkage above the SignalSource boundary.
5. Provider severity and Battalion operational severity remain distinct from
   human-owned engineering/backlog priority.
6. Raw telemetry remains outside Run state by default; Battalion retains
   references and minimized evidence.
7. Rich diagnosis/RCA remains outside SignalSource and may consume Signals or
   OperationalFindings through a future workflow/application.
8. Every proposed GitHub Issue requires explicit human confirmation bound to
   the exact work candidate and then uses RFC-0014's existing WorkSource-backed
   ticket-creation authority path.
9. Battalion retains internal durable provenance from Issue creation to the
   originating OperationalFinding/Signals; organization policy controls
   Issue-visible provenance and disclosure.
10. Provider adapters and plugins may implement SignalSource over approved
    transports without gaining Run, repository, graph, or workflow-policy
    authority.
11. SignalSource operations declare only the Actor/Project/Run/WorkItem
    references semantically required for that operation; pre-work evidence does
    not manufacture WorkItem or Run identity.
12. RFC-0006 and RFC-0009 are reconciled after acceptance without weakening
    their existing least-authority guarantees or rewriting their historical
    initial-capability decisions.
