# RFC-0004 — Desktop Operator Interface

**Status:** Accepted
**Decision Date:** 2026-08-14
**Ticket:** BTN-29  
**Author:** Architecture  
**Target:** Post-v1  
**Related:** `philosophy.md`, ADR-0003, ADR-0014, ADR-0015, ADR-0016,
ADR-0017, ADR-0018, BTN-17, `docs/ui/`

---

## Summary

Battalion should provide a standalone, desktop-first operator interface for
starting, observing, understanding, and directing human-controlled software
delivery work.

The interface is not an IDE, a generic chat client, or a dashboard placed over
logs. It is an operator console organized around durable engineering objects:
tickets, runs, node executions, artifacts, interrupts, human decisions, and
Instincts.

The desktop client shall use the same reusable application behavior as the CLI.
It shall not invoke LangGraph directly, edit persisted `RunState` values, bypass
write scopes, or implement another run or resume path. Framework selection is
deferred until a bounded desktop prototype demonstrates the required process,
streaming, security, and packaging boundaries.

This RFC supersedes the product direction in the earlier draft UI documents
under `docs/ui/`. Those documents remain useful screen explorations, but they
are not the current interface contract. In particular, the narrow web UI from
cancelled BTN-17 is not the first Battalion interface.

The operator does not currently know Rust, but that is not a reason to reject
Tauri. Battalion exists so both machine and human improve. Learning Rust may be
a valuable outcome if the language provides the strongest long-term boundary.
The comparison must therefore measure learning investment and resulting
maintainability rather than treating unfamiliarity as permanent incapacity. A
Tauri implementation would still keep Battalion policy in Python and limit Rust
to process supervision, narrowly scoped desktop capabilities, and transport
adaptation.

## Status and Scope

This is a design proposal, not shipped behavior.

BTN-29 defines:

- the operator-facing information hierarchy
- primary desktop navigation and screens
- live-run inspection and safe human intervention semantics
- presentation of execution evidence, provenance, cost, and Intel
- the boundary shared by CLI and graphical clients
- the shared scope and benchmark contract for follow-up Tauri, PySide6, and
  Electron architecture-spike tickets
- future directions for search, analytics, and read-mostly mobile access

BTN-29 does not implement a production interface, replace persistence, add
framework spikes, add semantic retrieval, automate model routing, or grant new
authority to any role.

## Evidence Available Today

The interface can now be designed against implemented contracts rather than
speculative telemetry.

### Run and Control State

`RunState` is the durable graph-control and resume contract. It records the run
and ticket identifiers, specification, status, phase, write scopes, reviewer
rejections, budget, interrupts, checkpoints, resume target, and execution
record. Local JSON remains authoritative for graph continuation.

### Node Execution Evidence

ADR-0014 and BTN-19 add one bounded `NodeExecution` per graph-node attempt. It
records:

- stable execution identity
- role and concrete phase
- configured model identity
- bounded input references
- output reference or verdict
- start and end timestamps
- outcome
- tool activity
- review and inferred test results
- artifact path, digest, originating run, and originating node execution
- linked interrupts

This is sufficient for the first workflow map and completed-run inspector.

### Cost Evidence

ADR-0017 and BTN-16 attach successful completion usage to the active node
execution. BTN-35 revises monetary evidence to a nullable decimal amount with
separate ISO 4217 currency and explicit provider-reported, estimated, or unknown
source. Token counts remain available when cost is unknown. The run-level budget
remains an independent turn counter used by interrupt trigger 3.

### Intel and Human Decisions

ADR-0015 keeps Recon outside the completed graph. ADR-0016 and BTN-23 provide an
audited human workflow for accepting, editing then accepting, or rejecting
Recon candidates. Accepted Instincts and review decisions use separate local,
append-only repositories.

ADR-0018 and BTN-24 provide deterministic, role-specific retrieval with an
inspectable inclusion or exclusion reason for every active Instinct considered.

### Important Limits

The current contracts do not yet provide:

- a project-wide catalog of runs; saved run files must be discovered
- session identity or session semantics
- durable live-event ordering below node boundaries
- complete model-call retry evidence or failed-attempt usage
- an explicit distinction between a genuinely zero cost and unavailable cost
- cached, reasoning, or provider-specific token classes
- prompt template identity and rendered prompt provenance
- exact context-item inclusion reasons outside Intel retrieval
- general typed intervention commands beyond existing interrupt and resume
  behavior
- durable Recon candidate persistence as a first-class inbox
- cross-run search or analytics indexes

The UI shall label unavailable evidence as unavailable. It shall not infer zero,
success, causation, or provenance from absence.

### Operator Summary

In addition to mechanical execution evidence, each completed or paused node
should eventually produce a bounded operator summary inspired by the Squad
Handoff pattern described during BTN-29 design:

- what I did
- what should happen next
- open questions
- verification performed
- artifacts produced or changed
- last responsible node and phase
- model and prompt version metadata

This summary deliberately omits copied source code, full prompts, and hidden
reasoning. Its statements link to the underlying execution evidence rather than
replacing it. Prompt version is not captured by the current execution contract,
so this summary requires a follow-up schema and prompt-versioning decision.

### Code, Prompt, and Context Provenance

Battalion should identify the code and instructions used by a node without
copying them into execution history.

Code provenance should record:

- version-control system
- full base commit object identifier and hash algorithm
- branch or detached-head state as display metadata
- whether the working tree was dirty at node start and completion
- hashes of bounded input files admitted to context
- existing artifact hashes for produced or changed files

A commit identifier alone is sufficient only for a clean tree. For a dirty
tree, the base commit plus dirty-state marker and bounded input/output hashes
make the limitation explicit without storing a patch or source contents. The UI
must say that the exact uncommitted workspace cannot be reconstructed when only
hash evidence was retained.

Prompt provenance should record:

- stable prompt identity, such as role and template path
- explicit prompt contract version
- full prompt-template content hash and hash algorithm
- Battalion revision that supplied the prompt
- relevant model configuration identity

The rendered prompt and template contents are not retained by default. The
version is human-readable; the hash proves which exact template was used.

Context provenance should use bounded references, content hashes, inclusion
reasons when available, and truncation metadata. It should not copy admitted
source, specifications, plans, or Instinct text into the execution record when
their authoritative artifact can be referenced.

## Product Principles

### Ticket Before Conversation

The ticket is the durable engineering objective. A run is one execution of that
objective. A node execution is one role attempt within the run. Messages and
model output are supporting evidence, not the primary navigation model.

### Human Authority Is a Visible Lane

Interrupts, approvals, candidate review, architecture decisions, and operator
guidance are part of the workflow. They should not appear as exceptional chat
messages or disappear after a resume.

### Explain Work Through Evidence

The interface should expose inputs, authority, decisions, tools, review
outcomes, artifacts, uncertainty, and cost. Raw provider reasoning may be
displayed when available, but the product must not depend on private
chain-of-thought as its explanation system.

### Calm by Default

The initial view should answer:

1. What is Battalion doing?
2. Which role currently owns the ticket?
3. What has happened and what changed?
4. What may the active role change?
5. Is human action required?
6. What has the work consumed?

Detailed payloads remain progressively disclosed.

### Repository Authority Remains Explicit

Execution evidence and conversation do not outrank specifications, accepted
ADRs, the backlog, or source. The interface may help create or inspect durable
artifacts, but it shall not silently promote a model statement into project
authority.

### Local First

The first interface reads local run and Intel data and controls a local
Battalion runtime. Hosted telemetry, remote access, synchronization, and mobile
control are optional future layers.

## Information Hierarchy

The primary hierarchy is:

```text
Project
├── Ticket
│   └── Run
│       ├── Node execution
│       │   ├── Model-call cost observations
│       │   ├── Tool activity
│       │   ├── Review and test evidence
│       │   └── Produced artifacts
│       ├── Interrupts
│       └── Human actions
└── Intel
    ├── Recon candidates
    ├── Operator review decisions
    └── Accepted and superseded Instincts
```

`Session` is deferred. No implemented Battalion contract currently defines its
identity, lifetime, or relationship to tickets. It should be added only if use
shows a grouping that project, ticket, and run cannot express.

An artifact has its own identity through path and digest and may be reached from
its producing node execution, a ticket history, or search result.

## Primary Navigation

The desktop application should have four primary destinations.

### Work

The default destination. It contains active, awaiting-human, and ready tickets;
the selected run's execution map; and an inspector.

### History

Completed, cancelled, blocked, and earlier runs grouped by ticket. History
supports exact and structured filtering first, then optional semantic search.

### Intel

Recon candidates needing review, operator decisions, accepted Instincts, and
supersession history.

### Analytics

Cost, token use, latency when captured, outcome measures, and role/model
comparisons. Analytics is introduced only after its measures and missing-data
semantics are trustworthy.

Settings may live in the application menu until it has enough scope to justify
a destination.

## Work Screen

The Work screen uses four stable regions:

```text
+--------------------------------------------------------------------+
| Project and search                                      New run     |
+------+----------------+---------------------------+----------------+
| Nav  | Ticket list    | Execution map             | Inspector      |
|      |                |                           |                |
|      |                | Human authority lane      | Intervention   |
+------+----------------+---------------------------+----------------+
| Run identity · save state · tokens · cost · connection             |
+--------------------------------------------------------------------+
```

### Ticket List

The list is grouped by actionability rather than showing every node execution
as a peer:

- Needs you
- Running
- Ready
- Recent

Each entry shows ticket, concise objective, status, current phase, elapsed time,
and whether human action is pending. Selecting a ticket restores the most
recent relevant run and the operator's last inspected object.

### Execution Map

The map is derived from concrete `NodeExecution` records. It represents actual
attempts rather than one decorative copy of the static graph.

```text
Architect · attempt 1             accepted
  ↓ plan handoff
Driver RED · attempt 1            succeeded
  ↓ RED review
Reviewer RED · attempt 1          accepted
  ↓ expected failure confirmed
Driver GREEN · attempt 1          succeeded
  ↓ GREEN review
Reviewer GREEN · attempt 1        rejected
  ↳ Driver GREEN · attempt 2      running
```

Every edge explains why it exists: fixed handoff, expected-outcome acceptance,
review rejection, configured checkpoint, interrupt, resume, or operator action.
If the current record cannot prove the reason, the edge is labeled unknown.

Each node summarizes role, phase, attempt, status, duration, model, tokens, cost,
and artifact count. Selection drives the inspector.

### Human Authority Lane

Human events are displayed alongside node execution, not hidden inside the
machine lane. This lane contains:

- configured manual checkpoints
- interrupts and their resolutions
- queued guidance
- explicit operator decisions
- cancellation or restart decisions
- architecture or product decisions linked to durable artifacts

The first implementation can display interrupts and resume actions supported by
the runtime. General guidance remains disabled until a typed application
command and safe-boundary semantics exist.

## Inspector

The inspector is object-sensitive. Selecting a run, node, edge, artifact,
interrupt, decision, or Instinct changes its content without navigating away
from the Work screen.

The initial node inspector has four views.

### Activity

A concise sequence of domain facts: node start and completion, scoped writes,
test execution, review verdicts, interrupts, and artifacts. It is not a copy of
stdout.

### Context

Objective, bounded input references, specification, accepted plan reference,
workspace context, supplied Instincts, retrieval decisions, configured model,
and declared write scope. Missing prompt identity or exact context provenance
is shown as unavailable until captured.

### Artifacts

Path, recorded digest, current digest comparison, originating run and node,
and available diff or open-in-editor action. A changed current digest is shown
as later modification, not as corruption by default.

### Usage

Per-call and node aggregates for model, input tokens, output tokens, and cost.
Every displayed monetary amount is labeled provider-reported, estimated,
unknown, or historical price projection when those distinctions become
available.

Raw persisted JSON and provider diagnostics may appear under an advanced
disclosure. They are not a primary navigation tab.

## Human Intervention

Typing text is not sufficient to define an intervention. A human command needs
an explicit intent, target, timing, and expected effect.

### Two Intervention Types

BTN-29 defines exactly two typed intervention intents for v1. Both are supplied
text plus a target node role; neither is a runtime verdict override.

**Correction** targets Driver (RED or GREEN) or Refactorer. The human supplies
additional implementation context: a wrong assumption, a missed constraint, or
a pointer toward the right approach. Refactorer receives the same intervention
type as Driver because both are write-scoped code-producing nodes.

**Design decision** targets Architect. The human answers one of Architect's own
declared open questions. BTN-25 requires Architect to distinguish evidence,
assumptions, decisions, open questions, and deferred work, so this type has an
existing structural landing point rather than a freeform authority channel.

Reviewer does not receive its own intervention type. Reviewer's checkpoint
verdict is determined by the actual clean-copy test run under BTN-12; the LLM's
role on rejection is producing a normalized root-cause sentence for interrupt
trigger 1. Letting human intervention reshape that sentence would create a path
to quietly reset a rejection counter used by the interrupt system.

A human who disagrees with why a rejection happened supplies that context to
Driver's next attempt as a Correction. A human who wants to overturn a Reviewer
verdict outright is exercising a manual checkpoint override, not an
intervention, and is out of scope for this RFC.

### Landing Point: Next Attempt Only

Battalion's node-per-attempt model has no channel into an in-flight LLM call.
An intervention is not mid-generation steering. A Correction or Design decision
is queued at the next checkpoint and enters the next target-node attempt's
assembled context through the same named, inspectable context path used for
retrieved Instincts. The Inspector distinguishes human-supplied context from
model- and Instinct-supplied context.

Live mid-generation steering, if ever desired, requires a separate proposal for
a streaming completion interface and node architecture that can safely pause
mid-generation. Nothing in this RFC assumes that capability.

### Authority Boundary

An intervention cannot expand the target node's declared write scope, and a
Correction cannot silently redefine architecture that Architect has not
approved. The scope/tool-binding layer continues to enforce node authority;
intervention text is additional context, not elevated authority.

The application must respond to a submitted intervention with one of:

- queued for the next attempt at a named checkpoint
- rejected with a reason, such as a malformed target or authority violation
- requires a broader product or architecture decision

The interface must distinguish cooperative pause from immediate termination. It
must not imply that an in-flight provider request or filesystem operation can
be safely cancelled unless the runtime provides that guarantee.

BTN-29 specifies this interaction but does not add the missing intervention
runtime contract.

The framework comparison prototypes will not implement general interventions.
They may render a disabled intervention surface to test layout, but only
read-only inspection and simulated run-state transitions are compared.
Intervention runtime work should build the two typed intents defined above
rather than reinventing intervention semantics inside three UI spikes.

## Interrupt Resolution

All six v1 interrupt types must remain distinct. The interrupt view shows:

- trigger name and time
- originating node execution
- checkpoint and retry history where applicable
- captured context
- current resume target
- allowed resolution actions
- consequences of each action

Resume must call the same reusable graph behavior used by `battalion resume`.
Dismissal, navigation, and closing a dialog never imply approval.

## Intel Screen

Intel is a first-class human workflow rather than an analytics subsection.

### Candidate Inbox

Candidates are grouped into Needs review, Accepted, Edited and accepted, and
Rejected decisions. A candidate view shows recommendation, applicability,
audience, tags, cited execution evidence, originating run, and relevant active
Instincts.

The operator may accept, edit then accept, or reject. The UI calls
`InstinctReviewWorkflow`; it does not write the Intel or decision repositories
directly. Protected provenance and lifecycle fields are not editable.

The current Recon API returns candidates but does not define a canonical
candidate inbox repository. A production inbox requires a separate persistence
decision or an intentionally ephemeral post-run review flow.

### Instinct Library

The library shows active and superseded Instincts, applicability, role audience,
evidence, creation provenance, acceptance provenance, and supersession links.

### Retrieval Inspection

For a selected node execution, the interface should show every Instinct
considered and ADR-0018's literal inclusion or exclusion reason. This is a
teaching and trust feature: the human can see not just what knowledge was
supplied, but why.

## History and Search

The first history implementation should discover and validate local run-state
files and group them by ticket. Exact search and structured filters cover:

- ticket and run identifiers
- role, phase, status, and checkpoint
- model
- artifact path and digest
- review cause
- interrupt type
- Instinct identifier and tags
- date and cost range

Semantic search is an optional derived index for remembered concepts and intent.
It complements exact search; it does not replace it.

Search indexes are rebuildable projections. Repository artifacts, run state,
Intel records, and operator decision records remain their respective sources.
The user must know when an embedding service would transmit source or execution
content off the machine.

Search over execution history remains separate from Intel retrieval. A search
result is evidence for a human; it does not become accepted node guidance.

## Model Effectiveness

Battalion may eventually compare models within roles using:

- first-review acceptance
- rejection and retry count
- interrupt and infrastructure-failure rate
- operator intervention count
- elapsed time
- token and monetary cost
- test and specification compliance
- later human edits or rollback evidence

Comparisons must segment by role, checkpoint, prompt/context policy, Battalion
version, project domain, and available ticket characteristics. They must expose
sample size, time range, missing evidence, and the underlying runs.

Completion rate alone is not model quality. Historical observations are
confounded by ticket difficulty and changing prompts, context, and tools.
Initial analytics are descriptive. Automatic model routing requires another
proposal and an explicit human-configurable policy.

No general-purpose ticket complexity score is proposed. If a defensible set of
task characteristics emerges from real usage, it can qualify comparisons later.
Until then, the interface should show narrow factual cohorts and their
underlying runs rather than imply that difficulty has been normalized.

## Shared Application Boundary

The CLI and graphical clients should depend on reusable Python application
commands and queries. Presentation adapters do not own graph policy.

Initial commands and queries include:

- discover and validate projects and saved runs
- construct and start a run from one caller-supplied `RunState`
- observe run progress
- inspect run and node evidence
- resume a paused run
- query cost projections
- run Recon after completion
- review an Instinct candidate through the audited workflow
- list and inspect accepted Instincts
- explain Instinct retrieval

The desktop client shall not:

- invoke LangGraph nodes directly
- construct an alternate resume algorithm
- mutate a saved `RunState`
- append fabricated execution evidence
- write Intel repository files directly
- bypass scoped tools
- treat UI navigation as authorization

Command results should include the resulting durable identifiers and state
version so stale clients can detect that their view has changed.

### Live Observation

Existing callbacks provide node lifecycle and transient token activity. The
application boundary should expose a typed stream that separates:

- durable facts already represented in state
- transient progress that may be dropped
- human-action requests requiring acknowledgement

The UI must recover by reloading persisted state after disconnect. It cannot
assume that receiving every transient message is required to reconstruct the
run.

### Process Model

Each active run should execute in its own supervised Python worker process.
This isolates provider failures, cancellation, resource use, and working state
between concurrent runs. A worker owns exactly one `run_id` for its lifetime;
durable state remains the recovery mechanism.

Project discovery, history queries, and Intel inspection should not require one
monolithic, always-running Battalion daemon. They may execute through
short-lived Python commands or a small non-authoritative supervisor. The three
framework spikes will determine the least complex arrangement.

### Run Identity

New runs should receive an opaque, generated UUID as their canonical
identifier. The UI presents a human-readable alias composed from the ticket and
a shortened identifier, but aliases are not persistence keys.

UUIDs make collisions across local catalogs and imported history negligible.
They do not identify a repository after it moves. Stable project identity and
migration from existing human-readable run identifiers remain open design work.

## Persistence and Indexing Direction

The first desktop vertical slice should use existing local sources:

```text
RunState JSON
Intel repository
Instinct decision repository
        │
        ▼
Python application commands and queries
        │
        ▼
Desktop client
```

This preserves ADR-0014: no parallel event store is needed before one is proven
necessary.

A later SQLite catalog may index cross-run history, full text, costs, and model
outcomes. Such a catalog must be rebuildable and must not become a second graph
control or knowledge authority. A move to transactional checkpoint and event
storage would require its own ADR and migration design.

### Recon Candidate Persistence

Recon candidates should be persisted before operator review as immutable,
human-readable Markdown files. A candidate file should contain strict,
validated front matter for the existing candidate identifier, schema version,
lifecycle, audience, applicability, tags, evidence references, provenance, and
supersession metadata, followed by readable recommendation and evidence
sections.

The exact front-matter format remains to be selected. Persistence must use
create-only writes, preserve the original candidate after edit-and-accept, and
make review decisions independently durable under ADR-0016. Accepted Instincts
may retain their current JSON repository initially; candidate Markdown does not
silently change that accepted-knowledge contract.

### Cost Representation

A future usage schema should separate:

- `cost`: nullable decimal amount
- `cost_currency`: nullable ISO 4217 currency code
- `cost_source`: `provider-reported`, `estimated`, or `unknown`

Known zero cost is represented as amount `0` with a known currency and source.
Unavailable cost is represented as `null` with source `unknown`, never as zero.
If estimates are later introduced, their pricing snapshot or basis should be
additional provenance rather than encoded into the amount.

## Desktop Delivery Options

Framework choice is an implementation decision, but its process and authority
boundary can affect architecture.

### Tauri 2 With a Battalion Sidecar

Strengths:

- standalone desktop product with a reusable web presentation layer
- explicit command and capability model
- channels suitable for ordered streaming
- support for bundled external binaries
- smaller runtime footprint than shipping a dedicated Chromium instance
- a bounded opportunity for the operator to learn Rust through real systems
  work without moving Battalion's application policy out of Python

Risks:

- introduces Rust and a cross-language process boundary
- packaged Python and model-provider dependencies need careful supervision
- system webview differences require cross-platform testing

### PySide6

Strengths:

- one primary implementation language
- direct integration with the current application layer
- mature native desktop controls and process APIs

Risks:

- less direct reuse for a future browser client
- rich graph, diff, and search interfaces may require substantial custom work
- easier to accidentally couple widgets to runtime policy

### Electron

Strengths:

- mature desktop and frontend ecosystem
- consistent embedded Chromium rendering
- straightforward implementation of graph-heavy interfaces

Risks:

- larger distribution and memory footprint
- Node, renderer, preload, and Python boundaries increase privileged surface
- capabilities must be designed explicitly rather than inherited from the
  framework

### Provisional Direction

Tauri 2 with a TypeScript frontend and packaged Battalion Python sidecar is a
promising candidate. Rust represents an initial learning investment and a
possible long-term capability gain, not an automatic maintenance penalty. The
benchmark should record the effort required to become productive, the clarity
of the resulting boundary, and the operator's confidence maintaining it. Tauri
receives neither a penalty nor a presumptive advantage before that evidence.
This is not an accepted stack decision.

Subsequent outcome: BTN-38 through BTN-40 completed the controlled spikes, and
[ADR-0022](../adrs/adr0022.md) selected PySide6 with Qt Widgets for production
desktop presentation. This provisional section remains as decision history.

The relevant framework capabilities are documented by their maintainers:

- <https://v2.tauri.app/start/frontend/>
- <https://v2.tauri.app/develop/calling-rust/>

- <https://v2.tauri.app/develop/sidecar/>
- <https://doc.qt.io/qtforpython-6/>
- <https://www.electronjs.org/docs/latest/tutorial/process-model>

## Framework Prototypes

Before selecting a stack, three functionally equivalent disposable prototypes
shall be implemented by separate follow-up tickets: Tauri, PySide6, and
Electron. Each prototype uses the same fixture data, visual structure, actions,
and success criteria. Shared frontend code may be reused between Tauri and
Electron only if doing so does not hide framework-specific work from the
comparison.

Each prototype should demonstrate:

1. Launch and supervise the packaged Battalion Python process.
2. Discover and render saved runs without modifying them.
3. Start one simulated run through a replaceable application-command adapter.
4. Stream simulated node lifecycle activity without freezing the interface.
5. Recover the visible state after the client disconnects or restarts.
6. Reconcile a simulated interruption with reloaded durable state.
7. Open a provenance-linked artifact in the user's editor or file manager.
8. Deny arbitrary filesystem and shell access from the renderer.
9. Package and run on Windows without a separately installed Python runtime.
10. Establish a credible path for macOS and Linux packaging.

The prototypes should measure package size, idle and active memory, startup
time, implementation complexity, learning time, resulting operator confidence,
accessibility, testability, one-process-per-run supervision, process failure
behavior, permission surface, and cross-platform packaging risk.

The benchmark includes only simulated Correction and Design-decision actions,
as required by the canonical BTN-37 acceptance criteria; these remain queued
next-attempt fixture records and do not add production application operations.
It does not include live provider calls, semantic search, analytics, or
production repository writes. Using simulated data keeps framework comparison
from becoming a test of three different Battalion integrations.

BTN-37's shared control case, export commands, acceptance trace contract, and
measurement procedure live in the
[desktop benchmark guide](../../benchmarks/desktop/README.md). Tauri, PySide6,
and Electron must consume that scenario and validator unchanged.

Prototype code is evidence and may be discarded. It must not define Battalion
application policy.

## Mobile and Remote Access

A future mobile client should begin as read-mostly:

- run status and history
- search
- token and cost summaries
- artifact provenance metadata
- checkpoint notifications

Starting, steering, approving, or cancelling runs from mobile is deferred. It
requires authenticated remote authority, encrypted transport, project
isolation, stale-command protection, and safe-interruption semantics. A history
viewer does not justify prematurely building that control plane.

---

## Privacy and Retention

Run state, prompts, context, tool arguments, model output, diffs, test logs, and
search embeddings may contain source code or secrets.

Before capturing richer payloads, Battalion needs project-configurable policy
for:

- standard bounded evidence
- sanitized full payloads
- hash-only evidence
- transient, non-retained streams
- retention and explicit deletion
- local versus external indexing

The interface must identify omitted, sanitized, unavailable, and later-pruned
data. It must never present missing data as proof that an input or action did
not exist.

## Delivery Sequence After BTN-29

### 1. Application Boundary

Extract reusable project discovery, history queries, run commands, resume,
cost inspection, Recon invocation, and Intel review behavior from presentation
adapters.

### 2. Desktop Framework Spikes

Build equivalent Tauri, PySide6, and Electron versions. Evaluate process
supervision, streaming, recovery, permissions, packaging, maintenance burden,
and frontend feasibility. Record the selected stack in an ADR only after
evidence exists.

### 3. Read-Only Operator Console

Deliver ticket/run discovery, execution map, inspector, provenance, costs,
interrupt visibility, and Intel library without adding new execution authority.

### 4. Human Actions

Add canonical resume and candidate-review commands, then typed interventions
after safe-boundary semantics are implemented.

### 5. History Search

Add exact and structured search, a rebuildable local catalog, and optional
semantic indexing.

### 6. Analytics

Improve usage evidence, define outcome measures, and add descriptive model-role
comparisons.

| Read-only operator console | Work, History, execution inspection, provenance, cost, and Intel library |
| Human-action surfaces | Canonical interrupt resolution and candidate review, followed by next-attempt Correction and Design decision context |
| Search and analytics projections | Rebuildable history search and descriptive model-role evidence |

These need not all ship in one milestone. The three framework spikes should
depend on the same benchmark fixture so their results remain comparable. Recon
candidate persistence and other foundational evidence work may proceed before
framework selection because they belong to Battalion's application contract,
not to a desktop toolkit.

No identifiers are reserved by this section. The backlog remains the source of
ticket identity after the RFC is accepted.

## Decisions Made by This RFC

- The primary client is a standalone desktop application.
- Work is organized around tickets, runs, and concrete node executions rather
  than chats.
- Work, History, Intel, and Analytics are the primary product destinations.
- Human authority is visible alongside automated execution.
- CLI and graphical clients share application commands and policy.
- Existing local persistence remains authoritative for the first vertical
  slice.
- Search and analytics indexes are derived and rebuildable.
- Mobile begins, if built, as read-mostly.
- One supervised Python worker process owns each active run.
- New canonical run identifiers are generated UUIDs with separate display
  aliases; project identity and migration remain open.
- Recon candidates are persisted as immutable, human-readable Markdown with
  validated metadata before review.
- Operator summaries emphasize work performed, next work, open questions,
  verification, artifacts, and role/model/prompt metadata rather than copied
  code or full prompts.
- Code and prompt provenance use Git revision, dirty-state, explicit versions,
  and bounded hashes rather than retained source or prompt contents by default.
- Future cost observations separate nullable amount, currency, and source.
- The initial UI spikes implement no general intervention contract.
- V1 defines exactly two intervention types: Correction for Driver or
  Refactorer, and Design decision for Architect. Reviewer has no intervention
  type. Intervention content is queued context for the next attempt, never a
  mid-generation steering channel or Reviewer verdict override.
- Recon does not attach confidence to candidates. ADR-0012 and BTN-20 establish
  that confidence derives from operator-feedback evidence rather than creation,
  and the existing accept, edit-and-accept, or reject workflow remains
  sufficient.
- Framework selection follows equivalent Tauri, PySide6, and Electron spikes.

## Open Questions

1. What is the smallest reusable Python command/query surface that supports the
   first desktop vertical slice without becoming a transport-specific API?
2. What durable event granularity is needed for safe live recovery beyond the
   implemented node-execution boundaries?
3. Which strict metadata format and repository path should immutable candidate
   Markdown use, and what retention policy should apply to rejected candidates?
4. How should a project-wide run catalog recognize a repository after it moves,
   and how should existing human-readable run identifiers migrate to UUIDs?
5. Which objective ticket characteristics are sufficient to qualify model
   comparisons without inventing a misleading complexity score?
6. Which framework best satisfies the prototype criteria on supported desktop
    platforms?

Resolved during RFC review:

- code, prompt, and context provenance use Git revision, dirty-state,
  human-readable prompt versions, and bounded hashes instead of retaining code
  or prompt contents by default
- intervention types and landing points are Correction or Design decision,
  queued for the next attempt, with no Reviewer-targeted intervention
- Recon confidence behavior remains unchanged because ADR-0012 and BTN-20
  already reject creation-time confidence

## Non-Goals

- final visual styling or branding
- production UI implementation
- IDE replacement or embedded code editor
- generic chat interface
- mobile execution control
- hosted multi-user collaboration
- automatic model selection
- semantic Intel retrieval
- replacement of the six interrupt triggers
- replacement of `RunState` as graph-control authority
- automatic promotion of execution history into knowledge
- dependence on provider-private chain-of-thought

## Acceptance

Accepted by the human operator on 2026-08-14.

The operator workflows, shared application boundary, current evidence limits,
candidate and usage directions, three-spike benchmark criteria, and follow-up
decomposition are sufficiently explicit to guide architecture spikes and later
implementation without choosing architecture implicitly in UI code.

The six remaining open questions are intentionally deferred. They will be
resolved through implementation evidence and operational use and do not block
this architecture decision.
