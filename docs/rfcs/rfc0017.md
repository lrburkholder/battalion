# RFC-0017 — Terminal Run Immutability and Append-Only Follow-up History

**Status:** Draft  
**Date:** 2026-09-01  
**Ticket:** BTN-107  
**Author:** Architecture  
**Target:** Durable Run history / audit and recovery semantics  
**Related:** `philosophy.md`, RFC-0014, RFC-0015, RFC-0016, BTN-32, BTN-33, BTN-44, BTN-109, BTN-119

---

## Summary

Battalion should treat a terminal Run as a durable historical fact. Once a Run reaches a terminal state, its canonical execution record must not be rewritten. Later retry, correction, continuation, supersession, interpretation, or branch-from-prior-work must create additional durable history linked to the original Run rather than changing what the original Run says happened.

The central invariant is:

> A terminal Run may be referenced, superseded, retried, continued, or branched from, but not rewritten.

This is an auditability rule, not an autonomy mechanism. Battalion retains its existing first-class Run/domain model and human-directed authority boundaries. It does not adopt Carpenter's recursive Arc ontology or collapse Ticket, WorkItem, Signal, Artifact, Actor, and other domain concepts into Runs.

The application boundary mechanically enforces the invariant before persistence. Presentation clients, workflow models, and workers may request or produce transitions, but they do not decide whether terminal history is mutable.

## Status and delivery boundary

This RFC is a draft architecture for BTN-107. It defines terminal-history semantics and the boundary that enforces them. It does not by itself authorize a persistence-engine replacement, event-sourcing rewrite, universal audit ledger, or migration of every historical Battalion artifact into a new storage model.

Implementation should extend the existing Run identity, application, state/persistence, recovery, and first-class Run contracts incrementally.

## Goals

- make completed execution evidence trustworthy as durable history;
- prevent retries, corrections, UI actions, stale workers, or future workflow features from silently rewriting terminal outcomes;
- define which Run states are terminal independently of presentation clients;
- separate Run lifecycle from failure classification;
- distinguish immutable canonical execution evidence from permitted append-only follow-up evidence;
- give retries, corrections, continuations, and superseding work new durable identity;
- make predecessor/successor relationships typed and inspectable;
- preserve original attribution and timestamps for human, model, tool, artifact, verification, cost, and external-operation evidence;
- keep historical and legacy Runs readable without fabricating missing evidence;
- allow history/search/audit projections to distinguish an original outcome from later corrective or superseding work; and
- mechanically reject prohibited terminal or stale mutation before persistence.

## Non-goals

- adopting full event sourcing as Battalion's persistence architecture;
- making every Run field append-only while a Run is still active;
- treating every annotation or derived projection as part of canonical execution state;
- reopening a terminal Run in place;
- collapsing Battalion domain objects into a universal recursive Run abstraction;
- defining the complete audit-query or general annotation surface proposed by BTN-119;
- defining declarative retry/escalation policy proposed by BTN-109; or
- guaranteeing that legacy records contain evidence Battalion did not historically persist.

## Existing architectural constraints

RFC-0014 establishes first-class Run identity and semantics beyond the original Implementation-shaped `RunState`. A Run is therefore a durable execution identity, not merely a mutable graph session.

RFC-0015 establishes typed workflow boundaries and canonical artifact/provenance rules. Terminal immutability must preserve those original workflow inputs, outputs, and provenance rather than replacing them with later interpretations.

RFC-0016 reinforces a broader historical-provenance rule: disabling or relinking current identity must not rewrite historical attribution. BTN-107 applies the same principle to Run execution history.

The shared application boundary already exists to prevent presentation clients from directly mutating saved Run state. Terminal immutability belongs at that boundary and below it, not in desktop/CLI convention or model instructions.

Current `RunStatus` includes `done` and `failed-infra` but does not yet model cancellation as a first-class status. This RFC treats that shape as an ambiguity to remove: infrastructure is a failure classification, while terminal failure and cancellation are Run lifecycle outcomes.

## Terminology

### Canonical Run record

The durable Battalion-owned record of what occurred during a particular Run identity: admitted workflow identity and governing evidence, execution/state transitions, role/model/tool evidence, human decisions, produced artifacts and references, verification evidence, cost/token evidence where recorded, external-operation evidence, and terminal outcome.

The canonical record describes the Run as it happened. Later facts do not alter it.

### Terminal Run

A Run whose execution has reached a final outcome for that Run identity. No further workflow execution may occur under that identity.

The initial terminal lifecycle outcomes are successful completion, terminal failure, and cancellation. Terminality is versioned domain policy rather than a UI decision.

### Failure classification

Evidence describing a failure or interruption that occurred during a Run, such as infrastructure, provider/model, contract, authorization, or deterministic-gate failure. Failure classification does not itself determine whether the Run is terminal.

A transient network failure, worker interruption, or similar recoverable event may therefore be durable failure evidence while the Run remains non-terminal and eligible for recovery under admitted policy.

### Follow-up evidence

Durable evidence created after terminalization that refers to a terminal Run without rewriting its execution history. BTN-107 implements typed Run relationship evidence. Broader post-terminal audit annotations remain architecturally permitted but are deferred to BTN-119.

### Successor Run

A new Run with its own durable identity that intentionally derives from or responds to an earlier Run. A successor does not continue execution under the predecessor's identity.

### Supersession

A typed relationship indicating that later work is intended to replace or correct the practical result of earlier work. Supersession does not change the earlier Run's terminal outcome.

## Terminal-state and failure policy

Terminality must be a domain/application concept exposed through a single versioned policy or helper rather than duplicated as string checks across clients and workflow code.

The initial lifecycle classes are:

```text
non-terminal
  not-started
  in-progress
  blocked
  awaiting-human

terminal
  done
  failed
  cancelled
```

Failure classification is orthogonal:

```text
failure classification
  infrastructure
  model/provider
  contract
  authorization
  deterministic-gate
  ...
```

`failed-infra` should therefore be retired as a lifecycle status rather than made conditionally terminal. Infrastructure failure evidence may be recoverable or terminal depending on the Run's current lifecycle and admitted recovery/failure policy.

For example, a transient network failure can be recorded while the Run remains `in-progress` and retries or resumes. Only when recovery is exhausted, the failure is determined unrecoverable, or governing policy explicitly ends the Run does Battalion persist the terminal lifecycle state `failed`. The terminal failure evidence retains its infrastructure classification and cause.

`blocked` and `awaiting-human` remain non-terminal because the same Run is explicitly waiting for permitted continuation.

BTN-109 may define which failure/escalation conditions permit retry, recovery, or terminalization. BTN-107 defines the history invariant once a terminal outcome is admitted.

## Cancellation semantics

Cancellation is a first-class terminal lifecycle outcome and is not a subtype or spelling of infrastructure failure.

A cancellation records an intentional decision to end a Run and must retain attributable cancellation evidence such as the requesting/authorizing Actor or system authority, timestamp, reason where supplied, and source of the cancellation decision.

Worker termination, process crash, machine restart, network loss, or infrastructure interruption does not by itself mean `cancelled`. Such events remain interruption/failure evidence until Battalion's recovery or governing policy produces an intentional terminal decision.

A cancelled Run may still contain external side-effect evidence whose disposition is independently completed, failed, or ambiguous. Cancellation does not rewrite what already happened before the cancellation decision.

## Immutability boundary

Terminal immutability applies to the canonical execution record for a Run identity.

After terminalization, Battalion must reject operations that would change facts such as:

- terminal status or terminal outcome;
- workflow/recipe identity or admitted governing evidence;
- execution progress or node/role outcomes;
- human actions and their original dispositions;
- model/tool execution attribution;
- artifact/output evidence as originally recorded;
- verification/test evidence as originally recorded;
- token/cost evidence as originally recorded;
- external side-effect attempt/result evidence as originally recorded; or
- original timestamps and contributor/Actor attribution.

The invariant is semantic rather than file-oriented. Moving fields between persistence files or deriving projections does not make previously canonical facts mutable.

## Permitted append-only evidence

Not every fact learned after terminalization belongs inside the original execution record. Battalion may append narrowly defined follow-up evidence when that evidence cannot alter the meaning of what originally occurred.

BTN-107 implements:

1. **Run relationship evidence** — typed predecessor/successor links such as retry-of, supersedes, continuation-of, or branch-from.
2. **Compatibility/index evidence** — derived indexing or migration metadata necessary to read/search historical records, provided it does not fabricate original execution evidence.

The architecture also permits later **audit annotation evidence** — human/system interpretation, classification, or notes with independent identity, provenance, and timestamps — but BTN-107 does not introduce a general annotation facility. BTN-119 owns that broader audit/annotation contract.

Follow-up records are append-only and separately attributable. They are not fields that may be edited into the historical Run as though known during execution.

## Run relationship sidecars

Typed Run relationships are canonical append-only evidence stored separately from canonical Run execution state in per-Run sidecars.

The existing project Run catalog remains concerned with Run identity and discovery. It should not become a second mutable semantic history store.

A relationship is stored exactly once and contains both Run identities rather than duplicating forward and reverse copies that can diverge after partial writes. The canonical relationship evidence includes at minimum:

```text
relationship_id
relationship_type
source_run_id
target_run_id
created_at
authority/provenance
```

The relationship belongs to the sidecar associated with the Run/action that created the later relationship. For example, if Run B retries Run A, B's sidecar may contain `B retry-of A`; the same canonical relationship is not separately copied into A's sidecar.

Project-wide forward/reverse lookup may initially scan bounded sidecar evidence. A future project-level relationship index may be derived for query performance, but it is rebuildable and is not authoritative history.

The initial relationship vocabulary distinguishes at least:

```text
retry-of
  Repeat substantially the same intended execution after failure or other retry decision.

supersedes
  Later work intentionally replaces/corrects the practical result of an earlier Run.

continuation-of
  New Run performs additional work that could not or should not execute under the terminal predecessor identity.

branch-from
  New Run uses the earlier Run/evidence as a starting point but intentionally diverges.
```

A relationship does not imply that the predecessor's outcome changed. In particular, a successful retry of a failed Run leaves the first Run failed.

The storage representation must prevent ambiguous self-links, define duplicate-equivalent relationship operations as deterministic/idempotent or explicitly conflicting, and reject contradictory cycles where deterministically detectable.

## Retry, correction, and supersession

Once terminal:

```text
Run A (failed)
   |
   +-- retry-of --------> Run B (done)

Run C (done, later found wrong)
   |
   +-- superseded-by ---> Run D (done)
```

Run A remains failed. Run C remains done with the evidence and output it actually produced. Search/history may show that D supersedes C, but it must not present C as though D's result had been C's original result.

A correction requested before terminalization may continue under the same Run only when existing workflow/authority policy permits it. A correction after terminalization creates new durable work identity.

## Application enforcement and worker authority

Battalion is the authoritative coordinator and durable-state writer for Runs. Run workers produce proposed transitions/checkpoints/results; they do not independently own canonical persistence authority.

Any application operation that can admit Run execution/state must:

1. establish the current canonical persisted state and revision;
2. verify that the proposed update was derived from that expected revision;
3. determine terminality using canonical lifecycle policy;
4. reject mutation of terminal canonical execution evidence;
5. route permitted post-terminal actions through explicit append/link operations rather than ordinary state-save operations; and
6. atomically persist the admitted next revision.

A presentation client cannot opt out of these checks. A model cannot authorize bypass by emitting different output. Direct persistence helpers should either enforce the same invariant or be sufficiently internal that supported application operations cannot bypass it.

Expected domain failures should be explicit, such as `TerminalRunImmutable` and a stale-revision failure, rather than incidental filesystem or validation errors.

## Persistence and concurrency

BTN-107 retains the existing crash-safe physical write approach while adding semantic stale-write protection.

Each persisted canonical Run carries a monotonically increasing revision. A proposed write declares the revision from which it was derived. The authoritative persistence boundary admits the write only if the expected revision still matches the current durable revision; the accepted write advances the revision.

Conceptually:

```text
current durable revision: 7
worker result derived from: 7
proposed next revision: 8
=> admit

current durable revision: 8
late worker result derived from: 7
=> reject as stale
```

This compare-and-set/revision contract protects against a late worker overwriting a newer or terminal state. It is semantically required even if execution is currently local and serialized.

The existing atomic temporary-file replacement remains responsible for preventing truncated/corrupt physical state after process termination. A filesystem/process lock is not part of the domain contract and should only be added if implementation demonstrates that simultaneous physical operations require one.

This separation keeps the contract portable if worker hosting or persistence changes later: workers propose results, Battalion admits them against current authoritative revision.

Append-only relationship operations require stable relationship identities or idempotency keys so retries do not create accidental duplicate evidence.

## Legacy compatibility

Historical Runs created before this invariant may lack cancellation state, revision metadata, typed relationships, complete provenance, or evidence introduced by later RFCs.

Compatibility rules:

- legacy Runs remain readable whenever their historical schema can be validated or explicitly adapted;
- migration may add schema/index/compatibility metadata but must not invent events, Actors, model executions, decisions, timestamps, relationships, or outcomes not supported by the original record;
- where terminality can be determined from historical status, the migrated/read-compatible Run receives the corresponding terminal classification;
- historical `failed-infra` records are interpreted through an explicit compatibility rule rather than silently pretending the old status always carried the new lifecycle/failure-classification distinction;
- where evidence is absent or ambiguous, projections report unknown/legacy rather than synthesizing certainty; and
- reading a legacy Run must not require mutating its original stored execution evidence merely to make it inspectable.

## History, search, and audit projections

Presentation/query layers may derive a current practical view such as "superseded by Run D" or "retry succeeded in Run B," but must preserve the original terminal outcome separately.

At minimum, projections should be able to expose:

```text
Run C
original_outcome: done
terminal_at: ...
superseded_by: Run D
current_interpretation: superseded
```

rather than rewriting Run C's outcome to `superseded` unless `superseded` is explicitly a derived projection field rather than canonical execution status.

BTN-119 builds richer audit projections and the general post-terminal annotation model over this foundation.

## Interaction with recovery

Recovery of a non-terminal interrupted Run may resume the same identity when existing recovery policy proves that doing so is safe.

A recoverable infrastructure failure therefore does not require a successor Run merely because failure evidence exists. The same Run may continue if its lifecycle remains non-terminal and policy permits recovery.

Recovery of a terminal Run is not resume. It is a new Run relationship governed by explicit retry/continuation/supersession semantics.

This distinction prevents a future recovery feature from turning terminal history back into mutable workflow state.

## Security and privacy

Immutability is not a justification for retaining secrets or prohibited sensitive data forever. Existing secret/data-handling boundaries still apply before evidence is persisted.

If Battalion later requires legally or operationally mandated deletion/redaction of already persisted sensitive material, that must be designed as an explicit exceptional evidence-redaction mechanism with durable tombstone/audit semantics where lawful and appropriate. It must not become a general-purpose route for editing inconvenient Run history.

This exception is deliberately not designed in BTN-107.

## Alternatives considered

### Allow reopening terminal Runs

Rejected. Reopening makes a Run identity mean different things at different times and weakens debugging, attribution, analytics, and human trust. A retry or correction is itself meaningful history and deserves a new identity.

### Treat failure classification as lifecycle state

Rejected. A classification such as infrastructure failure may describe either a transient recoverable event or the cause of a terminal failure. Encoding `failed-infra` as lifecycle conflates what happened with whether the Run can continue.

### Rely on UI convention

Rejected. CLI, desktop, future clients, workers, integrations, and tests would each need to reproduce the rule. Battalion's architecture already establishes a shared application authority boundary.

### Use only a process/filesystem lock for concurrency

Rejected as the primary semantic guard. A late worker may legitimately acquire a lock after newer state has been persisted; locking alone cannot determine whether the worker's result was derived from stale state. Revision comparison provides that domain-level guarantee. Locks remain an implementation option for physical serialization if needed.

### Store relationships in the Run catalog

Rejected. The catalog's responsibility is Run identity/discovery. Making it authoritative semantic history would mix concerns and make terminal follow-up evidence dependent on a mutable project catalog.

### Use a project-level relationship store as canonical history

Deferred/rejected for the initial implementation. Per-Run sidecars keep canonical follow-up evidence adjacent to the Run while remaining separate from immutable execution state. Project-level indexes may be derived later for efficient lookup.

### Make the persisted Run file physically immutable and put everything afterward elsewhere

Directionally attractive but too storage-specific for the architecture contract. The semantic invariant matters more than whether implementation uses one file, several files, a database, or a future event store. The initial sidecar design is an implementation direction, not a permanent storage-engine constraint.

### Adopt full event sourcing

Rejected for BTN-107. Event sourcing could satisfy the invariant but would greatly expand scope and migration cost. Battalion can enforce terminal immutability and append-only follow-up evidence without committing the entire application to an event-sourced architecture.

### Copy Carpenter's Arc model

Rejected. Carpenter provides useful prior art for immutable terminal execution, but Battalion's human-directed first-class Run model and separate domain concepts are intentional. Immutability is adopted; the universal recursive ontology is not.

## Implementation direction

Implementation should likely be decomposed into:

1. separate lifecycle terminality from failure classification and retire `failed-infra` as a lifecycle status;
2. introduce first-class `failed` and `cancelled` terminal lifecycle states and attributable cancellation evidence;
3. add persisted monotonic Run revision and expected-revision admission checks;
4. enforce terminal mutation rejection at Battalion's authoritative application/persistence boundary;
5. add per-Run append-only sidecar storage for typed Run relationship evidence;
6. add retry/supersession/continuation creation paths using new Run identities;
7. provide explicit legacy compatibility for historical statuses/evidence;
8. update history/search projections without making derived indexes authoritative; and
9. add deterministic tests for terminal states, recoverable failures, stale writes, relationships, cancellation, and legacy records.

The Driver should not infer a storage redesign from this list. The smallest implementation satisfying the semantic contracts is preferred.

## Testing requirements

Tests must cover at least:

- successful (`done`) Run becomes immutable;
- terminal `failed` Run becomes immutable;
- `cancelled` Run becomes immutable and retains attributable cancellation evidence;
- recoverable infrastructure failure can remain non-terminal;
- worker/process interruption does not automatically mean cancellation;
- `blocked` and `awaiting-human` remain resumable/non-terminal;
- mutation of canonical terminal evidence is rejected;
- permitted append-only relationship evidence succeeds;
- relationship evidence is stored once with both Run identities;
- retry creates a new Run identity and preserves predecessor outcome;
- supersession creates a new Run identity/link and preserves predecessor outcome;
- stale worker result cannot overwrite a newer or concurrently terminalized Run;
- revision advances monotonically on admitted canonical writes;
- duplicate/idempotent relationship operation behavior;
- invalid/self/contradictory relationship behavior where applicable;
- legacy terminal Run remains readable;
- historical `failed-infra` compatibility does not fabricate modern evidence;
- missing legacy evidence is not fabricated; and
- history/search distinguishes original outcome from later follow-up state.

## Resolved design decisions

1. **Typed Run relationships use per-Run append-only sidecars as canonical follow-up evidence.** Relationships are stored once with both Run identities and explicit provenance. `ProjectRunCatalog` remains an identity/discovery mechanism. Project-wide forward/reverse indexes may be derived later but are not authoritative history.

2. **Battalion is the authoritative coordinator/writer; Runs are workers that produce proposed transitions/results.** Canonical Run state uses a monotonically increasing revision and expected-revision compare-and-set semantics. Stale results are rejected before persistence. Existing atomic file replacement remains the crash-safety mechanism; locks are optional implementation detail if physical serialization later requires them.

3. **Failure classification is separate from Run lifecycle.** `failed-infra` should be retired as a lifecycle status. Recoverable infrastructure failures may be recorded while the Run remains non-terminal. A Run becomes terminal `failed` only when recovery is exhausted, failure is unrecoverable, or governing policy deliberately terminalizes it.

4. **Cancellation is a first-class terminal lifecycle state with attributable cancellation evidence.** Intentional cancellation is distinct from worker termination, process crash, network loss, and other infrastructure interruptions.

5. **General post-terminal audit annotations are deferred to BTN-119.** BTN-107 establishes that later annotations cannot rewrite canonical terminal execution evidence, but implements only the typed Run relationships needed for retry, supersession, continuation, and branching.

## Decision requested

Accept the following architectural contract:

> Once Battalion records a terminal outcome for a Run identity, canonical execution evidence for that Run is immutable. Any later retry, correction, continuation, supersession, or interpretation is additional durable history with separate identity, provenance, or typed linkage. Failure classification is independent of lifecycle terminality; Battalion centrally admits worker-produced state transitions using revision-checked persistence; and post-terminal Run relationships live as append-only sidecar evidence rather than mutations of the canonical Run.
