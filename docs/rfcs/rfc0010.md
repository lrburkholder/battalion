# RFC-0010 — Deterministic Repository Quality Gates

**Status:** Proposed
**Ticket:** BTN-49
**Author:** Architecture
**Target:** Post-v2
**Related:** `philosophy.md`, BTN-19, BTN-30, RFC-0006, RFC-0008, RFC-0009, BTN-46, BTN-85, BTN-97

---

## Summary

Battalion will support **deterministic repository quality gates** as a distinct verification stage after Refactorer and before the final Reviewer checkpoint.

Quality gates execute repository-appropriate, mechanically evaluable checks such as linters, type checkers, format-verification commands, static analyzers, and similar tools. The repository owns the checker implementation and repository-specific configuration; Battalion owns when configured gates run, how results are normalized and persisted, how retry and interruption policy is applied, and how an authorized Actor may override a result.

Quality gates are not Reviewer responsibilities, AI roles, plugins, or external CI jobs. They are deterministic execution stages under Battalion application/graph policy. A blocking finding routes back to Refactorer without invoking final Reviewer. A mandatory gate that cannot produce a trustworthy result does not masquerade as a code defect; it becomes an inspectable execution problem and, where policy requires, a human interrupt.

Within RFC-0008's shared execution model, Quality Gates are part of an **Implementation Run** rather than a separate `WorkflowExecution`. Cartography may contribute derived repository evidence and candidate gate suggestions, but activating a gate remains an explicit project/repository configuration decision under Battalion policy.

The first validation case is `dmmulroy/anti-slop`, an opinionated vendored Oxlint ruleset for TypeScript/JavaScript. It is used only to prove that an opinionated repository-owned checker can fit the generic contract without special Battalion treatment. A representative Python checker validates that the contract is genuinely language-neutral.

Cartographer may later inspect repository-native scripts and tool configuration and suggest candidate gate declarations, but discovery does not grant authority: suggested gates become active only through explicit Battalion/project configuration.

External CI systems such as GitHub Actions, Jenkins, GitLab CI, or Azure DevOps are intentionally outside this local deterministic gate contract. They may later participate through a provider/plugin integration boundary and contribute external verification evidence.

## Context

Battalion already distinguishes execution roles and checkpoints. At the time of this RFC, Reviewer independently re-runs repository tests from a clean copy rather than trusting Driver's self-reported result. RED, GREEN, and REFACTOR checkpoints therefore preserve an independent verification boundary.

However, tests do not represent the complete mechanically checkable quality policy of a repository. Mature repositories may also require checks such as:

- `ruff check .`
- `mypy`
- `dotnet format --verify-no-changes`
- TypeScript linting
- Oxlint rule sets such as anti-slop
- dependency-boundary checks
- generated-code consistency checks
- repository-specific verification scripts

These checks differ from semantic review in an important way: they can generally be executed without model judgment. If a deterministic quality check can prove that a refactored candidate is not acceptable, invoking an LLM Reviewer first wastes tokens and obscures responsibility.

BTN-49 therefore asks:

> How should Battalion execute repository-defined deterministic quality checks so that cheap mechanical evidence can reject a refactored candidate before final semantic review without allowing the checker, its exit code, or its configuration to become graph authority?

The answer must preserve Battalion's existing architectural principles:

- one application/graph policy authority
- explicit write and side-effect boundaries
- durable evidence and provenance
- bounded retries rather than autonomous loops
- Actor-owned consequential overrides
- repository artifacts as project sources of truth
- no hidden dependency installation or repository mutation
- provider/plugin boundaries only where external integration is actually involved

---

## Goals

- define a language-neutral `QualityGate` execution and result contract
- place deterministic quality verification after Refactorer and before final Reviewer
- allow blocking findings to route directly back to Refactorer without spending Reviewer tokens
- distinguish checker findings from checker execution failures
- support warnings and informational findings without equating every finding with failure
- make gate identity, tool identity/version, configuration, invocation, repository state, findings, disposition, retries, and Actor overrides inspectable
- support per-gate retry budgets configured by Battalion policy
- support project-level policy and repository-specific gate declarations for projects containing multiple repositories
- keep gate execution read-only with respect to the target repository
- prevent a gate from installing dependencies, rewriting configuration, auto-fixing source, or broadening node write scopes
- preserve room for structured machine-readable findings while supporting plain-command tools through a bounded fallback
- allow Cartographer to suggest candidate repository-native gates without automatically activating them
- preserve external CI as a separate future integration concern
- validate the abstraction with anti-slop and a representative Python checker

## Non-goals

- replacing Reviewer with deterministic tooling
- moving all test semantics into BTN-49
- creating a new AI role for linting or quality verification
- treating quality gates as RFC-0009 plugins
- automatically discovering and enabling every repository script
- installing missing tools or dependencies
- allowing gates to mutate or auto-fix the target repository
- making external CI a local gate implementation
- deciding a universal lint/style policy for Battalion projects
- making anti-slop a Battalion dependency or privileged checker
- treating warnings as defects merely because they were emitted by a tool
- solving repository-instruction semantics such as `AGENTS.md` or `CLAUDE.md`; that is BTN-97

## Architectural decision

### 1. Quality gates are a distinct deterministic stage

The normal post-GREEN path becomes:

```text
Driver GREEN
    |
    v
Reviewer GREEN checkpoint
    |
    v
Refactorer
    |
    v
Deterministic Quality Gates
    |\
    | +-- blocking finding ----------> Refactorer
    |
    +---- mandatory gate unavailable/
    |     timeout/malformed result ---> human interrupt when policy requires
    |
    +---- pass or permitted findings
             |
             v
      Reviewer REFACTOR checkpoint
             |
             v
            Done
```

Quality gates do **not** run after GREEN by default. GREEN establishes the smallest working implementation and the GREEN Reviewer checkpoint verifies that behavior. Refactorer then produces the repository state expected to satisfy broader deterministic engineering-quality policy.

The final Reviewer checkpoint remains independent. Quality gates only answer mechanically evaluable questions; Reviewer remains responsible for semantic judgment and the independent checkpoint contract.

A future gate definition may support explicit stage applicability if a repository has a justified deterministic check elsewhere, but BTN-49's initial execution placement is after Refactorer and before `REFACTOR_CHECK`.

### 2. A gate is verification, not an Actor or role

A Quality Gate is not comparable to Architect, Driver, Reviewer, or Refactorer. It has no prompt, model identity, human-decision authority, or independent write scope.

Conceptually:

```text
Battalion graph/application policy
          |
          | decides when and whether a configured gate matters
          v
QualityGate runner
          |
          | invokes bounded repository-owned checker
          v
Repository-owned tool/configuration
          |
          v
Normalized QualityGateResult
          |
          | policy decides disposition
          v
continue / retry Refactorer / interrupt / Actor override
```

An implementation may use a graph node or equivalent orchestration primitive to represent the stage, but that is an execution mechanism, not a new model role.

### 3. Repository tools; Battalion execution policy

Ownership is deliberately split:

| Concern | Owner |
| --- | --- |
| checker implementation | repository/tool ecosystem |
| checker-specific configuration | repository |
| gate declaration for a repository | Battalion project/repository configuration |
| project-wide gate policy | Battalion project configuration |
| execution and normalization | Battalion |
| retry/interruption semantics | Battalion policy |
| Actor authorization for overrides | Battalion authorization/application boundary |
| semantic review | Reviewer |

A repository may therefore use Python, .NET, JavaScript/TypeScript, Rust, Java, shell scripts, or other ecosystems without Battalion needing language-specific graph behavior.

### 4. Project policy and repository declarations are separate layers

A Battalion Project may contain more than one repository. Gate configuration therefore has at least two conceptual layers:

```text
Battalion Project
|
+-- project quality-gate policy
|
+-- repository A
|   +-- repository gate declarations
|
+-- repository B
    +-- repository gate declarations
```

Repository declarations identify checks appropriate to that repository: command/API adapter, working directory, expected structured-output mode, applicable paths if supported, timeout ceiling, and stable gate identity.

Project policy controls matters such as:

- whether a gate is required, blocking, or advisory
- per-gate retry budget
- maximum timeout/resource ceilings
- whether unavailable mandatory gates require an interrupt
- which Actor capability is required for overrides
- higher-level mandatory gates or policy ceilings

Repository-local configuration may specialize project policy where explicitly allowed but may not silently weaken a mandatory higher-level requirement. The implementation ticket must define exact merge and precedence mechanics and reject ambiguous weakening rather than guessing.

### 5. Gate discovery is advisory only

Battalion does not silently infer authority from the presence of `package.json`, `pyproject.toml`, `.github/workflows`, `Makefile`, `justfile`, solution files, or arbitrary scripts.

Cartographer may later inspect repository-native evidence and suggest candidate gates, for example:

```text
Observed repository evidence
    pyproject.toml -> ruff + mypy
    package.json   -> lint script
    workflow file  -> verification command
            |
            v
Cartographer candidate suggestions
            |
            v
Actor/project configuration decision
            |
            v
authoritative QualityGate declarations
```

QualityGate execution must function without Cartographer. Cartographer suggestion output is derived knowledge, not configuration authority.

### 6. Gate execution is read-only

Quality gates verify candidate state; they do not transform it.

Allowed examples include:

- `ruff check .`
- `dotnet format --verify-no-changes`
- a linter in check-only mode
- a type checker
- a repository verification script that is contractually read-only

Disallowed as Quality Gates include:

- `ruff check --fix`
- `dotnet format` when it rewrites files
- commands that update lockfiles
- commands that regenerate tracked artifacts as part of normal success
- commands that install dependencies
- commands that rewrite lint configuration

If a repository requires an auto-fix or generated transformation, that work belongs to Refactorer/Driver or another explicitly authorized transformation step. A checker that violates its declared read-only contract is a gate execution failure and architecture/safety defect, not a successful check.

Battalion should mechanically detect target-tree mutation where practical by comparing repository state before and after execution. The exact tree-hash/worktree mechanism is left to implementation design, but the contract requires that silent mutation cannot be interpreted as a passing gate.

### 7. Gates never install missing tooling

Missing executables, packages, plugins, runtime dependencies, or configuration produce an explicit unavailable/configuration outcome. The QualityGate runner does not run `pip install`, `npm install`, package-manager restore commands, agent installation skills, or equivalent setup steps on its own.

This keeps verification deterministic and prevents a nominally read-only gate from becoming package-management or arbitrary network authority.

Repository/bootstrap setup is a separate concern and may be performed through an authorized workflow before gate execution.

### 8. Invocation contract

The language-neutral gate contract must support at least:

- stable `gate_id`
- repository identity
- working directory relative to repository root
- invocation kind
- command/arguments or adapter identity
- environment allowlist/overrides
- timeout ceiling
- expected output mode
- tool identity and version evidence where obtainable
- relevant configuration identity/hash where obtainable
- repository revision/tree evidence
- cancellation

Initial implementation should prioritize explicit command-backed gates because they fit existing repository tooling and are simple to inspect. The contract may allow a Battalion-owned adapter-backed executor where necessary for a tool with a stable API, but adapters do not become RFC-0009 plugins merely because they implement a local QualityGate executor.

Ambient shell interpretation should be avoided by default. Command-backed gates should use explicit argument arrays rather than concatenated shell strings unless a separately justified repository script requires a shell boundary.

### 9. Result model distinguishes findings from execution outcomes

A successfully executed checker may return no findings or one or more findings. Findings are not synonymous with execution failure.

Conceptual result:

```text
QualityGateResult
    gate_id
    repository_id
    attempt
    tool_identity
    tool_version
    invocation_evidence
    configuration_evidence
    repository_evidence
    started_at
    completed_at
    outcome
    findings[]
    bounded_diagnostics
```

Canonical outcomes are:

- `pass` — checker completed successfully with no reportable findings under its normalized contract
- `findings` — checker completed successfully and produced one or more normalized findings
- `unavailable` — required executable/runtime/tool/configuration is not available
- `malformed_output` — checker ran but output required for trustworthy normalization could not be parsed/validated
- `timeout` — checker exceeded its configured ceiling
- `execution_failure` — checker/process/runtime failed independently of normal reported findings
- `cancelled` — Battalion/operator cancellation prevented completion

A finding carries at least the information available from the underlying tool, potentially including:

```text
QualityGateFinding
    finding_id / fingerprint
    gate_id
    rule_id?
    severity
        error
        warning
        info
    path?
    line/column/range?
    message
    structured_details?
```

Plain-command tools that cannot emit structured diagnostics may use a bounded generic finding/diagnostic fallback. The runner must not fabricate file/rule precision that the underlying checker did not provide.

### 10. Tool exit codes are evidence, not graph authority

A process exit code is interpreted by the configured executor/normalizer. It does not directly decide Battalion routing.

For one tool, exit code `1` may mean ordinary findings; for another, it may mean execution failure. Battalion normalizes the tool's documented semantics into `QualityGateResult`, then application/graph policy decides disposition.

This keeps checker implementation separate from workflow authority.

### 11. Findings support severity and policy disposition

A gate may successfully return errors, warnings, and informational findings. Project policy determines their effect.

Typical mapping:

```text
error   -> blocking
warning -> advisory
info    -> evidence only
```

but the mapping may be gate-specific where explicit policy requires it.

A warning therefore does not cause the gate itself to be described as crashed or failed. The durable truth remains that the gate produced findings; disposition is recorded separately.

### 12. Blocking findings retry Refactorer

A blocking finding before final Reviewer routes back to Refactorer without invoking `REFACTOR_CHECK` Reviewer.

This is the primary token-efficiency property of BTN-49:

```text
Refactorer
    |
    v
cheap deterministic evidence
    |
    +-- unacceptable -> Refactorer
    |
    +-- acceptable ---> expensive/semantic final Reviewer
```

Quality-gate retries are separate from `reviewer_rejection_history`. A mechanical finding is not a Reviewer rejection and does not increment Reviewer same-cause counters.

### 13. Retry budgets are per gate and bounded

Each blocking gate has a small configurable retry budget governed by Battalion project policy.

Conceptually:

```text
anti-slop:
    retry_budget: 2
```

When a blocking gate finds a problem:

1. record the gate attempt and finding evidence;
2. route to Refactorer while the gate's retry budget permits;
3. re-run the required gate set after Refactorer produces a new candidate;
4. if the relevant blocking condition persists beyond policy, require a human decision rather than looping indefinitely.

The implementation should use stable finding fingerprints where possible so trivial line movement does not automatically reset the semantic identity of a repeated finding. Fingerprinting should favor stable inputs such as gate identity, rule identity, normalized path and normalized message/context while avoiding dependence on exact line number alone.

Retry accounting semantics must remain inspectable even when a finding disappears and another appears.

### 14. Execution problems are not code defects

`unavailable`, `timeout`, `malformed_output`, `execution_failure`, and `cancelled` do not automatically route to Refactorer. Refactorer cannot necessarily repair missing tooling, a crashed checker, or infrastructure failure.

Battalion surfaces these outcomes separately from source findings.

For a mandatory gate, an unavailable or untrustworthy result blocks final Reviewer progression unless project policy explicitly defines an allowed degradation path. The normal mandatory behavior is a human interrupt with enough bounded evidence to decide how to proceed.

For an advisory gate, policy may record the unavailable state and continue if that weakening is explicitly configured.

### 15. Human interrupts and Actor-bound overrides

Human interruption is required when policy cannot safely choose a deterministic next step, including at least:

- a mandatory gate remains unavailable/untrustworthy and policy requires it
- a blocking condition exhausts its retry budget
- an Actor requests an override requiring explicit authorization

Overrides are durable **Actor decisions**, not rewrites of gate history.

Conceptual record:

```text
QualityGateOverride
    actor_id
    run_id
    repository_id
    gate_id
    finding_ids?
    scope
    reason
    created_at
```

Supported override scopes should distinguish at least:

- one finding/attempt
- one gate for one Run
- repository policy change
- project policy change

An operator surface may therefore state:

> Actor Luke overrode `anti-slop` on Run 123 for this Run, with the recorded reason.

The original gate result remains `findings`; the override is a separate human-decision artifact that authorizes progression despite the result.

Permanent project/repository policy changes require the relevant Actor administration capability and must not be implemented as a hidden Run-local waiver.

The exact authorization capabilities build on Battalion's Actor/authorization architecture and are implementation follow-up work.

### 16. Reviewer receives bounded gate evidence

Final Reviewer should receive evidence that required gates ran and their disposition without receiving unbounded linter output.

The context projection should include, where relevant:

- which required gates passed
- which advisory gates produced findings
- any Actor overrides
- bounded summaries of advisory findings useful to semantic review
- provenance sufficient to inspect full durable results outside model context

Large raw stdout/stderr, repeated diagnostics, caches, and verbose successful output are not injected into Reviewer context by default.

This preserves provenance while controlling token cost.

### 17. Gate evidence is tied to repository and configuration state

Every result must be attributable to the candidate it actually checked.

Evidence should identify at least:

- repository identity
- repository revision/tree/worktree evidence sufficient to detect later changes
- `gate_id`
- gate configuration identity/hash
- tool/version where obtainable
- execution time and duration
- normalized result

The contract should permit safe result reuse only when Battalion can prove that relevant repository state, gate configuration, and tool identity remain compatible. Initial implementation does not need sophisticated caching; re-running after Refactorer is acceptable. The data model must not make future safe reuse impossible.

A successful result from an older candidate cannot silently authorize a changed candidate.

### 18. Parallelism is allowed but not required initially

Independent read-only gates may eventually execute concurrently. The contract therefore must not require sequential semantic dependence between unrelated gates.

Initial implementation may execute configured gates sequentially for simplicity and deterministic diagnostics. Parallelism is an optimization, not part of BTN-49 acceptance.

If parallel execution is later added, cancellation, resource ceilings, result ordering, and deterministic presentation must remain well defined.

### 19. External CI is a separate integration boundary

GitHub Actions, Jenkins, GitLab CI, Azure DevOps, and similar systems are not local deterministic QualityGate executors in this RFC. They introduce provider-specific network access, credentials, asynchronous job state, external side effects, availability, rate limits, and ambiguous remote outcomes.

A future Battalion capability may model external verification/CI and allow RFC-0009 plugins to implement provider adapters beneath that capability, analogous to other external integrations. The exact capability name and contract are intentionally deferred.

External CI may repeat the same repository checks as local Battalion gates. Passing local gates does not imply CI is unnecessary, and passing CI does not retroactively replace the local gate evidence for a Run.

### 20. Repository instructions are a separate layer

Non-deterministic project instructions such as `AGENTS.md`, `CLAUDE.md`, `CONTRIBUTING.md`, and path-scoped architectural guidance are not Quality Gates merely because they influence quality.

BTN-97 will define repository-instruction discovery, resolution, provenance, context assembly, and semantic-compliance architecture. Where a prose instruction can be made mechanically evaluable, a later implementation may promote that constraint into an explicit deterministic gate, but the prose instruction and its mechanical enforcement remain distinct artifacts.

## Anti-slop validation case

`dmmulroy/anti-slop` is intentionally used as a case study rather than an architectural dependency.

At the time BTN-49 was drafted, anti-slop described itself as opinionated Oxlint rules rejecting low-evidence/low-signal TypeScript and JavaScript patterns. Its documentation explicitly recommends vendoring the rules into the target repository and changing them to match team standards rather than treating the project as a fixed npm dependency. Manual setup copies its source into the target repository, installs matching Oxlint dependencies, and registers the vendored plugin in repository lint configuration.

That shape is useful evidence for BTN-49:

- policy lives with the repository
- the checker is opinionated and may emit debatable findings
- Battalion should not own or special-case the rules
- setup/mutation belongs outside the QualityGate execution stage
- once configured, the checker can be invoked as ordinary repository verification
- false positives require bounded retry and Actor override semantics rather than infinite autonomous repair

The disposable validation must not install anti-slop into Battalion core or promote it to a required Battalion dependency.

### Required TypeScript/JavaScript scenarios

A disposable fixture must demonstrate at least:

1. clean pass
2. blocking finding
3. warning/advisory finding where the tool/fixture can represent one
4. repeated finding through bounded Refactorer retry
5. Actor override with durable reason
6. malformed/unparseable output
7. missing checker/tool
8. timeout
9. checker execution failure
10. attempted repository mutation detected/rejected where practical
11. false-positive scenario demonstrating operator correction path

### Required Python scenarios

A representative Python checker, such as Ruff or another maintained deterministic repository check, must exercise the same logical contract sufficiently to prove that:

- gate identity/configuration is not JavaScript-specific
- working directory and invocation are language-neutral
- findings can be normalized without Oxlint-specific graph semantics
- unavailable/timeout/execution-failure behavior is shared
- severity/disposition and retry behavior are Battalion concepts, not tool concepts

The goal is contract validation, not a benchmark of which linter is better.

## Failure and degradation semantics

| Condition | Normalized result | Default policy consequence |
| --- | --- | --- |
| checker completes cleanly | `pass` | continue |
| checker reports blocking issue | `findings` | retry Refactorer within gate budget |
| checker reports warning/info only | `findings` | persist; continue if policy permits; bounded Reviewer projection |
| blocking finding exhausts retry budget | `findings` | human interrupt |
| mandatory tool missing | `unavailable` | human interrupt |
| advisory tool missing | `unavailable` | persist and continue only if policy explicitly permits |
| required structured output invalid | `malformed_output` | human interrupt for mandatory gate |
| checker exceeds timeout | `timeout` | human interrupt for mandatory gate |
| checker crashes/infrastructure fails | `execution_failure` | human interrupt for mandatory gate |
| user/system cancels | `cancelled` | preserve cancellation semantics; do not invent a defect |
| checker mutates target repository | `execution_failure` or dedicated policy violation | do not treat as pass; surface violation |

Specific implementations may introduce typed subcauses, but they must preserve the distinction between source findings and inability to obtain trustworthy verification evidence.

## Security and authority boundaries

QualityGate execution is deliberately narrower than the RFC-0009 plugin model.

A local gate receives only the repository access and execution environment required for verification. It does not receive:

- Battalion graph mutation authority
- `RunState` mutation authority
- Actor credentials
- repository publish/push authority
- external integration credentials by default
- automatic package-install authority
- arbitrary network authority by default
- Driver/Refactorer write tools

Filesystem, process, network, dependency-installation, and configuration-write behavior must remain least-authority. A gate declaration cannot broaden a node's write scope.

If a checker inherently requires network or credentials, it should be treated skeptically as a local deterministic gate. Where the real operation is an external service/CI check, the appropriate design is likely a future integration capability rather than weakening this local boundary.

Secrets and environment values must follow Battalion's existing secret/redaction policy. Raw environment inheritance should be minimized and explicit.

---

## Data and provenance requirements

The runtime representation does not need to live entirely in `RunState`. Durable storage may be normalized outside graph state and projected into the Run as bounded references/evidence.

At minimum Battalion must be able to answer after a Run:

- which gates were required for each repository
- which exact gate configuration applied
- which candidate repository state was checked
- what tool/version was invoked where obtainable
- what outcome and findings were produced
- how many retries occurred
- which findings persisted or changed
- whether final progression depended on an Actor override
- which Actor authorized the override and why
- whether any mandatory gate was unavailable or degraded

Evidence must remain inspectable without requiring model reconstruction of the event.

## Interaction with current Reviewer behavior

At the time of this RFC, Reviewer owns independent clean-tree test re-execution for RED/GREEN/REFACTOR checkpoints. BTN-49 does not silently rewrite that architecture.

The accepted placement is:

```text
... -> Refactorer -> Quality Gates -> Reviewer(REFACTOR_CHECK) -> Done
```

QualityGate findings do not enter `reviewer_rejection_history`. Reviewer rejection remains separate semantic/checkpoint evidence.

A later architecture ticket may choose to generalize or separate Reviewer's hard-coded test subprocess into a broader deterministic verification subsystem, but that is not required to accept BTN-49 and must preserve RED/GREEN polarity semantics if pursued.

## Configuration sketch

Exact schema is implementation work, but the architecture should support a shape conceptually equivalent to:

```yaml
quality_gates:
  policy:
    default_retry_budget: 1
    mandatory_unavailable: interrupt

  repositories:
    backend:
      gates:
        ruff:
          command: ["ruff", "check", "."]
          working_directory: "."
          required: true
          retry_budget: 2
          output: "ruff-json"

    web:
      gates:
        anti-slop:
          command: ["pnpm", "exec", "oxlint", "--format", "json", "."]
          working_directory: "."
          required: true
          retry_budget: 1
          output: "oxlint-json"
```

This example is illustrative only. RFC acceptance does not freeze YAML, field names, command syntax, package manager, or normalizer identifiers.

Project policy must be able to impose constraints that repository-local configuration cannot silently weaken.

## Alternatives considered

### Put all quality checks inside Reviewer

Rejected.

It mixes deterministic verification with semantic/model judgment, makes cheap mechanical failures consume Reviewer budget unnecessarily, and blurs mechanical failure history with Reviewer rejection history.

### Run gates after GREEN and after REFACTOR

Rejected as the default.

GREEN's purpose is to establish the smallest working implementation. Broader engineering-quality policy belongs naturally to the Refactorer output. Running the full suite after GREEN adds latency and potentially duplicate loops without a demonstrated need.

Stage-specific gates may be revisited where explicit repository policy justifies them.

### Treat quality tools as RFC-0009 plugins

Rejected.

A local repository checker such as Ruff, mypy, Oxlint, or anti-slop does not inherently represent an external provider integration. Forcing it through plugin lifecycle/marketplace semantics adds complexity and grants the plugin architecture authority it does not need.

### Treat external CI as a Quality Gate

Rejected for the initial contract.

Remote CI has credentials, provider identity, asynchronous job lifecycle, network failure, side effects, remote state, and ambiguous outcomes. It should fit a future external verification integration contract rather than weakening the deterministic local gate model.

### Let gates auto-fix findings

Rejected.

Verification and mutation are separate authorities. Auto-fixing would turn a deterministic checkpoint into an unbounded transformation stage and make provenance harder to reason about. Refactorer owns correction.

### Automatically install missing gate dependencies

Rejected.

Installation introduces repository mutation, dependency policy, network access, and potentially arbitrary code execution. Missing tooling is an inspectable `unavailable` state.

### Automatically infer gate policy from repository scripts

Rejected.

Discovery can suggest likely checks, but repository artifacts do not state Battalion blocking/override/retry policy merely by existing. Explicit configuration remains authoritative.

## Consequences

### Positive

- deterministic defects can short-circuit final Reviewer invocation
- quality tooling remains language/tool agnostic
- repository teams retain ownership of checker policy and configuration
- warnings are represented honestly instead of collapsed into pass/fail
- execution failures are not misreported as source defects
- retry loops are bounded and independently measurable
- Actor overrides remain attributable and auditable
- multi-repository projects can express distinct checker sets under shared policy
- future Cartographer discovery can improve setup without gaining configuration authority
- external CI remains cleanly separated behind integration semantics

### Costs

- Battalion gains another orchestration stage and durable evidence type
- tool-specific normalization adapters may be required for useful structured findings
- repository mutation detection adds execution overhead
- configuration precedence needs careful implementation
- Actor override UI/application operations require follow-up work
- projects must bootstrap their checker dependencies outside the gate stage
- some repositories will initially use coarse plain-output gates until structured normalizers exist

---

## Follow-up implementation work

RFC acceptance should split runtime work into separate tickets rather than implementing all concerns under BTN-49. At minimum follow-up planning should cover:

1. QualityGate configuration schema and project/repository precedence
2. deterministic command runner, timeout/cancellation, environment, and read-only mutation detection
3. normalized result/finding model, fingerprints, and durable provenance
4. graph/application placement between Refactorer and final Reviewer
5. per-gate retry accounting and Refactorer routing
6. mandatory gate failure interrupt semantics
7. Actor-authorized override application operations and durable decisions
8. structured normalizers for representative Python and TypeScript/JavaScript tools
9. bounded Reviewer context projection
10. disposable anti-slop + Python validation fixture
11. operator/CLI/desktop inspection of gate results and overrides
12. Cartographer candidate-gate suggestion integration after BTN-85 defines the relevant output contract
13. future external CI/verification capability architecture, if required

Any change to core graph topology, RunState, Actor authorization, or external integration capability must follow the repository's existing architecture/ADR requirements.

## Acceptance criteria mapping

### Compare core gates, plugins, and repository CI/hooks

This RFC selects Battalion-owned deterministic orchestration over repository-owned checkers. RFC-0009 plugins are rejected as the local checker boundary. External CI is deferred to a future integration capability. Repository scripts/checkers remain implementation inputs, not graph authority.

### Language-neutral contract

Sections 8–11 define invocation, result, findings, exit semantics, timeout/cancellation, unavailable behavior, and structured/fallback diagnostics independently of language.

### Execution placement and provenance

Sections 1, 12–17 place gates after Refactorer and before final Reviewer, define bounded retries, Actor interruption/override, and durable candidate/tool/configuration evidence.

### Least authority

Sections 6–7 and Security and authority boundaries prohibit silent mutation, auto-fix, dependency installation, graph/write-scope broadening, and ambient external authority.

### Disposable anti-slop and Python validation

The Anti-slop validation case defines pass, findings, malformed output, missing tool, timeout, execution failure, false positive/override, mutation detection, and language-neutral Python coverage.

### Advisory/blocking and operator correction

Sections 11–15 distinguish severity from disposition, define blocking Refactorer loops, and preserve Actor-bound overrides as separate durable human decisions.

---

## Decision

**Proposed:** Battalion adopts deterministic repository Quality Gates as a first-class verification stage after Refactorer and before final Reviewer.

Repository-specific checkers and configuration remain repository-owned. Battalion project/repository configuration declares which checks participate and how policy applies. Battalion owns deterministic execution, normalization, evidence, retry, interruption, and Actor-authorized override semantics.

Blocking findings return directly to Refactorer within a small per-gate configured retry budget.
