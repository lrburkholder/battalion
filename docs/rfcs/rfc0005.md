# RFC-0005 — Inference Targets and Zero-Cost Policy

**Status:** Accepted  
**Decision Date:** 2026-08-20  
**Ticket:** BTN-51  
**Author:** Architecture  
**Target:** Post-v1  
**Related:** BTN-3, BTN-14, BTN-15, BTN-35, BTN-52 through BTN-55,
ADR-0017, [ADR-0024](../adrs/adr0024.md)

---

## Summary

Battalion should keep LiteLLM as its model-access boundary while making the
identity and policy around each inference request explicit. A LiteLLM model
string is a transport input, not a complete statement of which model served a
role, where inference ran, or whether the call was allowed to incur monetary
cost.

The proposed contract separates the requested model, resolved model, provider,
backend endpoint, inference location, and cost policy. Local servers and remote
routers are optional inference sources behind LiteLLM. They do not receive
Battalion's role selection, model-diversity, graph, cost, retry, or failure
authority.

This RFC proposes three policies: `local-only`, `free-only`, and
`paid-capable`. Both zero-cost policies fail closed before graph execution when
required classification is absent. Runtime monetary evidence remains governed
by BTN-35: unknown is not zero, including after a call was admitted by a
zero-cost policy.

## Status and delivery boundary

The human operator accepted this architecture and ADR-0024 on 2026-08-20.
Acceptance establishes the post-v1 contract but does not change shipped
configuration, execution evidence, interrupts, or setup behavior. Implementation
proceeds only through BTN-52 through BTN-55.

## Goals

- make the effective inference target inspectable before and after a call
- support local and zero-cost remote sources without replacing LiteLLM
- preserve mechanically meaningful Driver/Reviewer diversity through proxies
- prevent retries and failover from crossing an operator-selected cost boundary
- preserve exact, sourced, currency-aware monetary evidence from BTN-35
- keep credentials and changing provider terms outside tracked configuration

## Non-goals

- selecting models automatically for a role
- promising that a free tier will remain free, available, or production-suitable
- treating local inference as free of electricity or hardware cost
- adding another graph, provider SDK boundary, budget interrupt, or policy router
- implementing BTN-52 through BTN-55 in this architecture ticket

## Evidence and existing capability

Battalion already passes `NodeLLMConfig.model` and `extra_params` through a
single LiteLLM wrapper. Setup recognizes several keyless local providers, while
BTN-14 currently compares only configured Driver and Reviewer model strings.
BTN-35 records response model, tokens, nullable monetary amount, currency, and
cost source; absent monetary evidence is explicitly unknown.

The endpoint options fit the existing boundary:

| Source | Relevant capability | Architectural consequence |
| --- | --- | --- |
| [LiteLLM](https://docs.litellm.ai/docs/providers/openai_compatible) | accepts provider-specific and OpenAI-compatible endpoints | endpoint fields belong in node configuration and continue through LiteLLM |
| [Ollama](https://docs.ollama.com/api/openai-compatibility) | exposes OpenAI-compatible local endpoints and concrete model names | useful local source; an Ollama-compatible URL alone does not prove same-host inference |
| [LM Studio](https://lmstudio.ai/docs/developer/openai-compat) | exposes a configurable OpenAI-compatible server | useful local or LAN source; bind address and authentication remain operator responsibilities |
| [vLLM](https://docs.vllm.ai/en/latest/serving/openai_compatible_server/) | serves models through an OpenAI-compatible API | useful self-hosted source without node-specific integration |
| [FreeLLMAPI](https://github.com/tashfeenahmed/freellmapi) | routes an OpenAI-compatible request across changing free tiers and reports the route | optional remote-inference router; its local process, catalog, or name is not cost or diversity proof |

FreeLLMAPI explicitly describes variable latency, no SLA, changing free-tier
capacity, personal experimentation, and continuing upstream terms. Those are
operational constraints, not facts Battalion may normalize away.

## Proposed identity contract

### Configured target

Each role selects a Battalion-owned target identifier whose non-secret
configuration contains:

- `requested_model`: the concrete model or model-family identifier Battalion
  asks LiteLLM to use
- `provider`: the LiteLLM adapter or OpenAI-compatible protocol family
- `backend`: a stable, operator-chosen identifier for the server or router
- `endpoint_url`: the non-secret base URL when one is required
- `inference_location`: `local`, `remote`, or `unknown`
- `cost_classification`: `local`, `verified-free`, `paid`, or `unknown`
- `canonical_model_family`: the identity used for diversity validation
- classification evidence, issuer, observation time, and optional expiry

Bearer tokens, provider keys, and other secrets are references resolved from
the approved environment or secret boundary. They are never persisted in
tracked YAML, run records, fixtures, logs, or URLs.

Endpoint location and inference location are different. `localhost` proves
only that the first network hop is local. A local FreeLLMAPI process, reverse
proxy, or gateway can perform remote inference. Conversely, a LAN endpoint can
serve a model on operator-owned hardware while still being non-local under the
strict same-host meaning of `local-only`.

### Resolved evidence

Each successful call should later record, without fabricating unavailable
fields:

- configured target identifier and requested model
- response or resolved model
- canonical model family when mechanically established
- backend and endpoint classification
- routed provider and routed model when reliably reported
- token and BTN-35 monetary evidence
- any contradiction between configured assumptions and runtime evidence

Display strings are projections of these typed fields. They are not parsed to
reconstruct identity later.

## Classification ownership and evidence

Battalion owns the classification schema and enforcement. The operator owns
the assertion that a configured endpoint and account may be used. A supported
adapter may contribute observations, but an endpoint, provider, or router may
not self-authorize merely by calling itself local or free.

`local` requires a same-host inference path that setup can validate. Loopback
transport is necessary for HTTP but not sufficient when the service is a
remote router. A Unix-domain or equivalent local transport may also qualify.
LAN, public, tunneled, and unverified proxy paths are not `local`.

`verified-free` requires evidence tied to the concrete target and credential or
entitlement being used. Evidence records its source and freshness. Catalog
labels and provider marketing may inform setup, but do not qualify alone. The
operator must attest to applicable upstream terms and Battalion must retain a
bounded source reference, observation time, and review expiry. A supported
adapter may add entitlement or route observations. Stale, missing, conflicting,
or expired evidence becomes `unknown`; it never becomes zero.

## Cost policies

| Policy | Preflight admission | Runtime behavior |
| --- | --- | --- |
| `local-only` | every role target is verified same-host local inference; remote and unknown are rejected | retries remain on the same local boundary; no remote fallback |
| `free-only` | every role target is `local` or has current `verified-free` evidence; paid and unknown are rejected | failover stays within approved free targets; reported non-zero monetary cost is a policy violation |
| `paid-capable` | paid, free, or unknown targets are allowed only when explicitly configured by the operator | no implicit target expansion; all monetary evidence remains recorded as reported |

The default for existing configurations should be `paid-capable` to preserve
backwards compatibility, but only the effective configured targets, including
the existing default when no model is supplied, are authorized.
`paid-capable` does not mean that arbitrary paid fallback is enabled.

Admission evidence and accounting evidence answer different questions. A
verified free entitlement can admit a request under `free-only`, while the
provider can still omit cost from its response. That response cost remains
`unknown` under BTN-35. A provider-reported zero is known zero only when its
currency and source are present. A provider-reported non-zero amount under a
zero-cost policy is durably recorded and pauses through the infrastructure or
policy-failure boundary defined below.

## Diversity through routers

BTN-14 means independent canonical model families, not merely different
strings, aliases, providers, or endpoints. Driver and Reviewer may not satisfy
diversity with two names that can resolve to the same family.

- Concrete requested models qualify only when Battalion can map both to stable,
  distinct canonical families.
- The same family served by two providers or quantizations is not diverse.
- Opaque aliases such as `auto`, profiles, smart routes, and fusion routes do
  not qualify for Driver or Reviewer unless a future contract can constrain
  and prove a distinct family before use.
- A router may fail over between providers only when it preserves the requested
  canonical model family and the active cost policy.

Unprovable diversity is a configuration error before graph execution. If
runtime evidence contradicts an admitted diversity assumption, Battalion
records the evidence, rejects the affected Reviewer verdict or node output,
and pauses as an infrastructure/policy failure at interrupt condition 5. It
does not silently continue with compromised review independence.

## Setup, credentials, and validation

Setup should validate each distinct effective target rather than deduplicating
only by provider. Validation checks URL syntax, location classification,
credential availability without disclosure, endpoint connectivity, requested
model availability, diversity identity, and policy admission. A minimal
completion may be required when model discovery alone cannot prove the target.
Saving configuration occurs only after the operator sees which checks can make
network calls.

Endpoint URLs may be persisted when they contain no user information or secret.
Local services exposed beyond loopback require the operator to configure their
authentication and network controls. Battalion does not start, secure, update,
or grant licenses for Ollama, LM Studio, vLLM, FreeLLMAPI, or upstream providers.

## Retry, failover, degradation, and terms

Battalion retries only within the configured identity and policy envelope.
Failover that changes canonical family, inference location, or cost
classification requires another explicitly configured target and may not occur
silently. Provider/router retry metadata should be retained when reliable.

Unavailable local inference, exhausted free capacity, authentication failure,
malformed route evidence, and endpoint failure use the existing typed
infrastructure-failure path after bounded retries. Offline operation can
continue only when every required target is locally available. There is no
automatic remote degradation for `local-only`, and no paid degradation for
`free-only`.

The operator remains responsible for the terms of every upstream provider,
model license, data handling, geography, quota, and account. Proxying does not
transfer those responsibilities to FreeLLMAPI or Battalion.

## FreeLLMAPI boundary

FreeLLMAPI may be configured as one OpenAI-compatible backend through the same
endpoint path as other sources. Battalion selects a concrete model family per
role, supplies the prompt, and validates the returned model and `X-Routed-Via`
evidence when available. FreeLLMAPI may perform provider-level failover only
inside that family and policy envelope.

Battalion does not consume FreeLLMAPI's graph, roles, smart selection, prompt
transformation, profiles, or fusion as policy. FreeLLMAPI installation on
localhost is remote inference when it calls remote providers. Its changing
catalog is discovery evidence, not durable proof of zero monetary cost,
availability, stability, suitability, or terms compliance.

## Delivery sequence

1. BTN-52 adds endpoint-aware configuration and setup.
2. BTN-53 adds the optional FreeLLMAPI backend path.
3. BTN-54 adds requested/resolved provenance and diversity enforcement.
4. BTN-55 adds durable policy configuration and zero-cost enforcement.

No implementation ticket may weaken the identity, diversity, secret, unknown
cost, or failover rules to simplify its local change.

## Alternatives rejected

### Replace LiteLLM with source-specific clients

This duplicates the existing provider boundary and pushes endpoint policy into
nodes.

### Trust different model strings for diversity

Aliases and routers can resolve different strings to one family, making the
constraint cosmetic.

### Treat missing cost as zero

This conflicts with BTN-35 and turns missing telemetry into authorization.

### Let FreeLLMAPI own role or cost routing

This hides policy in replaceable infrastructure and makes Battalion's durable
record unable to explain why a model was selected.

## Decision

Accepted in ADR-0024:

1. the separated inference identity contract
2. fail-closed `local-only` and `free-only` semantics
3. canonical-family Driver/Reviewer diversity with opaque routes disallowed
4. interrupt condition 5 for runtime identity or zero-cost contradictions
