# RFC-0013 — Typed Role Execution Outcomes and Authority Escalation

**Status:** Proposed  
**Date:** 2026-08-29  
**Ticket:** BTN-133  
**Author:** Architecture  
**Target:** Role execution contract / graph routing  
**Related:** `philosophy.md`, ADR-0002, ADR-0006, ADR-0014, RFC-0012, BTN-129, BTN-133, BTN-154

---

## Summary

Battalion should make a role's execution outcome a first-class, versioned contract rather than infer success, non-action, blockage, or escalation from empty file maps, exceptions, or prose.

The initial shared vocabulary is intentionally small:

- **completed-with-change** — the role validly produced the mutation or artifact its contract requires;
- **completed-with-no-change** — the role validly decided that no mutation/artifact is warranted;
- **blocked** — the role cannot complete because required execution context or mechanically satisfiable capability is unavailable;
- **escalated** — the role cannot choose without authority it does not possess, so a human-controlled decision boundary is required.

These are execution-result kinds, not permissions. Each role or role mode explicitly declares which result kinds it may emit.

Driver RED and GREEN gain a legal typed escape path when proceeding would require inventing missing specification, architecture, interface semantics, repository facts, or write authority. Refactorer's BTN-129 `no-change` behavior becomes the first compatibility case for the shared model.

A role result never selects the next workflow on its own. Battalion validates the result against the role's admitted contract and routes it through deterministic graph/application policy. Escalation remains human-controlled.

---

## Problem

Battalion currently assumes that a successful Driver call returns one or more files. An empty Driver file mapping is rejected because silently advancing with no work would be dangerous. That is correct for accidental or malformed no-op output, but it leaves no legal result for a Driver that correctly discovers:

- the ticket does not specify enough behavior to write a valid RED test;
- GREEN requires an architectural or public-interface choice that Driver is forbidden to invent;
- authoritative repository evidence conflicts;
- required context is missing;
- the admitted write scope cannot contain the necessary implementation.

The result is a protocol contradiction: Battalion's philosophy says Driver should escalate ambiguity rather than invent architecture, while the Driver schema largely requires a file-producing answer.

BTN-129 exposed the same structural issue from the opposite direction. Refactorer can legitimately decide that already-clear passing code should not be changed, so `develop` now carries an explicit `no-change` result with a bounded reason and durable execution evidence. That local solution should be generalized without making every role capable of every outcome.

---

## Goals

- define a small versioned role-result vocabulary owned by Battalion;
- preserve the distinction between successful mutation, successful non-action, blockage, and authority escalation;
- make allowed results role- and mode-specific;
- give Driver RED/GREEN a non-mutating authority-safe result;
- carry bounded machine-readable reason codes and inspectable evidence/context;
- make graph routing deterministic and explicit;
- reuse existing RunStatus, interrupt, execution-record, and human-action mechanisms where appropriate;
- reconcile Refactorer's BTN-129 `no-change` semantics with the shared contract;
- preserve legacy successful role output through explicit normalization/migration;
- make CLI/application/history surfaces able to display outcome meaning without prose reconstruction;
- keep prompts small by moving deterministic enforcement into Battalion.

## Non-goals

- creating a generalized workflow selector;
- letting a role decide which role runs next;
- letting Driver make architectural/product decisions through an "escalation" payload;
- storing or treating raw model chain-of-thought as authoritative evidence;
- replacing provider/protocol errors, scope violations, or infrastructure failures with model-declared outcomes;
- granting all roles every result kind;
- making empty output implicitly equivalent to no-change.

## Result contract

The canonical internal contract is a versioned envelope:

```text
RoleExecutionResult
  schema_version
  kind
  reason_code?
  summary?
  evidence_refs[]
  artifacts?
```

### Result kinds

```text
COMPLETED_WITH_CHANGE
COMPLETED_WITH_NO_CHANGE
BLOCKED
ESCALATED
```

The exact serialized spelling is an implementation detail, but persisted values must be stable and versioned.

### Completed with change

The role produced the artifact/mutation expected by its admitted contract.

For current file-producing roles, legacy output such as:

```json
{
  "files": {
    "widget.py": "..."
  }
}
```

may be normalized at the node boundary to `COMPLETED_WITH_CHANGE` so existing providers and tests do not require an immediate flag-day migration.

### Completed with no change

The role deliberately and validly concludes that its charter requires no mutation/artifact.

This is not a generic "I chose not to do the work" escape hatch. It is legal only for roles whose policy explicitly admits it.

Initial example: Refactorer.

### Blocked

The role cannot complete because a required precondition, context item, or mechanically satisfiable capability is unavailable, but the role is not asking Battalion to accept a design/product decision from the model.

Examples may include:

- required bounded context was not supplied;
- declared write scope cannot contain the required artifact;
- required authoritative repository evidence is unavailable.

A blocked result does not count as successful role completion and does not traverse the role's normal success edge.

### Escalated

The role has enough evidence to identify that proceeding requires authority it does not possess.

Examples:

- specification ambiguity changes externally observable behavior;
- a new architectural/interface decision is required;
- authoritative repository sources conflict and choosing one would redefine intent.

An escalation is a successful *role decision* but not successful completion of the workflow stage. Battalion persists the result and enters an explicit human-controlled resolution path.

## Role-aware capability policy

Result kinds are admitted by deterministic policy, not by the presence of fields in a shared schema.

Conceptually:

```text
RoleResultPolicy
  role
  mode?
  contract_version
  allowed_result_kinds[]
  allowed_reason_codes_by_kind[]
```

Initial policy:

| Role / mode | with-change | no-change | blocked | escalated |
| --- | --- | --- | --- | --- |
| Driver RED | yes | no | yes | yes |
| Driver GREEN | yes | no | yes | yes |
| Refactorer | yes | yes | narrowly, if later needed | no by default |
| Reviewer | existing contract unchanged in BTN-133 | not enabled merely by this RFC | not enabled merely by this RFC | not enabled merely by this RFC |
| Architect | existing contract unchanged in BTN-133 | not enabled merely by this RFC | not enabled merely by this RFC | not enabled merely by this RFC |

The shared vocabulary therefore does not silently enlarge role authority.

## Driver reason codes

Driver non-mutating outcomes use bounded reason codes. The initial set should cover at least:

```text
SPECIFICATION_AMBIGUITY
ARCHITECTURAL_DECISION_REQUIRED
MISSING_CONTEXT
AUTHORITATIVE_EVIDENCE_CONFLICT
INSUFFICIENT_WRITE_SCOPE
```

Recommended initial mapping:

| Reason | Default result kind | Meaning |
| --- | --- | --- |
| `SPECIFICATION_AMBIGUITY` | `ESCALATED` | More than one materially different observable behavior is consistent with supplied intent. |
| `ARCHITECTURAL_DECISION_REQUIRED` | `ESCALATED` | Progress requires a design/interface/ownership decision outside Driver authority. |
| `MISSING_CONTEXT` | `BLOCKED` | Required bounded evidence/context is absent; Driver cannot determine a valid implementation/test. |
| `AUTHORITATIVE_EVIDENCE_CONFLICT` | `ESCALATED` | Repository/spec/ADR sources disagree and selecting one would resolve intent or architecture. |
| `INSUFFICIENT_WRITE_SCOPE` | `BLOCKED` | The necessary valid mutation is outside admitted Driver write scope. |

The mapping is deterministic policy. A model cannot relabel an architectural decision as a benign block to obtain different routing.

Reason codes should be intentionally coarse. Their purpose is routing, analytics, and inspectability, not encoding model thought.

## Evidence and summary

A non-mutating Driver result carries:

- one bounded reason code;
- a concise operator-readable summary;
- bounded evidence references to supplied state/artifacts/workspace evidence when available.

It must not require or persist raw model reasoning.

Conceptually:

```json
{
  "result": {
    "schema_version": "1",
    "kind": "escalated",
    "reason_code": "architectural-decision-required",
    "summary": "The ticket requires choosing whether the new identifier is public API or internal state.",
    "evidence_refs": [
      {
        "kind": "artifact",
        "reference": "spec.md"
      }
    ]
  },
  "files": {}
}
```

The implementation should reuse the bounded evidence-reference patterns already present in execution records rather than create an unbounded free-form evidence dump.

## Distinguishing role outcomes from failures

A declared result is not a substitute for Battalion-detected failure categories.

Examples:

- malformed JSON remains a provider/protocol error;
- a Driver GREEN response that writes tests remains a mechanically detected role-contract violation;
- an attempted write outside bound tools remains a scope/authority enforcement failure;
- provider/network failure remains infrastructure failure;
- an unexpected application exception remains an application defect.

BTN-154 work visible on `develop` is relevant here: mechanically correctable pre-write role-contract violations can be corrected in-run. BTN-133 should not convert those violations into `BLOCKED` or `ESCALATED`, because doing so would let a model choose the interpretation of Battalion's own deterministic enforcement.

The boundary is:

```text
model reports inability/authority boundary
        -> validated RoleExecutionResult

Battalion detects malformed/prohibited behavior
        -> existing deterministic failure/correction path
```

## Graph routing

Normal role success edges remain unchanged for `COMPLETED_WITH_CHANGE` and, where explicitly permitted, `COMPLETED_WITH_NO_CHANGE`.

`BLOCKED` and `ESCALATED` never traverse the normal mutation-success edge.

Conceptually:

```text
Driver RED / GREEN
      |
      v
validate RoleExecutionResult
   /       |        |        \
change   no-change blocked  escalated
  |         X        |         |
  v                  v         v
normal edge       blocked   human-controlled
                 handling    interrupt/resolution
```

`X` is a role-policy rejection for Driver.

### Escalated routing

Driver escalation should reuse the existing durable interrupt/human-action boundary:

1. persist the validated result and execution evidence;
2. keep the stage incomplete;
3. transition to an awaiting-human state;
4. surface reason, summary, and evidence;
5. allow an authorized human action to supply/route the needed resolution;
6. resume through canonical application policy.

The role result itself does not name an arbitrary next node.

For example, an architectural escalation may ultimately lead the human to return to Architect or provide a governing decision, but that routing is Battalion/human authority, not Driver authority.

### Blocked routing

`BLOCKED` should use the existing blocked-state semantics where resolution is primarily contextual/configurational rather than a design choice. Resume must require the missing condition to be addressed; it must not mark the Driver stage complete.

If existing application resume semantics prove too weak to distinguish resolvable block from human escalation, implementation should add a typed resolution operation rather than overload prose.

## Refactorer compatibility

The `develop` branch's BTN-129 implementation currently accepts:

```json
{
  "outcome": "no-change",
  "files": {},
  "reason": "No behavior-preserving simplification is warranted."
}
```

and records a bounded `no_change_reason` in execution evidence before returning to Reviewer.

BTN-133 should preserve that semantic behavior while normalizing it internally to:

```text
kind = COMPLETED_WITH_NO_CHANGE
```

Compatibility options:

1. continue accepting the BTN-129 shape as a v0/provider-specific input and normalize it to the shared result model; or
2. version the Refactorer prompt/output contract and migrate it to the shared envelope.

The preferred initial path is **accept-and-normalize**, because it avoids coupling BTN-133 architecture to a prompt flag day and preserves existing UAT behavior.

The durable execution record should gain a general result field rather than retain Refactorer-only semantics forever. Existing `no_change_reason` data should remain readable.

## Persistence and history

Each completed node execution should be able to expose a normalized role result:

```text
NodeExecution
  ...
  role_result?
    schema_version
    kind
    reason_code?
    summary?
    evidence_refs[]
```

Legacy executions without `role_result` remain valid and are interpreted according to their historical execution-record version.

History/application projections can then distinguish:

- completed with change;
- completed with no change;
- blocked;
- escalated.

No client should need to infer these states from an empty artifact list, exception text, or a prose reason.

The normalized result belongs with durable execution evidence because it describes what the concrete node attempt did. RunStatus remains the aggregate workflow state.

## Prompt contract

Driver prompt changes should be minimal.

The prompt needs only enough judgment guidance to tell RED/GREEN:

- do not invent unspecified externally observable behavior;
- do not make new architecture/interface/ownership decisions;
- when a listed authority/context condition prevents valid completion, return the typed non-mutating result rather than fabricate a file.

Battalion should own:

- schema validation;
- allowed result kinds by role/mode;
- reason-code validation;
- write scope;
- file-type restrictions;
- normal-vs-escalation routing;
- persistence;
- resume authority.

This follows the PromptForge note on BTN-133: deterministic constraints belong in the controller where possible; prompts should retain role-specific judgment.

## Interaction with RFC-0012 workflow admission

RFC-0012 already defines an upgrade-only execution ratchet: compact work must strengthen handling when Driver discovers ambiguity, unresolved architecture, or scope expansion.

BTN-133 supplies the missing **role-level signal** for that policy.

A Driver `ESCALATED` or `BLOCKED` result can therefore become deterministic evidence for the admitted workflow to:

- pause for clarification;
- require architectural handling;
- upgrade a compact recipe to stronger handling;
- or remain blocked until configuration/context is repaired.

The Driver still does not select the recipe or upgrade target.

This is an important reason to keep the result vocabulary generic and machine-readable: future workflow admission logic should consume the result, not parse Driver prose.

## Alternatives considered

### Keep role-specific one-off outputs

Rejected. Refactorer `no-change` solves the immediate UAT case, but repeating custom empty/no-op/escalation conventions per role would make routing, persistence, history, and clients reconstruct semantics differently.

### Treat all non-action as exceptions

Rejected. A role correctly recognizing that it lacks authority is not the same as malformed output or provider failure. Exceptions also make legitimate no-change decisions look unsuccessful.

### Let every role emit every result kind

Rejected. A shared schema must not become a shared authority expansion.

### Use prose-only escalation

Rejected. Battalion owns the loop controller and can enforce typed boundaries mechanically. Prose-only escalation recreates the ambiguity BTN-133 exists to remove.

### Let the role choose the next role

Rejected. That turns an execution result into workflow authority and conflicts with human-controlled graph/admission policy.

### One generic `no-action` result

Rejected. "Nothing changed because no change was warranted", "nothing changed because context is missing", and "nothing changed because architecture authority is required" have materially different workflow semantics.

## Testing requirements

Credential-free tests should cover:

- legacy Driver successful file output normalizes to `COMPLETED_WITH_CHANGE`;
- allowed and disallowed result kinds per role/mode;
- RED escalation for specification ambiguity;
- GREEN escalation for architectural decision required;
- Driver blocked for missing context;
- Driver blocked for insufficient write scope where model-declared blocking is applicable;
- authoritative-evidence conflict escalation;
- reason-code/result-kind mismatch rejection;
- no normal Driver advancement after blocked/escalated result;
- explicit human-controlled escalation routing;
- persistence and resume of the unresolved result;
- Refactorer BTN-129 `no-change` compatibility and normalization;
- legacy execution records without role-result fields;
- CLI/application/history projections for all four result kinds;
- malformed result envelope remains a provider/protocol error;
- Battalion-detected contract violations remain deterministic correction/failure paths rather than model-selected outcomes.

## Open implementation questions

1. Should the normalized contract live in `battalion.state.models`, `battalion.execution`, or a dedicated `battalion.role_results` module? A dedicated module is likely cleaner if role policy and validation grow beyond persistence models.
2. Should `BLOCKED` always imply `RunStatus.BLOCKED`, while `ESCALATED` always implies `RunStatus.AWAITING_HUMAN`? This is the preferred initial mapping unless current resume semantics require a narrower transitional state.
3. Should evidence references be copied into the role result or reference existing node input evidence by stable identifier? Prefer references/deduplication if execution-record identity can support it cleanly.
4. Should Driver be allowed to report `INSUFFICIENT_WRITE_SCOPE` when Battalion can itself detect the scope problem before/at write resolution? Prefer deterministic Battalion detection whenever possible; retain the reason code only for cases where the model can establish that the valid solution necessarily lies outside admitted scope before attempting a prohibited write.
5. Should Reviewer eventually support `COMPLETED_WITH_NO_CHANGE` ("no findings")? Likely yes, but that should be an explicit follow-up decision rather than an accidental consequence of BTN-133.

---

## Proposed decisions

1. Introduce a versioned shared role execution-result vocabulary.
2. Use four semantic kinds: completed-with-change, completed-with-no-change, blocked, and escalated.
3. Make result permissions role/mode-specific through deterministic policy.
4. Permit Driver RED/GREEN changed, blocked, and escalated outcomes; do not permit Driver no-change.
5. Use bounded reason codes plus concise summary/evidence for Driver non-mutating results.
6. Do not persist raw model reasoning as result evidence.
7. Keep Battalion-detected contract/scope/protocol failures separate from model-declared role outcomes.
8. Route blocked/escalated results explicitly; never advance them through normal Driver success edges.
9. Keep escalation human-controlled and reuse durable interrupt/human-action mechanisms.
10. Normalize BTN-129 Refactorer `no-change` into the shared result model while preserving its existing semantics and compatibility.
11. Persist normalized result semantics with node execution evidence and expose them through application/history projections.
12. Preserve legacy successful outputs by normalizing them to completed-with-change.
13. Keep prompt changes minimal and move deterministic enforcement into Battalion.
14. Treat Driver role results as deterministic input to RFC-0012's upgrade-only workflow policy, never as workflow-selection authority.
