# RFC-0024 — Shared Communication Guidance and Self-Hosting Instruction Authority

**Status:** Accepted  
**Date:** 2026-09-06  
**Ticket:** BTN-250  
**Author:** Architecture  
**Target:** Post-v1 prompt and instruction hardening  
**Related:** `AGENTS.md`, `philosophy.md`, RFC-0004, RFC-0019, RFC-0021, RFC-0023, BTN-97

---

## Summary

Battalion will adopt a small Simplified Technical English (STE)-inspired communication standard for Battalion-owned model prompts and repository guidance.

The standard is a writing constraint, not a new authority source. It changes how models express work. It does not change what a role may decide, which artifacts are authoritative, or which operations a model may perform.

Battalion will also dogfood RFC-0021 when Battalion operates on its own repository. The Battalion repository is not exempt from repository-instruction discovery, resolution, precedence, conflict handling, audience filtering, provenance, drift handling, or compliance evaluation.

The implementation must keep three inputs distinct:

```text
Battalion-owned role contract
        +
Battalion-owned shared communication guidance
        +
RFC-0021 resolved repository instructions
        +
bounded task evidence
        |
        v
assembled model context
```

The same RFC-0021 path applies whether the target repository is Battalion or another project.

---

## Motivation

Earlier UAT exposed a usability problem: some model responses were much longer than the human needed for the current decision or task.

Long output also increases token use and can hide the important point inside narration, repeated context, or unnecessary alternatives.

The `jsath/simplified-technical-english` project provides useful prior art. Its core ideas are short sentences, one instruction per sentence, active voice, imperative instructions, plain words, and removal of common AI filler.

Battalion should use these principles without claiming formal ASD-STE100 compliance and without importing the upstream Claude skill as a runtime dependency.

---

## Goals

- make Battalion model output easier to scan and act on;
- reduce unnecessary narration and repeated context;
- preserve facts, caveats, risks, and explicit uncertainty;
- preserve exact code, commands, identifiers, schemas, quoted strings, error text, and required domain terms;
- keep role-specific output contracts authoritative over general style guidance;
- preserve prompt provenance when shared Battalion-owned guidance is composed with a role prompt;
- make Battalion consume its own repository instructions through RFC-0021 when self-hosting;
- keep repository instruction authority separate from built-in role behavior;
- support later evaluation of response length and communication quality without making arbitrary sentence counts a runtime gate.

## Non-goals

- formal ASD-STE100 compliance;
- importing the upstream skill or dictionary as a dependency;
- rewriting code, commands, identifiers, schemas, quotations, or required domain terminology to satisfy style rules;
- deleting material facts or uncertainty for brevity;
- imposing one hard sentence-length limit on every role;
- replacing role-specific schemas, JSON-only contracts, word limits, or other exact output rules;
- making repository instructions part of a hidden Battalion-only self-hosting path;
- treating prose style guidance as a deterministic Quality Gate.

---

## Decision

### 1. Define one Battalion-owned shared communication fragment

Battalion will ship one shared communication fragment for its packaged model roles.

It should express these rules in short form:

- use one clear meaning per word where practical;
- use short sentences;
- put one instruction in each sentence;
- use active voice;
- use imperative commands for instructions;
- use plain technical language;
- give only information needed for the current role, decision, or task;
- do not repeat supplied context unless repetition is needed for clarity;
- do not add preambles, conclusions, status narration, or alternatives unless the role contract needs them;
- preserve material facts, caveats, risks, and explicit uncertainty;
- preserve exact code, commands, identifiers, schemas, quotations, error text, domain terminology, and authoritative repository language;
- do not invent missing information to make output shorter.

The fragment must state that role-specific output contracts win when they are stricter or require a particular format.

### 2. Compose the shared fragment with packaged role prompts

Do not duplicate the complete guidance block in every packaged role prompt when a shared composition point can preserve the same behavior and provenance.

Prompt assembly must make the effective model input inspectable. The exact bytes supplied to the model must remain hashable.

Existing prompt contract versions remain separate from content hashes. A wording-only change can change the effective prompt hash without requiring a contract-version bump. A change to role authority, inputs, or output shape still requires the existing contract-version process.

Explicit operator prompt overrides remain authoritative under the existing override contract. Battalion must not silently prepend a packaged fragment to an override if that would make the effective override differ from the operator-controlled artifact without explicit configuration and provenance.

### 3. Keep response budgeting role-specific

STE-inspired language alone does not solve verbose output.

Each role remains responsible for its output budget. Existing strict contracts such as JSON-only output, one-sentence Reviewer output, or routine Architect word targets remain valid.

Roles without an exact limit should follow this default:

> Use the shortest response that preserves the information required by the role contract and the current human decision.

Do not introduce a global 20-word instruction limit or 25-word description limit in v1. Those values are useful upstream prior art, but Battalion should validate their effect before making them mechanical policy.

### 4. Treat Battalion as an ordinary RFC-0021 project when self-hosting

When Battalion operates on `lrburkholder/battalion`, repository-authored guidance such as `AGENTS.md` must enter through the same RFC-0021 pipeline used for other projects.

Battalion must not special-case its own repository by directly injecting repository guidance through a private self-hosting path.

Self-hosting therefore exercises:

- instruction discovery;
- native scope semantics;
- cross-format precedence;
- conflict detection;
- audience filtering;
- bounded context assembly;
- provenance identity;
- drift handling;
- semantic compliance evidence.

This is intentional dogfooding. A failure found while Battalion consumes its own repository instructions is evidence about the general RFC-0021 implementation.

### 5. Put Battalion repository writing guidance in repository authority

Battalion's contributor/agent writing rules belong in an authoritative repository instruction artifact, initially the root `AGENTS.md` unless RFC-0021 implementation chooses another supported repository-owned form with explicit precedence.

That repository guidance applies to work performed on Battalion itself through RFC-0021. It is not the mechanism that gives every Battalion role its built-in communication style when operating on other projects; the shared packaged communication fragment serves that purpose.

This distinction prevents two authority classes from being collapsed:

```text
built-in communication convention = Battalion product behavior
repository writing rule           = project authority for this repository
```

They may contain equivalent prose. They remain different sources with different provenance.

### 6. Preserve source attribution

Battalion documentation must credit `jsath/simplified-technical-english` as inspiration and state that Battalion uses an STE-inspired subset.

Battalion must not imply that the project implements the official ASD-STE100 specification or dictionary.

### 7. Evaluate effectiveness with observed output

Prompt tests should prove assembly, override behavior, inventory, and provenance. They should not rely only on brittle prose equality checks.

Later model evaluation may measure response size, required-information retention, format compliance, repetition, and task success. These measurements may justify stronger role-specific budgets or deterministic checks.

Do not treat lower token count alone as success. A shorter answer that removes a material risk or decision input is a regression.

---

## Precedence and conflict behavior

The communication fragment is subordinate to exact role contracts.

Examples:

- `Return JSON only` wins over a preference for prose paragraphs.
- An exact schema field name is preserved even if a simpler synonym exists.
- A required security term is preserved even if it is uncommon English.
- A role that must surface assumptions may not omit them merely to be brief.

RFC-0021 repository instructions remain declared project authority. If an applicable repository instruction conflicts with a built-in communication preference, Battalion must preserve the repository instruction and surface the conflict according to RFC-0021 rather than silently rewriting project authority.

A repository instruction cannot broaden a role's mechanical authority merely by asking for it. Existing role, graph, authorization, write-scope, and Quality Gate boundaries still apply.

---

## Implementation outline

1. Add the shared Battalion-owned communication fragment to packaged prompt resources.
2. Extend prompt assembly and provenance so packaged role prompts include the fragment while operator overrides preserve their existing authority semantics.
3. Add STE-inspired repository writing guidance to Battalion's authoritative repository instructions.
4. Add tests for packaged prompt composition, exact effective hashes/provenance, override behavior, and shipped-resource validation.
5. Add or extend RFC-0021 self-hosting fixtures so the Battalion repository follows the same instruction-resolution path as another repository.
6. Add attribution and architecture documentation.

The implementation may split prompt composition and RFC-0021 self-hosting validation into separate tickets if that keeps ownership and validation clearer.

---

## Validation

Acceptance evidence should prove:

- every packaged role receives the shared communication guidance;
- exact role output contracts still control formatting and stricter limits;
- prompt provenance identifies the effective assembled prompt bytes;
- operator overrides are not silently modified by packaged guidance;
- Battalion repository guidance contains the STE-inspired rules and attribution;
- self-hosted Battalion instruction discovery uses RFC-0021 rather than a special path;
- instruction conflicts and drift on Battalion are handled exactly as RFC-0021 specifies;
- no test claims formal ASD-STE100 conformance;
- no runtime dependency on `jsath/simplified-technical-english` is introduced.

---

## Consequences

### Positive

- routine model output should become shorter and easier to scan;
- response discipline becomes consistent across packaged roles without copying a large block into every prompt;
- prompt provenance remains inspectable;
- Battalion dogfoods its repository-instruction architecture;
- UAT can evaluate communication quality as a bounded product behavior.

### Costs and risks

- shared prompt composition adds another input to prompt provenance;
- poorly designed brevity rules can hide useful reasoning or risk information;
- operator overrides need a clear boundary so Battalion does not silently change them;
- RFC-0021 self-hosting validation depends on the general instruction pipeline being implemented.

These risks are preferable to hidden prompt mutation or role-by-role duplicated wording.
