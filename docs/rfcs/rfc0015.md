# RFC-0015 — Typed Workflow Boundary Contracts and Authority-Aware Artifact Flow

**Status:** Proposed  
**Ticket:** BTN-108  
**Author:** Architecture  
**Target:** Post-v2 workflow orchestration  
**Related:** `philosophy.md`, BTN-19, BTN-24, BTN-30, BTN-108, BTN-120, BTN-133, BTN-134, RFC-0013, RFC-0014

---

## Summary

Battalion should replace implicit cross-role sharing through one broadly mutable `RunState` with **versioned Battalion-owned workflow boundary contracts**.

The proposed architecture separates four concepts that are currently too easy to conflate:

1. **Durable canonical artifacts** — authoritative or evidentiary records with stable identity and revision.
2. **Boundary contracts** — typed, versioned declarations of exactly what one workflow stage consumes and produces.
3. **Context projections** — bounded views assembled from canonical artifacts for a particular execution/model call.
4. **Run state** — orchestration/lifecycle state that records progress, references, evidence, and decisions, but is not itself the universal semantic payload exchanged by every role.

A producing role does not hand unrestricted mutable Run state to the next role. Battalion validates the producer's typed output, persists or resolves the canonical artifact/evidence it represents, constructs the receiving contract from authoritative sources, validates compatibility, records the producer/consumer contract versions, and only then admits the receiving execution.

The initial contract family should cover the implementation lifecycle sufficiently to express:

```text
approved specification
        ↓
ArchitectureInput → ArchitecturePlan
        ↓
ImplementationInput → ImplementationResult
        ↓
ReviewInput → SemanticReviewResult
```

without requiring every workflow to use every artifact type.

A downstream artifact may **interpret** a governing artifact but does not replace its authority. In particular:

```text
approved specification > architecture/plan > task/implementation contract
```

is an authority chain, not merely a convenient context chain.

If a required governing artifact cannot be resolved, is incompatible, or contradicts a downstream plan/task, Battalion must represent that as explicit boundary/preflight evidence and route it according to admitted policy. It must not silently downgrade “governing artifact unavailable” into “no governing artifact exists.”

## Problem

Battalion's original state model was intentionally simple: every graph node reads and writes against one versioned `RunState` schema. That was appropriate for the first implementation workflow, but it does not scale cleanly to the workflow architecture now emerging.

The pressure is visible in three directions.

### 1. Role isolation is weaker than the role model implies

Architect, Driver, Reviewer, and Refactorer are conceptually bounded roles, but a shared state object makes the practical boundary “whatever fields are present in RunState.” That encourages accidental coupling and makes it hard to state mechanically what a role is allowed to rely on or produce.

A Driver should not need access to every field accumulated by Architect or prior nodes merely because all of them live in one object. A Reviewer should not inherit Driver-authored summaries as authoritative review context merely because they are convenient state fields.

### 2. New first-class Run types make one universal semantic state untenable

RFC-0014 establishes that Implementation, Review, and Architecture can be distinct first-class Runs with different governing inputs, lifecycle semantics, durable outputs, and authority boundaries.

Continuing to widen one `RunState` with nullable fields for every future workflow would create an implicit sum type without mechanical discrimination. Review-only fields, Architecture-only fields, implementation retry bookkeeping, external-work provenance, and future Specification/Research artifacts would accumulate in the same schema.

### 3. Context is being confused with authority

A model prompt needs a bounded projection of useful information. A workflow boundary needs authoritative identity, version, provenance, and compatibility evidence.

Those are not the same thing.

For example, an implementation model may receive a compact projection of an approved specification and architecture plan. The fact that only a projection is rendered into the prompt must not erase:

- which canonical specification governs;
- which exact revision was approved;
- which plan claims to interpret it;
- whether the plan is compatible with that revision;
- what was omitted from model context;
- how the canonical artifact can be resolved later.

A bounded prompt projection is an execution optimization. It is not a replacement for canonical artifact identity.

## Goals

- define a Battalion-owned, versioned contract mechanism for workflow inputs and outputs;
- mechanically validate boundaries before receiving execution begins;
- make malformed, missing, incompatible, or unsupported contracts explicit typed failures/evidence;
- separate canonical artifacts from model-context projections;
- preserve governing-authority chains from approved specification through architecture/plan to implementation task;
- make governing artifacts deterministically resolvable when a downstream contract references them;
- add bounded pre-execution consistency checks for plans/tasks before implementation begins;
- record what consistency relationships were actually checked rather than accepting free-form “looks consistent” assertions;
- record producer and consumer contract versions in durable execution evidence;
- define compatibility and migration behavior without silent coercion;
- preserve provenance for producing Run/node/Actor or authoritative external source;
- prevent provider/plugin/WorkSource payloads from becoming graph-facing contracts merely because they are structured;
- keep human decisions as separate authority-bearing records;
- evolve current RunState/checkpoint persistence rather than creating a parallel source of truth.

## Non-goals

- replacing `RunState` with stateless execution;
- defining every future workflow artifact in BTN-108;
- making raw model prompts or model responses canonical artifacts;
- making JSON Schema, Pydantic, attrs, or another serialization library part of the architectural contract;
- allowing one role to mutate another role's output artifact in place;
- encoding human approval as a field a model may populate;
- allowing compatibility adapters to reinterpret breaking changes silently;
- requiring full canonical artifact contents to be copied into every checkpoint or model context;
- solving general distributed schema negotiation beyond Battalion's own workflow/runtime boundary.

## Prior art: Carpenter

BTN-108 originated partly from Carpenter's typed inter-Arc contracts. A fresh review of Carpenter confirms the useful mechanism and also highlights where Battalion should be stricter.

Carpenter's reflection workflow now declares `input_contract` and `output_contract` per step. A preparation step emits a typed `GatheredActivity`; the reflection step consumes that contract and emits `ReflectionResult`; later steps consume the typed result rather than reparsing free text. Carpenter also removed a direct SQL update that had mutated a sibling Arc's `goal`, making its typed `arc_outputs` channel the cross-Arc data path.

The architectural lesson worth copying is:

> sibling/workflow executions should exchange explicit typed outputs, not mutate one another's generic state as an implicit communication channel.

Battalion should **not** copy Carpenter's exact Arc model, attrs implementation, YAML syntax, recursive autonomy, or prompt plumbing.

A second lesson is a useful negative example. Carpenter's dispatch-time sibling-output lookup is intentionally tolerant: if configuration, sibling output, a named field, or a prompt template is unavailable, it may return `None` and fall back to the Arc's static goal. That makes sense for Carpenter's compatibility path, but it is the wrong default for a Battalion governing boundary.

For Battalion:

```text
required contract/artifact missing
    ≠ optional context omitted
    ≠ no governing artifact exists
```

A required governing input that cannot be resolved must produce typed boundary/preflight evidence and prevent the receiving execution from proceeding until admitted policy resolves the condition.

## Design principles

### 1. Contracts belong to Battalion, not models or providers

A model may help populate a candidate output, but Battalion owns the contract definition, validation, canonicalization, provenance, and admission decision.

External payload shape is never sufficient authority to become a workflow contract.

```text
GitHub/Jira/MCP/provider payload
        ↓ normalization
Battalion-owned WorkItem / Artifact / Evidence
        ↓ contract assembly
Battalion workflow boundary contract
```

### 2. Canonical artifacts and context projections are different objects

A canonical artifact has durable identity and revision semantics.

A context projection is bounded execution input assembled from one or more canonical artifacts/evidence records.

Conceptually:

```text
ArtifactRef
  artifact_id
  artifact_kind
  revision
  content_digest
  storage/resolution identity
  authority/provenance

ContextProjection
  projection_id
  source_refs[]
  included_sections/elements[]
  omitted/truncated evidence
  rendered_digest
  purpose / receiving role
```

The projection may be persisted as execution evidence without duplicating the canonical source content.

### 3. Authority chains are explicit

A downstream artifact that interprets a governing artifact must retain a durable reference to it.

For the initial implementation lifecycle:

```text
ApprovedSpecification
  authority: human-approved governing requirement
        ↓ interpreted_by
ArchitecturePlan
  authority: approved design/plan constrained by specification
        ↓ decomposed_into
ImplementationTask
  authority: bounded implementation obligation constrained by both
```

The downstream artifact does not supersede the upstream artifact merely by being more specific.

If specification and plan conflict, the conflict is evidence requiring resolution. The plan cannot silently redefine the requirement.

### 4. Boundary validation happens before execution

Receiving execution begins only after Battalion has:

1. resolved required canonical references;
2. validated input contract structure;
3. checked supported contract versions;
4. applied only explicitly admitted compatibility adapters;
5. checked authority/provenance requirements;
6. run any required pre-execution consistency checks;
7. recorded the admitted contract/projection evidence.

### 5. Contract validation is deterministic where possible

Schema shape, required references, version compatibility, identity resolution, digest matching, duplicate identifiers, and declared relation coverage should be checked mechanically.

A model may contribute semantic consistency evidence where deterministic analysis is insufficient, but the result must be structured and scoped to relationships Battalion asked it to inspect.

### 6. No silent coercion

Unsupported-newer or breaking versions do not become older contracts by dropping fields.

Legacy support, if needed, is an explicit adapter/migration path whose use is recorded.

### 7. Human authority remains separate

Human interrupts, approvals, design decisions, finding dispositions, and other authority-bearing actions are durable records of their own.

A workflow output may reference a human decision but may not manufacture one as a generic contract field.

## Proposed contract model

### Contract identity

Every boundary contract type has stable identity independent of Python module/class names.

Conceptually:

```text
ContractDescriptor
  contract_name            # e.g. architecture-plan
  contract_version         # e.g. 1.0
  schema_identity/digest
  compatibility_family
```

The exact serialization is implementation detail. Stable names and versions are durable data and therefore must not depend on import paths that may be refactored.

### Contract envelope

A boundary instance records at minimum:

```text
WorkflowContractEnvelope
  contract_name
  contract_version
  contract_instance_id
  produced_at
  producer
    run_id | authoritative_source
    node_execution_id? 
    actor_id?
  payload_ref | bounded inline payload
  governing_refs[]
  provenance_refs[]
```

The payload may be inline when small and intrinsically contract-shaped, or referenced when it is a larger canonical artifact. The important invariant is that its canonical identity and digest remain inspectable.

### Input contracts are assembled, not merely forwarded

A receiving `ImplementationInput` should not simply be the previous node's `ArchitecturePlan` object.

Battalion assembles the input from authoritative records:

```text
ImplementationInput v1
  task
  governing_specification_ref
  architecture_plan_ref
  applicable_constraint_refs[]
  workspace/repository_ref
  admitted_write_scope
  required_evidence_refs[]
  context_projection_ref
  preflight_consistency_ref
```

This prevents producer convenience from defining receiver authority.

## Initial representative contracts

The names below are conceptual and may change during implementation. Their responsibilities should not.

### `ArchitectureInput v1`

Consumes:

- admitted WorkItem/design question;
- approved specification or explicit evidence that this workflow legitimately has none;
- applicable accepted ADR/policy references;
- repository/project context references;
- bounded context projection.

Produces an `ArchitecturePlan` or a BTN-133 role outcome indicating block/escalation/non-action.

### `ArchitecturePlan v1`

Contains/references:

- plan identity and revision;
- governing specification identity and exact revision;
- architecture/constraint references;
- decisions/assumptions;
- planned deliverables/tasks;
- touched/shared interfaces or files where known;
- dependency relationships;
- unresolved questions/required authority;
- provenance.

A plan that requires a specification must not be valid if its governing specification cannot be resolved.

### `ImplementationInput v1`

Contains/references:

- one bounded task/deliverable;
- governing specification revision;
- governing architecture/plan revision;
- applicable constraints and write scope;
- repository/workspace identity;
- required preflight consistency evidence;
- bounded model-context projection.

This is the primary enforcement point for “Driver implements the admitted task; Driver does not redefine architecture.”

### `ImplementationResult v1`

Contains/references:

- implementation task identity;
- resulting change/artifact identity;
- repository/workspace provenance;
- test/quality evidence;
- produced artifacts;
- deviations or unresolved requirements;
- significance/escalation evidence where applicable;
- producing execution provenance.

It does not self-authorize acceptance.

### `ReviewInput v1`

RFC-0014 already defines the shape conceptually. BTN-108 supplies the general contract mechanics behind it.

It assembles authoritative specification/architecture/change/evidence references rather than accepting a Driver summary as the source of truth.

### `SemanticReviewResult v1`

The semantic review domain artifact from RFC-0014 remains separate from role-attempt lifecycle semantics defined by RFC-0013.

The same layering applies to all contracts:

```text
RoleExecutionResult = what happened in one role attempt
workflow contract/artifact = what domain evidence that attempt produced/consumed
RunStatus = aggregate workflow lifecycle
human decision = authority-bearing disposition
```

## Boundary admission flow

The proposed generic transition is:

```text
producer execution
      ↓
candidate role result / declared outputs
      ↓
Battalion result adapter + contract validation
      ↓
canonical artifact/evidence persistence
      ↓
receiver input assembly from authoritative refs
      ↓
reference resolution + version compatibility
      ↓
required consistency/preflight checks
      ↓
context projection construction
      ↓
durable boundary-admission evidence
      ↓
receiver execution
```

The model is never trusted to say “the handoff is valid.”

## Boundary failures

Boundary failures must be typed enough for policy and UI to distinguish causes without parsing exception strings.

Initial categories should include:

```text
MALFORMED_CONTRACT
MISSING_REQUIRED_INPUT
UNRESOLVABLE_ARTIFACT
DIGEST_OR_REVISION_MISMATCH
UNSUPPORTED_CONTRACT_VERSION
INCOMPATIBLE_CONTRACT_VERSION
PRODUCER_CONSUMER_MISMATCH
AUTHORITY_REQUIREMENT_UNSATISFIED
PREFLIGHT_INCONSISTENCY
LEGACY_ADAPTER_UNAVAILABLE
```

These are boundary/admission evidence, not model-authored role results.

A boundary failure may cause the containing Run to become blocked, fail, or escalate according to admitted workflow policy. BTN-108 should not hard-code one lifecycle response for all workflows.

## Versioning and compatibility

### Version shape

Contract versions should have explicit major/minor semantics even if represented by a simpler internal type initially.

Recommended rules:

- **additive optional fields**: minor-compatible when old consumers can safely ignore them;
- **new required fields**: breaking unless an explicit adapter can supply them without inventing authority;
- **changed field meaning**: breaking;
- **removed fields**: breaking unless the field was explicitly deprecated/ignorable;
- **narrowed enums/constraints**: breaking for producers that may emit formerly valid values;
- **widened consumer acceptance**: potentially minor-compatible;
- **unsupported newer major version**: reject before execution.

### Producer/consumer compatibility

A workflow recipe should identify which input/output contract versions its stages support.

Conceptually:

```text
producer emits ArchitecturePlan 1.1
consumer accepts ArchitecturePlan >=1.0,<2.0
    -> compatible if 1.1 changes are declared additive

producer emits ArchitecturePlan 2.0
consumer accepts <2.0
    -> explicit unsupported-newer boundary failure
```

### Adapters

Adapters are Battalion-owned deterministic transformations between known contract versions.

An adapter must:

- identify source and target versions;
- preserve provenance and original contract identity;
- record that adaptation occurred;
- refuse transformations that would require guessing authority-bearing or semantically new data.

An adapter may rename a mechanically equivalent field. It may not invent a missing human approval, governing specification, or architectural decision.

### Historical interpretation

Durable execution evidence records both:

- the contract version produced;
- the contract version consumed after any explicit adaptation.

Historical Runs therefore remain interpretable after current schemas evolve.

## Governing artifact resolution

A governing reference must be deterministic enough that Battalion can answer:

- what artifact was meant;
- which exact revision governed;
- whether that revision still exists/is readable;
- whether its digest matches the recorded identity;
- who/what supplied its authority where applicable.

A path alone is insufficient durable identity because file contents can change.

An artifact reference should therefore combine stable logical identity with immutable revision/digest evidence.

If a governing artifact is intentionally absent for a workflow, that absence must be represented explicitly by the admitted workflow/input contract. It must not be inferred from lookup failure.

## Pre-execution consistency checks

Before implementation begins, Battalion should perform a bounded consistency pass over the admitted plan/tasks and governing constraints.

The purpose is not to prove the entire plan correct. It is to catch contradictions that are cheaper to resolve before separate implementation attempts begin.

Initial checks should cover at least:

1. **task-to-spec coverage/conflict** — tasks do not explicitly contradict governing requirements;
2. **task-to-plan consistency** — task obligations remain within the approved plan/architecture;
3. **task-to-task contradictions** — two tasks do not declare incompatible expectations for the same requirement/interface;
4. **shared-file/interface mismatches** — tasks touching the same known file/interface/schema do not assume incompatible shapes/orderings;
5. **dependency coherence** — declared prerequisites/outputs line up with consumers;
6. **constraint/write-scope conflicts** — a task is not admitted that requires changes outside its declared authority without escalation.

### Structured evidence, not a model assertion

A valid preflight result records what relationships Battalion actually checked.

Conceptually:

```text
PlanConsistencyEvidence v1
  governing_plan_ref
  governing_spec_ref
  checks[]
    check_kind
    subject_refs[]
    relation_checked
    method: deterministic | model-assisted
    outcome: consistent | inconsistent | indeterminate
    evidence_refs[]
    finding_id?
  uncovered_relationships[]
  overall_admission_recommendation
```

`overall_admission_recommendation` is derived from the structured checks/policy. It is not sufficient by itself.

A model-assisted check may identify a semantic contradiction, but Battalion owns the requested comparison set and records the specific relationships evaluated.

“Plan looks consistent” with no relationship evidence is invalid.

### Boundedness

Preflight must not become an unbounded all-pairs model review for large plans.

Battalion should derive candidate relationships mechanically where possible from:

- explicit dependency edges;
- shared artifact/file/interface declarations;
- common requirement references;
- shared schema/API symbols when deterministic Cartography evidence exists;
- manually or policy-declared coupling.

Model analysis is then used only where semantic adjudication adds value.

---

## Context projections

Typed contracts should not accidentally create giant prompts.

For every receiving execution, Battalion may build a bounded projection such as:

```text
ModelContextProjection
  source_contract_refs[]
  source_artifact_refs[]
  rendered_sections[]
  truncation/omission records[]
  token/byte limits
  projection digest
```

The receiving role can rely on the contract's canonical references even when the model only sees a subset of canonical content.

This lets Battalion improve context-selection strategies later without changing artifact authority or historical meaning.

A projection is execution evidence, not a new governing artifact.

---

## Provenance

Every contract/artifact produced within Battalion should be attributable where applicable to:

- Run;
- node execution;
- Actor;
- model/configuration identity for model-produced evidence;
- authoritative WorkSource or human source when normalized from outside Battalion;
- artifact revision/digest.

Provider identity and provenance may be retained, but provider-native objects do not leak through as graph-facing contracts.

## Relationship to RunState and checkpoint persistence

BTN-108 should **evolve**, not bypass, Battalion's existing persistence model.

The target separation is:

```text
Run envelope/state
  lifecycle/status
  workflow/recipe identity
  interrupt/human-action refs
  execution history refs
  current admitted artifact/contract refs
  workflow-kind-specific orchestration state

Canonical artifact store / repository artifacts
  specifications
  architecture plans
  implementation tasks/results
  review results
  consistency evidence
  other durable domain artifacts

Execution evidence
  consumed contract versions
  produced contract versions
  context projections
  adapters used
  boundary validation outcomes
```

RunState remains the orchestration index/checkpoint needed to resume a Run. It stops being the universal semantic object that every role mutates freely.

A checkpoint should retain references needed to reconstruct the admitted boundary state, not duplicate every artifact body.

This avoids a parallel source of truth: canonical artifact identity lives in one durable artifact mechanism, while RunState points to the exact versions admitted by that Run.

## Relationship to BTN-133

RFC-0013 solves a different boundary: **what result did one bounded role execution produce?**

BTN-108 solves: **what typed domain inputs/outputs are valid between workflow executions, and how does Battalion admit them?**

The two compose as follows:

```text
model/role attempt
  ↓ Battalion MCP/adapter
RoleExecutionResult
  + declared domain output
  ↓ Battalion validation
Workflow contract/artifact
  ↓ boundary assembly/admission
next role's typed input
```

A `BLOCKED` or `ESCALATED` role result may produce diagnostic evidence but does not masquerade as a valid domain output merely to satisfy the next stage's schema.

---

## Relationship to RFC-0014 / future Run types

RFC-0014's generic Run envelope and kind-specific workflow state depend on BTN-108 so first-class Run types can exchange artifacts without expanding one monolithic schema.

The same mechanism should support:

```text
Implementation Run → change/result artifact → Review Run
Architecture Run   → accepted RFC/ADR/plan → Implementation Run
Specification Run  → approved specification → Architecture Run
Research Run       → evidence artifact → Architecture/Specification/etc.
```

Cross-Run boundaries use the same contract machinery as important intra-Run stage boundaries. The distinction is lifecycle ownership, not contract technology.

## Security and authority consequences

Typed contracts improve security only if Battalion treats them as an enforcement boundary rather than fancy serialization.

Therefore:

- a contract cannot grant filesystem/tool authority beyond admitted Actor/workflow policy;
- a model cannot broaden write scope by emitting a larger scope field;
- external provider fields are tainted/untrusted until normalized and authorized;
- human approvals/design decisions remain separately signed/attributed authority records;
- compatibility adapters cannot synthesize missing authority;
- context projections must not cause secrets or unrestricted canonical content to be copied into model prompts merely because the full artifact is resolvable by Battalion.

## Alternatives considered

### A. Keep one shared `RunState` and add stronger field conventions — rejected

This preserves implementation simplicity but relies on discipline rather than mechanical role boundaries, worsens as more Run types arrive, and continues to confuse lifecycle state with semantic handoff data.

### B. One universal `Handoff` payload for every role — rejected

A universal envelope is useful for common metadata, but one universal semantic payload tends either to become an `Any` bag or a giant nullable union. Different boundaries genuinely require different domain contracts.

### C. Pass canonical artifacts directly as model prompts — rejected

This conflates authority/persistence with context-window optimization and makes later projection/token strategies difficult to evolve independently.

### D. Provider-native schemas as contracts — rejected

This violates Battalion's provider-neutral application boundary and would make workflow semantics depend on GitHub/Jira/MCP/model-provider payload evolution.

### E. Typed boundary contracts with canonical refs and bounded projections — proposed

This gives Battalion mechanical composition, explicit authority, versioned evolution, bounded model context, and reusable boundaries across first-class Run types.

## Migration strategy

Implementation should be incremental.

### Phase 1 — contract primitives

- stable contract identity/version types;
- canonical artifact reference/revision primitive;
- typed boundary failure evidence;
- contract registry/compatibility check;
- execution evidence recording produced/consumed versions.

### Phase 2 — implementation lifecycle pilot

Introduce typed contracts around one high-value transition first, preferably Architecture/plan → Driver implementation, because it exercises governing authority and task boundedness.

Keep existing RunState fields temporarily as compatibility projections where required, but make the typed contract the admitted boundary source.

### Phase 3 — remaining implementation transitions

- Architecture input/output;
- Driver result;
- Refactorer input/output where distinct;
- semantic Review inputs/results as RFC-0014 implementation lands.

### Phase 4 — remove obsolete universal-state coupling

Once all consumers have typed inputs, remove or narrow duplicated semantic fields from RunState. Migration must preserve legacy Run loading and historical interpretation.

## Open questions

### 1. Where should canonical workflow artifacts live initially?

Options include repository files with stable metadata/digests, Battalion's persistence store with repository projection where appropriate, or a hybrid based on artifact class.

The architecture requires stable identity/revision and deterministic resolution but does not yet require every artifact to share one physical backend.

### 2. Should contract schemas be code-first or data-first?

Pydantic models fit the current codebase and give mechanical validation quickly. A stable data-schema representation could improve plugins/tooling and cross-language inspection later.

The durable requirement is stable contract identity/version independent of Python import paths. We can begin code-first without making Python class names the persisted protocol.

### 3. Which fields belong inline in a boundary envelope versus canonical referenced artifacts?

Small control metadata is cheap and useful inline; larger governing/domain content should usually be referenced. We need an explicit rule to avoid both pointer-chasing everywhere and accidental artifact duplication.

### 4. Who owns semantic preflight consistency analysis?

The candidate relationship set should be Battalion-derived/deterministic where possible. It remains to decide whether semantic checks are a dedicated capability/node, part of Architecture Run completion, part of workflow admission, or reusable across those paths.

### 5. How strict should minor-version compatibility be?

We should decide whether consumers declare ranges explicitly or whether Battalion uses centrally registered compatibility rules. Either way, silent “Pydantic happened to parse it” compatibility is insufficient durable policy.

---

## Proposed decision

Accept the following architectural invariants:

1. **Workflow boundaries are explicit, typed, versioned, and Battalion-owned.**
2. **Canonical artifacts are separate from bounded model-context projections.**
3. **RunState remains orchestration/checkpoint state, not the universal semantic handoff payload.**
4. **Receiving inputs are assembled by Battalion from authoritative artifacts/evidence, not blindly forwarded from producer state.**
5. **Downstream artifacts preserve explicit references to governing authority; specificity does not silently supersede upstream authority.**
6. **Required unresolved/missing/incompatible governing artifacts fail boundary admission explicitly.**
7. **Pre-execution plan/task consistency is represented by structured evidence of the relationships actually checked.**
8. **Contract version compatibility and adapters are explicit and auditable; breaking data is never silently coerced.**
9. **Provider/plugin payloads are normalized before becoming workflow data.**
10. **Human authority-bearing decisions remain separate durable records.**
11. **The mechanism must support both intra-Run stage boundaries and cross-Run artifact flow without creating a second source of truth.**

If accepted, BTN-108 should be decomposed into implementation tickets rather than implementing the entire mechanism directly in this architecture ticket.
