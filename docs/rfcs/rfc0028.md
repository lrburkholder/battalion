# RFC-0028 — Anchored Artifact Annotations and Revision-Aware Human Review

**Status:** Draft  
**Date:** 2026-09-07  
**Ticket:** BTN-122  
**Author:** Architecture  
**Target:** Post-v2 workflow orchestration  
**Related:** `philosophy.md`, BTN-30, BTN-43, BTN-58, BTN-64, BTN-108, BTN-109, BTN-113, BTN-120, BTN-157, RFC-0015, RFC-0018, RFC-0023, RFC-0026

---

## Summary

Battalion should define a provider-neutral human-review primitive for attaching structured feedback to an exact durable artifact revision and a bounded location within that revision.

The primitive has two separate records:

1. **annotations** record comments, questions, revision requests, and other anchored feedback;
2. **review decisions** record authority-bearing acceptance, rejection, or other admitted dispositions when current policy and Actor authorization permit them.

Neither record mutates the reviewed artifact or prior review history.

Every review targets an exact canonical artifact revision resolved through BTN-157's Battalion-owned artifact repository/resolver boundary. BTN-122 implementations must not introduce a parallel artifact identity or local adapter system.

An annotation remains bound to the exact revision the Actor reviewed. A later revision may relocate the anchor for inspection, but relocation never transfers approval or rewrites history. `EXACT` is reserved for resolution against the original reviewed revision. Any successful match against another revision is `RELOCATED`.

Text anchors default to audit- and privacy-safe retention. They store digests, lengths, and only bounded excerpts when policy permits them. They do not duplicate full selected artifact text by default. The canonical historical artifact remains resolvable through BTN-157.

Stale-anchor relocation is project policy. A project may disable relocation, run it on demand, or run it automatically. The default is on demand when no explicit project policy exists. Relocation remains a derived projection in every mode.

The v1 data model represents partial review. However, authority-bearing `ACCEPT` completes an artifact-review gate only for the whole exact artifact revision unless a later accepted policy extends that rule. Partial acceptance remains durable review evidence and does not imply acceptance of unreviewed content.

RFC-0026 supplies bounded revision-loop semantics. RFC-0015 supplies typed workflow boundaries. RFC-0018 supplies failure and escalation. RFC-0023 supplies operation-time authority evaluation, while existing Actor authorization supplies permission for the concrete review operation.

---

## Problem

Battalion treats human judgment as a first-class authority boundary and increasingly exchanges durable, revisioned artifacts rather than conversational state.

A generic confirmation prompt is too weak for artifact review.

Humans need to express precise feedback such as:

- this paragraph is unclear;
- this requirement changes scope;
- this finding is accepted but deferred;
- this element needs revision;
- this part is satisfactory while another part is unresolved;
- this comment applied to revision 4, not revision 5.

If Battalion stores that feedback only in chat prose, later workflow stages must parse language and guess intent.

If Battalion stores one artifact-level boolean, it loses location, reviewer disagreement, partial review, unresolved findings, and revision history.

If Battalion silently reuses old review against a newer revision, it can claim that a human reviewed content they never saw.

Battalion therefore needs durable, revision-aware review evidence with explicit anchors, Actor identity, authority checks, and workflow integration.

---

## Goals

- Define a versioned review contract independent of PySide6, Markdown, model provider, and artifact type.
- Use BTN-157 canonical `ArtifactRef` identity and resolution as a required implementation prerequisite.
- Bind every annotation and decision to an exact durable artifact revision.
- Support text, structured, diff, and whole-artifact anchors.
- Treat line numbers and presentation coordinates as hints only.
- Preserve original annotations and decisions as immutable historical evidence.
- Detect stale review after artifact revision changes.
- Permit type-aware anchor relocation without transferring authority.
- Make stale-anchor relocation project policy.
- Default text-anchor persistence toward auditability with minimal duplicated content.
- Represent multiple reviewers, conflicts, supersession, and unresolved findings explicitly.
- Represent partial review without treating partial acceptance as whole-artifact approval in v1.
- Keep annotations separate from authority-bearing decisions.
- Keep addressed findings separate from reviewer-confirmed resolution.
- Use RFC-0023 and existing Actor authorization for authority-sensitive review operations.
- Prevent model-authored annotations from satisfying human-authority requirements.
- Feed review outcomes through RFC-0015 typed boundaries.
- Route planned revision through RFC-0026.
- Route failure and exhaustion through RFC-0018.
- Reference BTN-120 findings without mutating independent-review evidence.
- Expose review operations through the shared application boundary.

## Non-goals

- Build a collaborative document editor.
- Define rich-text rendering or editor widgets.
- Require browser loopback or a local HTTP server.
- Create a second artifact registry or resolver.
- Make every annotation authority-bearing.
- Let a model grant itself approval.
- Reopen or rewrite old artifact revisions.
- Merge reviewer disagreement into one synthetic verdict.
- Make fuzzy relocation authoritative.
- Define one anchor algorithm for every artifact type.
- Replace BTN-120 independent review.
- Replace RFC-0015, RFC-0018, RFC-0023, or RFC-0026.
- Persist raw chain-of-thought.

## Core contracts

### Exact review target

A review target uses the canonical BTN-157 artifact identity.

Conceptually:

```text
ReviewedArtifactRef
  artifact_ref
```

The referenced `ArtifactRef` supplies stable logical identity, artifact kind, immutable revision/digest evidence, storage identity, and deterministic resolution.

BTN-122 does not define an alternate file-path, database-row, Markdown-path, or client-owned identity scheme.

If the required artifact revision cannot be resolved through the common resolver, review creation or authority-sensitive review consumption fails closed.

### Review annotation

```text
ReviewAnnotation
  annotation_id
  schema_version
  artifact_ref
  anchor
  actor_id
  created_at
  originating_run_id?
  annotation_kind
  body?
  related_evidence_refs[]
  supersedes_annotation_id?
```

Representative kinds:

```text
COMMENT
QUESTION
REQUEST_REVISION
INFORMATION
UNRESOLVED
```

An annotation is review evidence. It is not automatically an authorization decision.

### Review decision

```text
ReviewDecision
  decision_id
  schema_version
  artifact_ref
  actor_id
  created_at
  originating_run_id?
  disposition
  coverage
  annotation_refs[]
  authority_evidence_ref
  authorization_evidence_ref
  supersedes_decision_id?
```

Representative dispositions:

```text
ACCEPT
REJECT
REQUEST_REVISION
UNRESOLVED
```

A review decision is authority-bearing only when the attempted operation satisfies current RFC-0023 authority requirements and Actor authorization.

Human-authored prose by itself is not an authority-bearing decision.

## Authority and authorization

BTN-122 defines semantic operations. It does not invent local capability names such as `can_approve_artifact`.

Representative authority-sensitive operations are:

```text
accept reviewed artifact revision
reject reviewed artifact revision
dismiss review finding
confirm review finding resolved
```

For each operation:

1. the operation declares the required authority;
2. RFC-0023 evaluates current policy against provenance and evidence;
3. Battalion checks whether the Actor may perform the concrete operation;
4. the decision binds to the exact artifact revision and coverage;
5. Battalion persists the decision before workflow progression.

Unknown or insufficient authority fails closed.

A model may suggest an anchor, summarize feedback, or propose a disposition. It cannot satisfy a required human decision by emitting structured output.

---

## Append-only history

Annotations and decisions are historical evidence.

Battalion does not edit them in place when:

- a new artifact revision appears;
- a concern is addressed;
- a reviewer changes their view;
- another Actor disagrees;
- a workflow proceeds.

Later records link to earlier records.

Conceptually:

```text
annotation A1: REQUEST_REVISION on R1
artifact R2 created
address record E1: producer says R2 addresses A1
annotation A2: reviewer response on R2
confirmation C1: reviewer confirms A1 resolved
```

This preserves who said what and when.

## Anchor model

Battalion uses a tagged anchor family.

Every anchor has:

```text
Anchor
  anchor_kind
  artifact_revision
  identity_payload
  integrity_evidence
  presentation_hint?
```

`presentation_hint` may include line, row, column, path, hunk number, or UI coordinates. It is never sufficient identity by itself.

### Text anchors

A text anchor identifies selected content and bounded context without copying the entire selected artifact content by default.

Conceptually:

```text
TextAnchor
  selected_text_digest
  selected_text_length
  bounded_excerpt?
  prefix_context_digest?
  suffix_context_digest?
  occurrence_hint?
  line_range_hint?
```

The default retention rule is:

```text
canonical historical content -> BTN-157 artifact resolver
anchor integrity              -> digest + length + bounded context
human convenience             -> bounded excerpt when project privacy policy permits
full selected text duplicate  -> not retained by default
```

A project may further restrict bounded excerpts for sensitive artifacts.

The resolver must still be able to reproduce the exact historical artifact revision needed for audit and inspection according to normal retention policy.

### Structured anchors

Structured artifacts should prefer stable element identity supplied by the artifact contract.

Examples:

```text
JSON Pointer / typed field path
stable element_id
schema-defined node identity
```

Conceptually:

```text
StructuredAnchor
  element_identity
  value_digest?
  schema_version?
```

If the element still exists but its value changes, Battalion reports that distinction instead of treating the reviewed content as unchanged.

### Diff anchors

Diff review binds to exact compared revisions.

```text
DiffAnchor
  base_artifact_ref
  head_artifact_ref
  path
  side
  selected_change_digest
  source_range_hint?
  target_range_hint?
```

If either endpoint changes, the old review remains review of the old diff.

### Whole-artifact anchors

```text
ArtifactAnchor
  scope: WHOLE_ARTIFACT
```

Whole-artifact decisions still bind to one exact artifact revision.

## Anchor resolution

Resolution statuses are:

```text
EXACT
RELOCATED
AMBIGUOUS
MISSING
```

`EXACT` is reserved for the original reviewed revision.

A successful match against any different revision is `RELOCATED`, even if the selected bytes are unchanged.

This rule keeps revision boundaries visible and prevents a relocated anchor from appearing to prove that the newer artifact was directly reviewed.

For a newer revision:

- one unique supported match -> `RELOCATED`;
- several plausible matches -> `AMBIGUOUS`;
- no supported match -> `MISSING`.

Battalion must not select the nearest line or element silently.

### Project relocation policy

Relocation is governed by project policy.

The policy may choose behavior equivalent to:

```text
disabled
automatic
on-demand
```

The exact serialized vocabulary belongs to the project-policy implementation.

If no explicit policy exists, Battalion uses on-demand relocation.

Automatic relocation may update derived projections or caches. It must not:

- edit the original annotation;
- change the original reviewed revision;
- transfer an authority-bearing decision;
- mark a concern reviewer-confirmed resolved.

Relocation remains deterministic or bounded derived evidence, not authority.

## Review coverage and v1 partial approval

The durable contract represents review coverage.

Representative forms:

```text
WHOLE_ARTIFACT
ANCHORS [A1, A2, ...]
ELEMENT_SET [E1, E2, ...]
```

Battalion preserves:

- accepted coverage;
- rejected coverage;
- revision-requested coverage;
- unresolved coverage;
- unreviewed coverage.

For v1:

```text
partial ACCEPT
    -> durable review evidence
    -> does not satisfy whole-artifact acceptance

WHOLE_ARTIFACT ACCEPT on exact revision
    -> may satisfy an authority-bearing acceptance operation
       when current policy and Actor authorization permit it
```

This keeps the contract extensible without making downstream partial-approval semantics ambiguous.

A future accepted workflow policy may define authority-bearing partial acceptance for a specific artifact type or operation.

---

## Multiple reviewers and conflicts

Review records remain per Actor.

Battalion must preserve cases such as:

```text
Reviewer A: ACCEPT
Reviewer B: REQUEST_REVISION
```

Workflow policy decides whether progression requires all reviewers, a designated authority, revision after any rejection, or HumanInterrupt for conflict.

The annotation store does not synthesize one boolean verdict.

---

## Addressing, confirmation, dismissal, and supersession

BTN-113 requires findings to remain explicitly addressable across rounds. BTN-122 therefore distinguishes producer/workflow evidence from reviewer agreement.

Representative states or records are:

```text
OPEN
ADDRESSED
CONFIRMED_RESOLVED
DISMISSED
SUPERSEDED
BLOCKED_OR_UNVERIFIABLE
OUT_OF_SCOPE_OR_ESCALATED
```

The exact durable vocabulary may be refined during implementation, but these meanings remain distinct.

### Addressed

`ADDRESSED` means an Actor or execution claims that a later artifact/revision addresses the concern and provides evidence.

It does not speak for the original reviewer.

### Confirmed resolved

`CONFIRMED_RESOLVED` means the reviewer, or another Actor explicitly authorized by admitted policy, confirms that the concern is resolved.

Another Actor cannot silently convert `ADDRESSED` into reviewer agreement.

### Dismissed

`DISMISSED` means an authorized disposition says the workflow is not required to satisfy the finding as stated.

Dismissal does not rewrite or delete the original finding or annotation.

### Superseded

A later annotation may supersede an earlier statement by the same reviewer or another admitted relationship. Supersession preserves the earlier record.

## Relationship to BTN-120 independent review

BTN-120 owns independent-review evidence custody.

Anchored human review may reference a BTN-120 finding:

```text
IndependentReviewFinding F1
        |
        +--> ReviewAnnotation A1
        |
        +--> ReviewDecision D1
```

The original finding remains immutable under BTN-120's trust boundary.

Human disposition is separate evidence.

The producing role does not gain mutation authority over independent-review findings through BTN-122.

## Workflow integration

### RFC-0015 typed boundaries

A receiving stage consumes typed references such as:

```text
ArtifactReviewInput
  artifact_ref
  annotation_refs[]
  decision_refs[]
  unresolved_finding_refs[]
  addressed_finding_refs[]
```

The receiving stage does not scrape review chat prose.

### RFC-0026 bounded iteration

The representative loop is:

```text
candidate R1
   |
   v
human review
   |-- ACCEPT exact R1 -----------------> success
   |
   +-- REQUEST_REVISION
             |
             v
          candidate R2
             |
             v
        human reviews exact R2
```

Each full admitted pass consumes RFC-0026 round state.

Prior annotations remain bound to prior revisions. The next round records how unresolved findings were addressed, dismissed, superseded, blocked, escalated, or left open.

A material governing-scope change follows RFC-0026 successor semantics instead of becoming hidden revision inside the same immutable-scope iteration.

### RFC-0018 failure and escalation

Examples that may trigger admitted failure/escalation policy include:

- required artifact revision cannot be resolved;
- authority evaluation fails;
- Actor authorization fails;
- anchor data is malformed;
- required review evidence is unavailable;
- iterative review exhausts its bound;
- required reviewer authorities conflict without an admitted progression rule.

A presentation client does not invent recovery behavior.

## Application boundary

Presentation code must not mutate review persistence directly.

The application boundary should expose operations equivalent to:

```text
create_annotation(...)
read_review(...)
create_decision(...)
record_addressed(...)
confirm_resolution(...)
dismiss_finding(...)
supersede_annotation(...)
resolve_anchor_against_revision(...)
list_review_history(...)
```

Names are implementation details.

The boundary enforces:

- BTN-157 artifact and revision resolution;
- schema validation;
- Actor identity;
- RFC-0023 authority evaluation where required;
- Actor authorization;
- append-only history;
- stale-revision checks;
- immutable decision coverage;
- reference integrity;
- BTN-120 evidence custody;
- Run/workflow linkage;
- project relocation policy.

Desktop, CLI, and future clients consume shared projections from this boundary.

## Desktop interaction boundary

The first desktop surface should support:

1. open an exact canonical artifact revision;
2. select text, a structural element, or the whole artifact;
3. create a comment, question, or revision request;
4. create an authority-bearing decision when permitted;
5. show current, stale, relocated, ambiguous, missing, addressed, and resolved state clearly;
6. show prior annotations and decisions without rewriting them;
7. open a newer revision and request or display relocation according to project policy;
8. distinguish “producer says addressed” from “reviewer confirmed resolved.”

The architecture does not require an embedded browser, localhost callback server, or ECC Plan Canvas implementation.

PySide6 may be one presentation surface. It does not define the durable contract.

## Persistence

Review evidence follows Battalion durable artifact/evidence conventions.

BTN-122 implementation requires BTN-157 canonical artifact persistence/resolution before anchored review is admitted.

At minimum Battalion persists:

- annotation/decision identity;
- exact canonical artifact revision reference;
- anchor payload and integrity evidence;
- Actor identity;
- timestamp;
- originating Run/workflow where applicable;
- related evidence references;
- supersession/address/resolution/dismissal links;
- authority and authorization evidence for authority-bearing decisions.

The review record should not duplicate full artifact content when canonical resolution can provide it.

Deleting or superseding an artifact from the current workflow view does not delete historical review evidence while normal project retention policy still requires it.

## Revision invariants

### Exact revision

Battalion can reproduce the exact durable revision reviewed by the Actor.

### Artifact changed

A decision on `A:R1` is not approval of `A:R2`.

### Moved anchor

If content moves unchanged and resolves uniquely on another revision, Battalion may report `RELOCATED`.

It never reports `EXACT` for that later revision.

### Changed anchor

Materially changed content requires new human review for authority-bearing progression.

### Deleted anchor

Relocation reports `MISSING`.

### Ambiguous anchor

Relocation reports `AMBIGUOUS` and does not choose silently.

### Addressed finding

A producer may record evidence that a new revision addressed a finding. That does not create reviewer confirmation.

### Authority-bearing acceptance

In v1, terminal acceptance requires `WHOLE_ARTIFACT` coverage of the exact current candidate plus required RFC-0023 authority and Actor authorization evidence.

## Security and privacy considerations

Anchored review can authorize downstream execution. The implementation must prevent:

- forged Actor identity;
- applying a decision to a different revision;
- changing decision coverage after authorization;
- converting model output into human approval;
- editing old review records;
- changing anchors after decision creation;
- using relocation to transfer approval;
- treating addressed as reviewer-confirmed resolved;
- bypassing BTN-157 canonical artifact resolution;
- bypassing BTN-120 independent-review custody.

Text-anchor retention should minimize duplicated sensitive content. Full selected text is not retained in the annotation record by default. Project privacy policy may reduce excerpts further.

Authority-bearing decisions include enough immutable candidate identity for Battalion to detect post-decision mutation.

## Rejected alternatives

### Store review only as chat messages

Rejected because workflow stages would need to parse prose and historical artifact identity would be weak.

### Create annotation-specific artifact adapters

Rejected for the first production implementation. BTN-157 already owns the common canonical artifact repository/resolver. BTN-122 consumers must sequence behind it.

### Use line numbers as durable anchors

Rejected because lines move and structured artifacts may not have meaningful lines.

### Persist complete selected text by default

Rejected because it duplicates canonical content and can increase privacy exposure. The default uses integrity digests plus bounded excerpts when policy permits them.

### Mutate annotations after revision

Rejected because it destroys historical evidence.

### One artifact-level approve/reject boolean

Rejected because it cannot represent partial review, anchors, conflicts, reviewers, or unresolved items.

### Let partial acceptance complete the v1 artifact gate

Rejected for v1. The data remains useful, but whole-artifact acceptance has clearer downstream authority semantics.

### Treat addressed as resolved

Rejected because the producer cannot silently speak for the reviewer.

### Automatically relocate in every project

Rejected because projects differ in artifact scale, privacy, performance, and review needs. Relocation is project policy.

### Automatically carry approval forward after relocation

Rejected because relocation does not prove review of the new revision.

### Copy ECC's browser-loopback Plan Canvas

Rejected. Battalion reuses the interaction principle, not that implementation architecture.

## Resolved decisions

1. **Artifact identity and resolution**  
   Require BTN-157's common Battalion artifact repository/resolver. Change downstream implementation dependency graphs so BTN-122 consumers do not ship an interim artifact-adapter path.

2. **Text retention**  
   Prefer audit and privacy safety. Persist digests, lengths, and bounded excerpts only when project policy permits them. Do not duplicate full selected text by default.

3. **`EXACT` versus `RELOCATED`**  
   Reserve `EXACT` for the original reviewed revision. Any successful resolution on another revision is `RELOCATED`.

4. **Partial approval in v1**  
   Represent partial acceptance as durable evidence. Permit authority-bearing terminal `ACCEPT` for the whole exact artifact only in v1 unless a later accepted policy extends the semantics.

5. **Resolution ownership**  
   Distinguish `ADDRESSED` from reviewer-confirmed resolution. Another Actor may record address evidence. Reviewer agreement requires the reviewer or another Actor explicitly authorized by policy.

6. **Stale-anchor relocation**  
   Make relocation behavior project policy. Support disabled, on-demand, or automatic behavior. Default to on-demand when no explicit project policy exists.

7. **Review decision authority**  
   Define semantic operations in BTN-122. Reuse RFC-0023 operation-time authority evaluation and existing Actor authorization rather than defining BTN-122-specific capability names.

---

## Decision criteria

Before acceptance, this RFC requires agreement that:

- annotations and authority-bearing decisions are separate;
- BTN-157 is the required artifact identity/resolution substrate;
- every decision binds to one exact canonical artifact revision;
- approval never silently transfers to a newer revision;
- `EXACT` applies only to the original revision;
- anchors are type-aware and line numbers are hints;
- text-anchor duplication is privacy-minimized by default;
- relocation is non-authoritative and project-configurable;
- history is append-only;
- v1 whole-artifact acceptance is distinct from partial review evidence;
- addressed and reviewer-confirmed resolved are distinct;
- BTN-120 findings remain under independent-review custody;
- workflow routing reuses RFC-0015, RFC-0018, RFC-0023, and RFC-0026;
- desktop and future clients remain consumers of the application boundary.
