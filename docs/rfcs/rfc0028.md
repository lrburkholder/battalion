# RFC-0028 — Governed Environment and Integration Validation

**Status:** Accepted  
**Decision Date:** 2026-09-07  
**Ticket:** BTN-198  
**Author:** Architecture  
**Target:** Environment/integration validation architecture  
**Related:** `philosophy.md`, RFC-0013, RFC-0015, RFC-0018, RFC-0019, RFC-0020, RFC-0021, RFC-0023, RFC-0025, RFC-0026, RFC-0027, ADR-0039, BTN-131, BTN-138, BTN-139, BTN-140, BTN-141, BTN-142, BTN-143, BTN-192

---

## Summary

Battalion should treat real execution environments as governed resources.

Environment validation should be a provider-neutral deterministic capability/subgraph. Workflow recipes can require it, specialize it, or omit it. Models may propose validation scenarios and interpret evidence. Models should not receive ambient cloud, staging, or production authority merely because validation is required.

The preferred flow is:

```text
accepted requirement / architecture
        ↓
validation obligation
        ↓
admitted workflow recipe
        ↓
environment admission
  - exact environment identity
  - bounded capabilities
  - credential references
  - scope constraints
  - cost authorization
  - approval policy
        ↓
deterministic provision / deploy / execute / observe / cleanup
        ↓
versioned validation evidence
        ↓
typed behavioral result
        +
policy / infrastructure / cleanup evidence
        ↓
workflow routing
```

This RFC does not introduce an Integration Tester model role.

It also does not define a new Run kind in v1. RFC-0026 reinforces the existing recipe-first approach: reusable workflow behavior should be expressed as admitted stages/subgraphs first. A later Run-kind specialization can be added if scheduling, placement, history, or UI needs justify it.

Automated environment validation remains distinct from Human QA/UAT. Machine evidence can inform human acceptance. It does not become human acceptance unless the admitted workflow explicitly has no human acceptance boundary.

---

## Problem

A request to "run the integration tests" can require more than local test execution.

It can require Battalion to:

- start disposable containers or databases;
- deploy a candidate to shared staging;
- authenticate to infrastructure providers;
- create billable resources;
- mutate shared or externally visible state;
- invoke third-party systems;
- consume quota or rate limits;
- retain diagnostic state;
- clean up resources and restore shared state.

These are governed side effects. They have authorization, cost, security, lifecycle, and evidence consequences.

Without a first-class contract, Battalion risks two bad outcomes:

1. Give a model broad credentials and let the test request imply broad external authority.
2. Avoid environment automation and leave integration validation as ad hoc manual work.

Neither fits Battalion's philosophy. Mechanical work should be automated. Human and project authority should remain explicit.

---

## Goals

- Define a versioned provider-neutral environment identity model.
- Define bounded environment capabilities.
- Keep secret material out of durable Battalion artifacts and model context by default.
- Reuse Battalion side-effect, authorization, provenance, and recovery mechanisms.
- Separate cost authorization from cost observation.
- Trace validation evidence to accepted requirements and exact candidate revisions.
- Distinguish behavioral failure from infrastructure, authorization, cost-policy, and cleanup problems.
- Make cleanup or an admitted retention disposition part of environment lifecycle completion.
- Support low-risk local integration with little or no human interruption.
- Require stronger authority for production, destructive, costly, or otherwise material actions.
- Compose validation through workflow recipes.
- Keep automated validation separate from Human QA/UAT.
- Avoid a model role when deterministic execution is sufficient.

## Non-goals

- Define provider-specific AWS, Azure, GCP, or Kubernetes APIs in the core contract.
- Require environment validation for every workflow.
- Replace Driver RED/GREEN testing.
- Replace Human QA/UAT.
- Give models direct provider credentials by default.
- Store secrets in Run state or evidence artifacts.
- Build a general cloud-management product.
- Guarantee real-time provider billing information.
- Treat every environment problem as a product defect.
- Treat every significant environment action as a test failure.

## Architectural alignment with newer RFCs

### RFC-0020: specification owns observable requirements

RFC-0020 makes Specification a first-class workflow with an exact accepted specification revision.

For environment validation, this means the specification should own **what must be observed** when that observation is part of product acceptance.

Example:

```text
requirement: persisted records remain readable after restart
observable obligation: create record -> restart service -> read record successfully
```

The specification should not normally choose a cloud account, namespace, credential, or deployment mechanism.

### RFC-0019: Architect owns architectural realization

Architect should resolve **how the observable obligation fits the accepted architecture**.

Architect may determine:

- which environment class is required;
- which existing deployment or persistence boundary should be exercised;
- which capability classes are required;
- which architectural evidence must be observed;
- whether the current architecture can satisfy the obligation without a new boundary.

This keeps product observation and architectural realization separate.

### RFC-0015: validation artifacts use typed workflow boundaries

RFC-0015 already separates durable canonical artifacts from the boundary contracts that carry references to them.

`ValidationObligation` and `EnvironmentValidationEvidence` fit that model directly. They should be canonical Battalion-owned artifact types in the RFC-0015 artifact family. Workflow boundary contracts should reference exact revisions of those artifacts rather than embedding a second validation-specific transport contract.

This does not require the Python implementation to place every type in one physical module. A dedicated validation module is acceptable as code organization. The architectural contract still belongs to the RFC-0015 artifact/boundary mechanism.

### RFC-0023: provenance, authority, and authorization stay separate

Environment validation must preserve the distinction:

```text
provenance     = where did this descriptor, policy, or evidence come from?
authority      = what may it govern under current policy?
authorization  = may this Actor perform this concrete operation?
```

A repository file can define an authoritative environment policy without containing credentials.

A credential reference can authorize an operation without becoming an authority source for architecture or product behavior.

### RFC-0025: significance is not failure

A validation execution can succeed behaviorally while still producing architectural significance evidence.

Examples:

- validation proves a public protocol change works, but the change remains architecturally significant;
- validation reveals that a migration changes a cross-component invariant;
- production-like validation requires a new security-sensitive boundary.

Do not encode significance as `behavioral_validation_failure`.

If a deterministic or admitted project rule produces a `SignificanceSignal`, route it through RFC-0025 `EscalationPolicy` separately from the validation result.

### RFC-0026: use admitted recipe stages/subgraphs first

Environment validation is a reusable workflow capability.

In v1, model it as one or more admitted recipe stages/subgraphs. Do not add a distinct `EnvironmentValidationRun` type only to make the workflow visible.

A later Run kind is justified only if Battalion needs a separate execution container for reasons such as:

- remote worker placement;
- independent scheduling;
- long-lived environment lifecycle;
- separate human ownership;
- independent history or UI semantics.

The contract must not depend on that future choice.

### RFC-0027: scoped institutional knowledge remains advisory unless admitted

RFC-0027 defines scoped institutional knowledge and keeps durable repository/project knowledge separate from authority-bearing workflow artifacts.

Environment validation may use applicable scoped knowledge to improve planning, scenario design, or diagnosis. That knowledge does not widen environment capability, credential scope, cost authorization, or workflow authority.

Environment policy and bindings remain explicit governed inputs even when institutional knowledge describes them.

## Environment validation as a Capability

Treat environment validation as a Battalion Capability, not as a provider-specific subsystem or model role.

The capability accepts Battalion-owned semantic arguments and returns Battalion-owned canonical evidence. Provider or local execution details remain behind the capability boundary.

Conceptually:

```text
EnvironmentValidationCapability
  admit(environment, candidate, scenario, authorization)
  execute(admitted_validation)
  observe(execution)
  reconcile(execution)
  finalize_lifecycle(execution)
```

The exact API shape is an implementation decision. The architectural requirements are:

- callers request semantic operations rather than provider commands;
- the Capability cannot broaden the admitted environment or authorization envelope;
- deterministic adapters perform external actions;
- all external mutations integrate with Battalion side-effect evidence;
- returned results become RFC-0015 canonical artifacts;
- model participation is optional and cannot own the execution boundary.

The first implementation should stop at a **provider-neutral fake/contract implementation** plus the disposable local adapter. Do not build a real cloud-provider adapter in the first implementation wave.

The fake should exercise the full contract surface, including:

- provider binding resolution;
- credential-reference handling without real secrets;
- capability admission;
- cost authorization and observation states;
- provision/deploy/mutate/observe/cleanup side-effect identities;
- failure and reconciliation paths;
- retention/lifecycle obligations.

A real provider adapter should be a later Capability implementation once the provider-neutral contract has been exercised through UAT.

## Environment descriptor ownership

Use a hybrid authority model.

The repository owns symbolic, reviewable environment policy and identity. Machine-local or integration-provider configuration resolves deployment bindings and secret-bearing credential references.

Conceptually:

```text
repository authority
  EnvironmentDescriptorPolicy
    environment_id
    environment_class
    allowed capabilities
    allowed scope classes
    lifecycle / cleanup policy
    cost policy
    approval policy
    binding_id

machine/provider configuration
  EnvironmentBinding
    binding_id
    provider
    account/project/subscription
    region/cluster
    endpoint/network binding
    credential_ref
    provider-specific parameters
```

The repository must not contain secrets merely because it contains the authoritative environment policy.

A binding cannot broaden repository policy. It may narrow the available capability or scope.

If repository policy and machine binding conflict, admission fails or escalates. Do not silently choose one.

## Environment identity model

The versioned environment contract should include at least:

```text
EnvironmentDescriptor
  schema_version
  environment_id
  environment_revision
  environment_class
    local_ephemeral
    shared_staging
    production_like
    production
  binding_id
  scope_policy
  lifecycle_policy
  capabilities[]
  credential_ref_requirements[]
  quota_policy?
  cost_policy?
  approval_policy
  lease_policy?
```

`environment_id` is stable project identity.

`environment_revision` pins the exact admitted policy revision.

Runtime evidence also records the resolved binding revision and exact environment instance when relevant.

## Capability model

Environment access uses bounded capabilities rather than one broad permission.

Initial capabilities:

```text
read_observe
deploy
create_resource
mutate_data
delete_resource
cleanup_teardown
```

Each capability may have scope constraints.

Example:

```text
create_resource
  resource_classes: [container_service, managed_database]
  namespace_prefix: battalion-${run_id}-
  max_instances: 3
```

Capabilities do not imply each other.

`deploy` does not imply arbitrary data mutation.

`create_resource` does not imply deletion outside execution-owned resources.

`cleanup_teardown` is normally limited to resources owned by the admitted operation.

Free-form model text cannot widen the capability envelope.

---

## Credential and secret delegation

Durable artifacts store credential references, not secret values.

Example:

```text
credential_ref: battalion://credentials/project-staging-deployer
```

Credential resolution happens inside an admitted deterministic operation.

Prefer short-lived, scoped, federated, or workload credentials when providers support them.

Evidence may record:

- credential reference identity;
- resolver/provider identity;
- non-secret principal identity;
- admitted scope;
- issue/expiry timestamps when available.

Evidence must not record tokens, passwords, private keys, session cookies, or equivalent secret material.

---

## Validation obligation ownership

Split responsibility between Specification and Architect.

### Specification owns

- the behavior that must be true;
- machine-observable acceptance conditions when required;
- required evidence categories when they are product requirements;
- any human acceptance requirement.

### Architect owns

- environment class realization;
- architecture-bound capability requirements;
- integration boundaries to exercise;
- required architectural evidence;
- reuse of existing environment/deployment mechanisms;
- any new architectural decision required by the obligation.

### Battalion owns

- admitted scenario identity;
- exact candidate identity;
- environment admission;
- capability and credential resolution;
- cost authorization;
- side-effect execution;
- evidence construction;
- policy routing.

## Validation obligation contract

`ValidationObligation` is a durable RFC-0015 canonical artifact.

Conceptually:

```text
ValidationObligation
  obligation_id
  source_requirement_refs[]
  observable_contract
  candidate_scope
  scenario_ref
  required_environment_class
  required_capabilities[]
  required_observations[]
  human_acceptance_required
  cleanup_or_retention_disposition
```

The scenario reference points to a deterministic and reviewable executable scenario revision.

A model may help author or revise the scenario. The admitted scenario revision, not free-form prose, becomes the executable boundary.

Workflow input contracts reference the exact admitted `ValidationObligation` revision.

## Validation evidence contract

`EnvironmentValidationEvidence` is a durable RFC-0015 canonical evidence artifact.

Every execution should produce versioned evidence:

```text
EnvironmentValidationEvidence
  schema_version
  evidence_id
  workflow_execution_id
  obligation_ids[]
  candidate_identity
  artifact_identities[]
  scenario_identity
  environment_identity
  environment_revision
  binding_revision
  resolved_instance_identity?
  admitted_capabilities[]
  credential_ref_identities[]
  authorization_decision_refs[]
  cost_authorization
  action_refs[]
  bounded_observations[]
  assertion_outcome
  policy_findings[]
  significance_signal_refs[]
  lifecycle_disposition
  cost_observation?
  failure_classification?
  overall_outcome
```

Raw logs, traces, screenshots, provider diagnostics, and snapshots should normally be referenced as bounded evidence rather than copied into the canonical envelope.

Workflow output contracts carry references to the exact evidence artifact rather than duplicating its semantic payload.

## Behavioral result versus policy result

Keep the behavioral result intact even when policy or environment lifecycle fails.

Example:

```text
assertion_outcome = passed
policy_findings = [cost_limit_exceeded]
overall_outcome = policy_failed
```

This preserves the fact that the candidate behaved correctly while also preserving that Battalion must not treat the validation as successfully complete under the admitted policy.

Do not rewrite the behavioral result to `failed` merely because cost, authorization, or cleanup failed.

---

## Failure and non-success taxonomy

Initial classes:

### `behavioral_validation_failure`

The environment was sufficiently healthy and the candidate violated the observable contract.

Typical route: Driver or Debugger.

### `environment_infrastructure_failure`

The environment could not provide valid test conditions.

Typical route: recovery policy, Deployer/infrastructure owner, or human escalation.

### `authorization_failure`

Required capability, credential, scope, or approval was absent, expired, or denied.

Typical route: admission/human authority or environment administrator.

### `cost_policy_failure`

Estimated, unknown, or observed cost violates admitted policy.

Typical route: policy authority or human decision.

Preserve the behavioral result if one exists.

### `cleanup_failure`

The required environment terminal disposition was not reached or verified.

Typical route: cleanup retry/reconciliation, Deployer/infrastructure owner, or human acknowledgement.

### significance evidence

Significance is not a failure class.

Route `SignificanceSignal` through RFC-0025.

## Cost authorization and observation

Separate these contracts:

```text
CostAuthorization
  currency
  maximum_authorized_spend?
  estimated_spend?
  estimate_basis
  unknown_cost_policy

CostObservation
  observed_actual_spend?
  observed_estimate?
  provider_metering_ref?
  observation_time
  completeness
```

Authorization asks what financial exposure policy allowed before execution.

Observation asks what the provider later reported or what Battalion can currently estimate.

Unknown actual cost is not zero.

A late cost exceedance produces a policy finding/failure while preserving any already-produced behavioral evidence.

## Cleanup and retention lifecycle

Environment validation is not complete merely because assertions finished.

The environment must reach an admitted lifecycle disposition.

Possible dispositions include:

```text
cleaned
restored
retained_until <deadline>
production_unchanged
cleanup_failed
```

For `retained_until`, durable scheduling of the retention deadline satisfies the **current admitted disposition** if policy explicitly allowed retention.

It does not mean teardown already happened.

Battalion must retain an outstanding lifecycle obligation until later teardown is verified.

---

## Shared-environment leasing

BTN-192 should own lease acquisition, scheduling, and concurrency mechanics.

RFC-0028 only requires environment policy to declare whether a lease is required and what lease class is needed.

Conceptually:

```text
lease_policy
  none
  exclusive
  shared_read
  shared_partitioned
```

Environment admission requires a valid lease reference when policy requires one.

This keeps resource scheduling out of the validation contract while preserving the dependency.

## Workflow composition

### Local integration

```text
Implementation
  -> deterministic code validation
  -> EnvironmentValidation(local_ephemeral)
  -> Review
```

### Staging deployment

```text
Implementation
  -> Review
  -> Deploy/Provision
  -> EnvironmentValidation(shared_staging)
  -> Human QA/UAT when required
```

### Production-like validation

```text
Review
  -> admitted provision/deploy stages
  -> EnvironmentValidation(production_like)
  -> cleanup or retained lifecycle obligation
  -> human acceptance/promotion when required
```

RFC-0026 permits these steps to live in admitted recipe topology without requiring a new Run type.

If later scheduling or worker placement needs independent Runs, preserve the same validation obligation and evidence identities across those Runs.

## Model participation

Models may:

- propose validation obligations;
- help author scenarios;
- identify useful observations;
- interpret bounded evidence;
- suggest diagnoses;
- recommend additional evidence.

Models may not:

- widen environment scope;
- select undeclared credentials;
- increase spend authorization;
- convert unknown cost to zero;
- bypass approval;
- waive required cleanup or lifecycle obligations;
- claim an external action occurred without evidence;
- suppress significance signals;
- rewrite infrastructure, policy, or cleanup problems as behavioral success.

## Concrete scenario: disposable local database

A persistence change must be tested against PostgreSQL semantics.

```text
class: local_ephemeral
capabilities:
  create_resource: postgres_container + private network
  mutate_data: execution-owned database only
  read_observe: execution-owned database/process
  cleanup_teardown: execution-owned resources only
credential_refs: none
cost authorization: known zero provider spend
approval: project pre-authorization
lease: none
```

Battalion creates the resources, runs the admitted scenario, records bounded evidence, and verifies cleanup.

No human interrupt is needed unless policy, resource, or cleanup conditions require one.

## Concrete scenario: provider-neutral cloud fake

The first cloud-shaped implementation should exercise the same contract without contacting a real provider.

```text
class: production_like
binding_id: fake-cloud-validation-v1
scope:
  synthetic validation account/project/subscription
  admitted region
  run-owned namespace
capabilities:
  read_observe
  deploy
  create_resource
  mutate_data: run-owned data only
  delete_resource: run-owned resources only
  cleanup_teardown
credential_ref:
  battalion://credentials/fake-cloud-validation
cost authorization:
  maximum_authorized_spend: CAD 5.00
  estimated_spend: CAD 1.40
  unknown_cost_policy: deny unestimated new resource classes
approval:
  project policy pre-authorizes this exact envelope
lease:
  exclusive or partitioned, according to environment policy
```

The fake produces deterministic provider-like responses and side-effect identities. It can simulate authorization denial, delayed cost observation, partial provisioning, cleanup failure, crash/reconciliation, and retention states.

This validates Battalion's contract and recovery behavior before any implementation can spend money or mutate a real cloud account.

## Automated validation versus Human QA/UAT

Automated validation asks:

> Did the exact candidate satisfy the admitted machine-observable contract in the admitted environment under the admitted authority and lifecycle policy?

Human QA/UAT asks:

> Does a human accept the product outcome for its intended use?

A workflow may require either or both.

The current Regiment reference keeps staging deployment and Human QA as separate steps. RFC-0028 preserves that distinction while adding a governed machine-validation layer before or alongside Human QA.

## Decisions

1. **Environment descriptor ownership:** use repository policy plus machine/provider binding resolution.
2. **Validation obligation ownership:** Specification owns observable requirements; Architect owns architectural/environment realization; Battalion owns execution/admission/evidence.
3. **Execution container:** use recipe stages/subgraphs in v1. Do not introduce a dedicated Run kind yet.
4. **Shared-environment leasing:** BTN-192 owns acquisition/concurrency mechanics. RFC-0028 declares lease requirements only.
5. **Late cost exceedance:** preserve behavioral evidence and add a typed policy failure/non-success outcome.
6. **Retention:** an admitted retained-until state can satisfy the current lifecycle disposition once durably scheduled, but teardown remains an outstanding lifecycle obligation until verified.
7. **First cloud-shaped implementation:** stop at a provider-neutral fake/contract Capability. Do not add a real provider adapter in the first implementation wave.
8. **Artifact ownership:** `ValidationObligation` and `EnvironmentValidationEvidence` belong to the RFC-0015 canonical artifact family. Workflow boundary contracts reference them by exact revision. Physical module placement remains an implementation detail.

There are no remaining architectural open questions in this RFC.

## Implementation decomposition after acceptance

BTN-198 is architecture-only.

Implementation is tracked through a reuse-first decomposition:

1. BTN-256 — Environment Validation Capability, environment descriptor/binding/admission contracts, credential boundary, and provider-neutral fake.
2. BTN-257 — RFC-0015 `ValidationObligation` and `EnvironmentValidationEvidence` canonical artifacts, cost/lifecycle evidence, and result taxonomy.
3. BTN-258 — WorkflowRecipe, authority, side-effect, recovery, significance, and Human QA/UAT integration using existing Battalion primitives.
4. BTN-259 — disposable local/container/database Environment Validation adapter.
5. BTN-260 — CLI/desktop inspection and credential-free UAT/evaluation.
6. BTN-192 is extended rather than duplicated for shared-environment lease acquisition/concurrency semantics.

Existing BTN-138/143, BTN-157/248/249, BTN-201, BTN-252/253, and side-effect ledger work remain dependencies/owners for their existing generic mechanisms rather than receiving duplicate RFC-0028 subsystems.

A real cloud-provider adapter is deferred until the provider-neutral Capability contract and local/fake implementations have passed UAT.

No production implementation belongs directly in BTN-198.

---

## Acceptance

RFC-0028 is accepted.

The accepted architecture preserves these invariants:

- models do not receive ambient environment authority;
- exact environment, candidate, scenario, binding, capability, and authorization identities are inspectable;
- repository environment policy and machine/provider bindings remain distinct;
- observable product requirements and architectural realization remain distinct;
- cost authorization and cost observation remain distinct;
- behavioral outcome, policy outcome, significance, and environment lifecycle remain distinct;
- cleanup or admitted retention disposition is explicit;
- shared-resource scheduling does not become hidden validation logic;
- automated evidence does not silently become Human QA/UAT acceptance;
- provider-neutral contract behavior is validated before a real provider adapter is introduced.
