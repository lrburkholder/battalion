# RFC-0027 — Scoped Institutional Knowledge

**Status:** Accepted  
**Ticket:** BTN-114  
**Author:** Architecture  
**Target:** BTN-M7 Integration Hardening & Channels  
**Related:** `philosophy.md`, BTN-24, BTN-58, BTN-97, BTN-110, RFC-0021, RFC-0023, ADR-0018

---

## Summary

Battalion should classify durable knowledge by the entity that owns its meaning and by the audience that may receive it.

The initial scopes are:

```text
RUN           execution-local state, observations, and evidence
USER          person-specific preferences and workflow context
PROJECT       shared project-specific institutional knowledge
ORGANIZATION  approved cross-project institutional knowledge
```

Scope is not authority.

Battalion keeps these concepts separate:

```text
scope          who or what does this knowledge belong to?
provenance     where did it come from?
authority      does current policy permit it to satisfy this operation?
authorization  may this Actor perform the operation?
relevance      should this knowledge be supplied here?
```

RFC-0023 owns provenance and authority evaluation. BTN-114 adds ownership scope and governed scope transitions.

Battalion must not silently widen knowledge scope. Repeated recall, model confidence, semantic similarity, indexing, provider memory, or repeated observations cannot move knowledge from `RUN` or `USER` into `PROJECT` or `ORGANIZATION`.

Repository artifacts remain authoritative where existing architecture says they are authoritative. This RFC does not replace specifications, ADRs, repository instructions, Intel/Instincts, or deterministic Quality Gates.

---

## Problem

Battalion already carries several kinds of information:

- Run state and execution evidence;
- accepted Intel/Instinct records;
- deterministic Instinct retrieval under BTN-24 and ADR-0018;
- repository documentation and ADRs;
- repository instructions under RFC-0021;
- external and derived artifacts with RFC-0023 provenance;
- model-provider or user-local memory outside Battalion.

Without a shared scope model, information can cross boundaries incorrectly.

Examples:

- a personal workflow preference becomes project guidance;
- a Run-local observation becomes durable project policy;
- project knowledge exists only inside one model provider's private memory;
- repeated project observations are treated as organization policy;
- another user cannot resume work without the previous operator's private context.

Battalion needs a provider-neutral way to state who owns knowledge without creating a universal memory database or a second authority system.

---

## Goals

- Define a versioned `RUN | USER | PROJECT | ORGANIZATION` scope contract.
- Keep scope separate from provenance, authority, authorization, audience, and relevance.
- Make project and organization knowledge portable across model providers.
- Keep private user context private by default.
- Define explicit promotion, demotion, and copy semantics.
- Prevent silent scope widening.
- Reuse RFC-0023 for provenance and operation-time authority evaluation.
- Preserve repository artifacts and existing Intel records as their current sources of truth.
- Let context assembly select by scope plus existing audience, applicability, relevance, and authority rules.
- Keep semantic and vector indexes rebuildable projections.
- Preserve cross-scope conflicts as inspectable evidence.
- Prefer offline operation and local reproducibility over introducing a central Battalion service in the initial design.

## Non-goals

- Move all documentation into a Battalion database.
- Define one storage backend for every knowledge type.
- Replace Intel/Instinct contracts.
- Replace repository instructions under RFC-0021.
- Make semantic search authoritative.
- Treat scope as a trust level.
- Treat broader scope as stronger authority.
- Treat newer content as automatically correct.
- Import provider-local memory as project or organization authority.
- Introduce a required central Battalion control plane in v1.

## Design

### Scope is an ownership boundary

```text
KnowledgeScope v1
  RUN
  USER
  PROJECT
  ORGANIZATION
```

| Scope | Meaning | Default visibility | Examples |
|---|---|---|---|
| `RUN` | Information owned by one execution | that Run and admitted consumers | observations, intermediate evidence, unresolved hypotheses, retry context |
| `USER` | Information owned by one person/operator | that user | workflow preferences, personal conventions, local tool preferences |
| `PROJECT` | Shared knowledge needed to work effectively on one project | authorized project participants | project invariants, accepted learned guidance, domain context, project decisions |
| `ORGANIZATION` | Approved knowledge intended to apply across projects | authorized organization participants/projects | shared engineering guidance, organization policy, cross-project conventions |

Scope does not grant authority.

A `PROJECT` record may be advisory. A `RUN` artifact may be authoritative for one Run decision. RFC-0023 decides whether evidence satisfies an authority-sensitive operation under current policy.

### Knowledge references should compose with existing records

Battalion should use a small composable scope contract instead of forcing every artifact into one universal knowledge schema.

Conceptually:

```text
ScopedKnowledgeRef v1
  knowledge_ref_id
  scope
  subject_id
  artifact_ref
  provenance_ref
  status
  created_at
  created_by_actor_id?
  created_in_run_id?
  transition_ref?
```

`subject_id` identifies the owner inside the selected scope:

```text
RUN          -> run_id
USER         -> actor/user identity
PROJECT      -> project_id
ORGANIZATION -> organization_id
```

The referenced artifact keeps its domain-specific contract.

Examples:

- an Instinct remains an Intel record;
- an ADR remains a repository artifact;
- a repository instruction remains governed by RFC-0021;
- Run evidence remains Run evidence.

The scoped reference does not copy authority into a new record.

This composition-first design is intentional. Battalion should introduce a broader shared base model only if implementation, UAT, or cross-artifact reuse demonstrates that it is necessary.

### `RUN` is the default scope for unpromoted execution knowledge

Execution-local observations and generated interpretations remain `RUN` scoped unless another admitted workflow explicitly creates knowledge at a different scope.

A Run observation does not become `PROJECT` knowledge because:

- several Runs observed it;
- several models repeated it;
- semantic search ranks it highly;
- it was written to disk;
- it was committed as a non-authoritative artifact;
- it was recalled frequently.

Run evidence may still be durable for audit and resume purposes.

Durable does not mean institutional.

### `USER` is private by default

`USER` knowledge is person-specific context.

Battalion must not expose it to another user or convert it into project guidance unless an admitted sharing or promotion operation allows that transition.

Provider-local memory may complement `USER` knowledge. It is not canonical Battalion project or organization knowledge.

Another authorized user must be able to resume project work without access to the previous user's private model memory.

For the initial design, Battalion stores user-scoped knowledge in a **Battalion user data directory** outside the project repository. The directory is provider-independent and portable with the user's Battalion environment.

The exact operating-system path and backup/synchronization mechanism are implementation details. The architectural requirements are:

- private by default;
- not committed into a project repository by default;
- provider-independent;
- addressable through stable Battalion user identity;
- portable between model providers and local execution environments;
- usable without a required central service.

### `RUN -> USER` promotion is deferred

BTN-114 defines `USER` scope and its storage boundary, but it does not introduce automatic or first-class learned personal-memory capture from Run observations.

A future user-memory RFC may define `RUN -> USER` promotion, confirmation, retention, deletion, and privacy semantics.

Until then, a Run-local observation must not be promoted into `USER` knowledge through generic scope-transition machinery.

### `PROJECT` is shared project knowledge

`PROJECT` knowledge represents durable project context that future authorized users and models may need.

Examples include:

- domain facts;
- project invariants;
- accepted learned guidance;
- repository-specific operating context;
- durable project decisions not already represented by a stronger artifact type.

Existing authority rules still apply.

For example, an advisory project Instinct that conflicts with an applicable RFC-0021 repository instruction does not override that instruction.

### `ORGANIZATION` requires explicit institutional admission

`ORGANIZATION` knowledge is not the automatic union of project knowledge.

Repeated project observations may create a candidate for organization-wide guidance. They do not create organization authority by repetition.

Creating organization-scoped knowledge requires an admitted operation with:

- source evidence;
- destination organization identity;
- Actor authorization for that operation;
- durable provenance;
- explicit human confirmation;
- the policy evaluation required by RFC-0023.

RFC-0023 still evaluates whether the resulting artifact satisfies any later authority-sensitive operation.

### Organization knowledge is local-first in v1

Battalion does not yet define a central service, control plane, or organization-wide authority host.

BTN-114 therefore does not introduce one solely to support organization knowledge.

For early Battalion:

- organization-scoped knowledge must remain usable offline;
- projects may materialize admitted organization knowledge locally;
- local copies must retain organization ownership, source identity, provenance, and revision identity;
- synchronization and revocation across projects are outside the initial implementation;
- a future central organization capability may replace or augment local materialization without changing scope semantics.

Offline operation and reproducibility have higher priority than central control in this version.

## Scope transitions

Battalion distinguishes **promotion**, **demotion**, and **copy**.

### Promotion

Promotion widens institutional reach.

Initial supported examples are:

```text
RUN -> PROJECT
USER -> PROJECT
PROJECT -> ORGANIZATION
```

`RUN -> USER` is reserved for a later privacy-focused memory design.

Every supported widening promotion requires explicit human confirmation.

Promotion must:

1. use an explicit Battalion operation;
2. preserve the source artifact/reference identity;
3. record destination scope and subject;
4. record the requesting Actor and Run where applicable;
5. preserve RFC-0023 provenance;
6. validate Actor authorization for the destination operation;
7. require explicit human confirmation of the exact promotion candidate;
8. evaluate the promotion operation under current admitted policy using RFC-0023 semantics;
9. create a new scoped record or immutable revision instead of rewriting historical ownership;
10. avoid assigning permanent intrinsic authority as a side effect.

Promotion changes ownership or audience reach. It does not automatically satisfy future authority requirements.

No project or organization policy may pre-authorize a widening transition so completely that the required human confirmation disappears. Policy may determine eligibility, required evidence, and who may confirm. The human confirmation remains mandatory.

### Demotion

Demotion narrows use.

Example:

```text
ORGANIZATION -> PROJECT
```

A project may specialize organization guidance for local use when current admitted organization/project policy permits that exception or specialization.

Demotion must not mutate the source. It creates a derivative or scoped reference with provenance back to the organization source.

### Copy

Copy preserves original ownership semantics.

A project may cache or materialize organization knowledge for offline use. The copy remains organization-derived and preserves source identity.

Copy is not promotion or demotion merely because storage location changes.

## Project exceptions to organization guidance

Project exceptions follow the same architectural pattern as RFC-0023 authority evaluation.

Scope itself does not encode override precedence.

When project-local guidance conflicts with organization guidance, the consuming authority-sensitive operation must evaluate current admitted project/organization policy.

That policy determines whether the project exception is:

```text
forbidden
explicitly permitted
permitted only through an admitted exception record/operation
unknown or conflicted
```

Battalion must preserve the organization source, project exception source, applicable policy identity, and operation-time evaluation evidence.

A project cannot create an effective organization-policy exception merely by adding newer or more specific project knowledge. If current policy does not establish that the exception is valid, the authority evaluation remains denied, unknown, or conflicted as RFC-0023 requires.

---

## Scope widening fails closed

No model, plugin, integration, indexer, or storage adapter may widen scope by directly changing a field.

The application boundary must validate at least:

```text
source scope
source subject
source artifact/provenance
requested destination scope
destination subject
requesting Actor
operation kind
applicable project/organization policy
exact human confirmation
```

Unknown or insufficient authorization must fail closed for widening operations.

A model can propose a promotion. It cannot admit its own proposal.

## Retrieval and context assembly

Scope is an admission boundary before relevance ranking.

A candidate retrieval sequence is:

```text
1. identify Run, requesting user, project, organization, role, and task
2. enumerate scopes visible to that execution
3. remove records outside the permitted subject/audience boundary
4. apply record-specific status and applicability rules
5. apply RFC-0023 authority evaluation where the consuming operation requires it
6. preserve or surface conflicts
7. rank/select using the owning retrieval strategy
8. apply context bounds
9. record what was supplied and why
```

Semantic or vector retrieval may later rank eligible material. It cannot make an ineligible record visible. It cannot make advisory content authoritative.

BTN-24 and ADR-0018 remain the deterministic retrieval contract for current Instincts. This RFC adds scope around that path instead of replacing it.

---

## Conflict semantics

Battalion must not use a universal rule such as:

```text
broader scope wins
newer wins
more frequently recalled wins
higher model confidence wins
```

Resolve conflicts using the governing artifact and authority contracts.

Examples:

- a `USER` preference conflicts with project repository instructions: repository instruction authority governs project work;
- a `PROJECT` Instinct conflicts with RFC-0021 authority: RFC-0021 rules govern;
- organization guidance conflicts with a project exception: current organization/project policy determines whether the exception is valid under the RFC-0023 pattern;
- two same-authority project claims conflict: preserve the conflict until the owning authority resolves it;
- unreviewed `RUN` evidence conflicts with accepted project guidance: preserve both; do not silently promote the Run evidence.

Conflict evidence should identify the competing artifacts, scopes, subjects, provenance, and applicable policy evaluation.

---

## Unreviewed knowledge remains visibly unreviewed

Indexing, committing, caching, or frequently recalling content does not change its review state.

Generated or retrieved knowledge that has not crossed its required admission boundary must remain visibly classified according to its owning contract, such as:

```text
contextual
candidate
unreviewed
accepted
superseded
```

This RFC does not require one universal status vocabulary. It requires retrieval to preserve the owning artifact's status and not infer authority from persistence.

---

## Provider-local memory

Battalion may use provider-local or user-local memory as contextual input when policy allows it.

Such input must:

- identify its provider/local provenance when imported;
- remain within the user's privacy boundary by default;
- enter as contextual evidence rather than hidden project authority;
- require an admitted scope transition before becoming `PROJECT` or `ORGANIZATION` knowledge.

Project and organization knowledge must remain usable across OpenAI, Claude, Mistral, local models, and future executors.

---

## Indexes are projections

Semantic indexes, embeddings, caches, inverted indexes, and search databases are projections over authoritative records and artifacts.

They may contain:

- record identifiers;
- vectors;
- snippets;
- normalized terms;
- derived search metadata.

They must not become the only source of authority-bearing content or scope ownership.

Deleting and rebuilding an index must not change:

- knowledge scope;
- subject ownership;
- provenance;
- review status;
- underlying authoritative artifacts.

## Reconciliation with existing architecture

### BTN-24 / ADR-0018

Current Instinct retrieval is project-local and deterministic.

It continues to:

- retrieve accepted, active, non-superseded Instincts;
- filter by role and literal applicability;
- use stable ordering;
- bound context;
- expose inclusion and exclusion evidence.

Current accepted Instincts are therefore naturally `PROJECT` scoped unless a later Intel revision introduces other scopes.

### RFC-0021

Repository instructions are declared project authority with their own path, audience, precedence, conflict, and drift rules.

They are `PROJECT` scoped for ownership purposes.

This RFC must not use generic knowledge ranking to override RFC-0021 resolution.

### RFC-0023

RFC-0023 remains authoritative for provenance, authority, and Actor authorization boundaries.

BTN-114 adds only the ownership dimension and transition rules.

In particular, BTN-114 must not persist a permanent intrinsic authority field merely because scope changes.

Project exceptions to organization guidance also reuse RFC-0023's operation-time policy evaluation pattern instead of introducing a second precedence lattice.

### Repository artifacts

Specifications, ADRs, instructions, and other repository artifacts remain their existing sources of truth.

Scoped knowledge references may point to them for retrieval and context assembly without moving their canonical content into a competing store.

## Candidate context model

```text
Run
 |
 +--> RUN knowledge ------------------------------+
 |                                                |
 +--> requesting USER knowledge -----------------+|
 |                                               ||
 +--> PROJECT knowledge ------------------------+||
 |                                             |||
 +--> permitted ORGANIZATION knowledge --------+|||
                                               ||||
                                               vvvv
                                        scope admission
                                               |
                                               v
                                  audience / applicability
                                               |
                                               v
                              authority evaluation if required
                                               |
                                               v
                                      relevance / selection
                                               |
                                               v
                                         context bounds
                                               |
                                               v
                                      supplied-context evidence
```

These paths describe visibility candidates. They do not define precedence.

## Validation

Tests or fixtures should prove at least:

- `RUN` knowledge is not visible to an unrelated Run;
- one user's private knowledge is not supplied to another user;
- user knowledge persists in the Battalion user data directory without model-provider dependence;
- project knowledge remains available after changing model provider;
- a different authorized user can resume project work without the previous user's provider memory;
- organization knowledge remains usable offline from a provenance-preserving local materialization;
- repeated Run observations do not auto-promote;
- generic `RUN -> USER` promotion is rejected because that transition is deferred;
- unauthorized `RUN -> PROJECT`, `USER -> PROJECT`, and `PROJECT -> ORGANIZATION` attempts fail closed;
- a widening promotion without exact human confirmation fails even when other policy requirements are satisfied;
- an authorized and human-confirmed transition preserves source identity, provenance, Actor, Run, and admission evidence;
- promotion does not persist intrinsic authority as a side effect;
- demotion and copy do not mutate the source;
- unknown provenance remains unknown;
- conflicting user/project knowledge preserves conflict evidence;
- a project exception to organization guidance is evaluated under current admitted policy rather than scope precedence;
- repository instructions retain RFC-0021 authority over advisory Instincts;
- provider-local memory enters only as contextual/user-local evidence until explicitly promoted;
- retrieval applies scope admission before relevance ranking;
- supplied-context evidence identifies record IDs, scopes, and omission reasons;
- rebuilding a semantic/vector index does not change authoritative records or scope.

---

## Deferred design

The following concerns are intentionally deferred instead of remaining open in BTN-114:

- first-class `RUN -> USER` learned-memory promotion, including deletion and privacy controls;
- organization-wide central synchronization, revocation, and control-plane semantics;
- cloud or multi-device synchronization of the Battalion user data directory;
- a larger universal knowledge base model beyond the small composable scope/reference contracts.

These should be revisited after real usage, UAT, and multi-user/multi-project operation provide evidence.

---

## Consequences

- Knowledge ownership becomes inspectable and provider-neutral.
- Private user context stays separate from shared project truth.
- User knowledge has a portable Battalion-owned local home without requiring a central service.
- Run evidence can remain durable without becoming institutional knowledge.
- Organization knowledge requires explicit human confirmation and governance.
- Early organization knowledge remains local-first and offline-capable.
- Project exceptions reuse the RFC-0023 policy-evaluation model.
- Existing repository and Intel contracts remain authoritative for their own artifacts.
- Retrieval gains an additional admission dimension before relevance selection.
- Every scope-widening promotion becomes a durable human-confirmed operation.
- Semantic indexes remain replaceable infrastructure rather than authority stores.
