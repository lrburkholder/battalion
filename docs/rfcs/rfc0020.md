# RFC-0020 — Specification Workflow and Human Authority Boundary

**Status:** Draft  
**Date:** 2026-09-05  
**Ticket:** BTN-45  
**Author:** Architecture  
**Target:** BTN-M11 specification workflow  
**Related:** `philosophy.md`, `spec.md`, `docs/future/specifier-role.md`, BTN-25, BTN-26, BTN-29, BTN-101, RFC-0008, RFC-0012, RFC-0019

---

## Summary

Battalion needs a first-class way to turn incomplete product intent into an implementation-ready specification without allowing a model to silently acquire product or architectural authority.

The leading architecture is a **distinct Specification workflow**, sharing durable execution mechanics with other Battalion workflows but retaining specification-specific state, authority, artifacts, and human decisions. A Specifier role may participate in that workflow, but the role is not the admission authority, does not approve its own output, and is not inserted as a mandatory node in every Implementation Run.

The governing invariant is:

> **Ceremony may scale down; human authority does not.**

RFC-0012 already owns deterministic-first workflow admission, Tactician escalation for semantic uncertainty, explicit human workflow choice, and the upgrade-only ratchet. BTN-45 therefore extends that architecture **symmetrically**: Tactician is not only useful when it recommends a simpler implementation recipe. When available evidence cannot establish that product intent is sufficiently authoritative for implementation, Tactician may recommend **Specification as the next registered workflow**. Battalion, not Tactician, performs the transition after the human admits that workflow.

This means Tactician can recommend movement in either direction: less ceremony when authoritative evidence positively admits a compact path, or more preparatory work when ambiguity, missing product decisions, or specification insufficiency means implementation should not yet be admitted. Specifier itself remains a bounded semantic producer rather than a universal router or meta-orchestrator.

A generated specification is **evidence and a proposal until an authorized human explicitly accepts a particular revision**. Acceptance creates the authoritative specification revision that downstream workflow admission and Architect planning may consume.

This RFC is planning only. It does not authorize a Specifier prompt, node, graph change, persistence schema, or UI implementation.

---

## Problem

Battalion's implementation workflow currently assumes that a sufficiently authoritative specification already exists before execution begins. That is safe but incomplete: real work often begins as an operator request containing partial requirements, unstated constraints, unresolved decisions, and repository context that must be reconciled before Architect or Driver should act.

The Regiment provides useful prior art by separating specification from architecture: its Specifier facilitates the what/why conversation and produces a Brief, and human partners review that Brief before it becomes Architect input. Battalion should preserve that authority boundary while fitting it into Battalion's stronger persistence, provenance, workflow-admission, execution-evidence, and application-operation contracts.

The design must also avoid a different failure mode: forcing every request through an artifact-heavy interview merely because Specification exists. RFC-0012 already established deterministic-first proportional workflow admission, explicit human workflow choice, and an upgrade-only ratchet. BTN-45 must compose with that architecture rather than duplicate it.

A further implication is that workflow admission cannot be understood only as choosing among implementation recipes. Sometimes the correct next workflow is not implementation at all. If deterministic evidence and, when needed, Tactician assessment reveal that intent is not sufficiently specified, Battalion should offer Specification before implementation admission.

## Existing architectural constraints

### Repository artifacts outrank conversation

Durable product intent must end as a repository- or project-owned specification artifact. Conversation, raw model reasoning, and transient UI state cannot become the source of truth.

### Specification is not Implementation Run state

RFC-0008 already reserves a `SpecificationExecution`-like workflow-specific state under a shared `WorkflowExecution` abstraction. Specification state must not be added to `RunState` merely because implementation consumes its output later.

### Workflow admission and Tactician authority are already owned elsewhere

RFC-0012 owns deterministic admission evidence, registered workflow recipes, Tactician escalation for semantic uncertainty, explicit human choice, and the upgrade-only ratchet. BTN-45 extends the set of meaningful **next workflow recommendations** to include Specification; it does not give Tactician new execution authority.

Tactician may recommend Specification when intent adequacy is semantically uncertain, just as it may recommend compact or full implementation handling when implementation admission is uncertain. Tactician does not directly invoke Specifier, start a workflow, approve a specification, construct an arbitrary graph, or override deterministic prohibitions. Battalion application/orchestration offers the recommendation to the human and starts only the human-admitted registered workflow.

Specifier therefore must not become a universal router or a second task-complexity classifier.

### Architect receives an approved specification

RFC-0019 treats the Architect plan as repository-grounded architectural intent derived from an already admitted evidence package including the approved specification. BTN-45 must stop before silently moving architectural choices into Specifier.

## Options

### Option A — Keep specification authoring outside Battalion

Humans or external tools produce authoritative specifications; Battalion continues to begin only after one exists.

**Advantages**

- smallest Battalion surface;
- simplest authority model;
- no new workflow state or human review UI.

**Costs**

- Battalion cannot help structure incomplete intent;
- specification provenance and correction evidence remain fragmented;
- no reusable workflow for projects whose starting point is conversational or incomplete requirements;
- Tactician can recognize insufficient intent but has no Battalion-owned workflow to recommend for resolving it;
- misses the opportunity to reduce mechanical requirements work while preserving human ownership.

### Option B — Separate Specification workflow

A `SpecificationExecution` converts bounded intent/evidence into one or more candidate specification revisions. An authorized human reviews, edits, accepts, rejects, or cancels. Only an accepted revision becomes authoritative input for implementation admission and Architect planning.

Specification is a registered workflow that deterministic admission policy or Tactician may recommend as the **next** workflow when current intent is insufficient for implementation. The recommendation does not itself start Specification; the human admits the transition and Battalion orchestrates it.

**Advantages**

- keeps product-intent authority separate from implementation execution;
- matches the shared-workflow direction established by RFC-0008;
- allows durable provenance, model/cost evidence, revision history, interrupts, resume, pause, blocking, and cancellation;
- composes with RFC-0012 instead of creating a separate routing system;
- lets Tactician recommend stronger preparatory handling as well as simpler implementation handling;
- can support proportional specification recipes without making Specifier universal;
- cleanly supports future non-model/manual or alternate specification producers.

**Costs**

- introduces workflow-specific persistence and application operations;
- requires explicit artifact identity/versioning and acceptance semantics;
- requires UI/CLI surfaces beyond the current Implementation Run;
- requires workflow admission to distinguish specification insufficiency from implementation risk/complexity.

### Option C — Add Specifier as an Implementation Run graph phase

Insert Specifier before Architect in the implementation graph.

**Advantages**

- superficially simple linear lifecycle;
- easy handoff from specification to architecture.

**Costs**

- conflates producing authoritative product intent with executing implementation;
- pressures `RunState` into carrying specification lifecycle state;
- makes Specifier mandatory even when an authoritative specification already exists;
- complicates re-specification, rejection, cancellation, and reuse of accepted specifications;
- prevents Specification from being a first-class workflow recommendation from Tactician;
- duplicates workflow-admission concerns already separated in RFC-0012.

**Initial assessment:** reject as the default architecture.

## Proposed architecture

The important distinction is between **intent adequacy** and **implementation handling**. These are related but not identical. A technically simple task may still need Specification because the desired behavior is ambiguous. A technically complex task may already have an excellent accepted specification and proceed directly toward Architect/full implementation handling.

```text
human intent / existing work item / governing artifacts
                    |
                    v
          bounded admission evidence
                    |
                    v
       deterministic workflow admission
          /                       \
   sufficient intent          uncertain / insufficient
          |                           |
          |                    Tactician when semantic
          |                    uncertainty remains
          |                           |
          |                 recommend Specification /
          |                 clarification / other
          |                           |
          |                    explicit human choice
          |                           |
          |                    Specification workflow
          |                           |
          |                   candidate specification
          |                           |
          |                    explicit human accept
          |                           |
          +<--------------------------+
                    |
                    v
       implementation admission evidence
                    |
        deterministic policy first
          /          |          \
      compact       full      uncertain
                                |
                           Tactician
                                |
                     recommendation to human
                                |
                         admitted recipe
```

This is conceptually one workflow-admission system operating at multiple boundaries, not two unrelated routers. Tactician's question is broader than "can we remove nodes?":

> **Given the authoritative evidence currently available, what registered workflow should the human be offered next?**

Valid answers may include compact implementation, full implementation, Specification, clarification, or another registered workflow allowed by policy. Tactician still does not choose or execute the workflow itself.

Within Specification:

```text
         admitted Specification workflow
                    |
          specification recipe
       /            |             \
  lightweight    standard       deep
       \            |             /
                    v
        candidate specification revision
                    |
                    v
           explicit human decision
        /          |          |        \
      edit       accept     reject    cancel
       |            |
       +----> new candidate   v
                         accepted specification
                                |
                                v
                     workflow admission resumes

At any non-terminal execution point:
  explicit operator suspension -> paused
  unresolved prerequisite       -> blocked
  execution fault               -> failed
```

`Specifier` is one semantic producer inside Specification workflow recipes. It does not own admission policy, artifact authority, acceptance, architecture, implementation, backlog mutation, or cross-workflow orchestration.

## Tactician and Specification

Tactician participates at workflow boundaries where deterministic evidence is insufficient. It does not merely select between a "normal" and "simpler" implementation path.

Two distinct escalation questions exist:

1. **Is product intent sufficiently authoritative to admit implementation at all?**
2. **Given adequate intent, what implementation workflow is appropriate?**

For the first question, deterministic evidence may establish that an accepted specification or equivalently authoritative work item is sufficient. If not, and the deficiency is semantically uncertain rather than mechanically prohibited, Tactician may recommend Specification or clarification.

For the second question, RFC-0012's existing compact/full/uncertain admission remains authoritative. Tactician may recommend compact, full, or clarification where deterministic policy returns uncertainty.

The same work can therefore legitimately move **upward** in ceremony before it later moves **downward** in execution ceremony. For example, a small code change with ambiguous desired behavior may require a lightweight Specification workflow and human acceptance, then qualify for compact implementation once intent is authoritative.

Likewise, an architectural subsystem may arrive with a complete accepted specification and bypass Specification entirely while still requiring full implementation handling and Architect involvement.

### Invocation boundary

The phrase "Tactician calls Specifier" is useful shorthand but is not the architectural authority model. The actual sequence is:

```text
Tactician assessment
       |
       v
recommend registered Specification workflow
       |
       v
human admits / rejects / chooses alternative
       |
       v
Battalion application starts SpecificationExecution
       |
       v
Specifier participates according to admitted recipe
```

This preserves RFC-0012's rule that Tactician is advisory and prevents it from becoming a hidden model-driven graph orchestrator.

## Specification artifact

The canonical artifact should have a stable identity plus immutable accepted revisions. Exact encoding remains open until existing persistence conventions are reconciled, but the logical contract should include at least:

```text
Specification
  specification_id
  project_id
  canonical_work_identity
  current_accepted_revision_id optional

SpecificationRevision
  revision_id
  specification_id
  status: candidate | accepted | rejected | superseded
  outcomes[]
  constraints[]
  non_goals[]
  acceptance_criteria[]
  unresolved_product_decisions[]
  governing_artifact_refs[]
  evidence_refs[]
  source/provenance
  producer execution/model/prompt/config provenance optional
  created_at
  accepted_by_actor_id optional
  accepted_at optional
```

The human-readable specification may remain Markdown, but authority belongs to the admitted revision identity and durable decision record, not to whichever text happens to be visible in a chat window.

### Candidate versus accepted authority

A model-produced revision is never authoritative merely because generation completed successfully. It remains a candidate until an authorized human explicitly accepts that exact revision.

Editing a candidate creates a new revision or otherwise changes its exact candidate identity before acceptance. Acceptance must bind to the reviewed revision rather than a mutable logical specification name.

### Ticket relationship

A specification must preserve canonical work identity rather than silently minting a parallel backlog identity. The specification may be linked to a WorkSource ticket or other work item; whether acceptance can create or update that ticket is a separate application operation governed by BTN-134-style WorkSource authority and must not be an implicit side effect of Specifier generation.

## Proportional ceremony

BTN-45 adopts RFC-0012's principle rather than inventing its own complexity score.

Specification recipes may vary in interview depth, evidence gathering, artifact detail, and whether semantic model assistance is needed, but all paths preserve explicit human authority where product/design intent is being established.

Representative shapes:

- **Exploratory/spike work:** a deliberately narrow question, constraints, non-goals, evidence expected, and a human-approved boundary preventing the spike from silently becoming production design.
- **Bounded change to an understood flow:** lightweight clarification of desired behavior and acceptance criteria, relying on existing accepted architecture and repository evidence.
- **Architectural/new-subsystem work:** deeper specification work surfacing unresolved product decisions, cross-system constraints, interfaces, operational concerns, and explicit Architect handoff.

These are examples, not mandatory Battalion domain enums.

Tactician may recommend that Specification is required without owning the choice of specification recipe. Deterministic policy should still do as much work as possible first: obvious missing authority or known full-specification requirements should not require a model call merely for confirmation, while semantically uncertain intent adequacy is appropriate Tactician territory.

### Upgrade-only ratchet

Once a lighter specification recipe begins, newly discovered evidence may require stronger handling. Cross-system impact, interface/schema change, architectural consequence, conflicting authoritative sources, missing product authority, or hidden scope may trigger escalation to a stronger recipe, Architect involvement, clarification, blocking, or cancellation.

The same ratchet applies across workflow boundaries. Work initially thought ready for implementation may be redirected to Specification when hidden ambiguity or missing product intent is discovered. Work may not silently continue under its original lighter admission merely because execution has already begun.

A Specification workflow may not downgrade itself merely to avoid an interrupt, artifact, blocked state, or authority boundary required by newly discovered evidence.

## Specification execution lifecycle

Specification needs durable lifecycle semantics beyond candidate acceptance. In particular, **paused** and **blocked** are distinct states and must not be collapsed into one generic inactive state.

A representative workflow-specific lifecycle is:

```text
requested
  -> inspecting
  -> synthesizing
  -> awaiting-human
  -> accepted
  -> rejected
  -> cancelled

cross-cutting non-terminal states:
  -> paused
  -> blocked

fault terminal/intervention state:
  -> failed
```

Exact state names may be reconciled with shared `WorkflowExecution` conventions during implementation, but the semantic distinction is normative.

### Paused

`paused` means execution **could otherwise continue**, but an authorized operator or admitted policy has intentionally suspended it. Examples include:

- the human explicitly pauses the workflow;
- cost/resource policy requires a deliberate suspension;
- the operator wants to defer specification work without cancelling it.

A paused execution preserves its prior resumable position and does not imply that any prerequisite is unsatisfied. `specification.resume` may return it to that position subject to normal authorization and stale-state checks.

### Blocked

`blocked` means execution **cannot validly continue until a prerequisite or dependency changes**. Representative causes include:

- an unresolved product decision requiring human authority;
- conflicting authoritative sources;
- a required Architect/Architecture decision;
- missing external/project evidence;
- an authorization or policy prerequisite;
- another workflow/dependency whose result is required before Specification can proceed.

Blocked state must carry typed durable blocker evidence rather than only a free-text status. Conceptually:

```text
SpecificationBlock
  block_id
  reason_code
  description
  evidence_refs[]
  dependency_ref optional
  required_resolution_kind
  created_at
  resolved_at optional
  resolution_evidence_refs[]
```

Blocked is not merely a human-selected label. Battalion enters it because admitted deterministic/application semantics establish that a prerequisite is unsatisfied. A user or model cannot make the workflow valid merely by choosing "unblock."

### Resolution and resumption

There should therefore be **no generic `specification.unblock` authority operation whose only effect is to clear the status**. The underlying condition is resolved through its owning action — for example, recording the required human product decision, admitting/completing Architecture work, supplying missing evidence, or satisfying authorization policy. Battalion then re-evaluates the blocker deterministically.

If all blocking conditions are resolved, the execution may return to its prior resumable state or another state required by policy. If blockers remain, `specification.resume` must fail closed or immediately remain blocked; it must not bypass the prerequisite.

This distinction also improves observability: a paused workflow answers "we chose not to continue yet," while a blocked workflow answers "we are not allowed or able to continue yet, and here is what must change."

## Human decision semantics

The application layer owns the human decision boundary.

Required operations conceptually include:

```text
specification.start
specification.inspect
specification.revise
specification.accept
specification.reject
specification.pause
specification.resume
specification.cancel
```

`specification.pause` is an explicit lifecycle operation because pausing is a deliberate operator/policy action. `blocked` is instead a durable application-owned state caused by typed unmet prerequisites, so this RFC does **not** define arbitrary `specification.block` / `specification.unblock` commands as equivalent user actions.

Acceptance records the authorized Actor and exact revision identity. Reject records the rejected revision and optional reason without mutating it into an accepted artifact. Cancellation terminates the execution without promoting a candidate. Ambiguity or conflicting authoritative sources produce clarification/escalation or a typed blocked state rather than a model-selected product decision.

A later revision after acceptance supersedes through another explicit human-controlled action; downstream runs keep the exact accepted revision they were admitted against for provenance and reproducibility.

Tactician recommendation is not one of these authority-changing operations. A recommendation to enter Specification becomes consequential only when the human chooses an admitted workflow and Battalion application policy starts it.

## Specifier role contract

If retained, Specifier's contract is intentionally narrower than the Specification workflow.

### Inputs

- operator-provided intent/work item;
- bounded governing specification/product evidence;
- relevant repository/project map evidence when available;
- prior accepted specification revision when revising;
- admitted recipe constraints and unresolved questions;
- Tactician assessment when it was part of admission evidence;
- explicit human constraints and decisions.

### Outputs

- candidate specification content;
- surfaced ambiguities and conflicting-source findings;
- unresolved product decisions requiring human input;
- evidence/provenance references;
- bounded rationale sufficient for inspection without provider-private chain of thought.

### Write scope

Specifier may write only workflow-owned candidate artifacts through Battalion application operations. It does not write implementation source, ADRs, accepted architecture, backlog/provider state, or accepted specification state directly.

### Tools

Read-only access should be limited to admitted evidence/query surfaces. Any provider or WorkSource mutation remains outside the role and behind separately authorized application operations.

### Model policy and context budget

Model selection and context limits must be explicit recipe/config policy and recorded as execution evidence. Specifier should receive only bounded evidence relevant to product intent and constraints rather than unrestricted repository context.

### Failure behavior

Missing authority, contradictory authoritative sources, insufficient evidence, context exhaustion, invalid structured output, or inability to make a candidate testable must fail closed into clarification/escalation, `blocked`, or `failed` according to the typed cause. They are not permission to guess.

Specifier may surface evidence that the current workflow is inadequate, but it does not directly switch workflows or clear blockers. The resulting trigger returns to Battalion's admitted failure/escalation/application boundary for deterministic handling, Tactician assessment when semantically necessary, and human choice.

## Relationship to Architect

Specifier answers **what/why and unresolved product intent**. Architect answers **architectural intent and system design**.

An accepted specification may require Architect through workflow admission. When Architect is required, the Architect receives the exact accepted specification revision plus admitted architecture/repository evidence. Specifier must not pre-decide architecture simply to make its candidate look complete.

If specification work discovers that a requested outcome cannot be stated without choosing architecture, it should surface the dependency rather than choose silently. The Specification execution may become blocked on that dependency; the human may then admit an Architect/Architecture workflow as the appropriate next workflow and return the durable decision to Specification as governing evidence. Battalion re-evaluates the blocker before Specification resumes.

This is another example of the same general orchestration rule: semantic roles report what is needed; registered workflow policy plus human authority decide the transition.

## Evidence and evaluation

BTN-101 owns the disposable workflow comparison/evidence spike. RFC acceptance should use representative work to compare at least:

- human/existing-spec baseline;
- a lightweight Battalion-assisted path;
- a deeper interrogation + synthesis path.

Useful measures include:

- operator correction count and time;
- unresolved-decision visibility before acceptance;
- missed or invented acceptance criteria;
- provenance completeness;
- unnecessary ceremony/model calls;
- rework caused by misunderstood intent;
- frequency and correctness of upgrade/escalation triggers;
- whether Tactician recommendations correctly distinguish "needs Specification" from "spec is adequate but implementation needs full handling";
- whether obviously adequate or obviously inadequate intent can be handled deterministically without unnecessary Tactician calls;
- whether paused and blocked executions are classified distinctly and whether blocked executions resume only after their prerequisites are actually satisfied.

Provider-private reasoning is not acceptance evidence.

## Open questions

1. **Artifact persistence:** should the canonical accepted specification live as repository Markdown with Battalion metadata, project-local structured persistence with a Markdown projection, or a hybrid contract?
2. **Human edit semantics:** should edit-and-accept be one atomic application operation or always create a candidate revision followed by a distinct accept action?
3. **Revision lineage:** what exact relationship should exist between specification revision, WorkSource ticket revision, and downstream `WorkflowExecution`/Implementation Run identity?
4. **Generalized workflow admission:** how should RFC-0012's deterministic-first admission contract represent "Specification is the next workflow" alongside compact/full implementation recipes without collapsing intent adequacy and implementation risk into one scalar or one overloaded enum?
5. **Architectural question loop:** when Specifier discovers a question that requires architecture to answer, should Specification remain durably blocked around an admitted Architect/Architecture workflow, or end with an unresolved dependency that the human resolves before resuming/new revision?
6. **Existing authoritative specs:** when a WorkSource item already points to an adequate authoritative specification, should Battalion create a zero-model Specification execution recording adoption/validation, or bypass Specification workflow entirely and proceed directly to implementation admission?
7. **Shared lifecycle ownership:** which pause/block/failure fields belong on shared `WorkflowExecution` versus `SpecificationExecution`, while preserving typed workflow-specific blocker semantics?

## Initial recommendation

Proceed with **Option B: a separate Specification workflow** and retain Specifier as a bounded semantic role inside that workflow rather than a universal graph node.

Treat **Specification as one of the registered next workflows that deterministic admission or Tactician may recommend**. Tactician should be symmetric: it can identify opportunities to reduce ceremony, but it can also identify that the current evidence is not ready for implementation and recommend stronger preparatory work. In either direction, Tactician recommends; the human chooses; Battalion orchestrates.

Specification executions must also distinguish **pause from block**: pause is an intentional suspension of otherwise-valid work; block is a typed, durable unmet prerequisite that cannot be bypassed by an arbitrary resume/unblock action.

This aligns with existing Battalion architecture better than adding a pre-Architect implementation node: RFC-0008 already anticipates `SpecificationExecution`, RFC-0012 already owns deterministic-first workflow admission, Tactician uncertainty escalation, human workflow choice, and the upgrade ratchet, and RFC-0019 already expects an approved specification at the Architect boundary.

The remaining decisions are mostly artifact/authority mechanics and how generalized workflow admission represents transitions into and out of Specification, not whether Specifier should become an autonomous product owner or whether Tactician should become an autonomous orchestrator.
