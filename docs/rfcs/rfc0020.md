# RFC-0020 — Specification Workflow and Human Authority Boundary

**Status:** Draft  
**Date:** 2026-09-05  
**Ticket:** BTN-45  
**Author:** Architecture  
**Target:** BTN-M11 specification workflow  
**Related:** `philosophy.md`, `spec.md`, `docs/future/specifier-role.md`, BTN-25, BTN-26, BTN-29, BTN-101, RFC-0008, RFC-0012, RFC-0019

---

## Summary

Battalion needs a first-class way to turn incomplete product intent into an implementation-ready specification without allowing a model to silently acquire product or architectural authority.

The selected architecture is a **distinct Specification workflow**, sharing durable execution mechanics with other Battalion workflows while retaining specification-specific state, authority, artifacts, and human decisions. A Specifier role may participate in that workflow, but the role is not the admission authority, does not approve its own output, and is not inserted as a mandatory node in every Implementation Run.

The governing invariant is:

> **Ceremony may scale down; human authority does not.**

RFC-0012 already owns deterministic-first workflow admission, Tactician escalation for semantic uncertainty, explicit human workflow choice, and the upgrade-only ratchet. BTN-45 extends that architecture symmetrically: Tactician is not only useful when it recommends a simpler implementation recipe. When available evidence cannot establish that product intent is sufficiently authoritative for implementation, Tactician may recommend **Specification as the next step**. Battalion, not Tactician, performs the transition after the human admits it.

A generated specification is **evidence and a proposal until an authorized human explicitly accepts a particular candidate revision**. Acceptance creates the authoritative specification revision that downstream workflow admission and Architect planning may consume.

Specification state is canonically persisted in **project-local structured storage**. Human-readable Markdown is a generated projection. WorkSource mutations such as GitHub/Jira comments may additionally project Specification progress or accepted results outward, but they are provider-specific side effects behind Battalion application authority and are never the canonical specification store.

---

## Decision

Battalion adopts **Option B: a separate Specification workflow**.

Specifier is a bounded semantic role inside that workflow rather than a universal pre-Architect graph node. Specification may be recommended by deterministic policy or Tactician when current evidence is not sufficient to admit implementation. Existing authoritative specifications bypass Specification entirely, with Battalion recording the evidence and reason for the bypass.

The workflow produces candidate specification revisions. A human reviews the exact candidate; edits create a new candidate revision; acceptance is a distinct operation binding authority to the accepted revision identity.

---

## Problem

Battalion's implementation workflow currently assumes that a sufficiently authoritative specification already exists before execution begins. That is safe but incomplete: real work often begins as an operator request containing partial requirements, unstated constraints, unresolved decisions, and repository context that must be reconciled before Architect or Driver should act.

The Regiment provides useful prior art by separating specification from architecture: its Specifier facilitates the what/why conversation and produces a Brief, and human partners review that Brief before it becomes Architect input. Battalion preserves that authority boundary while fitting it into stronger persistence, provenance, workflow-admission, execution-evidence, and application-operation contracts.

The design must also avoid forcing every request through an artifact-heavy interview merely because Specification exists. RFC-0012 already established deterministic-first proportional workflow admission, explicit human workflow choice, and an upgrade-only ratchet. BTN-45 composes with that architecture rather than duplicating it.

---

## Existing architectural constraints

### Repository artifacts outrank conversation

Durable product intent must end as a project-owned specification artifact. Conversation, raw model reasoning, transient UI state, and provider comments cannot become the source of truth.

### Specification is not Implementation Run state

RFC-0008 already reserves a `SpecificationExecution`-like workflow-specific state under a shared `WorkflowExecution` abstraction. Specification state must not be added to `RunState` merely because implementation consumes its output later.

### Workflow admission and Tactician authority are already owned elsewhere

RFC-0012 owns deterministic admission evidence, registered workflow recipes, Tactician escalation for semantic uncertainty, explicit human choice, and the upgrade-only ratchet. BTN-45 extends meaningful next-step recommendations to include Specification; it does not give Tactician execution authority.

Tactician may recommend Specification when intent adequacy is semantically uncertain, just as it may recommend compact or full implementation handling when implementation admission is uncertain. Tactician does not directly invoke Specifier, start a workflow, approve a specification, construct an arbitrary graph, or override deterministic prohibitions.

### Architect receives an approved specification

RFC-0019 treats the Architect plan as repository-grounded architectural intent derived from an already admitted evidence package including the approved specification. Specifier must not silently move architectural choices into the specification simply to make it appear complete.

---

## Why not the alternatives?

### Keep specification authoring outside Battalion

Rejected as the primary architecture. It keeps the authority model simple but prevents Battalion from helping structure incomplete intent, preserving specification provenance/corrections, and recommending a Battalion-owned next step when intent is insufficient.

### Add Specifier as an Implementation Run graph phase

Rejected. It conflates producing authoritative product intent with executing implementation, pressures `RunState` into carrying specification lifecycle state, makes Specifier mandatory even when an authoritative specification exists, and prevents Specification from being a first-class next-step recommendation.

---

## Next-step admission

Workflow admission should not attempt to predict the entire future workflow. At each meaningful boundary it answers:

> **Given the authoritative evidence currently available, what is the next appropriate step?**

Conceptual outcomes include:

```text
START_SPECIFICATION
START_ARCHITECTURE
START_IMPLEMENTATION
CLARIFY_WITH_HUMAN
NO_WORK_REQUIRED
```

These are illustrative outcome semantics, not necessarily final enum names.

If the next step is implementation, RFC-0012 then governs the separate question of which registered implementation recipe is appropriate: compact, full, or semantic uncertainty requiring Tactician assessment.

This preserves two independent questions:

1. **Is product intent sufficiently authoritative to move forward?**
2. **Given authoritative intent, what execution handling is appropriate next?**

A technically simple task may require Specification because desired behavior is ambiguous, then qualify for compact implementation once the specification is accepted. A technically complex task may already have an excellent authoritative specification and bypass Specification while still requiring Architecture/full implementation handling.

Tactician participates only where deterministic evidence is insufficient. It recommends the next step; the human chooses; Battalion orchestrates.

## Specification persistence and projections

### Canonical persistence

The canonical specification lives in **project-local structured persistence** behind Battalion-owned contracts.

Conceptually:

```text
Specification
  specification_id
  project_id
  canonical_work_identity
  current_accepted_revision_id optional

SpecificationRevision
  revision_id
  specification_id
  status: candidate | accepted | rejected | superseded
  outcomes[]
  constraints[]
  non_goals[]
  acceptance_criteria[]
  unresolved_product_decisions[]
  governing_artifact_refs[]
  evidence_refs[]
  source/provenance
  producer execution/model/prompt/config provenance optional
  created_at
  accepted_by_actor_id optional
  accepted_at optional
```

Exact storage encoding remains an implementation concern behind the logical contract.

### Markdown projection

Battalion generates a human-readable Markdown projection from canonical structured state. The projection is inspectable and repository-friendly but is not independently authoritative from the revision identity it represents.

### WorkSource projection

Battalion may optionally project Specification events/results into WorkSource through separately authorized application operations, for example:

- GitHub issue comments indicating that Specification began;
- a comment linking or summarizing a candidate ready for review;
- a comment noting an accepted specification revision;
- a comment recording unresolved dependencies or next-step disposition.

These mutations are Battalion-owned integration behavior, **not Specifier tools**. They remain provider-independent at the domain boundary and use the existing WorkSource mutation architecture. Failure to post a provider comment must not invalidate canonical Specification persistence.

## Candidate revision and acceptance

Candidate creation and acceptance are separate operations.

```text
generate/edit
    |
    v
candidate revision N
    |
    v
human reviews exact N
    |
    +--> edit -> candidate revision N+1
    |
    +--> accept N -> authoritative accepted revision
```

Any edit creates a new candidate identity. Acceptance therefore cannot silently include an edit. The authorized human accepts an exact revision that can be durably referenced downstream.

A model-produced candidate never becomes authoritative merely because generation succeeded.

---

## Work identity and revision lineage

Battalion separates **stable work identity** from **source snapshots** and **specification revisions**.

Conceptually:

```text
canonical work identity
   |
   +--> WorkSource evidence/snapshot used at specification time
   |
   +--> Specification
           |
           +--> revision 1
           +--> revision 2 [accepted]
                         |
                         +--> downstream WorkflowExecution
                               accepted_spec_revision_id = revision 2
```

The WorkSource item remains the stable external work identity when one exists. `SpecificationRevision` is Battalion's exact authoritative product-intent snapshot. External provider revision semantics are evidence, not Battalion's specification version model.

Downstream Architecture/Implementation executions bind to the **exact accepted specification revision**, not merely to the ticket or logical specification ID.

If the WorkSource item changes afterward, Battalion does not reinterpret historical executions. It may detect source drift and require re-admission, clarification, or a new specification revision depending on materiality.

---

## Existing authoritative specification bypass

When admission evidence already establishes an adequate authoritative specification, Battalion bypasses Specification entirely.

It should record why, for example:

```text
next_step: START_IMPLEMENTATION
specification_bypass:
  reason: authoritative_specification_already_available
  evidence_ref: ...
```

Battalion should **not** create a zero-model `SpecificationExecution` merely to record that no specification work was necessary. The admission evidence is sufficient provenance.

## Proportional ceremony

Specification recipes may vary in interview depth, evidence gathering, artifact detail, and whether semantic model assistance is needed, but all paths preserve explicit human authority where product/design intent is being established.

Representative shapes include:

- **Exploratory/spike work:** narrow question, constraints, non-goals, expected evidence, and a human-approved boundary preventing the spike from silently becoming production design.
- **Bounded change to an understood flow:** lightweight clarification of desired behavior and acceptance criteria using existing accepted architecture/repository evidence.
- **Architectural/new-subsystem work:** deeper specification work surfacing unresolved product decisions, cross-system constraints, interfaces, and operational concerns.

These are examples, not mandatory Battalion enums.

Tactician may recommend that Specification is the next step without owning the choice of specification recipe. Deterministic policy should handle obvious cases without an unnecessary model call.

### Upgrade-only ratchet

New evidence may force stronger handling. Cross-system impact, interface/schema changes, architectural consequence, conflicting authoritative sources, missing product authority, or hidden scope may trigger a stronger recipe, a different next-step recommendation, `needs_resolution`, blocking, or cancellation.

Work may not silently continue under a lighter admission merely because execution has already begun.

## Specification execution lifecycle

Specification distinguishes generic execution mechanics from workflow-specific semantic phase/outcome.

### Shared `WorkflowExecution` mechanics

Conceptually:

```text
WorkflowExecution
  execution_id
  workflow_kind
  status:
    requested
    running
    paused
    blocked
    completed
    failed
    cancelled
  pause/block/failure evidence
  worker/model/cost/provenance evidence
```

This layer answers **whether execution can currently proceed**.

### `SpecificationExecution` semantics

Conceptually:

```text
SpecificationExecution
  execution_id
  phase:
    inspecting
    synthesizing
    awaiting_human
  candidate_revision_id optional
  outcome:
    accepted
    rejected
    needs_resolution
  unresolved_dependencies[]
```

Exact fields/state names may change during implementation, but the separation is normative: generic execution state should not acquire Specification-only concepts such as `awaiting_specification_acceptance`.

### Paused

`paused` means the execution could otherwise continue, but an authorized operator or admitted policy intentionally suspended it. Resume may return to the prior resumable state subject to normal authorization and stale-state checks.

### Blocked

`blocked` means the **same execution is expected to continue** but cannot validly do so until a temporary prerequisite changes, such as:

- missing external/project evidence expected to arrive;
- temporary authorization/policy prerequisite;
- resource/worker dependency;
- another transient dependency whose resolution permits the current execution to continue.

Blocked state carries typed durable evidence. A generic shared record may conceptually contain:

```text
WorkflowBlock
  block_id
  reason_code
  description
  evidence_refs[]
  dependency_ref optional
  required_resolution_kind
  created_at
  resolved_at optional
  resolution_evidence_refs[]
```

There is no arbitrary "clear blocked" operation. The owning prerequisite is resolved and Battalion deterministically re-evaluates the execution.

### `needs_resolution`

`needs_resolution` is **not** the same as blocked.

When Specifier reaches a legitimate semantic boundary that requires a product or architectural decision outside its authority, that Specification attempt ends with a typed `needs_resolution` outcome and durable unresolved dependencies.

Examples include:

- an architectural choice is required before the product requirement can be made precise;
- authoritative product sources conflict and require human judgment;
- a product decision remains genuinely undecided;
- resolution requires work by another role/workflow rather than merely waiting for a transient prerequisite.

The human may then:

- resolve the issue directly and begin/revisit Specification with the durable decision;
- ask Architect/Architecture for suggestions or a durable architectural decision;
- change/cancel the requested work;
- take another admitted next step.

The completed `needs_resolution` Specification execution is preserved as evidence. Battalion does not hold it blocked indefinitely around another workflow.

This distinction yields:

> **paused** — we chose not to continue yet.  
> **blocked** — this same execution can continue once a temporary prerequisite clears.  
> **needs_resolution** — this Specification attempt has reached its authority boundary and ended with work that must be resolved elsewhere.

## Human decision semantics

The application layer owns the human decision boundary.

Required operations conceptually include:

```text
specification.start
specification.inspect
specification.revise
specification.accept
specification.reject
specification.pause
specification.resume
specification.cancel
```

`specification.pause` is explicit. Blocked state is application-owned and prerequisite-driven, so no arbitrary `specification.block` / `specification.unblock` operations are defined.

Acceptance records the authorized Actor and exact candidate revision. Reject records the rejected revision and optional reason without promoting it. Cancellation terminates the execution without promoting a candidate.

Tactician recommendations are not authority-changing operations. They become consequential only when the human chooses an admitted next step and Battalion application policy starts it.

## Specifier role contract

Specifier's contract is narrower than the Specification workflow.

### Inputs

- operator-provided intent/work item;
- bounded governing product/specification evidence;
- relevant repository/project-map evidence when available;
- prior accepted specification revision when revising;
- admitted recipe constraints and unresolved questions;
- Tactician assessment when part of admission evidence;
- explicit human constraints and decisions.

### Outputs

- candidate specification content;
- surfaced ambiguities and conflicting-source findings;
- unresolved product decisions requiring human input;
- unresolved dependencies when another authority/workflow is required;
- evidence/provenance references;
- bounded rationale sufficient for inspection without provider-private reasoning.

### Write scope

Specifier may write only workflow-owned candidate artifacts through Battalion application operations. It does not write implementation source, ADRs, accepted architecture, WorkSource/provider state, or accepted specification state directly.

### Tools

Read-only access is limited to admitted evidence/query surfaces. WorkSource mutation remains outside the role and behind separately authorized Battalion operations.

### Model policy and context budget

Model selection and context limits are explicit recipe/config policy and recorded as execution evidence. Specifier receives bounded evidence relevant to product intent and constraints rather than unrestricted repository context.

### Failure and boundary behavior

Missing authority, contradictory authoritative sources, insufficient evidence, context exhaustion, invalid structured output, or inability to make a candidate testable must fail closed into clarification, `blocked`, `needs_resolution`, or `failed` according to typed cause.

Specifier may report that another next step is required, but it does not switch workflows itself.

---

## Relationship to Architect

Specifier answers **what/why and unresolved product intent**. Architect answers **architectural intent and system design**.

An accepted specification may require Architecture as the next step. When Architect is required, it receives the exact accepted specification revision plus admitted architecture/repository evidence.

If Specifier discovers that the specification cannot be completed without an architectural choice, it ends with `needs_resolution` and records that dependency. The human may resolve it directly where authorized or say, in effect, **"pass this to Architect for suggestions/resolution."** Architecture remains a separate admitted step. A later Specification attempt can consume the durable architectural result as governing evidence.

Specifier does not suspend itself around Architect and does not pre-decide architecture simply to finish its own artifact.

## WorkSource integration

Specification may produce user-visible external updates through Battalion's WorkSource mutation boundary without granting mutation tools to Specifier.

Examples:

```text
SpecificationExecution
      |
      +--> canonical project-local state
      +--> Markdown projection
      +--> Battalion application operation
               |
               +--> WorkSource adapter
                        |
                        +--> GitHub/Jira comment
```

Such comments are useful collaboration/audit surfaces but remain non-authoritative projections. Provider failure, deletion, editing, or unsupported comment capabilities do not alter canonical Specification state.

## Evidence and evaluation

BTN-101 owns the disposable workflow comparison/evidence spike. RFC acceptance should compare at least:

- human/existing-spec baseline;
- a lightweight Battalion-assisted path;
- a deeper interrogation + synthesis path.

Useful measures include:

- operator correction count/time;
- unresolved-decision visibility before acceptance;
- missed or invented acceptance criteria;
- provenance completeness;
- unnecessary ceremony/model calls;
- rework caused by misunderstood intent;
- correctness of next-step/Tactician recommendations;
- deterministic handling of obviously sufficient/insufficient intent;
- distinction among paused, blocked, and `needs_resolution` outcomes;
- exact accepted-revision binding downstream;
- source-drift detection without reinterpretation of historical executions.

Provider-private reasoning is not acceptance evidence.

## Resolved architecture questions

1. **Artifact persistence:** project-local structured canonical persistence with generated Markdown projection. Optional WorkSource comments are non-authoritative external projections through Battalion-owned mutation operations.
2. **Human edit semantics:** editing produces a candidate revision; acceptance is a separate operation against an exact candidate revision.
3. **Revision lineage:** stable work identity remains distinct from provider/source snapshots and Battalion specification revisions. Downstream executions bind to the exact accepted specification revision; later WorkSource drift does not reinterpret history.
4. **Workflow admission:** admission asks **what is the next appropriate step now?** Specification is one possible next step, not an entire precomputed workflow. Implementation recipe admission remains a subsequent question.
5. **Architectural dependency:** Specification ends with `needs_resolution` rather than remaining blocked around Architecture. The human may resolve the dependency or admit Architecture/Architect for suggestions/resolution, then revisit Specification if needed.
6. **Existing authoritative specifications:** bypass Specification entirely and record the bypass reason/evidence; do not manufacture a zero-model Specification execution.
7. **Lifecycle ownership:** reusable execution mechanics (`running`, `paused`, `blocked`, `failed`, etc.) belong to shared `WorkflowExecution`; specification-specific phase/outcome (`inspecting`, `awaiting_human`, `accepted`, `needs_resolution`, unresolved dependencies) belongs to `SpecificationExecution`.

Acceptance of this RFC should create separate implementation tickets for at least:

- application operations and Actor authorization for review/accept/reject/pause/resume/cancel;
- generalized deterministic next-step admission including Specification and Tactician recommendation semantics;
- specification recipes and upgrade triggers;
- Specifier prompt/contract/model/context policy;
- exact accepted-revision binding into Architecture/Implementation executions and source-drift handling;
- optional WorkSource projection/comment operations through existing mutation authority;
- CLI/desktop inspection/revision/acceptance/lifecycle/blocker/unresolved-dependency surfaces;
- evaluation/regression coverage;
- required `spec.md`, ADR, and user-facing documentation updates.
