# RFC-0020 — Specification Workflow and Human Authority Boundary

**Status:** Draft  
**Date:** 2026-09-05  
**Ticket:** BTN-45  
**Author:** Architecture  
**Target:** BTN-M11 specification workflow  
**Related:** `philosophy.md`, `spec.md`, `docs/future/specifier-role.md`, BTN-25, BTN-26, BTN-29, BTN-101, RFC-0008, RFC-0012, RFC-0019

---

## Summary

Battalion needs a first-class way to turn incomplete product intent into an implementation-ready specification without allowing a model to silently acquire product or architectural authority.

The leading architecture is a **distinct Specification workflow**, sharing durable execution mechanics with other Battalion workflows but retaining specification-specific state, authority, artifacts, and human decisions. A Specifier role may participate in that workflow, but the role is not the admission authority, does not approve its own output, and is not inserted as a mandatory node in every Implementation Run.

The governing invariant is:

> **Ceremony may scale down; human authority does not.**

RFC-0012 already owns workflow admission and proportional execution. BTN-45 should therefore avoid creating a second complexity router inside Specifier. Specification can itself use registered, versioned workflow recipes with lighter or heavier evidence/artifact requirements, but known risk and newly discovered ambiguity can only ratchet work toward stronger specification/architecture handling.

A generated specification is **evidence and a proposal until an authorized human explicitly accepts a particular revision**. Acceptance creates the authoritative specification revision that downstream workflow admission and Architect planning may consume.

This RFC is planning only. It does not authorize a Specifier prompt, node, graph change, persistence schema, or UI implementation.

---

## Problem

Battalion's implementation workflow currently assumes that a sufficiently authoritative specification already exists before execution begins. That is safe but incomplete: real work often begins as an operator request containing partial requirements, unstated constraints, unresolved decisions, and repository context that must be reconciled before Architect or Driver should act.

The Regiment provides useful prior art by separating specification from architecture: its Specifier facilitates the what/why conversation and produces a Brief, and human partners review that Brief before it becomes Architect input. Battalion should preserve that authority boundary while fitting it into Battalion's stronger persistence, provenance, workflow-admission, execution-evidence, and application-operation contracts.

The design must also avoid a different failure mode: forcing every request through an artifact-heavy interview merely because Specification exists. RFC-0012 already established deterministic-first proportional workflow admission, explicit human workflow choice, and an upgrade-only ratchet. BTN-45 must compose with that architecture rather than duplicate it.

---

## Existing architectural constraints

### Repository artifacts outrank conversation

Durable product intent must end as a repository- or project-owned specification artifact. Conversation, raw model reasoning, and transient UI state cannot become the source of truth.

### Specification is not Implementation Run state

RFC-0008 already reserves a `SpecificationExecution`-like workflow-specific state under a shared `WorkflowExecution` abstraction. Specification state must not be added to `RunState` merely because implementation consumes its output later.

### Workflow admission is already owned elsewhere

RFC-0012 owns deterministic admission evidence, registered workflow recipes, Tactician escalation for semantic uncertainty, explicit human choice, and the upgrade-only ratchet. Specifier therefore must not become a universal router or a second task-complexity classifier.

### Architect receives an approved specification

RFC-0019 treats the Architect plan as repository-grounded architectural intent derived from an already admitted evidence package including the approved specification. BTN-45 must stop before silently moving architectural choices into Specifier.

## Options

### Option A — Keep specification authoring outside Battalion

Humans or external tools produce authoritative specifications; Battalion continues to begin only after one exists.

**Advantages**

- smallest Battalion surface;
- simplest authority model;
- no new workflow state or human review UI.

**Costs**

- Battalion cannot help structure incomplete intent;
- specification provenance and correction evidence remain fragmented;
- no reusable workflow for projects whose starting point is conversational or incomplete requirements;
- misses the opportunity to reduce mechanical requirements work while preserving human ownership.

### Option B — Separate Specification workflow

A `SpecificationExecution` converts bounded intent/evidence into one or more candidate specification revisions. An authorized human reviews, edits, accepts, rejects, or cancels. Only an accepted revision becomes authoritative input for implementation admission and Architect planning.

**Advantages**

- keeps product-intent authority separate from implementation execution;
- matches the shared-workflow direction established by RFC-0008;
- allows durable provenance, model/cost evidence, revision history, interrupts, resume, and cancellation;
- can support proportional specification recipes without making Specifier universal;
- cleanly supports future non-model/manual or alternate specification producers.

**Costs**

- introduces workflow-specific persistence and application operations;
- requires explicit artifact identity/versioning and acceptance semantics;
- requires UI/CLI surfaces beyond the current Implementation Run.

### Option C — Add Specifier as an Implementation Run graph phase

Insert Specifier before Architect in the implementation graph.

**Advantages**

- superficially simple linear lifecycle;
- easy handoff from specification to architecture.

**Costs**

- conflates producing authoritative product intent with executing implementation;
- pressures `RunState` into carrying specification lifecycle state;
- makes Specifier mandatory even when an authoritative specification already exists;
- complicates re-specification, rejection, cancellation, and reuse of accepted specifications;
- duplicates workflow-admission concerns already separated in RFC-0012.

**Initial assessment:** reject as the default architecture.

## Proposed architecture

```text
human intent / existing work item / governing artifacts
                    |
                    v
          Specification workflow intake
                    |
                    v
      admitted specification recipe
       /            |             \
  lightweight    standard       deep
       \            |             /
                    v
        candidate specification revision
                    |
                    v
           explicit human decision
        /          |          |        \
      edit       accept     reject    cancel
       |            |
       +----> new candidate   v
                         accepted specification
                                |
                                v
                    implementation admission
                                |
                      Architect when required
```

`Specifier` is one semantic producer inside Specification workflow recipes. It does not own admission policy, artifact authority, acceptance, architecture, implementation, or backlog mutation.

---

## Specification artifact

The canonical artifact should have a stable identity plus immutable accepted revisions. Exact encoding remains open until existing persistence conventions are reconciled, but the logical contract should include at least:

```text
Specification
  specification_id
  project_id
  canonical_work_identity
  current_accepted_revision_id optional

SpecificationRevision
  revision_id
  specification_id
  status: candidate | accepted | rejected | superseded
  outcomes[]
  constraints[]
  non_goals[]
  acceptance_criteria[]
  unresolved_product_decisions[]
  governing_artifact_refs[]
  evidence_refs[]
  source/provenance
  producer execution/model/prompt/config provenance optional
  created_at
  accepted_by_actor_id optional
  accepted_at optional
```

The human-readable specification may remain Markdown, but authority belongs to the admitted revision identity and durable decision record, not to whichever text happens to be visible in a chat window.

### Candidate versus accepted authority

A model-produced revision is never authoritative merely because generation completed successfully. It remains a candidate until an authorized human explicitly accepts that exact revision.

Editing a candidate creates a new revision or otherwise changes its exact candidate identity before acceptance. Acceptance must bind to the reviewed revision rather than a mutable logical specification name.

### Ticket relationship

A specification must preserve canonical work identity rather than silently minting a parallel backlog identity. The specification may be linked to a WorkSource ticket or other work item; whether acceptance can create or update that ticket is a separate application operation governed by BTN-134-style WorkSource authority and must not be an implicit side effect of Specifier generation.

## Proportional ceremony

BTN-45 adopts RFC-0012's principle rather than inventing its own complexity score.

Specification recipes may vary in interview depth, evidence gathering, artifact detail, and whether semantic model assistance is needed, but all paths preserve explicit human authority where product/design intent is being established.

Representative shapes:

- **Exploratory/spike work:** a deliberately narrow question, constraints, non-goals, evidence expected, and a human-approved boundary preventing the spike from silently becoming production design.
- **Bounded change to an understood flow:** lightweight clarification of desired behavior and acceptance criteria, relying on existing accepted architecture and repository evidence.
- **Architectural/new-subsystem work:** deeper specification work surfacing unresolved product decisions, cross-system constraints, interfaces, operational concerns, and explicit Architect handoff.

These are examples, not mandatory Battalion domain enums.

### Upgrade-only ratchet

Once a lighter specification recipe begins, newly discovered evidence may require stronger handling. Cross-system impact, interface/schema change, architectural consequence, conflicting authoritative sources, missing product authority, or hidden scope may trigger escalation to a stronger recipe, Architect involvement, clarification, or cancellation.

A Specification workflow may not downgrade itself merely to avoid an interrupt, artifact, or authority boundary required by newly discovered evidence.

## Human decision semantics

The application layer owns the human decision boundary.

Required operations conceptually include:

```text
specification.start
specification.inspect
specification.revise
specification.accept
specification.reject
specification.cancel
specification.resume
```

Acceptance records the authorized Actor and exact revision identity. Reject records the rejected revision and optional reason without mutating it into an accepted artifact. Cancellation terminates the execution without promoting a candidate. Ambiguity or conflicting authoritative sources produce clarification/escalation rather than a model-selected product decision.

A later revision after acceptance supersedes through another explicit human-controlled action; downstream runs keep the exact accepted revision they were admitted against for provenance and reproducibility.

## Specifier role contract

If retained, Specifier's contract is intentionally narrower than the Specification workflow.

### Inputs

- operator-provided intent/work item;
- bounded governing specification/product evidence;
- relevant repository/project map evidence when available;
- prior accepted specification revision when revising;
- admitted recipe constraints and unresolved questions;
- explicit human constraints and decisions.

### Outputs

- candidate specification content;
- surfaced ambiguities and conflicting-source findings;
- unresolved product decisions requiring human input;
- evidence/provenance references;
- bounded rationale sufficient for inspection without provider-private chain of thought.

### Write scope

Specifier may write only workflow-owned candidate artifacts through Battalion application operations. It does not write implementation source, ADRs, accepted architecture, backlog/provider state, or accepted specification state directly.

### Tools

Read-only access should be limited to admitted evidence/query surfaces. Any provider or WorkSource mutation remains outside the role and behind separately authorized application operations.

### Model policy and context budget

Model selection and context limits must be explicit recipe/config policy and recorded as execution evidence. Specifier should receive only bounded evidence relevant to product intent and constraints rather than unrestricted repository context.

### Failure behavior

Missing authority, contradictory authoritative sources, insufficient evidence, context exhaustion, invalid structured output, or inability to make a candidate testable must fail closed into clarification/escalation. They are not permission to guess.

## Relationship to Architect

Specifier answers **what/why and unresolved product intent**. Architect answers **architectural intent and system design**.

An accepted specification may require Architect through workflow admission. When Architect is required, the Architect receives the exact accepted specification revision plus admitted architecture/repository evidence. Specifier must not pre-decide architecture simply to make its candidate look complete.

If specification work discovers that a requested outcome cannot be stated without choosing architecture, it should surface the dependency rather than choose silently. The human may then route the question through Architect and return the durable decision to Specification as governing evidence.

## Evidence and evaluation

BTN-101 owns the disposable workflow comparison/evidence spike. RFC acceptance should use representative work to compare at least:

- human/existing-spec baseline;
- a lightweight Battalion-assisted path;
- a deeper interrogation + synthesis path.

Useful measures include:

- operator correction count and time;
- unresolved-decision visibility before acceptance;
- missed or invented acceptance criteria;
- provenance completeness;
- unnecessary ceremony/model calls;
- rework caused by misunderstood intent;
- frequency and correctness of upgrade/escalation triggers.

Provider-private reasoning is not acceptance evidence.

## Open questions

1. **Artifact persistence:** should the canonical accepted specification live as repository Markdown with Battalion metadata, project-local structured persistence with a Markdown projection, or a hybrid contract?
2. **Human edit semantics:** should edit-and-accept be one atomic application operation or always create a candidate revision followed by a distinct accept action?
3. **Revision lineage:** what exact relationship should exist between specification revision, WorkSource ticket revision, and downstream `WorkflowExecution`/Implementation Run identity?
4. **Specification recipe admission:** can existing RFC-0012 admission policy be generalized directly to `workflow_kind=specification`, or does Specification need a subordinate deterministic policy with the same governing primitives?
5. **Architectural question loop:** when Specifier discovers a question that requires architecture to answer, should Specification suspend around an Architect workflow/execution, or end with an unresolved dependency that the human resolves before resuming/new revision?
6. **Existing authoritative specs:** when a WorkSource item already points to an adequate authoritative specification, should Battalion create a zero-model Specification execution recording adoption/validation, or bypass Specification workflow entirely and proceed directly to implementation admission?

---

## Initial recommendation

Proceed with **Option B: a separate Specification workflow** and retain Specifier as a bounded semantic role inside that workflow rather than a universal graph node.

This aligns with existing Battalion architecture better than adding a pre-Architect implementation node: RFC-0008 already anticipates `SpecificationExecution`, RFC-0012 already owns workflow admission and the upgrade ratchet, and RFC-0019 already expects an approved specification at the Architect boundary.

The remaining decisions are mostly artifact/authority mechanics and how Specification composes with existing workflow infrastructure, not whether Specifier should become an autonomous product owner.
