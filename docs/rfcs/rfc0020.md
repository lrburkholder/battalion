# RFC-0020 — Governed Environment and Integration Validation

**Status:** Draft  
**Date:** 2026-09-04  
**Ticket:** BTN-198  
**Author:** Architecture  
**Target:** Environment/integration validation architecture  
**Related:** `philosophy.md`, RFC-0013, RFC-0015, RFC-0018, RFC-0019, ADR-0039, BTN-131, BTN-138, BTN-139, BTN-140, BTN-141, BTN-142, BTN-143, BTN-192

---

## Summary

Battalion should treat **real execution environments as governed resources**, not as ambient places where a model is free to run tests.

The proposed direction is a provider-neutral, versioned **Environment Validation contract family** that workflow recipes can require, specialize, or omit. Environment execution should normally be performed by deterministic tooling behind Battalion-owned admission, capability, side-effect, credential, cost, evidence, and cleanup boundaries. Models may help design scenarios, interpret bounded evidence, and diagnose failures, but should not receive broad ambient cloud/staging/production authority merely because validation is required.

The central architectural shape is:

```text
approved requirement / architecture
        ↓
validation obligation(s)
        ↓
workflow recipe selects environment-validation step/subgraph
        ↓
environment admission
  - exact environment identity
  - bounded capabilities
  - credential references
  - scope constraints
  - cost authorization
  - approval policy
        ↓
deterministic provision/deploy/execute/observe/cleanup
        ↓
versioned validation evidence
        ↓
typed outcome + failure classification
        ↓
workflow routing
  Driver / Debugger / Deployer / human authority / acceptance
```

This RFC does **not** assume Battalion needs an "Integration Tester" model role. The default design should be a reusable deterministic validation capability/subgraph that can be consumed by implementation, deployment, operational-validation, or other recipes. A model-backed role should be introduced only if a responsibility remains that cannot be expressed safely as deterministic execution plus existing planning/diagnostic roles.

Automated environment validation remains distinct from Human QA/UAT. It can supply stronger evidence to human acceptance, but it does not silently replace an acceptance boundary that a workflow requires.

---

## Problem

Battalion has increasingly strong contracts for code-local implementation and review, explicit workflow admission, durable side-effect evidence, bounded tool authority, and human decision boundaries. The current architecture is much weaker once validation crosses the repository/process boundary into a real environment.

"Run the integration tests" can mean all of the following:

- start a local database or disposable container;
- deploy a candidate into a shared staging namespace;
- authenticate to AWS, Azure, GCP, Kubernetes, or another infrastructure provider;
- provision billable resources;
- mutate shared or externally visible state;
- consume quotas or rate limits;
- invoke third-party systems;
- observe behavior that cannot be reproduced with a unit test;
- retain diagnostics long enough for debugging;
- delete resources and restore externally visible state afterward.

Those actions are not simply test mechanics. They are governed side effects with authorization, financial, security, lifecycle, and evidence consequences.

Without a first-class contract, Battalion risks one of two bad extremes:

1. **ambient authority** — a model or generic Driver process receives broad credentials and environment access, turning a test request into unconstrained external authority; or
2. **manual-only validation** — Battalion avoids the risk by stopping at code-local tests and leaving integration behavior to ad hoc human execution, losing automation, repeatability, provenance, and machine-usable evidence.

Neither is consistent with Battalion's goals. Mechanical work should be automated, but authority and acceptance should remain explicit.

---

## Goals

- define a provider-neutral, versioned environment identity and capability model;
- make environment authority explicit, bounded, inspectable, and revocable;
- prevent durable Battalion state from containing secret material;
- prefer deterministic credential use and environment actions over exposing credentials to models;
- connect provisioning, deployment, mutation, deletion, and cleanup to Battalion's side-effect ledger rather than treating them as implicit test behavior;
- separate monetary authorization from cost observation/accounting;
- make unknown cost explicit rather than coercing it to zero;
- define validation obligations that trace from accepted requirements/architecture to runtime evidence;
- make exact candidate/artifact identity and exact environment identity part of validation evidence;
- distinguish product/behavior failures from infrastructure, authorization, cost-policy, and cleanup failures;
- make cleanup/retention part of completion semantics;
- support low-risk disposable local integration testing without unnecessary human interruption;
- retain stronger human authority for production, destructive, costly, or otherwise material actions;
- allow workflow recipes to require, specialize, or omit environment validation;
- preserve Human QA/UAT as a distinct acceptance boundary where required;
- avoid inventing a model role when deterministic capabilities are sufficient.

## Non-goals

- defining provider-specific AWS/Azure/GCP APIs in the core Battalion contract;
- making every workflow perform environment validation;
- replacing unit/component testing or Driver RED/GREEN contracts;
- replacing Human QA/UAT;
- giving models direct shell/cloud access as the default integration mechanism;
- storing cloud/API secrets in Run state or evidence artifacts;
- creating a generalized cloud-management product;
- guaranteeing exact real-time cloud billing data before providers make it observable;
- proving that an external environment is truthful or uncompromised;
- requiring provisioning and validation to execute in one Run or process;
- assuming every integration failure is a product bug.

---

## Design principle: environment authority belongs to Battalion, not the model

The model may request or recommend a semantically named operation such as:

```text
validate candidate X using scenario Y in admitted environment Z
```

It should not, by default, receive the raw mechanism needed to turn that sentence into arbitrary cloud or staging actions.

Battalion owns the deterministic boundary that resolves:

- whether environment `Z` is admitted;
- which exact environment instance/revision is meant;
- which capabilities are allowed;
- which credential reference may be exercised;
- which account/project/subscription, region, namespace, endpoint, network boundary, and resource classes are in scope;
- how long authority lasts;
- what quota/rate/resource limits apply;
- what spend is authorized;
- what approval is required;
- how actions are written to the side-effect ledger;
- what evidence must be retained;
- what cleanup/retention disposition is mandatory.

A deterministic adapter may internally use credentials that the model never sees. If a provider integration genuinely requires model-visible secret material, that is an exceptional capability requiring explicit justification and policy rather than the default shape.

## Environment identity model

Battalion should define a versioned `EnvironmentDescriptor`-style contract. The exact implementation type is deferred, but the semantic fields should cover at least:

```text
EnvironmentDescriptor
  schema_version
  environment_id
  environment_revision
  class
    local_ephemeral
    shared_staging
    production_like
    production
  provider_kind
  binding_ref
  scope
    account_project_subscription?
    region_zone?
    namespace?
    endpoint_network_boundary?
    allowed_resource_classes[]?
  lifecycle
    disposable | retained | shared
    max_runtime?
    retention_policy?
    cleanup_policy
  capabilities[]
  credential_refs[]
  quota_policy?
  cost_policy?
  approval_policy
```

`environment_id` is a stable Battalion/project identity. `environment_revision` identifies the particular configuration/binding revision admitted for execution. Runtime evidence should additionally record the exact resolved environment instance where that distinction matters (for example a generated namespace, container network, cluster, account/project, or deployment slot).

The four minimum environment classes express risk posture, not provider technology:

- **local_ephemeral** — disposable process/container/database resources owned by the validation execution;
- **shared_staging** — a non-production environment shared across work or users, where collisions and persistent mutation matter;
- **production_like** — isolated or specially controlled infrastructure intended to approximate production semantics and potentially carry meaningful cost;
- **production** — live environment with direct user/business/operational impact.

Projects may define more specialized classes, but they should map to policy behavior rather than merely labels.

## Capability model

Environment access should be a bounded capability set rather than a single `can_use_environment` flag.

The initial shared vocabulary should include at minimum:

- `read_observe`
- `deploy`
- `create_resource`
- `mutate_data`
- `delete_resource`
- `cleanup_teardown`

Capabilities may be further constrained by scope. For example:

```text
create_resource:
  resource_classes: [container_app, postgres_database]
  region: ca-central-1
  namespace_prefix: battalion-btn198-
  max_instances: 3
```

Possession of one capability does not imply another. In particular:

- `deploy` does not imply arbitrary data mutation;
- `create_resource` does not imply deletion outside resources created by the admitted operation;
- `cleanup_teardown` should normally be scoped to resources owned by or explicitly delegated to the validation execution;
- `read_observe` should still be bounded to admitted endpoints/resources rather than generic account-wide discovery.

Capabilities are authorization inputs, not model instructions. Free-form prose cannot widen them.

## Credential and secret delegation

Environment descriptors and Run state may contain **credential references**, never durable secret material.

A credential reference identifies an authorized resolver/binding such as:

```text
credential_ref: battalion://credentials/project-staging-deployer
```

Resolution happens only inside an admitted deterministic operation and should return the narrowest usable authority supported by the provider. Where possible Battalion/provider adapters should prefer short-lived, scoped, workload/federated credentials over long-lived static secrets.

Evidence may record:

- credential reference identity;
- resolver/provider identity;
- non-secret principal/account identity;
- scope granted;
- issue/expiry timestamps where available;

but never tokens, passwords, private keys, session cookies, or provider secret values.

---

## Cost authorization is not cost accounting

A validation execution may have both:

```text
CostAuthorization
  currency
  maximum_authorized_spend?
  estimated_spend?
  estimate_basis
  unknown_cost_policy

CostObservation
  observed_actual_spend?
  observed_estimate?
  provider_metering_ref?
  observation_time
  completeness
```

These answer different questions.

**Authorization** answers: "What financial exposure did the human/project policy permit before this operation?"

**Observation/accounting** answers: "What cost did the environment/provider later report or allow Battalion to estimate?"

The architecture must never encode unknown actual cost as `0`. `0` means observed/derived zero; unknown means unknown. A workflow may reject execution before side effects when estimated/unknown cost violates policy, and may separately fail or flag completion when observed cost exceeds authorization or cannot be reconciled according to policy.

## Validation obligations

Specifier/Architect requirements should become explicit, versioned **ValidationObligation** artifacts or contract entries rather than relying on a model to reinterpret prose at execution time.

Conceptually:

```text
ValidationObligation
  obligation_id
  source_requirement_refs[]
  candidate_scope
  scenario_ref
  required_environment_class
  required_capabilities[]
  observations[]
  success_contract
  cleanup_disposition
```

A scenario reference points to a deterministic/reviewable executable scenario definition owned by the project or an admitted provider/plugin. The model may help propose or author such a scenario during planning/implementation, but the admitted scenario revision becomes the executable policy boundary.

Free-form model prose is not authoritative execution policy.

This gives runtime evidence a traceable chain:

```text
requirement
  -> validation obligation
  -> admitted scenario revision
  -> candidate identity
  -> environment identity/revision
  -> execution evidence
  -> outcome
```

## Environment validation evidence contract

Every environment validation execution should produce a versioned evidence artifact with enough information to reproduce the authorization story and evaluate the result without exposing secrets.

Minimum semantics:

```text
EnvironmentValidationEvidence
  schema_version
  evidence_id
  run_id / workflow_execution_id
  obligation_ids[]
  candidate_identity
  artifact_identities[]
  scenario_identity
  environment_identity
  environment_revision
  resolved_instance_identity?
  admitted_capabilities[]
  credential_ref_identities[]
  authorization_decision_refs[]
  cost_authorization
  start_time
  end_time
  action_refs[]            # side-effect ledger identities
  bounded_observations[]
  assertion_outcome
  cleanup_disposition
  cost_observation?
  failure_classification?
  overall_outcome
```

Raw logs, traces, screenshots, provider diagnostics, or database snapshots may be attached as bounded evidence references rather than embedded into the canonical envelope. Existing Battalion data-handling/redaction policy remains applicable.

A passing assertion is only one dimension of success. `overall_outcome = success` requires all mandatory completion conditions, including authorization compliance and required cleanup/retention disposition.

## Failure taxonomy

At minimum, environment validation should distinguish:

### `behavioral_validation_failure`

The admitted scenario executed in a sufficiently healthy environment and the candidate failed a required behavior/observation.

Typical route: Driver for implementation correction, or Debugger where diagnosis is non-trivial.

### `environment_infrastructure_failure`

The environment could not provide the conditions necessary to evaluate the candidate: provisioning failure, unhealthy dependency, network outage, provider incident, exhausted shared infrastructure, etc.

Typical route: retry/recovery policy, Deployer/infrastructure owner, or human escalation depending on environment ownership.

### `authorization_failure`

Required capability, credential, scope, or approval was absent/expired/denied.

Typical route: admission/human authority or environment administrator. This is not a product red test.

### `cost_policy_failure`

Estimated, unknown, or observed cost violates the admitted financial policy.

Typical route: human/project policy authority. It must not be disguised as infrastructure failure or test failure.

### `cleanup_failure`

Behavioral validation may have passed, but required teardown/restoration/retention disposition did not complete or could not be verified.

Typical route: deterministic cleanup retry/reconciliation, Deployer/infrastructure owner, and potentially explicit human acknowledgement for retained hazardous/orphaned resources.

Additional provider-specific errors may exist beneath these categories, but workflow routing should not collapse them into one generic `failed` result.

---

## Cleanup and retention are completion semantics

Environment validation is not complete when the test assertion ends. It is complete when the environment reaches the admitted terminal disposition.

For a disposable local environment that may mean every owned container/network/database is removed. For shared staging it may mean test data is deleted and the deployment slot is restored. For a production-like environment it may mean resources are retained for 60 minutes for diagnostics and then deleted. For production it may mean no cleanup action is permitted beyond a narrowly defined rollback.

Cleanup itself is an external side effect and should use the same capability, ledger, idempotency, and reconciliation mechanisms as provisioning.

If validation passes but cleanup fails:

```text
assertion_outcome = passed
overall_outcome = failed
failure_classification = cleanup_failure
```

This prevents a successful assertion from hiding leaked billable resources or persistent shared-state damage.

## Approval policy by environment class

Approval is policy-driven rather than hard-coded solely by label, but the default expectations should be:

### Local/ephemeral

Pre-authorized execution may be autonomous when:

- resources are disposable and execution-owned;
- capabilities are bounded;
- no material external side effects exist;
- cost is zero or policy-bounded/known-low;
- cleanup is deterministic and verified.

### Shared staging

Pre-authorization may still permit autonomous execution, but policy should account for:

- shared-state mutation;
- namespace/resource collision;
- concurrency/lease ownership;
- bounded data mutation;
- retention and cleanup;
- externally visible integrations.

Destructive operations outside an execution-owned scope should require stronger authority.

### Production-like

May be autonomous inside an explicitly granted environment budget and capability envelope, but provisioning cost, destructive actions, and retained resources generally justify stronger admission policy than local/staging.

### Production

Production environment validation is exceptional. Material mutation, deployment, destructive actions, or meaningful spend require explicit human authority unless a separately accepted project policy defines a very narrow pre-authorized operation. Human acceptance/promotion boundaries remain distinct even when production observation is automated.

---

## Side-effect ledger integration

Every externally visible environment operation should be represented as a logical operation in Battalion's existing side-effect architecture, including as applicable:

- acquire/lease environment;
- provision resource;
- deploy candidate;
- mutate data/state;
- invoke external system;
- rollback;
- delete resource;
- cleanup/teardown;
- release lease.

The environment-validation evidence artifact references these logical operation identities rather than inventing a parallel audit log.

This preserves replay/reconciliation semantics after crashes. On resume Battalion can ask, for example, whether a resource was actually created before retrying, or whether cleanup succeeded externally despite a local persistence failure.

## Architectural alternatives

### Option A — Dedicated Validation Run/node/model role

A first-class Validation Run would own environment execution after implementation/deployment.

**Advantages**

- visible lifecycle boundary;
- easy to schedule separately from implementation;
- can have independent worker/environment placement;
- clear history and status surface.

**Risks**

- if implemented as a model role, it encourages giving a model authority that deterministic tooling should own;
- one fixed Run shape may not fit local integration, staging, operational probes, and production observation;
- can duplicate Deployer/Debugger responsibilities.

**Assessment:** useful as a possible execution container, but not sufficient as the core abstraction and not justification for a new model role.

### Option B — Deployer sub-phase

Environment validation is embedded in deployment.

**Advantages**

- natural for deploy-then-test staging flows;
- reuses deployment authority and lifecycle.

**Risks**

- local/container/database integration tests may require no deployment;
- some validation happens before Deployer should exist;
- operational validation may be reused after deployment;
- conflates environment governance with one role's lifecycle.

**Assessment:** valid recipe specialization, not the universal architecture.

### Option C — Deterministic reusable validation capability/subgraph

Battalion defines environment admission, execution, evidence, failure, cost, and cleanup contracts independently. Workflow recipes compose these into one or more Runs/nodes as needed.

**Advantages**

- provider- and workflow-neutral;
- supports local integration through production observation;
- keeps secret/capability use behind deterministic boundaries;
- can execute inside one Run or as dependency-linked Runs;
- aligns with recipe-selectable workflow architecture;
- avoids inventing a model role.

**Risks**

- more contract design up front;
- needs careful ownership boundaries between workflow orchestration, integrations, side effects, and evidence persistence.

**Assessment:** preferred direction.

### Option D — Keep deployment + Human UAT boundary

Do not introduce automated environment validation.

**Advantages**

- smallest architecture;
- avoids cloud credential/cost complexity.

**Risks**

- leaves repeatable integration behavior manual/ad hoc;
- weakens provenance and reproducibility;
- scales poorly for self-hosting/autonomous mechanical work;
- cannot provide reliable automated evidence before human acceptance.

**Assessment:** rejected as the general architecture, though recipes may still intentionally omit automated environment validation.

---

## Preferred composition

The preferred architecture is **Option C**, while allowing the deterministic subgraph to be hosted in different execution shapes.

For simple local integration:

```text
Implementation Run
  -> code validation
  -> EnvironmentValidation(local_ephemeral)
  -> Review
```

For a staging deployment:

```text
Implementation Run
  -> Review Run
  -> Deployment/Provision Run
  -> Environment Validation Run
  -> Human QA/UAT
```

For dependency-aware cloud validation, BTN-192 may schedule provision, deploy, validate, and cleanup as separate dependent Runs while preserving one validation obligation/evidence chain.

The reusable contract is more important than whether those steps happen in one process, one Run, or several Runs.

## Model participation

Models may assist with:

- proposing validation obligations from requirements;
- designing executable validation scenarios;
- identifying useful bounded observations;
- interpreting returned evidence;
- suggesting diagnoses from infrastructure or behavioral failures;
- recommending whether additional evidence is needed.

Models should not be authoritative for:

- widening environment scope;
- selecting undeclared credentials;
- increasing spend authorization;
- converting unknown cost into zero;
- bypassing an approval gate;
- deciding that cleanup is optional when policy requires it;
- claiming an environment action happened without deterministic/provider evidence;
- silently reclassifying infrastructure/authorization/cost/cleanup failure as product success.

Existing Driver/Debugger/Deployer roles can consume the classified result. A new role should be considered only after deterministic execution and existing roles leave a real responsibility gap.

## Concrete scenario: disposable local database integration

A work item changes persistence behavior and has an obligation to validate against PostgreSQL semantics.

```text
Environment class: local_ephemeral
Capabilities:
  create_resource: postgres_container + private network
  mutate_data: execution-owned database only
  read_observe: execution-owned database/process
  cleanup_teardown: execution-owned resources only
Credential refs: none
Cost authorization: observed/known zero monetary provider cost
Approval: pre-authorized by project policy
```

Execution:

1. Battalion admits the exact candidate and scenario revision.
2. Deterministic tooling creates a uniquely named container/network and records side-effect intents/outcomes.
3. The scenario migrates schema, seeds bounded fixture data, executes the application behavior, and captures assertions/log references.
4. Battalion records candidate, scenario, exact container/image/environment identities, timing, and observations.
5. Cleanup removes the database and network, verifies absence, and records reconciliation evidence.
6. `overall_outcome` is success only if behavioral assertions **and** cleanup succeed.

No human interrupt is necessary unless local policy, resource limits, or cleanup/reconciliation fail.

## Concrete scenario: bounded cloud infrastructure validation

A candidate changes infrastructure/deployment behavior and requires validation in an isolated cloud project/account/subscription.

Provider-neutral example:

```text
Environment class: production_like
Binding: project-cloud-validation-v3
Scope:
  account/project/subscription: dedicated validation scope
  region: ca-central
  namespace_prefix: btn-198-${run_id}
  resource_classes: [container_service, managed_database]
  max_runtime: 90 minutes
Capabilities:
  read_observe
  deploy
  create_resource
  mutate_data       # namespace-owned validation data only
  delete_resource   # run-owned resources only
  cleanup_teardown
Credential ref:
  battalion://credentials/cloud-validation-deployer
Cost authorization:
  maximum_authorized_spend: CAD 5.00
  estimated_spend: CAD 1.40
  unknown_cost_policy: deny new unestimated resource classes
Approval:
  project policy pre-authorizes this exact environment/capability/cost envelope
```

Execution:

1. Battalion resolves a short-lived provider credential inside deterministic tooling; the model never receives the token.
2. A write-ahead side-effect record is created before provisioning.
3. The adapter provisions only admitted resource classes in the dedicated scope/region/namespace.
4. The exact candidate is deployed.
5. The admitted scenario executes external/operational checks and records bounded observations.
6. Cost observation is queried where available. Absence of final provider billing data remains `unknown/pending`, not zero.
7. Teardown deletes run-owned resources and reconciles provider state.
8. Validation evidence records authorization, action identities, observations, cost state, and cleanup disposition.

If assertions pass but a managed database cannot be deleted, the result is `cleanup_failure`, not success. If the provider rejects deployment because the credential lacks a required scope, the result is `authorization_failure`, not a product defect. If observed cost exceeds policy, the validation is not successful merely because the application behaved correctly.

## Automated validation vs Human QA/UAT

Automated environment validation asks:

> Did the admitted candidate exhibit the specified machine-observable behavior in the admitted environment, under the admitted authority, and reach the required cleanup/retention disposition?

Human QA/UAT asks a different question:

> Does a human accept the behavior/product outcome for the intended use?

A workflow may require either or both. When both are present, automated validation evidence becomes an input to human acceptance. Battalion must not convert machine evidence into human acceptance unless the workflow explicitly defines no human acceptance requirement.

This preserves the human-in-the-loop philosophy while eliminating mechanical environment execution where automation is appropriate.

## Open questions

1. **Canonical ownership of environment descriptors:** should environment descriptors live as project repository artifacts, Battalion project configuration, integration-provider configuration, or a hybrid where the repository contains symbolic policy/identity and machine-local Battalion configuration resolves secret/provider bindings?
2. **Validation obligation authority:** should Specifier produce candidate obligations that Architect approves/refines, should Architect own them entirely, or should the specification contain observable obligations while Architect adds environment/capability realization constraints?
3. **Execution container identity:** should the first implementation introduce a distinct `EnvironmentValidationRun` kind, keep validation as a generic recipe node/subgraph initially, or define the contract first and deliberately postpone Run-kind specialization?
4. **Lease/concurrency semantics for shared environments:** should leases be part of this RFC's core environment contract or delegated to BTN-192/resource scheduling as a required follow-on?
5. **Cost exceedance after irreversible spend:** when actual/estimated cost becomes known only after an operation, should the canonical result be a failed validation, a policy violation attached to otherwise complete evidence, or both (typed policy failure plus preserved behavioral result)?
6. **Retention as cleanup:** should an admitted `retain-until` disposition count as successful cleanup immediately once retention is durably scheduled, or only after later teardown has been verified?

These questions affect contract ownership and implementation decomposition but do not change the central recommendation that environment authority remain explicit, deterministic, and recipe-composable.

## Implementation decomposition (to finalize after acceptance)

BTN-198 is architecture-only. Acceptance should produce separate implementation tickets, likely covering:

1. environment descriptor + capability + scope contracts;
2. environment admission and human/policy authorization integration;
3. validation obligation/scenario contracts and requirement traceability;
4. environment validation evidence + typed failure taxonomy;
5. side-effect ledger integration for provision/deploy/mutate/cleanup operations;
6. credential-reference resolver boundary and secret-redaction rules;
7. cost authorization/observation contracts;
8. workflow recipe/subgraph integration;
9. disposable local/container/database reference adapter and tests;
10. cloud-provider reference adapter or provider-neutral contract fixture/evaluation;
11. shared-environment leasing/concurrency integration if not owned by BTN-192;
12. CLI/UI evidence presentation and human approval surfaces.

No production implementation should be performed directly under BTN-198.

---

## Acceptance direction

RFC-0020 should be accepted only after the open ownership/lifecycle questions are resolved and the final design demonstrates that:

- a low-risk local integration test can run with little/no human interruption;
- a cloud validation can execute without giving a model ambient credentials;
- monetary authorization and observed cost are separately represented;
- every external action is auditable/reconcilable;
- cleanup failure cannot be hidden by passing assertions;
- workflow recipes can include or omit validation;
- automated evidence remains distinct from human acceptance.
