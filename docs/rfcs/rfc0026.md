# RFC-0026 — Bounded Iterative Workflow Execution

**Status:** Draft  
**Date:** 2026-09-03  
**Ticket:** BTN-113  
**Author:** Architecture  
**Target:** Post-v2 workflow orchestration  
**Related:** `philosophy.md`, BTN-107, BTN-108, BTN-109, BTN-111, BTN-120, BTN-122, BTN-131, BTN-133, BTN-134, RFC-0012, RFC-0013, RFC-0014, RFC-0015, RFC-0017, RFC-0018, RFC-0020, RFC-0021, RFC-0023, RFC-0025

## Summary

Battalion should support **explicitly bounded iterative workflow regions** as a versioned part of an admitted `WorkflowRecipe`.

The primitive is not a role-specific review loop and it is not a generic autonomous retry mechanism. It is a Battalion-owned workflow construct for cases where the admitted engineering process intentionally permits a finite sequence such as:

```text
produce
  ↓
evaluate
  ├─ accept ───────────────→ terminal success
  ├─ revise ─→ produce
  ├─ escalate ─────────────→ admitted escalation / HumanInterrupt
  └─ fail ─────────────────→ terminal failure
```

The governing rules are:

1. The workflow definition declares the iterative region, its entry contract, its permitted transitions, and its maximum rounds before execution begins.
2. A model or role may report an outcome. It cannot add transitions, enlarge the round bound, reset the loop, or recursively create another loop.
3. Every round consumes and produces validated Battalion-owned artifact revisions through RFC-0015 typed boundaries.
4. Every round appends durable evidence. This includes exact artifact identity, execution identity, provenance, outcome, unresolved findings, and the transition taken.
5. Planned iteration is distinct from RFC-0018 failure recovery.
6. RFC-0023 authority rules apply to every authority-sensitive transition. Provenance does not itself grant authority or authorization.
7. RFC-0021 governs repository-instruction resolution and drift. Round evidence records the effective instruction/context evidence supplied to each execution.
8. RFC-0025 significance and escalation policy can interrupt a round. Significance is not an iteration disposition.
9. Resource use across all rounds contributes to the same Battalion-owned Run budgets from BTN-111.
10. Exhaustion is a first-class durable outcome and routes only to the workflow's declared exhaustion behavior.
11. HumanInterrupt may pause and resume the region without resetting round count, artifact identity, unresolved findings, governing scope, recovery counters, instruction provenance, or resource accounting.

The design should be generic enough for Specification, Architecture, semantic review/remediation, and other bounded deliberative workflows without hard-coding a specific Regiment, Squad, or Gator role pair.

## Problem

Battalion already has several kinds of repetition. None should be mistaken for a general bounded workflow-iteration primitive.

### Checkpoint retry

The current implementation workflow can retry after deterministic checkpoint rejection. This is narrow execution or recovery behavior.

### RFC-0018 recovery

RFC-0018 defines declarative recovery from failures, ambiguity, role escalation, provider problems, and related boundary conditions. Its purpose is to decide what Battalion may do after something goes wrong or requires recovery.

### Deliberative iteration

Specification, Architecture, review, and other first-class workflows can legitimately require planned iteration even when no execution failure occurred.

RFC-0020 now provides a concrete example:

```text
candidate specification revision
  ↓
human review
  ├─ revise ───────────────→ next bounded round
  ├─ accept exact revision → terminal success
  └─ unresolved dependency → HumanInterrupt / admitted escalation
```

A valid candidate specification can require another revision without any execution failure. Calling that a retry would erase an important distinction.

Without a first-class iterative-region contract, Battalion risks implementing each case as a bespoke graph cycle:

- Specification revision loops in one graph;
- Architect/human loops in another;
- review/remediation loops somewhere else;
- ad hoc counters embedded in nodes;
- resettable limits when roles or providers change;
- conversational state standing in for artifact identity;
- unclear interaction with HumanInterrupt, provenance, authority, instruction drift, significance, recovery, resource budgets, and terminal history.

That would make boundedness depend on graph topology and prompt discipline rather than Battalion policy.

---

## Goals

- Define a reusable, versioned bounded-iteration contract for admitted workflows.
- Keep iteration policy owned by Battalion rather than executing models.
- Distinguish planned workflow iteration from failure and recovery behavior.
- Persist round identity and evidence independently of conversational transcripts.
- Require typed artifact boundaries between rounds.
- Apply RFC-0023 provenance and authority semantics to governing artifacts and transitions.
- Preserve immutable governing scope where policy requires it.
- Make revision findings explicitly addressable across rounds.
- Preserve effective repository-instruction/context evidence per execution.
- Route significance through RFC-0025 instead of treating it as another loop outcome.
- Make exhaustion a first-class outcome.
- Preserve all loop state across pause/resume and process restart.
- Account for every round under shared Run resource budgets and recovery bounds.
- Support different roles, models, and providers on different stages and rounds.
- Support work-class-specific workflow recipes without one universal SDLC graph.
- Make loop history directly renderable by CLI, desktop, and history clients.
- Prevent recursive or dynamically expanded autonomous loops.

## Non-goals

- Implement an open-ended autonomous agent controller.
- Allow models to invent or mutate workflow topology.
- Define one universal Draft/Review role pair.
- Treat every retry as workflow iteration.
- Replace RFC-0018 failure/escalation policy.
- Replace RFC-0023 provenance, authority, or Actor authorization.
- Replace RFC-0021 repository-instruction resolution.
- Replace RFC-0025 architectural-significance routing.
- Replace BTN-111 resource accounting.
- Persist raw model chain-of-thought.
- Require all workflow kinds to use iteration.
- Allow a model/provider change to reset iteration state.
- Permit a participant to broaden an immutable governing scope artifact.
- Treat a bounded `SteelmanAssessment` as a nested iterative region by default.

## Architectural distinction: iteration versus recovery

The most important boundary in this RFC is semantic.

### Iteration

An **iteration transition** is a normal, pre-admitted workflow outcome. It means the workflow produced a valid result whose declared disposition is to execute another round.

Examples:

- a candidate specification needs revision after human review;
- an Architect proposal needs another revision after human feedback;
- review findings were remediated and require another independent review pass.

### Recovery

A **recovery transition** responds to execution failure, invalid output, unavailable evidence, provider failure, authority ambiguity, or another RFC-0018 trigger.

Examples:

- a model call fails;
- typed output cannot be validated;
- required governing evidence is missing;
- a role returns `BLOCKED` or `ESCALATED`;
- provider failover is required;
- a bounded implementation ruling is considered.

These can occur in the same Run and even inside one iteration round. They are governed by different policies.

```text
WorkflowRecipe / BoundedIterationPolicy
    decides whether a valid round outcome means "iterate"

FailureEscalationPolicy
    decides what to do when execution/recovery policy is triggered
```

A recovery action must not increment the workflow round merely because the same stage executes again. A deliberate revision round must not consume a recovery retry merely because a stage executes again.

Both forms of repetition remain subject to shared anti-evasion accounting. One cannot reset the other's limits.

## Proposed workflow contract

RFC-0012 already establishes registered, versioned `WorkflowRecipe` definitions. Bounded iteration should extend that family rather than introduce a separate orchestration system.

Conceptually:

```text
WorkflowRecipe
  recipe_id
  recipe_version
  workflow_kind
  stages[]
  transitions[]
  iterative_regions[]
```

An iterative region is declarative and finite.

A first-cut contract:

```text
BoundedIterationPolicy
  schema_version
  iteration_id
  entry_stage
  member_stages[]
  iteration_transition
  permitted_outcomes[]
  success_outcomes[]
  terminal_failure_outcomes[]
  escalation_outcomes[]
  max_rounds
  exhaustion_action
  governing_scope_refs[]
  immutable_scope
  finding_policy
```

The exact serialized field names are implementation detail for later Driver work. The architecture-level invariants are more important:

- `max_rounds` is a positive finite integer;
- permitted transitions are closed and declared before admission;
- the policy identifies exactly which transition starts the next workflow round;
- iteration cannot target itself recursively through another unbounded or dynamically declared region;
- exhaustion behavior is explicit;
- governing scope references are revision-pinned;
- authority-sensitive transitions evaluate current RFC-0023 policy requirements rather than assuming a reference is authoritative by existence alone;
- immutable scope cannot be silently replaced or widened inside the region;
- the recipe remains version-pinned for the lifetime of the admitted Run.

### Why region rather than edge-only metadata

BTN-113 describes "bounded iterative workflow edges", but a loop has state that belongs to the whole iterative construct rather than one transition alone:

- current round;
- maximum rounds;
- governing scope;
- unresolved findings;
- exhaustion outcome;
- entry/exit semantics;
- artifact lineage;
- provenance and authority evidence.

Representing that state as a named **iterative region** avoids scattering one logical policy across several graph edges while still allowing the concrete graph to contain ordinary edges.

## Admission and static validation

A `WorkflowRecipe` containing iterative regions must pass deterministic admission validation before a Run begins.

Validation should reject at minimum:

- missing or non-positive `max_rounds`;
- an iteration transition that is not part of the recipe;
- an outcome with no admitted transition;
- an iteration region with no terminal success, failure, or escalation path;
- iteration that can exit and re-enter in a way that silently resets the same logical bound;
- recursive iteration-region references;
- dynamically model-authored stage or transition identifiers;
- a mutable governing-scope declaration when policy requires immutability;
- incompatible boundary contracts between successive rounds;
- a workflow recipe whose iteration semantics cannot preserve the declared limit in the target engine.

Graph topology alone is not authority. The admitted recipe contract is.

## Durable iteration state

An active Run needs durable iteration state that survives process restart and HumanInterrupt.

Conceptually:

```text
IterationState
  iteration_instance_id
  iteration_policy_id
  current_round
  max_rounds
  status
  governing_scope_refs[]
  unresolved_finding_refs[]
  last_round_record_ref
```

This state belongs to the containing Run's workflow-specific persistence, consistent with RFC-0014's separation between common Run lifecycle and workflow-kind-specific state.

It must not be reconstructed by counting conversational messages or model invocations.

### Round numbering

Round numbers are one-based and monotonic within an iteration instance.

A round is consumed when the workflow reaches the region's declared round-outcome boundary with a valid persisted round result. Provider retries or recovery retries inside that round do not create a new workflow round.

Once consumed, a round number is not reused.

---

## Durable round record

Each completed round should append a durable record sufficient to explain what happened without parsing prose.

Conceptually:

```text
IterationRoundRecord
  schema_version
  iteration_instance_id
  round_number
  producing_run_id
  stage_execution_refs[]
  actor_refs[]
  model_inference_refs[]
  consumed_artifact_refs[]
  produced_artifact_refs[]
  governing_scope_refs[]
  provenance_refs[]
  effective_instruction_context_refs[]
  finding_refs[]
  significance_signal_refs[]
  disposition
  transition_id
  started_at
  completed_at
  resource_evidence_ref
  recovery_evidence_refs[]
```

The record preserves exact artifact revisions, not just logical artifact names.

Model/provider identity belongs in inference/execution evidence rather than one flattened "agent" string. A stage or round may use a different provider or model without changing iteration identity.

`provenance_refs[]` preserve where relevant artifacts and claims came from. They do not imply that those artifacts satisfy an authority-sensitive operation.

`effective_instruction_context_refs[]` identify the resolved repository instructions and bounded context supplied to the execution. RFC-0021 remains authoritative for discovery, precedence, conflicts, audience filtering, and drift behavior.

## Artifact-only workflow boundaries

RFC-0015 applies unchanged inside an iterative region.

A later round receives validated Battalion-owned inputs assembled from durable artifacts and evidence. It does not inherit unrestricted mutable scratch state or depend on a shared chat transcript.

For a revision loop, the minimum lineage should be mechanically visible:

```text
governing scope S@1
proposal P@1
review R@1
revision P@2
review R@2
...
```

The receiving stage may be given a context projection containing human/model-readable summaries. Those projections do not replace canonical artifact identity, provenance, or authority evaluation.

## Provenance, authority, and governing scope

RFC-0023 separates three questions:

```text
provenance     = where did this artifact or claim come from?
authority      = what may it influence under current policy?
authorization  = may this Actor perform the concrete operation?
```

RFC-0026 must preserve that separation.

A `governing_scope_ref` identifies the artifact or claim that the workflow treats as governing scope. It is not itself proof that the artifact satisfies every authority-sensitive transition.

Before an authority-sensitive transition, Battalion evaluates the operation's authority requirement against current project or organizational policy and the available provenance/evidence. Actor authorization remains a separate check.

This means that human-authored text is not automatically authoritative. A material governing-scope change occurs only through an admitted operation that produces or accepts a new authority-bearing artifact or decision.

---

## Immutable governing scope

Some iterative workflows require a governing artifact to remain fixed throughout the loop.

Examples include:

- an accepted specification revision;
- an Architect-approved scope;
- an exact review target revision;
- a human-approved architecture question or decision boundary.

When `immutable_scope` is enabled:

- every round records the exact governing scope revision(s);
- every round preserves provenance for those references;
- participating stages may interpret that scope;
- they may not replace, widen, or silently reinterpret its authority boundary;
- a proposed change that requires broader scope produces an explicit scope-inadequacy or escalation outcome;
- only an admitted authority path may establish a new governing scope.

A human comment or model suggestion does not change scope by itself. The change must occur through an admitted authority-bearing operation under RFC-0023.

If governing scope changes materially, Battalion should not pretend the original bounded loop continued unchanged. The architecture should create either a new iteration instance or a successor Run/workflow admission, depending on the surrounding workflow semantics.

This keeps revision from becoming a hidden architecture or product-scope mutation.

## Specification as a concrete bounded workflow

RFC-0020 establishes Specification as a first-class workflow. It produces candidate specification revisions until a human explicitly accepts an exact revision.

Bounded iteration should support that lifecycle directly:

```text
candidate spec S@1
    |
    v
human review
    |----------------------------|
    | revise                     | accept exact revision
    v                            v
candidate spec S@2          authoritative spec S@N
    |                            |
    +---------- bounded ---------+--> terminal success
```

Important distinctions:

- changing a candidate specification revision is normal iteration;
- accepting an exact candidate is an authority-bearing operation;
- a human comment does not become authoritative specification text merely because it is human-authored;
- a material change to an already accepted governing specification is not merely another candidate revision in the same immutable-scope iteration;
- unresolved dependency may end the bounded region at a HumanInterrupt or another admitted escalation path.

This is the first concrete consumer of the generic primitive. The primitive remains workflow-neutral.

---

## Findings and revision-addressability

A revision-request workflow needs more than text saying "please fix these things."

Findings should have stable durable identity so later rounds can demonstrate what happened to each one.

The minimum state model should distinguish:

- open or unresolved;
- addressed;
- explicitly rejected or dismissed by an authorized disposition;
- superseded by another finding;
- blocked or unverifiable;
- out-of-scope or escalated.

A later revision may introduce new findings. It must not silently omit an unresolved prior finding.

Conceptually:

```text
FindingDispositionRecord
  finding_id
  prior_round_ref
  current_round_ref
  disposition
  evidence_refs[]
  provenance_refs[]
  actor_or_execution_ref
```

BTN-120/BTN-122 review evidence and human annotation contracts should be reused where applicable rather than defining a second incompatible finding system.

An authority-sensitive finding disposition must satisfy RFC-0023 policy and Actor authorization. Human-authored prose alone is not enough.

## Architectural significance inside a round

RFC-0025 makes architectural significance first-class evidence.

A significance event is not an ordinary iteration disposition.

```text
valid iterative round
    |
    +-- ordinary revise --> next round
    |
    +-- SignificanceSignal --> EscalationPolicy
                                  |
                                  +--> Architect review
                                  +--> specialist review
                                  +--> HumanInterrupt
                                  +--> no extra action
```

Deterministic/project significance may enter policy directly. A model-produced significance observation first follows RFC-0025's confirmation boundary before it can become validated significance.

If significance policy interrupts the iterative region, Battalion preserves the current round state and iteration identity. Resume continues only through an admitted route.

A `SteelmanAssessment` may be bounded in its own execution contract. That does not automatically make it a nested `BoundedIterationPolicy` region. The initial RFC-0026 design should remain conservative about nested iterative regions.

---

## Repository instructions across rounds

RFC-0021 owns repository-instruction discovery, resolution, precedence, audience filtering, conflict handling, and drift semantics.

RFC-0026 adds one requirement: each stage execution must retain evidence of the effective repository instruction/context set it received.

This lets Battalion answer:

- what instructions governed round 1;
- whether round 2 received different instructions;
- whether a resume crossed an instruction drift boundary;
- whether RFC-0021 required re-evaluation, warning, interruption, or continuation.

RFC-0026 does not invent a second instruction-drift policy. It records enough execution evidence for RFC-0021 policy to remain visible and auditable.

---

## Exhaustion

Maximum-round exhaustion is a normal first-class workflow outcome. It is not an exception and it is not permission to start another loop.

When a round requests another iteration and `current_round == max_rounds`, Battalion must:

1. persist the final round record;
2. persist an exhaustion outcome;
3. execute exactly the recipe's declared exhaustion action.

Permitted exhaustion actions should be drawn from Battalion-owned workflow/recovery vocabulary, for example:

- HumanInterrupt;
- terminal failure;
- explicit escalation to another admitted workflow boundary.

An executing model cannot select a different exhaustion action or request one more round.

Switching role, model, provider, process, worker, or presentation client does not reset exhaustion.

---

## HumanInterrupt and resume

HumanInterrupt can occur before, during, or after an iteration round.

On pause, Battalion must durably retain:

- iteration instance identity;
- current or consumed round count;
- governing scope revisions;
- governing-scope provenance;
- current artifact lineage;
- unresolved finding identities;
- workflow recipe/version;
- recovery counters;
- resource budget consumption;
- effective instruction/context evidence;
- significance/escalation evidence;
- the exact interrupt reason.

Resume continues the same admitted iteration instance unless an admitted decision changes governing scope or workflow admission in a way that requires successor history.

A UI button labeled `retry` must not recreate the region with a fresh counter unless policy explicitly creates a new successor Run or iteration identity.

## Interaction with RFC-0018 recovery policy

RFC-0018 remains authoritative for failures and escalation triggers that occur during a round.

A round can therefore contain nested bounded recovery without changing the workflow round:

```text
round 2
  proposal stage
    provider failure
    → RFC-0018 bounded provider retry
    → success
  review stage
    valid "revise" disposition
  → iteration policy advances to round 3
```

Anti-evasion rules operate across both systems:

- iteration count cannot reset recovery counters;
- recovery/replan cannot silently create a fresh iteration instance;
- model/provider escalation cannot reset either bound;
- successor Runs preserve predecessor linkage and consumed historical evidence under RFC-0017.

---

## Interaction with BTN-111 resource budgets

All execution inside all rounds contributes to the containing Run's Battalion-owned resource accounting.

At minimum:

- model or inference calls;
- tokens where available;
- retries;
- escalations;
- elapsed time where supported.

A round transition does not create a fresh resource budget.

If a resource limit is reached before the iteration's `max_rounds`, the resource policy wins. Execution stops or routes according to admitted resource/failure policy.

A round allowance is permission to continue if other governance constraints also permit it. It is not a reserved execution entitlement.

## Work-class-specific workflows

BTN-113 also requires Battalion to support multiple explicit workflow definitions rather than one universal SDLC graph.

RFC-0012's `WorkflowKind` and `WorkflowRecipe` model already provides the base.

### Specification

```text
incomplete product intent
→ candidate specification
→ bounded human review/revision
→ exact human acceptance
→ authoritative specification
```

RFC-0020 owns the authority semantics for the final acceptance.

### Feature

```text
accepted feature specification
→ implementation
→ optional semantic review/remediation region
→ completion
```

### Defect

```text
demonstrated regression evidence
→ defect diagnosis/fix
→ verification
→ completion
```

### Intentional behavior change

```text
revised expected behavior/specification
→ implementation
→ verification against new expectation
→ completion
```

### Architecture

```text
admitted architecture question
→ evidence/proposal
→ bounded human review/revision
→ human acceptance
→ durable RFC/ADR
→ ticket decomposition
```

A `SignificanceSignal` may route implementation into Architect review under RFC-0025. That routing does not mean the model reclassified the work to obtain a fresh loop.

Different workflows may require different entry evidence and invariants. Battalion owns classification and recipe selection through admitted workflow machinery.

## Presentation and history

CLI, desktop, and history clients should render bounded iteration directly from persisted records.

A minimal presentation can show:

```text
Specification iteration — 3 round maximum
Scope: intent://work-item/BTN-123@7

Round 1
  Candidate: specification@1
  Review: request-revision
  Open findings: F-12, F-13

Round 2
  Candidate: specification@2
  Review: request-revision
  Addressed: F-12
  Open: F-13, F-18

Round 3
  Candidate: specification@3
  Human decision: accepted exact revision
  Addressed: F-13, F-18

Outcome: accepted in 3/3 rounds
```

Clients must not reconstruct this by interpreting model prose or chat chronology.

Where relevant, clients should also be able to inspect:

- governing artifact provenance;
- authority decision evidence;
- effective repository instruction/context evidence;
- significance/escalation events;
- recovery attempts;
- resource consumption.

## Termination and recursion safety

Battalion should validate two levels of boundedness.

### Local bound

Each iterative region has a finite `max_rounds` and explicit exit behavior.

### Composition bound

A recipe must not compose iterative regions, recovery replans, workflow upgrades, significance routes, or successor transitions in a way that creates a hidden autonomous cycle whose effective bound resets each time.

Initial policy can be conservative: reject workflow definitions with recursive iterative-region ancestry or re-entry paths that cannot prove preservation of the original bound.

A bounded capability such as `SteelmanAssessment` does not imply permission to nest an iterative region. Nested iteration should remain disallowed in the first implementation unless a later architecture decision defines provable composition rules.

Battalion does not need a general theorem prover. It needs a finite declarative recipe model whose legal transition forms make unbounded recursion structurally unavailable.

---

## Failure and terminal semantics

Representative workflow dispositions should include:

- `accept` / `approve`;
- `revise` / `retry-round`;
- `escalate`;
- `fail`;
- `cancel`;
- `exhausted`.

These are workflow-level dispositions, not necessarily final serialized enum names.

RFC-0013 remains the role-attempt outcome contract. A role returning `COMPLETED`, `BLOCKED`, or `ESCALATED` does not itself define the workflow transition. Battalion translates valid role evidence through admitted recipe and policy.

RFC-0025 significance is separate from those ordinary iteration dispositions. Validated significance enters `EscalationPolicy`.

Cancellation is a terminal Run lifecycle outcome consistent with RFC-0017. It must not be represented as iteration exhaustion merely because both stop execution.

## Alternatives considered

### 1. Hard-code specific role loops

Example: `Architect → Reviewer → Architect`.

Rejected because it couples the workflow primitive to today's role names, makes reuse difficult, and invites duplicated semantics for Review, Specification, and other workflows.

### 2. Treat all iteration as RFC-0018 retry/recovery

Rejected because a valid review-requested revision is not an execution failure. It would also overload retry counters and blur operator history.

### 3. Let LangGraph cycles define behavior implicitly

Rejected because graph topology does not by itself define authority, maximum rounds, artifact identity, exhaustion semantics, provenance, immutable scope, or anti-evasion rules.

### 4. Let the model decide when it is done

Rejected. Models produce evidence and dispositions. Battalion owns admitted continuation and termination.

### 5. Start a new Run for every round

Not selected as the default. A round is usually one lifecycle inside one first-class Run and should share governing scope, budgets, history, and termination.

Separate first-class Runs remain appropriate when the surrounding workflow crosses a first-class lifecycle or authority boundary under RFC-0014.

### 6. Treat significance as another iteration outcome

Rejected. RFC-0025 already defines significance as typed evidence routed through `EscalationPolicy`. Collapsing it into `revise` or `fail` would lose that distinction.

### 7. Treat every bounded sub-capability as nested iteration

Rejected for the initial design. A bounded `SteelmanAssessment`, provider retry, or other bounded operation can have its own finite execution contract without becoming a nested `BoundedIterationPolicy` region.

## Open questions

### 1. Should round count mean full region passes or revision attempts?

This draft proposes **full admitted round outcomes**: a round is consumed when the region reaches its declared round-outcome boundary with a valid result.

That keeps provider retries and recovery attempts out of the round count and gives history a stable engineering meaning.

### 2. What should happen when governing scope changes after human input?

RFC-0023 narrows this question. Human text does not itself change authority. A material governing-scope change occurs only through an admitted authority-bearing operation.

This draft proposes that a material governing-scope change **does not continue the same iteration instance**. It should create a successor iteration instance or successor Run with explicit lineage.

The remaining question is whether the default should be a new instance inside the same active Run or a successor Run. The answer may differ by `WorkflowKind`.

### 3. Should exhaustion route through RFC-0018 or be a direct workflow transition?

This draft treats exhaustion as a **workflow outcome** whose declared action may invoke HumanInterrupt, terminal failure, or another admitted escalation path.

That avoids misclassifying "used all planned rounds" as an execution failure while still reusing the same application routing and authority machinery where practical.

### 4. How much static composition analysis is required for v1?

A conservative first implementation could prohibit nested iterative regions and any re-entry into an already-exited iteration region.

Later versions could admit more composition only when ancestry and bounds remain mechanically provable.

RFC-0025 does not require nested iterative regions for Steelman. A bounded Steelman execution can remain an ordinary bounded capability.

### 5. Should unresolved findings use one general finding contract?

This draft prefers reuse of BTN-120/BTN-122 review/finding/annotation primitives where they fit.

Do not create an iteration-specific finding ontology unless those contracts prove too review-specific.

---

## Proposed decision

Adopt bounded iteration as a **declarative, versioned iterative-region capability inside `WorkflowRecipe`**, with:

- finite pre-admitted round bounds;
- closed permitted outcomes and transitions;
- durable iteration and round identity;
- RFC-0015 artifact-only boundaries;
- RFC-0023 provenance and authority evaluation at authority-sensitive transitions;
- RFC-0021 effective instruction/context evidence per execution;
- RFC-0025 significance routing outside ordinary iteration dispositions;
- Specification as a concrete first-class consumer under RFC-0020;
- optional immutable governing scope;
- durable unresolved-finding tracking;
- explicit exhaustion;
- no model-authorized bound expansion;
- no reset through role, model, provider, recovery, or presentation changes;
- HumanInterrupt-safe resume;
- composition with RFC-0018 recovery policy and BTN-111 resource budgets;
