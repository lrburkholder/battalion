# RFC-0019 — Bounded Iterative Workflow Execution

**Status:** Draft  
**Date:** 2026-09-03  
**Ticket:** BTN-113  
**Author:** Architecture  
**Target:** Post-v2 workflow orchestration  
**Related:** `philosophy.md`, BTN-107, BTN-108, BTN-109, BTN-111, BTN-120, BTN-122, BTN-131, BTN-133, BTN-134, RFC-0012, RFC-0013, RFC-0014, RFC-0015, RFC-0017, RFC-0018

---

## Summary

Battalion should support **explicitly bounded iterative workflow regions** as a versioned part of an admitted `WorkflowRecipe`.

The primitive is not a role-specific "review loop" and it is not a generic autonomous retry mechanism. It is a Battalion-owned workflow construct for cases where the admitted engineering process intentionally permits a finite sequence such as:

```text
produce
  ↓
evaluate
  ├─ accept ───────────────→ terminal success
  ├─ revise ─→ produce
  ├─ escalate ─────────────→ HumanInterrupt / admitted escalation
  └─ fail ─────────────────→ terminal failure
```

The governing rules are:

1. the workflow definition declares the iterative region, its entry contract, its permitted transitions, and its maximum rounds before execution begins;
2. an executing model or role may report an outcome, but cannot add transitions, enlarge the round bound, reset the loop, or recursively create another loop;
3. every round consumes and produces validated Battalion-owned artifact revisions through RFC-0015 typed boundaries;
4. every round appends durable iteration evidence, including exact artifact identities, producing execution identity, outcome, unresolved findings, and the transition taken;
5. intentional revision is distinct from RFC-0018 failure recovery, although failures that occur *inside* a round still route through the admitted failure/escalation policy;
6. resource consumption across all rounds contributes to the same Battalion-owned Run budgets from BTN-111;
7. exhaustion is a first-class durable outcome and routes only to the workflow's declared exhaustion behavior;
8. HumanInterrupt may pause and resume the region without resetting round count, artifact identity, unresolved findings, governing scope, recovery counters, or resource accounting.

The initial design should be generic enough for architecture proposal/review, semantic review/remediation, specification clarification, and other bounded deliberative workflows without hard-coding any specific Regiment/Squad/Gator role pair.

---

## Problem

Battalion currently has several kinds of repetition, but none should be mistaken for a general bounded workflow-iteration primitive.

### Checkpoint retry

The current implementation workflow can retry after deterministic checkpoint rejection. That is a narrow execution/recovery behavior.

### RFC-0018 recovery

RFC-0018 defines declarative recovery from failures, ambiguity, role escalation, provider problems, and related boundary conditions. Its purpose is to decide what Battalion may do after something goes wrong or requires recovery.

### Future deliberative workflows

Architecture, review, specification, research, and other first-class Run types can legitimately require planned iteration even when no execution failure occurred.

For example:

```text
Architecture proposal v1
  ↓
human/reviewer requests revision
  ↓
Architecture proposal v2
  ↓
accepted
```

Calling that a retry would erase an important distinction. The first proposal may have executed perfectly; the workflow simply requires another admitted round.

Without a first-class iterative-region contract, Battalion risks implementing each case as bespoke graph cycles:

- Driver/Reviewer loops in one graph;
- Architect/human loops in another;
- review/remediation loops somewhere else;
- ad hoc counters embedded in nodes;
- resettable limits when roles or providers change;
- conversational state standing in for artifact identity;
- unclear interaction with HumanInterrupt, failure recovery, resource budgets, and terminal history.

That would make boundedness depend on graph topology and prompt discipline rather than Battalion policy.

---

## Goals

- define a reusable, versioned bounded-iteration contract for admitted workflows;
- keep iteration policy owned by Battalion rather than executing models;
- distinguish planned workflow iteration from failure/recovery behavior;
- persist round identity and evidence independently of conversational transcripts;
- require typed artifact boundaries between rounds;
- preserve immutable governing scope where policy requires it;
- make revision findings explicitly addressable across rounds;
- make exhaustion a first-class outcome;
- preserve all loop state across pause/resume and process restart;
- account for every round under shared Run resource budgets and recovery bounds;
- support different roles, models, and providers on different stages/rounds;
- support work-class-specific workflow recipes without one universal SDLC graph;
- make loop history directly renderable by CLI/desktop/history clients;
- prevent recursive or dynamically expanded autonomous loops.

## Non-goals

- implementing an open-ended autonomous agent controller;
- allowing models to invent or mutate workflow topology;
- defining one universal Draft/Review role pair;
- treating every retry as a workflow iteration;
- replacing RFC-0018 failure/escalation policy;
- replacing BTN-111 resource accounting;
- persisting raw model chain-of-thought;
- requiring all workflow kinds to use iteration;
- allowing a new model/provider selection to reset iteration state;
- permitting a participant to broaden an immutable governing scope artifact.

---

## Architectural distinction: iteration versus recovery

The most important boundary in this RFC is semantic.

### Iteration

An **iteration transition** is a normal, pre-admitted workflow outcome. It means the workflow has produced a valid result whose declared disposition is to execute another round.

Examples:

- review requests revision;
- Architect proposal needs another revision after human feedback;
- specification clarification remains unresolved but within the admitted clarification cycle;
- review findings have been remediated and require another independent review pass.

### Recovery

A **recovery transition** responds to execution failure, invalid output, unavailable evidence, provider failure, authority ambiguity, or another RFC-0018 trigger.

Examples:

- model call fails;
- typed output cannot be validated;
- required governing artifact is missing;
- a role returns `BLOCKED` or `ESCALATED`;
- provider failover is required;
- a bounded implementation ruling is considered.

These can occur inside the same Run and even inside one iteration round, but they are governed by different policies.

```text
WorkflowRecipe / BoundedIterationPolicy
    decides whether a valid round outcome means "iterate"

FailureEscalationPolicy
    decides what to do when execution/recovery policy is triggered
```

A recovery action must not increment the workflow round merely because the same stage is executed again. Conversely, a deliberate revision round must not consume a "retry" merely because a stage executes again.

Both forms of repetition remain subject to shared anti-evasion accounting so one cannot be used to reset the other's limits.

## Proposed workflow contract

RFC-0012 already establishes registered, versioned `WorkflowRecipe` definitions. Bounded iteration should extend that family rather than introduce a separate orchestration system.

Conceptually:

```text
WorkflowRecipe
  recipe_id
  recipe_version
  workflow_kind
  stages[]
  transitions[]
  iterative_regions[]
```

An iterative region should be declarative and finite.

A first-cut contract:

```text
BoundedIterationPolicy
  schema_version
  iteration_id
  entry_stage
  member_stages[]
  iteration_transition
  permitted_outcomes[]
  success_outcomes[]
  terminal_failure_outcomes[]
  escalation_outcomes[]
  max_rounds
  exhaustion_action
  governing_scope_refs[]
  immutable_scope
  finding_policy
```

The exact serialized field names are implementation detail for the later Driver ticket. The architecture-level invariants are more important:

- `max_rounds` is a positive finite integer;
- permitted transitions are closed and declared before admission;
- the policy identifies exactly which transition starts the next workflow round;
- iteration cannot target itself recursively through another unbounded/dynamically declared region;
- exhaustion behavior is explicit;
- governing scope references are revision-pinned;
- immutable scope cannot be silently replaced or widened inside the region;
- the recipe remains version-pinned for the lifetime of the admitted Run.

### Why region rather than edge-only metadata

BTN-113 describes "bounded iterative workflow edges", but a loop has state that belongs to the whole iterative construct rather than one transition alone:

- current round;
- maximum rounds;
- governing scope;
- unresolved findings;
- exhaustion outcome;
- entry/exit semantics;
- artifact lineage.

Representing that state as a named **iterative region** avoids scattering one logical policy across several graph edges while still allowing the concrete graph to contain ordinary edges.

## Admission and static validation

A `WorkflowRecipe` containing iterative regions must pass deterministic admission validation before a Run begins.

Validation should reject at minimum:

- missing or non-positive `max_rounds`;
- an iteration transition that is not part of the recipe;
- an outcome with no admitted transition;
- an iteration region with no terminal success/failure/escalation path;
- iteration that can exit and re-enter in a way that silently resets the same logical bound;
- recursive iteration-region references;
- dynamically model-authored stage/transition identifiers;
- a mutable governing-scope declaration when policy requires immutability;
- incompatible boundary contracts between successive rounds;
- a workflow recipe whose iteration semantics cannot be represented by the target engine without preserving the declared limit.

Graph topology alone is not the source of authority. The admitted recipe contract is.

## Durable iteration state

An active Run needs durable iteration state that survives process restart and HumanInterrupt.

Conceptually:

```text
IterationState
  iteration_instance_id
  iteration_policy_id
  current_round
  max_rounds
  status
  governing_scope_refs[]
  unresolved_finding_refs[]
  last_round_record_ref
```

This state belongs to the containing Run's workflow-specific persistence, consistent with RFC-0014's separation between common Run lifecycle and workflow-kind-specific state.

It must not be reconstructed by counting conversational messages or model invocations.

### Round numbering

Round numbers are one-based and monotonic within an iteration instance.

A round is consumed when the workflow reaches the region's declared round-outcome boundary with a valid persisted round result. Provider retries or recovery retries inside that round do not create a new workflow round.

Once consumed, a round number is not reused.

---

## Durable round record

Each completed round should append a durable record sufficient to explain what happened without parsing prose.

Conceptually:

```text
IterationRoundRecord
  schema_version
  iteration_instance_id
  round_number
  producing_run_id
  stage_execution_refs[]
  actor_refs[]
  model_inference_refs[]
  consumed_artifact_refs[]
  produced_artifact_refs[]
  governing_scope_refs[]
  finding_refs[]
  disposition
  transition_id
  started_at
  completed_at
  resource_evidence_ref
  recovery_evidence_refs[]
```

The record should preserve exact artifact revisions, not just logical artifact names.

Model/provider identity belongs in inference/execution evidence rather than being flattened into one "agent" string. This allows one stage or round to use a different provider/model without affecting the iteration identity.

---

## Artifact-only workflow boundaries

RFC-0015 applies unchanged inside an iterative region.

A later round receives validated Battalion-owned inputs assembled from durable artifacts and evidence. It does not inherit unrestricted mutable scratch state or depend on a shared chat transcript.

For a revision loop, the minimum lineage should be mechanically visible:

```text
governing scope S@1
proposal P@1
review R@1
revision P@2
review R@2
...
```

The receiving stage may be given a context projection containing human/model-readable summaries, but those projections do not replace canonical artifact identity or governing authority.

---

## Immutable governing scope

Some iterative workflows require a governing artifact to remain fixed throughout the loop.

Examples include:

- an approved specification;
- an Architect-approved scope;
- an exact review target revision;
- a human-approved architecture question/decision boundary.

When `immutable_scope` is enabled:

- every round records the exact governing scope revision(s);
- participating stages may interpret that scope;
- they may not replace, widen, or silently reinterpret its authority boundary;
- a proposed change that requires broader scope produces an explicit scope-inadequacy/escalation outcome;
- only an admitted authority path may establish a new governing scope.

If the human changes the governing scope materially, Battalion should not pretend the original bounded loop continued unchanged. The architecture should create either a new iteration instance or a successor Run/workflow admission, depending on the surrounding workflow semantics.

This keeps "revision" from becoming a hidden architecture/product-scope mutation.

---

## Findings and revision-addressability

A revision-request workflow needs more than a text comment saying "please fix these things."

Findings should have stable durable identity so later rounds can demonstrate what happened to each one.

The minimum state model should distinguish:

- open/unresolved;
- addressed;
- explicitly rejected/dismissed by an authorized disposition;
- superseded by another finding;
- blocked/unverifiable;
- out-of-scope/escalated.

A later revision may introduce new findings, but it must not silently omit an unresolved prior finding.

Conceptually:

```text
FindingDispositionRecord
  finding_id
  prior_round_ref
  current_round_ref
  disposition
  evidence_refs[]
  actor_or_execution_ref
```

BTN-120/BTN-122 review evidence and human annotation contracts should be reused where applicable rather than defining a second incompatible finding system.

---

## Exhaustion

Maximum-round exhaustion is a normal first-class workflow outcome, not an exception and not permission to start another loop.

When a round requests another iteration and `current_round == max_rounds`, Battalion must:

1. persist the final round record;
2. persist an exhaustion outcome;
3. execute exactly the recipe's declared exhaustion action.

Permitted exhaustion actions should be drawn from Battalion-owned workflow/recovery vocabulary, for example:

- HumanInterrupt;
- terminal failure;
- explicit escalation to another admitted workflow boundary.

An executing model cannot select a different exhaustion action or request "one more round."

Switching role, model, provider, process, worker, or presentation client does not reset exhaustion.

---

## HumanInterrupt and resume

HumanInterrupt can occur before, during, or after an iteration round.

On pause, Battalion must durably retain:

- iteration instance identity;
- current/consumed round count;
- governing scope revisions;
- current artifact lineage;
- unresolved finding identities;
- workflow recipe/version;
- recovery counters;
- resource budget consumption;
- the exact reason for the interrupt.

Resume continues the same admitted iteration instance unless the human decision explicitly changes governing scope or workflow admission in a way that requires successor history.

A UI button labeled "retry" must not be allowed to recreate the region with a fresh counter unless policy explicitly creates a new successor Run/iteration identity.

## Interaction with RFC-0018 recovery policy

RFC-0018 remains authoritative for failures and escalation triggers that occur during a round.

A round execution can therefore contain nested bounded recovery without changing the workflow round:

```text
round 2
  proposal stage
    provider failure
    → RFC-0018 bounded provider retry
    → success
  review stage
    valid "revise" disposition
  → iteration policy advances to round 3
```

Anti-evasion rules must operate across both systems:

- iteration count cannot reset recovery counters;
- recovery/replan cannot silently create a fresh iteration instance;
- model/provider escalation cannot reset either bound;
- successor Runs preserve predecessor linkage and consumed historical evidence under RFC-0017.

---

## Interaction with BTN-111 resource budgets

All execution inside all rounds contributes to the containing Run's Battalion-owned resource accounting.

At minimum:

- model/inference calls;
- tokens where available;
- retries;
- escalations;
- elapsed time where supported.

A round transition does not create a fresh resource budget.

If a resource limit is reached before the iteration's `max_rounds`, the resource policy wins: execution stops/routes according to the admitted resource/failure policy. A workflow round allowance is permission to continue *if other governance constraints also permit it*, not a reserved execution entitlement.

## Work-class-specific workflows

BTN-113 also requires Battalion to support multiple explicit workflow definitions rather than one universal SDLC graph.

RFC-0012's `WorkflowKind` / `WorkflowRecipe` model already provides the right base.

Examples:

### Feature

```text
approved feature specification
→ implementation
→ optional semantic review/remediation region
→ completion
```

### Defect

```text
demonstrated regression evidence
→ defect diagnosis/fix
→ verification
→ completion
```

### Intentional behavior change

```text
revised expected behavior/specification
→ implementation
→ verification against new expectation
→ completion
```

### Architecture

```text
admitted architecture question
→ evidence/proposal
→ human review/revision region
→ human acceptance
→ durable RFC/ADR
→ ticket decomposition
```

Different workflows may require different entry evidence and invariants. Battalion owns classification and recipe selection through the admitted workflow machinery; a model cannot decide that its current task has transformed into a different work class merely to obtain a different loop or entry contract.

## Presentation and history

CLI/desktop/history clients should be able to render bounded iteration directly from persisted records.

A minimal presentation can show:

```text
Architecture iteration — 3 round maximum
Scope: artifact://spec/abc@7

Round 1
  Proposal: architecture-proposal@1
  Review: request-revision
  Open findings: F-12, F-13

Round 2
  Proposal: architecture-proposal@2
  Review: request-revision
  Addressed: F-12
  Open: F-13, F-18

Round 3
  Proposal: architecture-proposal@3
  Review: accepted
  Addressed: F-13, F-18

Outcome: accepted in 3/3 rounds
```

Clients must not reconstruct this by interpreting model prose or chat chronology.

## Termination and recursion safety

Battalion should validate two levels of boundedness:

### Local bound

Each iterative region has a finite `max_rounds` and explicit exit behavior.

### Composition bound

A recipe must not compose iterative regions, recovery replans, workflow upgrades, or successor transitions in a way that creates a hidden autonomous cycle whose effective bound is reset each time.

Initial policy can be conservative: reject workflow definitions with recursive iterative-region ancestry or re-entry paths that cannot prove preservation of the original bound.

Battalion does not need a general theorem prover. It needs a finite declarative recipe model whose legal transition forms make unbounded recursion structurally unavailable.

---

## Failure and terminal semantics

Representative workflow dispositions should include:

- `accept` / `approve`;
- `revise` / `retry-round`;
- `escalate`;
- `fail`;
- `cancel`;
- `exhausted`.

These are workflow-level dispositions, not necessarily the exact serialized enum names.

RFC-0013 remains the role-attempt outcome contract. A role returning `COMPLETED`, `BLOCKED`, or `ESCALATED` does not by itself define the workflow transition. Battalion translates valid role evidence through the admitted recipe/policy.

Cancellation is a terminal Run lifecycle outcome consistent with RFC-0017. It must not be represented as "iteration exhausted" merely because both stop execution.

## Candidate implementation shape

This RFC is architecture-only, but the eventual implementation likely needs changes in these areas:

- workflow recipe/schema definitions and admission validation;
- workflow-specific Run persistence for active iteration state;
- immutable append-only round records;
- typed boundary/artifact persistence integration;
- graph/runtime routing that consults iteration policy rather than embedding counters in role nodes;
- HumanInterrupt resume plumbing;
- recovery-policy integration;
- resource-budget integration;
- application inspection DTOs;
- CLI/desktop history rendering;
- deterministic tests for topology/policy rejection and runtime transitions.

The feature should remain below presentation clients and above model/provider implementations.

## Test matrix for implementation

Implementation should cover at minimum:

| Scenario | Expected result |
| --- | --- |
| immediate approval | round 1 recorded; success |
| one revision | rounds 1-2 recorded; success |
| multiple revisions | monotonic round history; success within bound |
| max-round exhaustion | exhaustion recorded; declared action only |
| explicit escalation | durable escalation; no silent retry |
| cancellation | terminal cancellation; no resume under same terminal Run |
| restart/resume | same iteration identity/count/artifact lineage |
| HumanInterrupt | pause/resume without counter reset |
| model change between stages | identity changes in evidence, loop identity unchanged |
| provider failover | recovery evidence recorded; loop count unchanged |
| omitted prior finding | boundary/policy rejection or explicit unresolved evidence |
| immutable-scope mutation | rejected/escalated |
| resource exhaustion first | budget policy stops iteration before max rounds |
| recovery retries inside round | retry counters change; round does not |
| role/model switch to evade bound | no reset |
| recursive loop declaration | admission rejected |
| workflow re-entry resetting loop | admission rejected or preserved ancestry required |
| distinct feature/defect/change recipes | correct entry evidence and admitted workflow selected |

## Alternatives considered

### 1. Hard-code specific role loops

Example: `Architect → Reviewer → Architect`.

Rejected because it couples the workflow primitive to today's role names, makes reuse difficult, and invites duplicated semantics for Review/Specification/other workflows.

### 2. Treat all iteration as RFC-0018 retry/recovery

Rejected because a valid review-requested revision is not an execution failure. It would also overload retry counters and blur operator history.

### 3. Let LangGraph cycles define the behavior implicitly

Rejected because graph topology does not by itself define authority, maximum rounds, artifact identity, exhaustion semantics, immutable scope, or anti-evasion rules.

### 4. Let the model decide when it is done

Rejected. That is precisely the opaque coding-agent loop-controller behavior Battalion is intended to avoid. Models produce evidence and dispositions; Battalion owns admitted continuation and termination.

### 5. Start a new Run for every round

Not selected as the default. A round is usually one lifecycle inside one first-class Run and should share governing scope, budgets, history, and termination. Separate first-class Runs remain appropriate when the surrounding workflow itself crosses a first-class lifecycle/authority boundary under RFC-0014.

## Open questions

### 1. Should round count mean full region passes or revision attempts?

This draft proposes **full admitted round outcomes**: a round is consumed when the region reaches its declared round-outcome boundary with a valid result.

That keeps provider retries/recovery attempts out of the round count and gives history a stable engineering meaning.

### 2. What should happen when governing scope changes after human input?

This draft proposes that a material governing-scope change **does not continue the same iteration instance**. It should create a successor iteration instance or successor Run with explicit lineage.

The remaining question is whether the default should be a new instance inside the same active Run or a successor Run. The answer may differ by WorkflowKind.

### 3. Should exhaustion route through RFC-0018 or be a direct workflow transition?

This draft treats exhaustion as a **workflow outcome** whose declared action may invoke HumanInterrupt, terminal failure, or another admitted escalation path.

That avoids misclassifying "used all planned rounds" as an execution failure, while still reusing the same application routing/authority machinery where practical.

### 4. How much static composition analysis is required for v1?

A conservative first implementation could prohibit nested iterative regions and any re-entry into an already-exited iteration region. Later versions could admit more composition only when ancestry/bounds remain mechanically provable.

This is likely safer than trying to support arbitrary cyclic workflow graphs immediately.

### 5. Should unresolved findings use one general finding contract?

This draft prefers reuse of BTN-120/BTN-122 review/finding/annotation primitives where they fit. We should avoid creating an iteration-specific finding ontology unless those contracts prove too review-specific.

---

## Proposed decision

Adopt bounded iteration as a **declarative, versioned iterative-region capability inside `WorkflowRecipe`**, with:

- finite pre-admitted round bounds;
- closed permitted outcomes/transitions;
- durable iteration and round identity;
- RFC-0015 artifact-only boundaries;
- optional immutable governing scope;
- durable unresolved-finding tracking;
- explicit exhaustion;
- no model-authorized bound expansion;
- no reset through role/model/provider/recovery changes;
- HumanInterrupt-safe resume;
- composition with RFC-0018 recovery policy and BTN-111 resource budgets;
- work-class-specific workflow recipes rather than one universal SDLC graph.

The open questions above should be resolved before this RFC is accepted and decomposed into implementation work.
