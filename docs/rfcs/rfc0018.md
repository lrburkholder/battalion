# RFC-0018 — Declarative Run Failure, Recovery, and Escalation Policy

**Status:** Accepted  
**Date:** 2026-09-03  
**Ticket:** BTN-109  
**Author:** Architecture  
**Target:** Post-v2 workflow orchestration  
**Related:** `philosophy.md`, BTN-8, BTN-27, BTN-30, BTN-55, BTN-107, BTN-108, BTN-111, BTN-112, BTN-113, BTN-118, BTN-120, BTN-125, BTN-131, BTN-133, BTN-134, RFC-0012, RFC-0013, RFC-0014, RFC-0015, RFC-0017, ADR-0024

---

## Summary

Battalion should make Run failure handling and recovery a **versioned declarative policy owned by admitted workflow/application authority**, rather than a collection of role-specific retry loops, exception branches, and prompt instructions.

The core architecture is:

1. execution produces a typed failure, boundary condition, role outcome, ambiguity, or policy trigger;
2. Battalion classifies that trigger using Battalion-owned deterministic semantics;
3. an admitted `FailureEscalationPolicy` is evaluated against the trigger and the Run's durable recovery counters/history;
4. the policy selects exactly one bounded action;
5. Battalion validates that action against workflow, Actor, inference/cost, side-effect, write-scope, and authority constraints;
6. Battalion persists the decision and evidence before executing the action;
7. exhaustion or any decision outside delegated authority routes to a human-controlled interrupt or terminal outcome according to policy.

The initial action vocabulary should cover:

- terminal fail/stop;
- bounded retry of an explicitly identified execution boundary;
- bounded replan/re-entry at an explicitly permitted workflow boundary;
- escalation to a named Battalion role or workflow target;
- escalation to an explicitly permitted inference target/model tier policy;
- HumanInterrupt;
- a narrowly scoped **bounded ruling** for reversible implementation-level ambiguity that remains entirely inside already approved product, architecture, authority, security, write-scope, side-effect, and cost constraints.

A model does not select or rewrite the governing recovery policy. A model may produce semantic evidence that a policy trigger exists, but Battalion owns classification, policy matching, limits, action validation, persistence, and routing.

The guiding distinction is:

```text
model/role says what happened or what ambiguity remains
Battalion policy decides what recovery actions are admitted
human decides whenever the required judgment crosses delegated authority
```

---

## Problem

Battalion already contains several kinds of recovery behavior, but they are not yet governed by one explicit policy model.

Examples include:

- checkpoint rejection retry behavior and same-cause detection;
- provider/infrastructure failure handling;
- HumanInterrupt triggers;
- BTN-133 `BLOCKED` and `ESCALATED` role outcomes;
- BTN-108 typed boundary failures;
- cost/inference-policy refusals and zero-cost fail-closed behavior;
- side-effect ambiguity and reconciliation;
- workflow upgrade behavior from RFC-0012;
- future bounded iteration from BTN-113.

These mechanisms are individually useful, but without a common recovery policy boundary the graph/application layer can accumulate special cases such as:

```text
if reviewer rejected: retry driver
elif provider failed: retry provider
elif boundary missing: block
elif role escalated: interrupt
elif model too weak: switch model
...
```

That creates three risks.

### 1. Recovery authority becomes implicit

An executing role may appear to decide whether it should retry, replan, switch roles, or request a stronger model merely because its prompt or node happens to contain that behavior.

This conflicts with RFC-0013, which explicitly says a role result does not select the next workflow. Recovery routing must remain Battalion/application policy.

### 2. Bounds can be bypassed across mechanisms

A retry bound on one node is insufficient if the Run can reset the effective loop by switching role, model, provider, subgraph, or workflow boundary. A bounded system needs counters and ancestry/transition semantics that survive those changes.

### 3. Human authority can erode by convenience

A useful lesson from autonomous-agent systems is that low-risk reversible ambiguity should not stall every Run. But a generic "make a ruling" escape hatch would be dangerous: implementation convenience must not become product, architecture, security, permission, destructive-action, or material tradeoff authority.

Battalion therefore needs an explicit distinction between **delegated bounded implementation judgment** and **human-required authority**.

## Goals

- define a versioned, declarative failure/escalation policy contract;
- keep policy selection outside model prompts and role outputs;
- classify materially different failure families with stable Battalion-owned semantics;
- make retry, replan, role escalation, model escalation, bounded ruling, terminal failure, and HumanInterrupt explicit policy actions;
- make every non-trivial recovery action bounded;
- prevent recursive or cross-mechanism loops from resetting recovery limits;
- preserve HumanInterrupt as the required/default path for authority-bearing decisions;
- permit explicitly delegated reversible implementation rulings without turning the Driver/controller into an autonomous Architect/Product owner;
- make recovery evidence durable and inspectable without parsing model prose;
- preserve BTN-107 terminal-history immutability;
- respect inference identity, diversity, endpoint, cost, and zero-cost policy during model escalation;
- compose with RFC-0012 `WorkflowRecipe`, RFC-0013 role outcomes, RFC-0015 boundary failures, and future BTN-113 bounded iteration rather than duplicating them;
- support application/CLI/desktop explanation of why a Run took a recovery path.

## Non-goals

- creating an autonomous planner that invents recovery graphs;
- allowing models to author or broaden their own recovery policy;
- replacing typed role outcomes with exceptions;
- converting every application exception into a retryable policy event;
- allowing bounded rulings to make product or architecture decisions;
- allowing model escalation to cross cost, endpoint, diversity, or authority policy;
- reopening or mutating terminal historical Runs;
- solving arbitrary distributed-workflow compensation;
- making every failure recoverable.

## Architectural boundary

Conceptually:

```text
execution / boundary / provider / deterministic gate
                    |
                    v
            typed TriggerEvidence
                    |
                    v
        FailureEscalationPolicy vN
                    |
          deterministic evaluator
                    |
        +-----------+-----------+
        |           |           |
     action      exhausted   no valid match
        |           |           |
        v           v           v
 action validator  fallback   fail-closed
        |
        v
 durable RecoveryDecision
        |
        v
 admitted transition / HumanInterrupt / terminal outcome
```

The **application/domain layer** owns:

- policy admission and identity;
- trigger classification;
- durable recovery counters/history;
- action validation;
- Run lifecycle transitions;
- Actor authorization;
- inference/cost policy enforcement;
- HumanInterrupt creation/resolution;
- terminal-history enforcement;
- persistence and inspection.

Graphs/nodes consume the resulting admitted transition. They do not redefine recovery authority.

## Relationship to `WorkflowRecipe`

RFC-0012 establishes `WorkflowRecipe` as the registered, versioned execution policy artifact. BTN-109 should extend that model by allowing a recipe to reference one or more exact recovery policies rather than embedding arbitrary recovery code into each stage.

Conceptually:

```text
WorkflowRecipe
  recipe_id
  recipe_version
  workflow_kind
  stages[]
  mandatory_verification[]
  human_interrupt_policy_refs[]
  failure_escalation_policy_refs[]
  ...
```

A recipe may bind different named recovery policies to different stage classes or trigger domains, but the set must be finite and admitted before execution.

The executing model cannot replace:

```text
policy: implementation-default@1.0
```

with:

```text
policy: whatever-lets-me-continue@latest
```

Policy identity/version becomes durable Run admission evidence and is retained in every recovery decision that uses it.

## Trigger model

Recovery policy should operate on a normalized Battalion-owned trigger rather than arbitrary exception text.

Proposed initial family:

```text
RecoveryTrigger
  trigger_id
  trigger_kind
  source
    run_id
    stage/node/workflow boundary
    execution_id?
  occurred_at
  failure_class?
  role_result_ref?
  boundary_failure_ref?
  gate_evidence_ref?
  ambiguity_ref?
  side_effect_ref?
  evidence_refs[]
```

### Initial failure classes

At minimum:

```text
ROLE_REJECTION
ROLE_BLOCKED
ROLE_ESCALATED
PROVIDER_INFRASTRUCTURE_FAILURE
DETERMINISTIC_GATE_FAILURE
AUTHORIZATION_POLICY_DENIAL
CANCELLATION
MALFORMED_CONTRACT_OR_INPUT
BOUNDARY_COMPATIBILITY_FAILURE
WRITE_SCOPE_OR_ROLE_CONTRACT_VIOLATION
SIDE_EFFECT_AMBIGUITY
RESOURCE_OR_COST_POLICY_EXHAUSTION
OTHER_NONRETRYABLE_APPLICATION_FAILURE
```

These classes do not erase the more specific evidence already owned by other mechanisms. For example, RFC-0015's `MISSING_REQUIRED_INPUT` remains the canonical boundary finding; BTN-109 may normalize it into a broader recovery trigger class while retaining the original evidence reference.

### Role results are not failures by definition

RFC-0013 distinguishes semantic role outcomes from platform-detected failures.

Therefore:

- `BLOCKED` and `ESCALATED` may generate recovery triggers;
- `COMPLETED_WITH_CHANGE` / legal `COMPLETED_WITH_NO_CHANGE` normally do not;
- malformed output, prohibited writes, provider errors, and deterministic contract violations remain Battalion-detected trigger sources rather than model-declared results.

## Policy contract

A policy has stable Battalion-owned identity/version independent of Python class names.

Conceptually:

```text
FailureEscalationPolicy
  policy_id
  policy_version
  schema_version
  rules[]
  default_action
  global_bounds
  compatibility_identity
```

Each rule is declarative:

```text
RecoveryRule
  rule_id
  match
    trigger_kinds[]
    failure_classes[]
    workflow_kinds[]?
    stages[]?
    roles[]?
    reason_codes[]?
  action
  bounds
  exhaustion_action
```

Rule ordering must be deterministic. Prefer either explicit priority with uniqueness validation or first-match order in the immutable admitted policy. Ambiguous overlapping rules that could produce different actions should be rejected at policy admission rather than resolved dynamically by a model.

## Action vocabulary

### 1. `FAIL`

Terminally fail the active Run or workflow according to Run-kind lifecycle semantics.

This is not equivalent to crashing. Battalion persists the triggering evidence and policy decision before terminalization where possible.

### 2. `RETRY`

Retry an explicitly identified execution boundary.

```text
RetryAction
  target_boundary
  max_attempts
  backoff_policy?
  permitted_failure_classes[]
```

A retry re-executes the same admitted obligation. It does not broaden scope, redefine architecture, reset workflow ancestry, or silently choose a new model family unless a separate admitted model-escalation action says so.

### 3. `REPLAN`

Return to an explicitly admitted planning/workflow boundary to produce a revised downstream plan or task set.

`REPLAN` is not "let the current model invent a new plan in place." It must identify a legal re-entry target already present in the admitted workflow family.

Conceptually:

```text
ReplanAction
  target_boundary
  max_replans
  immutable_governing_refs[]
  permitted_revision_scope
```

A replan may revise derived planning artifacts within their authority. It cannot silently revise the governing approved specification, accepted ADR, human decision, or other immutable scope artifact.

### 4. `ESCALATE_ROLE_OR_WORKFLOW`

Route to one named Battalion role/workflow boundary admitted by the recipe/policy.

```text
RoleWorkflowEscalationAction
  target_role | target_workflow_kind/recipe
  max_escalations
  required_input_contract
```

The target is policy data, not model output. A model may supply evidence for why escalation is needed but cannot name an arbitrary privileged destination.

### 5. `ESCALATE_MODEL`

Retry an admitted role/boundary using a stronger or alternate inference target permitted by Battalion inference policy.

```text
ModelEscalationAction
  target_policy_id
  max_model_escalations
  preserve_role_and_scope = true
```

The action selects an **inference target policy**, not an unvalidated model string supplied by the executing role.

Model escalation must still satisfy ADR-0024 and related inference policy:

- configured cost policy;
- local/free/paid boundaries;
- endpoint/location policy;
- model-family identity requirements;
- Driver/Reviewer diversity constraints;
- provider failover constraints;
- future Run resource budgets.

A `free-only` Run does not become paid-capable merely because the cheaper model failed.

### 6. `HUMAN_INTERRUPT`

Enter a durable human-controlled decision boundary.

```text
HumanInterruptAction
  interrupt_kind
  required_authority
  allowed_resolutions[]
```

This is the required/default action whenever continuing requires product, architecture, authority/permission, security/risk, destructive/irreversible, external side-effect approval, or material approved-tradeoff judgment.

### 7. `BOUNDED_RULING`

Permit a narrowly delegated implementation-level decision without stopping the Run.

This is intentionally the most constrained action in the vocabulary.

A bounded ruling is legal only when **all** of the following are true:

- the ambiguity is implementation-level rather than product/architecture intent;
- every candidate action remains within the same approved specification and architecture;
- every candidate action remains within existing write scope and capability/Actor authority;
- no candidate introduces a security-sensitive decision or changes an existing security policy;
- no candidate performs or newly authorizes a destructive/irreversible action;
- no candidate newly authorizes an external side effect requiring approval;
- no candidate materially changes an explicitly approved tradeoff;
- the decision is reasonably reversible;
- the expected consequence/rework cost if wrong is below a configured bound;
- the policy explicitly enables bounded rulings for this stage/ambiguity class;
- the ruling count remains within its configured bound.

If any condition cannot be established, bounded ruling is unavailable and policy falls through to the configured escalation, normally HumanInterrupt.

## Bounded ruling evidence

A ruling must produce durable structured evidence distinct from raw model reasoning.

Conceptually:

```text
BoundedRuling
  ruling_id
  policy_id + policy_version
  trigger_id
  run_id
  stage/execution identity
  decision_summary
  candidate_actions[]
  selected_action
  governing_refs[]
  delegated_authority_evidence[]
  reversibility_evidence
  expected_consequence_if_wrong
  expected_rework_cost_class
  prohibited-boundary checks[]
  producing model/Actor provenance
  created_at
```

The evidence should explain **why Battalion admitted the ruling**, not preserve a hidden chain-of-thought transcript.

A role/model may propose the selected implementation choice, but Battalion validates that the ruling contract and all policy predicates are satisfied before the Run continues.

---

## Human-required decision classes

The following are outside default bounded ruling authority and should route to HumanInterrupt unless another explicit human-authored policy grants a separately defined authority path:

- product scope or externally observable intent changes;
- new or changed architecture/ownership/public-interface decisions;
- permission, capability, Actor authority, or write-scope expansion;
- security/privacy/secrets/risk policy decisions;
- destructive or irreversible actions;
- external side effects that require approval;
- material changes to explicitly approved latency/cost/quality/compatibility/operability tradeoffs;
- overriding a deterministic policy denial;
- changing the governing recovery policy itself.

This list should be treated as a **deny boundary**, not as examples a model may reinterpret loosely.

## Boundedness and recursive-loop prevention

Every action capable of continuing execution must be bounded.

The policy evaluator should maintain platform-owned counters for at least:

```text
retry_count by recovery scope
replan_count by recovery scope
role/workflow escalation count
model escalation count
bounded ruling count
overall recovery transition count
```

BTN-111 may later supply broader Run resource accounting, but BTN-109 should define the recovery-specific invariants now.

### Bounds attach to logical recovery scopes, not process instances

Restarting a worker, changing provider, switching model, or re-entering a stage must not reset a consumed recovery bound.

A logical scope key should derive from stable Run/workflow/boundary identity and policy rule identity.

### Global transition ceiling

In addition to per-rule bounds, every policy should have a finite maximum recovery-transition count or inherit a finite recipe/project maximum.

This prevents cycles such as:

```text
A retry 2x -> role B -> model escalation -> A retry 2x -> role B -> ...
```

from being technically bounded at each edge while unbounded in aggregate.

### Cycle validation at admission

Where possible, Battalion should statically inspect the policy/recipe transition graph and reject configurations containing a reachable recovery cycle without a monotonically consumed finite bound and deterministic exhaustion path.

Runtime counters remain necessary because data-dependent rule selection may still create cycles not obvious from one edge in isolation.

---

## Exhaustion semantics

Every continuing action has an explicit exhaustion action.

Examples:

```text
provider failure
  -> retry same target up to 2
  -> escalate_model once if zero-cost policy allows
  -> HumanInterrupt

role rejection
  -> retry Driver up to 2 for distinct/correctable cause
  -> replan once if policy permits
  -> HumanInterrupt

boundary malformed
  -> FAIL
```

Exhaustion may select `FAIL`, `HUMAN_INTERRUPT`, or another explicitly bounded action. It may not implicitly reset the same rule.

---

## Cancellation

Cancellation is not a retryable failure.

Once an authorized cancellation is admitted:

- autonomous/mechanical recovery stops;
- no model/role escalation is attempted merely to avoid cancellation;
- side effects already in flight follow existing reconciliation/safety semantics;
- the Run reaches the RFC-0017 `cancelled` terminal lifecycle state;
- the cancellation and any cleanup/reconciliation evidence remain durable.

RFC-0017 establishes cancellation as a first-class terminal lifecycle outcome distinct from infrastructure failure. BTN-109 consumes that lifecycle contract directly: cancellation stops in-Run recovery, and any later retry or continuation must use RFC-0017 successor-history semantics rather than reopening the cancelled Run.

---

## Stale policy and version semantics

A running or resumable Run executes under the exact policy identity/version admitted for that Run.

A newer policy version does not silently reinterpret old recovery history.

Conceptually:

```text
Run admitted with implementation-default@1.2
project later upgrades to implementation-default@2.0
resume old Run
  -> continue under 1.2 if runtime still supports it
  -> otherwise explicit compatibility/refusal path
```

BTN-118 will govern project/runtime compatibility more broadly. BTN-109's invariant is that recovery semantics are version-pinned evidence, not "latest policy" lookup.

If the exact admitted policy is unavailable or unsupported on resume, execution must fail closed into an inspectable compatibility/blocking state. It must not substitute the current default policy.

## Persistence and inspectability

Every policy-selected action produces durable recovery evidence.

Conceptually:

```text
RecoveryDecision
  decision_id
  run_id
  trigger_ref
  policy_id
  policy_version
  rule_id
  selected_action
  counters_before
  counters_after
  exhaustion_state
  validation_evidence_refs[]
  resulting_status/phase/boundary
  created_at
```

For bounded rulings, the `BoundedRuling` artifact is additionally linked.

Application/history surfaces should be able to answer:

- what triggered recovery;
- which policy/version governed;
- which rule matched;
- what action was selected;
- why it was permitted;
- how many retries/replans/escalations remained;
- whether a human decision occurred;
- what eventually exhausted the path.

No client should need to reconstruct this from Driver/Reviewer chat prose or exception strings.

## Terminal Run immutability

RFC-0017 establishes the accepted invariant that a terminal Run may be referenced, superseded, retried, continued, or branched from but not rewritten.

BTN-109 therefore distinguishes:

### In-Run recovery

Allowed only while the Run is non-terminal and the admitted policy still permits transitions.

### Retry/supersession after terminalization

Creates a new Run or other explicitly linked follow-up identity according to BTN-107. The original Run's policy decisions, failure evidence, model calls, artifacts, and terminal outcome remain unchanged.

A UI action labelled "retry failed Run" must therefore eventually mean "create a linked new execution from the historical Run's admissible inputs/evidence," not mutate the failed historical record back to `IN_PROGRESS`.

## Relationship to existing mechanisms

### Existing checkpoint rejection retry

Current `retry_bound`, `reviewer_rejection_history`, and same-cause logic are implementation-specific predecessors of this policy mechanism.

Migration should preserve their behavioral invariant while moving the **routing decision and counters** into admitted recovery policy. Rejection analysis remains semantic evidence; it does not own retry authority.

### Existing HumanInterrupt triggers

HumanInterrupt remains a first-class authority boundary. BTN-109 should reuse existing interrupt/human-action persistence and evolve it where needed rather than create a second pause mechanism.

### RFC-0013 role outcomes

`BLOCKED` and `ESCALATED` become inputs to policy evaluation. The role never chooses the next node.

### RFC-0015 boundary failures

Boundary failures remain typed domain evidence and map into recovery triggers. BTN-109 supplies the lifecycle/routing decision that RFC-0015 deliberately leaves open.

### RFC-0012 workflow upgrade ratchet

Workflow admission/upgrade policy is related but distinct. An upgrade trigger may cause a policy-driven replan or workflow escalation, but recovery policy cannot downgrade a stronger admitted recipe.

### BTN-113 bounded iterative edges

Bounded iteration is workflow structure; BTN-109 is failure/recovery policy. Iteration exhaustion should produce a typed trigger that BTN-109 can route, rather than starting an unrelated new retry loop.

### ADR-0024 inference policy

Model escalation is subordinate to inference identity/cost/diversity policy. Recovery never grants permission to cross those boundaries.

### Side-effect ambiguity

Ambiguous external operations are special because blind retry may duplicate an effect. Existing side-effect reconciliation semantics remain authoritative; BTN-109 can route the resulting typed ambiguity but cannot classify it as an ordinary safe retry merely because a retry action exists.

## Policy authoring and admission

Policies are configuration/governance artifacts, not model output.

Initial authoring may use Pydantic-backed models consistent with Battalion's current Python architecture, but durable identity/versioning should follow RFC-0015's implementation-independent contract principles.

Policy admission validates at minimum:

- stable identity/version;
- known action/trigger enums;
- deterministic rule precedence;
- finite bounds for all continuing actions;
- valid exhaustion paths;
- allowed target boundaries/roles/workflows;
- allowed model-target policies;
- no bounded ruling rule that grants prohibited authority;
- static cycle safety where determinable;
- compatibility with the selected WorkflowRecipe;
- referenced policy/contract versions supported by the runtime.

Invalid policy blocks Run admission; the runtime does not "do its best" with a partially understood recovery policy.

---

## Defaults and fail-closed behavior

Battalion should not require every project to author a complex policy before any Run can execute. It may ship a small finite set of Battalion-owned default policies.

However:

- the exact default identity/version must be admitted and persisted like any other policy;
- unknown trigger/action/version combinations fail closed;
- no-match behavior is explicit;
- default policies should prefer HumanInterrupt over autonomous broadening;
- bounded rulings should be disabled unless a policy explicitly enables them for a narrow scope.

A safe initial default is conservative:

```text
known transient infrastructure failure -> small bounded retry
known deterministic correctable implementation rejection -> existing bounded retry behavior
role escalation / authority ambiguity -> HumanInterrupt
malformed contract / authorization denial -> fail or HumanInterrupt according to typed cause
unknown condition -> HumanInterrupt or FAIL, never autonomous invention
```

## Alternatives considered

### A. Keep recovery inside each graph/node — rejected

Simple locally, but duplicates logic, makes bounds inconsistent, and lets role implementation details become authority.

### B. Let a planner/model choose recovery dynamically — rejected

This is flexible but violates Battalion's human-directed architecture and makes loop bounds, cost policy, authority, and auditability probabilistic.

### C. One global hard-coded recovery switch statement — rejected

Better than prompt policy but still makes workflow-specific recovery evolution require code changes and does not provide durable versioned semantics.

### D. Declarative admitted policy + deterministic evaluator — proposed

This gives Battalion explicit bounded recovery semantics while still allowing different WorkflowRecipes/projects to choose different safe behaviors.

### E. Always HumanInterrupt on any ambiguity/failure — safe but too costly

This preserves authority but creates avoidable stalls for transient infrastructure failure and reversible implementation detail. Battalion should automate mechanical recovery where policy can prove it stays inside approved boundaries.

## Migration strategy

Implementation should be incremental.

### Phase 1 — policy/evidence primitives

- stable policy identity/version;
- trigger/failure classification;
- action models;
- deterministic rule evaluator;
- recovery counters and decision evidence;
- policy admission validation;
- conservative built-in default policy.

### Phase 2 — reconcile existing implementation retry

Move current checkpoint rejection retry/same-cause routing behind the policy evaluator while preserving behavior and tests.

### Phase 3 — role/boundary/infrastructure triggers

Integrate RFC-0013 role outcomes, RFC-0015 boundary failures, provider failures, deterministic gates, and authorization/policy denials.

### Phase 4 — model escalation and bounded rulings

Add model target-policy escalation only after inference-policy validation is wired. Add bounded rulings behind explicit opt-in policy and strong negative-authority tests.

### Phase 5 — broader workflow reuse

Use the same mechanism for Review Run, Architecture Run, bounded iteration exhaustion, significance routing, resource-budget exhaustion, and future Run kinds.

## Proposed decisions

The current architectural proposal is to accept these invariants:

1. **Failure/recovery routing is Battalion-owned policy, not role/model authority.**
2. **`WorkflowRecipe` references exact versioned recovery policy artifacts.**
3. **Recovery operates on typed Battalion-owned triggers that retain references to more specific source evidence.**
4. **The initial action vocabulary is `FAIL`, `RETRY`, `REPLAN`, role/workflow escalation, model escalation, `HUMAN_INTERRUPT`, and explicitly enabled `BOUNDED_RULING`.**
5. **Every continuing recovery action is bounded, and a global recovery-transition ceiling prevents cross-edge infinite loops.**
6. **Policy admission rejects ambiguous precedence, unsupported versions, invalid targets, unbounded cycles, and authority-broadening ruling rules.**
7. **Bounded rulings are reversible implementation-detail judgments only; they do not grant product, architecture, security, permission, destructive-action, side-effect-approval, or material-tradeoff authority.**
8. **HumanInterrupt is the required/default path when required judgment crosses delegated authority.**
9. **Model escalation selects a Battalion-owned inference target policy and remains subordinate to cost, endpoint, identity, diversity, and zero-cost policy.**
10. **Every retry, replan, escalation, ruling, exhaustion, and human escalation produces durable inspectable recovery evidence.**
11. **A Run resumes under its exact admitted policy/version; "latest" policy lookup cannot silently reinterpret recovery behavior.**
12. **Terminal Runs are never reopened by recovery; post-terminal retry/supersession creates linked new history under BTN-107 semantics.**
13. **Existing checkpoint retry, HumanInterrupt, role outcomes, boundary failures, workflow upgrade, bounded iteration, and side-effect semantics are reconciled through this mechanism rather than duplicated.**

## Resolved architecture decisions

Architecture review resolved the remaining design questions as follows:

### 1. Policy granularity

A `WorkflowRecipe` may reference a **small finite set of recovery policies keyed by stage or trigger domain**, with every policy reference explicitly bound by the admitted recipe.

One monolithic policy would become unwieldy across infrastructure, implementation, review, and human-boundary failures. Arbitrary per-node policy fragments would recreate the fragmentation this RFC is intended to remove.

### 2. Rule matching model

Rules use **first-match order in the immutable versioned policy**.

Policy admission must reject materially ambiguous overlaps where ordering would produce different recovery outcomes. Numeric priority is not added because it would introduce another precedence field without eliminating ambiguity.

### 3. Bounded ruling decision producer

`BoundedRuling` is a **capability independent of its producer**.

Deterministic selection is preferred when the choice can be made mechanically. Otherwise an active role/model may propose the ruling only when the admitted policy explicitly grants that capability for the relevant stage and ambiguity class. Battalion still validates the ruling against all authority and safety predicates before continuation. A dedicated adjudication role is not required merely to make the primitive safe.

### 4. Rework-cost representation

Bounded rulings use the ordinal vocabulary:

`TRIVIAL | LOW | MODERATE | HIGH`

plus a bounded explanation of expected consequence and rework if wrong.

Default policies admit only the low end of that scale for autonomous bounded rulings. Numeric hours or points are rejected as false precision.

### 5. Default unknown-condition behavior

Unknown/no-match handling distinguishes **operator-recoverable runtime uncertainty** from **semantics the runtime cannot safely interpret**.

- active human-directed Runs default to `HUMAN_INTERRUPT` for an otherwise valid but unmatched recoverable condition;
- malformed, unsupported, or uninterpretable policy/contract semantics fail closed at admission or compatibility validation rather than asking a human to bless undefined runtime behavior.

The policy contract should therefore keep unmatched-trigger behavior distinct from policy-admission/compatibility failure semantics.

### 6. Terminal recovery under RFC-0017

RFC-0017 is now accepted architecture and is directly consumed by BTN-109.

Recovery actions in this RFC operate only while a Run is non-terminal. Once a Run reaches `done`, `failed`, or `cancelled`, BTN-109 must not reopen it. Retry, correction, continuation, supersession, or branch-from behavior creates a new Run and typed append-only relationship evidence according to RFC-0017.

BTN-109 therefore does not define a competing terminal-history mechanism.

## Expected implementation decomposition after acceptance

BTN-109 should remain architecture-only. Acceptance should create separate implementation tickets for at least:

1. failure/escalation policy schema, registry, and admission validation;
2. typed trigger classification and normalization across current failure sources;
3. deterministic evaluator, recovery counters, cycle/exhaustion enforcement, and durable `RecoveryDecision` evidence;
4. migration of existing checkpoint rejection retry/same-cause behavior to policy;
5. RFC-0013 role outcome + RFC-0015 boundary failure integration;
6. provider/infrastructure and deterministic gate integration;
7. inference/model escalation integration with ADR-0024/BTN-55 policy;
8. bounded ruling capability and negative-authority enforcement;
9. application/CLI/desktop inspection and HumanInterrupt resolution surfaces;
10. RFC-0017 successor-history integration and compatibility/resume handling;
11. focused evaluation/UAT corpus for loops, exhaustion, authority denials, and low-risk rulings.
