# RFC-0007 — Actor Identity, Authority, Assignment, and Collaboration

**Status:** Accepted  
**Decision Date:** 2026-08-21  
**Ticket:** BTN-58  
**Author:** Architecture  
**Target:** Post-v1  
**Related:** BTN-30, BTN-32, BTN-43, BTN-59 through BTN-62, ADR-0020,
ADR-0021, ADR-0023

---

## Summary

Battalion needs a durable Actor identity before human attribution spreads from
BTN-43's string fields into assignment, remote clients, external identities,
and collaboration features. An Actor is a Battalion-owned identity with a
stable opaque identifier. Names, operating-system users, email addresses,
GitHub logins, authentication subjects, and credentials are attributes or
external bindings; none is the Actor's identity.

This RFC separates six concepts that must remain independently inspectable:

- identity answers which durable Actor a record refers to;
- authentication supplies evidence that a caller controls an account or local
  session;
- authorization decides whether that Actor may perform an operation;
- project membership binds an Actor to explicit capabilities in one project;
- assignment records current responsibility without granting authority; and
- collaboration evidence can recommend Actors but never grants a capability.

The proposal preserves `battalion.application` as the command and query
boundary. Presentation clients submit an authenticated Actor reference and a
typed operation; they never obtain permission to mutate `RunState`, Intel,
worker metadata, assignments, or project files directly.

## Status and delivery boundary

The human operator accepted this architecture and
[ADR-0026](../adrs/adr0026.md) on 2026-08-21. Acceptance establishes the
post-v1 identity, authority, assignment, ownership, and collaboration contract.
BTN-58 did not implement runtime behavior. BTN-59 now delivers Actor storage,
offline FTUE bootstrap evidence, local selection, shared application queries,
and compatible attribution for existing human evidence. Authentication,
authorization enforcement, assignment, ownership, and collaboration inference
remain follow-up work identified below.

## Goals

- define a stable identity for human and system actors;
- make project authority explicit and capability-based;
- distinguish execution roles from human responsibility and approval;
- retain immutable action and assignment provenance;
- keep historical BTN-43 string attribution readable without inventing facts;
- support local operation before remote authentication exists; and
- prevent inferred expertise or social proximity from becoming authority.

## Non-goals

- choosing an OAuth, hosted identity, directory, or account provider;
- implementing remote sessions, credential storage, or organization admin;
- changing Architect, Driver, Reviewer, or Refactorer graph authority;
- implementing BTN-59 through BTN-62; or
- treating assignment, ownership, authentication, or UI access as permission.

## Proposed Actor contract

An Actor is versioned independently from authentication and membership:

```text
Actor
  actor_id: opaque stable Battalion identifier
  kind: human | system
  display_name: mutable presentation label
  status: active | disabled
  created_at: timezone-aware timestamp
  created_by: Actor reference | null for the first bootstrap Actor
  provenance: bounded creation evidence
```

`actor_id` is never derived from mutable or provider-owned text. Human and
system Actors share the identity envelope so automation is attributable, but a
system Actor receives no implicit human approval capability. Disabling an
Actor prevents new authorized actions; it does not erase historical evidence.

An external identity binding associates an Actor with a provider instance and
provider subject. A GitHub login, email address, operating-system username, or
OAuth subject can change or be rebound under explicit administrative policy.
Credentials prove control of a binding or session and are stored outside the
portable Actor record.

Project first-time-use experience creates or selects the first local human
Actor before normal membership authorization can exist. Identity allocation
and the one-time bootstrap grant are persisted as separate facts. The initial
Actor has `created_by = null` plus explicit `first-project-bootstrap`
provenance; after its identifier exists, the append-only bootstrap event is
credited to that Actor and establishes its initial project membership and
administrative capabilities. The exception is valid only when the project has
no Actor or membership authority yet, is consumed atomically, and cannot be
replayed to recover or widen authority.

This FTUE needs no remote authentication. It is an explicit local trust-root
ceremony, not anonymous authority and not evidence that the operating-system
username is the durable identity.

## Membership and capabilities

Project membership binds one Actor to one project and an explicit set of
capabilities. The initial vocabulary is:

| Capability | Meaning |
| --- | --- |
| `inspect` | Read project and Run projections permitted by project policy |
| `operate` | Start, resume, and request cancellation of Runs |
| `resolve-interrupt` | Resolve a HumanInterrupt and authorize its corresponding resume path |
| `approve` | Make governed human decisions other than interrupt resolution |
| `assign` | Assign or hand off supported work targets |
| `administer` | Manage project membership and capability grants |

Capabilities are checked for the concrete application operation and target.
Authentication alone grants none. Membership alone grants only its listed
capabilities. Assignment and ownership grant none unless project policy also
assigns capabilities. `administer` is not a wildcard around application
invariants, write scopes, graph checkpoints, or immutable evidence.

Non-members and Actors without `inspect` are denied project and Run inspection
by default. Local unauthenticated read-only inspection is represented by an
explicitly configured system Actor with an `inspect`-only project membership;
it is not anonymous and must not be attributed as the human operator. A future
public projection remains separate publication policy rather than implicit
membership authority.

Architect, Driver, Reviewer, Refactorer, and Recon are Battalion execution
roles. They are not membership roles and must not be stored as substitutes for
human capabilities.

## Responsibility vocabulary

- **Actor:** durable identity attributed to an action or observation.
- **Operator:** Actor currently invoking a Run operation; a contextual label,
  not a durable role.
- **Assignee:** Actor currently expected to act on a Ticket or Run. Assignment
  communicates responsibility but does not authorize the action.
- **Owner:** the Actor currently accountable for a Ticket. Ownership is durable
  and historical, is implemented by BTN-61, and is neither necessarily the
  assignee nor an administrator.
- **Approval authority / reviewer:** Actor authorized by capability and any
  operation-specific policy to make a governed decision. This is distinct from
  the AI Reviewer node.
- **Observer:** Actor permitted to inspect a projection but not mutate it.

## Assignment and handoff

Ticket and Run assignment use a current projection plus append-only events:

```text
AssignmentEvent
  assignment_id
  target_type: ticket | run
  target_id
  assignee_actor_id: Actor | null
  assigned_by_actor_id
  assigned_at
  reason: bounded optional text
  supersedes_assignment_id: optional
```

Assigning or clearing responsibility appends an event and updates the derived
current assignment atomically. Reassignment transfers only current expected
responsibility. It does not transfer capabilities, rewrite earlier actions,
change authorship, erase prior assignment periods, or imply approval. A Run
may inherit a Ticket assignee only through an explicit, recorded policy; the
source assignment remains identifiable. Handoff requires the caller's
`assign` capability and any target-specific constraints.

BTN-61 also adds Ticket ownership as a separate current projection with
append-only ownership history. Initial ownership and every transfer record the
Ticket, owner Actor, authorizing Actor, timestamp, bounded reason, and
superseded ownership event. Ownership communicates durable accountability; it
does not grant capabilities, imply current assignment, rewrite provenance, or
automatically transfer when a Ticket or Run is reassigned. Ownership transfer
requires `assign` and the same stale-write protection as reassignment.

## Existing human actions and migration

BTN-43 records `HumanActionRecord.actor`, `HumanIntervention.actor`, and Recon
decision actors as bounded strings. BTN-59 should add a typed Actor reference
alongside a compatibility representation rather than parsing those strings.

New records must reference `actor_id`. Historical records containing only a
string remain readable as **legacy attribution** with the exact original value.
Migration must not match a string to a new Actor by display name, login, email,
or operating-system username. An explicit administrative linking operation may
add separate reconciliation evidence, but cannot rewrite the original record.

## Authorization matrix

| Application operation | Required baseline capability | Additional rule |
| --- | --- | --- |
| Inspect project or Run | `inspect` | Projection and sensitive-field policy still applies |
| Start Run | `operate` | Existing overwrite and configuration policy still applies |
| Resume Run without resolving an interrupt | `operate` | Canonical graph resume rules still apply |
| Resume Run while resolving an interrupt | `operate` and `resolve-interrupt` | The combined command must satisfy both checks |
| Resolve interrupt | `resolve-interrupt` | Actor must satisfy any interrupt-specific approval rule |
| Queue Correction | `operate` | Existing target and inactive-worker constraints remain |
| Queue Design decision | `approve` | Architect-only target constraint remains |
| Promote, edit-and-promote, or reject Recon candidate | `approve` | Existing immutable candidate and append-only decision rules remain |
| Request cancellation | `operate` | Worker lifecycle rules remain authoritative |
| Assign or hand off Ticket or Run; transfer Ticket ownership | `assign` | Target and responsible Actor must satisfy project policy |
| Change membership or grants | `administer` | Cannot grant beyond the administrator's delegable scope |

Denied commands return typed application failures and make no partial durable
mutation. Security-relevant denials should produce bounded audit evidence once
the audit contract is implemented. CLI, desktop, web, and mobile adapters all
receive the same results from the application boundary.

## Collaboration evidence

Observed co-editing, reviews, ownership history, domain expertise, response
patterns, and social-graph proximity are non-authoritative evidence. They may
rank or explain assignment recommendations. They may not create membership,
grant a capability, satisfy an approval rule, authenticate a caller, or silently
assign work. Recommendations must identify their evidence and remain subject to
an authorized human assignment operation.

## Follow-up delivery

- **BTN-59 — persistence and migration:** implemented versioned Actor identity,
  the one-time project FTUE bootstrap record, local selection, and legacy
  string attribution. Provider-owned external bindings remain authentication
  inputs for BTN-62 rather than fields on the portable Actor contract.
- **BTN-60 — application authorization:** implement membership, capability
  checks, typed denials, and operation-level policy.
- **BTN-61 — assignment, ownership, and handoff:** implement current assignment
  projections and immutable assignment history for Tickets and Runs plus
  current ownership and immutable ownership history for Tickets.
- **BTN-62 — authentication boundary:** define local and remote authentication
  inputs without coupling application policy to a provider.
- **Specification:** promote accepted identity, authority, and compatibility
  invariants into `spec.md` before implementation is called shipped.
- **ADR:** [ADR-0026](../adrs/adr0026.md) records the accepted durable Actor,
  capability, assignment, ownership, and collaboration boundaries.
- **Desktop and future clients:** carry authenticated Actor context and render
  typed denials; retain zero direct persistence authority.
- **Collaboration:** add recommendation evidence only after Actor and assignment
  contracts exist, with tests proving it cannot grant authority.

## Review decisions incorporated

- Local unauthenticated read-only inspection uses an explicit system Actor.
- Interrupt resolution has its own `resolve-interrupt` capability rather than
  sharing the general `approve` capability.
- Project FTUE establishes the first human Actor and attributes the one-time,
  auditable bootstrap event to that Actor.
- BTN-61 includes Ticket ownership and immutable ownership history alongside
  assignment and handoff.

## Alternatives rejected

### Use display names or provider logins as Actor IDs

They are mutable, provider-scoped, and collision-prone. Rebinding them would
silently rewrite the apparent author of durable evidence.

### Treat authenticated users as authorized project members

Authentication proves control of a credential or session, not project intent.
Conflating the two makes a provider configuration decision an authority grant.

### Let assignment imply permission

Assignment expresses expected responsibility. Making it authority would allow
a handoff to manufacture approval or administrative power.

### Infer approval authority from collaboration evidence

Observed expertise can be incomplete, stale, biased, or adversarially shaped.
It is useful for recommendations and unsafe as an authorization source.
