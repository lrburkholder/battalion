# RFC-0016 — Authentication, Principals, Remote Identity, and Delegated Execution

**Status:** Accepted  
**Date:** 2026-08-30  
**Ticket:** BTN-62  
**Author:** Architecture  
**Target:** BTN-M6 Collaborative Actors / future remote clients and workers  
**Related:** `philosophy.md`, RFC-0007, RFC-0011, RFC-0013, RFC-0014, RFC-0015, ADR-0025, ADR-0026, ADR-0028, ADR-0029, BTN-58 through BTN-63, BTN-64, BTN-65, BTN-70

---

## Summary

Battalion needs authentication for future remote presentation clients, shared servers, and remote execution workers without allowing an authentication provider, transport, machine credential, or presentation client to redefine Battalion identity or authority.

The central rule is:

> Authentication establishes a principal. Identity resolution may associate that principal with a durable Battalion Actor. Authorization remains a separate Battalion application decision.

A GitHub, Microsoft/Entra, operating-system, passkey, or future Battalion-hosted account is therefore not a Battalion Actor. It is an authentication or identity-link source. The durable Actor remains the Battalion-owned opaque `actor_id` accepted by RFC-0007 and ADR-0026.

This RFC also separates human authorization from machine execution. A remote worker may authenticate as a machine principal and execute an already admitted, bounded operation, but it must not impersonate the human Actor who authorized that operation or inherit that human's project capabilities.

Finally, authentication identity is not engineering contribution provenance. The credential that publishes a commit or invokes an operation does not prove who designed, implemented, reviewed, approved, or executed the work. Battalion must keep those facts distinguishable so future self-improvement can truthfully credit both human and Battalion/system contribution without allowing system contribution to imply self-authorization.

## Status and delivery boundary

This RFC is an accepted design for BTN-62. It does not authorize implementation of an authentication provider, hosted account service, web or mobile client, remote worker, shared server, OAuth flow, passkey flow, or credential store.

Follow-up tickets implement these contracts incrementally through the existing Actor, application authorization, integration, side-effect, workflow-contract, and persistence boundaries.

## Goals

- preserve Battalion-owned Actor identity across authentication providers, credential rotation, account renames, and transport changes;
- define the trust boundary between credentials/sessions and durable Actors;
- preserve offline/local desktop operation without requiring a hosted identity service;
- keep authentication and authorization mechanically distinct;
- define remote session, revocation, replay, transport, and secret-handling requirements at architecture level;
- distinguish human Actors from machine/worker principals;
- allow remote workers to execute bounded delegated authority without human impersonation;
- keep authentication principal, engineering contributor, authorizing Actor, and executor separately attributable;
- preserve historical provenance when identity links, credentials, sessions, or Actors are disabled or changed;
- remain provider-neutral; and
- fit the first-class Run and typed workflow-boundary architecture accepted after the original BTN-62 draft was written.

## Non-goals

- selecting GitHub OAuth, Entra, Azure, Auth0, passkeys, or another provider;
- defining a hosted Battalion account product;
- implementing organization administration or SSO policy;
- replacing project capability authorization accepted by RFC-0007 / RFC-0011 / ADR-0028;
- making provider permissions Battalion permissions;
- allowing arbitrary plugins to assert authenticated identity;
- defining a complete contribution-accounting or Git-attribution product;
- making model names durable human-equivalent identities;
- implementing remote worker scheduling or deployment; or
- changing graph role authority, write scope, interrupt semantics, or self-modification policy.

## Existing architectural constraints

RFC-0007 and ADR-0026 establish:

- `actor_id` as stable Battalion-owned identity;
- authentication, authorization, project membership, responsibility, and collaboration evidence as separate concepts;
- external identity values as bindings rather than Actor identity;
- local FTUE as an explicit project trust-root ceremony;
- disabled Actors remaining present for historical evidence;
- assignment and ownership granting no capabilities; and
- presentation clients using the shared Battalion application boundary rather than direct state mutation.

RFC-0011 and ADR-0028 establish that Battalion authorizes operations, not identities or transports. A provider may authenticate a caller and may separately permit or deny a provider-side operation, but only Battalion application/project policy grants Battalion authority.

ADR-0029 establishes durable replay-safe side-effect identity and evidence. Authentication and delegated execution must compose with that mechanism rather than create an independent external-effect ledger.

RFC-0014 and RFC-0015, accepted after the original BTN-62 draft, establish first-class Run envelopes and typed workflow boundary contracts. Authentication evidence, session references, and delegated execution evidence therefore attach to the relevant application/Run/operation boundary; they must not assume one universal Implementation-shaped `RunState` is the semantic carrier for every future workflow.

## Terminology

### Actor

A durable Battalion-owned participant identified by opaque `actor_id`. Actors may be human or system Actors. Actor identity is not derived from credentials, model names, display names, usernames, email addresses, or provider subjects.

### Authentication principal

The human account, local trust context, service, machine, or worker identity that successfully proved control of an accepted authentication mechanism for a particular authentication event or session.

A principal is runtime/security identity. It is not automatically a Battalion Actor.

### External identity binding

A credential-free mapping between an integration/provider-scoped external subject and a Battalion Actor. A binding resolves identity only. It grants no project capability.

### Authentication evidence

Bounded evidence produced after validating a local or remote authentication mechanism. It describes what principal was authenticated, by which configured mechanism, when, and under what validity constraints without persisting reusable credential material.

### Authenticated session

A short-lived runtime context derived from accepted authentication evidence. A session may resolve to a human Actor, a system Actor, or a machine principal that intentionally has no human Actor identity.

A session identifier is not durable Actor identity and must never replace `actor_id` in historical provenance.

### Authority

Permission for a concrete Battalion operation, evaluated at the shared application boundary under RFC-0007 / RFC-0011 / ADR-0028.

### Contributor

An Actor or attributable system execution that materially produced, transformed, reviewed, or otherwise contributed to an engineering artifact. Contribution is provenance, not permission.

### Executor principal

The authenticated principal that actually performs a side effect or executes a bounded delegated operation. The executor principal may differ from the Actor who authorized that operation.

## Core separation

Battalion must preserve this distinction:

```text
who authenticated
    != who contributed
    != who authorized
    != who executed the side effect
```

These identities may coincide in simple local use, but the architecture must not assume that they do.

For example, a future Battalion self-improvement history may truthfully contain:

```text
requested_by:        Human Actor A
designed_by:         Human Actor A + Battalion Architect system Actor
implemented_by:      Battalion Driver system Actor
reviewed_by:         Battalion Reviewer system Actor
accepted_by:         Human Actor A
executed_by:         remote worker principal W
git_published_by:    GitHub service principal B
```

Git metadata may project some of this information, but it must not become the canonical source of contribution or authorization truth.

## Proposed authentication boundary

```text
credential / local trust input
          |
          v
authentication adapter / verifier
          |
          v
AuthenticationEvidence
          |
          v
principal + optional identity resolution
          |
          +------ external subject ------+
          |                              |
          |                              v
          |                       ExternalIdentity
          |                              |
          |                              v
          |                            Actor
          |                              |
          +------------------------------+
                         |
                         v
                AuthenticatedSession
                         |
                         v
              battalion.application
                         |
                         v
             operation authorization
```

The authentication layer may prove a principal and resolve an explicit identity binding. It may not grant project membership, synthesize capabilities, bypass operation policy, select workflow authority, or mutate workflow state directly.

## AuthenticationEvidence contract

The precise implementation schema is follow-up work, but the architecture requires a versioned bounded record equivalent to:

```text
AuthenticationEvidence
  evidence_id
  mechanism_id
  principal_kind: human-account | local-session | service | machine | worker
  issuer_or_trust_domain
  subject
  authenticated_at
  valid_until?
  authentication_strength / assurance_class?
  credential_reference?       # symbolic/non-secret only
  session_binding?
  provider_evidence           # bounded non-secret metadata
```

Requirements:

- reusable credentials never enter durable workflow evidence, context projections, prompts, logs, or portable project identity;
- issuer/trust-domain identity is explicit so equal subject strings from different providers or tenants cannot collide;
- provider-specific claims remain bounded evidence rather than being copied wholesale into Actor or workflow records;
- unsupported, malformed, expired, revoked, or unverifiable evidence fails closed;
- provider authentication success alone does not create an Actor or membership; and
- absence of an identity binding is explicit and is not silently repaired by matching display name, email, username, or other mutable text.

AuthenticationEvidence is security evidence, not an authorization grant.

## Identity resolution

Human remote authentication normally follows:

```text
AuthenticationEvidence
  -> (integration/trust-domain, external subject)
  -> ExternalIdentity
  -> Actor
```

Resolution rules:

1. Provider subjects are scoped by configured integration/trust domain.
2. Exactly one active binding may resolve the subject for the relevant scope.
3. A missing binding does not auto-create an Actor.
4. Duplicate/conflicting bindings fail closed and require explicit administrative resolution.
5. A disabled external identity cannot establish a new Actor session.
6. A disabled Actor cannot perform new authorized actions even if an external credential remains valid.
7. Unlinking prevents future resolution through that link but does not rewrite history.
8. Relinking to a different Actor, if permitted, is an explicit audited administrative operation; historical evidence remains attributed to the Actor resolved at the time.
9. Credential rotation does not change ExternalIdentity or Actor when the stable provider subject remains the same.
10. Mutable provider presentation values may be metadata but are never the durable resolution key when a stable subject exists.

## Local desktop authentication

Battalion must remain usable offline without a hosted login service.

For a single-user local desktop deployment, the trusted local Battalion process may establish a local authenticated session for the explicitly selected active human Actor. This is a deployment-local trust decision, not proof that the operating-system username is the Actor.

Future deployments may strengthen local authentication with OS APIs, device credentials, passkeys, or other mechanisms without changing `actor_id`.

A shared-machine or remotely exposed deployment must not reuse the single-user local trust assumption merely because it runs on a desktop operating system.

## Remote human sessions

Web, mobile, and shared-server clients require explicit remote authentication before submitting protected application commands.

A remote authenticated session must:

- bind one authenticated principal and, when applicable, one resolved Actor;
- have bounded lifetime;
- support explicit logout/revocation;
- reject expired or revoked state;
- use replay-resistant session mechanisms;
- use transport security appropriate to deployment;
- avoid exposing provider credentials to presentation code where a server/platform boundary can contain them;
- never allow a client-supplied `actor_id` to substitute for server-side identity resolution; and
- re-run Battalion authorization for every protected application operation rather than treating session establishment as a blanket capability grant.

The session may cache identity resolution for its lifetime, but authorization evaluates current Actor status, membership, capabilities, operation, target, and policy.

## Machine and worker identities

A worker authenticates as itself. It must not possess or replay the human's authenticated session to execute work.

```text
Human Actor A
   |
   | authorizes bounded operation / Run
   v
DelegatedExecutionAuthority
   |
   v
Worker principal W
   |
   v
execute bounded work
```

A worker principal is not a human Actor merely because it is acting on a human-authorized Run.

### Delegated execution

Remote execution requires a bounded Battalion-owned delegation artifact or equivalent controller-owned authority record. The exact schema is follow-up work, but it binds at least:

- delegating/authorizing Actor;
- delegated operation and, where applicable, Run identity;
- intended worker/service class or concrete principal when known;
- project identity;
- permitted operation family;
- scope/target constraints;
- creation, expiry, and revocation semantics;
- originating human/application decision evidence; and
- logical operation identity sufficient to reconcile with ADR-0029 side-effect evidence when external effects occur.

Delegation is not transferable general authority. A worker receiving authority to execute Run X does not inherit the authorizing human's `approve`, `administer`, `assign`, `resolve-interrupt`, or unrelated `operate` capabilities.

If execution reaches a HumanInterrupt, the worker cannot satisfy it by presenting its machine credential or original delegation. A separately authenticated and authorized human decision is required.

### Delegation and first-class Runs

RFC-0014 makes Run identity meaningful beyond Implementation Run. Delegation therefore targets a concrete admitted operation and, when execution is Run-scoped, the exact first-class Run/recipe context rather than an implicit graph session.

A delegation cannot widen the admitted workflow recipe, role-result policy, write scope, governing artifact chain, or human authority boundary. RFC-0013 role outcomes and RFC-0015 workflow contracts remain independently validated by Battalion.

### Machine Actor versus machine principal

Not every machine principal needs a durable Actor.

Use a durable system Actor when Battalion needs persistent participant identity and responsibility across executions. Use a machine principal when the security concern is which machine/service authenticated for a bounded execution.

A worker process, host instance, ephemeral runner, or deployment credential should not automatically create a durable Actor for every runtime instance.

## Battalion roles and model identity

Architect, Driver, Reviewer, Refactorer, Recon, and future Battalion roles are execution roles, not authentication providers.

When durable contribution provenance is needed, Battalion may attribute work to a durable system Actor representing the responsible Battalion role/service while separately retaining execution evidence such as model provider, resolved model, prompt/config version, Run, recipe, and node/role invocation.

Individual model names should not become Actors merely because they generated tokens. Models are replaceable execution resources unless a future design gives a persistent autonomous agent independent durable identity and responsibility.

This RFC does not define the complete ContributionRecord schema; it establishes the identity/authority invariant required for that follow-up.

## Contribution and Git publication provenance

Battalion must not treat repository credential identity as canonical contribution evidence.

A future contribution-provenance contract should distinguish at least:

- requested by;
- designed/architected by;
- implemented by;
- reviewed by;
- accepted/approved by;
- side effect executed by; and
- repository artifact published by.

A future Git/GitHub projection may use bot accounts, commit authorship, `Co-authored-by` lines, custom trailers, PR metadata, or another mechanism to make this visible externally. However:

- Git metadata is a projection, not Battalion's canonical provenance;
- a human Git credential publishing code does not prove the human implemented the code;
- a Battalion bot publishing code does not prove Battalion authorized itself;
- contribution does not grant capability;
- authorization does not imply contribution; and
- historical contribution/authorization evidence survives credential, account, model, or provider changes.

RFC-0015's canonical-artifact and provenance model should be reused when contribution becomes a first-class durable contract rather than creating a parallel identity store.

## Credential storage boundary

Reusable authentication material belongs outside portable project identity and ordinary workflow evidence.

The following must not be persisted in Actor files, portable integration configuration, Run/workflow state, context manifests/projections, logs, prompts, ContributionRecords, or ordinary audit projections:

- passwords;
- access or refresh tokens;
- bearer/session secrets;
- OAuth client secrets;
- API secrets used for authentication;
- private keys;
- passkey private material; or
- equivalent replayable credentials.

Battalion configuration and durable records may contain symbolic credential references, public key identifiers/fingerprints, issuer IDs, subject IDs, expiry information, revocation state, and bounded non-secret evidence necessary for audit and resolution.

Credential storage is deployment-specific behind a narrow secret/credential boundary. This RFC does not choose an implementation.

## Account lifecycle

### Linking

Linking an external identity to an Actor is an explicit authorized administrative operation. Authentication of the external identity may be required as proof of control, but proof of control alone does not grant permission to link it.

### Unlinking

Unlinking prevents future session resolution through the binding. Existing Actor identity, memberships, assignments, human actions, workflow provenance, and contribution evidence remain unchanged.

### Conflicts and duplicates

A subject that resolves ambiguously fails closed. Battalion does not guess based on display names or email addresses. Resolution requires an explicit authorized action with durable evidence.

### Actor deactivation

Actor deactivation blocks new authorized activity. Existing sessions must become unusable no later than the next protected operation, even if their authentication credential remains valid.

### Credential rotation

Credential rotation is not identity migration. When the provider's stable subject remains the same, the ExternalIdentity and Actor remain the same.

## Session and revocation semantics

A future session implementation must make revocation enforceable at the application boundary. At minimum:

- session identity and expiry are server/controller validated;
- logout/revocation prevents future protected operations;
- Actor or identity-link disablement is observed before authorization;
- credential revocation and Battalion session revocation remain distinguishable facts;
- session refresh cannot silently change the resolved Actor;
- replayed or duplicated state-changing requests converge on existing Battalion idempotency/side-effect rules rather than treating session validity as replay protection for domain operations.

## Persistence and workflow evidence

The original BTN-62 draft predated RFC-0014 and RFC-0015. This RFC therefore replaces its assumption that authentication evidence belongs generically in `RunState`.

The durable rule is instead:

```text
security/runtime evidence
        -> bounded reference/evidence record
        -> application operation / Run envelope / workflow contract as appropriate
```

Authentication/session/delegation data enters a workflow only when the workflow requires it, and then only through a bounded Battalion-owned contract or provenance reference. Raw provider claims and reusable credentials never become model context merely because they were available to the controller.

For first-class Runs, durable provenance should be sufficient to answer:

- which Actor authorized or initiated the Run;
- which authenticated session/principal submitted the operation where security audit requires it;
- which worker principal executed delegated work;
- which delegation admitted that worker execution;
- which system Actor/model execution contributed artifacts; and
- which principal/provider executed external side effects.

These references supplement, rather than replace, RFC-0013 role execution evidence, RFC-0014 Run lifecycle, RFC-0015 artifact provenance, human-action evidence, and ADR-0029 side-effect evidence.

## Deployment comparison

| Deployment | Authentication expectation | Identity resolution | Authorization |
| --- | --- | --- | --- |
| Single-user local desktop | explicit local trust context may be sufficient | selected local Actor | normal Battalion application policy |
| Shared local machine | explicit per-user authentication required | binding -> Actor | normal Battalion application policy |
| Web/shared server | remote authentication required | binding -> Actor | normal Battalion application policy |
| Mobile client | remote authentication required | binding -> Actor | normal Battalion application policy |
| Remote worker | machine/service authentication | usually machine principal; optional durable system Actor | bounded delegation + application/runtime invariants |

No deployment may treat transport, provider login, machine possession, or UI visibility as authority.

## Security invariants

1. Credentials authenticate; they do not authorize Battalion operations.
2. External identities resolve Actors; they do not replace `actor_id`.
3. Clients never choose their authoritative Actor by supplying an `actor_id`.
4. Provider scopes cannot widen Battalion authority.
5. Assignment, ownership, contribution, and expertise evidence cannot widen authority.
6. Workers authenticate as themselves and cannot impersonate delegating humans.
7. Delegation is bounded to admitted operation/Run scope and cannot satisfy human authority gates.
8. Reusable secrets do not enter portable project state, workflow contracts, prompts, logs, or ordinary evidence.
9. Historical attribution is not rewritten when accounts, credentials, bindings, models, or Actors change.
10. Authentication/session evidence composes with existing workflow, authorization, and side-effect evidence rather than creating a competing source of truth.

## Follow-up implementation boundaries

Acceptance of this RFC produces implementation work in separate tickets rather than expanding BTN-62 into delivery. The implementation sequence covers:

1. authentication principal/evidence and verifier port contracts;
2. authenticated session lifecycle and revocation;
3. server-side external identity resolution using the existing Actor binding model;
4. local desktop trust-session adaptation without breaking offline use;
5. protected remote application protocol integration;
6. delegated execution authority and worker authentication;
7. credential/secret-store abstraction and redaction tests;
8. durable security/provenance references aligned with RFC-0014/RFC-0015 and ADR-0029;
9. contribution provenance as a separate contract if/when required; and
10. provider-specific adapters only after the provider-neutral contracts exist.

Provider selection is deferred until the relevant deployment/client ticket has concrete requirements.

## Alternatives rejected

### Provider account is the Actor

Rejected because provider subjects are external, scoped, and potentially replaceable. Battalion identity must survive provider changes.

### Authentication implies project membership

Rejected because it makes login/account linking a privilege grant.

### Worker impersonates the human who started the Run

Rejected because it destroys attribution and grants a machine authority unrelated to the bounded execution it needs.

### Every worker/runtime instance is a durable Actor

Rejected because ephemeral security principals do not automatically need persistent participant identity.

### Git author/publisher is canonical contributor

Rejected because publication credentials do not prove engineering contribution or authorization.

### Put authentication data directly into universal RunState

Rejected after RFC-0014/RFC-0015. Different first-class Runs have distinct contracts and state. Security evidence should be referenced through the relevant application/Run/workflow boundary, not copied into one universal semantic state object.

### Hosted Battalion account required for all use

Rejected because Battalion remains local-first and offline-capable.

## Acceptance criteria mapping

- Trust boundary between session/credential and Actor: authentication boundary, terminology, security invariants.
- External identities remain links: identity resolution and account lifecycle.
- Linking/unlinking/conflicts/deactivation/rotation: account lifecycle.
- Authentication distinct from authorization: core separation and ADR-0028 composition.
- Desktop-local operation: local desktop authentication and deployment comparison.
- Local/web/mobile/worker/shared-server comparison: deployment comparison.
- Session lifetime/storage/logout/revocation/replay/transport/secrets: remote sessions, credential boundary, session semantics.
- Machine/worker identity distinct from humans: machine and worker identities.
- Future implementation tickets identified: follow-up implementation boundaries.
- No provider/client/worker implementation authorized: status and delivery boundary / non-goals.

## Reconciliation note

This document is the renumbered and reconciled successor to the unmerged BTN-62 draft formerly stored on `btn-62-auth-identity-rfc` as `rfc0013.md`.

The original architectural decision remains intact. Reconciliation against current `main` made three material editorial/architectural updates:

1. references now use the accepted operation-authorization architecture in RFC-0011/ADR-0028;
2. delegated worker execution is explicitly constrained by the first-class Run/recipe and role-result boundaries accepted in RFC-0013/RFC-0014; and
3. authentication/session/delegation evidence is no longer described as generically living in `RunState`; it composes with the typed artifact/workflow boundary architecture of RFC-0015.

No authentication provider or deployment mechanism is selected by this reconciliation.

## Open questions

None are required to accept the provider-neutral architecture. Provider choice, exact session technology, concrete secret store, and remote-worker transport are deliberately deferred until consuming implementation/deployment tickets have concrete requirements.
