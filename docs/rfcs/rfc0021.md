# RFC-0021 — Repository Instruction Discovery, Resolution, and Compliance

**Status:** Accepted
**Decision Date:** 2026-09-05
**Ticket:** BTN-97
**Author:** Architecture
**Target:** Post-v2
**Related:** `philosophy.md`, BTN-19, BTN-24, BTN-26, BTN-30, BTN-49, RFC-0004, RFC-0006, RFC-0010

---

## Summary

Battalion will treat repository-authored instruction artifacts as a distinct source of declared project authority. They are neither learned Intel/Instinct guidance nor deterministic Quality Gates.

A shared repository-instruction capability will discover supported instruction artifacts, normalize them into a vendor-neutral model, determine which fragments apply to target paths and receiving audiences, resolve scope and precedence, surface conflicts, and assemble bounded role-specific context with durable provenance.

The first-class contract is:

> Given a repository revision, target paths, and receiving Battalion audience, what declared repository guidance applies, why does it apply, what conflicts remain unresolved, and what evidence proves what context was actually supplied?

Battalion resolves instruction authority; it does not rank prose by length, apparent completeness, detail, recency, vendor, filename, or model preference.

Repository instructions remain prose authority unless a separate deterministic rule implements an equivalent mechanically checkable constraint. RFC-0010 Quality Gates therefore remain architecturally separate.

Instruction compliance is also a first-class evaluation surface. Battalion preserves typed compliance evidence separately from operational Run-control and deterministic Quality Gate histories so model and role reliability can be evaluated against the exact authoritative context supplied.

A working-name **Documenter** capability will live as a separate repository-governance flow rather than a mandatory node in ordinary Implementation Runs. Like Cartography, it is especially useful for brownfield onboarding and later repository maintenance. It audits instruction health and proposes changes into a separate proposal store; it does not silently rewrite authority.

## Context

Repositories may carry project guidance in multiple forms, including:

- `AGENTS.md`
- `CLAUDE.md`
- path-scoped `.instructions.md`
- repository-specific instruction formats
- contributor/process documents such as `CONTRIBUTING.md`

These artifacts differ in syntax, scoping, intended audience, and ecosystem semantics. Battalion must not hard-code one vendor convention into Driver, Reviewer, or another role, nor ask each role to independently rediscover instruction authority.

BTN-49 / RFC-0010 explicitly left repository-instruction semantics outside deterministic Quality Gates. That boundary is intentional: a linter result is mechanically evaluable, while prose such as “reuse the existing abstraction” may require semantic judgment.

The former Squad/Regiment Documenter is useful prior art. Regiment treated durable instructions as maintained project artifacts and used explicit promotion gates before learned guidance became durable authority. Battalion preserves those authority boundaries while moving the maintenance capability outside the ordinary Architect → Driver → Reviewer chain.

Documenter is also analogous to Cartography:

- Cartography answers what the repository is and how it is structured.
- Documenter answers what instructions govern work there, who they are for, whether they conflict, and what maintenance should be proposed.

For brownfield repositories, Battalion should therefore encourage a sequence such as:

```text
Cartography
    |
    v
Documenter
    |
    v
normal Battalion workflows
```

This is recommended, not universally mandatory.

## Goals

- define a vendor-neutral repository-instruction artifact and fragment model
- deterministically discover supported instruction sources and record unsupported candidates without silently granting authority
- resolve path applicability, native source semantics, explicit cross-format precedence, and conflict evidence centrally
- preserve source path, content hash, repository revision, applicability reason, resolution order, audience, and bounded-context evidence
- let authoritative fragments declare intended audiences rather than hard-code every role subset in Battalion
- keep authoritative instructions distinct from Intel/Instincts, proposals, and deterministic Quality Gates
- preserve human authority over instruction creation, modification, audience assignment, and promotion
- keep generated instruction changes in a separate proposal store until explicit human acceptance
- make compliance evidence usable by Battalion evaluation/model-selection capabilities
- define how instruction drift affects active and resumable Runs without introducing routine acknowledgement interrupts
- establish Documenter as a maintenance flow without requiring handoff semantics in the initial implementation
- allow prose constraints to inspire later deterministic enforcement without conflating source prose with executable policy

## Non-goals

- defining one universal repository instruction syntax
- privileging `AGENTS.md`, `CLAUDE.md`, or another vendor convention
- ranking instruction sets by length, detail, recency, or model judgment
- automatically converting arbitrary prose into Quality Gates
- adding Documenter to every Implementation Run
- requiring Documenter handoffs initially
- letting generated or learned guidance become authoritative without explicit human action
- treating `CONTRIBUTING.md` as universally authoritative by filename alone
- asking execution roles to independently discover or reconcile repository instruction sources

## Architectural decision

### 1. Repository instructions are declared project authority

Battalion distinguishes four neighboring concepts:

| Concern | Authority | Typical form | Evaluation |
|---|---|---|---|
| Repository instructions | Declared project authority | Prose / scoped guidance | Deterministic resolution; semantic compliance where needed |
| Instruction proposals | Candidate future authority | Proposed edits/fragments/audience metadata | Human acceptance required |
| Intel / Instincts | Derived advisory knowledge | Learned observations / guidance | Advisory; cannot override repository authority |
| Quality Gates | Mechanically executable policy | Commands / structured rules | Deterministic execution per RFC-0010 |

A contradiction between an Instinct and an applicable repository instruction is resolved in favor of repository authority. Battalion should preserve the contradiction as evidence so the derived knowledge can later be corrected.

Generated content never becomes authoritative merely because a model produced it or because it appears beside an authoritative source.

### 2. Source formats normalize behind adapters

Supported source formats are parsed through repository-instruction adapters. An adapter owns format-specific discovery/parsing semantics, not graph authority or semantic compliance.

Candidate normalized shapes:

```text
RepositoryInstructionArtifact
- source_path
- format_id
- repository_revision
- content_hash { algorithm, value }
- scope_root
- parse_status
- fragments[]

RepositoryInstructionFragment
- fragment_id
- source_path
- scope
- include_patterns[]
- exclude_patterns[]
- audiences[]
- normalized_text
- source_order
- provenance
```

Consumers receive normalized fragments and resolution evidence rather than format-specific documents.

### 3. Resolution is selection and conflict detection, not ranking

Resolution performs a bounded operation:

1. discover supported sources
2. resolve each format's native scope semantics
3. determine effective fragments for requested paths/audiences
4. apply explicit project-configured cross-format precedence where present
5. combine compatible co-authoritative fragments
6. identify unresolved contradictions
7. remove only exact or deterministically normalized duplicates
8. assemble bounded context and record omissions/truncation

Semantic similarity alone does not justify collapsing authoritative prose.

### 4. Scope specificity is resolved within each format first

Nested/path-specific files can override broader files only according to their own format's semantics. Raw filesystem depth does not create universal precedence across different formats.

Battalion first computes each format's effective instruction set, then resolves cross-format authority.

### 5. Cross-format precedence is explicit; otherwise contradictions are authority conflicts

Battalion does not define `AGENTS.md > CLAUDE.md`, `CLAUDE.md > AGENTS.md`, or another universal vendor ordering.

The policy is:

1. preserve native format scope/order semantics
2. honor explicit project/repository cross-format precedence
3. combine compatible co-authoritative fragments
4. absent explicit precedence, contradictory co-authoritative fragments produce an **instruction authority conflict**
5. never choose a winner based on prompt order, filename, vendor, file length, raw nesting depth, or current provider/model

Authority conflicts preserve competing source paths/hashes/fragments, affected paths/audiences, and bounded conflict evidence for human resolution.

### 6. Conflict detection is deterministic where possible and bounded-semantic where necessary

Structured contradictions can be detected mechanically where the fragment representation allows it. Arbitrary prose cannot reliably be reduced to deterministic predicates.

A bounded semantic conflict check may therefore answer only:

> Do these co-authoritative applicable fragments impose mutually incompatible obligations for this audience/change?

The model does not select a winner or synthesize a compromise. Its result is evidence, not authority.

### 7. `CONTRIBUTING.md` and similar documents are opt-in/referenced guidance

`CONTRIBUTING.md` is not authoritative by filename alone. It may enter the resolved instruction set when:

- explicit project/repository policy includes it, or
- an already-authoritative instruction source explicitly references it as applicable guidance.

When included by reference, provenance records the authoritative source that caused inclusion.

This creates three source classes:

- intrinsically supported instruction formats
- referenced/opt-in guidance artifacts
- unknown/inert files unless explicitly configured or referenced

Unknown or malformed sources fail boundedly rather than being interpreted into authority by model guesswork.

### 8. Audience declarations drive role-specific subsets

Authoritative fragments may declare audiences such as `driver.green`, `reviewer`, `refactorer`, `implementation`, or `review`.

Documenter audits missing or overbroad audience metadata and proposes corrections. Because audience assignments alter effective authority, generated audience changes remain proposals until human acceptance.

Before Documenter has been run, or where audience metadata is absent, Battalion degrades conservatively:

- honor native format semantics
- honor explicit project policy
- do not invent narrow audiences merely to save tokens
- record broader inclusion/truncation decisions explicitly

Driver GREEN, Refactorer, Reviewer, Architect, Specifier, Cartographer, and future roles receive only the fragments whose path/native/audience semantics make them applicable.

### 9. Semantic compliance remains Reviewer-owned initially; compliance evidence has typed history

Operational semantic instruction compliance is initially a Reviewer lens. A distinct compliance evaluator is justified only if evaluation later demonstrates materially better isolation, cost, evidence packaging, or another genuinely distinct responsibility.

Compliance findings remain distinct from deterministic Quality Gate retries and from general Reviewer rejection history where conflation would erase useful semantics.

Candidate record:

```text
InstructionComplianceEvaluation
- instruction_context_identity
- model / provider identity where available
- role / mode
- candidate identity
- evaluated_fragments[]
  - fragment_id
  - disposition: followed | violated | ambiguous | not_applicable
  - severity / importance where available
  - evidence
- unresolved_authority_conflicts[]
- summary
```

This supports evaluation of rule-following by model, role, workflow type, instruction complexity, source format, context size, and other bounded dimensions. Battalion should not collapse this immediately into one raw percentage; violating one critical instruction can matter more than following many minor ones.

Repeated violations are also Documenter evidence because they may indicate weak models, ambiguous guidance, excessive context, poor audience targeting, or prose that should be promoted into deterministic enforcement.

### 10. Instruction context is revision-bound; drift does not normally require acknowledgement

Each execution attempt records enough provenance to prove the exact effective instruction context used without copying the full instruction text into RunState.

At minimum record:

- repository revision
- source paths
- content hashes and algorithms
- fragment identities
- resolution order
- applicability/audience reasons
- target paths
- explicit precedence policy identity where applicable
- bounded-context/truncation evidence

On retry or resume, Battalion re-resolves instructions against the effective repository revision.

If instruction files changed but deterministic scope/audience resolution proves that the effective context for the current work is unchanged, the Run continues without interruption and records the re-resolution evidence.

If the effective instruction-context identity changes, Battalion preserves the prior attempt evidence and starts the next attempt using the new context. Routine instruction drift does **not** require a human acknowledgement interrupt.

Battalion interrupts only when safe continuation is not possible, such as:

- an unresolved instruction authority conflict applies to the current work
- malformed required instruction authority prevents deterministic applicability/resolution
- another explicit policy condition makes the effective authority unusable

Execution-time roles do not get an escape hatch to semantically declare that an applicable changed instruction is “irrelevant.” Semantic irrelevance or scope correction belongs to Documenter. If Documenter concludes that guidance should not apply, it proposes a durable scope/audience/content change through the proposal store.

### 11. Generated instruction changes live in a separate proposal store

AI-authored instruction changes, audience assignments, consolidation suggestions, learned-guidance promotions, and deterministic-enforcement suggestions remain separate from authoritative repository instructions until accepted.

Candidate proposal shape:

```text
InstructionProposal
- proposal_id
- target artifact / scope
- proposed content or metadata change
- source evidence
- conflicts addressed
- related Intel / Instincts, if any
- affected paths / audiences
- generated_by
- created_at
- status
- human decision provenance
```

Acceptance is a consequential human action. Only accepted proposals are materialized into authoritative repository/configuration state. Rejected proposals remain durable proposal history.

### 12. Promotion from prose to deterministic enforcement is explicit

Authoritative prose may motivate deterministic rules such as forbidden dependency/import checks, path architecture restrictions, required tests/migrations, or generated-output checks.

Promotion creates a separately configured Quality Gate or deterministic rule. The source instruction remains provenance for why the rule exists; the prose itself does not become executable merely because Battalion can imagine a checker.

### 13. Documenter is a separate repository-governance flow

`Documenter` is the working name only. Final naming is explicitly deferred until implementation; alternatives such as `Historian` may be reconsidered then without changing this architecture.

Documenter initially requires no state-carrying handoff semantics. That is not a permanent prohibition: future evidence may justify promoting it into a fuller role.

Documenter may:

- audit authoritative instruction artifacts
- identify cross-format conflicts, redundancy, stale guidance, malformed scope, and missing audiences
- propose consolidation, clarification, and audience metadata
- inspect recurring compliance evidence
- cluster related Intel/Instincts into candidate durable guidance
- propose deterministic-rule promotion
- identify referenced guidance such as `CONTRIBUTING.md`
- determine whether semantically changed applicable guidance should instead be scoped/audienced differently, then propose that durable change

Documenter may not:

- silently reconcile authority conflicts for an executing role
- make generated guidance authoritative without human acceptance
- become a mandatory node in ordinary Implementation Runs merely because instructions exist

### 14. Documenter recommendation signals are evidence, not scheduling authority

Battalion should recommend another Documenter pass when deterministic evidence suggests repository instruction health has materially changed.

Initial recommendation signals are:

- **newly discovered instruction files** — a new supported authoritative source or newly referenced guidance appears
- **repeated compliance violations** — especially recurring violations of the same fragment or related cluster
- **instruction drift** — effective instruction context changes materially relative to previously analyzed repository state
- **authority conflicts/ambiguities** — new or recurring unresolved cross-format conflicts
- **malformed or unsupported instruction-like artifacts** — repository guidance appears present but cannot be consumed safely under the current format policy

These signals should produce an inspectable recommendation with reasons, not automatically invoke Documenter and not automatically interrupt an unrelated active Run.

Documenter recommendation evidence is therefore distinct from scheduling/graph authority. Only a conflict or other authority problem that actually blocks the current work interrupts execution.

## Validation fixture

Acceptance should include a disposable repository fixture proving at least:

- root and nested `AGENTS.md`
- `CLAUDE.md`
- one path-scoped instruction format
- same-scope compatible cross-format guidance
- same-scope contradiction with no precedence
- explicit project precedence resolving a contradiction
- native-format nesting that does not become universal cross-format precedence
- `CONTRIBUTING.md` ignored by default and included through authoritative reference
- malformed supported instruction content
- unknown instruction-like content remaining inert
- audience declarations and conservative fallback when absent
- generated Documenter proposals remaining non-authoritative before acceptance
- bounded role-specific context assembly and provenance identity
- exact/normalized duplicate handling without semantic-collapse of similar prose
- semantic conflict evidence that does not select a winner
- compliance evaluation history distinct from Reviewer control and Quality Gate history
- drift that leaves effective context unchanged and continues without acknowledgement
- drift that changes effective context and starts a new attempt without routine acknowledgement
- blocking authority conflict causing an interrupt
- Documenter recommendation signals for newly discovered files, repeated violations, drift, conflicts, and malformed/unsupported instruction-like artifacts
- recommendation evidence that does not automatically schedule or invoke Documenter

## Expected implementation decomposition after acceptance

The accepted RFC should split implementation into at least:

1. instruction format adapters + discovery/native-scope resolution
2. cross-format precedence + conflict evidence
3. referenced/opt-in guidance handling
4. provenance + audience-aware context assembly + context identity
5. retry/resume drift re-resolution policy
6. semantic Reviewer compliance behavior + typed compliance evaluation history
7. Documenter maintenance workflow + brownfield onboarding recommendation
8. Documenter recommendation-signal detection
9. instruction proposal store + human acceptance/materialization path
10. prose-to-deterministic-rule promotion boundary/tooling
11. UI/CLI inspection of effective instructions, audiences, conflicts, drift, recommendations, and proposals
12. specification/ADR/user-facing documentation updates
13. deterministic fixture/evaluation coverage, including model rule-following metrics

## Alternatives considered

### Let every role read repository instruction files directly

Rejected. This duplicates discovery logic, makes format support prompt-dependent, prevents deterministic provenance, and creates inconsistent scope handling.

### Treat repository prose as Quality Gates

Rejected. Most prose is not mechanically decidable, and RFC-0010 intentionally separates deterministic checker evidence from semantic review.

### Rank instruction sets by length, detail, recency, or model judgment

Rejected. Those properties do not establish project authority.

### Define a universal Battalion ordering such as `AGENTS.md > CLAUDE.md`

Rejected. Different repositories intentionally center different ecosystems.

### Treat the deepest file as universally authoritative across formats

Rejected. Path specificity is meaningful only through each format's native semantics.

### Semantically merge or aggressively deduplicate similar prose

Rejected. Semantic similarity can erase intentional nuance.

### Treat `CONTRIBUTING.md` as authoritative everywhere

Rejected. It becomes instruction authority only through explicit project opt-in or authoritative reference.

### Require human acknowledgement for every instruction-context drift event

Rejected. Routine acknowledgements create unnecessary interruption. Battalion re-resolves deterministically, starts a new attempt when effective context changes, and interrupts only when applicable authority cannot be resolved safely.

### Let an execution role prove an applicable changed instruction semantically irrelevant

Rejected. That creates an execution-time authority escape hatch. Durable semantic irrelevance/scope corrections belong to Documenter proposals and human acceptance.

### Automatically invoke Documenter whenever a recommendation signal fires

Rejected. Recommendation signals are evidence, not scheduling authority. They should encourage maintenance without silently changing the active workflow.

### Add Documenter to every Implementation Run

Rejected. Its responsibility is repository-governance maintenance, analogous to Cartography.

### Let Documenter write authoritative instructions directly

Rejected. Generated guidance remains in the proposal store until human acceptance.
