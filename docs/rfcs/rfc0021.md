# RFC-0021 — Repository Instruction Discovery, Resolution, and Compliance

**Status:** Proposed
**Ticket:** BTN-97
**Author:** Architecture
**Target:** Post-v2
**Related:** `philosophy.md`, BTN-19, BTN-24, BTN-26, BTN-30, BTN-49, RFC-0004, RFC-0006, RFC-0010

---

## Summary

Battalion will treat repository-authored instruction artifacts as a distinct source of declared project authority. They are neither learned Intel/Instinct guidance nor deterministic Quality Gates.

A shared repository-instruction capability will discover supported instruction artifacts, normalize them into a vendor-neutral model, determine which fragments apply to a changed path and role, resolve their order and conflicts deterministically where possible, and assemble bounded role-specific context with durable provenance.

The first-class contract is not “read `AGENTS.md`.” It is:

> Given a repository revision, changed path, and receiving Battalion role/workflow, what declared repository guidance applies, why does it apply, in what order, and what evidence proves what context was actually supplied?

Instruction resolution belongs behind the shared application/context boundary rather than inside prompts or presentation clients. Models consume resolved instruction context as evidence of project authority; they do not independently rediscover or reinterpret repository scope rules.

Repository instructions remain prose authority unless and until a separate deterministic rule implements an equivalent mechanically checkable constraint. RFC-0010 Quality Gates therefore remain architecturally separate: semantic non-compliance is not reported as a deterministic gate failure merely because a prose instruction exists.

Initial semantic compliance should remain Reviewer-owned unless evaluation demonstrates that a separate bounded evaluator provides materially better isolation or cost/quality behavior without duplicating Reviewer responsibility.

---

## Context

Battalion already treats repository artifacts as higher authority than conversational context and is moving increasingly important contracts from prompt wording into inspectable application policy. Repositories, however, often carry project-specific AI and contributor guidance in multiple forms:

- `AGENTS.md`
- `CLAUDE.md`
- path-scoped `.instructions.md`
- `CONTRIBUTING.md`
- future project-specific instruction formats

These artifacts differ in syntax, scoping rules, intended audience, and ecosystem semantics. Hard-coding one filename into Driver, Reviewer, or another role would couple Battalion to a vendor convention and encourage each role to implement its own incomplete discovery logic.

BTN-49 / RFC-0010 explicitly left repository-instruction semantics out of deterministic Quality Gates. That boundary matters: a linter exit code is mechanically evaluable; “prefer the existing abstraction over introducing another helper” often is not. Battalion needs to carry both kinds of project authority without pretending they have the same evidence semantics.

The former Squad/Regiment Documenter is useful prior art. Regiment treats durable instruction files as maintained project artifacts, separates them from prompt/customization artifacts, and uses explicit human-confirmation and promotion gates before learned guidance becomes durable instruction. Battalion should preserve those useful authority boundaries without assuming that Documenter itself belongs in the ordinary execution graph.

## Goals

- define a vendor-neutral repository-instruction artifact and fragment model
- deterministically discover supported instruction sources and record unsupported candidates without silently granting authority
- resolve path applicability, ordering, precedence, and conflict evidence centrally
- produce an inspectable ordered set of applicable instruction fragments for any changed path
- preserve source path, content hash, repository revision, applicability reason, resolution order, and bounded-context evidence
- provide role-specific instruction subsets instead of one unbounded repository-wide blob
- keep authoritative repository instructions distinct from learned Intel/Instinct guidance
- keep semantic instruction compliance distinct from deterministic Quality Gates
- preserve human authority over creation, modification, and promotion of durable instruction content
- define how instruction-set changes affect active and resumable Runs
- evaluate Regiment Documenter responsibilities as maintenance/promotion prior art without automatically creating a new Battalion role
- allow prose constraints to inspire later deterministic enforcement without conflating the prose source with its executable implementation

## Non-goals

- defining a universal repository instruction syntax
- privileging `AGENTS.md`, `CLAUDE.md`, or any single vendor convention as Battalion's canonical format
- converting arbitrary prose into deterministic Quality Gates automatically
- creating a permanent Documenter node in the normal execution graph by default
- allowing generated or learned guidance to become authoritative without explicit human action
- storing full instruction contents in RunState merely for provenance
- asking every role to discover repository instructions independently
- treating malformed or unknown instruction artifacts as valid authority by best-effort model interpretation

## Architectural decision

### 1. Repository instructions are declared project authority

Battalion distinguishes three neighboring concepts:

| Concern | Authority | Typical form | Evaluation |
|---|---|---|---|
| Repository instructions | Declared project authority | Prose / scoped guidance | Deterministic resolution; semantic compliance where needed |
| Intel / Instincts | Derived advisory knowledge | Learned observations / guidance | Advisory; cannot override repository authority |
| Quality Gates | Mechanically executable policy | Commands / structured rules | Deterministic execution per RFC-0010 |

A contradiction between an Instinct and an applicable repository instruction is resolved in favor of the repository instruction. Battalion should surface the contradiction so derived knowledge can be corrected rather than silently suppressing it.

### 2. Normalize source formats behind adapters

Battalion will model supported source formats through repository-instruction adapters. An adapter is responsible only for format-specific discovery and parsing semantics; it does not decide graph flow or semantic compliance.

Candidate normalized shapes:

```text
RepositoryInstructionArtifact
- source_path
- format_id
- repository_revision
- content_hash { algorithm, value }
- scope_root
- parse_status
- fragments[]

RepositoryInstructionFragment
- fragment_id
- source_path
- scope
- include_patterns[]
- exclude_patterns[]
- audience / role applicability
- normalized_text
- source_order
- provenance
```

The exact persisted schema remains to be refined during this RFC. The important boundary is that consumers receive normalized fragments and resolution evidence rather than format-specific documents.

### 3. Resolution is path- and role-aware

For a target path and role/workflow, the resolver returns an ordered `ResolvedInstructionContext` containing:

- applicable fragments
- source identity and content hash
- repository revision
- applicability reason
- precedence / resolution order
- detected conflicts or ambiguities
- exclusions
- truncation / omission evidence when context is bounded

Resolution should be deterministic whenever the source format itself supplies deterministic scope semantics.

### 4. Unknown and malformed formats fail boundedly

A file that merely resembles an instruction artifact does not become authoritative automatically.

Unknown formats are discoverable evidence but are not interpreted semantically by a model and promoted to authority implicitly. Malformed supported artifacts produce an inspectable resolution problem. Policy may allow unaffected paths/roles to continue where applicability can still be proven, but Battalion must not invent missing scope semantics.

### 5. Precedence is explicit, not prompt-order magic

Battalion will preserve source-format semantics where they are well-defined, then apply a Battalion resolution policy for cross-format ordering at the same effective scope.

The initial policy direction is:

1. narrower path scope overrides broader path scope for directly contradictory guidance
2. within the same scope and format, native source ordering applies
3. cross-format contradictions at the same scope are not silently resolved by filename preference; they become explicit conflict evidence unless project configuration establishes precedence
4. generated proposals have no authority merely because they exist beside human-authored sources

This section needs explicit human decision before acceptance because cross-format precedence is where Battalion could accidentally invent project policy.

### 6. Roles receive bounded subsets

At minimum:

- Driver GREEN receives instructions applicable to files it may change plus relevant repository-wide implementation guidance
- Refactorer receives the same path authority needed to preserve compliant behavior while cleaning the candidate
- Reviewer receives the effective instruction set necessary to evaluate semantic compliance for the candidate

Architect, Specifier, and Cartographer should not receive the same blob by default. Their subsets should be derived from the question they are answering and repository areas in scope.

### 7. Semantic compliance initially belongs to Reviewer

The default design is to make instruction compliance another Reviewer lens rather than introduce a dedicated compliance role/evaluator.

A separate bounded evaluator is justified only if experiments show at least one of:

- materially better isolation of instruction compliance from general review
- lower total token cost through targeted context
- meaningfully better deterministic evidence packaging for routing
- a responsibility that cannot be expressed cleanly as Reviewer behavior

Without such evidence, a new role would duplicate Reviewer at additional token and orchestration cost.

Instruction-compliance findings should route back to the responsible producer with bounded evidence identifying the violated instruction source/fragment and affected path. They remain distinct from deterministic gate retry history and should not automatically reuse `reviewer_rejection_history` if that would erase the distinction between general review and declared-instruction non-compliance.

### 8. Instruction context is revision-bound evidence

Each execution attempt records enough provenance to prove which instruction set was used without copying full instruction text into RunState.

At minimum record:

- repository revision used for resolution
- source paths
- content hashes and algorithms
- fragment identities
- resolution order
- applicability reasons
- role / target paths
- bounded-context/truncation evidence

On retry or resume, Battalion re-resolves against the effective repository revision. If the resulting instruction-set identity differs from the attempt's prior identity, the change is explicit context drift rather than a silent replacement of history.

The exact policy for whether drift automatically invalidates a resumable attempt, requires human acknowledgement, or simply starts a new attempt is an open decision.

### 9. Promotion from prose to enforcement is explicit

An authoritative prose instruction may motivate a deterministic rule such as:

- forbidden dependency/import checks
- path-level architecture constraints
- required test or migration changes
- generated-output consistency checks

Promotion creates a separately configured deterministic rule/gate. The source instruction remains provenance for why the rule exists; it does not itself become executable merely because Battalion can describe a checker that might enforce it.

### 10. Documenter-like responsibilities live outside the normal execution graph by default

Regiment's Documenter contributes two useful ideas:

- durable repository instructions are maintained artifacts worthy of periodic audit
- learned guidance requires explicit promotion controls before becoming authoritative instruction

Battalion should support those responsibilities as maintenance/proposal workflows, but BTN-97 does not establish a mandatory Documenter role/node. A future bounded maintenance workflow may audit instruction health, propose edits, cluster related learned guidance, or propose deterministic-rule promotion. Human acceptance remains required before generated instruction content becomes project authority.

## Candidate resolution flow

```text
Repository revision + target paths + receiving role
                    |
                    v
        discover supported sources
                    |
                    v
          parse through adapters
                    |
                    v
      normalize artifacts/fragments
                    |
                    v
    resolve scope + precedence + conflicts
                    |
                    +---- malformed/ambiguous authority ---> inspectable resolution problem
                    |
                    v
       bound context for receiving role
                    |
                    v
     record provenance + context identity
                    |
                    v
             role execution
                    |
                    v
       Reviewer semantic compliance
```

Quality Gates remain a separate deterministic stage; they do not consume arbitrary prose and do not report semantic instruction findings.

## Open questions

1. **Cross-format precedence:** when `AGENTS.md`, `CLAUDE.md`, and another supported instruction format provide contradictory guidance at the same path scope, should Battalion require explicit project precedence configuration, define a default ordering, or treat the conflict as blocking authority ambiguity?
2. **Resume/retry drift:** if applicable instruction hashes change between attempts, is that automatically a new attempt, an interrupt requiring acknowledgement, or merely recorded context drift when the target changes are unaffected?
3. **`CONTRIBUTING.md` authority:** should contributor documentation be authoritative by default, opt-in as an instruction source, or parsed only when project configuration declares it relevant? Unlike AI-specific files, many repositories use it for human process rather than executable-agent guidance.
4. **Human-authored versus generated files:** should generated instruction proposals live in a separate proposal store until acceptance rather than beside authoritative repository files, so authority is mechanically unambiguous?
5. **Compliance history:** should instruction-compliance findings receive their own typed history in RunState, or is a typed extension of Reviewer findings sufficient while still remaining separate from deterministic gate retries?
6. **Role subsets:** should Architect/Specifier receive repository-wide governance fragments by default, or only fragments explicitly declaring those audiences plus paths implicated by the work item?
7. **Maintenance workflow:** is a Documenter-like capability best expressed as a Tactician-invoked maintenance workflow, an explicit command/tool outside Runs, or deferred until enough instruction drift/promotion evidence exists?

## Validation fixture

Acceptance should include a disposable repository fixture containing at least:

- root `AGENTS.md`
- nested `AGENTS.md`
- `CLAUDE.md`
- one path-scoped instruction format
- same-scope cross-format conflict
- malformed supported instruction content
- an unknown instruction-like file
- changes spanning paths with different effective instruction sets
- role-specific context assembly with an intentionally small context budget

The fixture should prove both positive applicability and explicit omission/conflict evidence.

## Expected implementation decomposition after acceptance

The accepted RFC should split implementation into at least:

1. instruction format adapters + discovery/resolution
2. provenance + context assembly + context identity
3. semantic Reviewer compliance behavior + routing evidence
4. Documenter-like maintenance/promotion workflow, if accepted
5. prose-to-deterministic-rule promotion boundary/tooling, if accepted
6. UI/CLI inspection of effective instructions and conflicts
7. specification/ADR/user-facing documentation updates
8. deterministic fixture/evaluation coverage

## Alternatives considered

### Let every role read repository instruction files directly

Rejected. This duplicates discovery logic, makes format support prompt-dependent, prevents deterministic provenance, and creates inconsistent scope handling between roles.

### Treat all repository instructions as Quality Gates

Rejected. Most prose guidance is not mechanically decidable, and RFC-0010 intentionally separates deterministic checker evidence from semantic review.

### Add a dedicated Documenter/compliance role immediately

Rejected as the default. Regiment demonstrates useful maintenance behavior, but BTN-97 should not add another model role unless a bounded responsibility and measurable benefit justify it.

### Normalize on one Battalion-owned instruction filename

Rejected. Battalion should consume declared project authority rather than force repositories to migrate to a Battalion-specific convention merely to participate.
