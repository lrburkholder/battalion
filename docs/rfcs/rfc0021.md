# RFC-0021 — Repository Instruction Discovery, Resolution, and Compliance

**Status:** Proposed
**Ticket:** BTN-97
**Author:** Architecture
**Target:** Post-v2
**Related:** `philosophy.md`, BTN-19, BTN-24, BTN-26, BTN-30, BTN-49, RFC-0004, RFC-0006, RFC-0010

---

## Summary

Battalion will treat repository-authored instruction artifacts as a distinct source of declared project authority. They are neither learned Intel/Instinct guidance nor deterministic Quality Gates.

A shared repository-instruction capability will discover supported instruction artifacts, normalize them into a vendor-neutral model, determine which fragments apply to a changed path and receiving audience, resolve their scope and conflicts, and assemble bounded role-specific context with durable provenance.

The first-class contract is not “read `AGENTS.md`.” It is:

> Given a repository revision, target paths, and receiving Battalion audience, what declared repository guidance applies, why does it apply, what conflicts remain unresolved, and what evidence proves what context was actually supplied?

Instruction resolution belongs behind the shared application/context boundary rather than inside prompts or presentation clients. Models consume resolved instruction context as evidence of project authority; they do not independently rediscover scope rules or rank competing instruction files by length, apparent detail, filename, vendor, or model preference.

Repository instructions remain prose authority unless and until a separate deterministic rule implements an equivalent mechanically checkable constraint. RFC-0010 Quality Gates therefore remain architecturally separate: semantic non-compliance is not reported as a deterministic gate failure merely because a prose instruction exists.

Instruction compliance is also a useful evaluation surface. Battalion should preserve typed compliance evidence separately from operational retry/control history so model and role reliability can later be evaluated against the exact authoritative instruction context supplied.

The working-name **Documenter** capability will live as a separate repository-governance flow rather than a mandatory node in the ordinary Implementation Run. Like Cartography, it is especially useful for brownfield onboarding and repository maintenance. It audits instruction health and proposes changes, audiences, consolidation, and enforcement candidates into a separate proposal store; it does not silently rewrite repository authority.

## Context

Battalion already treats repository artifacts as higher authority than conversational context and is moving increasingly important contracts from prompt wording into inspectable application policy. Repositories, however, often carry project-specific AI and contributor guidance in multiple forms:

- `AGENTS.md`
- `CLAUDE.md`
- path-scoped `.instructions.md`
- repository-specific instruction formats
- contributor/process documents such as `CONTRIBUTING.md`

These artifacts differ in syntax, scoping rules, intended audience, and ecosystem semantics. Hard-coding one filename into Driver, Reviewer, or another role would couple Battalion to a vendor convention and encourage each role to implement its own incomplete discovery logic.

BTN-49 / RFC-0010 explicitly left repository-instruction semantics out of deterministic Quality Gates. That boundary matters: a linter exit code is mechanically evaluable; “prefer the existing abstraction over introducing another helper” often is not. Battalion needs to carry both kinds of project authority without pretending they have the same evidence semantics.

The former Squad/Regiment Documenter is useful prior art. Regiment treats durable instruction files as maintained project artifacts, separates them from prompt/customization artifacts, and uses explicit human-confirmation and promotion gates before learned guidance becomes durable instruction. Battalion preserves those authority boundaries while moving the capability outside the normal Architect → Driver → Reviewer execution chain by default.

In practice, the Documenter-like flow is also analogous to Cartography. Cartography answers what the repository is and how it is structured; Documenter answers what instructions govern work there, who those instructions are for, whether they conflict, and what maintenance should be proposed. This makes Documenter particularly useful during brownfield onboarding, where a repository may already contain overlapping AI instructions, contribution guidance, legacy conventions, and undocumented scope assumptions.

## Goals

- define a vendor-neutral repository-instruction artifact and fragment model
- deterministically discover supported instruction sources and record unsupported candidates without silently granting authority
- resolve path applicability, ordering, explicit precedence, and conflict evidence centrally
- produce an inspectable set of applicable instruction fragments for any changed path and audience
- preserve source path, content hash, repository revision, applicability reason, resolution order, and bounded-context evidence
- let authoritative fragments declare intended audiences rather than hard-code all role subsets in Battalion
- keep authoritative repository instructions distinct from learned Intel/Instinct guidance
- keep semantic instruction compliance distinct from deterministic Quality Gates and operational retry history
- preserve human authority over creation, modification, audience assignment, and promotion of durable instruction content
- keep generated instruction changes in a separate proposal store until explicit acceptance
- define how instruction-set changes affect active and resumable Runs
- establish a Documenter maintenance flow without making it a mandatory node in every Run
- make compliance evidence usable by Battalion evaluation/model-selection capabilities
- allow prose constraints to inspire later deterministic enforcement without conflating the prose source with its executable implementation

## Non-goals

- defining a universal repository instruction syntax
- privileging `AGENTS.md`, `CLAUDE.md`, or any single vendor convention as Battalion's canonical format
- ranking instruction sets by length, completeness, detail, recency, or model preference
- converting arbitrary prose into deterministic Quality Gates automatically
- creating a permanent Documenter node in the normal execution graph by default
- requiring Documenter handoffs in the initial design
- allowing generated or learned guidance to become authoritative without explicit human action
- storing full instruction contents in RunState merely for provenance
- asking every role to discover repository instructions independently
- treating `CONTRIBUTING.md` as universally authoritative by filename alone
- treating malformed or unknown instruction artifacts as valid authority by best-effort model interpretation

## Architectural decision

### 1. Repository instructions are declared project authority

Battalion distinguishes four neighboring concepts:

| Concern | Authority | Typical form | Evaluation |
|---|---|---|---|
| Repository instructions | Declared project authority | Prose / scoped guidance | Deterministic resolution; semantic compliance where needed |
| Instruction proposals | Candidate future authority | Proposed fragments/edits/audience metadata | Human acceptance required before materialization |
| Intel / Instincts | Derived advisory knowledge | Learned observations / guidance | Advisory; cannot override repository authority |
| Quality Gates | Mechanically executable policy | Commands / structured rules | Deterministic execution per RFC-0010 |

A contradiction between an Instinct and an applicable repository instruction is resolved in favor of the repository instruction. Battalion should surface the contradiction so derived knowledge can be corrected rather than silently suppressing it.

Generated content never becomes authoritative because a model produced it, because it was written beside an authoritative file, or because it appears more detailed than existing guidance.

### 2. Normalize source formats behind adapters

Battalion will model supported source formats through repository-instruction adapters. An adapter is responsible only for format-specific discovery and parsing semantics; it does not decide graph flow or semantic compliance.

Candidate normalized shapes:

```text
RepositoryInstructionArtifact
- source_path
- format_id
- repository_revision
- content_hash { algorithm, value }
- scope_root
- parse_status
- fragments[]

RepositoryInstructionFragment
- fragment_id
- source_path
- scope
- include_patterns[]
- exclude_patterns[]
- audiences[]
- normalized_text
- source_order
- provenance
```

`audiences` may identify specific roles/modes such as `driver.green`, `reviewer`, or `refactorer`, or broader bounded audience groups such as `implementation` or `review` where the project chooses to define them.

The important boundary is that consumers receive normalized fragments and resolution evidence rather than format-specific documents.

### 3. Resolution is selection and conflict detection, not ranking

Battalion does not ask which instruction set is “better,” longer, newer, more complete, or more detailed. Resolution is a bounded operation:

1. discover applicable instruction sources
2. resolve native scope semantics within each source format
3. determine effective fragments for the requested path and audience
4. apply explicit project-configured cross-format precedence where one exists
5. combine compatible co-authoritative fragments
6. identify unresolved contradictions
7. conservatively remove only exact or deterministically normalized duplicates
8. assemble bounded context and record omissions/truncation

For a target path and audience, the resolver returns a `ResolvedInstructionContext` containing:

- applicable fragments
- source identity and content hash
- repository revision
- applicability reason
- audience reason
- precedence / resolution order
- detected conflicts or ambiguities
- exclusions
- truncation / omission evidence when context is bounded

Semantic similarity alone is not sufficient to collapse two instructions. Redundant prose is cheaper than erasing a subtle distinction by over-aggressive model deduplication.

### 4. Scope specificity is resolved within formats before cross-format authority

Battalion preserves the native scoping semantics of each supported format first. A nested `AGENTS.md`, for example, can become the effective AGENTS authority for a subtree according to AGENTS semantics.

That does **not** mean a nested file automatically outranks an applicable file from another instruction format merely because its path is deeper. Battalion first computes the effective fragments produced by each format, then resolves those co-authoritative fragments using explicit project cross-format policy or conflict handling.

This prevents raw filesystem depth from becoming an accidental universal authority rule across ecosystems with different semantics.

### 5. Cross-format precedence is explicit; otherwise contradictions are authority conflicts

Battalion has no universal basis for declaring `AGENTS.md > CLAUDE.md`, `CLAUDE.md > AGENTS.md`, or any equivalent vendor ordering.

The policy is therefore:

1. preserve each format's native scope/order semantics
2. allow explicit project/repository policy to declare cross-format precedence
3. absent explicit precedence, combine compatible applicable fragments
4. absent explicit precedence, contradictory co-authoritative fragments produce an **instruction authority conflict**
5. do not silently choose a winner based on prompt order, filename, vendor, file length, nesting depth across formats, or current model/provider

An authority conflict records the competing source paths/hashes/fragments, affected paths/audiences, and bounded conflict evidence. The human may resolve it by revising an instruction, declaring explicit precedence, or recording that the fragments are compatible with an explanation that can inform later Documenter proposals.

### 6. Conflict detection is deterministic where possible and bounded-semantic where necessary

Some conflicts can be identified mechanically when fragments expose structured constraints, for example a forbidden dependency versus a required dependency, conflicting include/exclude scopes, or incompatible path restrictions.

Arbitrary prose cannot be reduced reliably to deterministic predicates. Battalion may therefore use a bounded semantic conflict check whose question is narrowly scoped:

> Do these co-authoritative applicable fragments impose mutually incompatible obligations for this audience/change?

The model does not choose which instruction wins and does not rewrite the sources into a synthetic compromise. Its conflict classification is evidence, not authority. The resulting conflict remains inspectable and human-resolvable.

### 7. Unknown, malformed, and opt-in guidance fail boundedly

A file that merely resembles an instruction artifact does not become authoritative automatically.

Unknown formats are discoverable evidence but are not interpreted semantically by a model and promoted to authority implicitly. Malformed supported artifacts produce an inspectable resolution problem. Policy may allow unaffected paths/audiences to continue where applicability can still be proven, but Battalion must not invent missing scope semantics.

`CONTRIBUTING.md` is **opt-in guidance**, not intrinsically authoritative by filename. It may enter the resolved instruction set when either:

- explicit project/repository policy includes it, or
- an already-authoritative instruction source explicitly references it as applicable guidance.

When inclusion occurs by reference, provenance records the authoritative source that caused `CONTRIBUTING.md` to become applicable. Other documentation/style/architecture files may use the same referenced-guidance mechanism rather than becoming ambient authority merely because they exist.

This creates three useful source classes:

- intrinsically supported instruction formats
- referenced/opt-in guidance artifacts
- unknown/inert files unless explicitly configured or referenced

### 8. Audience declarations drive role-specific subsets

Battalion should not hard-code that every repository instruction is sent to every role. Authoritative fragments can declare their intended audiences, and resolution filters by those declarations plus path applicability.

Documenter is responsible for auditing missing/overbroad audience metadata and proposing audience assignments as part of instruction maintenance. Because audience classification changes effective authority, a model-generated audience assignment is itself only a proposal until accepted by a human and materialized into authoritative repository policy/artifacts.

Before Documenter has been run or where audience metadata is absent, Battalion degrades conservatively:

- honor native format audience/scope semantics where they exist
- honor explicit project policy
- do not invent narrow audience classifications from model intuition merely to save context
- record broader inclusion/truncation decisions explicitly

At minimum, Driver GREEN, Refactorer, and Reviewer must be capable of receiving the authoritative fragments explicitly addressed to them. Architect, Specifier, Cartographer, and future roles receive only fragments whose declared/native audience and scope make them applicable rather than one repository-wide instruction blob.

### 9. Semantic compliance initially belongs to Reviewer; compliance evidence has its own typed history

The default design keeps operational semantic compliance as a Reviewer lens rather than introduce a dedicated compliance execution role.

A separate bounded compliance evaluator is justified only if experiments show materially better isolation, lower total token cost, better evidence packaging, or a responsibility that cannot be expressed cleanly as Reviewer behavior.

Instruction-compliance findings route back to the responsible producer with bounded evidence identifying the applicable instruction source/fragment and affected path. They remain distinct from deterministic Quality Gate retry history and from general Reviewer rejection history where conflating those histories would erase useful semantics.

Battalion should therefore preserve a typed compliance-evaluation record capable of representing at least:

```text
InstructionComplianceEvaluation
- instruction_context_identity
- model / provider identity where available
- role / mode
- candidate identity
- evaluated_fragments[]
  - fragment_id
  - disposition: followed | violated | ambiguous | not_applicable
  - severity / importance where declared or assessed
  - evidence
- unresolved_authority_conflicts[]
- summary
```

This history answers a different question from Run control history:

- **Run control history:** what happened operationally and what should happen next?
- **Compliance evaluation history:** how reliably did the model/role follow the authoritative instructions it was actually given?

The evaluation layer may aggregate this evidence across model, role, workflow type, instruction complexity, source format, context size, and other bounded dimensions. Battalion should not reduce it prematurely to a single raw percentage because violating one critical rule may matter more than following many minor ones.

Recurring compliance failures are also useful Documenter evidence: they may indicate a weak model, ambiguous/conflicting instructions, excessive context, poor audience targeting, or a prose rule that should be promoted into deterministic enforcement.

### 10. Instruction context is revision-bound evidence

Each execution attempt records enough provenance to prove which instruction set was used without copying full instruction text into RunState.

At minimum record:

- repository revision used for resolution
- source paths
- content hashes and algorithms
- fragment identities
- resolution order
- applicability reasons
- audience / target paths
- explicit cross-format precedence policy identity where applicable
- bounded-context/truncation evidence

On retry or resume, Battalion re-resolves against the effective repository revision. If the resulting instruction-context identity differs from the attempt's prior identity, the change is explicit context drift rather than a silent replacement of history.

The exact policy for whether that drift automatically starts a new attempt, requires human acknowledgement, or can continue when proven irrelevant remains open.

### 11. Generated instruction changes live in a separate proposal store

AI-authored instruction changes, audience assignments, consolidation suggestions, learned-guidance promotions, and deterministic-enforcement suggestions are stored separately from authoritative repository instructions until accepted.

A proposal should preserve at least:

```text
InstructionProposal
- proposal_id
- target artifact / scope
- proposed content or metadata change
- source evidence
- conflicts addressed
- related Intel / Instincts, if any
- affected paths / audiences
- generated_by
- created_at
- status
- human decision provenance
```

Acceptance is a consequential human action. Only after acceptance is the proposal materialized into the repository/configuration as authoritative instruction state. Rejection/closure remains durable proposal history rather than disappearing into conversation.

This mechanically distinguishes:

- current authority
- candidate future authority
- learned advisory knowledge
- observed resolution/compliance evidence

### 12. Promotion from prose to deterministic enforcement is explicit

An authoritative prose instruction may motivate a deterministic rule such as:

- forbidden dependency/import checks
- path-level architecture constraints
- required test or migration changes
- generated-output consistency checks

Promotion creates a separately configured deterministic rule/gate. The source instruction remains provenance for why the rule exists; it does not itself become executable merely because Battalion can describe a checker that might enforce it.

Documenter may propose such promotion when recurring violations or instruction shape suggest mechanical enforcement would be valuable, but acceptance/configuration follows the appropriate human authority path.

### 13. Documenter is a separate repository-governance flow, not a mandatory Implementation Run node

The working name is **Documenter**. “Historian” remains a possible future rename, but Documenter better reflects that the capability actively audits and proposes repository guidance rather than merely recording history.

Documenter is analogous to Cartography and initially has no required state-carrying handoff semantics. That decision is pragmatic rather than permanent; if future evidence shows that Documenter requires durable handoff/state boundaries, Battalion can promote it into a fuller role without changing the repository-instruction authority model.

Documenter may:

- audit discovered authoritative instruction artifacts
- identify cross-format conflicts, redundancy, stale guidance, malformed scope, and missing audience declarations
- propose consolidation or clarification
- propose audience metadata
- inspect recurring compliance evidence
- cluster related Intel/Instincts into candidate durable guidance
- propose prose-to-deterministic-rule promotion
- identify referenced guidance such as `CONTRIBUTING.md`

Documenter may **not**:

- silently reconcile authority conflicts for an executing role
- write generated guidance directly into authoritative instruction state without human acceptance
- become a mandatory node in the normal Architect → Driver → Reviewer loop merely because instructions exist

For brownfield repositories, Battalion should encourage a repository-onboarding sequence such as:

```text
Cartography
    |
    v
Documenter
    |
    v
normal Battalion workflows
```

This is recommended rather than universally mandatory. Greenfield repositories or already well-governed instruction sets may not need the same initial maintenance pass.

## Candidate resolution flow

```text
Repository revision + target paths + receiving audience
                    |
                    v
        discover supported sources
                    |
                    +---- referenced/opt-in guidance eligibility
                    |
                    v
          parse through adapters
                    |
                    v
      normalize artifacts/fragments
                    |
                    v
       resolve native format scopes
                    |
                    v
      apply explicit project precedence
                    |
                    v
 combine compatible fragments + detect conflicts
                    |
                    +---- authority conflict ----------> inspectable human resolution
                    +---- malformed/ambiguous scope ---> inspectable resolution problem
                    |
                    v
       filter by declared audience
                    |
                    v
       bound context conservatively
                    |
                    v
     record provenance + context identity
                    |
                    v
             role execution
                    |
                    v
       Reviewer semantic compliance
                    |
                    v
       typed compliance evaluation history
```

Quality Gates remain a separate deterministic stage; they do not consume arbitrary prose and do not report semantic instruction findings.

The maintenance feedback path is separate:

```text
instruction artifacts + conflicts + compliance history + Intel/Instincts
                              |
                              v
                         Documenter
                              |
                              v
                      proposal store
                              |
                         human decision
                         /           \
                    accept           reject
                      |                |
                      v                v
          authoritative repo change   retained/closed proposal
```

## Open questions

1. **Resume/retry drift:** if applicable instruction hashes or effective audience/precedence resolution change between attempts, when must Battalion start a new attempt or interrupt for acknowledgement, and when may it continue after proving the change irrelevant to the target?
2. **Documenter naming:** retain the working name `Documenter`, adopt a name such as `Historian`, or defer naming until the maintenance-flow implementation ticket? The current architectural behavior does not depend on the final label.
3. **Documenter invocation policy:** beyond recommending it for brownfield onboarding, what deterministic signals should encourage or suggest another Documenter pass—for example newly discovered instruction files, recurring authority conflicts, repeated compliance violations, or substantial instruction-context drift?

The following earlier questions are now resolved:

- cross-format precedence: explicit project precedence or unresolved authority conflict; no universal vendor ordering
- `CONTRIBUTING.md`: opt-in or included through authoritative reference
- generated instruction changes: separate proposal store until human acceptance
- compliance history: typed evaluation history separate from operational retry/control history
- role subsets: declared fragment audiences, with Documenter proposing missing audience metadata
- maintenance shape: separate Documenter repository-governance flow, encouraged for brownfield onboarding, not a mandatory Implementation Run node

## Validation fixture

Acceptance should include a disposable repository fixture containing at least:

- root `AGENTS.md`
- nested `AGENTS.md`
- `CLAUDE.md`
- one path-scoped instruction format
- same-scope cross-format compatible guidance
- same-scope cross-format contradiction with no precedence
- explicit project precedence resolving a contradiction
- a nested instruction whose specificity applies only within its native format semantics
- `CONTRIBUTING.md` ignored by default
- `CONTRIBUTING.md` included through authoritative reference
- malformed supported instruction content
- an unknown instruction-like file
- changes spanning paths with different effective instruction sets
- explicit audience declarations for Driver/Reviewer/Refactorer and at least one non-implementation audience
- absent audience metadata demonstrating conservative fallback behavior
- generated Documenter proposal that remains non-authoritative before acceptance
- role-specific context assembly with an intentionally small context budget
- exact/normalized duplicate handling without semantic-collapse of merely similar prose
- semantic conflict evidence that does not choose a winning instruction
- compliance evaluation records distinct from Reviewer retry/control and Quality Gate history

The fixture should prove positive applicability, explicit omission/conflict evidence, proposal-store authority boundaries, and stable context/provenance identities.

## Expected implementation decomposition after acceptance

The accepted RFC should split implementation into at least:

1. instruction format adapters + discovery/native-scope resolution
2. cross-format precedence + conflict evidence
3. referenced/opt-in guidance handling
4. provenance + audience-aware context assembly + context identity
5. semantic Reviewer compliance behavior + typed compliance evaluation history
6. Documenter maintenance workflow + brownfield onboarding recommendation
7. instruction proposal store + human acceptance/materialization path
8. prose-to-deterministic-rule promotion boundary/tooling
9. UI/CLI inspection of effective instructions, audiences, conflicts, and proposals
10. specification/ADR/user-facing documentation updates
11. deterministic fixture/evaluation coverage, including model rule-following metrics

## Alternatives considered

### Let every role read repository instruction files directly

Rejected. This duplicates discovery logic, makes format support prompt-dependent, prevents deterministic provenance, and creates inconsistent scope handling between roles.

### Treat all repository instructions as Quality Gates

Rejected. Most prose guidance is not mechanically decidable, and RFC-0010 intentionally separates deterministic checker evidence from semantic review.

### Rank competing instruction sets by length, detail, recency, or model judgment

Rejected. These properties do not establish project authority. Resolution selects applicable authority and surfaces contradictions; it does not score competing prose to invent a winner.

### Define a universal Battalion ordering such as `AGENTS.md > CLAUDE.md`

Rejected. Different repositories intentionally center different ecosystems. Battalion has no legitimate basis for imposing a vendor preference absent explicit project policy.

### Treat the deepest file path as universally authoritative across formats

Rejected. Path specificity is meaningful only through each format's native scope semantics. Raw nesting depth does not establish precedence between different instruction ecosystems.

### Semantically merge or aggressively deduplicate similar prose

Rejected. Semantic similarity can erase intentional nuance. Battalion may remove exact/deterministically normalized duplicates and may note similarity, but it should not collapse distinct authoritative fragments merely because a model considers them equivalent.

### Treat `CONTRIBUTING.md` as authoritative everywhere

Rejected. Many repositories use it for human contribution/process guidance unrelated to AI execution. It becomes instruction authority only through explicit project opt-in or authoritative reference.

### Add Documenter to every Implementation Run

Rejected. Its bounded responsibility is repository-governance maintenance, analogous to Cartography, not candidate implementation/review. It may become a fuller role later if handoff/state evidence warrants it.

### Let Documenter write authoritative instructions directly

Rejected. Generated guidance, audience metadata, and consolidation edits live in the proposal store until a human accepts and materializes them.

### Normalize on one Battalion-owned instruction filename

Rejected. Battalion should consume declared project authority rather than force repositories to migrate to a Battalion-specific convention merely to participate.
