# RFC-0006 — Transport-Neutral Integration Capabilities

**Status:** Accepted
**Decision Date:** 2026-08-21
**Ticket:** BTN-65
**Author:** Architecture
**Target:** Post-v1
**Related:** BTN-30, BTN-46, BTN-63 through BTN-80, BTN-105,
[ADR-0002](../adrs/adr0002.md), [ADR-0025](../adrs/adr0025.md),
[RFC-0022](rfc0022.md)

---

## Summary

Battalion should describe external behavior with Battalion-owned capability
contracts, not vendor APIs, SDK clients, protocol tools, or MCP server names.
Each configured integration binds one capability contract to a provider
adapter, and each adapter receives only the transport operations required for
that binding. Battalion retains policy, authority, durable identity, failure,
and side-effect semantics above both layers.

The initial capabilities accepted by this RFC were `WorkSource`,
`KnowledgeSource`, `RepositoryService`, `Notification`, `OutboundEventSink`, and
`HumanInteraction`. RFC-0022 subsequently adds `SignalSource` as an additional
Battalion-owned capability for bounded operational evidence. Native/local,
HTTP/REST, webhook, MCP, and protocol-specific transports such as SMTP are
implementation choices below those contracts. MCP is optional and has no
privileged relationship to Battalion's graph or application layer.

This RFC defines boundaries and delivery constraints. It does not implement a
runtime, provider, transport, plugin loader, or live integration.

## Status and delivery boundary

The human operator accepted ADR-0025's layered capability/provider/transport
decision and this RFC's detailed contracts on 2026-08-21. Acceptance
establishes the architecture for BTN-66 through BTN-80; it does not make those
integrations shipped behavior. Runtime behavior begins only in their
implementation tickets.

RFC-0022 was accepted on 2026-09-05 and extends this architecture with
`SignalSource` without changing the least-authority layer model or making an
external observation authoritative for Battalion work.

BTN-65 does not authorize graph changes, provider credentials, network calls,
remote mutation, MCP installation, or a general plugin system.

## Goals

- give application and graph code stable, provider-neutral external operations
- keep Battalion policy and authority independent of provider and transport
- bind adapters to the least transport authority required by an operation
- make reads, mutations, delivery attempts, and ambiguous outcomes explicit
- preserve durable Run, Actor, operation, and event identity across retries
- support built-in deterministic integrations without requiring plugins
- leave enough room for future providers without leaking their concepts into
  core graph state or prompts

## Non-goals

- selecting concrete GitHub, Jira, Discord, email, Slack, or MCP providers
- defining portable configuration, secret storage, or runtime discovery
- implementing actor authorization, idempotent delivery, or health checks
- allowing graph nodes to browse arbitrary remote tools or clients
- making external systems authoritative for `RunState`, graph transitions,
  human decisions, accepted Intel, or scoped working-tree writes
- completing BTN-46's plugin lifecycle, packaging, or marketplace decisions

## Layer model

```text
presentation client / graph orchestration
                 |
       battalion.application
                 |
 identity + authorization + operation policy + durable evidence
                 |
      Battalion capability contract
                 |
          provider adapter
                 |
       least-authority transport
                 |
          external system
```

The layers have separate responsibilities:

| Layer | Owns | Must not own |
| --- | --- | --- |
| Battalion application and policy | caller authorization, operation admission, Run/Actor association, idempotency, evidence, required/optional behavior | vendor requests, protocol sessions, arbitrary tool discovery |
| Capability contract | Battalion operation names, normalized inputs/results, side-effect class, typed failures | provider fields, credentials, URLs, MCP tool names |
| Provider adapter | mapping normalized operations to one provider's semantics, response normalization, provider error classification | widening caller authority, graph policy, raw credential storage |
| Transport | bounded request/delivery mechanics, cancellation, timeout, connection lifecycle | business meaning, Actor authorization, automatic capability expansion |
| External system | remote behavior and its own state | Battalion Run or human-decision authority |

A configured integration instance selects a provider adapter, transport, and
set of Battalion operations. The stable `integration_id` belongs to Battalion
configuration, not to a provider account name or URL. Configuration and secret
indirection are BTN-66 work.

## Common contract

Every capability operation declares:

- a stable Battalion operation name and schema version
- allowed Battalion callers
- bounded normalized input and output models
- whether it is read-only, internally mutating, or externally side-effecting
- the Actor, Project, Run, WorkItem, and integration references required by that
  operation's semantics; references that do not yet exist or are not meaningful
  are not fabricated merely to satisfy a generic envelope
- authorization and operation-policy requirements
- timeout, cancellation, retry, and idempotency expectations
- whether an unavailable integration blocks the operation or may degrade
- typed failure and ambiguous-outcome behavior
- the minimum durable evidence required without retaining secrets or arbitrary
  external payloads

Capability values may contain bounded extension metadata only when round-trip
provenance requires it. Core logic cannot branch on provider-specific metadata.
Credentials, bearer tokens, cookies, private keys, raw MCP sessions, and
transport clients are never capability inputs or durable results.

Provider adapters return normalized results plus bounded provider evidence.
They do not return a raw SDK response for callers to reinterpret.

## Initial capability contracts

### WorkSource

`WorkSource` imports and, where separately authorized, updates external units
of work.

- **Operations:** `work.get`, `work.list` or query, `work.refresh`, and distinct
  mutations such as `work.comment` and `work.transition`.
- **Allowed callers:** application intake and inspection services; graph
  orchestration may consume a normalized durable `WorkItem` snapshot. A graph
  node never receives the provider client.
- **Data boundary:** stable source reference, external item identity, revision
  evidence, title, bounded description, status, labels, assignment references,
  URL/reference, and retrieval provenance. Provider payloads stay below the
  adapter unless retained as explicit bounded evidence.
- **Side effects:** reads are side-effect-free from Battalion's perspective;
  comments, transitions, labels, and assignment changes are separate external
  side effects with stable logical operation IDs.
- **Failures:** not found, stale/conflicting revision, unsupported mutation,
  policy denial, authentication, rate limit, transport failure, malformed
  response, and ambiguous mutation outcome remain distinct.
- **Authority:** importing work does not authorize its requested changes.
  Mutations require application and operation policy independently of read
  access. GitHub Issues are Battalion's canonical ticket authority under
  ADR-0027 as amended by BTN-102; a future WorkSource still cannot silently
  redefine that authority.

### KnowledgeSource

`KnowledgeSource` supplies bounded, attributable knowledge for deterministic
context assembly. It is not the accepted-Intel repository.

- **Operations:** `knowledge.search` and `knowledge.get`; publication and
  mutation are intentionally absent from the initial contract.
- **Allowed callers:** application queries, Recon research, and the canonical
  context-assembly path. Individual role nodes receive selected normalized
  records, not an unrestricted search client.
- **Data boundary:** source identity, record identity, title, bounded content or
  content reference, revision, audience/applicability metadata, and retrieval
  provenance. Arbitrary corpora and credentials do not enter `RunState`.
- **Side effects:** initial operations are reads. Retrieval does not promote a
  record to accepted Intel or grant it prompt authority.
- **Failures:** unavailable source, partial results, stale revision, malformed
  record, access denial, query limit, cancellation, and transport failure.
- **Authority:** source content is evidence only. Existing Intel review,
  immutable promotion, audience, and applicability rules remain authoritative.

### RepositoryService

`RepositoryService` represents operations against a shared or remote repository
service without replacing Battalion's scoped local filesystem tools or fixing
Battalion to one local version-control engine.

- **Operations:** repository/ref inspection, revision lookup, change or diff
  retrieval, and separately authorized remote mutations such as branch,
  commit-reference, review-request, or merge-request publication.
- **Allowed callers:** application services and approved orchestration. Writing
  nodes continue to edit only through structurally scoped local tools.
- **Data boundary:** repository and ref identity, immutable revision evidence,
  bounded change metadata, review/publish references, and operation outcome.
  Provider repository objects do not enter core state.
- **Side effects:** inspection is read-only. Remote branch, review, merge, tag,
  or comment operations are individually named side effects; a generic
  `source_control.execute` operation is forbidden.
- **Failures:** missing/stale ref, conflict, protected branch, unsupported
  operation, policy denial, authentication, rate limit, transport failure, and
  ambiguous remote mutation.
- **Authority:** the contract cannot broaden node write scope, approve its own
  change, skip Reviewer checkpoints, or infer merge authority from possession
  of a provider credential.

Battalion currently obtains local revision and provenance evidence from Git.
That is a separate concern from `RepositoryService`. A future
`VersionControl` contract may abstract local working-copy, revision, branch,
and commit mechanics across Git or another engine. It must be proposed
separately because local engine replacement affects scope enforcement,
provenance, diff semantics, and repository quality gates. Neither contract may
grant writing nodes an alternate path around scoped filesystem tools.

### Notification

`Notification` delivers a bounded message to a Battalion Actor or explicit
Actor group. It is for human awareness, not machine event integration.

- **Operations:** `notification.send` with later status inspection where a
  provider supports it.
- **Allowed callers:** application interrupt and notification coordination,
  never an unconstrained role prompt.
- **Data boundary:** logical notification ID, Actor target, classification,
  bounded template data, safe return route, and delivery constraints.
  Provider destinations are resolved at the adapter boundary from external
  identity mappings; raw addresses and device tokens are not graph data.
- **Side effects:** every send is externally visible and uses BTN-70 durable
  attempt and idempotency semantics. Fan-out preserves one logical identity
  with distinct delivery attempts.
- **Failures:** missing destination, channel disabled, deferred/suppressed
  policy, policy denial, provider rejection, ambiguous delivery, and transport
  failure are distinct outcomes.
- **Authority:** delivery, receipt, or a provider reply never resolves a Human
  Interrupt. Interactive action must enter through `HumanInteraction` and the
  application authorization boundary.

### OutboundEventSink

`OutboundEventSink` publishes selected Battalion domain events to machine
consumers. It is distinct from human notification.

- **Operations:** `event.publish` for explicitly registered versioned event
  types.
- **Allowed callers:** the application event/evidence coordinator after a
  durable domain transition. Graph nodes do not construct arbitrary outbound
  payloads.
- **Data boundary:** stable event ID, event type and schema version, occurrence
  time, bounded Project/Run provenance, and event-specific minimized data.
  Prompts, transcripts, source trees, secrets, and arbitrary state dumps are
  excluded by default.
- **Side effects:** publish is externally visible and replay-safe under BTN-70.
- **Failures:** unsupported schema, policy denial, destination rejection,
  timeout, rate limit, transport failure, and ambiguous receipt.
- **Authority:** publication is one-way. A consumer gains no command, Actor, or
  Run authority from receiving an event.

### HumanInteraction

`HumanInteraction` carries a human action request or response across an
external presentation boundary while preserving Battalion as the decision
authority. It is not a conversational tool collection for graph nodes.

- **Operations:** `human.request` presents a bounded action request;
  `human.submit` delivers an authenticated, correlated response envelope to
  the application boundary.
- **Allowed callers:** application interrupt/human-action coordination.
  External adapters may submit only the response shape they are bound to.
- **Data boundary:** stable request ID, permitted response kind, safe bounded
  context, expiry/staleness evidence, authenticated external subject evidence,
  and correlation to a Battalion Actor where available. Provider messages and
  session credentials remain below the adapter.
- **Side effects:** presenting a request is an external side effect. Submitting
  a response is an input, not a Run mutation; application authorization and
  stale-state checks occur before the existing typed command is invoked.
- **Failures:** unlinked or ambiguous identity, authentication failure,
  expired/stale request, duplicate response, unsupported action, policy or
  authorization denial, malformed response, cancellation, and transport
  failure.
- **Authority:** identity resolution is not authorization. No external adapter,
  response channel, or notification reply can approve, resume, cancel, or
  reassign a Run directly.

## Additional capability accepted by RFC-0022

### SignalSource

`SignalSource` supplies bounded operational evidence that may indicate work is
needed. It is deliberately not a `WorkSource`: receiving a Signal does not
create, prioritize, authorize, or accept canonical work.

- **Operations:** `signal.get`, `signal.list`, and `signal.refresh`. Refresh
  re-reads admitted provider evidence and may emit new immutable observations;
  it never mutates an already emitted Signal.
- **Allowed callers:** Battalion application services responsible for admitted
  operational-evidence intake, correlation, inspection, or bounded context
  assembly. Graph nodes do not receive provider clients or arbitrary telemetry
  access.
- **Data boundary:** stable Signal identity, `integration_id`, stable provider
  source reference, observed time, bounded normalized summary, provenance,
  optional provider-native severity/importance, optional normalized operational
  severity, affected component/scope where known, durable external evidence
  references, bounded occurrence evidence, and bounded correlation hints.
  Raw logs, traces, dumps, provider SDK responses, and arbitrary telemetry
  payloads remain below the adapter unless separately retained as explicit
  minimized evidence.
- **Side effects:** the initial contract is observational. Webhook receipt is a
  transport direction, not authority to mutate WorkSource, create Runs, or
  modify repositories.
- **Failures:** source record missing/expired, unsupported query/cursor/grouping,
  malformed evidence, policy/authentication/permission denial, rate limit,
  timeout/cancellation, transport failure, partial/dropped observations where
  knowable, and stale external evidence references remain distinct.
- **Identity/retry:** polling retry, webhook redelivery, or transport replay
  must preserve observation identity so the same external observation is not
  manufactured into multiple Signals.
- **Authority:** Signals are evidence only. Correlation, deduplication,
  classification, and mutable lifecycle belong to Battalion-owned
  `OperationalFinding` state above the capability boundary. Every canonical
  Issue proposed from an OperationalFinding requires explicit human
  confirmation of the exact candidate and then uses the existing
  WorkSource-backed ticket-creation authority path. Provider or plugin access to
  SignalSource never implies WorkSource mutation, Run creation, repository,
  graph, or workflow-policy authority.

Provider-native severity and Battalion operational severity do not map
automatically to backlog priority. Issue-visible provenance is controlled by
organization policy, while Battalion retains the internal durable linkage
needed to explain the originating OperationalFinding, Signals, and human
creation decision.

## Transport taxonomy

| Transport | Examples of mechanics | Boundary rule |
| --- | --- | --- |
| Native/local | filesystem repository, local subprocess, in-process standard-library adapter | local access still receives explicit operations and paths; proximity is not authority |
| HTTP/REST | bounded HTTP request/response client | adapters receive approved methods, destinations, timeouts, and secret references, not an unrestricted session |
| Webhook | outbound POST delivery or verified inbound callback | outbound and inbound directions are separate grants; inbound data never implies command authority; inbound operational evidence may feed SignalSource only through its normalized contract |
| MCP | connection plus explicitly selected tools/resources | discovery is validation evidence; adapters receive an allowlisted binding, never the server's arbitrary tool set |
| Protocol-specific | SMTP and future purpose-specific protocols | expose only protocol mechanics required by the provider adapter; do not generalize credentials or sockets into ambient access |

An SDK is normally provider-adapter implementation, not a transport category.
It still needs a bounded network/credential boundary and may not bypass common
failure, policy, or evidence semantics.

One provider may support several transports and one transport may serve several
providers. Neither fact changes the capability contract.

## Caller and graph authority

The application boundary is the primary caller for external operations. Graph
or context orchestration can be constructed with capability-specific ports,
but a node receives only the exact normalized operation needed for its role and
phase. It never receives:

- a provider SDK client or authenticated HTTP session
- an MCP connection or discovered tool collection
- arbitrary network, subprocess, credential, or filesystem access
- a generic integration lookup that can select additional operations

Operation policy is structural and testable. Prompt text may explain an
operation but is never the enforcement mechanism. Transport and provider
bindings cannot add operations that the application did not admit.

## Failure and side-effect semantics

Common failures are typed by stage:

- invalid or incomplete configuration
- unavailable or incompatible integration/capability
- authentication or credential-resolution failure
- Battalion authorization or operation-policy denial
- external permission denial
- not found, conflict, stale revision, or stale human request
- rate limit or provider overload
- timeout or explicit cancellation
- transport/connectivity failure
- malformed or incompatible external response
- known external rejection
- ambiguous outcome after a possible external side effect

Provider details may decorate these categories without replacing them. Policy
denial must not masquerade as transport failure, and an unavailable optional
integration must not fail unrelated Runs.

Read retries may be bounded where safe. Side-effect retries require a stable
logical operation ID and BTN-70 evidence. A timeout after submission is
ambiguous, not automatically failed; the runtime must reconcile provider
idempotency or status evidence before retrying. Capability failure cannot
silently mutate `RunState` or erase prior durable evidence.

For observational SignalSource operations, retry/redelivery identity must also
be stable enough to avoid turning one external observation into multiple
Signals. That is distinct from OperationalFinding correlation across genuinely
different observations.

## Configuration, secrets, and health boundary

BTN-66 will define portable integration configuration and secret references.
BTN-67 will implement adapter/transport binding. BTN-69 will define preflight
health and advertised-capability validation. This RFC constrains that work:

- portable configuration may name providers, transports, operations, and
  non-secret settings, but not carry credentials
- secret resolution happens below policy admission and secrets never enter
  prompts, normalized results, logs, fixtures, or durable evidence
- discovery can prove availability but cannot grant authority
- capability or MCP tool drift fails validation or the affected operation; it
  does not expose newly discovered operations automatically

Operational evidence references that themselves carry credential material,
such as bearer-style signed URLs, must be redacted, converted to safe opaque
references, or rejected rather than persisted as ordinary Signal evidence.

## Relationship to plugins and BTN-46

Future plugins may implement a provider adapter or transport that conforms to
these contracts. Built-in adapters implement the same contracts and require no
plugin loader. Plugin provenance, lifecycle, isolation, installation, and
permission grants remain BTN-46 decisions.

A plugin is neither required nor privileged. It cannot define a competing core
capability, replace graph/state/interrupt/human-decision authority, obtain raw
clients on behalf of nodes, or convert its manifest permissions into Battalion
operation authorization. Plugin disablement or removal must degrade only its
bound integrations and retain required durable operation evidence.

The draft BTN-46 planning brief used the six capabilities originally accepted
by this RFC as its initial integration extension points. RFC-0022 subsequently
adds `SignalSource` through the same Battalion-owned architecture process;
plugin discovery itself still cannot create new capabilities.

## Delivery sequence

1. BTN-66 defines stable integration configuration and secret indirection.
2. BTN-67 implements capability-to-adapter-to-transport binding with fakes.
3. BTN-68 adds Battalion-owned operation policy.
4. BTN-69 adds health, compatibility, and capability-drift validation.
5. BTN-70 adds durable side-effect evidence and idempotent delivery.
6. BTN-71 through BTN-80 add individual contracts, providers, transports, and
   end-to-end proof without weakening this boundary.
7. BTN-105 / RFC-0022 adds the SignalSource architecture as a later extension;
   implementation is follow-up work rather than retroactively part of the
   original BTN-65 delivery sequence.

KnowledgeSource and RepositoryService may remain unimplemented during this
sequence. Their contracts are defined now so WorkSource, Intel, scoped writes,
and future repository integrations cannot absorb their responsibilities by
accident.

## Alternatives rejected

### Make MCP Battalion's integration model

MCP is one useful transport and discovery protocol. Treating its advertised
tools as Battalion capabilities would leak server naming into prompts, allow
capability drift to broaden authority, and disadvantage simpler deterministic
REST, webhook, SMTP, and local implementations.

### Give graph nodes provider clients

This creates ambient credentials and operations that prompt instructions
cannot reliably constrain. It also couples durable graph semantics to provider
and SDK behavior.

### Require every integration to be a plugin

This makes an unimplemented packaging lifecycle a prerequisite for basic
deterministic integrations and gives plugins architectural privilege over
built-in adapters.

### Use one generic external-tool capability

A generic execute boundary cannot state caller, data, side-effect, retry, or
authority semantics precisely enough to enforce least authority.

### Treat operational evidence as WorkSource data

Rejected by RFC-0022. Operational observations may indicate that work is
needed, but they are not canonical work and must not inherit WorkSource mutation
or Run authority merely because a provider emitted them.

## Decision

Under accepted ADR-0025, the six initial capability contracts, common failure
semantics, and plugin-neutral extension rule defined here are accepted.
RFC-0022 subsequently extends the current Battalion-owned capability set with
`SignalSource` under those same least-authority rules without rewriting the
historical initial-capability decision.
