# RFC-0008 — Cartographer Codebase Mapping and Maintenance Workflow

**Status:** Draft
**Ticket:** BTN-85
**Author:** Architecture
**Target:** Post-v1
**Related:** BTN-26, BTN-30, BTN-31, BTN-36, BTN-42, BTN-45, RFC-0006

---

## Summary

Battalion should add Cartography as a distinct project-maintenance workflow that
inspects a repository and maintains a durable, structured model of the codebase.
The map is derived institutional knowledge: it helps humans and later workflows
navigate the repository, but it is not architectural authority and does not
replace source code, specifications, ADRs, accepted Intel, or human decisions.

The canonical map should be structured and queryable rather than defined as a
set of generated Markdown files. A project-local durable store should own typed
mapping records for code units, relationships, summaries, evidence, and mapping
revisions. Human-readable Markdown or diagrams may be generated as projections
for review, publication, or interoperability, including compatibility with the
Gator/Regiment charter pattern.

Cartography should not be inserted into the Architect -> Driver -> Reviewer ->
Refactorer implementation graph. It has its own lifecycle and may reuse common
Battalion execution infrastructure such as project identity, worker supervision,
model usage evidence, cancellation, and live observation. This RFC uses the term
`WorkflowExecution` for the more general durable execution concept that may
ultimately contain both implementation Runs and Cartography jobs; whether to
introduce that abstraction immediately remains an implementation decision for a
follow-up ticket.

A Cartographer refresh is operator-initiated in the initial design. Battalion
may calculate staleness indicators mechanically, but elapsed time or changed
commits do not themselves authorize model inference or repository writes.

## Problem

Battalion currently assembles bounded execution context from ticket state,
approved plans, accepted Instincts, interventions, and phase-appropriate source
files. That is intentionally deterministic, but as repositories grow it forces
roles to rediscover structural facts repeatedly: where responsibilities live,
which modules depend on which others, where important entry points are, and
which areas are likely relevant to a ticket.

Regiment addresses this with Cartographer-generated charter Markdown. That is a
useful precedent, especially because it makes repository knowledge explicit and
version controlled, but Battalion has a richer persistence and application
boundary and does not need to constrain the canonical representation to prose
files.

The design must answer four separate questions:

1. What facts does Cartographer maintain?
2. What is the canonical durable representation?
3. How do humans and downstream workflows consume it safely?
4. How does Battalion know when the map may be stale without repeatedly paying
   an LLM to rediscover the repository?

## Goals

- reduce repeated repository exploration and model-token consumption
- give humans an inspectable map of the system and its evolution
- provide bounded, attributable structural context to execution workflows
- make freshness and provenance cheap to inspect without model inference
- support full and incremental refresh without silently retaining obsolete facts
- preserve human architectural ownership and existing source-of-truth hierarchy
- reuse Battalion execution infrastructure where that reduces duplication
- support future repositories much larger than Battalion itself

## Non-goals

- replacing source code, ADRs, specifications, or accepted Intel as authority
- having Cartographer make or approve architectural decisions
- automatically refreshing merely because a clock or commit threshold elapsed
- requiring every repository to expose generated Markdown charters
- constructing a perfect semantic program graph or compiler-grade index
- introducing a graph database server, hosted knowledge service, or mandatory
  external dependency for local Battalion operation
- allowing ordinary implementation nodes unrestricted access to a mapping store
- treating inferred ownership, intent, or relationships as facts without
  provenance and confidence/evidence distinctions

## Workflow boundary

Cartography is a project-level maintenance workflow.

```text
Project
  |
  +-- Cartography workflow ----> derived repository map
  |                                  |
  |                                  +--> human inspection
  |                                  +--> bounded context retrieval
  |
  +-- Specification workflow ---> accepted work specification
  |
  +-- Implementation Run -------> Architect -> Driver -> Reviewer -> Refactorer
```

The workflows may share infrastructure but do not share authority.

A Cartography execution has at minimum these lifecycle states:

- `requested`
- `inspecting`
- `assembling`
- `validating`
- `completed`
- `failed`
- `cancelled`

A failed or cancelled refresh leaves the last completed map readable. New data
is not promoted piecemeal into the current map unless the persistence design can
prove the resulting revision is complete and internally consistent.

### Reuse of Run infrastructure

Cartography should reuse the following concepts unless implementation evidence
shows a conflict:

- Project identity
- Actor attribution for operator-triggered actions
- detached worker supervision
- live observation events
- model/provider usage and cost evidence
- cancellation and failure evidence
- application commands and queries

It should not pretend to be a ticket implementation Run merely to obtain those
mechanics. A follow-up architecture ticket should decide whether Battalion
introduces a general `WorkflowExecution` identity with typed workflow kinds, or
keeps Cartography as a sibling durable execution type that reuses lower-level
services.

## Canonical map model

### Decision direction

The canonical representation should be structured records in a project-local
store. Markdown is a projection, not the primary storage contract.

The minimum conceptual model is:

```text
MapRevision
  - map_revision_id
  - project_id
  - repository_revision
  - started_at / completed_at
  - producer identity + prompt/model/config provenance
  - scope inspected
  - completeness / warnings

CodeUnit
  - stable map-local identity
  - kind
  - repository path / symbol locator
  - name
  - bounded purpose summary
  - responsibility tags
  - evidence references
  - first_seen / last_seen map revision

Relationship
  - source CodeUnit
  - target CodeUnit
  - relationship kind
  - evidence references
  - first_seen / last_seen map revision

Annotation
  - target map entity
  - author/provenance
  - text or structured value
  - generated vs human-authored distinction
  - lifecycle state
```

Initial `CodeUnit.kind` values should stay coarse, for example repository,
package/module, service/component, executable/entry-point, persistence boundary,
external integration boundary, test area, and important configuration surface.
The implementation should not begin with every class and function as a durable
entity unless evidence shows that granularity improves retrieval enough to
justify the storage and refresh cost.

Initial relationship kinds should likewise be bounded: contains, depends-on,
invokes/uses, reads-from, writes-to, implements-contract, and tests. New kinds
must remain schema-controlled rather than free-form model inventions.

### Why not canonical Markdown

Markdown has major advantages: Git diffs are excellent, humans can edit it,
and every coding agent can consume it. It is therefore useful as a projection
and interoperability surface.

It is weaker as Battalion's canonical representation because:

- retrieval requires parsing prose or conventions repeatedly
- relationship traversal is awkward
- entity identity across renames is difficult
- incremental updates encourage whole-file rewrites
- freshness is usually file-level rather than entity-level
- downstream context selection becomes text search rather than typed queries
- generated and human-authored content are difficult to separate mechanically

Battalion should retain the option to export Gator-compatible or Battalion-
native charter Markdown for repositories that want repo-visible maps.

### Why not a graph database

The data is graph-shaped, but that does not require a graph database. For local
first operation, a small relational/document store with typed nodes and edges is
simpler to package, migrate, back up, and test. The persistence interface should
not expose SQL or a specific database engine to callers so a future graph store
remains possible if scale warrants it.

The initial implementation should evaluate SQLite as the default project-local
store because it provides transactions, indexes, structured querying, and a
single portable file without a service dependency. This RFC does not require
SQLite until the persistence follow-up confirms it fits Battalion's existing
project storage conventions.

## Authority and provenance

The Cartographer may read repository content and write only its declared mapping
store/projections. It may not silently modify:

- implementation source
- tests
- `spec.md` or work specifications
- `plan.md`
- ADRs or RFC decisions
- `backlog.json`
- accepted Intel
- role definitions, graph control, write scopes, or interrupts

Every generated claim must be attributable to a completed `MapRevision` and,
where practical, to repository evidence such as paths, symbols, or inspected
revision content. The map may summarize architectural intent found in an ADR,
but the ADR remains the authority and the record should retain that source
reference.

Human annotations must be distinguishable from generated summaries. A refresh
must not overwrite a human annotation merely because the new model output
differs. Contradictions should be surfaced for review.

## Freshness and staleness

Freshness is evidence, not a binary claim that the model is correct.

Battalion can compute these values without an LLM:

- last successful mapping timestamp
- mapped repository revision
- current repository revision
- commit distance where the VCS can provide it
- paths changed since the mapped revision
- mapped entities whose evidence paths have changed
- paths deleted or renamed since the mapped revision
- whether the last refresh was partial or emitted warnings

A simple initial status taxonomy is:

- `missing`: no completed map exists
- `current`: mapped revision equals the inspected current revision
- `changed`: repository has changed since mapping
- `significantly_changed`: changed paths intersect mapped entities above a
  configured deterministic threshold
- `partial`: latest completed map declared incomplete coverage
- `unknown`: repository history cannot establish the relationship

Time since refresh and commit distance are presentation signals, not automatic
truth about semantic staleness.

### Operator behavior

The desktop and application query boundary should expose a projection similar
to:

```text
Architecture map
Updated 4 days ago | 23 commits behind
Mapped at 6d21c94 | current 92af4ab
Potentially affected: battalion.application, battalion.actors, battalion.graph
[Update mapping] [View map]
```

The initial `Update mapping` action is explicit and attributable to the Actor who
requested it. No staleness threshold automatically invokes an LLM.

## Refresh strategy

### Full refresh

The first Cartographer implementation should support a full refresh from a
selected repository revision. The new candidate map is built separately and
promoted atomically only after validation succeeds.

Validation should include at least:

- all referenced paths/symbols exist at the mapped revision where expected
- all relationship endpoints exist
- entity identifiers are unique
- required provenance fields are populated
- generated records conform to bounded schemas
- no writes occurred outside mapping-owned storage/projections

### Incremental refresh

Incremental refresh should be implemented only after the full-refresh contract
is reliable. It can use VCS changes since the mapped revision to select affected
entities and neighboring relationships.

Incremental logic must explicitly handle:

- file and directory rename
- deletion
- module split or merge
- new dependency edges
- removed dependency edges
- changes to configuration/entry points that affect several modules
- stale entities that are no longer supported by repository evidence

A changed path is a hint about what to re-inspect, not proof that only that map
entity can have changed semantically.

## Downstream consumption

Execution roles should not receive the entire map by default. The existing
context assembler should gain a Cartography retrieval stage that selects a small
set of relevant records deterministically from ticket/specification terms,
write-scope paths, planned paths, and relationship neighborhoods.

A normalized context record should contain, at minimum:

- map entity identity and kind
- bounded purpose/responsibility summary
- relevant relationships
- source evidence references
- mapped repository revision
- freshness status relative to the execution's repository revision

Context assembly must:

- have a separate token/character budget for map context
- use stable ordering
- identify stale or partial records explicitly
- omit the map cleanly when none exists
- never hide conflicts between map content and higher-authority artifacts
- avoid exposing a general mapping query tool directly to ordinary role prompts

Potential role usage:

- **Specifier:** orientation and terminology only; cannot derive product intent
  from topology.
- **Architect:** system boundaries, likely affected modules, and prior structural
  relationships; ADRs/specification outrank the map.
- **Driver:** narrow navigation around declared implementation scope.
- **Reviewer:** independent orientation and cross-boundary impact cues, not
  evidence that implementation is correct.
- **Recon/future workflows:** candidate structural observations with normal
  provenance and promotion rules.

## Relationship to RFC-0006 KnowledgeSource

Cartography is project-owned derived knowledge, while RFC-0006 `KnowledgeSource`
abstracts external or provider-backed attributable knowledge retrieval. The
canonical map should therefore not require an external `KnowledgeSource`
provider merely to read itself.

The retrieval shape should nonetheless be compatible in spirit: bounded records,
source identity, revision evidence, applicability, and deterministic context
selection. A future adapter could expose Cartography through a common internal
knowledge-query interface without changing map ownership.

## Human-readable projections

Battalion should support one or more projections after the canonical store is
stable:

- module charter Markdown
- high-level dependency listing
- diagram source suitable for rendering
- UI tree/graph views

Projections are reproducible views. Generated projections should either be
fully regenerated from the canonical store or clearly separate generated and
human-authored regions. Editing a projection must not silently mutate canonical
map records unless a later explicit import contract is designed.

## Failure and degradation semantics

- **No map:** execution continues using existing deterministic context paths.
- **Stale map:** selected records are labeled stale; policy may warn but does not
  silently block ordinary work in the initial implementation.
- **Partial map:** only records within declared completed coverage are eligible.
- **Refresh failure:** retain the prior completed map and durable failure evidence.
- **Malformed store:** fail Cartography queries explicitly; do not substitute
  guessed context.
- **Contradiction with authoritative artifact:** show both sources and authority
  ordering; do not auto-rewrite either.
- **Repository revision unavailable:** mark freshness unknown rather than current.

## Security and trust boundary

Cartographer is a high-read, low-write workflow. Repository-wide read access is
necessary for useful mapping, but writes must be restricted to mapping-owned
storage and explicitly configured projections.

Repository content is untrusted model input. Instructions found in source,
documentation, comments, fixtures, issue text, or generated files do not grant
Cartographer new tools or authority. The workflow should treat codebase content
as material to describe, not instructions to follow.

A future integration-backed Cartographer must still receive normalized,
least-authority repository reads through Battalion-owned boundaries rather than
ambient provider tools.

## Alternatives considered

### Regiment/Gator-style Markdown as canonical store

**Advantages:** transparent Git history, trivial portability, directly readable
by humans and coding agents, proven precedent.

**Rejected as canonical direction:** it makes structured retrieval, relationships,
identity, incremental refresh, and freshness harder than necessary. Retain as an
export/projection option.

### JSON files in the repository

**Advantages:** typed and versionable without introducing a database.

**Not preferred for the likely steady state:** large relationship sets and
incremental mutations can cause noisy diffs and whole-file rewrite pressure.
JSON remains viable for small fixtures, export, and migration snapshots.

### SQLite/project-local structured store

**Advantages:** local-first, transactional, queryable, indexed, one-file backup,
no server dependency, well suited to typed entities and edges.

**Current recommendation:** evaluate as the first implementation target behind a
persistence interface. Keep engine choice below application/context contracts.

### Dedicated graph database

**Advantages:** natural traversal and visualization queries.

**Rejected for initial implementation:** operational complexity and dependency
cost are unjustified at Battalion's current scale. Revisit only with measured
query/scale pressure.

### Re-explore repository on every Run

**Rejected:** preserves no institutional map, repeatedly spends model/tool
budget, cannot expose project-level freshness, and makes understanding dependent
on transient conversational exploration.

## Open decisions before acceptance

1. Whether `WorkflowExecution` becomes a new shared durable abstraction now or
   Cartography initially uses a sibling execution record.
2. Exact project-local storage location and whether SQLite fits current
   Battalion persistence conventions.
3. Initial `CodeUnit.kind` and relationship-kind enums.
4. Stable entity identity across Git renames and substantial module movement.
5. Whether human annotations live in the same store or a separately versioned
   overlay.
6. The deterministic retrieval/ranking algorithm and dedicated context budget.
7. Whether the first UI should show only list/tree navigation or also a graph
   visualization.
8. The threshold/algorithm for the `significantly_changed` presentation signal.

## Proposed follow-up tickets

If this direction is accepted, BTN-85 should be decomposed into at least:

1. **Cartography data contract and persistence** — typed revision/entity/edge
   models, migration/versioning, atomic promotion, queries, and test fixtures.
2. **Cartographer full-refresh workflow** — repository discovery, bounded model
   extraction, validation, provenance, cancellation, failure behavior.
3. **Cartography status and staleness service** — revision comparison, changed
   path/entity evidence, application queries.
4. **Cartography context retrieval** — deterministic selection and bounded
   injection into role context.
5. **Desktop Cartography surface** — freshness summary, affected areas, map
   inspection, explicit Update Mapping action.
6. **Human-readable map projections** — Markdown/diagram export, including a
   Gator-compatible experiment if useful.
7. **Incremental Cartographer refresh** — diff-selected reinspection, rename and
   retirement handling after full-refresh evidence is accepted.
8. **General workflow execution abstraction RFC/implementation**, if the
   implementation spike confirms that Run semantics are too ticket-specific to
   reuse cleanly.

## Acceptance test strategy

The eventual implementation should be proven with deterministic fixture
repositories before dogfooding Battalion itself. Coverage should include:

- first map of an unmapped project
- unchanged refresh
- changed implementation file
- cross-module dependency addition/removal
- rename and deletion
- partial/unreadable repository area
- model failure during refresh
- cancellation before promotion
- malformed generated records
- stale map consumption by an Execution Run
- contradiction between map summary and an ADR/specification
- human annotation surviving refresh
- atomic retention of the previous map after failed refresh
- context retrieval remaining within a fixed budget

The dogfood acceptance scenario should then map Battalion, modify a known module,
show deterministic staleness in the desktop/application projection, refresh on
operator request, inspect the map diff, and demonstrate that a later execution
receives only a bounded relevant subset rather than the full map.

## Decision requested

Accept the architecture direction that:

1. Cartography is a distinct project-maintenance workflow.
2. Its canonical product is structured, project-local derived knowledge rather
   than Markdown prose.
3. Markdown/diagrams are projections and interoperability surfaces.
4. Freshness is determined mechanically and displayed without automatic model
   invocation.
5. Execution workflows consume only bounded, provenance-rich map records through
   canonical context assembly.
6. The map is advisory derived knowledge; human-authored specifications, ADRs,
   source code, accepted Intel, and explicit decisions retain their existing
   authority.
