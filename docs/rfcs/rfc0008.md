# RFC-0008 — Cartographer Codebase Mapping and Maintenance Workflow

**Status:** Accepted
**Decision Date:** 2026-08-25
**Ticket:** BTN-85
**Author:** Architecture
**Target:** Post-v1
**Related:** BTN-26, BTN-30, BTN-31, BTN-36, BTN-42, BTN-45, BTN-58, BTN-59, BTN-61, BTN-86, RFC-0006, RFC-0007

---

## Summary

Battalion will add Cartography as a distinct project-maintenance workflow that
maintains a durable, structured **socio-technical project map**. The map connects
code structure, significant symbols, resources, cross-cutting invariants,
institutional knowledge, governing artifacts, evidence, and durable Battalion
Actors.

The Cartographer is one producer and maintainer of the map; the map is not merely
"Cartographer output." Human assertions, governing specifications and ADRs,
accepted project evidence, and future collaboration workflows may also contribute
typed records with distinct provenance and authority classes.

BTN-86 compared Markdown charters, structured files, SQLite, graph-adjacency JSON,
and hybrid projection approaches. Based on that evidence, RFC-0008 selects a
**project-local graph-adjacency structured representation with deterministic,
versioned JSON as the initial canonical encoding**, behind Battalion-owned
persistence/query contracts. Human-readable Markdown is a generated,
non-authoritative projection. A later storage backend may replace the JSON
encoding without changing the logical contract when measured scale, query,
concurrency, or migration pressure justifies it.

Cartography is not inserted into the Architect -> Driver -> Reviewer ->
Refactorer implementation graph. Battalion will generalize durable execution now
through a shared `WorkflowExecution` abstraction so Implementation Runs,
Cartography executions, and the upcoming Specification workflow can share
identity, worker supervision, observation, usage evidence, cancellation, and
failure mechanics while retaining workflow-specific state and authority.

A Cartographer refresh is operator-initiated in the initial design. Battalion may
calculate staleness indicators mechanically, but elapsed time or changed commits
do not themselves authorize model inference or repository writes.

## Problem

As repositories grow, execution roles repeatedly rediscover structural facts:
where responsibilities live, which symbols participate in flows, what state they
read or write, which cross-cutting invariants constrain them, and which humans or
governing artifacts hold relevant institutional context. Repeated exploration
wastes model/tool budget and leaves human understanding transient.

Regiment addresses this with Cartographer-generated Markdown. Gator provides
useful prior art: domain ownership and negative ownership, stable symbol
identifiers, read/write access patterns, callers and callees, tripwires,
pre-change institutional knowledge, cross-cutting invariants, and changed-path
dispatch. Battalion extends that model with durable persistence, Actor identity,
assignment/provenance, deterministic context assembly, application queries, and
workflow evidence.

The result is a durable model of the project as a socio-technical system rather
than a richer documentation format.

## Goals

- reduce repeated repository exploration and model-token consumption
- give humans an inspectable map of the system, constraints, and evolution
- connect code topology with durable Actor provenance and organizational context
- preserve the distinction between expertise evidence and authorization
- provide bounded, attributable structural/institutional context to workflows
- make freshness and provenance cheap to inspect without model inference
- support full and incremental refresh without silently retaining obsolete facts
- preserve human architectural ownership and source-of-truth hierarchy
- support projects and teams substantially larger than Battalion itself

## Non-goals

- replacing source code, ADRs, specifications, accepted Intel, or human decisions
- allowing Cartographer to make or approve architecture
- treating Actor association as approval authority
- automatically refreshing because a timer or commit threshold elapsed
- requiring generated Markdown in every repository
- constructing a compiler-grade semantic program graph
- exposing raw persistence/query handles to role prompts
- calculating broad expertise/social-graph scores in the initial release

## Workflow execution boundary

Battalion will introduce a shared durable execution concept:

```text
WorkflowExecution
  - execution_id
  - project_id
  - workflow_kind
  - requesting_actor_id
  - status
  - started_at / completed_at
  - worker/supervision evidence
  - model/provider usage evidence
  - observation/cancellation/failure evidence

  workflow-specific state:
    - ImplementationRun
    - CartographyExecution
    - SpecificationExecution
```

`WorkflowExecution` owns execution mechanics. Workflow-specific state owns
workflow semantics. Existing `RunState` must not become a generic dumping ground
for Cartography or Specification state.

Cartography remains a project-level maintenance workflow with at least:

- `requested`
- `inspecting`
- `assembling`
- `validating`
- `completed`
- `failed`
- `cancelled`

A failed or cancelled refresh leaves the last completed canonical map readable.

## Gator-derived logical content

Battalion Cartography preserves these concepts:

- **domain ownership** — what a logical subsystem owns
- **negative ownership** — what explicitly belongs elsewhere
- **stable symbol location** — significant callable/class/entry-point identities
- **access patterns** — resources/models/stores/files/external surfaces read or written
- **inbound/outbound relationships** — callers, callees, dependencies
- **tripwires** — non-obvious behavior that must be preserved or investigated
- **pre-change institutional knowledge** — implicit contracts and intentional decisions
- **cross-cutting patterns** — multi-domain flows, invariants, synchronization requirements, negative space
- **path dispatch** — deterministic changed-path -> relevant-map-area bindings

Fine-grained symbol facts do not require one document per symbol. Human projections
may remain grouped by logical domain.

`depends_on`, `invokes`, `reads`, `writes`, `read_writes`, `implements_contract`,
`tests`, `governed_by`, `asserted_by`, `verified_by`, `owned_by`, and
`assigned_to` where authoritative Battalion state exists.

## Entity identity and reconciliation

Map identities are Battalion identities assigned to mapped concepts. Repository
paths and symbol names are **revision-specific locators and evidence**, not the
identity itself.

Example:

```text
symbol_id = symbol:a82f...

revision N:
  path = battalion/application.py
  locator = resolve_interrupt

revision N+1:
  path = battalion/application/interrupts.py
  locator = resolve_interrupt
```

The implementation must explicitly evaluate entity reconciliation across refreshes.
At minimum it must test and represent:

- unchanged identity
- rename
- move
- split
- merge
- deletion
- new entity
- ambiguous successor/predecessor

When continuity cannot be established with sufficient deterministic evidence or
confidence, Battalion must **not silently merge identities**. It preserves the old
and new identities, records the ambiguity or possible-successor relationship, and
allows later evidence or human understanding to resolve it.

This reconciliation requirement is an explicit acceptance condition of the
Cartography data/refresh implementation work, not an optional refinement.

## Knowledge, authority, and human understanding

The map distinguishes four categories:

| Category | Example | Meaning |
| --- | --- | --- |
| Observed structure | `A invokes B` | Derived from repository evidence |
| Institutional knowledge | "This exists for legacy clients" | Attributed descriptive claim |
| Institutional constraint | "Do not bypass this boundary" | Normative claim whose authority depends on provenance |
| Governing decision | ADR requires a boundary | Reference to an authoritative artifact |

Initial authority classes are:

- `derived` — inferred by Cartographer
- `attributed` — explicitly asserted by a durable Actor
- `governing_reference` — points to an authoritative specification/ADR/policy

Cartographer cannot promote its own inference into governing truth.

Battalion should provide a **human understanding/comprehension surface**, not a
simple "AI claim approval queue." After a map update a human can inspect changed
observations, new constraint candidates, and changed supporting evidence and may:

- acknowledge/understand
- add context
- correct
- dispute
- turn a finding into an explicit governing decision or attributed constraint

Only an explicit human/governance action changes authority. Seeing or
acknowledging a derived observation does not itself make it governing.

Human-authored claims and constraints survive Cartographer refreshes. A refresh
may mark their supporting repository evidence stale or contradictory but cannot
rewrite the human assertion or fabricate Actor attribution.

## Actor model integration

Cartography reuses durable Actor identity. Initial Actor edges are deliberately
limited to direct provenance and authoritative project/work relationships:

- `requested_by`
- `asserted_by`
- `verified_by`
- `disputed_by`
- `owned_by`, when authoritative ownership exists
- `assigned_to`, when authoritative assignment exists

Broad inferred expertise scoring, social-graph ranking, recommended reviewers,
or "most knowledgeable person" calculations are deferred. Historical Actor
provenance may help answer "who supplied this context?" but never answers "who
is authorized to approve?"

## Persistence decision

BTN-86 provides empirical evidence but did not itself make the production
selection. RFC-0008 accepts the following initial boundary:

```text
Canonical logical model:
  Battalion Cartography graph

Initial physical encoding:
  deterministic, versioned graph-adjacency JSON

Human-readable projection:
  generated Markdown

Authority:
  canonical JSON owns map state
  generated Markdown is derivative/non-editable input

Application boundary:
  Battalion-owned Cartography repository/query contract
```

No role receives raw file mutation, raw graph-query authority, SQL/database
handles, or arbitrary map mutation capability.

A future backend may replace graph JSON when measured scale/query/concurrency or
migration evidence justifies it without changing the logical contract.

### Projection freshness

Canonical map freshness and projection freshness are separate states. If canonical
publication succeeds but Markdown generation fails, the map remains valid and the
projection becomes `stale` rather than causing the Cartography refresh itself to
roll back.

The UI must be able to represent this distinction.

## Freshness and staleness

Battalion computes without an LLM:

- last successful mapping time
- mapped repository revision
- current repository revision
- commit distance where supported
- changed paths
- mapped entities whose evidence paths changed
- affected `PathBinding`s
- renamed/deleted paths or symbols
- constraints whose supporting evidence changed
- partial/warning status

Time since refresh and commit distance are presentation evidence, not automatic
proof of semantic staleness and do not authorize inference spend.

## Refresh strategy

The first implementation supports a full refresh from a selected repository
revision. New generated structural state is built separately and promoted
atomically only after validation.

Validation includes:

- referenced paths/symbols resolve where expected
- relationship endpoints exist
- identifiers are unique
- provenance is populated
- generated records conform to schemas
- Actor references resolve when claiming durable Actor provenance
- generated refresh does not overwrite human-authored records
- entity reconciliation results are explicit and ambiguous matches are not silently merged
- writes remain inside Cartography-owned storage/projections

Incremental refresh follows only after full-refresh semantics are reliable. It
uses VCS changes and `PathBinding`s to select affected entities, constraints, and
neighboring relationships, while handling rename, deletion, split/merge, changed
resource access, changed cross-cutting flows, and stale evidence.

## Deterministic downstream retrieval

Map retrieval is deterministic first; semantic/vector retrieval is a future
optional enhancement.

### Seed selection

Seeds come from hard evidence such as:

- ticket/spec paths or explicit domain/symbol names
- declared write scopes
- Architect planned paths
- changed paths
- `PathBinding`s

### Bounded structural expansion

From seeds, select a bounded graph neighborhood containing relevant:

- containing Domains
- significant Symbols
- direct callers/callees
- read/write Resources
- applicable Constraints and tripwires
- governing artifacts
- cross-cutting patterns

Depth 1 is the default; Architect/Reviewer may use a bounded depth 2 where the
context budget permits it. Arbitrary recursive traversal is forbidden.

### Role weighting

- **Specifier:** terminology and system boundaries; implementation detail and Actor context low
- **Architect:** domains, cross-cutting patterns, constraints, governing decisions high
- **Driver:** symbols, access patterns, immediate dependencies, tripwires high
- **Reviewer:** constraints, inbound blast radius, cross-cutting patterns, changed evidence high

Actor context is low-weight unless directly relevant to an attributed claim or
an explicit human-action path.

### Authority and freshness

Authority and freshness are separate axes. A stale governing reference remains
more authoritative than a fresh model inference; both properties must be shown
rather than collapsed into one opaque score.

### Context budget

Cartography receives a separate bounded context allowance rather than consuming
unbounded source-file context. Initial implementation should start around 4K
characters for Driver and 6K for Architect/Reviewer, with deterministic truncation
and later tuning from measured runs.

## Human and UI interaction

The primary Cartography interaction is **graph-first visualization** with
list/search/detail views as supplements for accessibility and precise inspection.
The default graph should be focus-and-neighborhood based rather than an
unrestricted project-wide hairball.

The graph can display/filter:

- structure
- constraints/tripwires
- resources
- governing artifacts
- direct Actor provenance
- tests
- changes since the prior map

The desktop/application boundary also exposes freshness and an explicit
`Update mapping` action. No freshness threshold automatically invokes an LLM.

## Failure and degradation semantics

- **No map:** continue with existing deterministic context paths
- **Stale map:** label selected records stale; do not silently block ordinary work initially
- **Partial map:** only completed coverage is eligible
- **Refresh failure:** retain prior canonical revision
- **Projection failure:** canonical map may remain current while projection is stale
- **Malformed store:** fail map queries explicitly
- **Contradiction with governing artifact:** show both with authority ordering
- **Contradictory Actor assertions:** preserve provenance and mark disputed
- **Ambiguous entity continuity:** preserve identities and ambiguity; do not silently merge
- **Missing/deactivated Actor:** preserve historical actor_id provenance
- **Repository revision unavailable:** freshness is unknown, not current

## Security and trust boundary

Cartographer is high-read and low-write. Repository content and Actor-linked
institutional knowledge are data, not executable authority. Instructions found
in source/docs/comments/fixtures cannot grant tools or permissions. Actor
attribution likewise cannot grant capability authority.

Future integration-backed Cartography must use normalized, least-authority
repository reads through Battalion-owned boundaries.

## Implementation follow-up requirements

Accepted RFC-0008 should decompose into implementation work covering at least:

1. **WorkflowExecution abstraction** — general execution identity/mechanics shared
   by implementation, Cartography, and Specification workflows without flattening
   their state models.
2. **Cartography logical data contract and persistence** — typed map records,
   deterministic graph-adjacency JSON encoding, migrations/versioning, atomic
   publication, canonical/projection freshness, and Battalion-owned query APIs.
3. **Entity reconciliation** — implement and fixture-test unchanged/rename/move/
   split/merge/delete/new/ambiguous cases; ambiguous continuity must never be
   silently merged.
4. **Cartographer full-refresh workflow** — repository discovery, extraction,
   validation, provenance, cancellation, and failure behavior.
5. **Cartography status/staleness service** — revision/path/evidence changes and
   application queries.
6. **Cartography context retrieval** — deterministic seed/traversal/role weighting
   with fixed budgets and authority/freshness labels.
7. **Institutional knowledge + Actor linkage** — direct attribution,
   verification/dispute/supersession, historical Actor provenance, and the human
   understanding/comprehension surface.
8. **Desktop Cartography graph surface** — focus/neighborhood graph,
   search/detail supplements, freshness, changed areas, constraints, direct Actor
   provenance, and explicit Update Mapping.
9. **Generated Markdown projections** — domain/cross-cutting charter output and
   projection-staleness handling.
10. **Incremental Cartographer refresh** — diff-selected reinspection and
    reconciliation after full-refresh behavior is proven.

## Acceptance test strategy

The implementation must include deterministic fixture coverage for:

- first map of an unmapped project
- ownership and negative ownership
- stable-symbol mapping without line-number identity
- read/write resources and inbound/outbound edges
- cross-cutting invariants/tripwires
- changed-path dispatch
- unchanged refresh
- changed implementation file
- dependency addition/removal
- rename, move, split, merge, deletion, new entity, and ambiguous reconciliation
- partial/unreadable repository areas
- model failure/cancellation before promotion
- malformed generated records
- stale map consumption by an execution
- contradiction between derived claim and ADR/specification
- human Actor assertion surviving refresh
- disputed Actor assertions retaining both provenances
- historical attribution surviving Actor display/membership changes
- Actor provenance never granting authorization
- canonical publication succeeding while projection generation fails
- previous canonical revision surviving failed publication
- bounded deterministic context retrieval

The dogfood scenario maps Battalion, changes a known module, shows deterministic
staleness, refreshes on operator request, inspects map/projection changes, and
proves that later execution receives only a bounded relevant subset of topology,
constraints, governing references, and Actor provenance.

## Accepted decisions

RFC-0008 accepts that:

1. Cartography is a distinct project-maintenance workflow.
2. Battalion introduces `WorkflowExecution` now as the shared durable execution
   abstraction for Implementation, Cartography, and Specification workflows.
3. Battalion maintains a durable socio-technical project map.
4. The initial canonical encoding is deterministic graph-adjacency JSON behind a
   Battalion-owned persistence/query contract; generated Markdown is a
   non-authoritative projection.
5. Observed structure, attributed knowledge, institutional constraints, and
   governing references retain distinct provenance/authority classes.
6. Human interaction with derived Cartography is primarily a comprehension and
   understanding mechanism; only explicit human/governance actions raise authority.
7. Entity identities are Battalion identities independent of revision-specific
   paths/symbol locators; ambiguous reconciliation is preserved rather than guessed.
8. Retrieval is deterministic seed selection plus bounded graph traversal,
   role-specific weighting, explicit authority/freshness, and fixed context budgets.
9. The primary Cartography UI is graph-first with list/search/detail supplements.
10. Initial Actor evidence is limited to direct provenance and authoritative
    assignment/ownership relationships; inferred expertise/social-graph behavior is deferred.
11. Freshness is mechanical evidence and never automatically authorizes model spend.
12. Cartographer cannot silently promote its own inferences into governing
    architecture or accepted institutional truth.
