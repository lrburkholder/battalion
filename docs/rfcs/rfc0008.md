# RFC-0008 — Cartographer Codebase Mapping and Maintenance Workflow

**Status:** Draft
**Ticket:** BTN-85
**Author:** Architecture
**Target:** Post-v1
**Related:** BTN-26, BTN-30, BTN-31, BTN-36, BTN-42, BTN-45, BTN-58, BTN-59, BTN-61, BTN-86, RFC-0006, RFC-0007

---

## Summary

Battalion should add Cartography as a distinct project-maintenance workflow that
inspects a repository and maintains a durable, structured **socio-technical
project map**. The map is broader than a code dependency index: it connects code
structure, symbols, resources, cross-cutting invariants, institutional knowledge,
governing artifacts, evidence, and durable Battalion Actors.

The Cartographer is one producer and maintainer of this map; the map is not
merely "Cartographer output." Human assertions, governing specifications and
ADRs, accepted project evidence, and future collaboration workflows may also
contribute typed records with different provenance and authority classes.

The canonical map should be structured and queryable rather than defined as a
set of generated Markdown files. Human-readable Markdown or diagrams may be
generated as projections for review, publication, or interoperability,
including compatibility with the Gator/Regiment charter pattern. The physical
persistence technology is intentionally deferred to BTN-86, which will benchmark
repository-native files, embedded structured persistence, a credible embedded
graph representation if one exists, and hybrid approaches against one logical
Cartography contract.

Cartography should not be inserted into the Architect -> Driver -> Reviewer ->
Refactorer implementation graph. It has its own lifecycle and may reuse common
Battalion execution infrastructure such as project identity, worker supervision,
model usage evidence, cancellation, and live observation. This RFC uses the term
`WorkflowExecution` for the more general durable execution concept that may
ultimately contain implementation Runs, Cartography jobs, and Specification jobs;
whether to introduce that abstraction immediately remains a follow-up decision.

A Cartographer refresh is operator-initiated in the initial design. Battalion
may calculate staleness indicators mechanically, but elapsed time or changed
commits do not themselves authorize model inference or repository writes.

## Problem

Battalion currently assembles bounded execution context from ticket state,
approved plans, accepted Instincts, interventions, and phase-appropriate source
files. That is intentionally deterministic, but as repositories grow it forces
roles to rediscover structural facts repeatedly: where responsibilities live,
which symbols participate in a flow, what state they read or write, which
cross-cutting invariants constrain them, and which humans or governing artifacts
hold relevant institutional context.

Regiment addresses repository comprehension with Cartographer-generated charter
Markdown. Gator's charter model provides the deeper prior art: logical domains
state what they own and do not own; important callables are located by stable
symbol identifiers; access patterns, callers, callees, tripwires, pre-change
knowledge, and cross-charter connections are recorded; and a cross-cutting
charter captures invariants and implicit contracts that do not belong to any
single module.

Battalion should retain those useful ideas while exploiting capabilities that
Regiment does not have: durable project persistence, Actor identity, assignment
and provenance, deterministic context assembly, application-level queries, live
workflow evidence, and future collaboration data. The result is not simply a
more sophisticated charter format. It is a durable model of the project as a
socio-technical system.

The design must answer five separate questions:

1. What facts and institutional constraints does the project map maintain?
2. How are observed structure, attributed knowledge, normative constraints, and
   governing decisions distinguished?
3. What is the canonical durable representation?
4. How do humans and downstream workflows consume it safely and cheaply?
5. How does Battalion know when parts of the map may be stale without repeatedly
   paying an LLM to rediscover the repository?

## Goals

- reduce repeated repository exploration and model-token consumption
- give humans an inspectable map of the system, its constraints, and its evolution
- connect code topology with durable Actor provenance and organizational context
- preserve the distinction between expertise evidence and actual authorization
- provide bounded, attributable structural and institutional context to workflows
- make freshness and provenance cheap to inspect without model inference
- support full and incremental refresh without silently retaining obsolete facts
- preserve human architectural ownership and existing source-of-truth hierarchy
- reuse Battalion execution and Actor infrastructure where that reduces duplication
- support future repositories and teams substantially larger than Battalion itself

## Non-goals

- replacing source code, ADRs, specifications, accepted Intel, or human decisions
- having Cartographer make, approve, or silently elevate architectural decisions
- treating Actor association as proof of approval authority or project capability
- automatically refreshing merely because a clock or commit threshold elapsed
- requiring every repository to expose generated Markdown charters
- constructing a perfect compiler-grade semantic program graph
- selecting persistence technology without BTN-86 evidence
- allowing ordinary implementation nodes unrestricted access to a mapping store
- treating inferred ownership, intent, expertise, or relationships as facts
  without explicit provenance and authority classification

## Workflow boundary

Cartography is a project-level maintenance workflow.

```text
Project
  |
  +-- Cartography workflow ----> socio-technical project map
  |                                  |
  |                                  +--> human inspection
  |                                  +--> bounded context retrieval
  |                                  +--> collaboration/expertise evidence
  |
  +-- Specification workflow ---> accepted work specification
  |
  +-- Implementation Run -------> Architect -> Driver -> Reviewer -> Refactorer
```

The workflows may share infrastructure but do not share authority.

A Cartography execution has at minimum these lifecycle states:

- `requested`
- `inspecting`
- `assembling`
- `validating`
- `completed`
- `failed`
- `cancelled`

A failed or cancelled refresh leaves the last completed map readable. New data
is not promoted piecemeal into the current map unless the persistence design can
prove the resulting revision is complete and internally consistent.

### Reuse of Run infrastructure

Cartography should reuse the following concepts unless implementation evidence
shows a conflict:

- Project identity
- Actor attribution for operator-triggered actions
- detached worker supervision
- live observation events
- model/provider usage and cost evidence
- cancellation and failure evidence
- application commands and queries

It should not pretend to be a ticket implementation Run merely to obtain those
mechanics. A follow-up architecture ticket should decide whether Battalion
introduces a general `WorkflowExecution` identity with typed workflow kinds, or
keeps Cartography as a sibling durable execution type that reuses lower-level
services.

## Gator-derived logical content model

Gator demonstrates that useful Cartography requires more than packages and
`depends_on` edges. Battalion should preserve the following conceptual content:

- **domain ownership** — what a logical subsystem is responsible for
- **negative ownership** — what explicitly belongs elsewhere
- **stable symbol location** — callable/class/entry-point identities that survive
  ordinary line churn better than line-number anchors
- **access patterns** — resources, models, stores, caches, files, or external
  surfaces read, written, or read-written
- **inbound relationships** — callers and upstream dependencies
- **outbound relationships** — callees and downstream dependencies
- **tripwires** — non-obvious behavior that must be preserved or investigated
- **pre-change institutional knowledge** — implicit contracts and intentional
  decisions relevant before editing an area
- **cross-cutting patterns** — multi-domain flows, invariants, synchronization
  requirements, negative space, and other constraints that cannot live under one
  module
- **path dispatch** — deterministic changed-path -> relevant-map-area bindings
  suitable for refresh selection and context retrieval

Battalion does not need one Markdown file per domain to retain this granularity.
Fine-grained symbol and relationship records can be stored canonically while
human projections remain grouped by logical domain.

## Canonical socio-technical map model

The logical model is independent of BTN-86's physical persistence result.

```text
MapRevision
  - map_revision_id
  - project_id
  - repository_revision
  - started_at / completed_at
  - producer workflow/model/prompt/config provenance
  - requesting actor_id when human-triggered
  - inspected scope
  - completeness / warnings

Domain
  - domain_id
  - name
  - repository/path scope
  - owns[]
  - does_not_own[]
  - bounded purpose summary
  - evidence references
  - first_seen / last_seen

Symbol
  - symbol_id
  - domain_id
  - stable symbol locator
  - kind
  - path
  - bounded responsibility summary
  - first_seen / last_seen

Resource
  - resource_id
  - kind
  - locator/name
  - sensitivity/classification metadata where applicable

Relationship
  - source entity
  - target entity
  - kind
  - access mode where applicable
  - evidence references
  - first_seen / last_seen

KnowledgeClaim
  - claim_id
  - statement
  - applies_to[]
  - provenance
  - asserted_by_actor_id optional
  - verified_by_actor_ids[]
  - evidence references
  - authority_class
  - lifecycle

InstitutionalConstraint
  - constraint_id
  - kind
  - statement
  - applies_to[]
  - asserted_by_actor_id optional
  - verified_by_actor_ids[]
  - governing_artifact_refs[]
  - evidence references
  - authority_class
  - lifecycle
  - supersedes / disputed_by references

PathBinding
  - path matcher
  - relevant domain/symbol/constraint references
  - evidence/revision

Annotation
  - target map entity
  - actor_id or generated provenance
  - bounded content
  - lifecycle
```

The implementation may normalize these differently, but the semantic
distinctions must survive storage selection.

### Map granularity

Battalion should map logical domains and significant stable symbols. It should
not make every local helper, generated symbol, or trivial function a durable
entity by default. Symbol inclusion should be driven by architectural relevance,
public/internal boundary value, state access, cross-domain participation, or
tripwire significance.

This differs from the earlier coarse-only direction. Gator's evidence suggests
that stable callable identifiers are valuable precisely because they support
navigation, blast-radius reasoning, and access-pattern documentation without
fragile line anchors.

Initial relationship kinds should remain schema-controlled, for example:

- `contains`
- `depends_on`
- `invokes`
- `reads`
- `writes`
- `read_writes`
- `implements_contract`
- `tests`
- `governed_by`
- `asserted_by`
- `verified_by`
- `owned_by` where ownership is a real Battalion concept
- `assigned_to` where assignment is imported from authoritative Battalion state
- `relevant_actor` for explicitly non-authoritative expertise/context links

Free-form model-invented edge types must not silently become durable schema.

## Knowledge and authority classes

The map must distinguish at least four categories that may describe the same
area of code but mean different things:

| Category | Example | Meaning |
| --- | --- | --- |
| Observed structure | `A invokes B`; `B writes RunState` | Derived from repository evidence |
| Institutional knowledge | "This path exists for legacy clients" | Attributed descriptive claim |
| Institutional constraint | "Do not bypass this cache because reporting depends on the side effect" | Normative claim whose authority depends on provenance |
| Governing decision | ADR requires human mutation through the application boundary | Authoritative reference to a governing artifact |

A Cartographer inference such as "this appears to be an invariant" must not be
stored with the same authority as an ADR-backed constraint or a human assertion.
A useful initial authority taxonomy is:

- `derived` — inferred by Cartographer from repository/evidence
- `attributed` — explicitly asserted by a durable Actor
- `governing_reference` — points to an authoritative specification/ADR/policy;
  the referenced artifact, not the map record, remains authoritative
- `accepted_project_knowledge` — only if a later explicit human review/promotion
  process is designed; Cartographer may not grant this status itself

Lifecycle should support at least `active`, `superseded`, and `disputed`.
Contradictory claims may coexist with provenance until a human or governing
artifact resolves them.

## Actor model integration

Cartography should reuse durable Actor identity from RFC-0007/BTN-59 rather than
inventing charter-local author names.

Actor links can express several different facts and must remain mechanically
separate:

- who requested a Cartography execution
- who asserted an institutional claim or constraint
- who later verified, disputed, or superseded it
- who currently owns or is assigned related work, when authoritative Battalion
  assignment/ownership data exists
- who has historical participation or inferred expertise relevant to the area

The final category is explicitly **non-authoritative**. Evidence that an Actor
has contributed to a subsystem, authored several constraints, resolved related
interrupts, or historically owned work may help answer "who should we ask?" It
must never answer "who is allowed to approve?" Authorization continues to come
from project membership and capability policy, not Cartography.

Example:

```text
InstitutionalConstraint
  statement: "Interrupt resolution must pass through Actor authorization."
  applies_to: [domain:battalion.application, symbol:resolve_interrupt]
  asserted_by_actor_id: actor:bob
  verified_by_actor_ids: [actor:alice]
  governing_artifact_refs: [ADR-0026]
  authority_class: governing_reference
```

The map can later surface that Bob supplied context and Alice verified it while
still requiring the active Actor's actual `approve` or `resolve-interrupt`
capability before any workflow action is admitted.

### Socio-technical queries enabled by the model

The map should eventually support bounded questions such as:

- What calls this symbol and what does it mutate?
- What domains may be affected by changing this path?
- What constraints or tripwires apply to this code?
- Which ADR/specification governs the relevant constraint?
- Who originally supplied this institutional knowledge?
- Who currently owns or is assigned related work?
- Which Actors have relevant non-authoritative expertise evidence?
- How fresh is each structural or institutional fact relative to the current
  repository revision?

This is a defining difference from repository-only Cartography.

## Authority and provenance

The Cartographer may read repository content and write only its declared mapping
store/projections. It may not silently modify:

- implementation source or tests
- `spec.md` or work specifications
- `plan.md`
- ADRs or RFC decisions
- `backlog.json`
- accepted Intel
- Actor membership/capabilities, assignment, or ownership records
- role definitions, graph control, write scopes, or interrupts

Every generated claim must be attributable to a completed `MapRevision` and,
where practical, to repository evidence such as paths, symbols, or inspected
revision content. The map may summarize architectural intent found in an ADR,
but the ADR remains the authority and the record retains that source reference.

Human-authored claims and constraints must survive Cartographer refreshes. A
refresh can mark supporting code evidence stale or contradictory; it cannot
rewrite what an Actor said or manufacture a new Actor attribution. Contradictions
must be surfaced for review.

## Persistence boundary and BTN-86

This RFC selects the logical information model, not its storage engine. BTN-86
must benchmark the candidates against this schema and the same candidate-neutral
operations.

At minimum BTN-86 evaluates:

- Markdown/Gator-style charters as a control
- repository-native structured files
- SQLite or equivalent zero-service embedded structured storage
- one credible lightweight embedded graph-oriented representation if available
- hybrid storage where structured canonical data produces human-readable
  projections

The benchmark should weight deterministic retrieval, incremental updates,
atomic publication, revision diffing, failure recovery, portability, schema
evolution, inspectability, and dependency cost above raw throughput.

Whatever wins must remain behind Battalion-owned persistence/query contracts.
Execution roles must not receive raw SQL, database handles, graph query access,
or arbitrary map mutation tools.

## Freshness and staleness

Freshness is evidence, not a binary claim that the model is correct.

Battalion can compute these values without an LLM:

- last successful mapping timestamp
- mapped repository revision
- current repository revision
- commit distance where the VCS can provide it
- paths changed since the mapped revision
- mapped entities whose evidence paths have changed
- path bindings affected by changes
- paths/symbols deleted or renamed since mapping
- constraints whose supporting evidence changed
- whether the last refresh was partial or emitted warnings

A simple initial status taxonomy is:

- `missing`
- `current`
- `changed`
- `significantly_changed`
- `partial`
- `unknown`

Time since refresh and commit distance are presentation signals, not automatic
truth about semantic staleness.

### Operator behavior

The desktop and application query boundary should expose a projection similar
to:

```text
Project map
Updated 4 days ago | 23 commits behind
Mapped at 6d21c94 | current 92af4ab
Potentially affected: battalion.application, battalion.actors, battalion.graph
3 institutional constraints have changed supporting evidence
[Update mapping] [View map]
```

The initial `Update mapping` action is explicit and attributable to the Actor who
requested it. No staleness threshold automatically invokes an LLM.

## Refresh strategy

### Full refresh

The first Cartographer implementation should support a full refresh from a
selected repository revision. The new generated structural layer is built
separately and promoted atomically only after validation succeeds.

Validation should include at least:

- referenced paths/symbols resolve at the mapped revision where expected
- relationship endpoints exist
- entity identifiers are unique
- required provenance fields are populated
- generated records conform to bounded schemas
- Actor references resolve when they claim durable Actor provenance
- generated refresh does not overwrite human-authored claims/constraints
- no writes occurred outside mapping-owned storage/projections

### Incremental refresh

Incremental refresh should follow only after full-refresh semantics are reliable.
It can use VCS changes plus `PathBinding` records to select affected entities,
constraints, and neighboring relationships.

Incremental logic must explicitly handle:

- file/directory and symbol rename
- deletion
- module split or merge
- new and removed dependency edges
- changed resource access patterns
- changed cross-cutting flows
- configuration/entry-point changes with broad effects
- stale entities no longer supported by repository evidence
- institutional constraints whose supporting code changed but whose human
  assertion remains historically valid

A changed path is a hint about what to re-inspect, not proof that only that map
entity changed semantically.

## Downstream consumption

Execution roles should not receive the entire map by default. The existing
context assembler should gain a Cartography retrieval stage that selects a small
set of relevant records deterministically from ticket/specification terms,
write-scope paths, planned paths, `PathBinding`s, and relationship neighborhoods.

A normalized context record should contain, where relevant:

- entity identity and kind
- bounded purpose/ownership/negative-space summary
- significant symbols and access patterns
- relevant relationships
- applicable KnowledgeClaims and InstitutionalConstraints
- Actor attribution where useful
- governing artifact/evidence references
- mapped repository revision
- freshness/authority/lifecycle status

Context assembly must:

- have a separate token/character budget for map context
- use stable ordering and deterministic selection
- identify stale, disputed, partial, or derived records explicitly
- omit the map cleanly when none exists
- never hide conflicts between map content and higher-authority artifacts
- never infer Actor authorization from expertise/provenance links
- avoid exposing a general mapping query tool directly to ordinary role prompts

Potential role usage:

- **Specifier:** orientation and terminology; cannot derive product intent from
  topology or inferred organizational knowledge.
- **Architect:** system boundaries, likely affected domains, governing decisions,
  institutional constraints, and people who may have useful context.
- **Driver:** narrow navigation around declared implementation scope plus
  applicable tripwires and access patterns.
- **Reviewer:** independent blast-radius and invariant cues, including changed
  supporting evidence for institutional constraints.
- **Recon/future workflows:** candidate structural/institutional observations with
  normal provenance and promotion rules.

## Relationship to RFC-0006 KnowledgeSource

Cartography is project-owned derived and attributed knowledge, while RFC-0006
`KnowledgeSource` abstracts external/provider-backed attributable retrieval. The
canonical project map therefore does not require a `KnowledgeSource` provider to
read itself.

The retrieval shape should remain compatible in spirit: bounded records, source
identity, Actor attribution where present, revision evidence, applicability,
and deterministic context selection. A future adapter may expose Cartography
through a common internal knowledge-query interface without changing ownership
or authority.

## Human-readable projections

Battalion should support projections after the canonical contract is stable:

- Gator-style or Battalion-native domain charter Markdown
- cross-cutting constraint/invariant views
- changed-path dispatch tables
- high-level dependency listings
- diagram source
- UI tree/graph views
- Actor/context views showing attributed institutional knowledge without
  confusing expertise with authorization

Projections are reproducible views. Editing a generated projection must not
silently mutate canonical map records unless a later explicit import contract is
designed.

## Failure and degradation semantics

- **No map:** execution continues through existing deterministic context paths.
- **Stale map:** selected records are labeled stale; initial policy warns rather
  than silently blocking ordinary work.
- **Partial map:** only records within declared completed coverage are eligible.
- **Refresh failure:** retain the prior completed map and durable failure evidence.
- **Malformed store:** fail Cartography queries explicitly; do not guess context.
- **Contradiction with governing artifact:** show both with authority ordering.
- **Contradictory Actor assertions:** retain provenance and mark disputed rather
  than silently choosing one.
- **Missing/deactivated Actor:** preserve historical actor_id provenance; do not
  rewrite the claim to another Actor.
- **Repository revision unavailable:** mark freshness unknown rather than current.

## Security and trust boundary

Cartographer is a high-read, low-write workflow. Repository-wide read access is
necessary for useful mapping, but writes must be restricted to mapping-owned
storage and explicitly configured projections.

Repository content is untrusted model input. Instructions found in source,
documentation, comments, fixtures, issue text, or generated files do not grant
Cartographer new tools or authority.

Actor-linked institutional knowledge is also data, not executable authority. A
claim attributed to an administrator or project owner does not itself grant the
Cartographer, a downstream role, or another Actor any capability.

A future integration-backed Cartographer must still receive normalized,
least-authority repository reads through Battalion-owned boundaries rather than
ambient provider tools.

## Alternatives considered

### Regiment/Gator-style Markdown as canonical store

**Advantages:** transparent Git history, direct human readability, trivial
portability, proven comprehension pattern.

**Not selected by architecture alone:** structured retrieval, Actor linkage,
relationship traversal, identity, incremental refresh, and freshness are harder.
BTN-86 retains Markdown as the benchmark control and may still justify it or a
hybrid if evidence outweighs these concerns.

### Repository-native structured files

**Advantages:** typed, versionable, inspectable, no database.

**Status:** viable BTN-86 candidate. Relationship density, incremental mutation,
and diff noise must be measured rather than assumed.

### SQLite/project-local structured store

**Advantages:** local-first, transactional, queryable, indexed, single-file,
zero service dependency.

**Status:** strong BTN-86 candidate, not an RFC-0008 decision.

### Dedicated/embedded graph storage

**Advantages:** natural relationship traversal and visualization queries.

**Status:** benchmark only if a credible lightweight embedded option exists. A
server or paid/hosted dependency is out of scope for local-first Battalion.

### Re-explore repository on every Run

**Rejected:** preserves no institutional map, repeatedly spends model/tool
budget, cannot expose project-level freshness or Actor-linked institutional
knowledge, and makes understanding dependent on transient exploration.

## Open decisions before acceptance

1. Whether `WorkflowExecution` becomes a shared durable abstraction now or
   Cartography initially uses a sibling execution record.
2. BTN-86 persistence benchmark result and selected storage/projection boundary.
3. Exact initial Domain/Symbol/Resource and relationship-kind enums.
4. Stable entity identity across Git renames and substantial module movement.
5. Exact promotion/review workflow, if any, from `derived` Cartographer claims to
   accepted human/project knowledge.
6. Whether human institutional records live physically with generated map records
   or in a separately versioned overlay while sharing one logical query model.
7. Deterministic retrieval/ranking algorithm and dedicated context budget.
8. Initial UI navigation: list/tree only, graph visualization, or both.
9. Threshold/algorithm for `significantly_changed` presentation.
10. Which Actor/expertise evidence sources are useful enough to include without
    drifting into a premature social-graph implementation.

## Acceptance test strategy

The eventual implementation should be proven with deterministic fixture
repositories before dogfooding Battalion itself. Coverage should include:

- first map of an unmapped project
- domain ownership and explicit negative ownership
- significant-symbol mapping without line-number identity
- read/write resource access and inbound/outbound relationship mapping
- cross-cutting invariant/tripwire mapping
- changed-path dispatch to relevant domains/constraints
- unchanged refresh
- changed implementation file
- cross-module dependency addition/removal
- rename and deletion
- partial/unreadable repository area
- model failure or cancellation before promotion
- malformed generated records
- stale map consumption by an Execution Run
- contradiction between derived map claim and ADR/specification
- human Actor assertion surviving refresh
- two Actor assertions being retained as disputed rather than silently merged
- historical attribution surviving Actor display-name or membership changes
- expertise/relevant-Actor evidence not granting authorization
- atomic retention of the previous map after failed refresh
- context retrieval remaining within a fixed budget

The dogfood acceptance scenario should map Battalion, modify a known module,
show deterministic staleness in the desktop/application projection, refresh on
operator request, inspect the map diff, and demonstrate that a later execution
receives only a bounded relevant subset containing topology, applicable
constraints, governing references, and Actor provenance rather than the full map.

## Decision requested

Accept the architecture direction that:

1. Cartography is a distinct project-maintenance workflow.
2. Battalion maintains a durable socio-technical project map, not merely a set
   of Cartographer-generated documentation files.
3. The map connects code domains/symbols/resources with cross-cutting
   relationships, institutional knowledge and constraints, governing artifacts,
   evidence, and durable Actors.
4. Observed structure, attributed knowledge, normative constraints, and
   governing decisions retain distinct provenance and authority classes.
5. Actor links provide attribution, collaboration context, and non-authoritative
   expertise evidence; they never substitute for capability authorization.
6. BTN-86 selects the physical persistence approach empirically; Markdown and
   diagrams remain potential projections/interoperability surfaces.
7. Freshness is determined mechanically and displayed without automatic model
   invocation.
8. Execution workflows consume only bounded, provenance-rich map records through
   canonical context assembly.
9. The Cartographer cannot silently promote its own inferences into governing
   architecture or accepted institutional truth.
