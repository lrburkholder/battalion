# RFC-0025 — Architectural Significance Signals and Steelman Interrupts

**Status:** Proposed  
**Date:** 2026-09-06  
**Ticket:** BTN-112  
**Author:** Architecture  
**Target:** Post-v2 workflow orchestration  
**Related:** `philosophy.md`, BTN-8, BTN-108, BTN-109, RFC-0014, RFC-0015, RFC-0018, RFC-0023

---

## Summary

Battalion should make architectural significance first-class evidence.

A change can be correct, tested, and mechanically valid while still crossing a boundary that needs architectural judgment. Battalion must detect and preserve that fact separately from test results and implementation success.

Execution may produce `SignificanceSignal` records. Battalion validates and persists each signal. Admitted policy then selects the required route. The signal does not grant permission and does not choose its own route.

When policy requires Architect review, Battalion also requires a bounded `SteelmanAssessment`. The steelman records the strongest credible case against landing the exact candidate. It is evidence, not the Architect decision.

```text
candidate change
    |
    v
SignificanceSignal
    |
    v
Battalion validation and persistence
    |
    v
admitted policy
    |-------------------|-------------------|
    v                   v                   v
Architect interrupt   specialist review   no extra action
    |
    v
SteelmanAssessment
    |
    v
human disposition
```

## Problem

Battalion already checks correctness inside an admitted implementation boundary. It has TDD checkpoints, deterministic gates, typed workflow contracts, review evidence, authorization, write scope, and escalation policy.

Those mechanisms do not answer this question:

> Did a locally correct change alter a boundary whose blast radius exceeds the producing execution's authority?

Examples include:

- a public API change with passing local tests;
- a shared invariant change;
- a responsibility move across an architecture or ownership boundary;
- a schema or data-model change that requires migration;
- a security-sensitive change that does not violate an existing deterministic rule;
- a project-defined architectural tripwire.

Do not solve this only with prompt prose. Do not add a separate hard-coded pause mechanism. Represent significance as typed evidence and route it through Battalion policy.

## Goals

- Define a versioned `SignificanceSignal` contract.
- Keep it independent of provider, model, language, and role.
- Support deterministic, project-policy, and model-observed signals.
- Preserve affected scope and provenance.
- Keep evidence, routing, and human disposition separate.
- Reuse BTN-109 escalation mechanics without calling significance a failure.
- Carry signal references through BTN-108 typed workflow contracts.
- Require a steelman when policy requires Architect review.
- Make compatibility and blast radius inspectable.
- Prevent passing tests from suppressing significance.
- Let local changes bypass architecture review when no significance rule fires.
- Prevent a model from suppressing or resolving required significance evidence.

## Non-goals

- Give models architecture approval authority.
- Interrupt on every change.
- Replace review, security checks, tests, or authorization.
- Treat model confidence as authority.
- Store chain-of-thought as steelman evidence.
- Require deterministic detection for every concern.
- Infer organization structure from repository layout alone.
- Let a signal choose the next workflow action.
- Let project tripwires broaden execution authority.

## Design

### Significance is evidence

A `SignificanceSignal` says that a candidate crossed or may have crossed a named boundary for concrete reasons.

It does not say that execution may continue. It does not approve architecture. It does not select a role or workflow.

Battalion policy owns routing. Human authority owns architectural disposition.

### Detection and disposition are separate

A signal can come from:

- deterministic repository analysis;
- admitted project policy;
- a model role with sufficient bounded evidence;
- a later review or boundary-validation step.

Battalion validates the signal. Policy selects the route. An authorized human or specialist records the disposition.

### Tests do not prove insignificance

These facts can both be true:

```text
unit tests = pass
public interface = changed
```

The passing test result cannot erase the significance signal.

### Prefer deterministic evidence

Use deterministic detection when repository or tool evidence supports it. Allow semantic model observation when syntax is insufficient.

A model-observed signal must identify:

- the boundary or invariant;
- affected artifacts;
- a concrete before/after claim;
- supporting evidence references;
- why the effect is non-local.

Reject unsupported statements such as "this feels architectural."

## `SignificanceSignal v1`

```text
SignificanceSignal v1
  signal_id
  schema_version
  significance_class
  trigger_source
    kind: deterministic | project_policy | model_observation
    rule_id / detector_id / observation_kind
  subject
    project_id
    repository/workspace identity
    change/revision identity
  affected_scope[]
  evidence_refs[]
  producer
    run_id
    workflow_kind
    stage/node/execution_id?
    actor_id?
    role/model provenance?
  compatibility_assessment_ref?
  created_at
```

Use references to evidence. Do not copy unrestricted Run state into the signal.

Initial classes:

```text
PUBLIC_INTERFACE_CHANGE
CROSS_COMPONENT_INVARIANT_CHANGE
ARCHITECTURE_BOUNDARY_CROSSING
OWNERSHIP_BOUNDARY_CROSSING
SCHEMA_OR_DATA_MODEL_CHANGE
SECURITY_SENSITIVE_CHANGE
PROJECT_TRIPWIRE
```

`PROJECT_TRIPWIRE` must retain the configured tripwire identity and evidence.

## Trigger sources

### Deterministic analysis

Possible detectors include:

- public API or exported-symbol diffs;
- schema, DDL, or migration diffs;
- dependency or module-boundary changes;
- configured security-sensitive paths;
- ownership metadata;
- configured path, annotation, manifest, or policy tripwires.

Record the detector or rule version and the evidence that fired it.

### Project policy

Projects may define domain-specific tripwires. Store these as admitted, versioned, inspectable project policy. Do not hide executable policy in model prompt text.

A project tripwire can make a local change significant. It cannot grant permission to bypass review.

### Model observation

Allow model observation for semantic boundaries that deterministic tools cannot reliably detect. Treat the observation as evidence, not authority.

## Compatibility assessment

Use a structured `CompatibilityAssessment` when the significance class or policy makes compatibility relevant.

```text
CompatibilityAssessment v1
  assessment_id
  signal_refs[]
  compatibility_dimensions[]
    source compatibility
    binary/runtime compatibility
    data compatibility
    protocol compatibility
    migration compatibility
    operational compatibility
  known_consumers_or_dependencies[]
  affected_versions/environments[]
  migration_or_rollout_requirements[]
  unknowns[]
  evidence_refs[]
  producer provenance
```

Each dimension must be explicit: `not_applicable`, `supported`, `breaking`, or `unknown`.

## Steelman assessment

When admitted policy requires Architect review, require a durable `SteelmanAssessment` before the human decision boundary.

If the execution cannot produce a steelman because required evidence is missing, make that absence explicit interrupt evidence.

```text
SteelmanAssessment v1
  steelman_id
  signal_refs[]
  candidate_change_ref
  strongest_counterarguments[]
  likely_consumers_or_dependencies_affected[]
  blast_radius
  compatibility_or_migration_concerns[]
  secondary_effects[]
  lower_blast_radius_alternatives[]
  evidence_refs[]
  limitations_or_unknowns[]
  producing execution provenance
```

The steelman should answer:

- What is the strongest reason not to land the change as-is?
- Who or what can break despite local correctness?
- Which compatibility obligations change?
- What migration, rollout, coordination, or documentation work follows?
- What secondary operational, security, or maintenance effects are plausible?
- Is there a credible lower-blast-radius alternative?

Do not invent an alternative when none is credible. Record the evidence and limitation instead.

The steelman is immutable review evidence. It is not the Architect decision.

## Routing and BTN-109

Do not add a significance-specific pause state.

Treat significance as a normalized policy-trigger family. Keep existing failure classes unchanged.

```text
SignificanceSignal
    -> normalized policy trigger
    -> admitted escalation/workflow policy
    -> HUMAN_INTERRUPT | specialist workflow | explicit no-extra-action
```

Do not force significance into `failure_class`. A successful implementation can still be significant.

Policy admission must reject a configuration that lets an executing model suppress a mandatory trigger or grant itself a more permissive route.

## BTN-8 HumanInterrupt

BTN-8 remains the durable human decision mechanism.

A significance interrupt should reference:

```text
interrupt kind: ARCHITECTURAL_SIGNIFICANCE
signal refs[]
steelman ref?
compatibility assessment ref?
required authority
allowed resolutions[]
```

Keep the exact resolution vocabulary centralized with BTN-8. BTN-112 only requires inspectable links between significance evidence and disposition.

## BTN-108 workflow contracts

Carry significance evidence through explicit typed outputs or references. Do not give producing models broader mutation rights over Run state.

RFC-0015 already anticipates significance and escalation evidence in `ImplementationResult v1`.

```text
model result
  -> Battalion validation
  -> persisted significance/steelman evidence
  -> canonical typed result references evidence
  -> next boundary receives authoritative references
```

Deterministic detectors may attach signals without model output.

## Aggregation

Keep signal records immutable.

Deduplicate exact duplicate emissions by stable identity or digest. Group related signals for display or policy evaluation when useful. Do not erase source provenance or independent classes.

A model observation cannot suppress a deterministic or project-policy signal.

Policy should normally evaluate the union of validated classes for the candidate.

## Trivial-change bypass

Do not infer significance from line count or model uncertainty.

Bypass significance review when:

- no deterministic detector fires;
- no project tripwire fires;
- no valid model signal exists;
- no other admitted policy requires architecture review.

A one-line public-contract change can be significant. A large internal refactor can be non-significant.

## Model suppression and self-resolution

A model must not be able to:

- delete deterministic or project-policy signals;
- mark a signal resolved;
- forge a human disposition;
- replace a required `HUMAN_INTERRUPT` with continue;
- omit a required signal because tests pass;
- rewrite admitted significance policy;
- mutate a steelman after disposition.

Battalion application code owns validation, persistence, routing, interrupt state, and disposition linkage.

## Inspection requirements

Inspection must answer:

- Why is this change significant?
- Which classes fired?
- What produced each signal?
- Which artifacts or boundaries are affected?
- What compatibility effects were found?
- What is the strongest case against the change?
- Which consumers may be affected?
- Which lower-blast-radius alternatives were considered?
- Which route did policy select?
- What did the authorized human or specialist decide?

Show signal evidence, steelman evidence, policy routing, and human disposition as separate records.

## Persistence and provenance

RFC-0023 applies.

`SignificanceSignal`, `CompatibilityAssessment`, and `SteelmanAssessment` are evidence artifacts. Provenance does not grant authority.

Only an admitted human-decision or HumanInterrupt operation can create the authority-bearing Architect decision.

Retain exact project-policy and detector identity/version where they contribute to a signal.

## Versioning

Use stable Battalion-owned contract names and versions under RFC-0015.

Fail closed when a workflow or policy encounters an unsupported significance contract version or class. Do not silently interpret an unknown class as insignificant.

Compatibility adapters may normalize known older forms. Preserve original evidence and adapter provenance.

## Validation

Implementation must test:

- each initial deterministic significance class;
- project tripwires;
- valid and invalid model observations;
- trivial-change bypass;
- passing tests plus a significance signal;
- compatibility states;
- required steelman generation;
- specialist routing;
- explicit policy no-extra-action;
- typed contract propagation;
- model suppression and forged disposition attempts;
- aggregation without provenance loss;
- unsupported contract versions/classes failing closed.

## Alternatives rejected

**Prompt-only significance check:** not versioned or mechanically routable.

**Hard-coded pre-commit interrupt:** creates a parallel ceremony and misses other detection points.

**Review finding only:** significance is not necessarily a defect.

**BTN-109 failure class:** misstates the domain because successful work can be significant.

**Always interrupt:** prevents admitted specialist and informational routes.

## Open questions

1. Must a model-observed signal have independent corroboration before it can force an Architect interrupt, or can admitted policy allow one structured model observation to trigger directly?
2. Should architecture-boundary and ownership-boundary signals remain separate stable classes?
3. Where should project tripwire policy live?
4. Should the same execution produce the steelman, or should policy invoke an independent read-only steelman capability?
5. Should compatibility assessment be mandatory for every Architect interrupt or only when the class/policy makes it meaningful?
6. Should BTN-112 rename or generalize RFC-0018's `FailureEscalationPolicy`, or leave the accepted name intact?

## Proposed decision

Adopt `SignificanceSignal` as a first-class evidence contract and significance as a first-class normalized policy-trigger family.

Keep these layers separate:

```text
SignificanceSignal / CompatibilityAssessment
    = boundary impact evidence

SteelmanAssessment
    = strongest bounded case against the candidate

admitted escalation/workflow policy
    = required process

human/specialist disposition
    = authority-bearing decision
```

This preserves human-directed architecture while making architectural escalation inspectable, testable, configurable, and independent of one model's prompt intuition.
