# RFC-0024 — Architectural Significance Signals and Steelman Interrupts

**Status:** Proposed  
**Date:** 2026-09-05  
**Ticket:** BTN-112  
**Author:** Architecture  
**Target:** Post-v2 workflow orchestration  
**Related:** `philosophy.md`, BTN-8, BTN-108, BTN-109, RFC-0014, RFC-0015, RFC-0018, RFC-0023

---

## Summary

Battalion should make **architectural significance** a first-class, versioned evidence contract evaluated by Battalion-owned policy rather than a prompt-level intuition or a special-case pre-commit check.

The central rule is:

> A change can be locally correct, fully tested, and mechanically valid while still crossing a boundary that requires architectural judgment.

Execution may therefore produce one or more `SignificanceSignal` records when it observes a change that crosses a configured architectural or risk boundary. A signal is evidence, not permission and not a workflow transition. Battalion validates and persists the signal, then evaluates the admitted workflow/failure-escalation policy to determine whether the result requires an Architect/HumanInterrupt, specialist review, another explicitly admitted path, or no extra action.

For paths that require architectural judgment, the producing execution must also create a bounded `SteelmanAssessment`: the strongest credible case against landing the change, grounded in the affected interfaces, consumers, compatibility obligations, migration cost, secondary effects, and lower-blast-radius alternatives that can be identified from available evidence.

The steelman is durable review evidence. It remains distinct from the human Architect's decision and cannot self-resolve the interrupt it helped trigger.

Conceptually:

```text
implementation / review / deterministic analysis
                 |
                 v
        candidate SignificanceSignal
                 |
        Battalion validation
                 |
                 v
       durable significance evidence
                 |
                 v
   admitted escalation/routing policy
       |              |             |
       v              v             v
 Architect/Human   specialist    no extra
 Interrupt         review        action
       |
       v
 bounded SteelmanAssessment
       |
       v
 explicit human/policy disposition
```

---

## Problem

Battalion already has strong mechanisms for determining whether work is correct *inside* an admitted implementation boundary: TDD checkpoints, deterministic gates, typed workflow contracts, review evidence, authorization, write scope, and declarative failure/escalation policy.

Those mechanisms do not answer a different question:

> Even if this implementation is correct, did it change something whose blast radius or architectural meaning exceeds the authority of the producing execution?

Examples include:

- changing a public API while keeping all local tests green;
- changing a shared invariant relied upon by multiple modules;
- moving responsibility across an ownership or architecture boundary;
- changing a schema or data model in a way that implies migration or compatibility work;
- modifying security-sensitive code without violating an existing deterministic security rule;
- touching a project-specific tripwire that the organization has declared architecturally significant.

Without a first-class mechanism, Battalion would have to rely on one of two weak options:

1. ask the model to "notice significant changes" in prompt prose, making the result difficult to inspect, test, version, and route consistently; or
2. encode every significance class as a bespoke graph pause, creating a parallel escalation system beside BTN-8 and BTN-109.

Neither is acceptable. Significance should become a typed evidence source consumed by existing orchestration policy.

---

## Goals

- define a versioned `SignificanceSignal` contract independent of provider, model, repository language, and role;
- cover initial significance classes for public interfaces, cross-component invariants, architecture/ownership boundaries, schema/data-model changes, security-sensitive changes, and project-configured tripwires;
- distinguish deterministic, policy-derived, and model-observed triggers;
- preserve concrete affected scope and producing Run/node/Actor provenance;
- keep significance evidence distinct from permission, routing, and human disposition;
- compose with BTN-109 recovery/escalation policy rather than creating a second pause mechanism;
- carry significance evidence through BTN-108 typed workflow contracts without widening model mutation authority over Run state;
- require a bounded steelman for Architect-interrupting paths;
- make compatibility and blast-radius evidence inspectable without reconstructing a chat transcript;
- ensure passing tests cannot suppress an independently triggered significance signal;
- avoid forcing trivial/local changes through architectural review unless project policy explicitly marks them significant;
- make attempts by an executing model to suppress or self-resolve a required signal mechanically ineffective.

## Non-goals

- asking a model to approve architecture;
- turning every code change into an Architect interrupt;
- replacing semantic Review Run, security review, deterministic tests, or authorization policy;
- treating model confidence as architectural authority;
- preserving raw chain-of-thought as the steelman artifact;
- requiring deterministic detection for every possible architecture concern;
- inferring arbitrary organization structure from repository layout alone;
- making a significance signal itself choose the next workflow action;
- allowing project tripwires to grant broader execution authority.

---

## Design principles

### 1. Significance is evidence, not control authority

A `SignificanceSignal` says:

```text
"this admitted execution crossed or may have crossed boundary X,
for these concrete reasons and affected artifacts"
```

It does **not** say:

```text
"therefore I may continue"
"therefore the Architect approves"
"therefore route to role Y"
```

Routing remains application/policy authority, consistent with RFC-0018.

### 2. Detection and disposition are separate

The producer of a signal may be:

- deterministic repository analysis;
- project/repository policy;
- a model role operating within its existing evidence contract;
- a later review or boundary-validation step.

The consumer that decides what happens next is Battalion's admitted policy evaluator.

The human Architect's resulting decision is a third, separate record.

### 3. Tests prove local obligations, not architectural insignificance

A passing deterministic gate can prove that its declared check passed. It cannot erase another independently valid significance signal.

For example:

```text
unit tests = pass
API compatibility detector = public interface changed
```

remains significant even if every unit test is green.

### 4. Deterministic signals are preferred where reliable; semantic observation remains allowed

Battalion should mechanically detect significance where repository/tool evidence makes that reliable, but significance is not limited to syntactic rules.

A model-observed signal is legal when the role has enough bounded evidence to identify a concrete affected boundary and explain the observation. Model observation remains lower-level evidence subject to policy and review; it does not become authority because the model was confident.

### 5. Project policy may define significance without redefining Battalion semantics

Projects need domain-specific tripwires. Battalion should therefore support configured rules that map project-specific evidence onto a stable significance class or explicit configured tripwire identifier.

The configuration should not create arbitrary executable policy code inside a model prompt.

### 6. The steelman is adversarial evidence, not ritual prose

A steelman must make the strongest credible case **against** landing the candidate as-is. It is not a generic "risks" paragraph and not a request for hidden reasoning.

It should be concrete, bounded, and tied to available evidence.

## `SignificanceSignal` contract

The durable contract should have stable Battalion-owned identity/version independent of implementation class names.

Conceptually:

```text
SignificanceSignal v1
  signal_id
  schema_version
  significance_class
  trigger_source
    kind: deterministic | project_policy | model_observation
    rule_id / detector_id / observation_kind
  subject
    project_id
    repository/workspace identity
    change/revision identity
  affected_scope[]
    artifact/component/interface/schema/boundary identity
  evidence_refs[]
  producer
    run_id
    workflow_kind
    stage/node/execution_id?
    actor_id?
    role/model provenance?
  compatibility_assessment_ref?
  created_at
```

The signal should carry references to evidence rather than unrestricted copies of Run state.

### Initial significance classes

The initial stable class vocabulary should include at least:

```text
PUBLIC_INTERFACE_CHANGE
CROSS_COMPONENT_INVARIANT_CHANGE
ARCHITECTURE_BOUNDARY_CROSSING
OWNERSHIP_BOUNDARY_CROSSING
SCHEMA_OR_DATA_MODEL_CHANGE
SECURITY_SENSITIVE_CHANGE
PROJECT_TRIPWIRE
```

`PROJECT_TRIPWIRE` must retain the exact configured tripwire identity and evidence that fired it.

The stable classes are intentionally broad enough to survive language/framework changes while allowing detector-specific reason codes underneath them.

## Trigger sources

### Deterministic analysis

Examples may include:

- exported/public symbol or API surface diffs;
- schema/DDL/migration diffs;
- dependency-edge or module-boundary changes;
- files/directories explicitly marked as security-sensitive;
- ownership metadata or CODEOWNERS-equivalent boundary changes;
- configured path, annotation, manifest, or policy tripwires.

A deterministic trigger should identify the detector/rule version and exact evidence used.

### Project/repository policy

A project may declare domain-specific significance such as:

```text
changes beneath deployment/production/
changes to billing calculation policy
changes to protocol version manifests
changes to generated client compatibility contracts
```

Policy should be admitted/versioned and inspectable. A project tripwire can make an otherwise local change significant, but it still cannot grant the producing role permission to bypass architectural review.

### Model observation

Some boundaries are semantic and may not be reliably detectable from syntax alone.

A model-observed signal should therefore require structured support:

```text
observed boundary/invariant
affected artifact(s)
concrete before/after claim
supporting evidence refs
reason this has non-local blast radius
```

Unsupported "this feels architectural" output is invalid signal evidence.

---

## Compatibility assessment

Significance paths that involve interfaces, schemas, shared invariants, ownership boundaries, or project policy may require a structured compatibility assessment.

Conceptually:

```text
CompatibilityAssessment v1
  assessment_id
  signal_refs[]
  compatibility_dimensions[]
    source compatibility
    binary/runtime compatibility
    data compatibility
    protocol compatibility
    migration compatibility
    operational compatibility
  known_consumers_or_dependencies[]
  affected_versions/environments[]
  migration_or_rollout_requirements[]
  unknowns[]
  evidence_refs[]
  producer provenance
```

Not every dimension applies to every change. The record should explicitly distinguish `not_applicable`, `supported`, `breaking`, and `unknown` rather than allowing omitted dimensions to imply safety.

A model may help produce this assessment, but deterministic/tool evidence should be retained where available.

---

## Steelman assessment

For any path whose admitted policy requires Architect review, Battalion requires a durable `SteelmanAssessment` before presenting the decision boundary, unless the interrupt itself was raised because the producing execution lacked enough evidence to create one. In that exceptional case the missing steelman becomes explicit interrupt evidence rather than being silently omitted.

Conceptually:

```text
SteelmanAssessment v1
  steelman_id
  signal_refs[]
  candidate_change_ref
  strongest_counterarguments[]
  likely_consumers_or_dependencies_affected[]
  blast_radius
  compatibility_or_migration_concerns[]
  secondary_effects[]
  lower_blast_radius_alternatives[]
  evidence_refs[]
  limitations_or_unknowns[]
  producing execution provenance
```

The artifact should answer, where applicable:

- What is the strongest reason not to land this change as-is?
- Who or what can break even if the local implementation is correct?
- Which compatibility obligations are being altered?
- What migration, rollout, coordination, or documentation burden follows?
- What secondary operational/security/maintenance consequences are plausible?
- Is there a credible alternative that preserves more of the existing boundary or reduces blast radius?

The steelman does not need to oppose the change at all costs. If no credible lower-blast-radius alternative exists, it should say so and provide evidence/limitations rather than inventing one.

The steelman is not the Architect decision. It remains immutable review evidence after disposition.

## Routing through BTN-109

BTN-112 should not introduce a parallel significance-specific pause state.

Instead, validated significance evidence becomes a first-class policy trigger/evidence source consumable by RFC-0018's `FailureEscalationPolicy` or its eventual generalized trigger vocabulary.

Conceptually:

```text
SignificanceSignal
      ↓
normalized policy trigger
      ↓
FailureEscalationPolicy / admitted workflow policy
      ↓
HUMAN_INTERRUPT
ESCALATE_ROLE_OR_WORKFLOW
specialist review
explicit no-extra-action rule
```

A signal is not necessarily a failure. The implementation may have completed correctly. Therefore implementation should avoid forcing significance into a misleading `failure_class` merely to reuse BTN-109.

The preferred reconciliation is to generalize the RFC-0018 trigger layer from "failure-only" semantics to typed **recovery/escalation/policy triggers**, with significance as one trigger family while preserving existing failure classes unchanged.

The actual action remains policy-selected. For example:

```text
PUBLIC_INTERFACE_CHANGE
  -> Architect HumanInterrupt

SECURITY_SENSITIVE_CHANGE
  -> admitted Guardian/Review workflow, then HumanInterrupt if policy requires

PROJECT_TRIPWIRE docs-only compatibility note
  -> recorded evidence, no additional interrupt
```

Policy admission must reject configurations that allow an executing model to suppress a mandatory significance trigger or grant itself a more permissive route.

## Relationship to BTN-8 HumanInterrupt

BTN-8 remains the durable human-controlled decision mechanism.

A significance-triggered interrupt should reference:

```text
interrupt kind: ARCHITECTURAL_SIGNIFICANCE
signal refs[]
steelman ref?
compatibility assessment ref?
required authority: architect / configured human authority
allowed resolutions[]
```

The human resolution is separately persisted and may include outcomes such as:

```text
ACCEPT_AS_IS
ACCEPT_WITH_FOLLOWUP
REVISE_CHANGE
REVISE_ARCHITECTURE_ARTIFACT
ROUTE_TO_SPECIALIST
REJECT_CHANGE
```

The exact BTN-8 resolution vocabulary should remain centralized rather than duplicated here; BTN-112 only requires that significance evidence and its disposition be inspectably linked.

---

## Relationship to BTN-108 typed workflow contracts

Significance evidence should travel as an explicit output/reference in typed workflow contracts, not by giving the producing model broader mutation rights over Run state.

RFC-0015 already anticipates this in `ImplementationResult v1` through `significance/escalation evidence where applicable`.

A representative flow is:

```text
Driver/model output
  -> candidate ImplementationResult
  -> Battalion output validation
  -> persisted SignificanceSignal / SteelmanAssessment refs
  -> canonical ImplementationResult references those artifacts
  -> receiving boundary assembled from authoritative refs
```

A model can propose signal content inside its allowed output contract. Battalion validates, canonicalizes, persists, and routes it.

Deterministic detectors may attach signals outside model output entirely.

---

## Signal aggregation and deduplication

One candidate change may trigger several detectors for the same underlying boundary change.

Battalion should preserve raw detector evidence while presenting a bounded aggregate view to policy and humans.

The v1 rule should be conservative:

- signals are immutable evidence records;
- exact duplicate detector emissions may be mechanically deduplicated by stable identity/digest;
- related non-identical signals may be grouped by candidate change and affected boundary for display/policy convenience;
- grouping must not erase source provenance or independently triggered significance classes;
- lower-confidence model observations cannot suppress deterministic or policy-derived signals.

Policy should normally match against the union of validated signal classes for the candidate.

---

## Trivial-change bypass

Battalion should not infer significance merely from change size, model uncertainty, or the fact that an Architect exists.

A local change bypasses significance review when:

- no deterministic significance detector fires;
- no admitted project tripwire fires;
- no valid model-observed signal is produced;
- no separate workflow/review policy requires architectural review.

A one-line change may still be significant if it changes a public contract or fires a project tripwire. A large internal refactor may remain non-significant if it preserves declared architecture/invariants and policy does not classify it otherwise.

The relevant property is boundary impact, not line count.

---

## Model suppression and self-resolution

Executing models do not own significance lifecycle state.

They must be unable to:

- delete a deterministic/policy signal;
- mark a signal "resolved";
- forge human Architect disposition;
- replace a required `HUMAN_INTERRUPT` with a self-selected continue action;
- omit a required signal merely because tests pass;
- rewrite admitted project significance policy;
- mutate a steelman after human disposition to make the historical decision appear better supported.

Battalion/application code owns validation, persistence, routing, interrupt state, and disposition linkage.

---

## Inspection/UI requirements

A Run/change inspection surface should be able to answer without parsing chat:

```text
Why was this change considered significant?
Which class(es) triggered?
Which detector/policy/model observation produced each signal?
What exact artifacts/components/boundaries were affected?
What compatibility consequences were identified?
What was the strongest case against landing it?
Which dependencies/consumers might be affected?
What lower-blast-radius alternatives were considered?
What policy route was selected?
What did the authorized human/specialist decide?
```

Signal evidence, steelman evidence, policy decision, and human disposition should remain visibly distinct.

---

## Persistence and provenance

RFC-0023 applies directly.

`SignificanceSignal`, `CompatibilityAssessment`, and `SteelmanAssessment` are Battalion-produced/normalized evidence artifacts. They retain source and derivation references; their provenance does not itself grant authority.

A human Architect decision becomes authority-bearing only through the admitted human-decision/HumanInterrupt operation. Human-authored text inside a steelman or chat transcript is not equivalent to that decision.

Where a signal derives from repository policy or deterministic tooling, the signal should retain the exact policy/detector identity/version and bounded source evidence needed to explain the trigger later.

---

## Versioning and compatibility

The signal, compatibility, and steelman contracts should use stable Battalion-owned names/versions consistent with RFC-0015.

Breaking semantic changes require a new contract version. Adding a new significance class should be treated carefully because old policy evaluators may not know how to route it.

The safest default is fail-closed admission:

- a workflow/policy declares the significance contract versions and classes it understands;
- an unsupported newer class/version does not silently become "not significant";
- explicit compatibility adapters may normalize known old forms while preserving original evidence and adapter provenance.

## Testing strategy

Implementation should cover at least:

- deterministic public-interface signal;
- cross-component invariant signal;
- architecture-boundary signal;
- ownership-boundary signal;
- schema/data-model signal;
- security-sensitive signal;
- configured project tripwire;
- model-observed signal with sufficient evidence;
- rejection of unsupported/speculative model-observed signals;
- trivial/local change bypass;
- passing tests plus independently triggered significance signal;
- compatibility assessment with supported/breaking/unknown dimensions;
- required steelman generation for Architect-interrupting path;
- policy route to specialist rather than Architect where configured;
- explicit policy no-extra-action for a permitted tripwire;
- signal propagation across typed workflow contract boundaries;
- executing model attempt to suppress deterministic signal;
- executing model attempt to forge disposition/self-resolve interrupt;
- duplicate/related signal aggregation without provenance loss;
- unsupported signal contract/class failing closed at admission.

## Alternatives considered

### A. Prompt-only "architectural significance check" — rejected

Simple initially, but not versioned, mechanically inspectable, reliably testable, or consistently routable. It also makes architectural escalation depend too heavily on whichever model happened to execute the change.

### B. Hard-coded pre-commit interrupt — rejected

This copies the useful shape of Gator too literally. Significance can be detected during implementation, review, boundary validation, or other Run kinds, and not every significant event should route identically. Battalion needs a runtime/policy primitive rather than one Git-hook ceremony.

### C. Treat significance as a Review finding only — rejected

Review can discover significance, but significance is not necessarily a defect. A fully correct public API change may require architectural judgment without constituting a review failure.

### D. Treat significance as a BTN-109 failure class — not preferred

This permits reuse of routing mechanics but misstates the domain: a successful implementation can be significant. Prefer extending the normalized policy-trigger layer so failure remains one trigger family and significance another.

### E. Always interrupt on every significance signal — rejected

Some projects may route security-sensitive changes through specialist review first, or configure informational tripwires that remain durable evidence without a human stop. The signal should be first-class while disposition remains admitted policy.

## Open questions

1. **Should every model-observed significance signal require an independent Reviewer/deterministic corroboration before it can force an Architect interrupt, or should admitted project policy be able to let one sufficiently structured model observation trigger the interrupt directly?**

2. **Should `ARCHITECTURE_BOUNDARY_CROSSING` and `OWNERSHIP_BOUNDARY_CROSSING` remain separate stable classes?** They often overlap, but ownership can be organizational without being architectural, and architecture boundaries can exist without explicit ownership metadata.

3. **Where should the project tripwire configuration live?** The architectural requirement is that it be versioned/admitted project policy rather than model prompt text; the exact file/artifact may belong with the broader project policy surface.

4. **Should the steelman be produced by the same execution that triggered significance, or should Architect-interrupting policy normally invoke an independent read-only steelman capability to reduce self-justification bias?** The ticket says the producing execution must provide it, but Battalion can satisfy that either as a bounded output obligation or by a dedicated immediately-following capability over the exact candidate.

5. **Should compatibility assessment be mandatory for every Architect-interrupting signal, or only for significance classes/policies where compatibility is meaningful?** The current proposal makes it conditional but structured when present.

6. **Does RFC-0018's `FailureEscalationPolicy` name need to broaden as part of BTN-112 implementation?** Its accepted semantics already include non-failure ambiguity and policy triggers, but first-class significance makes the mismatch in the name more visible.

---

## Proposed decision

Adopt `SignificanceSignal` as a first-class Battalion evidence contract and significance as a first-class normalized policy trigger family.

Keep four layers mechanically distinct:

```text
SignificanceSignal / CompatibilityAssessment
    = what boundary appears to have been crossed and why

SteelmanAssessment
    = strongest bounded case against the exact candidate

admitted escalation/workflow policy
    = what process is required because of that evidence

human/specialist disposition
    = authority-bearing decision about what happens next
```

This preserves Battalion's human-directed architecture model while making architectural escalation inspectable, testable, configurable, and independent of any one model's prompt intuition.
