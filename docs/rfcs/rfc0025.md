# RFC-0025 — Architectural Significance Signals and Steelman Interrupts

**Status:** Proposed  
**Date:** 2026-09-06  
**Ticket:** BTN-112  
**Author:** Architecture  
**Target:** Post-v2 workflow orchestration  
**Related:** `philosophy.md`, BTN-8, BTN-108, BTN-109, RFC-0008, RFC-0014, RFC-0015, RFC-0018, RFC-0023

---

## Summary

Battalion should make architectural significance first-class evidence.

A change can be correct, tested, and mechanically valid while still crossing a boundary that needs architectural judgment. Battalion must detect and preserve that fact separately from test results and implementation success.

Deterministic analysis and admitted project policy may produce validated `SignificanceSignal` records directly. A model may instead produce a structured significance observation. Battalion presents that observation at a HumanInterrupt so the human can confirm or reject significance before it can cause architectural escalation.

Validated significance enters `EscalationPolicy`. The signal does not grant permission and does not choose its own route.

When policy requires Architect review, Battalion also requires a bounded `SteelmanAssessment`. A steelman is the strongest credible case against the proposed change, rather than a weakened strawman. It uses deterministic, measured, and semantic evidence. It is evidence, not the Architect decision.

```text
candidate change
    |
    |-------------------------------|
    v                               v
deterministic/project signal   structured model observation
    |                               |
    v                               v
validated SignificanceSignal   HumanInterrupt: significant?
    |                               | yes
    |<------------------------------|
    |                               | no -> retain rejected observation
    v
CompatibilityAssessment when required
    |
    v
EscalationPolicy
    |-------------------|-------------------|
    v                   v                   v
Architect review      specialist review   no extra action
    |
    v
SteelmanAssessment
    |
    v
human architectural disposition
```

## Problem

Battalion already checks correctness inside an admitted implementation boundary. It has TDD checkpoints, deterministic gates, typed workflow contracts, review evidence, authorization, write scope, and escalation policy.

Those mechanisms do not answer this question:

> Did a locally correct change alter a boundary whose blast radius exceeds the producing execution's authority?

Examples include:

- a public API change with passing local tests;
- a shared invariant change;
- a responsibility move across an architecture or ownership boundary;
- a schema or data-model change that requires migration;
- a security-sensitive change that does not violate an existing deterministic rule;
- a project-defined architectural tripwire.

Do not solve this only with prompt prose. Do not add a separate hard-coded pause mechanism. Represent significance as typed evidence and route it through Battalion policy.

## Goals

- Define a versioned `SignificanceSignal` contract.
- Keep it independent of provider, model, language, and role.
- Support deterministic, project-policy, and structured model-observed evidence.
- Preserve affected scope and provenance.
- Keep significance confirmation, routing, and architectural disposition separate.
- Generalize BTN-109 escalation mechanics without calling significance a failure.
- Carry signal references through BTN-108 typed workflow contracts.
- Require a steelman when policy requires Architect review.
- Prefer deterministic and measured steelman evidence when available.
- Apply model-diversity evidence when a model contributes to the steelman.
- Make compatibility and blast radius inspectable.
- Prevent passing tests from suppressing significance.
- Let local changes bypass architecture review when no significance rule fires.
- Prevent a model from suppressing or resolving required significance evidence.

## Non-goals

- Give models architecture approval authority.
- Let a model observation directly force Architect review.
- Interrupt on every change.
- Replace review, security checks, tests, or authorization.
- Treat model confidence as authority.
- Store chain-of-thought as steelman evidence.
- Require deterministic detection for every concern.
- Infer organization structure from repository layout alone.
- Let a signal choose the next workflow action.
- Let project tripwires broaden execution authority.
- Create a new Steelman role.

## Design

### Significance is evidence

A `SignificanceSignal` says that a candidate crossed a named boundary for concrete reasons.

It does not say that execution may continue. It does not approve architecture. It does not select a role or workflow.

Battalion policy owns routing. Human authority owns architectural disposition.

### Detection, confirmation, and disposition are separate

Validated significance can come directly from:

- deterministic repository analysis;
- admitted project policy;
- a later deterministic review or boundary-validation step.

A model observation is different. It is a candidate significance claim until a human confirms it.

A structured model observation must identify:

- the boundary or invariant;
- affected artifacts;
- a concrete before/after claim;
- supporting evidence references;
- why the effect is non-local.

Reject unsupported statements such as "this feels architectural."

Present a valid model observation through `HumanInterrupt`. The human decides whether the observation establishes significance. This is a significance-confirmation decision, not an Architect disposition.

If the human confirms it, Battalion creates or admits the corresponding `SignificanceSignal` and evaluates `EscalationPolicy`. If the human rejects it, retain the observation and rejection as evidence. This evidence can support UAT, evaluation, and the project's "both learn" feedback loop. It must not silently change policy or model behavior.

A confirmed model observation may later route to Architect review. That is a separate decision boundary.

### Tests do not prove insignificance

These facts can both be true:

```text
unit tests = pass
public interface = changed
```

The passing test result cannot erase the significance signal.

### Prefer deterministic evidence

Use deterministic detection when repository or tool evidence supports it. Use semantic model observation when syntax or measured evidence is insufficient.

Deterministic evidence has priority over a conflicting model claim. A model cannot suppress a deterministic or project-policy signal.

## `SignificanceSignal v1`

```text
SignificanceSignal v1
  signal_id
  schema_version
  significance_class
  trigger_source
    kind: deterministic | project_policy | confirmed_model_observation
    rule_id / detector_id / observation_id
  subject
    project_id
    repository/workspace identity
    change/revision identity
  affected_scope[]
  evidence_refs[]
  producer
    run_id
    workflow_kind
    stage/node/execution_id?
    actor_id?
    role/model provenance?
  compatibility_assessment_ref?
  created_at
```

Use references to evidence. Do not copy unrestricted Run state into the signal.

Initial classes:

```text
PUBLIC_INTERFACE_CHANGE
CROSS_COMPONENT_INVARIANT_CHANGE
ARCHITECTURE_BOUNDARY_CROSSING
OWNERSHIP_BOUNDARY_CROSSING
SCHEMA_OR_DATA_MODEL_CHANGE
SECURITY_SENSITIVE_CHANGE
PROJECT_TRIPWIRE
```

Keep `ARCHITECTURE_BOUNDARY_CROSSING` and `OWNERSHIP_BOUNDARY_CROSSING` separate. They may co-occur. Architecture boundaries describe technical or governing structure. Ownership boundaries describe responsibility, coordination, or authority. Policy may route them together without erasing that distinction.

`PROJECT_TRIPWIRE` must retain the configured tripwire identity and evidence.

## Trigger sources

### Deterministic analysis

Possible detectors include:

- public API or exported-symbol diffs;
- schema, DDL, or migration diffs;
- dependency or module-boundary changes;
- configured security-sensitive paths;
- ownership metadata;
- configured path, annotation, manifest, or policy tripwires.

Record the detector or rule version and the evidence that fired it.

### Project policy

Battalion should provide a project-owned configuration and policy surface for Battalion-specific project behavior. Project significance tripwires belong in that surface as admitted, versioned, inspectable policy. The exact file or directory layout is outside BTN-112.

Do not hide executable policy in model prompt text.

RFC-0008 Cartography may project relevant tripwires into cross-cutting charter documentation. That projection helps humans and models understand the project. Generated documentation is not the canonical policy source.

A project tripwire can make a local change significant. It cannot grant permission to bypass review.

### Model observation

Allow model observation for semantic boundaries that deterministic tools cannot reliably detect. Treat the observation as evidence, not authority.

A model observation cannot directly force Architect review. A sufficiently structured observation triggers a HumanInterrupt for significance confirmation. Only a confirmed observation becomes validated significance that can enter `EscalationPolicy`.

## Compatibility assessment

Require a structured `CompatibilityAssessment` for deterministic significance controls. This includes deterministic detectors and deterministic evaluation of admitted project tripwires.

For model observations, require the assessment after the human confirms significance when policy or the significance class makes compatibility relevant. Policy may also require it for any other route.

```text
CompatibilityAssessment v1
  assessment_id
  signal_refs[]
  compatibility_dimensions[]
    source compatibility
    binary/runtime compatibility
    data compatibility
    protocol compatibility
    migration compatibility
    operational compatibility
  known_consumers_or_dependencies[]
  affected_versions/environments[]
  migration_or_rollout_requirements[]
  unknowns[]
  evidence_refs[]
  producer provenance
```

Each dimension must be explicit: `not_applicable`, `supported`, `breaking`, or `unknown`.

A deterministic significance signal must not omit the assessment because a dimension appears irrelevant. Mark that dimension `not_applicable` instead.

## Steelman capability and assessment

When admitted policy requires Architect review, require a durable `SteelmanAssessment` before the human architectural decision boundary.

Steelman is a capability, not a new Battalion role. It is a bounded adversarial assessment over the exact candidate change and available evidence. Its purpose is to enforce the Ponytail principle: challenge the proposed solution with the strongest credible opposing case before the human accepts it.

The capability is evidence-first, not model-first. Use deterministic or measured counter-evidence when available. Examples include:

- benchmark or latency regressions;
- resource-use changes;
- dependency fan-out;
- API-surface growth;
- schema or migration burden;
- complexity deltas;
- new cross-boundary edges;
- compatibility breaks;
- Tactician-style bounded complexity or scope signals;
- project-policy tripwires.

A measured regression is stronger evidence than a model prediction of the same regression. A model may interpret the measurement, identify missing risks, or propose alternatives. It must not replace stronger deterministic evidence with speculation.

A policy may consider deterministic or measured evidence sufficient to satisfy its steelman requirement. In that case, an additional model invocation is optional unless policy requires semantic adversarial review.

When a model contributes to the steelman, prefer an independent read-only invocation over the immutable candidate and evidence. Apply Battalion's resolved model-identity and diversity evidence. The steelman model should differ from the producing model when admitted diversity policy requires or prefers it. If Battalion cannot establish the requested diversity, record that limitation. Do not claim independent challenge without supporting identity evidence.

Failure to establish model diversity does not by itself fail the change unless admitted policy requires diversity. Deterministic evidence remains valid regardless of model availability.

If the workflow cannot produce the required steelman because required evidence is missing, make that absence explicit interrupt evidence.

```text
SteelmanAssessment v1
  steelman_id
  signal_refs[]
  candidate_change_ref
  deterministic_or_measured_findings[]
  semantic_findings[]
  strongest_counterarguments[]
  likely_consumers_or_dependencies_affected[]
  blast_radius
  compatibility_or_migration_concerns[]
  secondary_effects[]
  lower_blast_radius_alternatives[]
  evidence_refs[]
  limitations_or_unknowns[]
  producing capability provenance
  model_diversity_evidence?
```

The steelman should answer:

- What is the strongest reason not to land the change as-is?
- What deterministic or measured evidence supports that case?
- Who or what can break despite local correctness?
- Which compatibility obligations change?
- What migration, rollout, coordination, or documentation work follows?
- What secondary operational, security, performance, or maintenance effects are plausible?
- Is there a credible lower-blast-radius alternative?

Do not invent an alternative when none is credible. Record the evidence and limitation instead.

The steelman is immutable review evidence. It is not the Architect decision.

## `EscalationPolicy` and BTN-109

Generalize RFC-0018's `FailureEscalationPolicy` to `EscalationPolicy`.

Failure remains one trigger family. Significance, blocked or escalated outcomes, bounded ambiguity, and future admitted triggers may use the same policy mechanism. This avoids parallel routing systems.

RFC-0018 remains the historical accepted decision for failure and recovery policy. BTN-112 broadens that mechanism and introduces the new name. Implementation must preserve or migrate existing `FailureEscalationPolicy` contracts explicitly rather than silently changing their meaning.

Do not add a significance-specific pause state.

```text
validated SignificanceSignal
    -> normalized significance trigger
    -> admitted EscalationPolicy
    -> HUMAN_INTERRUPT | specialist workflow | explicit no-extra-action
```

Do not force significance into `failure_class`. A successful implementation can still be significant.

Policy admission must reject a configuration that lets an executing model suppress a mandatory trigger or grant itself a more permissive route.

## BTN-8 HumanInterrupt

BTN-8 remains the durable human decision mechanism.

There are two distinct significance-related human boundaries.

First, a structured model observation uses a HumanInterrupt to ask whether the claimed significance is real. This interrupt does not require Architect authority merely because a model raised the observation.

Second, a validated significance signal may cause `EscalationPolicy` to require an Architect or other authorized human disposition.

A significance-confirmation interrupt should reference:

```text
interrupt kind: SIGNIFICANCE_CONFIRMATION
observation ref
claimed significance class
supporting evidence refs[]
allowed resolutions: confirm | reject
```

An architectural significance interrupt should reference:

```text
interrupt kind: ARCHITECTURAL_SIGNIFICANCE
signal refs[]
steelman ref?
compatibility assessment ref?
required authority
allowed resolutions[]
```

Keep the exact architectural resolution vocabulary centralized with BTN-8. BTN-112 only requires inspectable links between significance evidence and disposition.

## BTN-108 workflow contracts

Carry significance evidence through explicit typed outputs or references. Do not give producing models broader mutation rights over Run state.

RFC-0015 already anticipates significance and escalation evidence in `ImplementationResult v1`.

```text
model result
  -> Battalion validation
  -> candidate observation or persisted significance evidence
  -> human confirmation when observation is model-derived
  -> canonical typed result references admitted evidence
  -> next boundary receives authoritative references
```

Deterministic detectors may attach signals without model output.

## Aggregation

Keep signal and observation records immutable.

Deduplicate exact duplicate emissions by stable identity or digest. Group related records for display or policy evaluation when useful. Do not erase source provenance or independent classes.

A model observation cannot suppress a deterministic or project-policy signal.

Policy should normally evaluate the union of validated significance classes for the candidate. Unconfirmed model observations are not part of that union.

## Trivial-change bypass

Do not infer significance from line count or model uncertainty.

Bypass architectural significance review when:

- no deterministic detector fires;
- no project tripwire fires;
- no model observation is confirmed;
- no other admitted policy requires architecture review.

A valid structured model observation still requires its bounded HumanInterrupt even if the human later rejects significance.

A one-line public-contract change can be significant. A large internal refactor can be non-significant.

## Model suppression and self-resolution

A model must not be able to:

- delete deterministic or project-policy signals;
- promote its own observation to validated significance;
- mark a signal resolved;
- forge a human confirmation or architectural disposition;
- replace a required `HUMAN_INTERRUPT` with continue;
- omit a required signal because tests pass;
- rewrite admitted significance policy;
- mutate a steelman after disposition;
- claim model diversity without resolved identity evidence.

Battalion application code owns validation, persistence, routing, interrupt state, and disposition linkage.

## Inspection requirements

Inspection must answer:

- Why is this change significant or suspected to be significant?
- Which classes fired or were claimed?
- What produced each signal or observation?
- Did a human confirm or reject a model observation?
- Which artifacts or boundaries are affected?
- What compatibility effects were found?
- What deterministic or measured counter-evidence exists?
- What is the strongest case against the change?
- Which consumers may be affected?
- Which lower-blast-radius alternatives were considered?
- Was a model used for steelman, and was diversity established?
- Which route did policy select?
- What did the authorized human or specialist decide?

Show observations, validated signals, compatibility evidence, steelman evidence, policy routing, and human dispositions as separate records.

## Persistence and provenance

RFC-0023 applies.

`SignificanceSignal`, model significance observations, `CompatibilityAssessment`, and `SteelmanAssessment` are evidence artifacts. Provenance does not grant authority.

A human significance-confirmation record admits or rejects a model observation. It does not itself approve the architecture.

Only an admitted human-decision or HumanInterrupt operation can create the authority-bearing Architect decision.

Retain exact project-policy and detector identity/version where they contribute to a signal. Retain model identity/diversity evidence when a model contributes to a steelman.

## Versioning

Use stable Battalion-owned contract names and versions under RFC-0015.

Fail closed when a workflow or policy encounters an unsupported significance contract version or class. Do not silently interpret an unknown class as insignificant.

Compatibility adapters may normalize known older forms. Preserve original evidence and adapter provenance.

The `FailureEscalationPolicy` to `EscalationPolicy` transition requires an explicit compatibility or migration path.

## Validation

Implementation must test:

- each initial deterministic significance class;
- architecture and ownership classes independently and together;
- project tripwires from admitted project configuration;
- valid and invalid model observations;
- model observation HumanInterrupt confirmation and rejection;
- rejected observations retained as evidence;
- model observations unable to directly force Architect review;
- trivial-change bypass;
- passing tests plus a significance signal;
- mandatory compatibility assessment for deterministic controls;
- explicit `not_applicable` compatibility states;
- deterministic and measured steelman evidence;
- model-assisted steelman generation;
- model diversity evidence and unavailable-diversity behavior;
- policy satisfied without a model when deterministic steelman evidence is sufficient;
- specialist routing;
- explicit policy no-extra-action;
- typed contract propagation;
- model suppression and forged disposition attempts;
- aggregation without provenance loss;
- `FailureEscalationPolicy` migration or compatibility;
- unsupported contract versions/classes failing closed.

## Alternatives rejected

**Prompt-only significance check:** not versioned or mechanically routable.

**Hard-coded pre-commit interrupt:** creates a parallel ceremony and misses other detection points.

**Review finding only:** significance is not necessarily a defect.

**Significance as a failure class:** misstates the domain because successful work can be significant.

**Model observation directly triggers Architect:** gives a semantic model claim too much routing authority and removes the human learning boundary.

**Model-only steelman:** ignores stronger deterministic and measured evidence and makes adversarial review depend unnecessarily on inference.

**Always interrupt Architect:** prevents admitted specialist and informational routes.

## Decision

Adopt `SignificanceSignal` as a first-class evidence contract and significance as a first-class `EscalationPolicy` trigger family.

Adopt these rules:

1. Deterministic and admitted project-policy controls may establish significance directly.
2. A structured model observation requires a HumanInterrupt before it becomes validated significance.
3. Keep architecture-boundary and ownership-boundary classes separate.
4. Store project tripwires in a project-owned Battalion configuration/policy surface. Allow Cartography to project them into cross-cutting documentation.
5. Require compatibility assessment for deterministic significance controls.
6. Make Steelman a read-only capability that prefers deterministic and measured evidence and may use an independent model for semantic adversarial review.
7. Apply resolved model identity and diversity evidence when a model contributes to Steelman.
8. Generalize RFC-0018 `FailureEscalationPolicy` to `EscalationPolicy` with explicit compatibility or migration.

Keep these layers separate:

```text
model significance observation
    = unconfirmed semantic evidence

SignificanceSignal / CompatibilityAssessment
    = validated boundary-impact evidence

SteelmanAssessment
    = strongest bounded case against the candidate

EscalationPolicy
    = required process

human significance confirmation
    = admission/rejection of model-observed significance

human/specialist architectural disposition
    = authority-bearing decision
```

This preserves human-directed architecture while making architectural escalation inspectable, testable, configurable, and independent of one model's prompt intuition. It also creates an explicit learning boundary when Battalion sees architectural significance that the human did not initially see.
